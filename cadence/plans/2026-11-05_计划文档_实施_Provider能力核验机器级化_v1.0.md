# 计划文档：实施 · Provider 能力核验机器级化（核验只核验一次，机器一份事实）

> **给实施 worker：** 必用 `subagent-driven-development`（推荐）或 `executing-plans` 逐 Task 执行本计划。步骤用 checkbox 语法跟踪。

**目标：** 把 provider 能力核验记录从「按项目/逻辑代码库区分」改成「机器级一份事实」—— 核验只核验一次；「Provider 管理」入口不再要求选中项目；capability 面不再按项目/逻辑代码库定位。

**架构：** capability 记录与探针证据从 `.aria/projects/{p}/...` 移到 `.aria/provider-capabilities/`；`ProviderCapabilityStore` 与 `ProviderCapabilityRevalidateService` 的 API 去掉 `project_id`；HTTP 面改为 `/api/providers/capabilities*` 四条机器级路由（旧四条删除、不留 shim）；前端能力卡/面板去掉两个 id props。root-recipe 相位的 per-LC 凭据重核验通道**原样不动**。

**技术栈：** Rust（edition 2024，工具链见 `rust-toolchain.toml`）+ axum + React/TS + Vite + Vitest + Tailwind。

**规格（实施前必读，Plan 只展开它、不改它）：**

## 全局约束（每条 Task 隐含包含）

- 🔴 **cargo 必须串行**：`flock /tmp/aria-cargo.lock cargo ...`（否则与其它进程抢 target 目录）
- 🔴 **禁止触碰** `/tmp/aria-verify`（owner 共享验收实例）、`/tmp/aria-accept`（掩码测试台）；测试产物只落 `/tmp`（`tempfile::tempdir()`）
- 🔴 **行数门禁**：`tests/it_core/large_file_guard.rs` —— `src`/`tests`/`web/src` 下超 1200 行的文件必须在 `GRANDFATHERED` 登记且**登记值不得再涨**；新增文件 < 1200 行
- 🔴 **TDD**：每个 Task 先写失败测试并跑出失败，再实现到绿
- 🔴 **只改作用域，不改期望值**：MUST NOT 删用例、MUST NOT 加 `ignore`、MUST NOT 放宽断言强度
- 🔴 **不扩大范围**：不重构 capability 记录结构（版本钉定/三态/`record_verified_probe` 导入语义一律不动）、不动 provider 优先级、不动安装机制、不动「不点击不运行探针」契约
- 提交只暂存本 Task 明确的文件；**禁 `git add -A`**、禁 `reset --hard`/`clean -f`/强推、禁 `--no-verify`
- 分支 `bugfix-b-11-02`；MUST NOT 在 `main` 上提交

## 审查焦点（规格暗示但没有任务覆盖、最容易咬人的五类）

1. **无项目时打开面板** —— 用户在一个都没有项目的工作区点「Provider 管理」，必须能打开并看到机器级事实（不得置灰、不得空白）
2. **旧作用域残留** —— 项目目录/LC 子树下若仍出现 `capabilities.json`，即为第二作用域（能力面历史包袱重演）
3. **重复读路径** —— 代码里若出现「机器级没有就回退找项目级/LC 级旧记录」的分支，即为半改状态
4. **root-recipe 判定漂移** —— 拆掉 per-LC 字段前后，同一逻辑代码库的 root-recipe 准入结论必须**完全一致**（不得出现「拆前拒绝、拆后放行」）
5. **作业归属** —— 批量核验作业不得再绑定项目/逻辑代码库，也不得因为读作业时携带了旧 id 而 404

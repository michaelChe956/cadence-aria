# WorkItem 单候选计划事务重构 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 workitem 段从「多阶段对话状态机」重构为「单候选计划事务」：markdown 编译器模型 + 中央策略层 + 唯一对话流式人工门，消除死循环、提升速度与弱模型成功率。

**Architecture:** 人和 LLM 只读写 `work-item-plan.md`（EARS 句式 markdown）；确定性编译器单向编译为 typed IR（复用 `CanonicalWorkItemContract`/`VerificationPlan`），IR 携带 source hash + compiler version；中央策略层将评估结果归入四类 typed outcome 并裁决状态跳转；现有三层 validator、原子 compile 事务、coding engine 全部复用不动。

**Tech Stack:** Rust（backend）、TypeScript/React（web）、Node .mjs（campaign driver）

**Spec:** `openspec/changes/rearch-workitem-plan-pipeline/`（proposal.md / design.md / specs/work-item-plan-single-candidate/spec.md / tasks.md——本计划实现该 spec，执行者必须同时阅读）

## Global Constraints

- cargo 命令禁止 `-j` 参数；定向测试必带 `--lib`（如 `cargo test --lib work_item_plan_policy`）
- 文件行数红线 1200 行（含 web），large_file_guard 守门

- 不修改：`work_item_split_validator` 校验规则语义、`workspace_engine/compile.rs` 事务逻辑、coding engine/WS、story/design 段
- 失败关闭原则：未知协议消息、未知 finding 类别一律记录后终止，不发明恢复策略

```rust
pub enum PlanOutcome {
    Valid { advisories: Vec<ClassifiedFinding> },
    Repairable { findings: Vec<ClassifiedFinding> },   // 触发唯一一次聚合返修
    HumanRequired { findings: Vec<ClassifiedFinding> }, // 唯一人工门
    Fatal { reason: String, diagnostics: Vec<ClassifiedFinding> },
}

pub struct RunHistory {
    pub seen_fingerprints: Vec<FindingFingerprint>,
    pub repairs_used: u32,
    pub transitions_used: u32,
}

pub fn evaluate(
    mechanical_errors: Vec<ClassifiedFinding>,   // 来自 validator/linter，class 恒 MechanicalError
    review: Option<&ReviewVerdict>,               // reviewer 输出（已按 D3 重校准）
    history: &RunHistory,
    budgets: &RunBudgets,
) -> PlanOutcome;
```

裁决规则（顺序敏感，必须按序实现）：
1. `transitions_used >= max_transitions` → `Fatal("transition_budget_exhausted")`
2. 任一 finding 的指纹 ∈ `history.seen_fingerprints` → `Fatal("repeated_finding_fingerprint")`（含该 finding）
3. `mechanical_errors` 非空或 review 含 Repairable 类 finding：若 `repairs_used >= max_repairs` → `Fatal("repair_budget_exhausted")`，否则 → `Repairable`
4. review 含 HumanRequired 类 finding → `HumanRequired`
5. 否则 → `Valid`（Advisory 类随结果携带）

- [ ] **Step 1: 写失败测试**（5 条裁决规则各一个测试 + 优先级冲突测试：同时含 Repairable 与 HumanRequired 时 Repairable 优先，因为规则 3 先于 4）


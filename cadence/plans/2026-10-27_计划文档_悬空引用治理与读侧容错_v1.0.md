# 悬空引用治理与读侧容错 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为「已删实体留下的旁支/记账类悬空引用」交付三层治理能力——① 读侧只对旁支引用容错（跳过该条目并告警，主记录缺失语义与真实错误一律不变）；② 全量巡检先只报不改（**无法完成判定**——读取失败**或**所需存在性数据源 / 作用域不可用——隔离为「不可判定」）；③ 按类型幂等销账（证据分级 + 留痕 + 清理后自证归零）。

**Architecture:** 全部新逻辑落在新目录 `src/product/dangling_reference/`：判定能力（按字段名的静态判据表 + 九类目标存在性核对 + L1/L2 证据分级）→ ①层四个容错列举只读 API（包装既有只读 API，既有读路径零改动）→ ②层五分区巡检遍历器（纯只读，无删除分支）+ 清单渲染与 findings 摘要令牌 → ③层按类型销账（三道闸 + 白名单 + intent 四前置条件 + 窗口簇按 attempt 聚合）+ 状态根下单一批追加式 JSONL 台账。既有文件只碰三处极小胶水：`src/product/mod.rs`（+1 行模块声明）、`src/product/app_paths.rs`（+约 8 行台账路径）、`src/cli.rs`（+约 15 行巡检/清理子命令）。

**Tech Stack:** Rust（`std::fs`、`std::path`、`std::collections::BTreeSet`）、serde_json、chrono（UTC 时间戳）、sha2 + hex（复用既有 `sha256_hex`，不新增依赖）；测试用 `tempfile`（仅 dev-dependencies）；不引入 `regex`。

**Spec:** `openspec/changes/add-dangling-reference-governance/`（proposal.md / design.md / specs/dangling-reference-governance/spec.md / tasks.md）与 `cadence/designs/2026-10-27_技术方案_悬空引用治理与读侧容错_v1.0.md`

## Global Constraints

- 只吞「目标已删」这一种错：JSON 解析失败 / schema 不符 / IO 失败 / 权限错误一律照旧上抛，MUST NOT 被降级为「跳过该条目」（REQ-DRG-05）。
- 主记录缺失语义一律不变：既有 `story_spec_not_found` 等错误码与文案逐字不动，既有测试不得变；主记录缺失 MUST NOT 被降级为「跳过并告警」（REQ-DRG-04）。
- 只对旁支/记账类引用容错。既有 fail-closed 读路径一律不接入容错：窗口租约列举（`src/product/reviewer_window_store.rs:1129`）、reviewer 资源物理清理扫描（`src/product/reviewer_resource_purge.rs:53`）、台账按 owner 反查（`src/product/entity_operation_store.rs:400` 附近）、scope 准入与墓碑复核、intent 的版本化单条读（`src/product/issue_automation_store.rs:1201` / `:1242`）（REQ-DRG-06）。
- 实体删除墓碑永不删；用户业务数据（story / design / plan 正文、versions、artifact）永不删（REQ-DRG-19）。
- 未归类与降级类型（session / checkout / aggregate_index / logical_member / enrollment）一律只报不删；不删任何不具备 L1 证据、且不满足证据等级表中该类型 L2 专属可算条件的旁支记录（REQ-DRG-02 / 12 / 14 / 19）。
- 默认 dry-run：开启销账 MUST 同时提供 `--apply` 与巡检发现集合的摘要令牌；`--apply` 入口 MUST 在内部重跑巡检并重算摘要比对，不一致即拒绝、零删除、零留痕、退出码非零（REQ-DRG-13 / 22）。
- 幂等语义只用于重入，MUST NOT 替代 enrollment 文件锁语义：「缺失视为已清」MUST NOT 成为在锁外跳过判定的理由（REQ-DRG-15 / 20）。
- 销账后 MUST 再巡检一次自证归零；归零只统计销账白名单内且本次可删的类型；「只报不删残留」与「不可判定」各自单列且不参与归零断言；存在任一不可判定条目时 MUST NOT 宣称归零或治理完成（REQ-DRG-17 / 23）。
- 「不可判定」= **读取失败**（IO / 解析 / 权限）**或所需存在性数据源 / 作用域不可用**（存在性判 `Unknown`）；已判定为悬空但证据不足者归「只报不删残留」（REQ-DRG-02 / 11 / 23）。
- 存在性判定 MUST 为**三态**：`Exists`（明确命中）/ `Missing`（明确未命中）/ `Unknown`（无法判定）。判定面缺所需数据源或作用域时 MUST 报 `Unknown` 并归「不可判定」，MUST NOT 报 `Missing`；读失败 MUST 原样上抛，MUST NOT 退化为 `Missing`（REQ-DRG-01 / 21 / 23）。判 `Unknown` 的条目 MUST NOT 计入悬空条目数、MUST NOT 计入归零、MUST NOT 进入令牌的发现集合（REQ-DRG-17 / 22）。
- 证据等级表（销账白名单的单一事实源）逐行同 spec REQ-DRG-02 附表：`StorySpec`=L1、`DesignSpec`=L1、`Plan`=L1、`Session`=只报不删、`Attempt`=L2（专属条件 = 窗口四条件 W-1..W-4）、`Checkout`=只报不删、`AggregateIndex`=只报不删、`LogicalMember`=只报不删、`Enrollment`=只报不删（永不删）。
- L1 四条 MUST 同时成立：墓碑存在 + `phase == deleted` + `deleted_at` 有值 + 无 `{issue_root}/entity-operations/pending-failures/{kind}/{id}.json`；`purging` / 缺完成时间 / 带 pending failure 一律不算 L1，归「只报不删残留」。
- attempt 存在性 MUST 两路核对：路 1 coding attempt（`CodingAttemptStore::get_attempt_by_id`，`src/product/coding_attempt_store/attempt.rs:401`）、路 2 规划面 workspace session；任一路命中即判「仍在」，两路皆不命中才算不存在。路二 MUST 用「枚举」（遍历状态根下全部 project × issue 调 `LifecycleStore::list_workspace_sessions`，`src/product/lifecycle_store/workspace.rs:258`）建 id 集合，MUST NOT 用 `get_workspace_session`（读路径写回副作用）、MUST NOT 用 `find_workspace_session_path`（`pub(super)` 跨模块不可见）；路二枚举失败 MUST 归不可判定，MUST NOT 当成「目标不存在」（REQ-DRG-21）。
- 窗口簇删除 MUST 按 attempt 聚合：该 attempt 名下**全部**窗口（含 `window-archive` 中的归档窗口）都满足 W-1..W-4 才可把该 attempt id 交给物理清理器；任一不满足则一个都不删（W-1 终态 / W-2 无租约 / W-3 两路目标皆无 / W-4 worktree 已不存在）（REQ-DRG-12）。

## Review Focus

1. **活窗口被误判悬空并被物理删除**：规划面评审窗口把 workspace session id 写在 attempt 位上，只做单路核对必然 NotFound → 活窗口被判悬空并进入物理删除；且物理清理器按 attempt id 批量删（含归档窗口），同一 attempt 下只要有一窗不满足条件，就会把满足条件的窗口连坐删掉。必须两路核对 + 按 attempt 聚合全满足才删（Task 2 Step 1 的 `dangling_resolver_attempt_two_routes` / `dangling_window_l2_verdict_requires_all_four_conditions`、Task 7 Step 1 的 `dangling_window_cluster_is_grouped_by_attempt`）。
2. **intent 正常中间态被当悬空删掉补偿锚点**：`plan_id` / `session_id` 是预派生 id，plan 尚未创建时它们就已写在 intent 文件里，「引用目标不存在」是正常中间态而非已删证据；删掉 intent 文件 = 删掉补偿锚点 = 自动化链永久卡死（Task 7 Step 1 的 `dangling_intent_without_l1_evidence_is_report_only`、Task 7 Step 5 的六个前置夹具）。
3. **读取失败被当成「目标已删」→ 自证归零误报治理完成**：巡检里的读失败若被算成「未悬空」，悬空计数会自证归零，误报治理完成；巡检自身扫到的坏记录 / 不可读分区若被静默跳过，同样把「漏报」误算成「已归零」（Task 4 Step 1 的 `dangling_patrol_isolates_undetermined_entries`、Task 8 Step 5 的 `dangling_cleanup_undetermined_blocks_governance_complete`）。
4. **迁移期 `purging` 墓碑被当已删**：删除进行中的墓碑对应子树可能仍被重入清理，销账删掉其旁支记录会造成「级联重试漏清且无人察觉」；缺完成时间或带待人工处置删除失败事实的墓碑同理（Task 2 Step 1 的 `dangling_resolver_l1_requires_all_four_conditions`、Task 7 Step 5 的 `dangling_intent_four_preconditions_uses_lock_inner_evidence`）。
5. **巡检与销账并发时锁序 / 锁内重读不一致**：取代路径在 enrollment 文件锁内做「`metadata().is_ok()` → `remove_file()`」两步非原子；销账不取同一把锁或用锁外旧值判定，会让取代侧报 IO 失败，或在相位/证据已推进时误删（Task 7 Step 5 的 `dangling_intent_four_preconditions_uses_lock_inner_phase` / `dangling_intent_four_preconditions_uses_lock_inner_evidence`）。

2. `decide_intent_cleanup`：MUST 在 enrollment 文件锁内做全部判定 —— 用 `with_exclusive_lock(&enrollment_path, || { ... })`（锁文件由既有 `lock_path_for` 约定生成，即 `automation-enrollment.json.lock`），锁内重读三项：
   - **enrollment 状态**：读 `{issue_root}/automation-enrollment.json`（不存在 → 允许继续；存在且 `enabled == true` → 只报不删；存在且 `terminated_at` 有值且 `enrollment_id` 与 intent 一致 → 允许继续；`enrollment_id` 不一致 → 只报不删；`enabled == false` 且 `terminated_at` 为空 → 按「仍有活授权」只报不删）。
   - **generation intent 相位**：锁内读 `{issue_root}/automation-generation-intent.json` 的 `phase`；当被判定删除的记录**就是** generation intent 时，相位 MUST 为 `PlanGenerationPhase::Claimed`，否则只报不删；被判定删除的记录是 plan intent 时，相位不构成删除约束（依据技术方案 §2.4.3 实测结论：plan intent 可删、generation intent 因 `phase != Claimed` 只报不删）。
   - **L1 墓碑证据**：被引用的 story / design / plan 在**锁内重读**后仍满足 L1 四条；`session_id` / `enrollment_id` 的缺失 MUST NOT 构成依据。
   四项全通过 → `CleanupDecision::Delete { evidence_level: "L1", action: "delete_record", .. }`；任一不通过 → `CleanupDecision::ReportOnly { reason }`（reason MUST 指明未满足哪一条）。

struct DanglingReferenceOptions {

fn parse_dangling_reference_options(rest: &[String]) -> Result<DanglingReferenceOptions, CliError> {
    let mut apply = false;
    let mut confirm_token = None;
    let mut report_dir = None;
    let mut index = 0;
    while index < rest.len() {
        match rest[index].as_str() {
            "--apply" => apply = true,
            "--confirm" => {
                index += 1;
                let value = rest.get(index).ok_or_else(|| CliError {
                    code: "invalid_cli_args".to_string(),
                    message: "--confirm 需要一个令牌值".to_string(),
                })?;
                confirm_token = Some(value.clone());
            }
            "--report-dir" => {
                index += 1;
                let value = rest.get(index).ok_or_else(|| CliError {
                    code: "invalid_cli_args".to_string(),
                    message: "--report-dir 需要一个目录值".to_string(),
                })?;
                report_dir = Some(value.clone());
            }
            _ => {}
        }
        index += 1;
    }
    Ok(DanglingReferenceOptions { apply, confirm_token, report_dir })
}

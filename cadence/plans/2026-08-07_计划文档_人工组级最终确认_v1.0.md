# 人工组级最终确认 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development`（推荐）or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将新 Group Coding Attempt 的最终步骤从不稳定的 Internal Group Reviewer/shard/reduction Provider 链路改为“客观就绪快照 + 明确人工 Final Confirm”，并保留每个 Work Item 已完成的 Coder、独立 Code Review、Coder rework、Plan Repair 与终态一致性门禁。

**Architecture:** 在全部 Work Item 完成其独立审查之后，以权威 UnitRun、完整提交区间、Code Review、handoff 与 plan binding 建立并持久化不可变的 `GroupFinalReadinessSnapshot`。新 attempt 直接转入既有 `FinalConfirm`/`WaitingForHuman`，由用户读取快照并确认；Final Confirm 仍运行完成 binding、基于完整区间的范围检查和 shared worktree clean 检查。历史 shard/reduction 记录只读保留，恢复的旧 attempt 用同一快照转人工路径，绝不启动新 Provider。

**Tech Stack:** Rust 2024、Tokio、Serde、现有 JSON `CodingAttemptStore`、Axum WebSocket/REST、React、TypeScript、Zustand、Tailwind、Vitest。

## Global Constraints

- OpenSpec 权威来源：`openspec/changes/scalable-group-final-review/`；本计划逐项覆盖 `tasks.md` 的 1.1–3.3，不得引入新的 AI 汇总、语义 finding 或返修路径。
- **前置依赖：** `2026-08-07_计划文档_Coder提交与Provider自动重试_v1.0.md` 的 Task 1–8 已完成、通过全量验证，且 `start_commit..completion_commit` 的文件/commit 查询接口稳定。未满足时不得开始本计划的实现。
- 新 Group attempt 不得启动 `InternalPrReview`、Internal Group Reviewer、shard、reduction 或任何替代的自动语义审查 Provider；因而不得再出现 `reduction_output_invalid`、shard 输出无效或对应 retry gate。
- Readiness 是数据完整性检查，不是第三层代码审查：不得生成 finding、不得重新解释独立 Code Review verdict、不得创建 Coder rework、不得启动 Plan Repair、不得新增 `write_policy`/路径范围门禁。
- 每个 Work Item 的 Git 事实只能来自该 `CodingUnitRun.start_commit..completion_commit`；相等 SHA 是空观察区间，不能显示起始提交的父提交 diff。
- 完整 snapshot 才可启用人工 Final Confirm；不完整 snapshot 必须持久化精确诊断、保持未完成，且不可被确认操作绕过。
- 人工 Final Confirm 不免除既有终态检查：completion binding、完整区间范围校验、shared worktree clean 都继续执行；它们失败仍走确定性诊断/人工清理语义，不变成 Group Reviewer finding、Coder rework 或 Plan Repair。
- 不得自动 add、commit、删除范围外残留。即使 `node_modules` 等目录令 worktree dirty，也只显示证据并保留最终已有的人工清理动作；是否允许该目录只取决于具体 Work Item 的 `write_policy`。
- 历史 shard/reduction/InternalPrReview 工件不迁移、不删除、保持可读；恢复时身份不一致必须失败关闭并给出诊断，不能猜测映射关系。
- 先写失败测试，再写最小实现；Rust 定向快反馈统一使用 `cargo test --locked --lib <过滤名>`，绝不传 `-j 1`；前端只使用 `pnpm`。

以下类型是后续任务共用的固定接口边界：

```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct GroupFinalReadinessSnapshot {
    pub attempt_id: String,
    pub status: GroupFinalReadinessStatus,
    pub units: Vec<GroupFinalReadinessUnit>,
    pub diagnostics: Vec<GroupFinalReadinessDiagnostic>,
    pub created_at: String,
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct GroupFinalReadinessUnit {
    pub unit_id: String,
    pub logical_work_item_id: String,
    pub unit_run_id: String,
    pub start_commit: String,
    pub completion_commit: String,
    pub commit_shas: Vec<String>,
    pub diff_ref: String,
    pub code_review_report_id: String,
    pub review_verdict: ReviewVerdict,
    pub review_summary: String,
    pub review_findings: Vec<ReviewFinding>,
    pub review_raw_provider_output_ref: Option<String>,
    pub handoff_revision_id: String,
    pub plan_revision_id: String,
}
```

对于不完整证据，`units` 可以保留已解析字段，但 `diagnostics` 必须明确缺少或不一致的 record；不能填充伪 SHA、伪 report 或推测 handoff。实现时可在 `GroupFinalReadinessUnit` 的部分字段使用 `Option`，但 Web contract 必须能无歧义地展示 “缺失” 而不是空字符串冒充有效值。

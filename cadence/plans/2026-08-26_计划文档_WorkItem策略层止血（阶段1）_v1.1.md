# WorkItem 策略层止血（阶段 1）实施计划 v1.1

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在现有 JSON 生成路径上落地 typed finding 分类、中央策略层、终态矩阵、两阶段 review scope 与运行状态持久化，消除死循环，使每次 workitem 运行到达明确终态（completed / awaiting_human / stopped_needs_human / failed）。

**Architecture:** parser 保留 `ParsedReviewEnvelope.raw_verdict`，分类器只基于 raw verdict 翻成 `ClassifiedFinding`；中央评估器只消费分类结果、服务端生成的 review invocation scope、运行历史与预算，产出带 history delta/reservation 的 typed outcome；路由层在持久化后按策略分流。运行策略与 flow 种类在 session 创建时固定；待决人工门快照可断线恢复。`stopped_needs_human` 接管始终创建 interactive 新运行，原运行终态不可改写。

**Tech Stack:** Rust（backend）、Node .mjs（campaign driver）

**Spec:** `openspec/changes/workitem-typed-outcome-policy/`（proposal.md / design.md / specs/work-item-typed-outcome-policy/spec.md / tasks.md——执行者必须同时阅读；design.md 的 P1-D1~P1-D8 是精确语义来源）

```rust
        initial_revision_id: String,
```

- `ReviewFinding` 的领域形状新增 `category: Option<ReviewFindingCategory>`、`class_hint: Option<FindingClassHint>`、`contract_field: Option<String>`；历史数据缺字段为 `None`，且继续拒绝未知**字段名**。
- `parse_review_envelope` 是唯一 parser adapter：先把 JSON 解析为带 `Option<String>` 原始 category/class_hint 的 `RawReviewFinding`，再用显式转换器产生领域 `ReviewFinding`。`Option<Enum>` 的 serde 缺省行为只解决字段缺失、会把未知 variant 变成通用 serde 错误，**不足以**产生稳定诊断；不得直接依赖它。未知值必须分别返回 `UnknownFindingCategory(raw)` / `UnknownFindingClassHint(raw)`，字段类型错误返回 `InvalidFindingField`。
- 错误名称与映射唯一固定：`ReviewStructuredOutputError::UnknownFindingCategory`（parser）→ `ClassificationError::UnknownCategory` → `FatalReason::UnknownCategory` → diagnostic code `unknown_finding_category`；class_hint 对应唯一链路是 `UnknownFindingClassHint` → `ClassificationError::UnknownClassHint` → `FatalReason::UnknownClassHint` → `unknown_class_hint`。转换由显式 `From`/映射函数完成，绝不以“或对应协议错误”含混替代。所有链路都写入 durable `failed`，绝不进入 `HumanRequired`。
- 分类按 `raw_verdict`：合法 hint 优先；无 hint 时 needs_human→HumanRequired、pass+findings→Advisory、revise 且 contract_gap/self_contradiction + contract_field→Repairable、其余 revise→HumanRequired。Repairable 兜底要求 `contract_field` 去空白后非空。
- `Verification` scope 由服务端生成并和 invocation 一起持久化；prompt 仅从该 scope 构造。复评只校验原指纹是否重现，以及机械校验报告是否由该 invocation 重跑；**不**为 `ReviewFinding` 新增 path/region 字段，`ReviewInvocationScope` 也不以 `changed_paths` 做范围校验或作空字符串占位。缺/错机械报告、digest 不符等结构性违例为 `FatalReason::ProtocolViolation`；原指纹越界作为内容性新 finding 交由策略层产出 `HumanRequired(VerificationNewFindings)`。

```rust
pub struct ReviewEvaluationInput<'a> {
    pub mechanical: &'a [ClassifiedFinding],
    pub review: &'a [ClassifiedFinding],
    pub phase: ReviewPhase,
    pub invocation: &'a ReviewInvocationScope,
}

pub struct EvaluationDecision {
    pub outcome: PlanOutcome,
    pub history_delta: RunHistoryDelta,
}

pub enum PlanOutcome {
    Valid,
    Repairable { findings: Vec<ClassifiedFinding> },
    HumanRequired {
        findings: Vec<ClassifiedFinding>,
        repeated_fingerprints: Vec<FindingFingerprint>,
        reason: HumanReason,
    },
    Fatal { reason: FatalReason, diagnostics: Vec<PolicyDiagnostic> },
}

pub enum FatalReason {
    TransitionBudgetExhausted,
    UnknownCategory,
    UnknownClassHint,
    InvalidStructuredOutput,
    StateCorruption,
    ProtocolViolation,
    PersistenceFailure,
    SafetyInvariantViolation,
}

pub enum HumanReason {
    NativeHumanRequired,
    RepeatedFingerprint,
    RepairBudgetExhausted,
}

pub struct RunHistoryDelta {
    pub seen_fingerprints_to_add: BTreeSet<FindingFingerprint>,
    pub repairs_used_delta: u32,
    pub manual_repairs_used_delta: u32,
    pub transitions_used_delta: u32,
    pub initial_review_count_delta: u32,
    pub verification_review_count_delta: u32,
}

pub struct RepairReservation {
    pub token: String,
    pub owner_session_id: String,
    pub owner_run_id: String,
    pub provider_start_idempotency_key: String,
    pub state: RepairReservationState,
    pub commit_id: Option<String>,
}

pub enum RepairReservationState { Reserved, ProviderStarted, Committed, Released }

pub fn evaluate(
    input: &ReviewEvaluationInput,
    history: &RunHistory,
    budgets: &RunBudgets,

```

`FatalReason` 与 `HumanReason` 均使用 `#[serde(rename_all = "snake_case")]`，`FatalReason` 实现 `Display` 并只输出上述稳定 variant code；`PolicyDiagnostic { code, message, field: Option<String> }` 承载可展示细节，避免把原始未知输入混入 reason。三种 `HumanReason` 的唯一来源分别是原生/兜底 human_required、非 advisory 重复指纹、以及 repairable 在自动 repair 预算无余量（包括复评仍未解决）时。

`RunHistoryDelta::merge_into` 只接受未超预算的加法：集合取并集、所有 `*_delta` 以 checked_add 合并；发现持久化历史本已超预算、溢出、或 delta 使其超预算时返回 `Fatal(StateCorruption)`。纯 evaluator 的 `transitions_used_delta` 恒为 0；其只能由 durable route handler 在 stage transition 成功持久化后设置为 1。advisory 从不写入 `seen_fingerprints`。

纯 evaluator 只以 `PlanOutcome::Repairable` 声明需要返修；Task 5/6 的 durable route handler 在已知 session/run owner 后才物化 `RepairReservation`。每个 token 由 `(owner_session_id, owner_run_id, provider_start_idempotency_key)` 唯一绑定：CAS `Reserved` 不增加 `repairs_used`；成功记录 provider 启动后转 `ProviderStarted` 并一次性提交 `repairs_used_delta=1`；后续工作流完成转 `Committed`。启动失败或重启发现没有 `ProviderStarted` 启动账本的 `Reserved` token，必须按 token 幂等转 `Released`，不增加计数；重启发现 `ProviderStarted`/`Committed` 时复用 idempotency key，绝不二次启动。

# 计划文档：修复 LC 仓聚合初始化在「只装部分 provider」场景下的失败与不可行动失败面

> 关联 OpenSpec change：`fix-aggregate-init-partial-provider-zero-change`
> 分支：`bugfix-11-12`（worktree `.worktrees/bugfix-11-12`，基线本地 `main` `77cd2a13`）
> 日期：2026-11-12

## 一、Goal

让「机器上只装了部分 provider（本次现场：Pi 已装、Claude Code / Codex 未装）」的机器能够完成
LC 仓聚合初始化；并让聚合初始化失败时，用户从失败面**看得到 provider 到底做了什么**，
而不是只看到一句 `zero_change=true`。

## 二、根因证据（2026-11-12 podman 容器 E2E）

容器镜像：Rust 构建 + node + Pi CLI 1.5.0 + codegraph 1.6.2 + pip/uv/uvx；
**故意不装 Claude Code / Codex**（即「只装一家 provider」场景）；宿主 `~/.pi`、`~/.agents`、
`~/.kimi-code` 复制到临时目录后挂载（宿主原件零改动）；`--network host` 让容器访问宿主的
模型网关 `127.0.0.1:3425`（用户配置里的默认 provider `magpie`）。

### 2.1 结论

| 环节 | 观察 | 判定 |
|---|---|---|
| provider 选择 | 选中 Pi；Claude Code / Codex `skipped_reason=cli_unavailable` | **不是故障点**（与用户界面一致） |
| `pre_check` turn | Pi 展开 skill 成功；把 `用大陆镜像` 翻译为 `--mirror cn`；执行 `pre-check.sh run --mirror cn --no-interrupt --upgrade` | provider 侧参数映射正常 |
| 脚本结果（坏环境） | `"overall": "failed"`——base-tools phase 的 `uvx` 装不上（脚本用 `pip install uv` 装 uv，容器无 pip）⇒ `--no-interrupt` 立即中止 ⇒ **聚合根零落盘** | **失败机制**：任一 phase 失败 ⇒ 零落盘 |
| 平台判定 | 聚合根零字节变化 ⇒ REQ-BOOT-17 判零变更失败 | 判定符合契约 |
| 失败面 | 诊断只有 `root recipe turn produced no workspace change (provider=pi, step=pre_check, zero_change=true)`；脚本的 JSON 报告被整段丢弃 | **真缺陷：失败面不可行动** |
| 健康环境（补齐 pip/uvx 后） | run1：pre_check ✓、rule_and_mcp_config ✗（Pi 发问 ⇒ fail-closed `provider interaction required`）；run2（重跑）：**五个 step 全 completed** | **「只装一家 provider」本身不是阻断点**；健康环境下整条 recipe 跑得通 |
| 脚本幂等性 | 脚本 `check` 模式报告 `all-skipped` / 0 created / 0 updated | 四条命令的契约就是幂等 |

### 2.2 与用户现场的关系

用户现场（2026-11-12，实例不在这台机器上：本地 4317 实例无 project，远端
`arch-code...` 从本机不可达）失败签名是 `zero_change=true`——turn 正常结束、零落盘。
结合上面的机制可知：**用户的 pre-check 脚本某个 phase 失败了**（用户环境的前置工具或网络
与容器坏环境同构），而平台把「哪个 phase 失败、失败原文是什么」整段丢掉了。

⇒ 平台侧要做两件事：
1. **失败面可行动**：诊断必须带出 provider 的真实输出（脚本 JSON 报告）。
2. **零变更判据补事实**：命令**确实执行且报告成功**（幂等无产物变化）不该判失败；
   命令没被执行 / 执行了但失败，仍判失败。

### 2.3 另见（不在本 change 内）

容器现场还观察到第三种失败形态：Pi 在 turn 里发问 ⇒ 平台 fail-closed
（`provider interaction required`，retryable=false）⇒ 后续 turn 不跑。与「零变更」是不同
故障（失败码、诊断形态都不同），本 change 不动它，已在此记为独立观察。

第四种（修复后跑出）：provider 在成员仓里执行**只读** `git status` ⇒ git 刷新了成员仓的
`.git/index` ⇒ 审计按「成员 .git 分类优先于 allowlist」判 `member_git` 越界 ⇒ 该命令
verdict=Rejected ⇒ 末命令收口时「rejected 的 recipe 不能 finalize」⇒ 聚合初始化失败。
这是**独立**故障（与零变更无关），且是否触发取决于成员仓 index 是否陈旧（环境相关），
本 change 不动它，已在此记为独立观察。



## 三、决策

1. **失败诊断带 provider 真实输出**（本 change 的必做项）：零变更失败的诊断 =
   失败事实（provider / step / 零变更）+ provider 输出尾部（经既有脱敏入口
   `sanitize_turn_output`）。契约见 delta spec 的 REQ-BOOT-17 修订。
2. **turn 输出超预算保留头尾**：只留头会把脚本报告（收尾处）整段截掉。
3. **零变更判据是否细化**（命令已执行但幂等无变更 ⇒ 判成功）：**待二次取证**。
   二次取证要回答的问题：在**已初始化**的聚合根上重新跑四条命令时，脚本是否真的
   零变更（若零变更 ⇒ 「重新初始化」永远失败 ⇒ 需要改判据）。
   未拿到该证据前不动判据（契约是冻结的，REQ-BOOT-17 明文要求零变更判失败）。
4. **不在平台侧重复实现 Cadence-skills 脚本的工具安装**：base-tools phase 属于
   Cadence-skills 的职责；平台侧只保证失败可行动 + 环境前置（codegraph / 根可写 /
   链接层）不被绕过。若二次取证显示「缺 pip/uvx」是常见现场，再单开 change 处理
   「部署镜像前置工具」。

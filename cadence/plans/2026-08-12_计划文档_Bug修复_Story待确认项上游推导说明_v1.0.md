# Story 待确认项上游推导说明修复实施计划

> **面向执行 Agent：** 必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 逐任务执行。本计划用复选框跟踪步骤。

**目标：** 允许 Story Spec 在没有开放问题时，以“无待确认项 + 全部要求可由上游 Issue 明示约束推导、未发起结构化交互确认”的说明通过校验，同时继续拒绝伪装成无开放项的真实待确认事项。

**实现方式：** 在 `artifact_constraints.rs` 的 Story 专属待确认项判定中，为空标记附带的“上游 Issue 明示约束推导、无需结构化交互”说明增加一个严格正例。`未发起结构化交互确认` 仅在该完整正例语境中表示“无需交互”，不能被既有 `未确认` 未决词误判；判定必须同时排除真正的未解决提示，防止 `无待确认项。仍待确认……` 绕过门禁。

**技术栈：** Rust、Cargo 内置单元测试。

## 全局约束

- 仅修改 Story 的待确认项校验；不改变 Design、Work Item、WorkItemPlan 的行为。
- 必须遵循 TDD：先新增失败回归测试并验证失败，再写最小实现。
- 不调用真实 Provider，不改写 `.aria` 历史数据，不引入依赖。
- 真实未解决提示（如“仍待确认”“需确认”）即使前缀是“无待确认项”也必须继续失败。
- 定向验证命令必须使用 `cargo test --locked --lib <过滤名>`，不得使用 `-j 1`。

### Task 1：修复 Story 待确认项的上游推导说明判定

**文件：**

- 修改：`src/product/workspace_engine/tests/part_10.rs:124-187`
- 修改：`src/product/workspace_engine/artifact_constraints.rs:543-640`

**接口：**

- 使用：`validate_workspace_artifact_constraints(content, &WorkspaceType::Story)`。
- 产出：Story 的 `## 待确认项` 在内容明确为“无待确认项，且全部需求、成功标准与验收口径可由上游 Issue 明示约束推导”时不产生 `AskUserQuestion` 阻断原因。

- [x] **步骤 1：写失败回归测试**

在 `part_10.rs` 的现有 Story 待确认项测试附近新增测试，产物内容必须包括：

```rust
## 待确认项
无待确认项。所有需求、成功标准与验收口径均可由上游 Issue（issue_0001）的明示约束推导得出；未发起结构化交互确认。
```

断言 `report.passed` 为真，并在断言消息中输出 `report.blocking_reasons()`。

同时新增或调整一个回归反例，内容为：

```rust
## 待确认项
无待确认项。Codex 的 npm 包名仍待确认。
```

断言失败原因仍包含 `待确认项` 与 `AskUserQuestion`。

- [x] **步骤 2：验证测试为红**

运行：

```sh
cargo test --locked --lib story_artifact_
```

预期：新正例因“待确认项未通过 AskUserQuestion 交互解决”失败；反例保持通过测试。

- [x] **步骤 3：实现最小判定**

在 `open_item_line_is_resolved` 附近增加仅供空标记说明使用的辅助判定。它必须：

1. 仅对以既有空标记开头的行生效；
2. 识别“可由上游 Issue 的明示约束推导”这一结论（允许中英文 Issue 大小写归一）；
3. 识别“无需/不需要发起结构化交互”或实际案例中的“未发起结构化交互确认”；后者只能与前两项同时出现时解释为“无需交互”，不能单独抵消未决词；
4. 从空标记后剩余说明中检查既有未解决提示；存在 `仍待确认`、`需确认`、`[OPEN-*]`、`TBD` 等任一提示时返回否；
5. 不能把所有以“无”开头的文本一律放行。

然后只在上述严格条件满足时把该行视为已解决；保留原有“显式结构化交互确认”和“非待确认项”路径。

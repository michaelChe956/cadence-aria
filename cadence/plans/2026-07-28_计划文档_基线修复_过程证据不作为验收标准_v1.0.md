## 关键约束

### 过程事实判定标准

同时满足两条即为过程事实，reviewer 不得据以否决：

1. 无法从当前 diff、验证命令输出、handoff 字段或人工检查结果观测；
2. 实现完成后即使返修也无法产出该证据。

**属于**：red commit 存在性、失败→通过的提交序列、开发时序、提交拆分粒度、分支创建与 rebase 历史、Coder 会话内操作顺序。

**不属于**（仍必须审查）：测试文件是否存在、测试是否覆盖需求场景、验证命令是否真实执行且非零、测试输出是否与实现自相矛盾、Forbidden Write Scopes 是否被越过。

### `non_zero_test_execution` 语义口径

两侧 prompt 措辞必须一致：表示验证命令执行时实际运行了非零数量的测试，是当前可观测的执行结果；不表达测试曾先失败，不表达提交顺序，不表达任何开发时序。

### 🔴 reviewer 提示词有四条构造路径，不是两条

**只改两个协议函数，本变更在 Code Review 阶段完全不生效**——而那正是本缺陷最常触发的阶段。`code_review.rs:68-74`：

```rust
let prompt = match self.render_reviewer_unit_run_context(&attempt, &reviewer)? {
    Some(rendered) => rendered.text,
    None => { self.build_code_review_prompt(...).await? }
};
```

`render_reviewer_unit_run_context`（`plan_defect.rs:413-455`）在 `attempt.scope == WorkItemGroup` 且有 active unit + projection bundle 时返回 `Some`。此时 prompt **完全**是 `render.rs` 的 projection 文本，`code_review_material_protocol()`、`reviewer_test_scope_contract()`、`no_default_stack_assumption_contract()` 全部不出现。projection 路径唯一的 reviewer 侧行为契约是 `render.rs:471-484` 的 `role_structured_output_contract`，只讲 JSON 格式。

四条路径都要覆盖：

| 路径 | 构造位置 | 触发条件 | 当前含 `reviewer_test_scope_contract` |
|---|---|---|---|
| **Code Review — projection 渲染** | `render.rs` reviewer 渲染 | group scope + active unit + projection bundle（**主路径**） | 否 |
| Code Review — 传统 prompt | `prompts.rs:52-55` | 上述条件不满足 | 是（`:54`） |
| GroupFinalReview — group | `internal_pr_review.rs:119-122` | group scope | 是（`:120`） |
| GroupFinalReview — 非 group | `prompts.rs:121-123` | 非 group scope | **否** |

projection 路径建议作为一个新 section 注入，而非塞进 `role_structured_output_contract`——后者命名是讲输出格式的，混入行为契约会让命名失真。

### 🔴 校验层：Warning 级，可见但不阻断

**严重级别选 `Warning`，有意不与既有一致。** 既有 `blank_` / `duplicate_acceptance_criterion_id` 都是 `Error`（`validation.rs:447`、`:467`）。选 `Warning` 因为本检出只能做关键词匹配，误报会让合法候选被整体拒绝。

Warning 通道的完整行为已查清（**不再是待定项**）：

- **不阻断候选**：`WorkItemDraftLocalValidator::validate`（`types.rs:57-84`）的三个消费点（`draft_batch/authoring.rs:80`、`:271`、`draft_batch/decisions.rs:400`）全部只读 `report.has_errors()`（`types.rs:9-13`，只看 Error）。不触发 `RetryOnce`、不置 `ValidationFailed`、不影响 `can_accept`。
- **可见，但只在一处**：`report.findings` 经 `plan_outline/dto.rs:3-15` 进 `WorkItemDraftCandidatePayload.validator_findings`，经 `workspace_engine/controls.rs:216-256` 持久化推送；前端 `WorkItemPlanArtifactContent.tsx:148` 的 DraftsTab **无条件**渲染 `ValidatorFindings`，`:710-730` 不按 severity 过滤。`draft_candidate` artifact 默认 tab 就是 `drafts`（`WorkItemPlanArtifactPanel.tsx:351-353`）。
- **⚠️ chat 确认流上静默**：`DraftValidationFailureNotice`（`ChatInputBar.tsx:188-190`、`WorkItemPlanStagedPanel.tsx:75-77`）只在 `!can_accept` 时渲染；batch 路径的 `failure_summary`（`draft_batch/runs.rs:401-409`）只收 `ValidationFailed` 记录。

所以「让缺陷可见且可路由」成立，但**成立条件是用户查看 artifact panel 的 Drafts tab**，不能笼统说「可见」。

`ContractFindingSeverity::Warning` 在 `src/` 非测试代码**零构造点**（只在 `draft.rs:21` 的 match 分支被消费），必须新增一个与 `error_finding`（`validation.rs:420-435`）对称的构造函数。已确认，不是待定项。

### 校验检出保守原则

校验层只有 `criterion_id` 与 `statement` 文本，只能做关键词匹配。**宁漏不误**：匹配条件必须要求同时出现「提交/commit」类词与「先失败/red/顺序/时序」类词，不得对单一关键词命中即报。漏检由 reviewer 侧边界兜底。

### `ManualCheck` 与 `HandoffField` 的语义是本变更新建立的

`model.rs:109-116` 四个成员是裸枚举，无 doc comment、无 `as_str`、无任何消费逻辑区分；全仓非测试代码里 `EvidenceKind` 只出现三处（`model.rs:59`、`work_item_projection/model.rs:71`、`reviewer.rs:24` clone），**没有任何行为依赖具体 kind**。

`NonZeroTestExecution` ↔ `VerificationCheck.non_zero_test_execution_required`（`model.rs:69`）有实质依据（同名、同语义域）。但 `ManualCheck` ↔ `manual_instruction`、`HandoffField` ↔ `HandoffContract.required_fields` 只是合理推断，代码里没有连接。

因此写 prompt 语义说明时这两个 kind 需自己定义措辞，且**定义与 splitter 实际用法不符就会产生新漂移**。措辞保持在「可观测性」这一共同性质上：`manual_check` 指人工检查的**结果**，`handoff_field` 指交接字段的**存在与内容**——都是当前状态，不含时序。

### 三层拦截缺一不可

- splitter prompt：源头拦截（软约束，provider 可违背）
- canonical 校验：兜底检出（启发式，可能漏检）
- reviewer 协议：末端兜底（漏检发生后唯一防线）

任何单层都不足，三层必须在同一批实施。

### 不做历史兼容

既有含过程性 acceptance criterion 的契约实施后会被检出。不添加豁免名单、不添加宽限期、不为历史记录编写兼容测试。实施中遇到「旧契约会触发新 finding」的场景，一律不加兼容分支。

## 阶段二：reviewer 侧契约

对应 tasks 2.1–2.4。

2.1 在 `src/product/coding_workspace_engine/prompts.rs` 于 `reviewer_test_scope_contract`（`:269-276`）之后新增：

```rust
pub(crate) fn reviewer_process_evidence_boundary_contract() -> &'static str
```

内容结构（照 `reviewer_test_scope_contract` 的行组织方式）：
- 判定标准两条；
- 不得创建以过程事实为目的的 finding；

## 已知缺口

`reviewer.rs:25` 把所有 criterion 的 `failure_route` 硬编码为 `CoderRework`，包括契约缺陷类。即使 reviewer 正确识别出某条 criterion 有问题，projection 仍在暗示「让 Coder 修」。这是独立的路由缺陷，本 Plan 不修，仅记录。

## 风险

1. 🔴 **只改两个协议函数会让本变更完全白做（最高风险）。** Code Review 主路径走 projection 渲染（`code_review.rs:68-74`），`code_review_material_protocol` 根本不出现在 prompt 里。2.3a 是本变更是否生效的唯一关键步骤，1.4a 是其判据。
2. 🔴 **边界被 reviewer 过度解读，导致真实测试缺陷被放过。** 缓解：2.1 必须显式列出仍必须审查的可观测项；1.6 的三条回归断言必须先写、先失败、后通过。
3. **校验层误报，合法 criterion 被拒。** 缓解：保守匹配 + `Warning` 级别 + 1.10 的负向用例 + 1.10a 的不阻断断言。
4. **`Warning` 的可见性有限定条件。** 只在 artifact panel 的 Drafts tab 可见，chat 确认流上静默。若后续认为不够，改 `Error` 需同步收窄匹配集合——但那会引入误报阻断风险，权衡时不要只看「更醒目」。
5. **两侧 `non_zero_test_execution` 措辞漂移。** 缓解：1.8 用同一子串同时断言两侧。
6. **`manual_check` / `handoff_field` 的语义是新造的。** 代码里这两个 kind 没有任何行为依赖，措辞若与 splitter 实际用法不符会产生新漂移。保持在「可观测性」这一共同性质上，不对具体用法过度承诺。
7. **format 占位与参数不匹配。** 阶段二涉及三个长 `format!`（`prompts.rs:30-33`、`prompts.rs:97-100`、`internal_pr_review.rs:96-99`），`{}` 序列与参数列表必须逐一对齐。**注意原 Plan 曾把后两者的行号混用**，改前先确认文件。
8. **与 `remove-testing-stage` 在 `render.rs` 撞车。** 真实交集不在 `prompts.rs`（两个协议函数没有任何 Testing 字样），在 `render.rs`：`test_evidence_refs` 经 `render.rs:449` 的 `ReviewExecutionEvidence` section 进 prompt 且是 mandatory section（`:80`），与 2.3a 要改的是同一条渲染路径。谁后做谁负责确认 section 集合完整、渲染不失败。

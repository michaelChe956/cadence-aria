## 一、Goal

让「本机没有装 claude code / codex / pi / kimi code / codegraph」的用户，在页面上点【安装】后**真的装上并立刻可用**；同时让聚合索引在大型聚合根上不再因 codegraph 输出被截断而报 `codegraph_files_invalid_json`。

## 二、症状（用户现场）

| # | 症状 | 现场证据 |
|---|---|---|
| 1 | 本地没装四家 provider 中任意一个或多个，点【安装】**没有效果，从未装成功** | 用户报告 |
| 2 | 本地没装 codegraph，点【安装】**没有效果** | 用户报告 |
| 3 | 聚合索引 degraded，错误 `aggregate_index_failed:codegraph_files_invalid_json: parse JSON from codegraph files: EOF while parsing a string at line 32565 column 48` | 用户截图 |

## 三、根因与证据（容器实测，非推理）

### 根因 A（症状 3）：codegraph 输出被 1 MiB 抓取上限截断，且截断事实被丢弃

| 环节 | 位置 | 事实 |
|---|---|---|
| 上限 | `src/product/logical_codebase/aggregate_index/codegraph_cli.rs:39` | `const OUTPUT_LIMIT_BYTES: usize = 1024 * 1024;`，在 `:283-284` 套给**所有** codegraph 调用 |
| 截断 | `src/cross_cutting/bounded_command_runner.rs:191-209` | `read_limited` 恰好保留 `limit` 字节、丢弃其余并置 `truncated`（达到上限后**继续读取并丢弃**，子进程不会因管道阻塞而挂死 ⇒ 现象是「exit 0 但 JSON 解析失败」） |
| 丢标志 | `codegraph_cli.rs:345-350` | `fn command_result` 只取 `stdout/stderr/duration_ms`，`stdout_truncated` 被丢掉 |
| 误报 | `codegraph_cli.rs:216-219` | 截断文本喂 `serde_json::from_str` → `codegraph_files_invalid_json`（伪装成「协议不符」） |

**容器实测（真实 codegraph 1.6.2，node:24-bookworm）**：9k~20k 文件的 `files --json` 为 1.3~3.9 MB；把前 1,048,576 字节交给**仓库同版本 serde_json 1.0.149** 与 `CodeGraphFile { path: PathBuf }` 解析 → 逐字复现 `EOF while parsing a string at line 32565 column 48`；同一载荷不截断 → 解析成功（20000 entries）。已排除：格式变化（1.6.2 仍是 pretty JSON 数组）、stdout 混日志（stderr 实测 0 字节）、并发写文件、编码问题。

### 根因 B（症状 1/2）：装到的目录不在服务进程 PATH 上 ⇒ 装完探测仍失败 ⇒ 界面仍显示「未安装」

| 环节 | 位置 | 事实 |
|---|---|---|
| 前缀回落 | `src/product/provider_installation/runner.rs:397-412` `resolve_effective_prefix` | CLI 缺失时回落到 `npm prefix -g`；**不检查**该前缀的 `bin` 是否在 PATH 上 |
| 前缀探测 | `effective_prefix.rs:38-45` `visible_cli_prefix` | 只认「PATH 上已有该命令」的前缀（CLI 缺失时此路不通） |
| 装后探测 | `runner.rs:201-236` `HealthRefreshProber` | codegraph 分支跑 `codegraph --version`（PATH 查找）；四家 provider 走 `provider_health.refresh()`（同样只按 PATH 找） |
| 提示缺失 | `runner.rs:245-264` `npm_path_hint` | 只对 `row.npm_package.is_some()` 产出 ⇒ **Kimi 完全没有提示** |

**容器实测（5 种布局，podman `localhost/diag-installfix:latest`）**：
- 布局 A（npm 前缀 bin 不在 PATH，服务 PATH=`/shim:/usr/bin:/bin`，`npm prefix -g=/opt/node`）：`npm install -g --prefix /opt/node …@colbymchenry/codegraph@latest` **exit 0**，二进制落 `/opt/node/bin/codegraph`，但装后探测 → `env: 'codegraph': No such file or directory`（127）⇒ 作业 completed、`installed_version` 为空、界面仍「未安装」⇒ 用户点一次没效果、再点一次再没效果。claude-code / codex 同形。
- 布局 C（Kimi 官方脚本）：脚本输出 `Installed to /root/.kimi-code/bin/kimi` + `Added /root/.kimi-code/bin to PATH in /root/.bashrc` ⇒ **只改 shell rc**，运行中服务进程 PATH 不变 ⇒ 探测 127 ⇒ 必然「没有效果」，且无 `path_hint`。
- 布局 B1（fnm 式目录软链农场）：`visible_cli_prefix` 规范化后能命中真实前缀 ⇒ 探测成功 ⇒ **不是**根因（避免误判）。
- 布局 B2（逐文件软链农场当 prefix）：npm `EEXIST` exit 1。
- 布局 D（root 拥有的 `/usr/local`）：见根因 C。

### 根因 C（症状 1 的次因）：可写性判定只看权限位 ⇒ 选到根本写不进去的系统前缀

`src/product/provider_installation/effective_prefix.rs:61-84`：`is_writable_dir` → `dir_is_writable` 只看 `mode & 0o222`。root 拥有的 `/usr/local`（0755）⇒ `mode & 0o222 = 0o200` ⇒ 对任意用户都判「可写」⇒ npm 报 `EACCES … mkdir '/usr/local/lib/node_modules/@colbymchenry'`（exit 243）⇒ `$HOME/.npm-global` 兜底永远走不到。容器实测同点 `os.access(W_OK) → False`。

### 根因 D（放大器）：前端把后端整句提示再包一层

`web/src/components/lifecycle/ProviderInstallActionButton.tsx:290-292`（修复前）：后端 `path_hint` 本身已是完整句子（「已安装到 /opt/node；若 `codegraph` 不在 PATH 上，请把 /opt/node/bin 加入 PATH 后重试」），前端又拼成「…；若命令不在 PATH，可把 <整句> 加入 PATH」⇒ 用户看到破碎双句，更像「没效果」。

### 已排除的机制（有执行证据）

- npm 子进程缺 HOME / 环境不继承：`src/cross_cutting/process_manager.rs:428-441` `env_clear` 已删，子进程继承宿主环境，`request.environment` 只是覆盖层 ⇒ 排除。
- 按钮不渲染 / 请求丢失 / 作业卡死：路由与前端调用链完整、作业落盘后才 spawn ⇒ 排除（仅留边缘项：重启后 stale `running` 作业无对账，见 §8 风险 R4）。

补充事实（实施期实测）：`codegraph` 1.6.0/1.6.2 **都支持** `--no-metadata`，但该 flag 在 `--json` 模式下**下载荷逐字节不变**（只影响 tree 文本格式）⇒ **owner 2026-11-13 裁决去掉该 flag**：`files` 只下发 `["files","--json"]`，不附加任何未经实测证明能降低载荷的旗标（避免未来 CLI 移除该 flag ⇒ `files` 全线失败）。

**既有规格漂移（记录，本 change 不改）**：主规格 `openspec/specs/logical-codebase-aggregate-index/spec.md` REQ-IND-01 仍写「exact version 钉定 v1.5.0」，与实现的 `>=1.6.0, <2.0.0` 不符。版本门本轮**不动**，归档同步时由双审对齐。

### 包 4：聚合索引验收改走 codegraph 库 API（owner 2026-11-13 裁决，已实施）

**为什么**：验收要回答「每个登记成员目录有没有被索引的文件」，而今天的做法是让 codegraph 吐出**整个仓库的文件清单**（`codegraph files --json`）再全量读进内存。实测载荷与规模线性相关（每文件约 110~200 B；`codegraph.db` : JSON ≈ **13 : 1**）⇒ 用户现场 **3.1 GB 索引 ⇒ 清单约 230 MB**，抓取上限（1 MiB / 64 MiB）**无论如何都装不下** ⇒ 验收必失败（现场报 `codegraph_files_invalid_json`）。**索引本身是好的，只是平台读不出来、因此不承认它**。

**怎么做**（照 magpie 之外的官方库面实测）：
- 新增 `src/product/logical_codebase/aggregate_index/codegraph_coverage.rs` + 内嵌的 Node helper `codegraph_coverage_helper.mjs`；
- helper 用 **codegraph 自带的 Node**（`<包根>/node_modules/@colbymchenry/codegraph-<plat>/<arch>/node`，实测 v24.16.0）执行 ⇒ **不要求用户装 Node**；找不到自带 node 时才回退 PATH 上的 `node`（需 ≥22.5）；
- helper：`const pkg = (await import(sdkUrl)).default ?? mod; const { CodeGraph } = pkg;` → `await CodeGraph.open(root)` → 逐成员 `await cg.hasFilesUnder(member)`（**目录边界精确**：`hasFilesUnder("member-al")` 对 `member-alpha` 返回 false，比 CLI `--filter` 的裸前缀更准）→ 顺带取 `getStats()` / `getIndexState()` / `isIndexStale()`；输出**几百字节**的 JSON；
- Rust 侧 SDK 路径解析顺序：① 我们的安装前缀（npm 标准布局 `<prefix>/lib/node_modules/@colbymchenry/codegraph/npm-sdk.js`）→ ② `npm root -g` 探针 → ③ 从 `codegraph` 可执行真实路径反推；node 解析顺序：自带 node → PATH node（≥22.5）；
- **回退保底**：SDK 找不到或版本不兼容 ⇒ 回退既有 CLI 清单路径（保留 64 MiB 上限与专用截断码），并在激活记录留审计 warning；
- **健康闸**：索引状态异常（stale / pending>0 / state 异常 / fileCount=0）⇒ 记 **warning，不阻断激活**（保持今天「不因健康问题阻断」的语义）；
- **排除性查询**（非成员目录 / `.worktrees` / `.aria` / 构建产物未被索引）**保持走既有 CLI `query --json`**，不动。

### 包 5：前端无限轮询收敛（owner 2026-11-13 报 bug，已定位）

## 十一、magpie 对照（借鉴 / 不借鉴）

> 参照物：`yetone/magpie`（Go），commit `5a2d0ff`。引用为该 commit 的永久链接行号；我方已独立复核关键条目（`install.go`、`cliupdate.go`、`cliupdate_shim.go`、`internal/proc/path_other.go`、`internal/proc/version.go`、`internal/library/rtk_path_other.go`）。

| 维度 | magpie 做法 | 我们的采纳 |
|---|---|---|
| 缺失 CLI 的安装 | **不代跑**，只展示 vendor 安装命令让用户复制到终端（`install.go` #L3-L9：安装可能缺 Node/Homebrew，且 npm 全局前缀可能要 sudo） | **不采纳**（我们是产品内一键安装，是需求）；**采纳其前提检查与提示形态**（Node/npm 缺失、不可写前缀 ⇒ 给迁移提示，绝不 sudo） |
| 更新机制 | 按**二进制真实路径**判定装法：vendor 自带 updater（`claude update` / `codex update`）或 npm/bun/pnpm/brew；判不出就只显示版本、不提供更新（`cliupdate.go` #L295 `howInstalled` / #L400-L466 `fromNodeModules`） | **采纳其前缀反推思路**：我们的 2.3 已在 CLI 已装时用「PATH 上生效前缀」，2.7 进一步把安装子进程的 PATH 前插目标前缀 |
| npm 更新命令 | `npm install -g --prefix <发现的前缀> [--allow-scripts=<pkg>] <pkg>@latest`；**无 `--omit=optional`** | **采纳** `--allow-scripts=<pkg>`（2.7②）与「装上但缺平台包 ⇒ `--include=optional` 重试一次」（2.7③） |
| 前缀可写性 | `unix.Access(dir, W_OK)` 真实判定；不可写 ⇒ unix 不提供 npm 更新（不做 sudo），win 走提权 | **采纳**（2.1 的 mode 预筛 + 真实写入探测） |
| PATH 可见性 | 四层：①启动时 `UserPath()` 注入已知用户目录（`userDirs` 清单）+ 登录 shell PATH（2s 上限）；②`FindTool` 无视 PATH 兜底扫 `UserBinDirs`；③`OffPath` 状态显式建模并打 UI 黄标；④自家二进制按需 symlink 到终端 PATH 上的可写目录 | **采纳 ①②③**（2.4b/2.4c/2.9）；**④列为待裁决**（§十 未决点 10） |
| 版本检测 | 本地版本**优先读 npm 包 `package.json`**（不执行进程），否则 `bin --version`；更新后重探测 + `runsBroken` 检查 + 坏则给 `mendHint` | **采纳**（2.8 三重验证） |
| 镜像/国内 | agent CLI 的 registry 硬编码 `registry.npmjs.org`，**无镜像** | **不采纳**（我们面向国内用户，保留阿里镜像默认 + `NPM_REGISTRY` 覆盖） |
| 平台差异 | 菜单栏 app + 本机网关、单用户桌面 | 我们是服务端 + 界面安装 ⇒ 不能照搬「让用户自己去终端装」；但「装完必须交叉验证 + 给可复制修复命令」必须照搬 |

## 十二、客户机定位指引（生产日志 / 诊断端点）

> 目标：客户反馈「安装没效果 / 聚合索引报截断」时，不远程登录也能拿到第一手证据。

### 12.1 日志在哪、怎么确认开了

- 落点：`<workspace>/.aria/logs/aria.log`（`aria web --workspace <dir>` 的 `<dir>/.aria`，与 `ProductAppPaths` 同一状态根）。
- 形态：**追加**写，目录不存在自动创建；同时照旧写 stderr（launcher `tail` 能看到同一批行）。
- 文件打不开（目录被占 / 权限不足）⇒ **降级为只写 stderr**，并在 stderr 打一行
  `[aria-logging] cannot write <path>: <原因>; continuing with stderr only`，**服务照常启动**。
- 启动时 stderr 固定打一行 `[aria-logging] log_file=<path> filter=default|RUST_LOG`，
  用来确认日志通道确实建立。
- 当前**不做轮转**：客户回传 `aria.log` 后可直接截断或删除；长期运行请自行切割。

### 12.2 默认口径与 `RUST_LOG` 覆盖

默认（不设环境变量）等价于：

```text
warn,cadence_aria::product::provider_installation=info,cadence_aria::product::logical_codebase::aggregate_index=info
```

即全局 `warn`，只把本轮两个诊断模块开到 `info`。

`RUST_LOG` **存在且非空时完全取代**默认口径（不是叠加）：

```bash
# 全量 info（噪音大，短时排障用）
RUST_LOG=info aria web --workspace /path/to/ws
# 只把安装链开到 debug，其余保持 warn
RUST_LOG=warn,cadence_aria::product::provider_installation=debug aria web --workspace /path/to/ws
# 只看 warn 及以上
RUST_LOG=warn aria web --workspace /path/to/ws
```

写错指令不会让服务起不来（非法指令按 lossy 丢弃）。日志**不会**出现密钥 / token /
凭据 / 模型配置 / 作业 stdout 正文；不要为了排查把 `RUST_LOG` 开到原始输出级别。

### 12.4 诊断端点怎么配合

- 发现文件：`.aria/web-endpoint`（workspace 根下，内容为纯端口号；**仅回环 host 绑定时写入**）。
- 取端口并拉快照：

```bash
PORT=$(cat /path/to/ws/.aria/web-endpoint)
curl -s "http://127.0.0.1:$PORT/api/providers/diagnostics" | jq .
```

- 与本轮相关的分区：`install_targets`（服务进程生效 PATH / 登录 shell PATH / 各安装目标状态）、
  `path_overlay`、`install_jobs`（最近作业）、`codegraph`、`aggregate_index`、`provider_health`。

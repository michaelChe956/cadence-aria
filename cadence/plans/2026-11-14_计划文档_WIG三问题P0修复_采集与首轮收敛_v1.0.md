## 十一、C/E 实施口径（2026-11-15）

**S-C 陈旧人工门**（`a3fb2975`）：根因是 `recover_delegated_author_rerun_failure` 对**任何**接力启动失败都开门，而自动链接力重驱孤儿接力（`delegated_rerun_orphan` → 消费 `repair_reservation` 预领 → 接力真跑成功）随后**没人关门**。修法：接力**接管后**收口该门——durable 判定三件事：会话 `WaitingForHuman`（该门不写门快照，故其本身即门开态证据）、`repair_reservation.state != Reserved`（预领被消费＝接力确实领走了 provider start；仍 `Reserved` ⇒ 接力未接管，人工出口必须保留，方法零副作用）、durable 时间线上存在 **Active** 且摘要带恢复路径标记的 `HumanConfirm` 节点（**用户**开出的门无该前缀，绝不被关）。复用既有门节点链路、门开态 CAS 与 `HumanGateClosed` 广播，未新增第二套门状态机。

**S-E 内容级再返修一次**（`675a9ae7` + `554a966a`）：`route_outcome` 在 `AutoIfValid` 下对内容级 `HumanRequired`（`NativeHumanRequired` / `VerificationNewFindings`）改走 `TriggerAggregateRepair`；额度按**逐工件** `history.review_cycles[cycle_key].repairs_used < budgets.max_repairs` 判定（不看会话总计 ⇒ 不跨工件共享；用 `<` 而非 `<=` ⇒ 不把 cycle 记到 `max_repairs+1` 触发 `StateCorruption`）；三类安全原因（`RepeatedFingerprint` / `UnstableFindingIdentity` / `RepairBudgetExhausted`）**不开放**（防循环）；无 actionable finding 或 cycle 身份缺席 ⇒ 保守交门。

**混合轮修正**（`554a966a`）：初版把混合轮（平台编译失败 finding + 模型 finding）也放开了额外返修——平台那半在到闸门前已被上游改写链消费，闸门只看得到模型条目，无法区分纯内容轮与混合轮，既有红线 2 被绕过。修法：新增 `has_platform_compile_failure_origin(verdict)`（判定单源 = finding message 的平台前缀，逐条生效，不改成按轮次豁免），在 verdict 仍完整时判定并沿 `route_outcome_from_decision → GateSnapshotContext` 传入闸门；含平台来源的轮次不开放额外返修 ⇒ **混合轮仍落人工门**，纯内容轮按用户裁决再返修一次。

### 13.2 设计方给出的两条根因（推翻我此前的"诊断不够详细"假设）
1. **`duplicate_handoff_provided_contract_ref` 不是马虎，是方言**：模型把二元组写成 `- provided_contract_refs: (WI-001, c-x)`，按 `,` 切分后得到 `(WI-001` 与 `c-x)` 两个值；同一 WI 写两行即造出「`(WI-001` 重复」的**假阳性**（现场：每个 WI 恰好 1 条 duplicate，与该方言完全吻合）。首轮 prompt 早已教过"同 WI 内唯一"仍复现 ⇒ **教学句不是瓶颈**。
2. **`direct_dependency_scope_conflict` 是规则冲突**：`include_integration_tests=true` 要求集成/E2E WI，而排他 scope 任意两 WI 不得重叠（有向依赖 ⇒ `write_scope_conflict`，无序 ⇒ `parallel_scope_overlap`）；目录级 `busi/src/test/` 与他人文件级 scope 天然相交 ⇒ **现状可满足性为零**。
3. **关键分界**：只有 `unknown_structured_key` 进 `TEACHABLE_PARSE_FAILURE_CODES`（有重驱通道）；另两码走 `validate_plan_candidate_ir` fail-closed ⇒ **模型看不到它们**，把诊断写详细只改善人读与留证，**不改变首轮通过率**。

**目标**：修正覆盖探测占用盘检时间的实现问题，对客户的 69/64/5 场景给出可复验而非推测的证据。
**Spec**：`openspec/changes/archive/2026-11-19-fix-aggregate-index-scan-verdict-and-log-bundle-coverage/`。Rust / serde / Vitest。实施方式：subagent-driven-development，任务分片以此计划为接口。

## 共同约束

继续执行 REQ-IND-01/04/06：仅 NoSource 可跳过，缺键、截断、权限失败、真正盘检超时仍阻断，十个外部码、LKG、负查询、权限与旧记录读回不变。不扩大阈值。新增的世代诊断与导出投影只记录成员短名和有限枚举，不持久化/导出 stderr、文件路径清单、快照正文或 SDK 输出。测试产物全部在 `/tmp`，不跑客户仓、外部 provider 或发布流水线。

## 任务 1：扫描器和可解释原因（1.1）

`aggregate_index/source_scan.rs` 及相邻扫描测试：为既有四态补带原因的内部详细结果和实际枚举入口标志；区分 deadline、条目预算、深度、取消、IO、Git 失败与输出截断。保留既有预算注入测试。测试短前缀无源码但 `stdout_truncated=true` 必须为 Unknown；预算入场即耗尽不可调用枚举；实际读取失败不得归为预算。必要时分离测试或小型诊断类型以保持文件边界。将低层状态传给任务 2，不包裹/透传 stderr。

## 任务 2：计时边界与持久化（1.1/1.2）

`aggregate_index/operation.rs`（verify、cross_verify_uncovered、apply_index、fail_building）、`types.rs`、`source_scope_tests.inc.rs`。让 verify 在 SDK 或 CLI 提供覆盖图后才启动一次整批预算，覆盖 elapsed 和盘检 elapsed 来自独立单调计时；在盘检路径记录每个未覆盖成员 verdict、reason 和是否已开始枚举，失败也持久化在该世代的可选 `source_scan`，不写入 LKG。历史 JSON 缺该字段按 None 读取；更新显式构造 record 的现有测试夹具。`failure_copy_table.inc.rs` 复用事实前缀变体，只对确证的单一预算/限额原因给相应中文说明，机器码仍是原码，混合原因中立。缺覆盖键不盘检。
调用方持有 `Option<SourceScanEvidence>`，`verify` 使用可注入单调 clock，在覆盖图完成后建一个批次预算。成功或失败（含盘检后的负查询失败）均把已观察的证据交回该代的终态写入；未取得覆盖图则不合成证据。

- [x] 合成夹具推进虚拟时钟超过 2 秒；测试正例 64/69 已覆盖、另外五仓经扫描确认无源码时可激活（不代表客户五仓真实组成）。反例有 IO/缺键/漏收时仍阻断；真正超时不发布新代，带耗时和逐成员事实。均不依赖 sleep。
- [x] 定向 Rust 验证覆盖 source_scope_tests、source_scan、failure_copy、log_bundle，并检查成功代与失败代独立。

## 任务 3：打包范围及 Pi（2.1/2.2）

`src/web/handlers/log_bundle/archive.rs` 的 `walk_aria` / `aria_member_bytes`、`archive_tests.rs`：仅项目/LC 下的直接世代 JSON 按明确字段投影；只导出合法 ID/时间/状态、已知事实类型及有界结构化诊断，未知正文不原样回退。沿用安全 FD、授权、预算与 manifest，不采集树中任意 JSON。用旧版/新版成功及失败记录、结构旁文件与敏感字段测打包内容。`archive.rs` 的 Pi root 选择及 `sessions.rs::discover_pi`：同一启动环境优先级，允许平铺或 cwd 布局但均须识别原生会话头，保持最近三组/脱敏，不能用 provider 安装状态充数；现有根中有候选但无法识别与无候选明确区分。前端 `CockpitLogBundleButton.tsx` 同步采集说明（现行目录名是 receipts，保留 npx 命令及人工批准）。
世代路径严格按 `lc_scope_root` 两个布局；清单 `content_policy` 明确白名单投影、不导出原始 warning；同源解析失败封套。Pi 仅从 `path_overlay::shell_env` 缓存补足未设置的宿主变量，不触发登录探测或 Pi 进程。

## 验证与审查（4.1）

后端定向 `cargo test --locked --lib`（source_scope_tests、source_scan、failure_copy、log_bundle），前端工作台/日志弹窗 Vitest 与 typecheck；OpenSpec strict、格式、代码审查。旧缺字段/混合原因/敏感字段/迟到请求/真实超限是审查重点。仅按已有证据定位至盘检，现场触发器未测不得称已确认；只有客户正式升级并有新世代才可称客户现场恢复。
客户若日后更新，用同一新世代的 `source_scan`、覆盖/验收日志核对逐成员结论即可；旧现场没有入场余量证据，不用 provider 会话或源码来补推。

## 原版对照证据

在 `v0.1.8` 的原始生产代码上构造 69 个合成成员，覆盖探针固定返回 64 个已收录、5 个未收录。两轮使用相同主检出；计数的是未收录成员的文件枚举入口。该正例的五仓只有配置，不推断客户五仓的类型。

| 人为加入的覆盖查询耗时 | 实际进入成员枚举 | 重建结果 |
|---|---:|---|
| 0 秒 | 5 | Active |
| 3.1 秒 | 0 | `aggregate_index_source_scan_incomplete` |

对照证实计时位置足以触发这个报错；客户旧版本仅有覆盖完成、失败时间和汇总原因，不能据此还原具体入场余量。

修正后的确定性回归：覆盖阶段虚拟耗时 3,100 ms，五个合成配置仓均实际进入枚举并可激活；若枚举本身推进 2,200 ms 则只有第一个成员开始枚举、其余四个不启动，仍报无法确认，且不覆写 LKG 的盘检证据。初次定向验证 Rust 单测 308 项、HTTP 集成测试 16 项、前端组件测试 36 项通过，TS 类型检查与 Rust 库 Clippy 通过。未在客户环境重跑。

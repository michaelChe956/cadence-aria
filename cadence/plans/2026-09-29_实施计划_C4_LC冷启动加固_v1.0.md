# C4 LC 冷启动加固 Implementation Plan

> **完成状态：已实施完成（2026-09-30 打标）：对应 change `logical-codebase-bootstrap-and-repair-surface` 已于 2026-09-30 归档（`openspec/changes/archive/2026-09-30-logical-codebase-bootstrap-and-repair-surface`），终局关闸三轮予关闸（`cadence/reports/2026-09-30_终局关闸_缺口修复迭代验收_v1.0.md`），归档报告 `cadence/notes/2026-09-30_归档报告_缺口修复迭代_v1.0.md`。**

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 执行本计划。每个任务都必须按 checkbox（`- [ ]`）逐步完成；本计划只展开已批准的 OpenSpec change，不允许自行扩大范围。

**Goal:** 交付 `logical-codebase-bootstrap-and-repair-surface` 的 C4 合同：新逻辑代码库在没有手工 seed 的情况下，经唯一 authority resolver、可重入冷启动步骤和显式 repair 操作进入 `PlanningReady`；失败时保留可读事实、进入产品化等待面，并在用户到点处理后复用原链继续。

**Architecture:** 在现有 `RepositoryRouting`、LC registration batch、aggregate initialization/index operation、identity migration journal、policy/gateway 和 EventHub 之上增加一层稳定的 authority/bootstrap 投影与薄应用动作入口，不创建第二套 durable operation 状态机。冷启动依赖顺序固定为 `identity → manifest/checkout → rules/policy → member index → aggregate index active`；步骤事实分别落在既有登记批次、manifest/checkout、policy、aggregate initialization checkpoint、aggregate index 和 journal 中，GET 只组合这些事实，显式 POST 才推进或修复。失败先持久化，再通知；用户完成准备、继续、重试、核验或 mapping 裁决后，由原 registration/index/provider 编排链从 checkpoint 继续。

**Tech Stack:** Rust 2024、Axum、Tokio、serde、现有文件锁与原子 JSON store、真实 Git 只读探针、CodeGraph/aggregate-index CLI；React、TypeScript、Vitest、Testing Library。不得新增外部依赖。

**Spec:** `openspec/changes/logical-codebase-bootstrap-and-repair-surface/{proposal.md,design.md,tasks.md,specs/logical-codebase-registration/spec.md,specs/logical-codebase-aggregate-index/spec.md,specs/codebase-kinds/spec.md,specs/project-rule-aware-prompts/spec.md,specs/session-policy-envelope/spec.md}`；上位合同为 `cadence/designs/2026-09-28_方案设计_真实链缺口修复总方案_v1.2.md` §5.3、§5.5、§6.2 A03/A04、§6.3；步骤格式参照 `cadence/plans/2026-09-27_实施计划_WIGAutopilot_P2后台coding链_v1.0.md`。

## Global Constraints

- **自动推进＋人到点处理：** 无人工门且副作用可证明安全时，成功步骤自动进入下一步骤；遇到 mapping 冲突、source digest 漂移、规则/政策/capability 缺失、gateway 不可用或 provider 外部副作用未知时，必须持久化等待事实、展示原因和按钮，等用户明确点击后继续。不得把等待伪装成成功，也不得后台盲重。
- **唯一 authority：** 任何带 LC 身份的成员、checkout、manifest、selection、policy、rules reference、member index、aggregate index 和 provider target 均由同一个 resolver 从 `logical-codebases/{lc_id}/` 权威子树解析；单仓只从对应真实物理仓布局解析。不得按路径存在性猜测、跨 LC 回退、以项目级历史布局或“最新可用”记录静默替代当前 authority。
- **代码库 kind 互斥：** `single_repo` 与 `logical` 是同级且互斥的 target kind；kind 缺失、kind 与 issue/enrollment 不符、重复候选、target 身份不一致或跨 kind 访问一律 fail-closed，返回结构化冲突和重新选择/核验动作。源码中的 `RepositoryRouting::Legacy` 枚举名保留，不作为产品文案。
- **冷启动顺序：** 必须严格按 `identity → manifest/checkout → rules/policy → member index → aggregate index active` 推进；active aggregate index 不是成员登记和前置材料的准入条件。现有 `AggregateInitializationStepKind::V1` 的五步协议（`machine_skills → aggregate_preflight → pre_check → rule_and_mcp_config → openspec_and_examples`）保持独立，不能被改名、冒充或当作 C4 的五步协议。
- **可重入与版本绑定：** 每个动作带 `command_id`、目标身份和 expected revision/object identity；同一命令键重放必须返回同一 durable 结果，不得再次执行 provider turn、登记 attach 或 index build；过期 revision、错误对象、错误 LC 或错误 kind 必须 fail-closed。不可证明 provider 外部副作用是否发生时，转人工核验而不是宣称 exactly-once。
- **GET 纯投影：** 详情、成员、policy、rules、bootstrap、aggregate index 和 aggregate initialization GET 只能读取 durable projection、缺失材料、checkpoint、失败原因和允许动作；MUST NOT 启动 provider、checkout、registration、repair、index、recovery 或任何状态突变。当前 GET 中的 `recover_interrupted` 必须迁移到显式动作。
- **复用现有事实：** 复用 registration batch、`AggregateInitializationOperationStore`、`AggregateIndexStore/Operation`、`IdentityMigrationJournalStore`、`AggregatePolicyArtifactStore`、`LogicalCodebaseProviderGateway` 和 EventHub。不得建设通用 durable operation 平台、全局 owner/fence/epoch、自动 takeover 或第二套 durable 状态机；新增的 bootstrap 类型只能是投影、命令和薄应用服务，不能另建并行权威记录。
- **登记安全：** preflight 和登记 attach 只能执行现有只读 Git 探针；成员仓不得被 checkout、reset、branch、index、config、commit 或写入规则。首建不要求用户手工复制 `selection/manifest/policy/index/rules/capability`，所有材料必须由产品动作产生或核验。
- **identity repair 安全：** repair 入口绕过普通成员列表和成功身份解析，直接读取 journal/registry/authority metadata；不删除 journal、不直接编辑权威 JSON、不自动吞并 mapping 冲突、不在用户确认前切 read authority。安全 prefix 也必须由用户确认，并追加可审计 repair 事实。
- **index 失败语义：** 首建 Building 记录必须先于 CLI/index 命令落盘；首建失败或首建期间成员 HEAD/dirty 漂移保留 `Failed`，无 active 时投影 `missing`；已有 active 的刷新失败保留 last-known-good 并投影 `degraded`；只有成员覆盖、代表性查询、排除查询和 revision 全部验证成功才能变为 `Active/PlanningReady`。single-writer 继续由现有文件锁和 HTTP guard 双重约束。
- **provider 准入：** 预检必须检查真实 provider 将消费的成员 `.claude/rules/language.md`、聚合 policy artifact 的 `policy_id/revision/digest` 和实际 gateway capability 谓词；`authority_root` 不是 `AggregatePolicyArtifact` 的字段，而是 `SessionPolicyEnvelope` 的字段（`src/product/logical_codebase/policy.rs:179-195`，`#[serde(default)] pub authority_root: PathBuf`），漂移断言经 resolver 冻结的 authority root 与 `ValidatedSessionLaunchPolicy::envelope().authority_root` 比对。`ProviderCapabilityStore::ensure_bootstrap` 仅是记录初始化，不能证明真实能力；不得复制一次规则、写假 capability、绕过 gateway、回落旧路径或静默切换 provider。spawn 前还必须使用 `SessionPolicyEnvelope` 和既有 `revalidate_before_spawn`。
- **通知先事实后投影：** 失败/等待、checkpoint、repair audit 和 action result 先写已有 durable record，再调用 `EventHub::publish`；EventHub/SSE 只负责通知和补读触发，不承担 durable notification store。通知投递失败不得回滚业务事实，GET/页面刷新必须能补读同一等待项。
- **C4 边界与 C1 排产合同：** C4 只交付稳定 resolver、authority/policy/revision/digest、bootstrap/repair projection 与 action contract，C1/C2/C5 消费它们，不在本计划中改 `advance_plan`、coding runner/attempt claim、单仓自动化入口、完整 plan/coding 生命周期或 Pi initialization recipe。**与 C1 存在文件域交叠，不得声明“并行且不交叠”，按排产串行化执行：** C4 Task 2（`src/product/coding_attempt_store/{admission.rs,group.rs,group_validation.rs,group_initialization.rs}`）必须排在 C1 Task 3/6 合入之后执行；C4 Task 3/6/7/9（涉及 `src/web/types.rs`、`src/web/error.rs`、`src/web/app.rs`、`src/web/handlers/mod.rs` 与 Cockpit 投影 `web/src/state/workspace-cockpit-projection.ts`、`web/src/components/chat-workspace/cockpit/CockpitInbox.tsx`）必须排在 C1 Task 3/6/9/10 合入之后执行；C4 其余任务（Task 1/4/5/8/10 中不触碰上述交叠文件者）可与 C1 并行。C1 计划 Global Constraints 载有同一排产合同。
- **Non-Goals 继承：** 不建设新的通用 durable operation 平台；不在 GET 中启动副作用；不直接改 JSON、删除 journal 或自动解决 mapping；不实现单仓自动化、完整 plan/coding 生命周期或 Pi recipe；不放宽 LC 单 target、gateway 和真实 provider capability 边界；不把 capability 记录当真实能力证明。
- **零回归与验证边界：** 旧单仓路径、legacy alias、已有 aggregate initialization 五步、已有 last-known-good 和现有 gateway 行为必须保持；每项必须有真实行为回归测试。实施者只运行任务列出的定向命令，不运行项目级全量 build、lint、formatter 或全套测试；最终集成验证由主控统一执行。Rust 定向命令使用 `cargo test --locked --lib <filter> -- --nocapture`，Web 使用 `pnpm -C web exec vitest run <file>`。

## Review Focus

1. **旧布局、重复候选和 kind/authority 冲突：**同一 source 以别名重复提交、旧项目级布局与 LC 子树并存、single repo 身份访问 LC 或 issue 绑定不符时，必须返回结构化冲突且不写成员、不猜路径；由 **Task 1/Task 2** 的 resolver 路由行为测试覆盖。
2. **冷启动中断、页面关闭、GET 重复查询和显式继续：**查询 Running operation 不能 recovery 或启动 provider；用户关闭页面后再次 GET 必须看到原 checkpoint，只有带正确 command/revision 的继续动作推进且不重跑已完成 provider turn；由 **Task 3/Task 4/Task 6** 覆盖。
3. **首建 index 漂移、single-writer、last-known-good：**首次构建失败/漂移不得伪造 active；已有 active 刷新失败必须 degraded 且保留可读 generation；并发重建必须 409；由 **Task 5** 覆盖。
4. **Failed journal digest/mapping 冲突与未确认切读：**安全 prefix 可读但需确认；digest 漂移或多候选 mapping 必须等待和人工提交，确认前 journal、authority、read mode 和 provider 启动计数均不变；由 **Task 7** 覆盖。
5. **规则、policy、capability 缺失或漂移：**实际 `.claude/rules/language.md` 缺失、policy digest/revision/authority_root 漂移、gateway 不支持或只有 bootstrap capability 记录时，provider 必须零启动并给出准备/核验动作；有效材料才允许 envelope 启动；由 **Task 8/Task 9** 覆盖。

### 5. 比例、边界与交接自审

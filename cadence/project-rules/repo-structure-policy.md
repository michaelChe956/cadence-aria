# 仓库结构与合并方式规则（强制）

## 适用范围

本规则适用于本仓库的所有会话、操作者和子代理，与 [main 分支保护规则](branch-protection.md) 同时生效。

## 强制要求

### 1. `core.bare` 恒为 `true`，禁止任何形式修改

- 主仓的共享 Git 配置必须保持 `core.bare=true`。禁止设置、取消设置、临时覆盖或通过工具间接改写该值；不得把改动它作为任何操作的前置条件。
- 创建或移除工作树前后，只读核验 `git config --local --type=bool --get core.bare` 返回 `true`，且 `git worktree list` 仍将主仓标为 `(bare)`。发现异常或无法核验时，停止写操作并报告，不得自行改写配置。

### 2. 所有内容必须在功能分支的 worktree 中实施

- 代码、文档、规则、配置和脚本的新增、修改与删除，都必须在本仓库已登记的功能分支 worktree 中进行。动手前用 `git worktree list` 核对路径和分支；不得在 bare 主仓目录或 `main` 工作树中实施变更。
- bare 主仓只承载共享 Git 数据和工作树登记。其根目录的遗留文件和目录不是工作区；不得在其中创建、编辑或清理项目内容。测试产物仍遵循 [/tmp 隔离规则](test-content-tmp-only.md)。

### 3. 区分同步基线和交付改动

- **同步基线（不用 PR）**：在自己的功能分支 worktree 中，可以把 `origin/main` 已有的改动合入当前功能分支，并在这里解决冲突。这样只更新功能分支，不会修改 `main`。多人共用的功能分支建议用 `merge` 同步，不改写已共享的提交历史。
- **交付改动（必须走 PR）**：除上述同步外，跨分支交付代码、文档、配置或规则等变更都必须通过 GitHub Pull Request。只要目标是 `main` 或明确指定的共享集成分支，就不能用“同步基线”为由跳过 PR。
- 禁止在本地直接合并到 `main`，禁止用直推、强推或其他方式绕过 PR。需要同步本地 `main` 时，只允许快进到已经通过 PR 合入的远端提交，不得在本地 `main` 创建提交。
- 远端 `main` 的分支保护用于强制 PR；现有本地 `pre-commit` 继续负责拦截 `main` 上的直接提交。发布另遵循 [版本发布策略](release-policy.md)。

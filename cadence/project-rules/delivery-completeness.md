# 交付完整性规则（用户可操作能力 ≠ 后端接口）

日期：2026-10-30
状态：已启用（强制）
触发来源：一次真实遗漏——owner 要求「提供一个重新 Cadence-skills 初始化的**按钮**」，实现只做了 `POST .../reinitializations` 端点，任务清单里没有前端任务、k3 审查把它归入「可接受」、自测只走 curl 不验证页面，三层连续漏掉，最终用户在界面上**无入口可点**。

## 核心原则

> **owner 说「按钮 / 页面 / 用户能看到 / 能操作」时，交付物是「用户在界面上能完成这件事」，不是「有个接口」。**
> 接口是手段；**用户路径可达**才是验收标准。

## 规则 1：需求 → 任务拆解必须含前端与 UI 验收（根本防线）

写 `tasks.md` / 实施计划时：

1. 若 owner 需求措辞含 **「按钮 / 页面 / 界面 / 入口 / 能看到 / 能点 / 交互」** 等用户可见表述，任务清单**必须**同时包含：
   - 前端实现任务（具体文件 + 具体交互）
   - **UI 验收用例**（断言用户可见文案、按钮在哪些状态下出现/不出现、点击后调用哪个接口）
2. **只列端点＝任务未拆完**。禁止把「提供 X 能力」等价为「新增 X 接口」。
3. 若某能力只在特定状态才有意义（如「聚合初始化完成后才能重新初始化」），任务里必须写清**状态矩阵**：每个状态下显示哪个按钮、其余按钮是否隐藏，并为矩阵每一格写用例。

## 规则 2：k3 审查的「可接受（记录即可）」不得收录用户可见入口缺失

k3 独立审查出结论后，controller 复核三档归类：

- **「用户可见入口缺失 / 用户路径不可达」一律不得归入「可接受（C 档）」**，必须提到「必须先修」。
- 同理应升档的还有：契约与实现明显矛盾、可导致不可恢复数据丢失、会让 owner 既定主流程中断的问题。
- 若确实认为可延后，必须**显式写明**「本批不交付、owner 已知悉」，不得以「记录即可」含糊放过。

## 规则 3：自测必须覆盖真实交互面

声称「完成/可测」之前：

1. **凡涉及用户交互路径的改动，自测必须有页面级验证**（浏览器打开、点击、观察界面结果），**不能只用 curl/API 证明接口通**。
2. API 自测通过 ≠ 功能可用；前端资源是否更新、按钮是否渲染、状态矩阵是否正确，都必须看页面。
3. 自测报告里要写清「我点了什么、看到什么」，而不是只贴 HTTP 200。

## 规则 4：前端产物交付校验（重发必查）

本仓前端资源打包进 Rust 二进制（`web/dist` → release 二进制）：

1. 改动 `web/src/**` 后，**重发前必须重建前端产物并重建二进制**；只重建二进制而 dist 未更新，等于没发。
2. 重发后**必须验证页面实际拿到的资源包含本次改动**（例如拉取 `/assets/index-*.js` 检查关键文案，或核对 asset hash 与本地 dist 一致）。
3. 判断依据优先级：**页面实际加载的 JS** > 二进制内字符串扫描（二进制可能压缩嵌入，`strings` 为 0 不代表缺失）。

## 违反判定

出现下列任一情形，视为**交付未完成，不得声称完成**：

- owner 要「按钮」，交付只有端点 → 未完成
- 任务清单缺前端任务或 UI 验收用例 → 未完成
- k3 已指出「用户可见入口缺失」而未被修复或被降档 → 未完成
- 自测只覆盖 API 未覆盖页面 → 未完成
- 前端改动已提交但运行实例仍是旧资源 → 未完成

## 检查清单（交付前逐项打勾）

- [ ] owner 需求里的每个用户可见名词（按钮/入口/页面/提示）都能在界面上找到对应物
- [ ] `tasks.md` 含前端实现任务 + UI 验收用例（含状态矩阵）
- [ ] k3 结论中没有被降档的「用户可见入口缺失」
- [ ] 自测包含页面操作证据（点了什么 → 看到什么）
- [ ] 前端改动已重建 dist + 二进制，并验证页面实际加载的新资源含该改动
- [ ] 交付说明中列出「用户能怎么做」，而不只是「接口是什么」

## 2.5 判据的源码对齐（重要：口径必须按编译后的真实语义）

## 5. 结论要点

**① 性能方向：显著改善（本次实测唯一可靠的结论）。**
墙钟中位 **-40.0%**（置换 p = 0.0192）、output 中位 **-22.8%**
（p = 0.0114）、thinking 中位 **-22.8%**（p = 0.0145）、
成本中位 **-19.4%**（p = 0.0242）、turns 中位 **-17.5%**
（p = 0.0369）。
**几何均值比**（对数尺度，抗离群）：墙钟 **0.533**（即快约 47%）、
output **0.592**、成本 **0.589**。
input 中位 -14.2%（p = 0.2137）方向一致但未达显著。
**敏感性分析**（各档去掉最慢 1 次离群）仍全部显著 ⇒ 结论稳健。

**② 质量方向：完全没有可测差异 —— 这推翻了 n=2 时我的改写。**
`unknown_done_when_ref` 越界率：xhigh 中位 **5.6%** vs high 中位 **5.0%**，
秩和置换检验 **p = 0.8039 ⇒ 未达显著**；汇总率 **26.2%** vs **24.2%** —— 几乎相同。
逐次分布也几乎一致（两档各 5 次为 0%，其余散布 10%~88%）。
⇒ **effort 档位对 IR 拒收风险没有影响**；越界是**纯随机现象**。

**③ 越界与档位、思考量都无关。**
Spearman rho(thinking 深度, 越界率) = **-0.056**（≈0）。
⇒ **cross-WI 缺陷的主因不是 effort 档位**，降档顺带解决它只是 n=2 的小样本假象。

**④ 对方案的直接影响（三处，均已落档）。**
- **方案 A（命名域 `WIC-` + 服务端命名策略）是越界的唯一根治手段** —— 它的验收 MUST 是
  **≥10 次真实运行的越界率分布**（中位数 + 0% 占比）与基线分布对比，单次「没报错」不能证明有效
  （已写入 `isolate-plan-criterion-namespace` tasks 1.4）。
- **G-1（effort）的价值定位是「省时长 / token / 成本」，不是「保质量」** —— 主方案 §9 里
  基于 n=2 写入的「首要收益 = 降低 IR 拒收率」**已撤回**。
- **G-5（上下文直供）可能反向的风险仍未排除** —— 直供更多事实可能诱发更多思考 ⇒ 提高越界风险；
  本实验未测 G-5，实施后必须专门复测越界率。

**⑤ 挖出一条独立于 effort 与命名域的平台缺陷（Q-7）。**
`lower.rs:522` 的 task 字段是**赋值覆盖**（后者胜、**无诊断**）⇒ 模型多写的 AC 被静默丢弃
（实测两档都高频：xhigh 49 处 / high 61 处），
直接造成「验收标准定义了却无人验证」。**A 包修不了它，effort 降档也压不掉它** ⇒ 需独立归属。

## 6. 局限（必须随结论一起引用）

1. **样本量**：owner 授权的 10 次/档**已跑满**（见 §4 表头 n=10/10）。**但同档内方差极大**
   （xhigh 墙钟极差 **293.3~1947.6 秒（6.6 倍）**、含两次 $7.42 与 $14.68 的离群运行；
   越界率极差 0%~88.2%）⇒ 结论只能读**中位数 + 分布 + 秩和检验**，不能读单点、也不能读均值。
2. **装置级 ≠ 平台全流程**：绝对量级显著小于原现场（原现场 author_run 2679s，本次 xhigh ~419s）——

3. **【装置保真度缺口】本次运行 `mcp__codegraph__` 工具未被授权** —— fixture 的
   `.claude/settings.json` 里有 `permissions.allow: ["mcp__codegraph__*"]` 与

4. **方案本身未实现**：本对照测的是「档位」这一个变量，**不覆盖** A/B/C/E/G 包的效果。
5. **单仓单需求**：一个 issue、一个 fixture；不能外推到其它需求形态。
6. **未测 reviewer 侧**：`codex` reviewer 的投影裁剪（`rework-prompt-input-surface`）不在本实验范围。

## 7. 本实验给方案带来的新问题（须登记）

**Q-1【已被 n=10/10 推翻，保留作过程记录】：曾据 n=2 认定「档位对 IR 拒收风险的影响远大于对耗时的影响」。**
n=10/10 的运行级秩和置换检验 **p = 0.8039 ⇒ 完全无差异**，且越界率与 thinking 深度 **rho ≈ 0** ⇒
该结论**不成立**。最终结论见 §5：effort 是**性能杠杆**（墙钟中位 -40.0%，置换 p=0.0192，显著），
**不是质量杠杆**；越界的根治靠方案 A。
> 原 n=2 结论（已撤回）：「xhigh 越界率 65% → high 5%」为小样本假象 —— n=10/10 时汇总率
> 变为 **26.2% vs 24.2%**（几乎相同），按每次运行为观测单位的中位 **5.6% vs 5.0%**（p=0.80）。
> 过程中每一档的中间结论都被后续数据修正过，**全程留档于 Q-4**。
xhigh 越界率 **33.9%**（n=6），high **2.4%**（n=5）；Fisher p=**9.7e-16**、OR=0.048。
⇒ **effort 档位首先是一个「质量杠杆」，其次才是「性能杠杆」。**
这**改变了方案的收益排序**：方案 §9 把 effort 的收益表述为「时长/token 降幅」，而实测显示它对
**IR 首次通过率**的影响更大（IR 错误直接触发重驱整轮 = 623.7 秒 + 一次压缩 + 一次 resume 上下文重建）。
⇒ 建议在方案 §9 的收益表里，把 G-1 的首要收益改写为「**降低 IR 拒收率 ⇒ 消除重驱整轮**」，
时长/token 降幅作为次要收益且**待 n=10/档 复核**。

**Q-2：G-5（上下文分级直供）可能反向 —— 未测，须专门复测。**
直供更多事实可能诱发更多思考 ⇒ 提高 cross-WI 风险。本实验**未测** G-5，故该风险**尚未排除**。
⇒ G-5 实施后**必须**复测 cross-WI 越界率，**不得**默认「直供越多越好」。

**Q-3：装置保真度缺口使绝对数字不可与原现场比。**
本次运行**没有 codegraph 工具**（fixture 的 trust 门挡掉了 `mcp__codegraph__*` 授权），
而原现场有 3 次 codegraph_explore、输出 36,589 字符（占工具输出 38.5%）。
⇒ 本装置的探索工具面**比原现场贫乏**，绝对耗时/token 不可与原现场直接比；
**可比的只有「同装置、同输入、跨档位」的相对对照**。

**Q-4：小样本会得出相反结论 —— 本次实验的三次「翻转」全过程留档。**
- **n=2 时**：「high 快 51%、IR 零错误、xhigh 恰好 15 处」⇒ 差点据此把 G-1 的首要收益
  改写成「降低 IR 拒收率」（已写入主方案，后撤回）。
- **n=6/5 时**：xhigh 出现一次 **1057.6 秒 / 141,010 output / $7.42 / 63 turns** 的极端离群运行
  （且它**越界为 0**）⇒ 均值被单点主导。
- **n=9/9 时**：high 出现 70.8% 的高越界运行 ⇒ 「high 的 IR 更好」被削弱到**不显著**（p=0.66）。
- **n=10/10 时**：xhigh 出现**第二次**极端离群（**1947.6 秒 / 144 turns / 209,867 output / $14.68**）
  ⇒ 中位数差的 bootstrap CI 被撑到**跨 0**；改用**秩和置换检验**（只看序、不看幅度）后**性能方向
  恢复显著**（墙钟 p=0.0192），而**质量方向 p=0.8039 ⇒ 彻底无差异**。
⇒ **教训（已写进方案的验收纪律）**：① 性能指标**必须以中位数 + 极差报告**；② 质量类指标**必须以
每次运行的分布报告**，不得用按引用数加权的汇总（那是加权假象）；③ **n=2 不得作为决策依据**，
即便方向一致。

**Q-5【新 · 平台侧缺陷】重复 key 静默覆盖 —— 与 effort、与命名域都无关。**
`lower.rs:522` 的 `entry.3 = split_value(...)` 是**赋值覆盖**：模型在同一 task 里写多行
`- done_when_refs:` / `- requirement_refs:` 时，**前面的值被静默丢弃**，**既不报错也不产生诊断**。
实测两档都触发（n=10/10）：**xhigh 49 处、high 61 处**。
⇒ 这是一个**平台侧的可观测缺口**（不是模型的错，也不是 effort 的错）：模型的一个常见写法，
被平台静默接受成「只保留最后一行」，导致
**① 该 task 声称要验证的验收标准凭空消失；② 落盘的 plan 与作者意图不一致**。
⇒ 建议在 `mechanicalize-plan-compile-repair`（或一个新的小 delta）里把 **task 字段的重复 key
判为诊断或错误**，而不是静默覆盖；并明确 `requirement_refs` 的**累积 vs 覆盖**语义
（`lower.rs:1041` 注释说 `capabilities`/`required_capabilities` 是**累积**语义，
而 `done_when_refs`/`requirement_refs` 是**覆盖**语义 —— 同一份 grammar 里两套语义，无文档说明）。

**Q-6：孤儿 criterion 有两个独立成因，同一后果 —— 且 A 包只修得了一条。**
「criterion 定义了却没有任何 task 验证」有两条互不相干的成因：
① **越界**（task 引用了别的 WI 的 AC）⇒ 本 WI 的 AC 无人验证 —— 这是**命名域缺陷**，A 包可修；
② **重复 key 覆盖**（Q-5）⇒ 被静默丢弃的那行 AC 无人验证 —— 这是**平台缺陷**，**A 包修不了**。

实测个案（xhigh-1，逐 WI 核对编译后生效引用）：

| WI | 声明的 criterion | 编译后生效引用 | 孤儿 | 成因 |
|---|---|---|---|---|
| WI-001 | AC-001, AC-002 | AC-003, AC-004, AC-006 | AC-001, AC-002 | ① 越界 |
| WI-002 | AC-003, AC-004 | AC-003, AC-006 | **AC-004** | ② **重复 key 覆盖** |
| WI-003 | AC-005~AC-008 | AC-002, AC-003, AC-005, AC-006 | AC-007, AC-008 | ① 越界 |
| WI-004 | AC-009, AC-010 | AC-003~AC-006 | AC-009, AC-010 | ① 越界 |

（WI-002 的 TASK-006 写了两行 `- done_when_refs:`（AC-004 / AC-006）与两行 `- requirement_refs:`
（REQ-001 / REQ-002）⇒ 依 `lower.rs:522` 的赋值覆盖语义，**编译后只剩 AC-006，AC-004 被静默丢弃**。）

⇒ **两条路径、同一后果：验收标准定义了却没人测**，而现状**没有任何机制报告这件事**。
⇒ 结论：**只上 A 包不足以闭合验收闭环**，编译器侧的重复 key 诊断必须**并行**补上。

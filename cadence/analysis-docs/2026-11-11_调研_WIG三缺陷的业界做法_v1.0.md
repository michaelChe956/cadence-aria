> 所有外部链接均于 2026-11-11 用页面/源码全文核实（非仅搜索摘要）；核心机制均摘自原文。

## 0. 结论速览

| 方向 | 一句话结论 | 可迁移性 |
|---|---|---|
| A. 校验失败后的修复/重试/降级 | 业界一致收敛为「**机械校验错误原文回灌 + 会话内追加修复轮，预算 1–3 次**」；预算耗尽后的成文降级是「**终态异常携带完整修复包**（原始输出 + prompt + 全部失败历史）」，而非静默或裸失败 | 高（终态修复包、错误分层） |
| B. finding 严重度与阻断判定 | 成熟工具**全部**把「严重度」与「阻断」分离成两个轴：规则/规则作者定严重度，**配置或策略层定阻断**；没有任何 surveyed 工具让「模型自报严重度直接充当门禁」 | 高（正是问题③第 1 点的病灶） |
| C. 多仓文件清单注入 | 三种流派并存：**预算内排序树**（aider）、**JIT 检索工具**（Claude Code/Cursor）、**混合**（预装静态 + 按需检索）；多仓归属的成文做法是「**每仓各自基准 + 就近文件优先/只读成员仓克隆**」（AGENTS.md 嵌套、Greptile Repo Clusters） | 高（多仓基线树聚合 + 归属前缀） |

## A. 结构化输出校验失败后的自我修复 / 重试 / 降级

### A.1 业界做法总表（直接回答简报三问）

| 实现 | 校验失败的重试预算 | 重试之间**改什么** | 预算耗尽后的终态/降级 |
|---|---|---|---|
| **Microsoft TypeChat** | **1 次修复**（`_max_repair_attempts = 1`） | 追加两条消息：assistant 原始输出 + user 修复指令（含校验器诊断原文） | `Failure` **保留最近一次被拒的值与响应文本**（可供下游诊断） |
| **Instructor**（567-labs） | `max_retries` 可配（`from_provider` 文档默认 0，示例常用 2–3） | 捕获校验错误 → 格式化为反馈清单 → **追加进 prompt 上下文**再请求 | `InstructorRetryException`：`failed_attempts[]`（每次的异常+原始补全）、`n_attempts`、`total_usage`、`last_completion`、**`messages`（完整会话历史，可直接续跑）** |
| **Pydantic AI** | `retries={'output': N}`（每输出工具独立计数）；与传输/SDK/回退层**不共享预算** | 校正轮在消息历史里追加 `RetryFeedbackPart`（留在历史里，后续复用历史的 run 也可见）；hook 抛 `ModelRetry` 也走同一预算 | 耗尽后 run 失败，异常为 `UnexpectedModelBehavior`，其 `__cause__` 保留 `ModelRetry` 信息（可判是否可重试） |
| **LangChain** `RetryWithErrorOutputParser` | 1 次修复 | 把**原始 prompt + 补全 + 抛出的错误**三者一起交给另一个 LLM 修正 | 修复仍失败 ⇒ 抛异常给调用方（无内置降级） |
| **OpenAI Structured Outputs** | **0 次重试（预防）** | 不重试，**换解码约束**：JSON Schema 编译为 CFG，逐 token 掩码非法采样 | 残余失败显式化：`refusal` 字段标记拒答、`finish_reason` 标记截断——区分「结构非法」与「安全拒答/超长」 |
| **Guardrails AI** | 由每个 validator 的 `on_fail` 动作决定 | 不只改 prompt，**改动作**：8 种 `OnFailAction` 分级 | 成文降级阶梯：`filter`（剔除非法值）/`refrain`（空值）/`fix`（静态修复）/`exception`（抛错）等 |
| **BAML**（BoundaryML） | 校验级**无自动重试**；网络级 `retry_policy`（`max_retries` + 常数/指数退避）独立配置 | 网络重试不改 prompt；校验失败直接抛类型化异常 | `BamlValidationError` 携带 `prompt`（原始提示）+ `raw_output`（原始输出）+ `detailed_message`（**含 fallback 链全部失败历史**） |

**「重试几次」的结论**：没有一个 surveyed 框架默认超过 3 次；TypeChat/LangChain 收敛在 1 次，Instructor/Pydantic AI 暴露可配预算但示例普遍 2–3。WIG 现状「恰一次教学重驱」**在业界预算区间内**，问题不在次数，在**重驱轮注入的内容与终态质量**（见 A.3）。

**「重试之间改什么」的结论**：默认只做一件事——**把校验错误的原文回灌**（TypeChat 用校验器诊断、Instructor 用错误清单、Pydantic AI 用 `RetryFeedbackPart`）；「换模型」不用于校验失败（Pydantic AI 明确把 model fallback 划为可用性回退层，与 output 校正层分开）；「换解码约束」是另一条预防路线（OpenAI），与重试正交。**没有任何框架在重驱轮默认提供新的检索能力**——重驱轮是「修正格式」而非「重新调研」。

**「预算耗尽后的降级」的结论**：成文做法是**显式终态 + 可执行修复包**：Instructor（全部尝试 + 会话历史）、BAML（prompt + raw_output + 完整失败史）、TypeChat（保留最近被拒值）、Guardrails（分级动作而非二选一）。共同点：**失败产物不丢弃、不静默**，下游（人或程序）可以拿着修复包继续。

### A.2 机制摘录与评注

#### A.2.1 Microsoft TypeChat —— 可直接借鉴的最小修复循环

- 源码：<https://github.com/microsoft/TypeChat/blob/main/python/src/typechat/_internal/translator.py#L23>（`_max_repair_attempts = 1`）；修复循环主体 <https://github.com/microsoft/TypeChat/blob/main/python/src/typechat/_internal/translator.py#L77-L125>
- FAQ（官方对机制的描述）：<https://microsoft.github.io/TypeChat/docs/faq/> ——「Validating the LLM response conforms to the schema. If the validation fails, repair the non-conforming output through further language model interaction… sends a repair prompt back to the model that includes diagnostics from the TypeScript compiler.」
- **核心机制**：`translate()` 内 `while True` 循环——先截取响应中首个 `{` 到最后一个 `}` 的片段再解析（天然容忍前后噪声），解析/校验失败则计数、把「assistant 原始输出 + user 修复提示（错误原文逐字嵌入）」追加进 `messages` 再来一轮；`num_repairs_attempted >= _max_repair_attempts` 即返回 `Failure`，且 `Failure` 一路携带 `last_failure.value`（最近一次被拒的解析值）。
- **对本仓库的启示**：① 修复轮必须**双消息回灌**（错误 + 上一次的原始输出同轮在场）——WIG 的 fresh 重驱 prompt 已带上一版全文（`sc_revision.rs` 的 `build_work_item_plan_markdown_fresh_revision_prompt`），resume 重驱靠会话历史，形态一致；② 终态保留被拒原值是低成本、可诊断的降级。

#### A.2.2 Instructor —— 反馈回灌 + 终态异常即修复包

- 文档：<https://python.useinstructor.com/learning/validation/retry_mechanisms/>
- 重试实现源码：<https://github.com/567-labs/instructor/blob/main/instructor/v2/core/retry.py>
- **核心机制**：校验失败 → 错误格式化为反馈（「The following errors occurred during validation: … Please fix these errors」）→ 注入 prompt 上下文重试，至 `max_retries`；全部失败抛 `InstructorRetryException`，字段含 `failed_attempts`（逐次 `attempt_number`/`exception`/`completion` 原始补全）、`n_attempts`、`total_usage`、`last_completion`、`messages`。
- **对本仓库的启示**：`messages`/`failed_attempts` 的设计意图就是「**落人工时附带可执行的修复包**」——人工接手者可以从最后一次补全和全部错误历史继续，而不是从零重问。这正是简报问题②「无人接手」缺口的对症做法。

#### A.2.3 Pydantic AI —— 重试分层税与可审计的校正轮

- 文档：<https://pydantic.dev/docs/ai/core-concepts/retries/>、输出与 `ModelRetry`：<https://pydantic.dev/docs/ai/core-concepts/output/>
- **核心机制**：把「重试」显式拆成 8 层（transport / provider SDK / durable execution / model fallback / model-request attempts / tool / output / hooks），**层与层不共享预算但会相乘**（文档给出最坏情况 N×F×M×K 的乘法公式与 18 次线上请求的算例）；只有最后三层是「agent retry」（每次都要花一轮模型往返），其中 output 校正在历史里追加 `RetryFeedbackPart`——**校正反馈本身留在消息历史中，可审计、可被后续 run 复用**。
- **对本仓库的启示**：WIG 的「教学重驱（作者轮）」「评审返修轮」「编译失败重驱」同样是不共享预算的三层；Pydantic AI 的文档价值在于**把预算相乘风险写成显式契约**（哪层吃哪个预算、最坏几次调用），对应本仓库「重驱恰一次闸门 + 返修轮 transition budget」的既有设计语言。

#### A.2.4 OpenAI Structured Outputs —— 预防路线：约束解码

- 博文：<https://openai.com/index/introducing-structured-outputs-in-the-api/>
- **核心机制**：JSON Schema 编译成 CFG，采样时逐 token 计算合法集合并掩码（「masks the next sampling step, effectively lowers the probability of invalid tokens to 0」）；评测：复杂 schema 遵循率 **100%**（`gpt-4o-2024-08-06` + strict）对比 `gpt-4-0613` 不足 40%。残余失败**显式分类**：`refusal` 字段（安全拒答）、`finish_reason`（`max_tokens` 截断）——结构非法在正常路径上被消灭，剩下的失败都有独立码。
- **对本仓库的启示**：不是让重试更聪明，而是**让一类非法在生成侧不可能发生**；以及「拒答/截断与结构错误分离编码」的失败分类学。迁移阻力见 4.2。

#### A.2.5 Guardrails AI —— 校验失败的分级动作阶梯（成文降级）

- 源码（动作枚举）：<https://github.com/guardrails-ai/guardrails/blob/main/guardrails/types/on_fail.py#L23-L30>
- **核心机制**：每个 validator 失败时的处置不是全局一个策略，而是 per-validator 的 `OnFailAction`：`reask`（回灌重问）、`fix`（静态修复）、`fix_reask`（先静态修复、修不过再回问）、`filter`（剔除非法值）、`refrain`（返回空）、`noop`、`exception`（抛 `ValidationError`）、`custom`。
- **对本仓库的启示**：**失败处置按「错误类别 × 可修复性」分级**，而不是所有错误共用同一条「回灌一次→终局」路径。WIG 的 `missing_section`（可机械教学）与「写范围越界」（需要事实输入）目前共用同一条教学重驱通道，分级后可以对前者加倍教学、对后者注入事实。

#### A.2.6 BAML —— 网络重试与校验失败分离 + 错误包

- 错误处理：<https://docs.boundaryml.com/guide/baml-basics/error-handling>；retry_policy 参考：<https://docs.boundaryml.com/ref/llm-client-strategies/retry-policy>
- **核心机制**：`retry_policy`（`max_retries`、`constant_delay`/`exponential_backoff`）只管网络错误；解析/校验失败抛 `BamlValidationError`，携带 `prompt`、`raw_output`、`message`、`detailed_message`（「complete history of all failed attempts when using fallback clients or retry policies」）。
- 说明：调研中未能找到「BAML 校验失败自动升温重试」的官方文档佐证，**该传闻机制不采信**；BAML 的可借鉴点是错误对象即修复包。

#### A.2.7 论文证据：哪种自我修复有效

- **Self-Refine**（迭代自反馈提升输出质量）：<https://arxiv.org/abs/2303.17651>
- **Large Language Models Cannot Self-Correct Reasoning Yet**（ICLR 2024，Google）：无外部反馈的自我纠错不升反降，prompt 里加「请检查并修正」类指令会损害表现：<https://arxiv.org/abs/2310.01798>，正式版 <https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html>
- **CRITIC**（ICLR 2024，MSR）：**外部工具反馈**（校验器/执行器）闭环下的自我纠错有效：<https://arxiv.org/abs/2305.11738>，<https://www.microsoft.com/en-us/research/publication/critic-large-language-models-can-self-correct-with-tool-interactive-critiquing>
- **对本仓库的启示**：WIG 的教学重驱用的是**机械校验器的外部反馈**（正确的一类）；而「重驱作者轮工具调用 0 次、纯文本盲改」仍属弱反馈。文献边界恰好解释了实测形态：格式类错误（`missing_section` 行号级诊断）一次回灌常可修复，**语义/事实类缺口（需要仓库事实）回灌错误文本修不动**——对应 Guardrails 的分级动作思路。

### A.3 对照本仓库问题②（现状代码锚点已核实）

现状（均已 grep 核实）：

- 作者侧结构门拒收的「恰一次教学重驱」闸门：`src/product/workspace_engine/provider_drive.rs:788-793`（`artifact_retry_attempted` 布尔）与 `:1032-1036`（已重驱过 ⇒ `finish_invalid_workspace_artifact_after_retry`）；结构门/编译/IR 重驱**共享唯一槽位**：`src/product/workspace_engine/tests/single_candidate.rs:1546-1547` 注释。
- 重驱 prompt 构造：`src/product/workspace_engine/prompts.rs:209` `build_work_item_plan_compile_reredrive_prompt`；对 `unknown_structured_key` 已附 14 个合法 section/key 白名单（`workspace_engine/tests.rs` 内 `compile_reredrive_prompt_lists_section_whitelist_for_unknown_key` 断言）。
- coder 侧同型机制（参照先例）：`src/product/coding_workspace_engine/coding.rs:3-7`（`CODING_OUTPUT_TEACHING_REREDRIVE_NODE_TITLE`，timeline node 存在性即持久恰一次闸门）+ `coding.rs:491-498`（重驱轮复用会话/错误原文回灌）。

与业界对照的**缺口清单**（供设计任务取用）：

1. **终态无修复包**：`finish_invalid_workspace_artifact_after_retry` 之后计划停在 draft、失败码是 `missing_section:N` 等，但**没有把「最后一轮原始输出 + 全部 blocking_reasons + 重驱 prompt」固化为可接手产物**——业界（Instructor/BAML/TypeChat）全部保留。本仓库已有 timeline node 先例（coder 侧），成本最低。
2. **重驱轮零事实输入**：回灌的是错误原文与白名单（教学），对 `missing_section` 类已对路；但对需要仓库事实的错误没有「最低限度事实注入」（如缺失 section 的**同仓既有模板段**）。业界的对应物是 Guardrails 的分级动作/Pydantic AI 的 hook 注入，不引入自由工具调用。
3. **失败分类未与终态解耦**：OpenAI 把「拒答/截断」从「结构错误」里分出来；本仓库 `missing_section`（可教学）、`invalid_work_item_id`（可机械改写）、`write_scope_out_of_bound`（需事实）目前共用同一通道同一预算。

## B. finding 严重度分级与「必须修复 vs 建议」判定

### B.1 业界做法总表（直接回答简报三问）

**问：成熟 lint/review 工具如何定义「阻断」？** 一致答案：**阻断不是 finding 的内在属性，而是策略层（配置/阈值/门禁）作用于严重度轴的结果**。

| 工具 | 严重度轴（谁来定） | 阻断轴（谁来定） | 两轴是否分离 |
|---|---|---|---|
| **rustc** | 六级：allow/expect/warn/force-warn/deny/forbid，**每条 lint 有编译器内置默认级** | crate 属性 / `-D` `-A` / `-D warnings` / CI 策略；`forbid`/`force-warn` 一旦设定**不可被下游降级** | ✅ 规则作者定默认级，构建配置定实际阻断 |
| **ESLint** | 规则只声明 `meta.type`（problem/suggestion/layout），**severity（0/1/2）完全由配置文件赋值** | `error` 影响退出码；`warn` 不影响，除非 CLI `--max-warnings N` 设阈值 | ✅ 严重度是配置、阻断是阈值 |
| **Semgrep** | `severity: LOW/MEDIUM/HIGH/CRITICAL`，**由规则作者写在 YAML 里**（旧 ERROR/WARNING/INFO 映射到 HIGH/MEDIUM/LOW） | CLI `--error`（「Exit 1 if there are findings」）与 CI 策略 | ✅ |
| **reviewdog** | 诊断自带 severity（RDF: UNKNOWN/ERROR/WARNING/INFO） | 独立的 `-fail-level`：none/any/info/warning/error，「达到该级及以上才 exit 1」 | ✅ 显式双轴（`FailLevel` 枚举 + `ShouldFail()`） |
| **SonarQube** | issue 严重度（BLOCKER…INFO） | **Quality Gate 条件**＝度量 × 比较符 × 阈值（如「Blocker issue > 0 ⇒ fail」），且只作用于**新代码** | ✅ 且门禁是可组合条件，不是严重度的直接映射 |
| **CodeRabbit**（AI review bot） | severity ∈ Critical/Major/Minor/Trivial/Info + 6 个分类轴（Security & Privacy 等）；**findings 与 nitpicks 分区** | 「actionable findings」才 request-changes；`max_merge_risk` 阈值与团队/路径 override 可强制人工 | ✅ 模型产出严重度，但阻断由 actionable 定义+风险策略决定 |
| **SARIF 2.1.0**（OASIS 标准） | `result.level` ∈ none/note/warning/error | 标准不定义阻断；由消费端（GitHub checks、CI）决定 | ✅ 交换格式本身两轴分离 |

**问：严重度与可操作性是否分离？** 是，且各有定型做法：ESLint 用 `type`（problem/suggestion）与 severity 正交；CodeRabbit 用「findings vs nitpicks」物理分区 + 「Potential Issue / Refactor Suggestion / Nitpick」标签；rustc 用 lint group（`warnings`/`unused` 等）与 level 正交。**没有一个工具把「可操作性」折进「严重度」单轴**。

**问：模型自报的严重度是否被信任？** surveyed 范围内**没有**任何工具让模型自报的严重度直接充当阻断门禁：传统工具的 severity 出自规则作者（Semgrep YAML、rustc 内置默认）；最接近的 AI review bot（CodeRabbit）由模型产出 severity，但阻断判定走「actionable」定义 + 风险阈值（`max_merge_risk: minimal|low|moderate|high|critical`）+ 人工覆盖（`@coderabbitai approve/resolve`、路径 override 强制 human approval），并给每条 finding 留了「Comment is not true」等驳回反馈通道。即：**模型可以建议严重度，门禁权在平台策略**。

### B.2 机制摘录与评注

#### B.2.1 rustc：默认级 + 可提升/可锁定 + 组覆盖

- 官方文档：<https://doc.rust-lang.org/rustc/lints/levels.html>
- **核心机制**：六级体系中 `deny` 产出 error、`warn` 产出 warning；每条 lint 有默认级，可被 crate 属性 `#![deny(lint)]` / CLI `-D lint` 提升、`-A` 降级，**后写的赢**（`-D unused -A unused-variables` 即组内打洞）；`forbid`/`force-warn` 一旦设定不可覆盖（「cannot be overridden to be anything lower」）；`--cap-lints` 是依赖编译时的封顶机制。lint group（如 `unused`）允许批量定级再单条打洞。
- **对本仓库的启示**：这正是「**平台硬规则先于模型自报**」的成熟形态——本仓库 `classify.rs` 已有同型先例（`disposition != actionable` 时压过 `class_hint`，REQ-WSC-12），缺的是把 `severity=suggestion` 也纳入平台硬规则，而不是在 suggestion 分支继续采信 `class_hint`。

#### B.2.2 ESLint：severity 属于配置、阈值属于 CI

- Configure Rules（Rule Severities）：<https://eslint.org/docs/latest/use/configure/rules#rule-severities> ——「"warn" or 1 - turn the rule on as a warning (**doesn't affect the exit code**)」
- CLI `--max-warnings`：<https://eslint.org/docs/latest/use/command-line-interface#--max-warnings>
- **核心机制**：规则本体不携带严重度；同一规则在不同配置里可以是 error 也可以是 warn；warning 默认不阻断构建，CI 用 `--max-warnings 0` 把「警告数量」变成显式阈值策略。
- **对本仓库的启示**：`severity` 字段（作者/评审语境下的 must_fix/suggestion）应像 ESLint 的 `meta.type` 一样只是**描述性元数据**；进不进「必关闭集合」由平台规则表决定，且阈值显式（如「suggestion 类永不阻断」）。

#### B.2.3 Semgrep：规则作者定级、阻断在 CI 开关

- 规则语法（severity 行）：<https://docs.semgrep.dev/writing-rules/rule-syntax#schema> ——「Severity can be LOW, MEDIUM, HIGH, or CRITICAL… The older levels ERROR, WARNING, and INFO match HIGH, MEDIUM, and LOW.」
- CLI `--error`：<https://docs.semgrep.dev/cli-reference> ——「Exit 1 if there are findings.」
- **核心机制**：severity 是规则的**作者标注**字段（Supply Chain 场景改用 CVE 赋级，说明「谁对严重度负责」是按数据来源显式声明的）；是否阻断由命令行/CI 策略决定。

#### B.2.4 reviewdog：`fail_level` —— 阻断阈值的参考实现

- 源码：<https://github.com/reviewdog/reviewdog/blob/master/fail_level.go#L12-L26>（枚举）、<https://github.com/reviewdog/reviewdog/blob/master/fail_level.go#L66-L75>（`ShouldFail`：`severity <= minSeverity` 才失败）
- **核心机制**：报告侧 severity 与退出码侧 `fail_level` 是两个独立参数；`-fail-level=error` 表示只有 ERROR 级才让 CI 失败。GitHub issue #1937 还展示了「fail-level 与 runner 配置级交互」的边界争议，说明两轴分离后需要明确**优先级规则**（显式配置 > runner 默认）。

#### B.2.5 SonarQube：Quality Gate＝条件组合，作用于增量

- 官方文档：<https://docs.sonarsource.com/sonarqube-server/10.6/user-guide/quality-gates#defining-quality-gates>
- **核心机制**：门禁条件＝「度量 × 比较符 × 错误值」（官方例：measure=`Blocker issue`、operator=`>`、value=`0`，即「无新 Blocker」）；推荐的 *Sonar way* 门禁是四个**新代码**条件（无新 issue、热点 100% 复审、覆盖率 ≥80%、重复 ≤3%）——**阻断看增量而非存量**，且同一严重度在不同项目可配不同门禁。

#### B.2.6 CodeRabbit：AI 评审 bot 的阻断模型（与问题③同构）

- 自动审批/请求修改：<https://docs.coderabbit.ai/pr-reviews/automatic-approvals> ——「CodeRabbit requests changes on **actionable findings** and approves once its feedback is resolved」；配置项 `reviews.auto_approvals.enabled` 的语义即「Request changes for **blocking** findings」；`max_merge_risk`/`max_security_risk` ∈ minimal…critical，可按团队/路径 override 强制人工。
- findings 与 nitpicks 分区 + severity 五级：<https://docs.coderabbit.ai/ide/findings> ——「The thread label combines the finding type and its severity… Severity is one of **Critical, Major, Minor, Trivial, or Info**」；nitpicks 单独分区、不占 finding 视图；每条 finding 有「Fix with AI / Ignore / Provide feedback（含 'Comment is not true'）」处置动作。
- **对本仓库的启示**：这是与 WIG 评审最同构的参照系——**模型产出 severity，但「哪些 finding 阻断」由平台的 actionable 定义 + 风险阈值决定，且始终保留人工驳回通道**。问题③第 1 点（`severity=suggestion` + `class_hint=repairable` 进必关闭集合）相当于 CodeRabbit 让每条 nitpick 都能自动 request-changes——业界没有这么做。

#### B.2.7 SARIF：行业交换标准的两轴

- 结果 schema（`level`）：<https://github.com/oasis-tcs/sarif-spec/blob/main/sarif-2.1/schema/sarif-schema-2.1.0.json>；规范正文 §3.27.10：<https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html>
- **核心机制**：`result.level` 只有 none/note/warning/error 四值（默认 warning），安全类另有数值型 `security-severity`（CVSS）——**定性级与定量分共存但分字段**；标准不规定阻断，消费端（GitHub code scanning、CI）各自定策略。

### B.3 对照本仓库问题③第 1 点

现状（已核实）：`src/product/work_item_plan_policy/classify.rs:127-139`——`disposition != actionable` 时落 `Advisory`（REQ-WSC-12 平台硬规则，**先于** `class_hint`）；但 `disposition == actionable`（含缺省）时**直接采信模型自报的 `class_hint`**（`finding.class_hint.map(class_for_hint)`）。实测样本（`verification_checks[CHECK-012]` 等）即：模型把 `severity=suggestion` 的 finding 标 `class_hint=repairable` ⇒ 进必关闭集合 ⇒ 升人工。

业界对照结论：** surveyed 的所有工具都不允许「产出方自报的级别直接决定阻断」**。本仓库已有的 `advisory_disposition_preempts_class_hint_for_classification`（tests_classify.rs:248 起）正是业界模式的局部实现——需要把同一原则扩到 `severity=suggestion` 分支。归属：简报判定此点归 `close-contract-findings-before-pass`（0/24 未实施）。

## C. monorepo / 多仓场景的文件清单注入

### C.1 业界做法总表（直接回答简报三问）

**问：给全量文件树、按需检索、还是给可调用的检索工具？** 三种流派都有头部代表，且头部实践在向「**混合**」收敛：

| 流派 | 代表 | 机制要点 |
|---|---|---|
| **预算内排序树**（静态注入） | aider repo map | tree-sitter 提取符号 → 引用图 → PageRank 排序 → **二分搜索装满 token 预算**（默认 1k tokens，无聊天文件时 ×8 扩到全仓视野） |
| **JIT 检索工具**（不预装树） | Claude Code（Anthropic 官方描述）、Cursor Agent | 只预装极轻量标识（CLAUDE.md/AGENTS.md），文件发现靠 glob/grep 工具**按需**拉取；Cursor 另用 Explore subagent 在独立上下文里做广域搜索、只回摘要 |
| **索引 + 语义检索** | Cursor codebase indexing、Greptile | 全量 embedding/代码图索引，查询时检索 top-k；Greptile 明确以 **Repo Clusters** 支持多仓只读上下文 |
| **混合**（Anthropic 的推荐姿势） | Claude Code | 「CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate… just-in-time」 |

**问：多仓（多个 git root）时如何标注归属？**

- **AGENTS.md 嵌套约定**（开放标准，Codex/Cursor/Aider/Jules 等共 60k+ 仓库采用）：monorepo 内**每个子项目各放一份 AGENTS.md**，agent 读取「距被编辑文件最近的文件」——「The closest AGENTS.md to the edited file wins」；OpenAI 主仓现有 88 个 AGENTS.md。<https://agents.md/>
- **Greptile Repo Clusters**：把 ≤20GB 的一组相关仓建成簇，评审任一成员的 PR 时**其余成员只读克隆为上下文**；等价于 `.greptile/config.json` 的 `context.repos` 字段，显式列出的 repos 优先。<https://www.greptile.com/docs/code-review/cross-repo-context>
- **Cursor multi-root workspaces**：每个 workspace folder 的上下文对 Agent 可用，但**依赖单一 git 根的特性（如 worktrees）被禁用**，云端 Agent 不支持 multi-root——多仓支持是有显式边界声明的。<https://cursor.com/docs/agent/tools/search>

**问：上下文膨胀怎么控？**

- **预算 + 排序 + 装配算法**：aider 的 `map-tokens`（默认 1k）+ PageRank 重要性排序 + 二分装配（误差 <15% 即停）；无聊天文件时自动放大（`map_mul_no_files=8`）。
- **compaction / 结构化笔记 / 子代理**：Anthropic 的长任务三板斧（压缩历史、外置笔记、子代理隔离探索上下文），核心原则「find the smallest set of high-signal tokens」。<https://www.anthropic.com/research/effective-context-engineering-for-ai-agents>
- **硬上限**：Greptile 簇总量 ≤20GB——多仓聚合有显式容量上限。

### C.2 机制摘录与评注

#### C.2.1 aider repo map —— 预算内排序树的最完整开源实现

- 文档：<https://aider.chat/docs/repomap>；源码 <https://github.com/Aider-AI/aider/blob/main/aider/repomap.py>（`__init__` 默认 `map_tokens=1024` 在 <https://github.com/Aider-AI/aider/blob/main/aider/repomap.py#L46>；图构建与 `nx.pagerank(G, weight="weight", **pers_args)` 在 <https://github.com/Aider-AI/aider/blob/main/aider/repomap.py#L474-L529>）
- **核心机制**：tree-sitter 抽取 def/ref 标签 → 构建「引用文件 → 定义文件」加权有向图（边权 = 标识符乘数 × √引用次数；聊天中文件作引用方时 ×50；提及的标识符 ×10；私有前缀 0.1；定义过多 0.1）→ **带 personalization 的 PageRank**（聊天文件/提及文件作为 personalization 向量）→ 得到文件-标识符排名 → `get_ranked_tags_map_uncached` 用**二分搜索**取排名前缀渲染成树，直到 token 计数贴近 `max_map_tokens`（误差 <15% 即接受）；sqlite 缓存 tags。
- **对本仓库的启示**：本仓库 D5 事前的基线树注入（`[confirmed_context]` 的 `baseline:` 段，cap = 32,000/4 = 8,000B，`sc_baseline_tree.rs:13,79` 与 `prompts.rs:384-387` 的**成员仓轮转保底截断**）已经是同构的「预算内清单」；aider 证明的是下一步方向——**预算紧张时按「与任务的相关性」排序裁剪，而不是轮转均分**。

#### C.2.2 Anthropic：JIT 上下文与混合策略（官方工程博文）

- <https://www.anthropic.com/research/effective-context-engineering-for-ai-agents>
- **核心机制**：上下文是**有限注意力预算**（context rot：token 越多召回越差）；推荐「最小高信号 token 集」；agent 只维护**轻量标识符**（文件路径、存储查询、链接）+ 工具按需加载（Claude Code 对大数据库的做法）；明确推荐混合姿势（预装 CLAUDE.md + glob/grep 按需）；长任务用 compaction / 结构化笔记 / 子代理隔离探索上下文（子代理消耗数万 token 但只回 1-2k 摘要）。
- **对本仓库的启示**：WIG 作者轮是**单发全量 prompt、无工具轮**的架构（实测重驱轮工具调用 0 次）——这决定了「JIT 检索」路线不可直接套用（见 4.2），但「**最小高信号**」原则支持继续收紧基线树/上下文面的注入内容。

#### C.2.3 Cursor：本地 grep 索引 + Explore 子代理 + multi-root 边界

- <https://cursor.com/docs/agent/tools/search>（原 codebase-indexing 页重定向至此）
- **核心机制**：Instant Grep 自建本地索引（「Cursor does not upload file paths or code to build a search index」，grep 路线不用 embedding）；广域搜索交给 **Explore subagent**（独立上下文 + 更快模型 + 并行搜索，主会话只收摘要）；FAQ 明确 multi-root 支持（每 folder 上下文可用）与边界（单 git 根特性禁用、云 Agent 不支持）。

#### C.2.4 Greptile Repo Clusters —— 多仓只读上下文的成文做法

- <https://www.greptile.com/docs/code-review/cross-repo-context>
- **核心机制**：Repo Clusters 把相关仓（服务 + SDK + 共享类型）组成簇（≤20GB）；评审簇内任一仓 PR 时，**其余成员仓被只读克隆并作为上下文提供给评审器**；显式 `context.repos` 优先于簇。这正是「聚合根多仓」场景的产品化实现：**主仓可写、成员仓只读供上下文**——与 WIG 的写范围判定（成员仓写入需授权）同构。

#### C.2.5 AGENTS.md 嵌套 —— 多仓/子项目归属标注的事实标准

- <https://agents.md/>
- **核心机制**：每仓（或 monorepo 每子项目）根放 AGENTS.md；agent 取「距被编辑文件最近」的一份，冲突时近者胜、用户显式指令最高；OpenAI 主仓 88 份。**归属信息放在文件系统就近位置而非集中清单**——多仓场景天然扩展（每仓一份）。

### C.3 对照本仓库多仓基线树缺陷

现状（已核实）：`src/product/workspace_engine/plan_preflight.rs:132-183`——`plan_baseline_tree` 经 `plan_baseline_repository_path` 按 issue 的 `repo_id` 只解析**一个**物理仓（dual 物理仓优先、回退 id 精确匹配）；编译器路径越界判定（`work_item_plan_compiler/validate.rs` + `write_scope_bound.rs`）用的是**同一棵树** ⇒ 多仓计划中 frontend/gateway 的 AC 路径必然误判「不在基线树内」；D5 事前注入同源，只能呈现事实不能修复判定。

业界对照结论：**多仓上下文的成文做法都是「每仓各自基准 + 显式归属标注 + 只读成员仓」**（Greptile 只读克隆、AGENTS.md 就近归属、Cursor 每 folder 可用），**没有**「只装一个仓的树然后让其它仓路径全部判非法」的等价物。修复方向明确：聚合根的基线树应是**成员仓树的聚合体，带仓归属前缀**，校验器与注入共用。归属：简报判定为既有缺陷、属 `REQ-WSC-02` 域（非本次三缺陷 change 的独占面）。

## 横向结论

### 4.1 可直接迁移到本仓库的 3 条做法

以下每条给「来源模式 → 本仓库落点（文件/函数级）→ 硬约束关系 → 归属」。**落点是调研级指引，详细契约由设计任务定稿。**

1. **严重度/阻断两轴分离：平台规则压过模型自报（rustc `-D` / ESLint severity-属配置 / CodeRabbit actionable 模式）**
   - 落点：`work_item_plan_policy/classify.rs` 的 `classify_finding`（:127-139）——`disposition == actionable` 分支不再直接采信 `class_hint`；`severity == suggestion` 的 finding 一律落 `Advisory`（不进必关闭集合、不驱返修），`class_hint` 仅在 `severity == must_fix` 时参与分类。配套调整 `evaluate.rs` 必关闭集合口径。
   - 验收口径：在 `work_item_plan_policy/tests_classify.rs` 仿 `advisory_disposition_preempts_class_hint_for_classification`（:248）写对照组——同一 payload `severity=suggestion + class_hint=repairable` ⇒ `FindingClass::Advisory`；`severity=must_fix + class_hint=repairable` 照旧进返修（证明判据只认 severity 轴）。
   - 代价：零 token、零预算冲击（纯 policy 层）；对既有断言的影响集中在 REQ-WSC-12 系列（advisory 先行已有测试，扩展语义兼容）。归属：`close-contract-findings-before-pass`（简报判定）。
2. **终局失败携带「可执行修复包」（Instructor `InstructorRetryException` / BAML `BamlValidationError` 模式）**
   - 落点：`workspace_engine/provider_drive.rs:1032-1036` `finish_invalid_workspace_artifact_after_retry`——终局时把「全部 blocking_reasons（逐轮）、最后一轮 provider 原始输出 ref、重驱 prompt ref」固化进 timeline node/store（先例：`coding_workspace_engine/coding.rs:3-7` 的 `CODING_OUTPUT_TEACHING_REREDRIVE_NODE_TITLE` 审计留痕 + `single_candidate.rs:1546` 共享槽位注释）。
   - 验收口径：在 provider_drive 相关测试断言「重驱后仍失败 ⇒ 终态记录包含 N 次 blocking_reasons、最后一次原始输出可寻址」；失败不静默（硬约束 5 的直接断言）。
   - 代价：store 写入，不进 prompt、**不占 23,500/32,000 任一面**；无兼容性破坏（新增终态附带物）。归属：`bound-sc-generation-teaching` 域或其子任务。
3. **多仓基线树=成员仓聚合 + 归属前缀（Greptile Repo Clusters / AGENTS.md 就近归属模式）**
   - 落点：`workspace_engine/plan_preflight.rs` 的 `plan_baseline_tree`/`plan_baseline_repository_path`（:132-183）——从「单 repo_id 一棵树」改为「聚合根全部成员仓各解析一棵、路径以仓 id/名前缀标注」；校验器（`validate.rs` 路径越界判定）与 D5 注入（`sc_baseline_tree.rs` 渲染）同源受益。
   - 验收口径：`plan_preflight` 测试新增「双成员仓 issue ⇒ 树同时含两仓路径、跨仓 AC 路径不再误判越界」；`prompt_contract_baseline_tree.rs` 的 8,000B cap 与轮转保底断言保持通过（多仓下每仓至少 1 条的既有不变量）。
   - 代价：注入字节增长受既有 cap 约束（32,000/4 = 8,000B，`prompts.rs:384-387` 轮转截断保底已覆盖多仓语义）；校验器判定从「单树成员」变「带前缀聚合树成员」，需同步 `baseline_candidates.rs` 的近邻路径建议。归属：`REQ-WSC-02` 域（既有缺陷，简报已划界）。

### 4.2 不建议迁移的 2 条及原因

1. **约束解码 / CFG 掩码（OpenAI Structured Outputs 路线）**。原因：① WIG 产物是 markdown 语法子集而非 JSON Schema，CFG 化需要重写整套「schema→文法」管线；② provider 面是 `StreamingProviderAdapter` 多厂商流式适配，没有统一的采样掩码钩子，只能在个别厂商上成立；③ 该路线的收益是「结构非法不可能发生」，而问题②的实测失败（`missing_section` 重驱后仍失败）更多是**语义/内容缺口**，掩码救不了内容。与硬约束的关系：技术上不违反预算红线，但工程面横跨 provider 层，超出本次三缺陷 change 的可控范围——作为方向性共识记录，不作落地项。
2. **给作者轮加检索工具 / 子代理（Anthropic JIT / Cursor Explore 路线）**。原因：① 工具定义与工具轮输出都计入 prompt/上下文消耗，直接冲击**固定面 23,500B 不抬**与**上下文面 32,000B** 红线（硬约束 2）；② 作者轮当前契约没有工具面（实测重驱轮工具调用 0 次），新增工具面等于新增一类运行时行为开关，逼近硬约束 3 的禁区；③ 引入不可控轮次后，「失败显式可诊断」的终态语义（硬约束 5）更难保证。检索需求应由**平台侧事实注入**（基线树聚合、同仓模板段）满足，而非作者侧工具化。

（次级否决备注：SonarQube 式五级 severity 也不建议照搬——本仓库 `must_fix/suggestion` 二值轴已覆盖 SARIF 四级/CodeRabbit 五级中的关键子集，问题③的根因是「谁说了算」而非「粒度不够」，加粒度只增加标注与维护成本。）

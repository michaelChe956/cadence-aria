# Design 链路加固需求分析

- 日期：2026-08-22
- 范围：只读审阅 Design Spec 生成、返修、review、aggregate Design 回写和确认 gate；不修改生产代码、测试或 OpenSpec。
- 对照对象：`openspec/changes/harden-story-pipeline-weak-models/`、`cadence/reports/story-weak-model-campaign/`、`.superpowers/sdd/2026-08-21_计划文档_Story链路弱模型加固与Token瘦身_v1.1/`。

## 结论

**需要做一轮更窄的 Design 专项加固，但不应复制 Story 的整套 P0：通用的 nonce、受限 JSON 恢复、few-shot、severity 三档、滑动窗口和 Kimi provider 能力已经自动覆盖 Design；必须优先修复 aggregate Design 的“提示词契约—输出提取—回写—确认”闭环，并以 Design 语料验证其结构与 review 边界。**

这里的判断有两层：

1. 对普通单仓 Design，弱模型最常见的“artifact fence / heading / ID / reviewer JSON”失效已经进入共享实现，重复改造价值低。
2. 对 aggregate Design，`involved_repository_ids` 与 `change_order` 是后续 Work Item 跨仓 `depends_on` 的控制数据。目前存在提示词要求、提取位置、nonce 认证范围和确认校验不一致的问题；弱模型少字段、将 JSON 放到 fence 外、复制旧 JSON 或只列部分仓库时，系统不能稳定地在正确位置 fail-closed。这是实质性的 Design 特有 P0 风险。

> 注意：现有 Story sanity 只有每 provider 1 个样本，且基线 120 秒、优化后 300 秒，不能推断 Design 的真实失败率，也不能作为 release gate。因此本文将“需要加固”建立在代码契约缺口和下游影响上，而不把 Story 的 0/3 → 3/3 当作 Design 的量化证据。

## 1. 链路盘点

### 1.1 普通 Design author/review 主链

```text
生成：build_streaming_input
  └─ build_prompt → parser-derived author schema + Design skeleton + history compaction
返修：build_revision_full_prompt / build_revision_delta_prompt
  └─ schema（full 另有 skeleton）+ history compaction（full）
审核：build_review_input
  └─ Design boundary rules + parser schema review gate + compact history
  └─ nonce structured review JSON → 三档 severity → review gate
确认：Story/Design review 一律回 AuthorConfirm；最终确认仍经 aggregate confirm gate（若适用）
```

`WorkspaceType::Design` 没有另一套 reviewer parser：普通 Design 和 Story 均经过 `build_review_input`、`reviewer_output_contract`、`parse_review_value`、`review_gate_for`。因此 P0/P1 的共享修复会直接生效。

### 1.2 aggregate Design 特有支路

```text
aggregate_design_scope_prompt
  └─ inventory + involved_repository_ids + change_order 指令
build_streaming_input（仅检测到 aggregate scope 的 Story/Design）
  └─ design_aggregate StructuredOutputContract + nonce schema
provider 完成
  └─ extract_artifact_content(full output)
  └─ write_back_aggregate_output(artifact_markdown)
  └─ parse_design_aggregate_output → update_design_spec_aggregate
最终确认
  └─ validate_confirm_aggregate_spec
Work Item compile
  └─ confirmed Design.change_order → cross-repository depends_on
```

该支路将 LLM 输出变成持久化调度数据，风险高于纯 Markdown 描述；也是本轮应优先处理的部分。

### 2.1 Design artifact 现有结构契约

`artifact_constraint_spec_for(WorkspaceType::Design)` 已定义：

- 必需二级 heading：设计范围、设计决策、公共组件、API 契约、数据模型、风险、追踪关系；
- 必需稳定 ID：至少各出现一个 `[DEC-*]`、`[CMP-*]`、`[API-*]`；
- 必需追踪 token：`source id`（或现有实现识别的 `issue_`、`story_spec_`、`design_spec_`、`work_item_`）；
- 禁止 Work Item Plan、任务拆分、开发任务、执行 checklist 及 `[TASK-*]`/`WI-*`；
- reviewer boundary：可执行测试计划/范围/文件/框架/命令/构建命令或把测试职责分派到组件/文件必须 `must_fix`；纯 `[DEC-*]`→`[REQ-*]/[AC-*]` 的抽象验收追踪不得因此判强返修。

所以，**Design 的 heading、三类 ID、追踪 token 与禁止项同样有弱模型“少 heading、少 ID、带错层内容”的结构失败风险，但当前普通 author gate 已具备拒绝与（可用 provider 下）重试能力。** 与 Story 相比，Design 甚至多一个必需 heading，且必须同时出现三族 ID；不能因没有 Design campaign 就假设风险更低。

同时要区分“已有 gate”与“语义充分性”：当前 validator 主要检查某类 token **至少出现一次**。它不验证每个决策是否可追踪、ID 是否唯一、每个 API/组件是否有相应关系，也不扫描正文中的所有可执行测试方案。这不是本次要求立即扩大为完整 Design 语义分析器的理由，但说明 Design campaign 必须测到这些退化形态。

## 3. Design 专属缺口

### P0-A：aggregate Design 的输出位置、nonce 与回写链不闭合

这是最优先的问题，且并非仅提示词优化。

1. **提示词要求与消费位置冲突。** `aggregate_author_output_contract` 写的是“artifact 之外必须额外输出一个 nonce sentinel block”；但 `complete_assistant_message` 先以 `extract_artifact_content(full_content)` 取得 artifact，再把 **`artifact_markdown`** 传给 `write_back_aggregate_output`。若模型遵守“artifact 外”的指令，sentinel 会被 artifact extractor 去掉，`parse_design_aggregate_output` 看不到它，回写跳过并仅追加诊断。现有 Design 回写测试为了成功，实际把 sentinel 放在 artifact fence **内部**（`src/product/workspace_engine/tests/part_02.rs:940-949`），与 prompt 契约相反，也会让控制 JSON 留在 Design artifact 内。
2. **首次 contract 没有完整贯穿返修。** 只有 `build_streaming_input` 对带 aggregate scope 的 Story/Design 设置 `StructuredOutputContract`；`build_revision_input_with_resume` 返回的 input 固定 `structured_output_contract: None`，而 `build_revision_full_prompt`、resume delta 和 `build_author_revision_prompt` 也不重新追加 aggregate metadata contract。artifact retry 虽克隆初始 `base_input`，因而保留**同一个旧 nonce contract**，但 retry prompt 本身没有 aggregate metadata 指令，也没有新 nonce。故正常 reviewer/用户返修没有 contract，artifact retry 也不是“每轮明确、独立认证”的闭环。
3. **回写重新“发现”输出，而没有使用原请求 contract 的解析结果。** `write_back_aggregate_output` 调 `parse_design_aggregate_output(artifact_markdown)`，后者经 `extract_structured_json` 调用 `parse_last_structured_output`。该 API 只验证 start nonce 与 JSON 内 nonce 彼此相等，**不知道本请求派发的 nonce**；更严重的是 `extract_structured_json` 解析 sentinel 失败后允许 raw JSON 或 Markdown `json` fence fallback。这个兼容 fallback 对 aggregate control data 破坏了 P0 “request-bound nonce”意义。
4. **失败不阻断 metadata 漂移。** 缺/错 aggregate metadata 时，artifact 仍会保存并进入 AuthorConfirm；若 record 中先前存在有效 involved/order，后续缺 metadata 的 revision 保留旧值，确认 gate 可能放行与新版 artifact 不一致的 scope。该行为对 Story 也存在，但 Design 的 `change_order` 直接影响 Work Item 依赖，所以后果更高。

**建议修复方式（Design P0，基础设施可同时复用给 aggregate Story）：**

- 把“artifact Markdown”与“aggregate metadata structured payload”分离：在 provider completion 时用**该次 `StructuredOutputContract`**解析并持有业务 JSON，回写直接消费该受认证 payload；不要从已经提取的 artifact 再猜测 JSON。
- 每个 aggregate Design author turn（初次、full revision、resume delta、用户反馈 revision、artifact retry）都生成新的 `design_aggregate` contract，并在该 turn 的 prompt 中要求独立 metadata envelope。artifact 外的 envelope 应不进入持久化 Markdown；若产品决定 metadata 放 artifact 内，则同步改 prompt 和 artifact pollution policy，但两者必须只选一个。
- aggregate metadata 专用 parser 禁止 raw/fenced JSON fallback；缺 start/end tag、nonce 缺失/错配、无效 JSON 一律按可区分诊断失败。普通 legacy helper 是否保留 fallback 应与 aggregate 专用路径隔离。
- 对“artifact 已合格但 metadata malformed”提供**一次有界 metadata-only repair**：传入已恢复/已解析的业务 JSON 或明确字段错误，只允许重发 nonce envelope，不得重新写 Design artifact。若修复仍失败，停在可见 blocker/AuthorConfirm 前，不把旧 scope 静默沿用。

### P0-B：`change_order` 的业务 schema 与确认 gate 比 prompt 弱

`aggregate_design_scope_prompt` 明确要求：`change_order` 必须“恰好覆盖全部 `involved_repository_ids` 且不重复”。实际实现有三处弱化：

|层次|当前行为|风险|
|---|---|---|
|`parse_design_aggregate_output`|`change_order` 使用 `#[serde(default)]`，字段缺失直接变为空数组；未知字段也未拒绝。|弱模型漏字段会被当作“合法但空”。|
|`validate_aggregate_design_scope`|检查 `involved ⊆ effective_member_ids`、`change_order ⊆ involved`、`change_order` 不重复；不检查 `involved` 本身去重，也不检查两个集合相等。|`involved=[A,B]`、`change_order=[A]` 会通过。|
|`validate_confirm_aggregate_spec`|仅在 logical Design 的 involved 数量大于 1 且 `change_order` **为空**时拒绝。|部分序列（例如只列 A）能确认，随后 Work Item compile 只为 order 中的仓库映射依赖，B 被遗漏。|

现有 parser 单测甚至演示 `involved=[A]`、`change_order=[A,B]` 的解析成功；后续 store 会拒绝越界 B，但 parser 层未表达完整 schema。生命周期测试覆盖了“order 在 involved 外”和“order 重复”，也明确有“空 change_order 在 Draft 可持久化”的测试；缺的是“字段缺失、空/部分 order、involved 重复、两集合不相等、旧值残留”的端到端阻断。

**建议修复方式（Design 特有 P0）：**

- 将“生成/回写的 aggregate Design payload”定义为严格业务 schema：字段必须存在；`involved_repository_ids` 非空、无重复；`change_order` 非空、无重复，并且集合与 involved 精确相等；UUID 有效；拒绝未知字段。Draft 创建阶段仍可保留空值，以支持“尚未生成”的实体，但**author 已返回 aggregate payload 的回写阶段**不能用 Draft 宽松规则代替。
- 成员归属仍以 `effective_member_ids` 作权威校验；确认 gate 也重复检查 exact-set equality，防止历史/手工数据绕过。
- 将 `change_order` 作为被确认 Design 的可审计版本字段；元数据修复或 Design revision 后若未更新，应在确认前明确失败，不继续使用旧序列。

### P1-A：Design review 的边界规则有 prompt 覆盖，但无判例或确定性兜底

好消息是：Design reviewer 的 schema gate、三档 severity 和 `EXAMPLE_NONCE` 已与 Story 同步；`part_31::design_reviewer_boundary_distinguishes_traceability_from_executable_testing` 以及 `workspace_context` 测试都确认边界文本被注入。因此**不需要再复制一套通用 reviewer few-shot 或 severity 文案**。

但 Design 的关键边界仍主要依赖弱模型读长文本作分类：

- `reviewer_boundary_rules_for(Design)` 写明“测试计划/场景/文件/框架/命令/构建命令/职责分配”必须 `must_fix`；
- 同一规则又写明纯抽象 `[DEC-*]`→`[REQ-*]/[AC-*]` 追踪不得判 `must_fix`；
- `validate_workspace_artifact_constraints` 的 deterministic 部分没有把这些自然语言边界作为 forbidden token/heading；现有测试大多验证规则字符串存在，而不是验证真实 Design candidate 得到预期 finding。

**建议：**先增加 Design reviewer 的最小对照 few-shot（有效抽象 traceability 与无效可执行测试计划各一个，均使用 `EXAMPLE_NONCE`），并加 prompt/structured-finding 回归测试。随后根据 campaign 的假阳性/漏报数据，决定是否把无歧义的 heading/命令形式提升为 artifact deterministic pre-gate；不要在没有产品边界确认时用宽泛关键词扫描误伤“设计风险”或抽象验收说明。

### P1-B：Design artifact 结构与语义缺少独立实测

Story change 的 proposal 明确将“Design 阶段的 design spec/review 优化”列为 non-goal；其 corpus、golden diff 和 sanity 都只面向 Story。现有 Design 单元测试覆盖 canonical headings、fence/retry、review prompt 和部分 aggregate 回写，但没有真实弱模型的以下数据：

- 首次 artifact fence + Design schema 一次通过率；
- `[DEC-*]`/`[CMP-*]`/`[API-*]`/source token 漏失或错误追踪的分布；
- reviewer JSON syntax/schema 成功率和 boundary false-positive/false-negative；
- aggregate metadata 的 nonce、集合/顺序合规率；
- fresh/resume 的实际 input-token usage。

**建议复用 Story campaign 基础设施，新增冻结的 Design corpus 与 normalizer：**至少覆盖单仓 API/数据模型、三仓契约→provider→consumer order、用户 choice 映射到 DEC、抽象追踪与测试越界对照、review-revision。每条记录 author、reviewer、full-chain、metadata 以及 retry；token 继续 fresh/resume 分列。通过前不得声称 Design 达到 Story 的 95% 或 40% 指标。

### P2：共享但值得一并处理的返修/瘦身缺口

1. `build_author_revision_prompt`（用户自由反馈修订）目前只要求“完整 markdown + 改动摘要”，不注入 author schema、artifact fence 解释或 skeleton；这是 Story/Design/WorkItem 的共享后门，不是 Design 独有。artifact gate 最终仍会拒绝不合格输出，但 Kimi/Pi 在 `provider_allows_artifact_retry` 中被排除，不宜长期只靠最终失败。建议作为共享小任务，把 schema/结构示例或等价明确合同补入该入口，同时保留其 bare-markdown 兼容策略的显式测试。
2. Task 4 报告已记录 reviewer compact history 会把未关闭 strong finding 加入一次，又在 `build_review_input` 追加一次；这是全 workspace 的 token 冗余，Design 也继承。它不是本轮 P0 blocker，但应在 Design token campaign 前去重或至少量化。

## 4. Story 八类发现模式与 Design 可迁移性

下表将 Task 2/3/4 报告、baseline/optimized sanity 中可复核的问题归纳为八类。它们不是八条“Design 已失败”的实测结论，而是决定本轮不应只看 prompt 文案的审阅清单。

|Story 发现模式|Story 证据|Design 对应判断|
|---|---|---|
|1. 协议 producer/fixture 遗漏迁移|Task 2 的 C1：集成 fixture 仍用旧 sentinel，后续统一迁移。|aggregate Design 的后续 revision 和 artifact 外 metadata 实际上仍未按 request-bound contract 闭环；应作为同类 P0。|
|2. 看似不在范围的 legacy/bypass 路径会绕过协议|Task 2 的 I1：runtime-unit、fake/adapter 路径最终仍需迁移，而不是简单豁免。|`extract_structured_json` raw/fenced fallback 和 `parse_last_structured_output` 的 discovered nonce 对 aggregate control data 是同类 bypass；必须隔离或移除。|
|3. few-shot 必须防照抄|Task 2：author skeleton 缺 ID/traceability，reviewer 用 `EXAMPLE_NONCE`。|普通 Design skeleton/reviewer 已覆盖；aggregate Design metadata 没有 anti-copy 的业务示例/严格成员校验组合，应补受控示例和 fail-closed 测试。|
|4. JSON 容错只能限定于已认证 sentinel 内|Task 2：多对象、超限、坏 fence fail-closed。|aggregate Design 不应在认证失败后退回 raw/fenced JSON；否则专门加的受限恢复被旁路。|
|5. severity/impact 有 live 与历史双入口差异|Task 3：live 严格三档，历史归一化，impact 并入 message。|Design review 走同一 parser，已覆盖；不需独立改 severity。Design campaign 应仍测 live malformed finding 和历史回放。|
|6. 窗口压缩不能丢 choice、未关闭 finding、canonical inputs|Task 4：三入口、fail-closed、强 finding 全文、相邻 artifact diff。|Design 同样覆盖；其 DEC/choice 和 multi-repo order 更需在多轮 case 中验证不丢失。|
|7. 窗口实现仍可能产生 token 冗余，字符数不是 usage|Task 4：未关闭 finding 可能重复；字符数只是代理指标。|Design 不应仅凭共享单测宣称 token 达标，需 fresh/resume 真机 usage。|
|8. 真实 provider 完成与单测不同，sanity 也不等于 release gate|baseline 三组在 120 秒均未完成；optimized 在更长窗口下 author 3/3 有 artifact，但 claude reviewer 未完成，且每组合仅一例。|没有 Design 真机样本，不能从 Story 数字外推；P1 campaign 是必要验证，不是可选装饰。|

另一个应谨慎解读的证据是 Kimi：`optimized-sanity.md` 首段曾记录 terminal capability 失败；Task 7 后续附录又记录通过裸 ACP 抓包修正 `terminal/output` 后的 e2e 成功。两者说明 provider 修复必须以当前版本的 Design 真机记录复核，而不是仅引用早期 Story sanity。

## 5. 建议修复清单与优先级

### P0：在进入任何 Design 弱模型 campaign 前完成

1. **aggregate Design structured metadata 闭环（最高优先级，Design 特有业务约束）。**
   - 统一 artifact 与 aggregate envelope 的物理位置和生命周期；以 request-bound `StructuredOutputContract` 的 parsed payload 回写，不再从 artifact Markdown 重新猜测。
   - 全部 aggregate Design author 路径（初次、full/delta revision、用户反馈 revision、retry）发出新 nonce、同一 metadata contract。
   - aggregate parser 禁止 raw/fenced fallback；metadata 不合法走一次 metadata-only repair，仍失败则显式阻断确认。
   - 回归：artifact 外 envelope 成功、artifact 不含 control JSON、错误/旧 nonce、漏 nonce、raw JSON、fenced JSON、重复 sentinel、full/delta/feedback revision 全部 fail-closed 或修复成功。

2. **收紧 Design `involved_repository_ids` / `change_order` schema 与确认 gate。**
   - 回写 payload 要求两个字段存在、非空、UUID 合法、各自不重复，且集合严格相等；再校验属 `effective_member_ids`。
   - `validate_confirm_aggregate_spec` 作为 defense-in-depth 再校验精确覆盖，而非只判空。
   - 回归：字段缺失、空、部分 order、order 含多余仓库、重复 involved/order、member 越界、旧 scope 与新版 artifact metadata 缺失均不能确认；正确的 1/2/3 仓 order 能映射 Work Item `depends_on`。

### P1：与 P0 合并验收或紧随其后

3. **Design reviewer boundary 判例加固。**
   - 在现有全局 `EXAMPLE_NONCE` few-shot 后追加 Design 对照：抽象 DEC→REQ/AC traceability 是 suggestion/不报强返修；明确测试计划/命令/文件/职责分配必须 `must_fix`。
   - 增加真实 candidate→review finding 的 fixture；根据数据再决定无歧义文本是否升格到 deterministic pre-gate，避免关键词误杀。

4. **Design 弱模型 campaign、normalizer 与 gate。**
   - 复用 Story manifest/统计程序，单独冻结 Design corpus/golden，不修改 Story golden 语义。
   - 指标至少含 artifact schema 一次通过、reviewer syntax+schema、full chain、aggregate metadata exact-set 通过、边界分类、retry、fresh/resume usage 和工具可用性。
   - 在有等量配对样本前，不宣称 95% 成功率或 ≥40% token 降幅；现有 Story 1 样本 sanity 不可替代。

### P2：可与后续共享可靠性/瘦身任务合并

5. **补齐 `build_author_revision_prompt` 的共享 author contract**（schema/输出格式/anti-copy 或明确兼容策略），并覆盖 Design 用户反馈修订。
6. **清理 reviewer prompt 中未关闭 strong finding 的双重重放**，随后以 Design 多轮样本核对 token 实际 usage。
7. **验证而非重写 Kimi provider 层**：Design campaign 在当前 CLI/adapter 版本上记录 terminal/fs/MCP 可用性；MCP gateway 接线问题按 provider/envelope 全局事项跟踪。

## 6. 建议验收矩阵

|层级|最小验收证据|
|---|---|
|aggregate contract|每条 aggregate Design author 路径都有 request nonce；artifact 外 metadata 成功回写且不污染 Markdown；任何非 contract JSON 不被采用。|
|metadata schema|字段缺失、nonce 错配、无效 UUID、空/重复/部分/额外 order、非成员 ID 均 fail-closed；正常 1/2/3 仓输出持久化并保留 order。|
|final gate/downstream|确认 gate 拒绝不完整 order；Work Item compile 只在 confirmed、精确 order 下建立跨仓 depends_on，并验证无环。|
|artifact/review|Design 7 heading、三族 ID、source、禁止项、abstract traceability 与 executable-testing 两类边界均有正反用例；review JSON 仍只接受三档 severity。|
|弱模型实测|冻结 Design corpus，按 provider×strategy 记录 author/reviewer/full-chain/metadata 四口径和 usage；报告样本数、超时、retry 与失败分类。|

## 7. 残余风险与不建议做的事

- 不建议再为 Design 单独复制 nonce parser、severity enum、history compactor、Kimi client service；这些都应继续是共享设施，复制会重新制造 Task 2 所解决的协议漂移。
- 不建议立刻把所有 Design 内容质量都做成关键词 validator。当前 parser schema 有意只承诺 heading/ID/token/禁止项；“设计质量”“测试职责是否可执行”等需要先用对照样本确定可安全机械化的边界。
- P0 修复若改变 aggregate envelope 的持久化位置，需要一次性更新 artifact extraction、stream display、writeback、恢复和 fixture，避免出现“prompt 在 artifact 外、consumer 在 artifact 内”的第二个协议。
- Design 专项 campaign 之前，关于其弱模型成功率、token 降幅和 reviewer 边界准确率的结论均为**未测定**。

## 1. 根因：引用作用域与命名域混淆

### 1.1 本次 15 条错误的确切机制

原始 run1 将 plan criterion 按 WI 分配：

| WI | 本地声明 criterion | 跨 WI 引用错误数 |
|---|---|---:|
| WI-001 | AC-001、AC-002 | 4 |
| WI-002 | AC-003、AC-004 | 1 |
| WI-003 | AC-005 | 6 |
| WI-004 | AC-006 | 4 |
| 合计 | | **15** |

这些 AC 全在源 spec 全局清单内，也全在 plan 某个 WI 内存在。task 引用了**其他 WI** 的 criterion，因而失败。

代码证据链：

- `product/work_item_contract/validation.rs:245-269`：构造当前 contract 的 `acceptance_criterion_ids`，逐 task 检查 `done_when_refs` membership。
- `product/work_item_plan_compiler/validate.rs:36-55`：逐 draft 执行本地 validator。
- `product/work_item_split_validator/types.rs:90-97` → `draft.rs:9-35`：当前 WI 调用 canonical 校验并投影 findings。
- 实测 `timeline_node_001_prompt_ir_reredrive`：15 条原文与跨 WI 引用逐条一致；run2 的 WI-local 越界为零。

### 1.2 prompt 的不对称规则

`product/work_item_split_engine/prompts/sc_author_teaching.rs`：

- `:90` 只说 `done_when_refs 仅引用先定义 criterion_id`，没有本 WI 限定。
- `:108` 对 `requirement_refs` 明确要求本 item 的 Traceability 登记；实测该字段没有同类越界。
- `:127` 又把 `requirement_refs/done_when_refs` 混写为都取自全局 `[design_requirements]`。
- `:44` 要求 plan criterion 全局唯一并顺序递增，容易让模型按全 plan 使用 criterion。

清单来源：`context.rs:125-138` 从 story+design Markdown 扫描 `REQ-/NFR-/AC-` token，去重排序；`prompts.rs:321-322` 传入 reference discipline；`sc_author_teaching.rs:83-88` 拼为一个平铺清单。实测 13 项：`AC-001..AC-006 + REQ-001..REQ-007`。

story 原文使用 `[AC-001]` 等形式，**没有证据支持“story 用另一种编号形式迫使模型自行编号”**。真正的问题是源 spec AC、plan criterion 身份、WI-local membership 三种概念使用同一外观。

`web/workspace_ws_handler/run/single_candidate.rs:416-428` 的 `forged_done_when` 又要求 plan criterion 引用出现在 spec AC 集内。它可能误拒“spec 3 条 AC、plan 合法细分 5 条 criterion”的输入。

### 1.3 合并改法：同一工作包 A，不重复派发

**引用 prompt-quality 片段**：`2026-11-08_WIG方案片段-prompt质量_v1.0.md`。其统一决定是 plan criterion 使用 `WIC-*`，不是 WAC/PAC；本片段不重复派发该工作包。

契约：

- `[design_requirements]` 是源 spec 引用域，只供 `Traceability.requirement_id`、任务 `requirement_refs` 使用。
- plan `criterion_id` 为 `WIC-*`；`done_when_refs`、`reviewer_check_refs` 只引用本 WI 声明的 WIC。
- 删除 `forged_done_when` 的 spec 白名单检查，保留 Traceability 源 ID 登记集检查。
- 返修既有 ID 不重编号；新增 ID 接最大已分配序号之后，不要求补前 WI 后把后面所有 ID 重排。

统一措辞草案：

> `requirement_refs` 引用源 spec 已登记 ID，并必须在本 WI 的 Traceability 中存在完全相同的来源三元组。  
> `done_when_refs` 只引用本 WI 的 Acceptance Criteria 中声明的 criterion_id；其他 WI 声明的 criterion_id，即使全 plan 存在，也不得引用。  
> 源 spec 的 AC 编号与 plan criterion 编号属于不同命名空间，不因数字相同而建立溯源关系。  
> `reviewer_check_refs` 必须覆盖全部且仅本 WI 的 criterion_id。

命名隔离只防身份混淆，**不证明语义溯源真实**。WI 可以合法细化/部分承接复合 story AC，statement 不逐字相等不能直接判为造假；仍需 reviewer 核对源条文及实际承接内容。当前编号白名单只能证明 ID 存在。

实现注意由工作包 A 统一处理：`parse.rs:443` 改 criterion 值前缀；`grammar.rs` 仅白名单 key，无需为该值前缀改结构 key；`fingerprint.rs:8,140-159` 加 WIC 与边界匹配，避免未来子串误识别。WAC 内含 AC，当前无边界 `find("AC-")` 会造成两域身份碰撞，因此不采用。

### 1.4 收益、风险与验证

- **收益**：规则直接覆盖本次全部 15 条错误类型。是否一次通过仍需真实生成验证，不能把 prompt 修正等同成功率保证。

- **风险**：parser、教学、fixtures、指纹及存量 source 读取策略需一致迁移；不能仅改 prompt。

## 2. 修复基线载体：准确描述 resume、compaction 与显式 source

### 2.1 既有选择与官方语义

不携带上一版全文是明确的既有设计选择：`sc_revision.rs:56-62` 区分 fresh 自足、普通 resume 依赖历史；`tests/single_candidate/anchor_t17.rs:155-165` 断言普通 resume 不注入 `[previous_source]`；`workspace_engine/prompts.rs:472-475` 选择 author native session。

### 2.3 显式 previous_source 的准确理由

仍推荐显式携带，理由是：

1. 将唯一权威修复基线绑定到 source hash；不让模型自行选择历史中的哪一版。
2. 不依赖 provider 历史保留与 compaction 策略。
3. fresh/resume/不同 provider 使用同一契约。
4. prompt 与平台 IR 保护器消费同一基线。

**不能称其是本次唯一原文载体**，也不能把“模型忘了”当已证根因。

直接根因组合是：作用域教学缺口、诊断定位丢失、整篇再生成要求、缺少平台保护域校验；旧全文存在并不能避免附带重写。

### 2.4 输入改法与成本

教学 builder 传入：上一版完整 source/hash、完整诊断 `code/field/line/message`、由 IR/AST 生成的 WI/task 定位与本地合法 criterion 集、允许修改闭包。

`single_candidate.rs:246-257` 当前丢掉 field；`validate.rs:488-497` 的 line 恒 0。`draft.rs:14-18` 会把 WI 与 contract/capability 引用合并进 work_item_ids，**field 不是单 WI 字符串**。保留完整 field，不从 message 反解析 task→WI 归属。

措辞草案：

> 上一轮已输出完整 source，但未通过下列校验。`[previous_source]` 是本次唯一权威修复基线，不依赖会话记忆选择版本。

### 3.1 (b) 的精确白名单

可做：`acceptance_criterion_without_reviewer_check` 时，将本 WI 已声明且唯一确定的 criterion ID 追加到 handoff reviewer refs；不创造验收语义。按现有机器指令治理执行并重验，要求幂等、不可降低 error。

## 4. IR 层不变区硬检

### 4.1 选层与触发时机

`compiler/lower.rs:17-30` 的 IR/item 已是可比较结构，canonical 字段在 `work_item_contract/model.rs:7-26`。在既有 `converge_work_item_plan_source` 产出新 IR 后、prevalidate/complete 与候选 refs 提升前执行。

不新增第二套 source parser，不用文本 diff 比例。也不直接比较整个 IR：source hash、自然语言和派生值会变，应逐既有结构化字段比较。

### 4.2 三种失败基线

| 失败形态 | 基线 | IR 硬检 |
|---|---|---|
| IR 契约失败 | handler 本轮内存 IR；compile 已成功、尚未 complete 落盘 | 适用 |
| reviewer 返修 | durable `PlanCandidateIrRecord` | 适用 |
| parse/compile 语法失败 | 没有旧 IR | 不适用 |

持久化证据：`source_store.rs:66-70` IR record、`:297` get；reviewer 在 `single_candidate_input.inc.rs:41-54` 使用。engine `single_candidate.rs:493/512` 才写 source/IR，本次 handler 预检失败在此之前。不可用 session 上一合法 IR 冒充本轮失败基线。

### 4.3 字段级比较规则

按 WI 与稳定 ID 对齐，重复身份继续由原 compiler 拒绝。**未授权结构化变化数阈值=0**，不是 diff 比率：

- WI 集、归属/kind/Plan Intent/依赖边；
- TASK/CHECK/WIC ID 集及所属 WI，禁止既有 ID 重编号；
- CT 供需键 `(consumer WI, provider WI, contract_id)`；
- required/provided capabilities 与兼容策略；
- task→requirement、task→done_when 引用边；
- handoff required/provided/reviewer refs；
- Traceability `(source_type, source_id, requirement_id)`；
- write scopes、验证命令、required/evidence 等结构化配置。

section 必需性由原 parser/compiler 判断，不重新解析文本；集合语义字段按集合比较，重复仍拒绝，不因数组换序误拦。

**自然语言 statement 改写不纳入硬事实阈值**；仅计量并交原 reviewer 判定。本层不能证明 statement 语义没变，不能承诺所有未涉及自然语言字节不变。prompt 仍要求逐字保持。

### 4.4 允许闭包

对于 unknown done_when：仅允许违规 task 的 done_when refs、必要的新本地 criterion、相应 reviewer check 追加；新 ID 追加，不重编号/移走/删除既有 criterion。其他 Inputs/CT/任务身份/Traceability 全部保护。

已有确定性 autorepair 的改动只按本轮实际精确指令纳入许可，不开放整个 section。

reviewer finding 有稳定可验证字段定位才生成精确闭包；缺定位时不猜、不放开整个 plan，转人工。模型自称需要修改某字段不构成授权。

### 4.5 越权终态与 parse 边界

- IR 教学越权：沿 handler `single_candidate.rs:1363-1378` → `Failed`，附 `repair_scope_violation` 和结构差异，不再 provider。
- reviewer 返修越权：构造**单一 HumanRequired 平台结论**，直接走 route_outcome；Interactive → WaitingForHuman，AutoIfValid → StoppedNeedsHuman。
- 保留旧 candidate refs，拒绝提升越权新候选。
- 不混入 Repairable findings：`evaluate.rs:349-389` 优先处理可修项，会误再触发自动返修。
- 纯 parse 失败只用一次 compile 教学槽＋原 source＋诊断＋精确 section 修正规则，修后全量编译。**没有旧 IR 就不声称硬检；无法证明保护域时不新增自动重跑。**

收益：精确拦住本次 CT 重排、WI-004 Input 丢失、TASK 重编号及 Traceability 删除。机器能证明的是结构事实保护，不是业务等价。代价为本地字段比较和误拦风险；通过最小闭包与字段级报告控制。

### 6.2 当前控制链

### 6.3 建议保持 1/12/3

不增加预算，不调低全局保险丝：初评＋一次修复＋一次复评足以判断修复是否收敛；再一轮全量生成没有新权威信息。只改 max_repairs 也不会取消复评闭包/初复评次数上限。12 是跨阶段保险丝，缺失败现场不应随意改变。人工3次允许 owner 注入决定，不能当自动化预算。

### 6.4 独立前置：修账目，不改次数事实

**已确证 B**：`workspace_engine/mappings.rs:167-179` 固定 event_id=usage_role；`:90-111` 同 ID 整条替换，同 node 两次 author 的 run1 usage 丢失。

**Claude 未判定**：result 原文未找到；run2只有1个message，无法判别 result usage 是 invocation累计/末轮值/其他版本范围。11条api-request无usage，23条blob为请求内容，session-env为空。CLI二进制的“Cumulative like modelUsage”截句实际描述subagent计数，不能证明usage范围。

[官方cost-tracking文档](https://code.claude.com/docs/en/agent-sdk/cost-tracking.md)明确：去重per-step input/cache可累计，但assistant output_tokens为placeholder，真实output读result；故撤回assistant output求和当真实总量。官方还区分usage、modelUsage、total_cost_usd的范围与resume恢复语义，不能混用。

修法：per-provider-run不可变usage identity，保存run/role/invocation sequence/usage scope；同run累计快照替换、跨run汇总必须按scope明确定义，不能盲加以免session累计重复计数；Codex先取明确total字段。用双字段、多message、多run、resume、同node fixture验证。

账目修复是优化度量前置，但次数预算由history控制，不依赖token ledger。**token低报不能推出重试次数低报**；本次reviewer初评就是1次。

## 7. 收敛保障与有信息的停止

现有初评→一次修复→复评→停止机制保留。增加说明性失败簇，不发明模糊自动裁决：

- IR按code＋WI＋字段类聚合，附具体task/ref；
- reviewer按既有category/稳定field，缺定位明确未定位；
- 展示已消除、残留、新增、保护域拦截差异；
- 簇只组织人工摘要，不替代FindingFingerprint，不赋额外自动资格。

```text

仍失败：WI / task / 字段 / 当前值 / 合法目标

```

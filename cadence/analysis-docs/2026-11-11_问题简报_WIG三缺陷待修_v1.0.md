## 0. 系统是什么

`cadence-aria` 是一套多仓（monorepo 聚合根）研发自动化平台。**WIG（Work Item Generation）** 是其中的「**work item plan 生成**」链路：

```
作者轮 author_run（LLM 产出完整 work-item-plan.md）
   └→ preflight 机械预检（plan_preflight：机械校验器 + plan 基线树 + 写范围 + intent 归属）
        ├─ Error ⇒ 教学重驱（把错误原文 + 修正指令注入作者，最多一次）⇒ 再走预检
        └─ 通过 ⇒ LLM 评审 reviewer_run
                        ├─ finding（severity=must_fix / suggestion；contract_field 定位）
                        ├─ 必关闭集合命中 ⇒ 升人工（stopped_needs_human）
                        └─ 否 ⇒ 编译 work_item_plan_compile ⇒ 计划 confirmed
```

## 2. 待修的三个问题

### 问题 ①：比例型指标不显著（计划产出 / 编译通过 / 人工介入率）

**现象**：重复报这一项被修掉了（p=0.0013），但**更上游的产出率没有显著改善**（计划产出 4/15 → 6/20，p=0.179）。

**判定**：① 不是独立缺陷，而是 ②③ 的**结果** —— 产出率 = 作者不早死 × 预检通过 × 评审不升级人工。修好 ②③，① 大概率随之改善；但也要考虑「统计功效不足」本身（n=8/臂 ⇒ 要 p<0.05 需要效应量很大或 n≥12/臂）。

### 问题 ②：`missing_section` 类「教学重驱耗尽」失败（改前改后都 3/8）

**现象**：作者产出结构不合法的 markdown ⇒ 平台注入「错误原文 + 修正指令」的教学重驱（**恰一次**）⇒ 重驱后仍不合法 ⇒ 终局 `failed`（plan 停在 draft，**没有产出计划**）。

**实测证据**（同时段两臂都有，与改动无关）：

- 失败码：`missing_section:1` / `:33` / `:53` / `:57` / `:137`、`invalid_work_item_id:34/37`、`unknown_structured_key:1/2`
- 重驱的 prompt 里带「具体失败原因：missing_section:53:结构化 section 缺少必需字段」等
- 重驱作者轮**工具调用 0 次**（不查仓库，纯盲改）
- 重驱后仍不合法 ⇒ 终局失败，**无人接手**

**要解决的核心问题**：结构化输出校验失败后的**自我修复循环**如何设计，才能在有限预算内收敛或优雅降级。

### 问题 ③：残留的「升级人工」

改后重复报已归零，但人工介入仍有 3/8，**归因已换**：

1. **`suggestion` + `class_hint=repairable` 被判「必关闭」**：模型自己把一条 `severity=suggestion` 的 finding 标成 `class_hint=repairable`，平台（`work_item_plan_policy/classify.rs:124-139`）在 `disposition==actionable` 时**直接采信模型的 `class_hint`** ⇒ 进了必关闭集合 ⇒ 升人工。
   - 实测样本：`verification_checks[CHECK-012]`（建议：前端断言脚本依赖未运行的常驻容器）、`acceptance_criteria[AC-003], acceptance_criteria[AC-004]`（建议：两条 AC 缺任务级追踪）、`verification_checks[CHECK-002], verification_checks[CHECK-013]`（建议：数字前缀 grep 可能误判）—— 都是**改进建议**，被当成必关闭。
2. **写范围越界** `write_scope_outside_bound_repository`：作者把写范围写成 `/tmp/notice-delete-frontend-check/**`（聚合根非成员区），预检判不可写。

**另一个已定位的既有缺陷（多仓基线树只覆盖一个仓）**：`plan_baseline_tree` 按 issue 的 `repo_id` 只解析**一个**物理仓（实测案例只有 busi 的 20 条路径），而**校验器用的就是同一棵树** ⇒ 多仓计划里 frontend/gateway 的 AC 路径**必然**被判「不在基线树内」。D5 事前注入的是同一棵树 ⇒ 只能让作者看见事实、不能修复多仓判定。

## 3. 硬约束（违反即需 owner 裁决）

1. **单文件 ≤1200 行**（`tests/it_core/large_file_guard.rs`；个别文件在守卫登记表里有更高的**登记上限**，登记须附理由且表须排序无重复）⇒ 优先拆分而非抬线。
2. **固定规范面质量预算 23,500 B**（`WORK_ITEM_PLAN_MARKDOWN_PROMPT_QUALITY_BUDGET_BYTES`）**不得上调**；**上下文面预算 32,000 B**（`WORK_ITEM_PLAN_MARKDOWN_CONTEXT_BUDGET_BYTES`）；新增直供内容**计入其所属面**（owner 2026-11-10 裁决），**不得以「动态段」名义规避任一面**。实测：基线树清单注入后固定面字节**逐字不变**（`bytes=23448 margin=52`）。
3. **不给产品新增运行时 env 开关面**（env 层归属 `explicit-sc-author-effort`）。`Cargo.toml` 里的**编译期** feature 只允许作**测量脚手架**（当前有 `wig-d5-before` / `wig-d5-after` / `wig-d6`，判决后须移除或定案）。
4. `REQ-WSC-06`（prompt 分层职责）是 `rework-prompt-input-surface` 的**独占** requirement；其它 active change 不得双 MODIFIED 同一 requirement。相关未实施 change：`isolate-plan-criterion-namespace`（命名域/引用域，REQ-WSC-06 之外）、`close-contract-findings-before-pass`（**契约类 finding 免阻断闭环**，0/24 未实施，正是问题 ③ 第 1 点的归属）、`mechanicalize-plan-compile-repair`（typed IR 诊断，0/37 未实施）、`bound-sc-generation-teaching`（教学重驱窗口，0/32 未实施）。
5. 失败**不得**静默吞掉；计划未产出必须是**显式、可诊断**的终态。

## 4. 调研要求

请重点查 **GitHub 上与工业界**对下列三类问题的既有做法（给出可点开的链接与它们的核心机制，不要泛泛而谈"可以用 AI 解决"）：

**A. LLM 结构化输出校验失败后的自我修复 / 重试 / 降级**
关键词建议：`structured output validation retry`、`json schema repair LLM`、`self-correction code generation`、`repair loop budget`、`constrained decoding`、`grammar-constrained generation`、`retry with error feedback`、`agent output validation harness`。
要回答：业界通常重试几次？重试之间**改什么**（仅回灌错误？换提示？换模型？换解码约束？）？有没有「重试预算耗尽后**优雅降级**」的成文做法（如产出部分可用产物 / 落到人工但附带可执行的修复包）？

**B. 代码评审 / 计划评审 finding 的严重度分级与「必须修复 vs 建议」的判定**
关键词建议：`review comment severity taxonomy`、`blocking vs non-blocking review findings`、`lint severity levels error/warning`、`actionable finding definition`、`agent review gate policy`、`must-fix gate`。
要回答：成熟的 lint/review 工具（如 ESLint、Semgrep、CodeRabbit、SonarQube、Reviewdog、golangci-lint）如何定义「阻断」？**严重度与可操作性是否分离**？模型自报的严重度是否被信任？

**C. monorepo / 多仓场景下，把「文件清单」喂给 LLM 的做法**
关键词建议：`monorepo context for llm agent`、`file tree in prompt`、`repo map`、`codebase indexing agent`、`tree-sitter context`、`ripgrep for llm context`、`workspace-aware agent`。
要回答：业界是**给全量文件树**、**按需检索**、还是**给可调用的检索工具**？多仓（多个 git root）时如何标注归属？上下文膨胀怎么控？

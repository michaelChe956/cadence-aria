### 9.3 事实：prompt 教的是**全局**作用域 —— 与校验器矛盾

首轮 prompt 原文（`timeline_node_001.json` 的 `prompt` 字段）：

```
[cross_reference_discipline]
done_when_refs 仅引用先定义 criterion_id。
requirement_refs 仅引用清单；清单外 REQ-* 拒绝。
...
每个被 tasks 的 requirement_refs 引用的 requirement_id，必须在本 item 的 Traceability
section 有对应登记行（requirement_id 逐字相同）；登记值只能来自 [design_requirements] 清单。

[weak_model_precision]
引用纪律：requirement_refs/done_when_refs 只能逐字复制 spec 已定义 id（REQ-*/AC-*/NFR-*），
且都必须逐字取自 [design_requirements] 清单；清单外 REQ-*/NFR-* → unknown_requirement_ref
拒绝、清单外 AC-* → unknown_done_when_ref 拒绝。
```

而 `[design_requirements]` 是**全局**清单（实测 13 项）：
`AC-001、AC-002、AC-003、AC-004、AC-005、AC-006、REQ-001、REQ-002、REQ-003、REQ-004、REQ-005、REQ-006、REQ-007`

**规则不对称性（关键）**：

| 字段 | prompt 是否给出「本 WI 内」规则 | 校验器实际作用域 |
|---|---|---|
| `requirement_refs` | **有**：「必须在本 item 的 Traceability section 有对应登记行」 | 本 WI 的 traceability |
| `done_when_refs` | **无**：只说「仅引用先定义 criterion_id」+「逐字取自全局清单」 | 本 WI 的 acceptance_criteria |

`done_when_refs` 的两条指引（「先定义」= 文档顺序在前；「取自全局清单」）**都指向跨 WI 引用**，
而校验器要求 WI 本地引用。模型照 prompt 做，必然触发 `unknown_done_when_ref`。
run1 里 `requirement_refs` 零越界，正是因为它有「本 item」那条规则——**这反证了规则缺口的因果关系**。

### 9.4 事实：重驱**修对了语义**，但用「全量重写」达成，附带破坏

run2 的 AC 分布变为「每 WI 一段连续区间」且 done_when 全部 WI 本地自洽：
WI-001=[AC-001,AC-002,AC-003]、WI-002=[AC-004]、WI-003=[AC-005]、WI-004=[AC-006]。
**语义修复完全正确**（0 越界）。但代价是整篇重写带来的附带破坏：

- WI-002 原本的 `AC-003` 被并入 WI-001、WI-002 只剩 `AC-004` → WI-001 的
  `reviewer_check_refs` 从 2 条变 3 条（这是语义变更，不是缺陷）；
- `CT-001/CT-002/CT-003` 全局编号重排；
- **WI-004 丢失一个 `input_contracts` 条目**（`CT-002` + `required_capabilities` 整块消失）→ 真缺陷；
- `TASK-008..TASK-022` 整体后移为 `TASK-009..TASK-017`；
- `design_traceability` 中一条三元组被删。

**结论**：IR 失败的根因是**一条 prompt 规则缺失**（`done_when_refs` 缺「本 WI 内」限定），
而非模型能力问题；重驱之所以昂贵且引入新缺陷，是因为**只有全量重写这一条路**，
没有定点修补路径。

### 9.5 事实：诊断信息在回灌时丢失了定位信息

`web/workspace_ws_handler/run/single_candidate.rs:250-263` `format_compile_failure_reasons`：

```rust
format!("{}:{}:{}", diagnostic.code, diagnostic.line, diagnostic.message)
```

- `diagnostic.line` 恒为 `0`（`work_item_plan_compiler/validate.rs:488-499` `validator_diagnostic`
  明确写 `line: 0`，注释「validator 投影无 source 行事实，不伪行」）；
- `diagnostic.field`（= `finding.work_item_ids.join(",")`，即**出错的 WI id**）**被丢弃**；
- `message` 本身**不含 WI id**（形如 `task TASK-019 references unknown acceptance criterion AC-002`）。

→ 回灌给模型的 15 条错误，**模型无法知道每条属于哪个 WI**，只能自己推。而
`[design_requirements]` 又只给全局编号。这是「重驱整篇重写」的**直接诱因**：
模型没有足够信息做定点修补，只能重写。

### 9.6 事实：重驱 prompt 反而**强化**了错误规则

实测 run2 的 prompt（2097 字符）片段：

```
[design_requirements] AC-001、…、REQ-007
每条 Traceability 三元组 requirement_id 必填且逐字取自上列清单;修复引用时不重编号、
禁止新增清单外 REQ-*/NFR-*/AC-*/TASK;done_when 只指向已定义编号。
```

「done_when 只指向已定义编号」——「已定义」未限定作用域，且紧邻全局 `[design_requirements]` 清单，
**继续暗示全局引用**。重驱 prompt 非但没有修正 9.3 的规则缺口，反而复述了它。

## 10. 【第二个决定性发现】`AC-xxx` 是三重命名空间，且编号存在**不证明**溯源真实性

### 10.1 事实：同名 `AC-00N` 在三处指三件不同的事

| 命名空间 | 定义处 | 语义 | 本次实例 |
|---|---|---|---|
| **A. spec 域** | story spec 正文（`story_spec_0009`） | 故事级验收标准，7 个 REQ + 6 个 AC | `AC-001` = 每行末尾显示删除按钮；`AC-003` = 确认删除后提示成功+刷新+直连404；`AC-005` = 已删除公告点删除提示中文原因 |
| **B. plan 域** | 计划内各 WI 的 `### Acceptance Criteria` 段 | 工作项级验收标准，**全局唯一且全局递增**（`sc_author_teaching.rs:44` 明文） | `AC-001` = WI-001 的「渲染完成显示删除按钮」；`AC-003` = WI-002 的「删除一条已存在公告被物理删除」；`AC-005` = WI-003 的「网关返回 404 五字段」 |
| **C. validator 域** | `validation.rs:245-250` | **本 WI 自己声明的** criterion 集合 | WI-001 只认 AC-001/AC-002；WI-002 只认 AC-003/AC-004 |

**A 与 B 的编号空间恰好重叠但语义完全不同。**

### 10.2 事实：Traceability 的编号存在**不证明**溯源语义真实

run1 的 Traceability 段逐条核对（story spec 的 AC 原文见 `versions/story_spec_0009/version_0001.json`）：

| Traceability 声明 | 计划本 WI 的同名 AC 实际内容 | story 同名 AC 的实际内容 | 覆盖情况 |
|---|---|---|---|
| WI-001: `source_id: story_spec_0009, requirement_id: AC-001` | WHEN 公告列表渲染完成 SHALL 每行末尾显示「删除」按钮且空态不报错 | 每行末尾显示删除按钮；空态无报错 | ✅ 覆盖 |
| WI-001: `... requirement_id: AC-002` | WHEN 用户点「删除」并在确认框点「取消」SHALL 不发请求且数据不变 | 点删除弹二次确认；点取消不发请求 | ⚠️ 覆盖不足（漏「弹框」这半句） |
| WI-002: `... requirement_id: AC-003` | WHEN 删除一条**已存在**公告 SHALL 记录被物理删除且列表查不到 | 确认删除公告 A 后提示成功+刷新+**直连404** | ❌ **疑似错映射**（B 是 busi 物理删除，A 是前端成功流+直连404） |
| WI-002: `... requirement_id: AC-004` | WHEN 删除一条**不存在**公告 SHALL 返回 404 且五字段 | 对不存在的公告返回 404+五字段契约 | ✅ 覆盖 |
| WI-003: `... requirement_id: AC-005` | WHEN **直连**删除不存在 id SHALL **网关**返回 404 且五字段 | 已删除公告点删除提示**中文原因不白屏** | ❌ **疑似错映射**（B 是网关 404，A 是前端错误提示） |
| WI-004: `... requirement_id: AC-006` | WHEN 自动化验证被汇总执行 SHALL mvn verify 全绿+lint 零 error | 自动化:busi/gateway 新增用例，mvn verify 全绿 | ⚠️ 覆盖不足（多出 lint 要求） |

**口径（务必精确，勿夸大为「造假」）**：6 条声明中 **2 条覆盖、2 条覆盖不足、2 条疑似错映射**。
「疑似错映射」指该 plan 侧 criterion 的行为与被登记的 spec AC **不是同一件事**
（WI-002 的 AC-003 是 busi 物理删除，而 story 的 AC-003 是前端成功流+直连404；
WI-003 的 AC-005 是网关 404，而 story 的 AC-005 是前端错误提示不白屏）。

需要克制的一点：**plan 域的 criterion 合法地可以细化或部分承接 story 的复合 AC**，
因此「statement 不逐字相等」本身**不构成**造假证据。上面两条 ❌ 的判定依据不是
「措辞不同」，而是**行为主体与结果不同**（busi vs 前端、网关 vs 前端）——即登记的
溯源指向了语义上另一条验收标准。**这两条需要人工/reviewer 复核才能定性**，
本文档只陈述「编号匹配与语义匹配不一致，且已发现两条不一致」这一可验证事实。

**平台为什么没拦住**：`prevalidate_plan_candidate_ir` 的伪造检查
（`single_candidate.rs:406-434`）只比对**编号字符串**是否在 spec 清单里
（`registered`），**从不比对语义**。编号恰好都在清单内（AC-001..AC-006 恰好存在），
所以检查通过。`forged` 与 `forged_done_when` 均为空（已实测确认）。

**这解释了「期望 work item plan 生成的更准确」的真正含义**：当前的溯源链是
**编号级匹配**，不是语义级追踪。编号能对上不代表语义对得上；而平台**没有任何一层**
检查语义。reviewer 审的「Cross-Item Contract Supply/Demand」与「Traceability」
都建立在这套编号之上，所以 reviewer 判 pass **不代表**溯源语义正确。

> 命名空间物理隔离（如 plan 域改用 `WAC-`）只能**防身份混淆**（让「编号巧合」
> 不再可能），**不能保证**模型真的读了 spec 原文 —— 仍需显式映射规则 + 语义复核
> 手段（如 reviewer 侧比对 statement 与 spec AC 原文的覆盖关系）。此约束由
> DesignConvergence 提出，本文档采纳。

### 10.3 事实：第二处校验与第一处作用域相反（潜在缺陷）

`single_candidate.rs:417-431` 的 `forged_done_when` 检查要求
`done_when_refs` 中以 `AC-` 开头的引用**必须在 spec 清单内**（A 域）；而
`validation.rs:256-270` 要求 `done_when_refs` **必须在本 WI 自己的 AC 集内**（C 域）。

两条同时生效 ⇒ **一个 plan 里的 criterion 只能叫 spec 已有的 AC 编号，且本 WI 的
AC 集必须 ⊆ spec AC 集**。本次两轮恰好都满足（plan 域编号 AC-001..AC-006 与 spec
域 AC-001..AC-006 数量与编号巧合一致），所以第二处从未触发。

但这是**巧合**，不是设计：若某个 spec 只有 3 个 AC 而 plan 需要 5 个工作项级验收，
或 plan 域编号与 spec 域编号任意错位，第二处就会把**合法**的 plan 判为伪造。

> 设计角色 DesignConvergence 的独立结论与此一致：「不能按最近编号自动映射」
> ——自动重映射会掩盖真实语义错误（模型可能本意就是引用另一个 WI 的验收）。
> 本节进一步给出更强的事实：**当前的「映射」已经是自动的、且是错的**（按编号巧合冒充）。

- **探索阶段只占前 ~200 秒**（11:54:24 → 11:57:40 之前，5 轮、10 次工具调用）。

  间隔只有 3~6 秒。

**所以「启动一次要 5-10 分钟才有 token 输出」的机制是**：模型在**生成 plan 正文**时进入
长思考（单轮 thinking 数十秒到十分钟量级），期间无 text 输出 → 用户侧看不到 token。
**这与「探索太多」是两个不同的问题**，优化手段完全不同：
- 探索多 → 靠 prompt 供给事实 + 探索预算约束；
- 生成期长思考 → 靠**降低 thinking 预算 / effort 档** 或**分段生成**，

### 12.1 根因（已确证的两条独立缺陷 + 一条未判定）

**依据（官方一手文档）**：`https://code.claude.com/docs/en/agent-sdk/cost-tracking.md`

**缺陷 A'（reviewer/codex 侧：字段优先级导致累计值永远取不到）—— 已确证**：
codex wire 同时提供扁平 `inputTokens`（**最后一轮**）与嵌套 `total_token_usage`（**累计**，
官方语义明确），而 `cross_cutting/codex_provider/parse.rs:461-484` `parse_codex_usage`

```rust

    .or_else(|| nested("/total_token_usage/input_tokens"))   // ← 累计值排在 fallback
```

`field()` 先命中扁平日 ⇒ **累计值永远走不到 fallback**。

|---|---|---|---|---|---|---|
| 0 | suggestion | advisory | advisory | verification_unattributable | **None** | WI-001 |
| **1** | **suggestion** | **actionable** | **advisory** | **contract_gap** | **None** | **WI-004** |
| 2 | suggestion | advisory | advisory | completeness | None | WI-004 |
| 3 | suggestion | advisory | advisory | verification_unattributable | None | WI-001 |
| 4 | suggestion | advisory | advisory | scope_conflict | None | WI-003 |

**finding #1 的原文**：
> 「端到端验收项只声明了来自前端的一项输入契约，但它的验收标准同时要求「删除成功返回 204 空响应体」

### 17.2 事实：平台把它归为 advisory，`pass` 未被重开

平台侧判定链（逐段核实）：

1. `web/workspace_ws_types/review.rs:187` `with_platform_disposition_rules()`
   （由 `parsers.rs` 的 `parse_raw_review_finding` 收口时调用）：
   `disposition==advisory` **且** `category ∈ {ContractGap, SelfContradiction}`
   → 改写为 `actionable`。**finding #1 满足**（contract_gap）→ **disposition 变为 actionable** ✅
2. `parsers.rs:427` `effective_work_item_plan_review_verdict()`：把 `Pass` 重开为 `Revise`
   需要**同时**满足：`is_actionable()` **且** `severity ∈ {Blocking, MustFix}`。
   **finding #1 的 severity 是 `suggestion`** ⇒ **不重开** ⇒ verdict 保持 `Pass`。
3. `work_item_plan_policy/classify.rs:124` `classify_finding()`（`:132` 起判
   `!finding.is_actionable()`）：`disposition==actionable` ⇒ 不走 Advisory 短路，
   改用 `class_hint` ⇒ **模型给的 `class_hint=advisory`** ⇒ `FindingClass::Advisory`。
   → 即使到了 policy 层，它也是 advisory，**不构成 `Repairable`**。

> ⚠️ **行号修正（经双审）**：本节原写 `classify.rs:117` / `classify.rs:117-127` ——
> 函数实际起于 **`:124`**，判定链在 `:132-139`；`with_platform_disposition_rules`
> 定义在 `web/workspace_ws_types/review.rs:187`（由 `parsers.rs` 调用），不在 `parsers.rs` 自身。
> 判定结论**成立**，仅坐标更正。

### 17.3 结论：抱怨③ 的机制是「**severity 门槛 + class_hint 双重降级**」

**reviewer 已经做对了它该做的事**（finding #1 的描述精确到「依赖边存在而契约来源缺失」），
**是平台的两道门槛把它降级成了提示**：

- 门槛一：`severity` 必须 ∈ {blocking, must_fix} 才允许把 `pass` 重开为返修
  （`parsers.rs:441-446`）。模型给 `suggestion` → 不重开。
- 门槛二：`class_hint` 直接决定 policy 分类（`classify.rs:117-127`）。
  模型给 `advisory` → 即使 disposition 被平台改成 actionable，也仍是 Advisory。

**这两道门槛的设计意图是防止「模型过度返修」**（评论里写明：
「must_fix 仅限机械漏网硬错误或明确自相矛盾；完备度意见只能是 advisory」，
`prompts/review.rs:64` / `:93`）。**但代价是：模型倾向于把一切都标成 `suggestion`+`advisory`
以求稳妥**，于是**真缺陷被降级成提示，pass 被放行**。

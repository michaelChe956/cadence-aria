# 本轮改动与三个原始投诉的关联分析

- 日期：2026-11-14
- 范围：`feat-wig-optimize-11-08` 分支自上一版交付 `07a0df79` 起的改动（182 commits，121 files，约 +26.5k/−1.5k）
- 口径：区分「机制是否补齐」「是否有真实运行证据」「是否可度量」三层；未测即标未测。

## 一、三个原始投诉

① 首 token 慢　② IR 教学重驱频繁　③ reviewer 返修反复耗尽

## 二、逐条结论

| 投诉 | 本轮是否触及 | 具体机制改动 | 真实证据 | 结论 |
|---|---|---|---|---|
| ① 首 token 慢 | **未触及** | 没有任何 provider 启动/握手/流式首包路径改动；A3 反而把完整失败 source（≤262,144 B）注入教学 prompt，教学轮输入更长 | durable 产物无首 token 时间戳 ⇒ **该指标当前不可测**（8 臂只测到节点时长之和与墙钟） | **未优化**；教学轮有轻微增负 |
| ② IR 教学重驱频繁 | **部分（修成因，不修次数）** | 教学 prompt 现在自含上一轮**完整失败 source**（P20 严格读回 → P21 无损围栏 → P22 262144 硬闸），并有全文审计可回读；终局保留全量 `blocking_reasons` 与未截断指令，不再只有摘要 | 触发上限本来就是「每失败轮最多 1 次」，频率不会下降；8 臂里 after 侧 IR failed 3/4、编译通过 0/8、confirmed 0/8 ⇒ **无成功率提升证据** | **机制补齐，效果未证实** |
| ③ reviewer 返修反复耗尽 | **未触及** | 未改 reviewer prompt / 轮次上限 / findings 序列化 / 返修清单（这些属上一轮交付）；本轮仅有一处相关：失败包 `is_current=false` 且 `mark_latest` 跳过 A4，防止失败包被误标"已确认" | 8 臂里 **7/8 臂 reviewer 轮次 = 0**，唯一一轮是静态 preflight（0 工具调用、约 0.166 s）⇒ 实质无 reviewer 样本 | **未优化，也未度量** |

### 一个真实但间接的收益（与 ③ 的"耗尽"相关）
修掉了「崩溃重进会用同一 handle **二次启动 provider**」的真实缺陷（P08 三分类 Ready/Completed/Waiting + fresh operation 绑定）。重复启动会白烧预算与墙钟，是"反复耗尽"的隐形放大器。**未量化**。

## 三、本轮真正交付了什么（与三条投诉无关，但构成后续优化的度量基础）

1. **失败可诊断**：每轮完整失败原因（诊断 >4 条也不截断）、raw/source 绑定、教学 prompt 全文审计、终局修复包、只读 JSON。
2. **不谎报**：失败包不冒充当前工件；pending 不可对外可见；坏回执显式报错；发布屏障之后的广播失败不再等同于发布失败（此前正是它导致"A4 count 0"误判）。
3. **可复现**：A3 的 source 链（严格读回 → 唯一归一化 → 摘要/字节核验 → 262,144 硬闸打在最终字符串上）。
4. **恢复安全**：已启动轮不会二次启动；Unknown 走真实等待而非伪造终局。

## 四、要真正回答三条投诉，还缺什么

| 缺口 | 现状 | 需要的最小改动 |
|---|---|---|
| TTFT 不可度量 | durable timeline/execution events 无首 token 时间戳 | 在 timeline node detail 记录首 token 时刻（1 处写入 + 1 个断言） |
| 无成功臂 | 8 臂全部失败、confirmed 0/8 | 需要一个能产出 confirmed 计划的样本/配置，否则任何"成功率"结论都不成立 |
| reviewer 无样本 | 7/8 臂 reviewer 轮次为 0 | 先定位瓶颈是否根本不在评审（当前证据指向 author/compile），必要时用原案例现场数据复现 |

## 五、诚实表述（可直接引用到验收报告）

> 本轮改动不是性能优化。它解决的是"失败之后能不能解释、能不能复现、能不能交付工件"。对用户提出的首 token 慢、IR 教学重驱频繁、reviewer 返修反复耗尽三项，本轮**未降低触发频率、未缩短首 token、未减少返修轮次**；其中 IR 教学一项只补齐了"重驱输入缺完整失败源"这一成因，效果仍需在具备成功臂的装置上度量。

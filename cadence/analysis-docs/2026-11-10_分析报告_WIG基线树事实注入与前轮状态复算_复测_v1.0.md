## 1. 结论摘要

1. **D6 达成设计目标：「重驱后重复报错 ⇒ 升级人工」这条路径被消除。**
   - 基线：走到第二轮评审的 run **2/2** 的第二轮**重复报了第一轮的同一 `contract_field`**（`acceptance_path_not_in_baseline` / `intent_unexecutable`）⇒ 两个 run **全部**升级 `human_required` ⇒ `stopped_needs_human`。
   - 复测：走到第二轮评审的 run **3/3** 的第二轮**与第一轮零交集**，且第二轮 findings **全部是 `suggestion`**（零 `must_fix`）⇒ **重复报归零**。
2. **剩余的人工介入来自另一条机制，不是重复报。** 唯一一次 `stopped_needs_human`（high-4402）的第二轮 6 条 finding **全是 `suggestion`、零重复**，但其中 3 条带 `class_hint=repairable` ⇒ 被平台判为**必关闭** ⇒ 升级人工。该判定面属 **`close-contract-findings-before-pass`（0/24 未实施）** 的待修内容 ⇒ **复测把「下一道坎」精确指向了那个已立项 change**。
3. **代价明确且不可忽视：墙钟显著变长，token 基本持平。** 墙钟中位数 xhigh **1,591.4s**（基线 520.8s，**3.1×**）、high **2,288.4s**（基线 788.8s，**2.9×**）；而 input/output token 中位数与基线同量级（91,964 / 19,644 vs 101,282 / 24,295）⇒ **变慢不在 token 成本，在作者轮耗时**（作者轮 1,279s / 2,048s vs 基线 358~662s，两区间**不重叠**）。
4. **新发现一个既有产品缺陷（先于本 change 存在）**：plan 基线树只覆盖 issue 的**一个**物理仓，而**校验器用的就是同一棵树** ⇒ 多仓计划里 frontend/gateway 的 AC 路径**必然**被判「不在基线树内」。D5 事前注入的是同一棵树 ⇒ **只能让作者看见事实、不能修复多仓判定**。
5. **preflight 拦截率不降反升**（基线 2/4 → 复测 3/5）：因为注入清单后作者获得了 busi 的真实路径事实，转而去写 **frontend/gateway** 的路径 ⇒ 越界从「凭空造路径」转为「跨仓引用」⇒ 暴露了第 4 条的既有缺陷，而非制造了新的越界。
6. ⚠️ **净效果目前为负，须诚实报告**：D5 事后 + D6 消除了「重复报 ⇒ 人工介入」，但 **D5 事前（基线树清单注入）引入了基线没有的新失败模式** —— 作者产出结构不合法（`missing_section`）→ parse 教学重驱一次 → 仍不合法 ⇒ 终局未产出计划（复测 **2/5**，基线 **0/4**），且墙钟 **2.4×**。嫌疑集中在 D5 事前（唯一改动作者 prompt 的项），但 n 太小无法确证 ⇒ **判决需「关闭 D5 事前、只留 D5 事后 + D6」的同装置同时段 A/B**。

## 6. 新发现：多仓场景下 plan 基线树只覆盖一个仓（既有缺陷）

**事实**（复测现场取证）：
- 注入作者 prompt 的 `baseline:` 段内容是 **busi 仓的成员内相对路径**（`.gitignore` / `checkstyle.xml` / `pom.xml` / `src/main/java/com/testcenter/busi/…`），**不含** frontend / gateway。
- 根因：`plan_baseline_tree` → `plan_baseline_repository_path` 按 issue 的 `repo_id` 解析**单一**物理仓（`git ls-tree` 该仓基线分支）。
- **校验器用的就是同一棵树**（`validate.rs` 的 `context.baseline_tree`）⇒ 多仓计划里 **frontend/gateway 的 AC 路径必然被判「不在基线树内」**。

**关联**：基线 run3（`acceptance_path_not_in_baseline` 命中 WI-004=frontend）的直接原因即此。

**影响判定**：
- D5 事前**只能让作者看见事实**（看见 busi 有哪些文件），**不能修复多仓判定** ⇒ 它把失败从「凭空造路径」推向「跨仓引用」（复测 preflight 拦截率 3/3 高于基线 2/4，正是这个原因）。
- D5 事后（回灌最近候选）**同样受限**：候选路径取自同一棵 busi 树 ⇒ 对 frontend 的越界**给不出可用候选**（如实说明「无可用候选」）。

**归属**：属 **REQ-WSC-02 域**（已归档 change `2026-09-26-single-candidate-contract-preflight-and-loop-identity`），**须另立 change**：基线树覆盖全部成员仓 + 按成员仓分组比较 + 候选按成员仓检索。**需 owner 裁决其验收语义**（放宽判定会让原本应拒收的候选通过）。

⇒ 已登记在 `openspec/changes/rework-prompt-input-surface/design.md`「Risks / Trade-offs」。

## 7. 局限

1. **样本不足**：截止当前 n=3 可评估（基线 n=4）。preflight 拦截率、人工介入率的**统计显著性不足**，本报告只下「重复报归零」这一**机制级**结论（3/3 且基线 2/2 反向），不下比例型结论。
2. **墙钟归因未确证**（见 §5）：时段效应未排除。
3. **provider 层失败 1 次**（high-4403：已流式输出 30,350 字符后中断，无产品侧错误事实）⇒ 环境噪声，已单列不计入。
4. **单一案例**：外部效度有限。
5. **复测二进制早于「清单分组修正」**（`0ab6abcc`）：该修正**只改清单的分组呈现，不改路径集合**，故不影响效果指标；但实际 prompt 文本与复测所用二进制略有差异。

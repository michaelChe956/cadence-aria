## 6. 新发现：多仓场景下 plan 基线树只覆盖一个仓（既有缺陷）

**事实**（复测现场取证）：
- 注入作者 prompt 的 `baseline:` 段内容是 **busi 仓的成员内相对路径**（`.gitignore` / `checkstyle.xml` / `pom.xml` / `src/main/java/com/testcenter/busi/…`），**不含** frontend / gateway。
- 根因：`plan_baseline_tree` → `plan_baseline_repository_path` 按 issue 的 `repo_id` 解析**单一**物理仓（`git ls-tree` 该仓基线分支）。
- **校验器用的就是同一棵树**（`validate.rs` 的 `context.baseline_tree`）⇒ 多仓计划里 **frontend/gateway 的 AC 路径必然被判「不在基线树内」**。

**关联**：基线 run3（`acceptance_path_not_in_baseline` 命中 WI-004=frontend）的直接原因即此。

**影响判定**：
- D5 事前**只能让作者看见事实**（看见 busi 有哪些文件），**不能修复多仓判定** ⇒ 它把失败从「凭空造路径」推向「跨仓引用」（复测 preflight 拦截率 3/3 高于基线 2/4，正是这个原因）。
- D5 事后（回灌最近候选）**同样受限**：候选路径取自同一棵 busi 树 ⇒ 对 frontend 的越界**给不出可用候选**（如实说明「无可用候选」）。

**归属**：属 **REQ-WSC-02 域**（已归档 change `2026-09-26-single-candidate-contract-preflight-and-loop-identity`），**须另立 change**：基线树覆盖全部成员仓 + 按成员仓分组比较 + 候选按成员仓检索。**需 owner 裁决其验收语义**（放宽判定会让原本应拒收的候选通过）。

⇒ 已登记在 `openspec/changes/rework-prompt-input-surface/design.md`「Risks / Trade-offs」。

## 7. 局限

1. **样本**：实施后臂 n=7 可评估（基线 n=4）。「重复报归零」是**机制级**结论（3/3 且基线 2/2 反向）；比例型指标（产出成功率、人工介入率）样本仍不足，只能作**方向性**判断。
2. **墙钟归因未确证**（见 §5）：时段效应未排除。
3. **provider 层中断 1 次**（high-4406：作者轮无教学重驱记录、直接中断，无产品侧错误事实）⇒ 环境噪声，已单列不计入（**注意**：high-4403 / xhigh-4405 早期曾被误判为 provider 失败，实为产品级 `missing_section` 失败，已修正口径**）。
4. **单一案例**：外部效度有限。
5. **复测二进制早于「清单分组修正」**（`0ab6abcc`）：该修正**只改清单的分组呈现，不改路径集合**，故不影响效果指标；但实际 prompt 文本与复测所用二进制略有差异。

依据（预先声明的第一条规则命中）：
- **同时段基线臂（一行代码都不改的 `db34f3f0`）也出现同型失败** —— run 4601 的失败码为 `unknown_structured_key:1/2` + `missing_section:1`（「文档必须包含固定一级标题」），与实施后臂的 `missing_section:53/:57/:137` **同型**；

- 三处证据一致 ⇒ 该失败模式在**有 D5 事前 / 无 D5 事前 / 完全未改**三种代码状态下**都出现** ⇒ 与改动无关。
⇒ 同时段基线臂 1/3 失败、墙钟 1,126s（历史基线 607s）⇒ **provider 侧退化在同时段确实存在**，这解释了 §3.5 的全部比例型偏差。

「重复报 ⇒ 第二轮带 must_fix ⇒ 升级人工」这条链在**所有不含 D6 的臂**中 **3/3** 成立；**含 D6 的臂 0/3**：

### 9.2 判决规则（预先声明，避免事后挑数据）
- 若**同时段基线臂**也出现同量级的「未产出计划」失败（`missing_section` / IR 族）⇒ 退化是**环境性**的 ⇒ **D5 事前无责，可保留**；§3.5 的比例型指标作废，净效果需在 provider 健康窗口重测。

- **D6 的机制级结论（重复报 0/3 vs 2/2）在两种情形下都成立**，不受本判决影响。

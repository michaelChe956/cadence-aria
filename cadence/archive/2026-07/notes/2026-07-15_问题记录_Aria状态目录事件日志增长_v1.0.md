# Aria 状态目录事件日志增长问题记录

## 文档信息

- 记录日期：2026-07-15
- 版本：v1.0
- 类型：问题记录
- 适用对象：`.aria/`、Coding Workspace、Coding Attempt、Role Run 事件与 Artifact 持久化
- 当前样本：`project_0001 / issue_0001 / coding_attempt_0001`

## 背景

将 `feat-b-0709` worktree 中的 `.aria/` 迁移到 `feat-b-0715` 后，发现该目录磁盘占用约 42 MB。经逐目录、逐文件和事件类型盘点，当前容量主要来自 Coding Workspace 对 Provider 执行过程的完整历史记录，不是迁移失败、文件损坏或异常二进制缓存。

单次 42 MB 对本地开发暂不构成立即风险，但当前数据采用持续追加方式保存。如果长期创建 Issue、Coding Attempt 和 Role Run，`.aria/` 容量会随执行次数持续增长，因此需要记录为存储治理问题。

## 当前样本数据

当前 `.aria/` 样本的核心数据如下：

| 项目 | 实测值 |
|---|---:|
| `.aria/projects` 总大小 | 42,003,638 bytes |
| 文件数量 | 约 545 个 |
| Coding Attempt 数据 | 34,648,247 bytes |
| Workspace Timeline 数据 | 6,073,866 bytes |
| Role Run JSONL 事件日志 | 24,131,303 bytes |
| Role Run 外置 Artifact | 9,804,364 bytes |
| Role Run 数量 | 39 次 |
| Role Run 事件总数 | 61,913 条 |
| `text_delta` 事件 | 59,456 条 |
| 大字段外置事件 | 144 条 |

Role Run JSONL 与外置 Artifact 合计约占整个 `.aria/` 的 81%，Workspace Timeline 约占 14%。两类数据合计超过总容量的 95%。

## 当前问题

### 1. Provider 流式文本按细粒度事件持续追加

一次 Provider 执行会产生大量 `text_delta`。当前样本共有 59,456 条 `text_delta`，每条都会携带 Attempt、Role Run、节点、阶段、角色、序号、事件类型、时间和 payload 等 JSON 元数据并追加到对应的 JSONL 文件。

因此，即使单条文本增量很小，大量重复的事件 envelope 仍会形成明显的存储放大。

### 2. 大字段同时保留 Artifact 与 JSONL 预览

`CodingAttemptStore::append_role_run_event` 会对事件 payload 做规范化。`prompt`、`content`、`output`、`stdout`、`stderr`、`detail`、`message` 等字段超过 16,384 bytes 时：

- 完整内容写入 `artifacts/role-run-events/`。
- JSONL 事件继续保留最多 16,384 bytes 的预览、Artifact 引用和截断标记。

该机制有利于诊断和审计，但会同时产生完整 Artifact 与较大的 JSONL 预览，进一步增加磁盘占用。

### 3. 完成后的 Coding Attempt 未自动压缩

当前 Role Run 事件存储以追加和全量读取为主。已确认 `delete_attempt` 会删除整个 Attempt 目录，但未发现 Coding Attempt 完成后自动执行以下治理：

- 合并连续 `text_delta`。
- 将完整流式事件压缩为最终消息或阶段摘要。
- 清理已不再被引用的 Artifact。
- 按时间、数量或容量执行保留策略。

因此，已完成 Attempt 的过程级事件仍会长期原样保留。

### 4. Workspace Timeline 同样保存较完整的上下文历史

Workspace Timeline 中保存节点详情、Artifact 版本和会话恢复数据。当前样本该部分约 6.1 MB，其中部分单文件超过 200 KB，最大节点详情文件约 537 KB。

这些数据承担页面恢复和历史查看职责，不能直接按临时日志处理，但也需要评估是否保存了可由其他权威数据重建的重复内容。

## 问题判断

- 当前 42 MB 是现有持久化机制正常运行产生的数据，不是本次 `.aria/` 迁移异常。
- 当前样本经历了多个 Work Item、39 次 Role Run、代码返修与审核流程，容量与执行复杂度基本对应。
- 单次容量暂不严重，但缺少自动压缩和保留策略会导致长期近似线性增长。
- 若累计 100 次相近规模的 Coding Attempt，粗略容量可能达到数 GB，需要在长期使用或产品分发前治理。
- 不应通过手工删除 `role-run-events/`、`artifacts/` 或 `workspace-timelines/` 子目录解决，否则可能破坏审计、重试诊断、页面历史和恢复能力。

## 影响

- `.aria/` 的备份、复制和 worktree 迁移成本持续增加。
- 长期使用后可能明显占用用户磁盘空间。
- Role Run 全量事件读取可能增加历史页面加载和恢复成本；该影响当前尚未进行性能基准验证。
- 用户目前无法查看各类数据占用，也无法按安全边界清理已完成的历史记录。
- 若直接引入粗粒度定期删除，可能误删仍被 Timeline、Chat Entry、重试诊断或 Artifact 引用的数据。

## 后续治理方向

后续设计时建议评估：

1. 在 Role Run 完成后合并连续 `text_delta`，保留最终消息、关键状态事件、权限事件、失败信息和必要执行证据。
2. 对已完成 Coding Attempt 增加可恢复、幂等的压缩流程，活跃 Attempt 继续保留完整事件。
3. 减少 JSONL 预览与外置 Artifact 的重复存储，预览长度应与页面和诊断实际需求匹配。
4. 建立 Artifact 引用关系检查，仅清理确认无引用的文件。
5. 为 `.aria/` 增加容量统计、按项目/Issue/Attempt 展示和安全清理入口。
6. 支持按总容量、Attempt 数量或保留时间配置策略，同时为需要长期审计的项目提供保留选项。
7. 为现有历史数据提供显式迁移或压缩命令，不在启动时静默执行破坏性清理。

## 验收关注点

- 活跃 Coding Attempt 的实时事件、断线恢复、权限交互和失败诊断不受影响。
- 已完成 Attempt 压缩后，页面仍能展示最终对话、阶段状态、审核结论、测试证据和必要 Artifact。
- 连续执行压缩或清理操作结果幂等，不产生悬空引用或部分删除状态。
- 对压缩前后磁盘占用和页面恢复耗时建立可重复的基准测试。
- 清理策略默认保守，未能证明无引用的数据不得自动删除。

## 当前处理结论

本次仅记录问题及实测证据，不删除当前 `.aria/` 数据，也不修改现有持久化实现。永久方案需要在存储容量、恢复能力、诊断证据和历史审计之间进一步权衡。

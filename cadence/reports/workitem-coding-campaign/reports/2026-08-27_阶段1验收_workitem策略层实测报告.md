## 4. Codex 与 Pi 的差异分析

### 相同输入与相同策略前提

两次最终记录的 Story、Design、版本和 description digest 全部一致，均配置：author/reviewer 为同一 provider、`review_rounds=1`、`run_policy=auto_if_valid`、开启 superpowers/OpenSpec、强制前后端拆分、包含 integration 测试且不含 e2e。因此，差异不是由输入语料或策略开关不同造成。

### 观察到的不同结果

1. **Codex**：outline 初评通过；batch 初评先出现 3 个 must-fix 与 2 个 suggestion，消耗一次聚合 repair。复评又出现一个 blocking、一个 must-fix 与一个 suggestion；其中 blocking 的「坏数据夹具注入与服务生命周期组合契约」不属于原 verification fingerprint 集合。策略将其归为 `verification_new_findings`，在 auto 模式终止为 `stopped_needs_human`。
2. **Pi**：outline 初评与 batch 初评均为 `pass`，只报告建议级问题。driver 依据选项自动 `skip_optional_findings`，随后 final compile 创建三项 Work Item 并确认计划。

### 归因边界：reviewer 严格度与 provider 输出质量共同作用

不能仅凭两个样本给 provider 排名，也不能将结果完全归因于 reviewer「宽/严」。本次记录至少支持以下受限解释：

- Codex reviewer 在 batch 层连续两轮审查到跨 Work Item 的**可执行契约闭合**缺口，例如 `createServer(options)` 与 `start({ port })` 如何组合，及浏览器入口未传 `fetchImpl` 的真实运行时行为。其检查维度更偏向生命周期、注入路径与生产入口闭合。
- Pi reviewer 对 Pi 产物给出 `pass`，其唯一保留是 `default_port=3000` 与 `PORT` 交接字段在草案内部的溯源不足，裁定为 suggestion。它认可三项写入范围互斥、契约供需逐字一致和追踪闭环。
- 同时，author 输出本身也不同：Pi 产物被 persistence/compile 接受并含完整的三项 scope、验证计划与 dependency graph；Codex 候选使 reviewer 仍能提出新的具体契约缺口。因 author 与 reviewer都同 provider，本实验不能将审查阈值和候选质量拆分为独立因果变量。

因此，本次可确认的是：**策略层对两种有效运行分支都保持了正确行为**——Pi 的有效候选可自动确认；Codex 的复评新增实质问题不可被无限返修，应升级人工。下一阶段若需要比较 provider 特性，应采用交叉 author/reviewer 矩阵、固定 reviewer rubric、重复样本和 blinded artifact 审查，而不能据此做能力排序。

## 6. 已知限制与环境噪音

1. **样本量限制**：每个 provider 仅 1 个最终干净实例。该实测足以验收状态机与 driver 的分支覆盖，但不足以推导 provider 的稳定率、平均质量或排序。
2. **flaky terminal 测试波动**：终端/terminal 类测试被登记为环境噪音，不应以单次 terminal 时序异常反推策略层回归。本次验收运行的 policy、driver 与完整 workspace-engine 测试均通过；未将未复跑的 terminal 波动计入阶段 1 功能缺陷。
3. **`provider_health` 环境失败**：计划 v1.1 已登记 `web_provider_health_api::provider_health_http_matrix_reports_stable_states` 的确定性环境失败：宿主 `PATH` 存在真实 Pi/Kimi CLI，使「四 provider 均阻断」测试前置失效。这不是阶段 1 diff 的因果失败；应以注入 Pi/Kimi stub 修复测试前置。
4. **历史 rep1–4 的定位**：它们是诊断归档，分别含 hard timeout、review needs-human、未处理 review decision、review needs-human；属于策略层收口前的失败过程。它们用于解释修复动机和 golden 来源，**不得**覆盖 rep9/PI rep1 的最终验收结论。
5. **Codex durable ID 注记**：如第 1 节所述，输入说明的 `issue_0014` 与最终 rep9 自报的 `issue_0015` 不一致。已用实际 result 的 ID 做主关联并保留差异；后续 campaign driver 应把 result/session 映射单独输出为 manifest，减少人工串号风险。
6. **E2E 未启用**：Pi confirmed plan 仍带 `integration_or_e2e_skipped_risk` warning。该 warning 与本阶段「策略层实测」不冲突，但产品实现验收前仍需人工或阶段性 E2E 证据。
7. **阶段 1 终审确定性回归（已修复，非 flaky）**：终审以基线 HEAD 全绿为对照，确认下列问题均由本 worktree 的阶段 1 diff 引入；它们不是 terminal/Kimi 环境波动，亦不得按 flaky 处理。修复后定向复验均为通过：
   - `large_file_guard::product_source_and_test_files_stay_under_line_limit`：`src/web/workspace_ws_handler/tests.rs` 曾为 1401 行，超过 1200 行红线；基线通过。已将 `ProviderRunRequested` 的新增单元测试移至 `src/web/workspace_ws_handler/tests/provider_run_events.rs`，入口文件现为 1122 行；修复后 guard 通过。
   - `workspace_ws_integration::workspace_ws_user_message_interrupts_active_stream_before_completion`（`tests/it_core/workspace_ws_integration/part_03.rs`）：确定性报错 `active stream completed before the interrupting message was applied`；基线通过。根因为 handler 启动替代 run 前先等待被旧流持有的 engine mutex，导致 interrupt 不能及时 cancel；现改为先中断 active run 再读取 engine 状态，修复后通过。

## 7. 遗留与阶段 2 衔接建议

### I-3（2026-08-27 接管实测发现）：resume 路径死锁

对已有生成历史的 session 重发 `start_generation`（takeover 子会话续跑场景），outline 通过后会跳过 generation-mode/batch 生成/batch 评审/compile，直接落到 `human_confirm` 阶段。此时 Confirm 被拒（`INVALID_HUMAN_CONFIRM_ACTION: cannot confirm WorkItemPlan without compiled WorkItem records`），`work_item_plan_compile_recovery_action` 也被拒（`requires active work_item_plan_compile_recovery node`）——两头堵死，会话只能废弃。证据：rep12 ws.jsonl + takeover 会话（workspace_session_takeover_workspace_session_0018）实测。修复方向：resume 时若存在已 supersede 的 batch/draft 状态，应恢复 generation-mode 选择或提供 compile 入口，而非直接进人工门。

### I-4（2026-08-27 interactive 实测发现）：修订后 active node 追踪错位

人工反馈修订（RequestChange → revision → outline 重写 → 复审 pass）完成后，outline pass 未进入 generation-mode 分支，而是落入 `route_legacy_review` 的兜底分支（`review_gate=UserConfirmAllowed → enter_human_confirm`，routing.rs:603-611），直接出现人工门；此时 batch 未按新 outline 重新生成、Final Compile 未执行，Confirm 被 `INVALID_HUMAN_CONFIRM_ACTION: cannot confirm WorkItemPlan without compiled WorkItem records` 拒绝。机制：修订流程后 engine 的 active_node_type 解析未命中 WorkItemPlanOutlineReview（疑停留在 outline_confirm 节点），触发兜底。证据：rep22 ws.jsonl（08:15:04 outline pass round 5 → human_confirm 节点 timeline_node_032）。与 I-3 同属修订/恢复路径状态追踪缺陷族。

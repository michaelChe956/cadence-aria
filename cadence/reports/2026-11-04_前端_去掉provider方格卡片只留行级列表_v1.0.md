## 2. 行级列表最终呈现什么

一行一个 provider（`<ul data-testid="provider-capability-list">`，`divide-y` 分隔，无卡片边框），行内依次：

1. **provider 名**（Claude Code / Codex / Pi / Kimi Code）
2. **状态**：`已确认` / `未核验`（`provider-capability-status-<provider>`）。口径 = 三个能力维度全 Confirmed 才「已确认」，否则「未核验」（与 admission fail-closed 同口径，不夸大；denied 的证据仍由维度列如实显示）
3. **批量作业逐项状态**（有作业时）：`批量：已确认 / 批量：核验中 / 批量：核验失败 / 批量：跳过（CLI 不可用）/ 批量：超时（该项未完成，未确认）`（`capability-batch-status-<provider>`）
4. **版本落后提示**（安装目标面 `install-targets.action === "update"` 时）：`版本落后`（`provider-capability-outdated-<provider>`）
5. **当前版本**（`provider.version`，未探测显示「未探测」；`provider-capability-<provider>-version`）
6. **三个能力维度**（原卡片里的信息，一个不少）：`启动 已核验/未核验/拒绝`、`写边界 …`、`恢复 …`（`provider-capability-<provider>-launch|write_boundary|resume`，聚合口径与文案逐字沿用原实现）
7. **【核验 <provider>】** 按钮（单 provider 真实探针入口，行为不变）
8. **安装/更新入口**：未安装 →【安装】+ 手动命令；已核验且版本落后 →【更新】+ `当前 X → 最新 Y`（`provider-install-versions-<provider>`）
9. **批量失败项的【重试】** 按钮（走单 provider 端点，不重跑整批）
10. **单 provider 核验回显**（进行中 / already_confirmed / revalidated / 失败稳定码+detail）

行数恒为 4（四家 provider），整块面板只此一组列表。

1. **行级列表是否承载了原卡片里的全部信息**：是。逐项核对——provider 名 ✅、版本 ✅、单 provider【核验】按钮 ✅、三个能力维度（启动/写边界/恢复，含拒绝态）✅、安装/更新入口（安装+手动命令 / 更新+当前→最新）✅、核验回显 ✅；owner 点名的 provider 名 / 状态 / 版本落后 /【更新】/ 当前→最新 ✅ 全部在行内。原「批量逐项结果列表」里的逐项状态 ✅、失败项【重试】✅、跳过项的【安装】入口 ✅（CLI 不可用时安装入口照旧渲染）也都在行内。**唯一形态变化**：这些信息从「卡片内三行 + 卡片外一组列表」变成「同一行内并列」，行内元素较多，建议 owner 看一眼实际观感。
2. **`ProviderCapabilityBatchResults` 仍在模块里但面板不再调用它**：批量模块的逐项列表组件及其 6 条回归断言**一条未删**（避免「删断言」），但面板的行级列表已吸收逐项信息，故不再二次渲染它 —— 该组件目前在应用内无调用点。若要彻底清理，需连同 `ProviderCapabilityBatch.test.tsx` 的对应断言一起迁移，本次未做（超出授权范围且会触及「不得删断言」红线）。请裁定：保留（现状）还是另开一次迁移。

## 缺口（改前）

三类根记录（`StorySpecRecord`/`DesignSpecRecord`/`IssueWorkItemPlan`）无「曾确凿确认」
typed 事实：曾 Confirmed 后回退 Draft/ChangeRequested 的记录与从未确认的 Draft 不可分，
旧记录历史未知也不可分——删除前无法区分「免确认／曾确认需确认／旧未知需确认」，
且无服务端分类接口（§0.2 `classify_entity_deletion_confirmation` 不存在）。

## 实现

- `src/product/models/lifecycle.rs`：三 record 各增 `ever_confirmed: Option<bool>`
  （`#[serde(default, skip_serializing_if = "Option::is_none")]`——旧 bytes 反序列化为
  None、再 serialize 不补字段）；新增 `DeletionConfirmation::{NotRequired, Required{
  reason}}` 与 `DeletionConfirmationReason::{PreviouslyConfirmed, LegacyHistoryUnknown}`
  （经 `models::*` 既有 glob 导出，`models/mod.rs` 零改动）。
- `src/product/lifecycle_store/plan.rs`（LifecycleStore）：
  - `create_issue_work_item_plan`：root 首次持久由真实创建决定——
    `Some(matches!(input.status, Confirmed))`（Draft 创建 false；直接以 Confirmed 落档
    即确凿确认态 true）。
  - `confirm_issue_work_item_plan`/`commit_issue_work_item_plan`：置 Confirmed 的**原
    write** 同步 `Some(true)`；确认 CAS/前置校验零改动。
  - `request_issue_work_item_plan_change`：Confirmed→ChangeRequested 回退读取当前态
    单调合并 `Some(true)`（从 Draft 直转则保持原值）。
  - `update_issue_work_item_plan`：读取当前根仅替换既有字段，typed 值自然保留
    （候选替换 `replace_issue_work_item_plan_candidate` 全程走此路径——typed 字段不可
    经候选替换变 false）。
  - `restore_issue_work_item_plan_snapshot`：`read_json_if_exists` 读当前根后
    `merge_ever_confirmed`（Some(true) 赢；None 吸收 Some(false)——旧未知不因 restore
    降级为「可证未确认」；双 Some(false) 才保持）。
  - `classify_entity_deletion_confirmation(&EntityScope)`（§0.2 归属 LifecycleStore）：
    读真实记录＋versions（Story/Design 任一版本 `confirmed_by` Some＝确凿确认证据）＋
    publication（Plan 的 `work-item-revision-publications/{plan_id}` 发布日志非空＝真实
    发布证据）。current Confirmed｜ever=true｜真实发布在档 → Required(PreviouslyConfirmed)；
    Some(false) → NotRequired；None 旧记录 → Required(LegacyHistoryUnknown)。根缺失沿
    `load_existing_spec`/`get_issue_work_item_plan` 原 NotFound fail-closed。**session
    存在不作为确认证据**（Draft 阶段即有 session：WorkItemPlan draft session 与 WI 子
    session 均先于/独立于确认存在，接口行的「session」读面按此裁定不采信，注释明示）。
- `src/product/lifecycle_store/spec.rs`：`create_story_spec`/`create_design_spec` 首次
  持久 `Some(false)`；`update_spec_confirmation_status` 确认或「当前态为 Confirmed 的
  回退」单调置 true（其余保持原值，旧 None 不补字段）；`append_version` 的
  `confirmed_by=Some` 版本＝确凿确认，同事务把根置 true（§0.2「任何确凿确认/发布成功
  根写 Some(true)」；版本 JSON 本身不回填、不改写）。
- 候选 parser 内存 record（`work_item_split_engine/parse.rs`、`revision.rs`、
  `work_item_plan_compiler/validate.rs` 投影）：`ever_confirmed: None`——不把旧未知当
  新 false，实际 root 创建决定。
- `src/product/lifecycle_store/tests/cascade_d1_4.rs`（新，经 include! 挂载，沿
  cascade_d1_1.rs 惯例）：`cascade_d1_4_confirmation_history_classification` 单测覆盖
  Step 1 全项——①三类新建 Some(false) 免确认；②current Confirmed（Story 状态写＋Plan
  confirm）需确认且原 write 置 true；③Confirmed→Draft/ChangeRequested 回退单调 true
  仍需确认；④确认→回 Draft→restore 旧（legacy None）snapshot 仍 true；⑤Draft 态真实
  `replace_issue_work_item_plan_candidate` 后 typed 仍 true；⑥None 旧 Draft（直接落盘
  无字段 bytes）→ Required(LegacyHistoryUnknown)；⑦真实发布需确认——legacy Plan 根
  bytes 不动、仅发布日志在档即 PreviouslyConfirmed；legacy Story 仅 confirmed_by 版本
  在档同理（versions 证据）；⑧None 旧 bytes 经 append_version（confirmed_by None）与
  update_issue_work_item_plan 重写后原始 bytes 仍无 `ever_confirmed` 键、分类不降级。

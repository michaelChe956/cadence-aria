## 4. 已完成的本地实测（现役 4317；全部串行、无并发压测）

### 4.1 环境

2 project 目录 × 1 issue × 3 session；session record 28–64KB；**debug 构建**。

### 4.2 五组读数

| 组 | 含义 | 读数 |
|---|---|---|
| A | 命中 session + 404 detail（全扫描 + 读 3 个 session record parse + 404） | **12.8–24.7ms**（中位 ~12.9ms） |
| B | session 不存在（纯扫描未命中，不读 record） | **0.85–1.04ms** |
| C | 静态首页（框架 + 网络常数） | **~1.0ms** |
| D | 同 A 但经 vite:5173 代理 | **14.6–20.5ms**（≈A，代理加价 ~2ms） |
| E | 存在的 detail（200 全链路） | **17.8–22.0ms** |

### 4.3 判定含义

1. **A − B ≈ 12ms = 「同 issue 全部 session record 的读取 + parse」价**（扫描对存在但 id 不匹配的候选也要整读）——**owner 真机单价随 (projects × issues) 与每 issue 的 session 数线性放大**；
2. **B ≈ C** ⇒ 当前规模下纯扫描价可忽略；
3. **D ≈ A** ⇒ vite 代理本身不加明显延迟。

### 4.4 洪水规模估算（E4）与「不足以复现」结论

验证实例 `workspace_session_0011` = **10 节点全部 completed ⇒ 每轮水合集合 10 个请求**（`detailHydrationNodeIds` 排除法全收，`useCockpitNodeDetailHydration.ts:16-20`）；单轮排队理论值 **~30ms** ⇒ ★**当前验证实例的数据规模本身不足以复现 owner 的 1–1.5s** ⇒ 变量在 owner 真机规模或别的机制**★。

### 4.5 服务端无历史耗时数据可回溯

`/tmp/aria-deploy/session.log` 只有连接诊断/取消日志，**没有请求级耗时打点** ⇒ 「读日志回溯历史耗时」这条路不通（本轮亦未新增打点）。

### 4.6 ★不可外推声明★

上述 A~E 全部读数来自**小规模验证实例 + debug 构建 + 串行请求**：**绝对毫秒数不可外推到 owner 真机**；可迁移的只有**相对关系**（A−B 的构成、D−A 的代理加价）与**机制存在性**（§3 已逐一锚点复核）。真机量级必须由 §5 取证卡实测。

## 5. ★owner 侧零成本取证卡（本报告核心——可直接照做）★

> 全程只需浏览器 DevTools 与 curl；**不装任何东西、不改任何代码、不动现役 4317**。按 §6 顺序做，多数情况前 3 步即可收口。
> 顺带项（取证 0）：若延迟正在发生，随手执行 `ps aux | grep aria` 记下 aria 进程 CPU%——**这是 M8 唯一的取证手段**（CPU 高 ⇒ 僵尸 running 在烧 CPU 的旁证；CPU ≈0 ⇒ M8 降权）。

### 取证 1（= E2）：Network 面板看一次按钮点击的排队/服务端分解 —— ≤5 分钟

- **操作**：DevTools（F12）→ Network → 点 🚫 清空列表 → 点任一「慢」的按钮。
- **看哪个数字**：
  1. 点开该次交互触发的第一条（或最慢的）请求 → **Timing** 面板 → 记下 **Queueing/Stalled** 段与 **Waiting (TTFB)** 段各自时长；
  2. 同一时刻 Network 列表里状态为 pending 的 `timeline-node-details` **条数**，及其中 **404 占比**。
- **判定**：
  - **Stalled ≈ 1–1.5s 且同刻 pending 的 detail 请求 ≥ 6** ⇒ **M1 直接证据**（HTTP/1.1 同源 6 连接被 404 洪水占满，真请求在浏览器排队）；
  - **Stalled ≈ 0 而 TTFB ≈ 1–1.5s** ⇒ 慢在服务端 ⇒ 转取证 3（E5）/取证 4（E1）/取证 5（E3）。

### 取证 2：数 404 条数是否「持续增长」而非一次性 —— +2 分钟（与取证 1 同屏）

- **操作**：Network 面板保持打开，正常停留/操作页面 30–60s，观察 `timeline-node-details` 的 404 计数随时间的变化。
- **看哪个数字**：404 计数曲线——持续爬升 vs 一次性一批后停止。
- **判定**：
  - **持续增长** ⇒ M1 的「404 不记忆重发」放大器坐实（锚点 `useCockpitNodeDetailHydration.ts:61-73`：404/空 detail 后从去重集合删除 ⇒ 每轮重发）；
  - **一次性** ⇒ 洪水规模有限，M1 降权，重心移向服务端机制。

### 取证 3（= E5）：lifecycle / 旧 runtime 端点计时 + 找「串行 issue-lifecycle 串」 —— 3–5 分钟

- **操作**：Network 过滤框输入 `issue-lifecycle`（或 `lifecycle`）；触发一次带终止回执的常规操作；再分别挑 lifecycle 端点与旧 runtime 族端点（tasks / advance / stop）各 1–2 条看 Timing。
- **看哪个数字**：
  1. issue-lifecycle 请求是否**成串串行**（瀑布图呈阶梯：一条完成后下一条才发出）；
  2. lifecycle 端点单条 TTFB；
  3. 旧 runtime 族端点 vs workspace-session 族端点的 TTFB 对比。
- **判定**：
  - **看到成串串行的 issue-lifecycle 请求** ⇒ **M7 坐实**（`terminationReceiptIdentity.ts:17-29`：`for project { await listProductIssues } for issue { await getIssueLifecycle }`，每个 issue 一次完整 lifecycle 投影请求且串行 await，与 M5 叠加放大）；
  - lifecycle 端点单条 TTFB 高（数百 ms 级）⇒ **M5**（每个 `get` 独立全量 parse、无缓存）；
  - 慢的只有旧 runtime 族端点而 workspace-session 族不慢 ⇒ **M4**（`state.runtime` StdMutex）；反之 **M4 排除**（workspace-session 族不走此锁）。

### 取证 4（= E1 真机重跑）：五组 curl 读数 —— 5–10 分钟

- **操作**：在 DevTools 里对目标请求右键 **Copy as cURL**，套用下面的计时模板重跑五组（`<URL>` 为对应请求完整 URL）：


- **五组怎么做、读数怎么看**：

| 组 | URL 来源 | 真机读数含义 |
|---|---|---|
| A | DevTools 里任一条 **404** 的 `timeline-node-details` | M2 单价（全扫描 + 同 issue 全部 session record 整读 parse）；**真机若达数百 ms～秒级 ⇒ M2 随规模放大坐实** |
| B | 把 A 的 URL 中 session id 改成不存在的值 | 纯扫描未命中价；B 本身大 ⇒ 目录规模（projects×issues）本身大 |
| C | `curl -o /dev/null -s -w 'code=%{http_code} total=%{time_total}s\n' 'http://127.0.0.1:4317/'` | 框架 + 网络常数基线 |
| D | 同 A，端口换 vite 的 5173 | 代理加价（验证实例实测 ~2ms） |

- **判定**：**A − B** = session record 整读+parse 价（随 projects×issues×sessions 线性放大）；**A ≈ B 且都大** ⇒ M2 的扫描价主导；**D − A** = vite 代理加价。C 用于剔除网络常数。

## 7. 各机制的关系边界（★必读：充分性 ≠ 唯一性★）

- **M1 × M2 —— 相关但未证明同一根因**：M2（全 projects×issues 扫描 + 不匹配候选整读）是 M1 洪水中**每个 404 请求服务端单价的组成部分**，两者叠加；但现有证据（小规模实测 + 无真机现场数据）**不能证明** owner 真机上二者构成同一根因链。
- **充分性 ≠ 唯一性**：即使 ④「404 记忆」修复后延迟随之消失，也**只证明 M1 链是 ⑦ 的充分条件**——**不排除 M2/M3 同时存在**，各自在总延迟中的**占比仍未知**（修复只是把 M1 的贡献清零后总延迟恰好归零或降至不可感知）。
- **M3 是全局乘法器**：debug 构建放慢一切服务端路径，可与任何机制叠加；owner 走 dev 链路则恒有贡献，但量级需 E3 分离。
- **M4 的边界**：仅旧 runtime 族端点（tasks/advance/stop）经过 `state.runtime` 的 `StdMutex`；workspace-session 族（timeline/detail）**不走此锁**。若取证 1/3 显示慢的全是 workspace-session 族请求，**M4 直接排除**。
- **M5 × M7 叠加**：M7 每个 issue 发起一次完整 lifecycle 投影请求，打的正是 M5 的端点（每个 `get` 独立全量 parse、无缓存）；M7 在终止回执身份解析这条全局路径上把 M5 串行放大 N×M 倍。
- **M6 与 M2 同族**：均为「全量重读重解析」类服务端开销，路径不同（lifecycle JSONL vs workspace session 目录扫描）。
- **M8**：无代码锚点（原笔记即推测），只能现场 `ps` 取证；**不参与充分性论证**。
- **h2c**：生产部署是否启用 h2c 未核实——若启用，HTTP/1.1 同源 6 连接上限不成立，M1 机制整体失效，故未列为机制。

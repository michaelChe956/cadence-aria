# 单 provider 可用 + 知识库无人值守执行 验收报告

- 日期：2026-11-11
- 分支：`feat-wig-optimize-11-08`（worktree `.worktrees/feat-wig-optimize-11-08`）
- OpenSpec change：`openspec/changes/archive/2026-11-11-allow-single-provider-aggregate-initialization/`（ADDED「聚合初始化的 provider 依赖只覆盖被选中的那一家」「知识库操作的无人值守执行」「聚合初始化失败面的 provider 口径」）
- 主规格同步：`openspec/specs/logical-codebase-knowledge-base/spec.md`（17 → **20** 条 requirement）

## 1. 用户反馈的两个现象

| # | 现象 | 定性 |
|---|---|---|
| A | 「LC 项目初始化不允许用户只有其中一个 provider，强制要求四家都安装」 | 一半是**真缺陷**、一半是**文案误导**：① skills 链接层校验要求 shared/codex/claude **三层**都装齐，没装 Codex 时 codex 层缺失 ⇒ 整条聚合初始化被 `skills_commands_missing` 拦死（真缺陷）；②「重新检测完成：仍有 N 个 provider 不可用…按下面的安装指引处理后点「重试」」把未安装的 provider 说成必修项（文案误导） |
| B | 「知识库初始化失败了」（卡片显示 `bootstrap 失败` / 「知识库操作执行失败」） | 真因：Pi 在 bootstrap turn 里**发问/请求授权**，而知识库 operation 是无人值守（没有应答通道）⇒ turn 直接判 `provider_interaction_required`；界面只给了一句无信息量的兜底，看不出 provider 问了什么 |

## 2. 改动

| 面 | 改动 |
|---|---|
| 后端 · skills 链接层 | `ensure_skills_commands_linked(home, provider)`：**只校验被选中 provider 那一层**（Pi→shared / Claude Code→claude / Codex→codex）；调用点传 operation 输入里的 provider。选了 Pi 时 codex/claude 层缺失不再阻断 |
| 后端 · 无人值守 | 知识库 operation 与聚合初始化 root recipe 的 prompt 都追加**无人值守指令**（不提问、不请求授权、不等回答；需用户决策的分支按 skill 的非破坏性默认路径继续，无法安全继续时停止并记录） |
| 后端 · 失败可诊断 | provider 发问时把**提问原文**（含选项）写进诊断；知识库侧新增独立稳定码 `knowledge_base_provider_interaction_required` + 成品文案（区别于「provider 执行失败」） |
| 前端 · 失败面口径 | 重新检测结论：可用 ≥1 家 ⇒「已具备执行条件；另有 N 家未安装或不可用——不影响本次执行，需要换一家时再按指引安装」；0 家 ⇒「至少要有一家可用」 |
| 前端 · 诊断可见性 | 环境类失败的折叠标题点明「诊断信息（真实失败原因）」 |
| 前端 · 避免误触发 | 知识库已建成时【确认并初始化】禁用并显示「知识库已初始化」（防误跑一次十分钟的 bootstrap） |

## 5. 遗留

| 项 | 说明 |
|---|---|
| 知识库产物写入聚合根会改动根规则摘要 | 触发 `rule_digest_drift`（需「重新生成政策」）。这是「知识库允许写根 CLAUDE.md/AGENTS.md」与「政策 receipt 冻结根规则摘要」两条契约的固有张力，未在本轮处理 |
| 聚合初始化失败仍是通用码 | 聚合侧仍用 `aggregate_pre_check_failed` 这类通用码（已在诊断里写明「provider 发了什么」），没有像知识库侧那样拆出独立码；可按需对齐 |
| 单 provider 的真机验证 | 只在单测里覆盖（构造「只有 shared 层」）；真机环境四家都装了 |

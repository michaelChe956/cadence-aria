## 0. 头条裁决：通道 C 的上限口径（controller 两次追加铁证的最终答案）

**规格原文（均已逐字核实）**：

- REQ-WSC-09（`openspec/specs/work-item-plan-single-candidate/spec.md:478-490`，主规格）：
  > 「……**每 candidate 至多一次额外驱动（既有上限不变）**；非 parse 语法类失败不触发重驱、按既有路径处理。」
  > 场景「重驱上限不被突破」：**WHEN** 同一 candidate 的编译失败类别先后命中两个可教学类别 **THEN** 教学重驱**总共仍至多一次**。
- REQ-SG-05（`openspec/specs/workspace-structural-governance/spec.md:80-95`，主规格）载体表：
  > 「每次自动结构执行 SHALL 绑定耐久授权……**attempt key/上限**……与审计。claim 与真实 start SHALL 分账……**实际start MUST 有ledger**……」
  > 「**SC 初轮**｜已有生成 run/reservation/phase｜**仅已批准 RepairOnce 才原+1=2，否则1**；不伪造人工 turn」
  > `:86`：「上限/授权无法证明则**零额外调用**并显式系统故障」；`:139`（REQ-SG-07）：「在 **2 attempts** 内能合法即完整交付/复评，否则到顶停工程故障**并保持合法 refs**；不会 spawn 第3次」。
- 实现（`web/workspace_ws_handler/run/single_candidate.rs`）：`:1211`/`:1212` 双局部布尔槽；注释 `:1200-1202` 逐字「两类槽互不挤占、每类至多一次 → 额外 provider 驱动总上限 2 次」；structure 槽在 `:1389-1397` 由 `Completion::Rejected { repair_prompt }` 置位并再驱。

**裁决（三问逐条）**：

1. **权威上限是谁的** —— 两条规格**不是互相矛盾，而是分工**：REQ-WSC-09 管**资格与次数**（每 candidate ≤1 次额外驱动），REQ-SG-05 管**授权绑定、账本与物理包络**（SC 初轮：原+1=2，需「已批准 RepairOnce」）。二者对 compile 类教学重驱给出**同一个答案**：REQ-WSC-09 的「恰好一次」本身就是 SG-05 表中 SC 初轮被批准的那次 RepairOnce 等价物（原+1=2 内的那 +1）。**冲突不在两条规格之间，而在实现与两条规格之间**：
   - **structure 槽违反两条主规格**：它使同一 candidate 可达「额外 2 次 / 合计 3 次启动」，同时冲破 REQ-WSC-09 场景「总共仍至多一次」与 REQ-SG-05「原+1=2」。且它**没有任何批准条款**（REQ-WSC-09 授权的是 parse 语法类；`:1200` 注释明言它是 2026-10-31「真机修订」加的）——按 `:86` 严格读法，授权无法证明则应「零额外调用」。
   - **IR 类重驱无主规格承载**：REQ-WSC-09 字面只授权 parse 语法类、且明言「非 parse 语法类失败不触发重驱」；IR 校验失败（`validate plan candidate IR failed`）发生在 compile 成功之后，落在该条的**字面排除/未覆盖区**——现有 IR 类重驱（含断言它的 `single_candidate_ir_reredrive.rs` 测试）是**无规格条款的既成行为**。这是本次抱怨② 直接踩中的通道，必须补条款。
2. **本次现场触发几次 / 是否超限** —— **恰好 1 次**（compile/IR 共享槽，run1→run2）。在 REQ-WSC-09 的 ≤1 与 SG-05 的原+1=2 之内 ⇒ **本次不构成上限违反**（controller 读法成立）。但**账本与授权绑定缺口在本次现场已经实际发生**：一次真实 provider start，无 attempt key、无 prompt digest 绑定、无 provider-start ledger（E3/E4）。即：上限没超，**义务全欠**。
3. **缺口定性（三合一 + 一未决）** ——
   - **授权缺口**：IR 类与 structure 类重驱无批准条款；
   - **账本缺口**：违反「实际start MUST 有ledger」「SHALL 绑定 attempt key/上限/审计」；
   - **上限缺口**：双槽设计最高 3 次启动 > 原+1=2（两槽同触即超；严格读法下 structure 槽单发即超）；
   - **预算池归属：未决**（REQ-WSC-21 的触发域是门段 `final_compile_*` 候选无效类，`spec.md:818-820`，字面不达 generate 段 handler —— 归类裁决见 §QJ）。

**对主审 §3.5 / §8.1 的最小修法**（controller 建议采纳并加强）：

- §3.5 G-03 通道表格的「契约」列：把「**规格未覆盖**」改为「**受 REQ-WSC-09（资格/每 candidate ≤1）+ REQ-SG-05（SC 初轮载体：授权绑定、start ledger、原+1=2 包络）双重约束；当前实现三者皆缺，structure 槽另与 REQ-WSC-09『总共仍至多一次』场景直接冲突（既存问题，非本方案引入）**」。
- §3.5「structure 教学槽……额外 provider 总上限 2 次｜**不变**」一行必须加注：「**该口径与主规格 REQ-WSC-09 / REQ-SG-05 冲突（既存）**——『不变』不得被读作『与规格一致』，须随 §QJ 归类裁决一并交 owner」。
- §3.5 裁决 2 的「通道 C 记账缺口**并入 `fix-author-rewrite-quota-pool` 的范围裁决**」是**错挂**：该 change 四件套（proposal/design/tasks/delta）零提及 handler/教学通道（grep `教学|compile_ir_rerun|handler|通道 C|重驱` = 0 命中），其 delta 是 REQ-WSC-21 门段语义。正确挂接见 §QJ 与 §流程。
- §8.1 #9 的「红测」**拆三条**（当前表述自相矛盾：「红测」却「当前是绿」）：
  1. **A 池半边（合法绿守卫）**：一次 IR 教学重驱后 `run_history.repairs_used == 0` —— 直接引用 REQ-WSC-21 `:840`「MUST NOT 消耗 `max_repairs`」场景 2；
  2. **账本半边（真红测，暂以 expected-fail 登记）**：一次 IR 重驱必须留下**恰一条** provider-start ledger / attempt 记录 —— 当前 ledger 机制尚不存在（SG4a 0/36 未实施），按仓内先例（`mechanicalize` tasks 4.2「ignored + 说明，修复后转绿」）登记为缺陷占位；
  3. **`manual_repairs_used == 0` 半边移入 owner 决策桶**：池归属未决前把它写成绿断言 = 把今天的缺口钉成契约（与 `compile_failure_auto_rewrite.rs:254-260` 钉死 A 池偏差同构），归属落地时必翻。
- §8.1 新增验收（controller 建议，采纳）：「同一 candidate 先后命中两个可教学类别时，额外 provider 驱动次数 **≤ 主规格 REQ-WSC-09 规定值（1）**」；structure 槽按既存冲突登记为待裁决偏差（owner 若裁定其合法，**必须先 MODIFIED REQ-WSC-09 + REQ-SG-05 表**，这正是 OpenSpec-first）。

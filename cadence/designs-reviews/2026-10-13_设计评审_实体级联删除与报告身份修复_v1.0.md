## 一、两方向裁定与坑

### 1.1 级联删除：补齐拥有关系，而不是无差别清理

已核实入口均为现有实体 DELETE：`src/web/app.rs:288-299,325-330`，对应 `src/web/handlers/lifecycle/deletion.rs` 的 `delete_work_item_plan`、`delete_story_spec`、`delete_design_spec`、`delete_work_item`。不是 `IssueStore::delete`，也不是 native fresh/recovery 的重置入口。

- Plan legacy 路径已经逐个删 work item、删 plan/session、删 verification/profile，再清 drafts/compiles/outlines（`deletion.rs:55-83`；`lifecycle_store/plan.rs::delete_issue_work_item_plan:123-151`）。
- Plan schema-v2 路径清绑定的 WorkItem sessions、plan metadata/session、整个 revision/publication 子树、drafts/compiles/outlines及共享资源残留（`deletion.rs::delete_schema_v2_work_item_plan_with_cleanup:268-335`）。
- **确定缺口：** 上述两路没有清 `work-item-plan-sources/{plan_id}`；其四种对象为 source_revision、plan_candidate_ir、mechanical_report、publication_provenance（`work_item_plan_source_store.rs:15-18,516-533`）。
- **另一个真实遗漏：** schema-v2 删除不调用 `delete_work_item`；metadata 方法只删 plan/session（`lifecycle_store/plan.rs:154-174`）。但现 finalizer 已把编译结果写成 issue-wide `LifecycleWorkItemRecord`，并写 `source_work_item_plan_id/work_item_set_id`（`workspace_engine/compile/finalizer.rs::persist_compiled_work_item_records:228-270`）。仅 purge revision 子树不能清这些记录。需要按记录的真实 plan 归属删，不能仅按可能重复的 logical WI 名称盲删。
- Story/Design 当前已删除主 JSON、版本目录及对应 workspace 类型 sessions（`lifecycle_store/spec.rs:176-200,261-285`）。会话清理递归删除 timeline、会话附属目录、lock、JSON（`workspace_timeline_artifacts.inc.rs:201-229`）。这里本来就是物理级联，不应称“全部 durable 都留着”。

**坑 A：审计证据并非只有源存储。**

- Story/Design 的 `SpecVersionRecord` 含 `provider_run_refs/review_refs/confirmed_by`（`models/outline.rs:362-373`），当前删实体会连这些版本一起删。
- Plan revision 保存 `publication_provenance_ref`；provenance 再精确引用 source/IR/report（`workspace_engine/plan_projection.rs:481-492`；`work_item_plan_source_store.rs::validate_provenance_references:471-502`）。单删 source/report 会留下 dangling provenance；整条链永久删除才是闭包。
- issue-wide `provider-review-rounds/{id}.json` 是按 `session_id` 关联的独立审计记录，当前实体会话清理不删它（`lifecycle_store/review.rs:10-37`；`paths.rs:66-70`）。保留这份孤儿并不等于保住完整审计；若 session ID 再复用，还存在归属串代风险 `[INFERENCE]`。
- `provider-runs` 还有 split 运行档案，plan 用 `created_from_provider_run` 引用（`lifecycle_store/plan.rs:635-671`；`models/lifecycle.rs:290-306`）。是否连带永久清除，也必须在“全部审计是否删除”的契约中明说。

**坑 B：上游 spec 不是被 plan 拥有的对象。**

Story 被 `DesignSpecRecord.story_spec_ids`、`IssueWorkItemPlan.source_story_spec_ids`、`LifecycleWorkItemRecord.story_spec_ids` 引用；Design 被 plan/work item 引用（`models/lifecycle.rs:122-126,147-155,290-295`；已发布 lineage 也持两种 refs：`models/work_item_revision.rs:14-23`）。当前两个 spec 删除方法未检查引用者。删除 spec 后留下 plan 的业务材料/编译来源悬空，是独立于源目录漏清的风险。

建议：本次“删 design/story 同理”解释为清**该实体自己拥有**的版本、会话与审计，不隐式跨级删除引用它的整个下游计划；存在存活引用时拒绝永久删，或由 owner 另定跨级删除流程。Plan 删除必须保留上游 spec/versions；现行 `openspec/specs/work-item-group-deletion/spec.md:32-44` 明确要求这一点。

**坑 C：静态目录清空不等于运行已停止。**

`WorkspaceSessionRegistry::remove` 仅摘 registry；活动连接的旧 `Arc<WorkspaceSessionManager>` 明确继续存活（`registry.rs:131-139`）。source-store 写入的对象级 flock 会创建父目录（`work_item_plan_source_store.rs:705-723`）。因此“先删目录、最后 evict manager”不能单独证明不会被在途 writer 重建 `[INFERENCE]`。

永久删除应先阻断同 scope 新启动/创建，再使已有 provider/compile writer 停止并收口，然后删持久对象；并发删除与重生成应只有一个赢家。复用当前会话锁/CAS/运行所有权体系，不以临时 unlink `.lock` 充当取消。具体运行停等接口本次没有完整核验，不承诺已经存在可直接调用的完整关闭 API。

**坑 D：部分失败会使重试不可达。**

当前 plan metadata 在 source/plan-store purge 之前删除，而 endpoint 开头要求 `get_issue_work_item_plan` 成功（`deletion.rs:27-29,317-327`）；Story/Design 先删主 JSON，再清版本/sessions，handler 仅成功后 evict（`spec.rs:186-199,271-284`；`deletion.rs:86-119`）。后续 IO 失败可能留下残余且下一次删请求无法走完 `[INFERENCE]`。

建议契约：门禁拒绝前零删除；一旦接受，清理步骤 NotFound=OK，IO/JSON 等真实错误必须返回，partial 可按原 scope 重入完成，不得返回 deleted 后留东西。可选择“保留可重试根记录到最后”或耐久删除标记；这是失败一致性要求，不必承诺跨 store 原子事务。跨目录成功/失败与 manager eviction须一致，Story/Design也覆盖部分失败路径。

**坑 E：不只采集 plan.work_item_ids。**

半残状态下 child session 可能仅有 runtime binding，旧 revision/work-item 集合可能与当前摘要不同。schema-v2 清理已经按 `work_item_runtime_binding.plan_id` 扫描 sessions（`deletion.rs:293-315`），但 handler 的 eviction 集仅由 plan+`plan.work_item_ids`形成（`:30-34`）。建议一次形成真实待删 manifest：实体 scope、所有所属 WI、全部匹配 sessions、audit refs；磁盘删除和内存摘除消费同一集合。不应按一个 entity ID 删不同 plan 绑定的同名 work-item session。现 `delete_workspace_sessions_for_entity` 只匹配 entity_id+workspace_type，未匹配 plan binding（`workspace_timeline_artifacts.inc.rs:216-218`）。

**坑 F：issue-wide 共享资源不能随意整目录删除。**

现 schema-v2 调用 `cleanup_shared_worktree_by_routing(app_paths, project_id, issue_id)` 时不传 plan 或 target，旁注写多仓 `shared-worktrees/` 全清（`deletion.rs:328-330`）。本次没有取得该 helper 实际实现，不能断言已经误删；但这是必须核验的边界，不能在级联补丁中扩大它。现行规格要求按 `(project, issue, repository)` 定位且其他 plan/异仓数据不受影响（`openspec/specs/work-item-group-deletion/spec.md:25-44`）。不得整删 `coding-attempts`、shared lock目录、issue 或仓库/LC注册目录。

### 1.2 IdentityMismatch：方向成立，修身份生成而非放宽校验

现场诊断已确认：13:58 旧报告与16:37新报告来自逐字节相同 source/同 IR；期间 F2b 让 finding 从缺 `kind` 变成 typed `kind=Some`，compiler_version未相应改变。因此 source/IR put 幂等成功，而新旧 report 同 ID 异 body，触发 `put_immutable` 冲突分支。其余6份历史报告不参与本次比较（原始证据与排除过程：`local://diag-report-identity-mismatch.md:13-39`）。

直接核验代码：

- author：`workspace_engine/single_candidate.rs:545-574`，report ID只用 source hash前16位；manual revision：`conversational_gate_parts/revision_turn.inc.rs:277-295`，同规则。
- `validate_mechanical_report_record:434-468`只按 report中的 source_revision_id/ir_id 读指定对象、验hash/version，不扫描历史。
- `put_immutable:574-597`校验旧对象、整记录相等才幂等成功，否则拒绝。这是正确的不可变保护。

**推荐最小修法：**为报告身份使用全长稳定摘要，摘要涵盖 `{source_revision_id, ir_id, report}` 的完整冻结内容；未来 SG3a.0 的 `structure_report` 也须进入身份。相同payload重放得到同ref，不同 findings/结构上下文得到新ref；旧记录和旧canonical refs仍可读，不改字节、不补造旧typed证据。current session CAS指向本轮实际新ref，发布仍精确join其source/IR/report/provenance。

实施陷阱：`hash_without_content_hash:665-676`只排除 `content_hash`，保留 `id`；不能先调用现 `content_hash()` 再把id设成其结果。需显式 identity摘要排除`id/content_hash`，填id后再计算现存储content_hash。两条生产writer必须使用同一生成逻辑，不仅改author。

备选：身份绑定稳定 evaluation/turn 元组及 validator语义版本。成本是冻结与重放要完整携带这些额外事实；仅bump compiler_version不足以修 source-only ID，且可能让source-only IR ID先撞version。内容摘要方案对本案及不同上下文 findings更直接；编译器版本是否需独立演进属于真实语义版本治理，不应用临时version bump代替完整报告身份。

**不会放宽：** scope/kind/record.id/content hash/source hash/compiler version/join、publish freshness、旧对象不可覆盖、SG旧无结构证据不能授权新合法性。多轮历史必须合法共存，但旧ref不能冒充current，也不能把“历史有同source”当成最新review通过。

额外范围提醒：IR ID也只按source hash派生，而IR还受target/member映射及compiler影响（`single_candidate.rs:445-487`；`work_item_plan_source_store.rs:244-258`）。这是潜在同类风险 `[INFERENCE]`，本次事故IR未变，不把IR身份重设计夹进小修；下游若发现实际IR也不等，应回到独立诊断/契约裁定。

### 2.2 层次与执行顺序

沿用现 `deletion.rs` 作为跨store协调层，低层store拥有路径及验证/幂等purge；不要把HTTP状态/manager eviction塞入source store，也不要让 `delete_workspace_sessions_for_entity` 反向删除整个实体的durable历史。

建议删除流程合同：

1. 校验scope，装载实体/归属manifest；核coding attempt、spec incoming refs、确认/曾发布保护规则；任何拒绝均零删除。
2. 取得删除与生成/compile共用的互斥或耐久停用判据，阻止新启动，处理在途writer；依据必须是服务端真实scope，非前端提供列表。
3. 按manifest清实体拥有的下属records/sessions、plan/source/revision产物和明确审计归属；步骤缺失=成功，实际IO错误不吞。
4. 根记录的最终删除/删除事实提交可重入；所有涉及manager在成功/部分清理失败两路均按同一manifest摘除/关闭。
5. 返回成功仅代表所选删除模式的闭包达到；不得为了“clean”清上游spec、其他plan、其他target或LC trust。

跨store不是当前真实事务，建议避免宣称all-or-nothing；达到的是拒绝前零删除、接受后可重试收敛、准确错误和无误伤。

## 四、删除语义选项表（owner拍板）

“不可变”是对象仍存活时禁止同ID改内容，不自动等于法律/产品层面的永不删除。下面区别实体永久删除与native fresh；后者现有anchor契约要求保存原workspace/entity/反馈/review/audit（`fix-planning-session-anchor-recovery/specs/workspace-session-resume-recovery/spec.md:41-55`）。

|选项|正在编辑/未发布|Confirmed或曾发布|Review/审计|收益与成本|
|---|---|---|---|---|
|A：完整物理删除|清完整拥有闭包|无coding attempt、无存活外部引用时，也明确允许永久删|所属versions、source/IR/report/provenance、revision/publication、session/timeline/tombstone、归属review/run档案全部删除；可只保一个不含内容的删除操作事实|最贴近owner“删干净”、沿现purge模式最小；明确丢失确认依据和复盘能力，必须接受不可恢复。不能只删一半还宣称保审计|
|B：统一软删/tombstone|退出活动查询/生成/compile，保数据|同样软删|完整引用闭包保留；tombstone只禁新资格，不删证据|可追溯；不能释放空间，7份历史仍在，必须修正确identity/current选择。需全caller过滤/准入、ID不复用、软删读取语义；不是一行`deleted=true`|
|C：分级（推荐）|从未发布且无incoming refs：完整物理清；当前Draft不足以判定|已确认、曾发布或仍被引用：默认不执行永久清除；若产品要求仍可“删除”，明确采用软删或另设永久删除授权|保护已发布整条审计；未发布临时候选随实体彻底清理|兼顾干净与审计；需owner裁定保护判据与Confirmed用户入口。可以先采用“保护对象typed拒删”的完整模式，不能伪装已经实现软删|

### 建议owner一次裁定的合同

1. **“删除”是否代表全部业务证据永久消失？** 选A就明确包括Confirmed/曾发布审计，不再承诺这类实体历史可复盘；选C则默认保护这些对象。
2. **保护依据不是仅`status==Confirmed`。** 本案已有14:08发布provenance而16:37 re-init把plan改回Draft。`provenance/发布历史`与current状态冲突时，不能据Draft把旧确认证据当临时垃圾。
3. **Review保留到什么边界？** 推荐保留则保完整source/IR/report/review/发布关联，不仅留issue-wide review孤儿；硬删则精确清归属review/run，不清别的plan审计。
4. **上游被引用的Story/Design怎样删？** 推荐存活引用时typed拒绝，要求先处理下游；不默认跨级级联plan/coding workspace。Plan删除始终保留上游spec及版本。
5. **保留历史时ID是否允许复用？** 不允许新实体/新session把旧审计当自己的；软删模式需身份终止事实。当前目录分配与explicit id写入允许同id路径出现，不能把物理移除根JSON当可靠的身份代际隔离（`lifecycle_store/plan.rs:28-37,58`；既有cleanup注释已承认same-id复用风险）。

## 1. 背景与目标

Cadence Aria 当前是一个「AI 辅助软件开发平台」，所有 AI 能力通过 CLI 子进程（Claude Code / Codex）完成，后端没有任何对外 HTTP/LLM 客户端。

本需求新增一个**独立顶层**的「图片创作 Agent」：用户通过**多轮对话**与执行器迭代「图片 prompt」，prompt 满意后**由用户点按钮触发**图片生成，Aria 后端统一调用 `gpt-image-2`（colorflowai 网关）返回 base64 图片展示。典型用途是生成 PPT 配图、业务流程图。

### 1.1 非目标

- 不改造现有 Project/Issue/Coding 域。
- 不引入新的对话 LLM（prompt 迭代复用现有 CLI 执行器）。
- 不做多用户隔离、不做 key 加密落盘（与现有 `.aria` 状态文件同级明文）。
- 不支持自主工具调用式生图（生图始终由用户显式触发）。

## 2. 设计决策汇总（已与用户确认）

| # | 决策点 | 结论 |
|---|---|---|
| D1 | prompt 迭代由谁驱动 | 复用现有 CLI 执行器（Claude Code / Codex 等所有支持执行器），通过 `resume_provider_session_id` 续接多轮 |
| D2 | 两阶段衔接模型 | **模型①**：执行器只聊 prompt；Aria 后端统一调 image2；由**用户点按钮**触发生图 |
| D3 | 放置位置 | **独立顶层** `/image-create`，不依赖 Project/Issue/git，执行器跑临时 scratch 目录 |
| D4 | 参考图 | 单张可选参考图；后端按有无图自动选 `/images/edits` 或 `/images/generations` |
| D5 | API Key 存储 | 存 Aria 后端 `.aria` 配置文件，前端设置页录入，不暴露给 CLI 子进程 |
| D6 | 模板 | 选模板/自定义机制；预置「PPT 商务配图」「业务流程图」两套 |

## 3. gpt-image-2 调用方案（技术依据）

来源：OpenAI 官方 API 参考 + colorflowai 同类 OpenAI 兼容代理文档交叉验证。

### 3.1 两个端点

| 用途 | 端点 | 请求格式 | 关键字段 |
|---|---|---|---|
| 纯文生图 | `POST /v1/images/generations` | `application/json` | `prompt`、`size`、`quality`、`output_format`、`background`、`n` |
| 参考图+prompt 改图 | `POST /v1/images/edits` | `multipart/form-data` | `image[]=@文件`（最多 16 张）、可选 `mask`、`prompt`、`input_fidelity`、其余同上 |

- 返回均为 `data[0].b64_json`（base64），契合「直接前端展示 base64、不落本地」。
- **`generations` 不接受参考图**；要「以图为内容」必须走 `edits`。

### 3.2 参数枚举（页面下拉框）

| 参数 | 选项 |
|---|---|
| `size` | `1024x1024` / `1536x1024`(横) / `1024x1536`(竖) / `auto` |
| `quality` | `low` / `medium` / `high` / `auto` |
| `background` | `transparent` / `opaque` / `auto` |
| `output_format` | `png` / `jpeg` / `webp` |
| `n` | 1 / 2 / 3 / 4（页面限制，避免一次生太多费钱；API 上限 10） |
| `input_fidelity`（仅 edits） | `low` / `high` |

````text

│  /image-create  (新顶层页面)                                          │
│  ├─ 会话列表 (多会话)                                                 │
│  ├─ 聊天区: 消息流(复用 chat-workspace 组件) + 新专用输入栏           │
│  ├─ Prompt 区块: 执行器产出的「建议 prompt」(可编辑/确认)             │
│  ├─ 参数面板: size/quality/background/format/n 下拉 + 参考图上传      │
│  └─ 设置入口 → 设置弹窗 (base_url + api_key + 默认参数)              │
└───────────┬───────────────────────────────────────┬───────────────────┘
            │ (阶段1) prompt 迭代                    │ (阶段2) 生图
            ▼                                       ▼
┌──────────── 后端 (Rust/axum) ──────────────────────────────────────────┐
│  /api/image-create/sessions (会话 CRUD)                                │
│  /api/image-create/sessions/:id/chat   (WS: 推 prompt 迭代流)          │
│  /api/image-create/generate            (POST: 调 image2，回 b64)       │
│  /api/image-create/settings (GET/PUT: key/默认参数)                    │
│                                                                        │
│  Prompt 迭代器: 复用 StreamingProvider(Claude/Codex) + resume session  │
│  图片客户端:   新增 reqwest → colorflowai /generations 或 /edits       │
│  存储:         .aria/image_create.json (settings) + 会话持久化         │
└────────────────────────────────────────────────────────────────────────┘
````

### 4.1 关键边界

- **prompt 迭代**走现有 CLI 执行器链路（`StreamingProviderInput` + `resume_provider_session_id`），跑在每次会话的 scratch 临时目录（无 git）。
- **图片生成**走全新 `reqwest` 链路，由后端发起，key 只在后端。
- 两者**完全解耦**，唯一耦合点是「最终 prompt 字符串 + 参数」从前端传给 `/generate`。

### 4.2 新增依赖

- 后端：`reqwest`（首次引入对外 HTTP 客户端；带 `json`、`multipart` feature）。

## 5. 两阶段数据流（核心流程）

### 5.1 阶段 1｜prompt 迭代（CLI 执行器，多轮）

````text
用户输入"画一个产品上线流程的配图"
  → 前端 POST /chat (sessionId, message)
  → 后端构造 StreamingProviderInput {
       prompt: 模板引导词 + 用户消息,
       working_dir: scratch_dir,
       resume_provider_session_id: 上轮的 provider session(首轮为空),
       structured_output_contract: { 最终prompt 字段 }
     }
  → 执行器流式输出 → WS 推前端 → 渲染成:
       (a) 对话气泡(执行器的解释/追问)
       (b) 「建议 prompt」可编辑区块
  → 执行器完成, 记录新的 provider_session_id 供下轮续接
````

- prompt 需让执行器**结构化输出**（`structured_output_contract`），便于提取成独立可编辑区块。
- 多轮续接：每一轮带同一 `provider_session_id`，执行器记得上文。

### 5.2 阶段 2｜生成图片（用户点按钮，Aria 后端调 image2）

````text
用户点击「用此 prompt 生成」, 前端提交:
  POST /generate { sessionId, prompt(可能用户编辑过), params, referenceImage?(base64) }
  → 后端读 settings.api_key
  → 有 referenceImage ? POST /v1/images/edits   (multipart: image[]+prompt+params)
                     : POST /v1/images/generations (json: prompt+params)
  → 拿 data[0].b64_json → 回前端 → <img src="data:image/png;base64,..."> 展示
  → 图片结果存入会话历史(便于来回看)
````

### 5.3 不满意循环

用户在聊天里继续输入反馈 → 回到阶段 1（同 provider session 续接，执行器记得上文）→ 更新 prompt 区块 → 再点生成。

## 6. API Key 与设置存储

### 6.1 存储文件

路径：`<workspace>/.aria/image_create.json`

````json
{
  "base_url": "https://colorflowai.com/v1",
  "api_key": "sk-xxx",
  "defaults": {
    "size": "1024x1024",
    "quality": "high",
    "output_format": "png",
    "background": "auto",
    "n": 1
  },
  "custom_templates": []
}
````

### 6.2 接口

- `GET /api/image-create/settings`：key 脱敏返回（如 `sk-****1234`）。
- `PUT /api/image-create/settings`：写盘。

### 6.3 安全

- key 仅后端读取用于 `reqwest` 请求头。
- **不传给 CLI 子进程**（子进程只做 prompt 迭代，不需要 key）。
- 前端不缓存明文，展示脱敏。

## 8. 模板机制与预置内容

### 8.1 机制

- 创建会话时选模板（卡片或下拉）或「自定义」填引导词。
- 模板引导词注入 prompt 迭代对话，约束生成方向。
- 预置两套内置；自定义模板存进 `.aria/image_create.json` 的 `custom_templates`。

### 8.2 预置模板内容

**模板①「PPT 商务配图」**（幻灯片配图、概念图、封面）

> 生成适合商业 PPT 的配图。要求：构图简洁、留白充足、主体居中或遵循三分法；风格偏扁平/等距(isometric)/2.5D 插画，色彩克制（主色+1-2 辅色，避免高饱和）；无文字、无水印；背景干净（纯色或轻渐变）；尺寸适配 16:9 或 1:1；视觉传达一个清晰概念，专业克制，不花哨。

**模板②「业务流程图/示意图」**（流程、架构、步骤说明）

> 生成清晰的业务流程图/示意图。要求：明确表达步骤/角色/流向，使用箭头、方框、连线等结构化元素；配色用语义色（开始/结束/判断/动作各一色），整体克制；节点文字为英文或简短中文，排版整齐对齐；风格扁平、线条统一粗细；适合插入文档说明，背景干净。

## 9. UI 视觉方向

参考 `[educational-platform]` 风格：**Claymorphism + 鲜艳块状 + 扁平 + 清晰层级 + 微交互**。

与现有 Aria 专业工作台调性有差异。方案设计阶段给出两种视觉方案对比：

- **方案①融合**：保留块状卡片 + 清晰层级 + 微交互，收鲜艳度、贴合 Aria 中性灰 + 品牌色。
- **方案②照搬**：完整 Claymorphism（圆润、柔和阴影、Playful 配色）。

> 视觉方案在设计评审阶段定稿（见 `cadence/designs/` 后续文档）。

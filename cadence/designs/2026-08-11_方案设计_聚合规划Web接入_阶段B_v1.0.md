## 2. 背景与目标

### 2.1 背景

Plan 3（WP4 聚合规划，12 Task）在后端实现了 `PlanningContextResolver`——使 Story/Design/WorkItemPlan 的 context/cwd/prompt 来自同一快照，AI 从聚合根只读启动、注入紧凑成员 inventory。该 resolver 已被 `socket.rs`（planning resume）使用。

但 **Web 入口（`handlers/lifecycle.rs`）尚未接线**：
- `generate_story_specs`（lifecycle.rs:379）传 `aggregate_codebase: None`
- `generate_design_specs`（lifecycle.rs:430）传 `aggregate_codebase: None`
- `prepare_work_item_plan`（lifecycle.rs:456）走单值 `repository_id` 路径
- `issue_lifecycle`（lifecycle.rs:14，GET 查询）无条件要求 `issue.repo_id`（lifecycle.rs:58），多仓 issue 无 repo_id 会报错

因此页面上多仓库 issue 无法触发聚合规划——Story/Design 生成时 AI 看不到成员仓清单，无法产出 `involved_repository_ids` 与 `target_repository_id`；且多仓 issue 的 lifecycle 查询本身就不通。

### 2.2 目标

让多仓库（逻辑代码库）issue 在页面上能完整走「Story → Design → WorkItem → compile」规划链路：
- Story/Design 阶段 AI 拥有完整聚合视野（成员仓 inventory + 索引摘要）
- Design 涉及多仓时必须带 `change_order`（改动顺序图）
- WorkItem 阶段产出带 `target_repository_id` 的单仓工作项
- compile 消费 change_order 映射成跨仓执行依赖

**单仓 issue 行为完全不变**（向后兼容）。

### 2.3 成功标准

- 多仓 issue 在页面点「生成 Story Spec」→ AI 注入聚合 inventory，产出跨仓 involved_repository_ids
- 多仓 issue（Design involved > 1 仓）的 Design 必须带 change_order
- WorkItem 按 target_repository_id 分组展示（前端消费后端已有的 `work_item_repository_groups`）
- compile 后跨仓 WorkItem 通过 depends_on 建立执行顺序
- 单仓 issue 全流程行为不变，既有测试全绿
- it_web / lib 门禁不回归

## 4. 方案设计

### 4.1 B1：Story/Design/WorkItemPlan/issue_lifecycle 接入 PlanningContextResolver

> v1.1 修订（reviewer finding 1 + 2）：用真实字段重写、明确上下文接线时序、增加 `issue_lifecycle` handler 改造。

**改动文件**：`src/web/handlers/lifecycle.rs`（**4 个 handler**，v1.0 漏了 issue_lifecycle）

**真实字段对照**（已核实代码）：
- `PlanningContextSnapshot`（planning_context.rs:19）**无 `id` 字段**，以 `project_id + issue_id` 标识（单 issue 一份，存于 `planning_context_snapshot_path`）
- `AggregateStorySpecScope`（inputs.rs:19）字段：`logical_codebase_ref: Uuid`、`effective_member_ids: Vec<LogicalRepositoryId>`、`involved_repository_ids: Vec<LogicalRepositoryId>`、`focus_repository_id: Option<LogicalRepositoryId>` —— **无 `snapshot_ref`**
- `AggregateDesignSpecScope`（inputs.rs:50）字段：`logical_codebase_ref`、`effective_member_ids`、`involved_repository_ids`、`change_order: Vec<LogicalRepositoryId>`

**统一接线逻辑**（4 个 handler 共用 routing 三态判定）：

```
1. RepositoryRouting::load_for_issue(app_paths, project_id, issue_id) 判定三态
2. Legacy (None,None) → 现状不变
   - repository_id = issue.repo_id（issue 必须有 repo_id）
   - aggregate_codebase = None
   - workspace session cwd = 单仓路径
3. Logical (Some,Some) → PlanningContextResolver.build(project_id, issue_id, targets)
   - targets 参数：Story/Design 传 &[]（AI 自决涉及哪些仓）；WorkItemPlan 传 design 的 involved
   - 拿到 ResolvedPlanningContext { cwd, inventory_injection, snapshot, context_resolution, ... }
   - aggregate_codebase 构造（AI 产出前的初始 scope）：
       AggregateStorySpecScope {
           logical_codebase_ref: manifest.logical_codebase_id,  // 来自 manifest，非 snapshot.id
           effective_member_ids: snapshot.effective_member_ids.clone(),  // 来自快照（权威）
           involved_repository_ids: vec![],  // 初始空，AI 产出后回填（create_story_spec 内部消费 AI 输出填充）
           focus_repository_id: None,  // AI 产出后回填
       }
     （AggregateDesignSpecScope 同理，change_order 初始 vec![]，AI 产出后回填）
   - workspace session cwd = resolved.cwd（聚合根 provider_context_root）
4. FailClosed → 稳定错误码 repository_routing_* + 4xx（与阶段 A 一致）
```

**上下文进入 WebSocket provider run 的机制**（v1.0 未定义，v1.1 补充）：
- handler 创建 workspace session 时，session 携带 `cwd = resolved.cwd`
- prompt 注入 `inventory_injection`（紧凑成员清单）经 `ensure_workspace_context_message`（lifecycle.rs 现有机制）写入 session 首条 context message
- WebSocket 连接后（socket.rs），provider run 从 session 读取 cwd + context message，机制与现有 planning resume 一致（socket.rs 已用 PlanningContextResolver）

**4 个 handler 各自的改动**：

| handler | 现状 | Logical 分支改动 |
|---|---|---|
| `issue_lifecycle`（GET 查询，:14）| :58 无条件 `issue.repo_id.ok_or_else(...)` | Logical 时不要求 repo_id（用 manifest/selection 解析）；Legacy 时保持现状。**这是多仓 issue 查询能通的前提** |
| `generate_story_specs`（:350）| :379 `aggregate_codebase: None` | Logical 分支接 resolver，构造 AggregateStorySpecScope（见上）|
| `generate_design_specs`（:405）| :430 `aggregate_codebase: None` | Logical 分支接 resolver，构造 AggregateDesignSpecScope |
| `prepare_work_item_plan`（:456）| 单值 `repository_id` 路径 | Logical 分支接 resolver，targets 传 design involved，校验 target ∈ effective selection（REQ-TGT-01）|

**关键点**：
- resolver 已实现（socket.rs 在用），这里把 4 个 handler 从「硬编码 None / 硬要求 repo_id」改成「按 routing 三态分支」
- Story/Design 的 aggregate_codebase 初始 scope 的 `involved_repository_ids` 留空——`create_story_spec` / `create_design_spec` 内部消费 AI 输出后回填（这是既有机制，inputs.rs 注释已说明「AI 明确声明的涉及仓库」）
- WorkItemPlan（prepare）的 targets 传 design 的 involved_repository_ids：compile 时校验 target 属于有效 selection（REQ-TGT-01）

### 4.2 B2：change_order → depends_on 消费 + 多仓 Design 强制 change_order

> v1.1 修订（reviewer finding 3 + 4）：3b 判定基准对齐 spec（Design involved > 1），depends_on 映射规则精确化。

**(a) 强制 change_order（实现 REQ-PLN-05 收紧）**：
- 文件：`src/product/lifecycle_store/spec.rs`（DesignSpec 创建/修订校验）
- 判定基准：**Design 的 `involved_repository_ids.len() > 1`**（不是「issue 有 manifest」）
- 现状：`change_order` 缺失不强制（spec.rs:126「change_order 缺失不强制」）
- 改后：
  - Design 的 `involved_repository_ids.len() > 1` 时 **必须**提供 change_order；缺失 → blocker `change_order_required_for_logical_codebase`
  - Design 的 `involved_repository_ids.len() <= 1`（单仓或未涉及仓）：change_order 可选
- 边界：change_order 若给出，全部 id 必须 ∈ involved 且不重复（既有校验 spec.rs:431-433 保留）

**(b) compile 消费 change_order（实现 REQ-TGT-04，精确映射规则）**：
- 文件：`src/product/workspace_engine/draft_batch/compile_support.rs`
- Design 的 `change_order: Vec<LogicalRepositoryId>` 是**仓库级**执行顺序（如 [公共契约仓, provider仓, consumer仓]）
- compile 时映射成 **WorkItem 级** `depends_on`（dependency_graph）。精确规则：
  1. 对每个 WorkItem A（target = tA）和 WorkItem B（target = tB），若 tA ≠ tB 且 change_order 中 tA 在 tB **之前**，则 B `depends_on` A（B 等 A 完成后才可执行）
  2. 同 target 仓的多个 WorkItem：**不**因 change_order 建立依赖（同仓内顺序由既有 WorkItem 级 depends_on / sequence_hint 决定，change_order 只管跨仓）
  3. 合并既有 WorkItem 级 depends_on（candidate 提取的，compile_support.rs:282）与本次跨仓 depends_on
  4. 环检测：合并后若存在环 → blocker `dependency_cycle`（REQ-TGT-04「校验无环」）
- 现状：compile_support.rs:282 已从 candidate 提取 WorkItem 级 depends_on，但没接 Design 级 change_order；本 task 补跨仓映射

## 6. 数据流（单仓 vs 多仓对比）

### 单仓 issue（现状不变）
```
issue.repo_id = "repository_0001"
issue_lifecycle: 要求 repo_id ✅
Story: repository_id = issue.repo_id, aggregate_codebase = None  → AI 看 1 仓
Design: 同理
WorkItem: repository_id = 某仓
coding: 在 target 仓执行
```

### 多仓 issue（B 接通后）
```
issue（无 repo_id，有 manifest+selection，50 成员仓）
issue_lifecycle: Logical 分支不要求 repo_id（用 manifest/selection 解析）← B1 新增
Story: aggregate_codebase = Some(AggregateStorySpecScope{ logical_codebase_ref, effective_member_ids, involved:[], focus:None })
       → AI 看 50 仓 inventory + 索引摘要
       → AI 产出 involved_repository_ids + focus_repository_id（create_story_spec 回填）
Design: AggregateDesignSpecScope{ ..., change_order:[] }
       → AI 产出 involved + change_order（若 involved>1 必须给）
       → 校验：involved>1 且 change_order 空 → blocker（B2）
WorkItem 生成（按仓拆分）:
       → 每个 WorkItem 带 target_repository_id（指向单一仓）
compile: 消费 change_order → 跨仓 depends_on（B2 映射规则）
分组展示: 前端消费 work_item_repository_groups（后端已有，B3 前端渲染）
coding: 每个 WorkItem 在自己 target 仓执行（阶段 C）
```

| 风险 | 缓解 |

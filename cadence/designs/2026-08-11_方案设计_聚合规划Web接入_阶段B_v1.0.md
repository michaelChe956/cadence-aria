## 2. 背景与目标

### 2.1 背景

Plan 3（WP4 聚合规划，12 Task）在后端实现了 `PlanningContextResolver`——使 Story/Design/WorkItemPlan 的 context/cwd/prompt 来自同一快照，AI 从聚合根只读启动、注入紧凑成员 inventory。该 resolver 已被 `socket.rs`（planning resume）使用。

但 **Web 入口（`handlers/lifecycle.rs`）尚未接线**：
- `generate_story_specs`（lifecycle.rs:379）传 `aggregate_codebase: None`
- `generate_design_specs`（lifecycle.rs:430）传 `aggregate_codebase: None`
- `prepare_work_item_plan`（lifecycle.rs:456）走单值 `repository_id` 路径

因此页面上多仓库 issue 无法触发聚合规划——Story/Design 生成时 AI 看不到成员仓清单，无法产出 `involved_repository_ids` 与 `target_repository_id`。

### 2.2 目标

让多仓库（逻辑代码库）issue 在页面上能完整走「Story → Design → WorkItem → compile」规划链路：
- Story/Design 阶段 AI 拥有完整聚合视野（成员仓 inventory + 索引摘要）
- Design 产出跨仓 `change_order`（改动顺序图）
- WorkItem 阶段产出带 `target_repository_id` 的单仓工作项
- compile 消费 change_order 映射成跨仓执行依赖

**单仓 issue 行为完全不变**（向后兼容）。

### 2.3 成功标准

- 多仓 issue 在页面点「生成 Story Spec」→ AI 注入聚合 inventory，产出跨仓 involved_repository_ids
- 多仓 issue 的 Design 必须带 change_order（多仓强制）
- WorkItem 按 target_repository_id 分组展示
- compile 后跨仓 WorkItem 通过 depends_on 建立执行顺序
- 单仓 issue 全流程行为不变，既有测试全绿
- it_web / lib 门禁不回归

## 3. 已确认的产品决策（brainstorming 结论）

| # | 决策 | 说明 |
|---|---|---|
| 1 | 单仓不走 resolver | 单仓（无 manifest）走 legacy 路径（直接 repo_id，aggregate_codebase: None）；仅多仓接 PlanningContextResolver。与阶段 A `(None,None)→legacy` 语义一致 |
| 2 | 多仓完整聚合视野 | 多仓 issue 的 Story/Design 生成注入完整聚合上下文（inventory + 索引摘要），AI 产出跨仓 involved_repository_ids；不一致即 fail-closed |
| 3 | 多仓强制 change_order | **收紧既有语义**：多仓 issue（有 manifest/selection）的 Design 必须提供 change_order；缺失即 blocker。单仓 change_order 仍可选。（既有 spec.rs:126「缺失不强制」需收紧）|
| 4 | 前端分组 | 后端 lifecycle API 返回 WorkItem 扁平列表（每个带 target_repository_id），不改 API 形状；前端用 `group_work_items_by_target` 分组展示 |
| 5 | 一个 Plan | B1+B2+B3+B6 作为一个 Plan（8-12 Task） |

## 4. 方案设计

### 4.1 B1：Story/Design/WorkItemPlan 接入 PlanningContextResolver

**改动文件**：`src/web/handlers/lifecycle.rs`（3 个 handler）

**统一接线逻辑**（3 个 handler 共用）：

```
1. RepositoryRouting::load_for_issue(app_paths, project_id, issue_id) 判定三态
2. Legacy (None,None) → 现状不变
   - repository_id = issue.repo_id
   - aggregate_codebase = None
   - workspace session cwd = 单仓路径
3. Logical (Some,Some) → PlanningContextResolver.build()
   - targets 参数：Story/Design 传 &[]（此时未产出 involved）；WorkItemPlan 传 design 的 involved/change_order
   - 拿到 ResolvedPlanningContext { cwd, inventory_injection, snapshot, ... }
   - aggregate_codebase = Some(AggregateStorySpecScope { snapshot_ref: snapshot.id, ... })
   - workspace session cwd = resolved.cwd（聚合根 provider_context_root）
   - prompt 注入 inventory_injection（紧凑成员清单）
4. FailClosed → 稳定错误码 repository_routing_* + 4xx（与阶段 A 一致）
```

**关键点**：
- resolver 已实现（socket.rs 在用），这里只把 3 个 handler 从「硬编码 None」改成「按 routing 三态分支」
- Story/Design 的 targets 传空：此时 AI 还没产出 involved_repository_ids，AI 自己决定涉及哪些仓；inventory 注入让 AI 有全局视野
- WorkItemPlan（prepare）的 targets 传 design 的 involved_repository_ids + change_order：compile 时用于校验 target 属于有效 selection（REQ-TGT-01）

**aggregate_codebase 类型**（已存在，`inputs.rs:34`）：
```rust
pub aggregate_codebase: Option<AggregateStorySpecScope>
// None = 传统单仓；Some = 逻辑代码库分支，以 involved_repository_ids 等聚合字段为权威
```

### 4.2 B2：change_order → depends_on 消费 + 多仓强制 change_order

**两点改动**：

**(a) 收紧语义（决策 3b）**：
- 文件：`src/product/lifecycle_store/spec.rs`（DesignSpec 创建/修订校验）+ `compile_support.rs`
- 现状：`change_order` 缺失不强制（spec.rs:126「change_order 缺失不强制」）
- 改后：
  - 多仓 issue（routing 为 Logical）的 Design **必须**提供 change_order；缺失 → blocker `change_order_required_for_logical_codebase`
  - 单仓 issue（routing 为 Legacy）：change_order 仍可选
- 实现要点：校验需感知 routing 状态（Legacy/Logical），而非无条件强制

**(b) compile 消费 change_order（实现 REQ-TGT-04）**：
- 文件：`src/product/workspace_engine/draft_batch/compile_support.rs`
- Design 的 `change_order: Vec<LogicalRepositoryId>`（仓的执行顺序，REQ-TGT-04）
- compile 时映射成 WorkItem 间的跨仓执行依赖（`dependency_graph`）
- 现状：compile_support.rs:282 已从 candidate 提取 `depends_on`（WorkItem 级），但没接 Design 级的 change_order（仓级）
- 改后：compile 时，若两个 WorkItem 的 target 仓在 change_order 里有先后，建立依赖边；保证无环（REQ-TGT-04「校验无环」）

### 4.3 B3：WorkItem 分组视图（前端分组，决策 4b）

## 6. 数据流（单仓 vs 多仓对比）

### 单仓 issue（现状不变）
```
issue.repo_id = "repository_0001"
Story: repository_id = issue.repo_id, aggregate_codebase = None  → AI 看 1 仓
Design: 同理
WorkItem: repository_id = 某仓
coding: 在 target 仓执行
```

### 多仓 issue（B 接通后）
```
issue（无 repo_id，有 manifest+selection，50 成员仓）
Story: aggregate_codebase = Some(聚合上下文)
       → AI 看 50 仓 inventory + 索引摘要
       → 产出 involved_repository_ids + focus_repository_id
Design: 同样从聚合上下文
       → 产出 involved_repository_ids + change_order（多仓强制）
WorkItem 生成（按仓拆分）:
       → 每个 WorkItem 带 target_repository_id（指向单一仓）
       → 跨 3 仓 design → 拆成 3 个 WorkItem，各 target 一个仓
compile: 消费 change_order → depends_on 建立跨仓执行顺序
分组展示: 前端按 target 分组（REQ-TGT-05）
coding: 每个 WorkItem 在自己 target 仓执行（阶段 C）
```

## 8. 与既有 spec 的关系

B 阶段是 `2026-08-05-add-logical-codebase` change 的 `target-aware-work-item` capability 的 **Web 接入实现**：
- REQ-TGT-01（target 必填与校验集）：B1 接线 + compile 校验

B 完成后，该 capability 的 Web 接入部分实现完毕；runtime binding 冻结（REQ-TGT-03 的 runtime 部分）留阶段 C。

## 2. 背景与目标

### 2.1 背景

Plan 3（WP4 聚合规划，12 Task）在后端实现了 `PlanningContextResolver`——使 Story/Design/WorkItemPlan 的 context/cwd/prompt 来自同一快照，AI 从聚合根只读启动、注入紧凑成员 inventory。该 resolver 已被 `socket.rs`（planning resume）使用。

但 **Web 入口（`handlers/lifecycle.rs`）尚未接线**：
- `generate_story_specs`（lifecycle.rs:379）传 `aggregate_codebase: None`
- `generate_design_specs`（lifecycle.rs:430）传 `aggregate_codebase: None`
- `prepare_work_item_plan`（lifecycle.rs:456）走单值 `repository_id` 路径
- `issue_lifecycle`（lifecycle.rs:14，GET 查询）无条件要求 `issue.repo_id`（lifecycle.rs:58），多仓 issue 无 repo_id 会报错

因此页面上多仓库 issue 无法触发聚合规划——Story/Design 生成时 AI 看不到成员仓清单，无法产出 `involved_repository_ids` 与 `target_repository_id`；且多仓 issue 的 lifecycle 查询本身就不通。

### 2.2 目标

让多仓库（逻辑代码库）issue 在页面上能完整走「Story → Design → WorkItem → compile」规划链路：
- Story/Design 阶段 AI 拥有完整聚合视野（成员仓 inventory + 索引摘要）
- Design 涉及多仓时必须带 `change_order`（改动顺序图）
- WorkItem 阶段产出带 `target_repository_id` 的单仓工作项
- compile 消费 change_order 映射成跨仓执行依赖

**单仓 issue 行为完全不变**（向后兼容）。

### 2.3 成功标准

- 多仓 issue 在页面点「生成 Story Spec」→ AI 注入聚合 inventory，产出跨仓 involved_repository_ids
- 多仓 issue（Design involved > 1 仓）的 Design 必须带 change_order
- WorkItem 按 target_repository_id 分组展示（前端消费后端已有的 `work_item_repository_groups`）
- compile 后跨仓 WorkItem 通过 depends_on 建立执行顺序
- 单仓 issue 全流程行为不变，既有测试全绿
- it_web / lib 门禁不回归

## 4. 方案设计

### 4.1 B1：Story/Design/WorkItemPlan/issue_lifecycle 接入聚合规划（方案 X：两阶段创建 + structured output 回写 + confirm gate）

> v1.2 重写（reviewer finding 1 揭示根本时序问题）。
>
> **问题背景**：`create_story_spec`/`create_design_spec` 在创建前同步调用 `validate_aggregate_*_scope`（spec.rs:45/129），空 involved 立即 blocker（spec.rs:396）。但 involved 由 AI 产出（在 WebSocket run 后），create 在 handler 同步执行。所以「先 create 空 scope 再回填」不可能。多仓必须用**两阶段创建**。

#### 真实字段对照（已核实）
- `PlanningContextSnapshot`（planning_context.rs:19）**无 `id` 字段**，以 `project_id + issue_id` 标识
- `AggregateStorySpecScope`（inputs.rs:19）：`logical_codebase_ref: Uuid`、`effective_member_ids`、`involved_repository_ids`、`focus_repository_id: Option`
- `AggregateDesignSpecScope`（inputs.rs:50）：同上 + `change_order: Vec`
- `extract_structured_json`（parsers.rs:14）：已实现的成熟机制，用 `<ARIA_STRUCTURED_OUTPUT nonce>...</ARIA_STRUCTURED_OUTPUT>` 标签从 markdown 提取 JSON（code review / plan repair 在用）
- `confirmation_status: Draft`（create 时，spec.rs:68）：已有草稿态概念

#### 方案 X 时序：两阶段创建

**阶段 1：HTTP handler（generate_story_specs / generate_design_specs）**
```
1. RepositoryRouting::load_for_issue 判定三态
2. Legacy（单仓）→ 现状不变（aggregate_codebase=None，create 不校验 involved）
3. Logical（多仓）→
   a. PlanningContextResolver.build() → resolved { cwd, inventory_injection, snapshot }
   b. create_story_spec：aggregate_codebase = Some(AggregateStorySpecScope {
          logical_codebase_ref: manifest.logical_codebase_id,
          effective_member_ids: snapshot.effective_member_ids.clone(),
          involved_repository_ids: vec![],   // 草稿态空（阶段2回填）
          focus_repository_id: None,
      })
   c. ★关键改动1：放宽 validate_aggregate_*_scope
      - Draft 态允许空 involved（仅校验给出的 involved ∈ effective_member_ids）
      - Confirmed 态强制 involved 非空（confirm gate，阶段2后）
   d. create_workspace_session（cwd = resolved.cwd，聚合根 provider_context_root）
   e. ★关键改动2：ensure_workspace_context_message 注入
      - aggregate_story_scope_prompt（现在 dead_code 的函数，这里调用）
      - inventory_injection.rendered（紧凑成员清单）
      - StructuredOutputContract（要求 AI 在 markdown 里产出 <ARIA_STRUCTURED_OUTPUT> JSON）
   f. 返回 session id
4. FailClosed → 稳定错误码 repository_routing_* + 4xx
```

**阶段 2：WebSocket AI run（前端连 session 后）**
```
AI 看 prompt（inventory + 「必须列出 involved」指令 + StructuredOutputContract）
→ 产出 markdown + structured output JSON
   Story schema: { "involved_repository_ids": ["<uuid>",...], "focus_repository_id": "<uuid>"|null }
   Design schema: { "involved_repository_ids": [...], "change_order": ["<uuid>",...] }
→ ★关键改动3：扩展 AI 产出解析
   - WebSocket 流程用 extract_structured_json 解析 involved_repository_ids（+ focus/change_order）
   - ★关键改动4：新增 update 入口 update_story_spec_aggregate / update_design_spec_aggregate
     （Draft 态可更新 involved/focus/change_order；解析后回写 StorySpecRecord/DesignSpecRecord）
→ 用户 confirm（workspace_session_confirm）
   → ★关键改动5：confirm gate
     - confirm_workspace_entity 对多仓（routing=Logical）Story/Design 校验：
       * involved 非空且 ∈ effective_member_ids（REQ-PLN-04）
       * Design: involved>1 必须 change_order（3b，REQ-PLN-05 收紧）
     - 校验失败 → blocker，不允许 Confirmed
```

#### structured output 契约（复用现有机制）
- 标签：`<ARIA_STRUCTURED_OUTPUT nonce="...">...</ARIA_STRUCTURED_OUTPUT>`（parsers.rs 现有）
- Story JSON：`{ "involved_repository_ids": [LogicalRepositoryId], "focus_repository_id": LogicalRepositoryId|null }`
- Design JSON：`{ "involved_repository_ids": [LogicalRepositoryId], "change_order": [LogicalRepositoryId] }`
- prompt 注入用 `aggregate_story_scope_prompt`/`aggregate_design_scope_prompt`（prompts.rs:375/415，现 dead_code）+ StructuredOutputContract（cross_cutting 现有）

#### 4 个 handler 各自的改动

| handler | 现状 | 改动 |
|---|---|---|
| `issue_lifecycle`（GET，:14）| :58 无条件 `issue.repo_id.ok_or_else` | Logical 时不要求 repo_id（用 manifest/selection）；Legacy 保持现状 |
| `generate_story_specs`（:350）| :379 `aggregate_codebase: None` | 阶段1 Logical 分支（方案 X）；Legacy 不变 |
| `generate_design_specs`（:405）| :430 `aggregate_codebase: None` | 阶段1 Logical 分支（方案 X）；Legacy 不变 |
| `prepare_work_item_plan`（:456）| 单值 repository_id | **不同于 Story/Design**：target 来自已 confirmed 的 design 的 involved，不是 AI 新产出。直接从 confirmed design 拿 involved/target，targets 传 resolver 校验 ∈ selection（REQ-TGT-01）。不需两阶段 |

#### WebSocket AI run 的 involved 解析与回写落点
- 解析：在 workspace_ws_handler 的 run 流程，AI 产出后用 extract_structured_json 提取 involved JSON
- 回写：调用新增的 `LifecycleStore::update_story_spec_aggregate` / `update_design_spec_aggregate`（Draft 态更新 involved/focus/change_order）
- 这与现有 SpecVersionRecord（只存 markdown）分离：involved 是 StorySpecRecord 字段（非 version 字段），update 直接改 record

### 4.2 B2：change_order → depends_on 消费 + 多仓 Design 强制 change_order

> v1.1 修订（reviewer finding 3 + 4）：3b 判定基准对齐 spec（Design involved > 1），depends_on 映射规则精确化。

**(a) 强制 change_order（实现 REQ-PLN-05 收紧）**：
- 文件：`src/product/lifecycle_store/spec.rs`（DesignSpec 创建/修订校验）
- 判定基准：**Design 的 `involved_repository_ids.len() > 1`**（不是「issue 有 manifest」）
- 现状：`change_order` 缺失不强制（spec.rs:126「change_order 缺失不强制」）
- 改后：
  - Design 的 `involved_repository_ids.len() > 1` 时 **必须**提供 change_order；缺失 → blocker `change_order_required_for_logical_codebase`
  - Design 的 `involved_repository_ids.len() <= 1`（单仓或未涉及仓）：change_order 可选
- 边界：change_order 若给出，全部 id 必须 ∈ involved 且不重复（既有校验 spec.rs:431-433 保留）

**(b) compile 消费 change_order（实现 REQ-TGT-04，精确映射规则）**：
- 文件：`src/product/workspace_engine/draft_batch/compile_support.rs`
- Design 的 `change_order: Vec<LogicalRepositoryId>` 是**仓库级**执行顺序（如 [公共契约仓, provider仓, consumer仓]）
- compile 时映射成 **WorkItem 级** `depends_on`（dependency_graph）。精确规则：
  1. 对每个 WorkItem A（target = tA）和 WorkItem B（target = tB），若 tA ≠ tB 且 change_order 中 tA 在 tB **之前**，则 B `depends_on` A（B 等 A 完成后才可执行）
  2. 同 target 仓的多个 WorkItem：**不**因 change_order 建立依赖（同仓内顺序由既有 WorkItem 级 depends_on / sequence_hint 决定，change_order 只管跨仓）
  3. 合并既有 WorkItem 级 depends_on（candidate 提取的，compile_support.rs:282）与本次跨仓 depends_on
  4. 环检测：合并后若存在环 → blocker `dependency_cycle`（REQ-TGT-04「校验无环」）
- 现状：compile_support.rs:282 已从 candidate 提取 WorkItem 级 depends_on，但没接 Design 级 change_order；本 task 补跨仓映射

## 6. 数据流（单仓 vs 多仓对比）

### 单仓 issue（现状不变）
```
issue.repo_id = "repository_0001"
issue_lifecycle: 要求 repo_id ✅
Story: repository_id = issue.repo_id, aggregate_codebase = None  → AI 看 1 仓
Design: 同理
WorkItem: repository_id = 某仓
coding: 在 target 仓执行
```

### 多仓 issue（B 接通后，方案 X 两阶段）
```
issue（无 repo_id，有 manifest+selection，50 成员仓）

【阶段1：HTTP handler】
issue_lifecycle: Logical 分支不要求 repo_id ← B1 新增
generate_story_specs:
   resolver.build() → cwd + inventory + snapshot
   create_story_spec(aggregate_codebase=Some{ involved:[] 草稿态 })
     ← 改动1: Draft 态放宽校验（允许空 involved）
   create_session(cwd=聚合根) + 注入 aggregate_story_scope_prompt + StructuredOutputContract
     ← 改动2: prompt 函数从 dead_code 转为调用
   返回 session id

【阶段2：WebSocket AI run】
AI 看 prompt（inventory + 「必须列出 involved」）
   → 产出 markdown + <ARIA_STRUCTURED_OUTPUT>{involved_repository_ids, focus}</...>
   ← 改动3: extract_structured_json 解析 involved
   ← 改动4: update_story_spec_aggregate 回写 record（Draft 态）
用户 confirm:
   ← 改动5: confirm gate 校验 involved 非空 + Design involved>1 须 change_order（3b）
   → 通过则 Confirmed；失败则 blocker

generate_design_specs: 同模式（structured output 含 change_order）
prepare_work_item_plan: 不同——target 来自 confirmed design 的 involved（非 AI 新产出）
   → 直接拿 involved 传 resolver 校验 ∈ selection（REQ-TGT-01）

compile: 消费 change_order → 跨仓 depends_on（B2 映射规则）
分组展示: 前端消费 work_item_repository_groups（后端已有，B3 前端渲染）
coding: 每个 WorkItem 在自己 target 仓执行（阶段 C）
```

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 3b 强制 change_order 破坏既有测试 | 判定基准是「Design involved > 1」（非 issue 有 manifest），既有单仓/单仓涉及测试不受影响；多仓涉及测试需同步加 change_order。TDD 先改测试 |
| B1 接线后单仓行为回归 | 单仓走 Legacy 分支（现状不变），routing 三态判定已有充分测试（阶段 A）|
| issue_lifecycle 改造破坏单仓查询 | Legacy 分支保持「要求 repo_id」现状，仅 Logical 分支放宽；单仓测试不受影响 |
| PlanningContextResolver 在 handler 同步调用阻塞 | resolver 是本地文件读 + 渲染，无网络 IO，不阻塞 |
| 聚合 inventory 注入超预算 | resolver 已实现预算截断（Plan 3 Task 4），复用即可 |
| B2 跨仓 depends_on 与既有 WorkItem 级 depends_on 冲突 | 合并规则明确（4.2.b），既有 WorkItem 级优先，跨仓作为补充；环检测兜底 |
| ★方案X：create 放宽 Draft 态破坏 REQ-PLN-04 | Draft 允许空 involved，但 confirm gate 强制非空；REQ-PLN-04「AI 不确定即 blocker」在 confirm 落地（AI 没产出→confirm 阻断）|
| ★方案X：structured output 解析 involved 是新机制（Story/Design 未用过 extract_structured_json）| 复用成熟机制（code review/plan repair 验证过）；TDD 先写解析单测；schema 简单（1-2 字段 JSON）|
| ★方案X：update 入口允许 Draft 态改 involved 可能被滥用 | update 入口仅限 WebSocket AI run 回写路径调用，校验给出的 involved ∈ effective_member_ids |

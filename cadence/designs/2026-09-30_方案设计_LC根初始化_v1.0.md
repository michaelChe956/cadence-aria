## 1. 背景与现状真相

### 1.1 聚合初始化不是可用 recipe

当前 `GatewayBackedAggregateProviderTurnDriver::streaming_input` 的 prompt 是 `aggregate initialization turn: {step}` 占位串，`timeout_secs` 为 1；三个 provider step 虽有 gateway、root target 和空 writable roots 的外形，但尚无真实四命令执行与配置生成链。`AggregateAssetPublisher::publish` 只把路径追加到内存 `Mutex<Vec<String>>`，没有把正文持久化到聚合根。详见 `src/product/logical_codebase/coordinator_provider_turn.inc.rs` 的 `streaming_input`、`AggregateAssetPublisher::publish`。

聚合初始化已有可保留的五步 durable 状态骨架：`machine_skills → aggregate_preflight → pre_check → rule_and_mcp_config → openspec_and_examples`。前三个 provider 行为现以三个占位 turn 代表；单仓 `ClaudeRepositoryInitializer::initialize` 则遍历初始化步骤并对每个有命令的步骤单独启动 provider turn。两者不应继续以占位 prompt 混淆为相同 recipe。详见 `src/product/logical_codebase/aggregate_initialization.rs::AggregateInitializationStepKind` 与 `src/product/repository_store/initializer.rs::ClaudeRepositoryInitializer::initialize`。

### 1.2 新 LC 的 admission 死锁

当前 `LogicalCodebaseProviderAdmissionPreflight::check` 在任一 provider spawn 前，逐个检查 active member main checkout 的 `.claude/rules/language.md`。初始化自己的聚合 provider turn 也先经过这个检查；新 LC 尚未有成员规则时，provider 被挡在初始化之前，永远无法生成规则。单仓初始化走 RepositoryInitializer 的专用通道，不经过 LC admission，因此没有同一死锁。来源：`src/product/logical_codebase/provider_admission_preflight.rs::check`、`src/product/logical_codebase/coordinator_provider_turn.inc.rs::GatewayBackedAggregateProviderTurnDriver::run_turn`、`src/product/repository_store/initializer.rs::ClaudeRepositoryInitializer::initialize`。

### 1.3 已写契约与未落地差异

- `non-interrupt-repository-bootstrap` 的 REQ-BOOT-01 已规定：LC 四条无中断命令在聚合根执行一次，单仓保持原契约；目前聚合 provider turn 仍是空壳。
- `logical-codebase-registration` 的 REQ-REG-09 已规定聚合根 canonical、非 Git、成员路径在根下且拦截根冲突；本方案沿用，不改其准入语义，也不写成员仓。
- `session-policy-envelope` 已规定只读 action 无 writable root、coding action 的唯一 writable root 等于 target worktree；本方案保留该授权约束，补充“provider cwd 可与 target 不同”的冻结与复验语义。
现有 `AggregatePolicyArtifact` 有 identity/revision/digest 结构，但 `BOOTSTRAP_POLICY_TEXT` 仍是最小占位正文。recipe 启动前必须先有明确、最小权限的临时策略，只授权当前初始化 operation 的 bootstrap action；四命令生成根规则后，再发布可供普通 LC 会话使用的最终策略版本及其 rule reference。策略正文 digest 与根规则文件 digest 是两个摘要，以 receipt 关联，不要求字节相同；任一事实缺失或漂移均不得进入 Ready。

## 2. Root-CWD 模型总设计

### 2.1 三步用户模型

1. **recipe 在 LC 聚合根执行一次。** LC 根准入（REQ-REG-09）先确定并冻结 canonical 根；随后完成所选 Codex/Kimi 的独立 root trust 硬前置登记，通过后才启动固定由 Claude Code 执行的既有五步 recipe，并复用单仓 RepositoryInitializer 的四命令执行循环，在 canonical 聚合根执行四条命令。聚合根是非 Git 目录，不进入单仓注册/持久化/GitFinalize 外层流程。
2. **成员仓挂在聚合根下。** 成员身份、main checkout 与独立 Git 边界沿用 REQ-REG-09 和既有 manifest/checkout；recipe 不复制规则、不向成员仓写文件、不要求每仓再跑一遍初始化。
3. **后续 LC provider session 均从聚合根启动。** Story、Design、Plan、Coding 及其 review/revision/split 子会话的 cwd/target 合同在本 change 中冻结并由现有 gateway/证据覆盖；Codex/Pi/KimiCode 的 LC gateway 实际接入由后续 `lc-gateway-multi-provider` change 交付，本 change 不新增其 gateway dialect 或 fallback。根上的 rules/MCP/skills/tools 由 provider 自身目录发现加载，不新增 Aria prompt 注入、环境变量注入、逐仓复制或同步通道。非 LC 单仓所有 builder 与 cwd 保持当前行为。

### 2.2 Root 身份与双工厂一致性

本方案的唯一 LC root identity 是 manifest 的 `provider_context_root` canonical path。它必须在登记 preflight、aggregate initialization preflight、`LogicalCodebaseGatewayFactory::build_for_lc`、workspace/coding gateway 构造和 recipe provider input 中保持同一 canonical 值。当前存在两条工厂路径：`src/web/gateway_factory.rs:64-131` 为 workspace/coding 构造 gateway 并将 `authority_root=manifest.provider_context_root`；`src/web/handlers/aggregate_initialization/production_dependencies.inc.rs:44-105` 为 aggregate provider driver 调 `build_for_lc`，其 provider cwd 来自 `AggregatePreflightSnapshot.aggregate_root`。Phase 1 必须增加 cross-factory root assertion：两者 canonicalize 后不一致时 fail-closed，不能让 recipe 写入一个根而规划/编码从另一个根发现配置。

`aggregate_root`、`authority_root`、envelope `working_directory` 和 root recipe receipt 的 `canonical_root` 是同一身份的不同字段投影；receipt 记录它们的 canonical equality 证明。路径字符串相同不是充分条件，必须实际 canonicalize 并复验 symlink/路径存在性。非 LC 单仓不进入该断言和分流。

### 2.3 Provider 启动目录与授权根矩阵

### 2.4 cwd-target-resume 统一合同

本方案选择“launch 层按 envelope 重绑”，不要求每个已有 builder 同时完成参数重构：

1. `LogicalPlanLaunch`、`gateway_start.rs:53-91`、`WorkspaceEngine::logical_planning_launch`、plan review builders、coding `resolve_launch_policy_for_role` 与 split `prepare_sync_launch` 各自生成独立 `working_directory` 与 `PolicyTarget`/`worktree_path`。LC cwd 冻结为 root，target 来自 member/checkout/attempt snapshot；单仓两字段映射旧目录。
2. 扩展 `SessionLaunchRequest`、`SessionPolicyEnvelope`、`ValidatedSessionLaunchPolicy`、`ValidatedStreamingProviderInput`/`ValidatedAdapterInput` 和 `AdapterInput`：新增 canonical `working_directory`，`worktree_path` 仅保留 target；`SessionResumeFingerprint::from_envelope` 将 cwd 纳入 digest，resume request 必须携带同一 cwd。
3. `provider_stream/launch.rs:13-45` 采用 launch-layer rebind：validated+logical gateway 同时存在时，按 validated envelope 的冻结 cwd 重绑 provider input，再调用 gateway；Legacy 直接 `provider.start` 不重绑。sync gateway 以 envelope cwd 装配/复验 input，仍以 worktree_path 做 target 解析。
4. `validate`/`revalidate_before_spawn` 的顺序保持并拆开：policy revision/digest → capability → resume evidence → `config_artifact_ref` digest → 独立 canonical cwd 与 envelope.working_directory 一致且位于 authority root 允许范围 → `ProductionPolicyTargetResolver` 重解析 target、checkout git-dir/worktree 身份 → availability。删除 `canonical_cwd == envelope.target.worktree` 强制等式，不删除 cwd 权威校验；target/git-dir 校验原样保留。
5. `writable_roots` 是逻辑路由门，不是实际 OS 沙箱：Coder envelope 仍要求单一 target worktree，review/plan/author 仍空写根；实际 provider 边界由 provider-specific evidence gate、cross-target baseline、工具策略和前后变更审计证明。

## 3. 死锁解法：根规则与 bootstrapping phase

### 3.1 正常 admission 改查根规则

将 `LogicalCodebaseProviderAdmissionPreflight::check` 的规则来源从“遍历每个 active member checkout”改为 authority resolver 给出的 canonical LC 根下的根规则（至少 `.claude/rules/language.md`）。不再将成员 checkout 的 `language.md` 缺失当成所有 LC session 的 admission 阻断条件。单仓 admission/规则读取不改。

admission 同时校验 LC 身份/manifest、有效 policy artifact、config reference 和 gateway capability；改规则来源不等于绕过 gateway、安全能力或 target 校验。根规则的内容摘要与 rule reference 必须一致；任何缺失、路径越界、symlink 逃逸或 digest 漂移继续 fail-closed。

### 3.2 Admission phase 凭据数据流

扩展 `check(&SessionLaunchRequest, &ProviderAdmissionPhase)`，显式区分 `Normal` 和 `AggregateBootstrap(BootstrapPhaseCredential)`；凭据为内部不透明类型，拟含 project_id、lc_id、operation_id、当前 aggregate step、input_digest 和 canonical root，不能由 UI/普通 session 自报。普通调用方必须传 Normal。

数据流：`AggregateInitializationCoordinator`/`coordinator_lifecycle.inc.rs` 在 `mark_step_running` 成功后读取 `AggregateInitializationOperationStore` 的 durable Running/current_step/input_digest → 内部构造 phase credential → 扩展 `AggregateProviderTurnDriver::run_turn` 参数传给 `GatewayFactoryProviderTurnDriver`（`production_dependencies.inc.rs`）→ factory 与 root assertion → concrete driver → admission.check(request, phase) → gateway validate/start。admission 在 spawn 前重新读取 scoped operation：Completed/Failed/Cancelled、错误 step/input_digest、LC/root 不同或凭据不在当前 provider step 时拒绝。不新增第二套 durable operation。

Bootstrap 仅豁免“根规则尚未生成”这一项，仍校验 manifest/authority、临时 bootstrap policy、aggregate-root write action、capability、availability、canonical cwd/target。四命令完成并落盘有效根 rule reference/receipt 后，普通 Normal admission 要求最终 policy+root rules；任何 aggregate target 都不能自动取得豁免。存量 LC 已冻结的 per-member rule digest 失效时，走 waiting → Prepare → root recipe → root 摘要重冻结，不静默切换，不做数据迁移；“现网无生产存量 LC”只能作为待确认假设。

### 3.3 两套独立五步状态机与 readiness 闭环

| 状态机 | 既有五步 | 本方案改动与不变项 |
|---|---|---|

## 4. 根 Recipe 步骤设计

### 4.1 四命令循环与五步 durable 状态映射

复用 `RepositoryInitializationStepKind::command()` 给出的四条既有命令及 `ClaudeRepositoryInitializer` 的逐命令启动/事件消费/超时/取消/错误摘要逻辑。命令按序、每条启动新的 provider turn，cwd 固定 canonical LC 根：

1. `/pre-check --no-interrupt --upgrade 用大陆镜像`
2. `/rule-config --no-interrupt`
3. `/mcp-configuration --no-interrupt`
4. `/project-rules-examples --no-interrupt`

保留 `AggregateInitializationStepKind::V1` 五个 step ID 与 durable 顺序；recipe 固定由 Claude Code 以原五步执行四个命令：`PreCheck` 执行命令 1，`RuleAndMcpConfig` 依次执行命令 2、3，`OpenspecAndExamples` 执行命令 4。recipe operation 启动前必须确认 LC 根准入后的独立 trust gate 已为所选 provider 全部完成；该 gate 不是 operation step，任一登记失败进入可重试 fail-closed 等待面，不创建/启动任何 recipe provider 命令。随后在 `PreCheck` 的真实 Claude Code provider turn 前仍须使用 bootstrap phase credential 完成根规则缺失例外的 spawn 前核验。任一命令失败即停止，不推进后续 aggregate step；保存真实 command index/summary 和步骤失败原因。step 只在其包含的命令全部成功并完成 root output publish 后标记 Completed。command loop 必须按显式 LC recipe scope 选择四条命令，不调用 Repository registration coordinator、单仓 operation store、成员 Repository 持久化或 GitFinalize。

这里复用的是四命令执行引擎及其取消、超时、输出截断和单命令语义，不是单仓登记的外层 lifecycle。单仓 recipe 命令字符串、cwd、operation 与 GitFinalize 行为必须保持零变化。

### 4.2 Pre-check 扫描半径与 profile 对齐

profile 事实来源为既有 `DeterministicRepositoryTypeDetector`、`RepositoryProfileDetector` 与 `resolve_aggregate_profile`：它们读取成员 main checkout 根，不递归、不执行 package scripts、不安装依赖、不越过 symlink；已有 profile 是 `JavaBackend`、`FrontendPnpmVite`、`Mixed`，未知类型 fail-closed。recipe 消费 aggregate preflight 冻结的 active member/main checkout 清单与 profile evidence，不从公共父目录盲目 `find`。

`pre_check` 的扫描上限固定为：canonical 聚合根自身的 root 配置输出，以及 manifest 中每个 active member 的 canonical main checkout/profile 路径；不扫描兄弟目录、未登记目录、worktree 子树、`.git`/`.aria`、构建产物或凭据。对后端/前端成员分别验证其已识别栈；`Mixed` 必须同时覆盖 Java 和 pnpm/Vite，不允许只用根目录的单一语言推断全 LC。凡需要 `git rev-parse` 的检测都在对应成员 main checkout 执行并校验其 Git 根，不得在非 Git 聚合根执行。成员 profile 探测沿用确定性 Cadence 代码，不把任意 provider 输出当 allowlist。

### 4.3 配置生成与发布边界

四条 recipe 命令由 provider 原生 CLI 在 canonical LC 根启动并生成根配置。根 `.claude/rules/language.md` 是 admission/readiness 的必需材料；MCP、skills 和 tools 使用其 provider 原生 project-level 路径和发现机制。执行期间不向每个 prompt 拼接根规则正文，不生成成员薄指针，也不将根配置复制/同步进任何成员仓。

`AggregateAssetPublisher::publish/published_paths` 当前仅在 `coordinator_tests.inc.rs` 被测试引用，生产 coordinator 未调用；实现只是内存 `Vec<String>`，没有 root 绑定、realpath/symlink 校验、文件写入、receipt 或 snapshot。因此这里不是“升级现有生产发布器”，而是新增生产 root recipe receipt store + filesystem auditor，并在 production coordinator/provider turn 中接线：校验 canonical root、允许路径、前后变更集、symlink/越界和用户冲突；持久化 command/step、canonical root、产物摘要、policy/rule identity、快照和未知变更证据。`.aria/aggregate/**` 仍是 Aria-owned 发布区；provider-native 根配置 allowlist 必须由真实 CLI 实测冻结。不可观测写入或成员工作树变化时 fail-closed，不自动覆盖/删除/回滚用户文件。

REQ-REG-09 检出的用户已有 CLAUDE.md/AGENTS.md/`.aria` 冲突不得被 recipe 覆盖；成员目录、成员 Git metadata、worktree 与绝对/父路径不得列入允许输出路径。预研 §1–§4 证明 fixture 中根级 AGENTS.md/CLAUDE.md、`.claude/rules`、`.mcp.json`、`.codex/config.toml` 能被发现，但不证明四条 recipe 命令的全部落盘路径；provider-native 根文件 allowlist 必须结合 recipe 输出与版本化 CLI 证据逐项冻结，不可凭 fixture 或推测扩大。pre/post 变更快照用 canonical 相对路径记录，不把根目录整体授权误称为精确 OS sandbox。

### 4.4 GitFinalize

聚合根不是 Git 仓，不执行、不模拟、不映射单仓 GitFinalize；不调用成员 Git add/commit/push，不改变任何成员主 checkout。单仓 registration 的 GitFinalize 原样保留。`profile_preflight_commands` 中面向成员的 git 探测只允许以已验证 member root 为 cwd，不能因此被误认为 aggregate GitFinalize。

### 6.1 Digest 不可混用

`AggregatePolicyArtifact::compute_digest` 实际对 `policy_text` 原始 UTF-8 bytes 计算 SHA-256（`policy.rs:88-90`）。bootstrap 完成后的 `policy_text` 必须是真实、可供 policy reader 解析的聚合政策正文；policy digest 与根 `language.md` readiness/content digest 分开，以 receipt 关联，不要求数值相同。

G1 的 managed skills link 与 provider-native root skills 是两条不同通道：`CadenceSkillsPaths::from_home` 固定 `~/.agents/Cadence-skills`（source repository）、其 `cadence-init/skills`（source）、`~/.agents/skills`（shared）、`~/.codex/skills/skills`（Codex）、`~/.claude/skills`（Claude）。`ManagedSkillLinkSynchronizer` 维护后三个 managed link layer，cwd 无关；recipe 不把同一平台技能再复制/链接到 LC root，root-native skills 只承载 LC 自有技能。实测以技能来源 realpath/name 去重，确认 provider 未重复加载后才给出成本结论。

根 MCP/settings/skills 等 provider-native 文件的 receipt digest 与 policy digest 分开记录；不声称现有 Aria config digest 代表 provider 自发现文件正文。`SessionPolicyEnvelope.config_digest` 当前按 `config_artifact_ref` 字符串计算，不等于根文件摘要。

G3：REQ-ENV-07 薄指针在本模型中不作为缺根规则 fallback；本 proposal 不发布新成员薄指针，但保留既有受控 pointer publication 通道及其 spec 状态，不 supersede/删除该通道。root-cwd 直接依靠 root policy/rules；pointer 缺失仍按既有策略阻断或标记。

G4：REQ-BOOT-01 中“逐仓本地化由确定性程序完成”以及既有 D4“必要确定性本地化”半句由本 root-cwd proposal supersede：统一在 LC root 执行 provider recipe，成员不再逐仓执行/写配置；理由是 root cwd 原生发现与单一事实源，成员 Git side effect 由 D4 baseline/evidence gate 取代。单仓 REQ-BOOT-01 场景不变。

G5：存量 LC 若存在旧 per-member digest，在全局切 root 后不得静默迁移；进入 waiting → Prepare → root recipe → 新 root policy/rule receipt 冻结。无生产存量 LC 仅为待验证假设，不改变 fail-closed 机制。

### 6.2 Provider 信任登记（recipe 前置独立步骤）

预研报告证明 Codex 与 Kimi 在非 Git、多成员根下的 MCP 真实调用依赖 workspace trust；因此在 LC 根准入（REQ-REG-09）确定并冻结 canonical root 后、Claude Code root recipe 启动前，必须完成本次所选 provider 的独立信任登记与核验。该登记是 recipe 的硬前置门，不属于 `MachineSkills → AggregatePreflight → PreCheck → RuleAndMcpConfig → OpenspecAndExamples` 五步，不插入步骤之间，也不新增第六个 durable step；任一登记失败时五步 recipe 不创建/不启动，初始化进入可重试 fail-closed waiting，不能降级或部分放行。登记的跨工作区副作用与等待/重试事实由关联 lifecycle 记录；普通 Codex/Kimi session 启动前继续复验。登记对象始终是 manifest `provider_context_root` 的 canonical path，禁止以成员路径、父目录或字符串别名替代，也不由模型 prompt 或用户临时输入完成。

- **codex**：在用户级 `~/.codex/config.toml` 的 `[projects."<canonical_lc_root>"]` 节登记 `trust_level = "trusted"`；LC root 启动时追加 `--skip-git-repo-check`。`-c` 命令行覆盖不作为 trust 登记替代。
- **kimi**：在 `~/.kimi-code/workspace-trust/wd_<basename>_<sha256(canonical_root)[:12]>` 写入 `{"root":"<canonical_lc_root>","trustedAt":<ms>}`，key 计算与预研报告记录的 `encodeWorkDirKey` 形态一致。
- **pi/Claude Code**：不新增用户级 trust 写入；沿用 provider 原生 root discovery 与既有 adapter/capability 检查。

信任登记必须满足：只登记当前 LC 根；重复执行幂等且不覆盖其他项目条目。写入前检查 root 对应 key 是否存在且是否被其他 LC/用户拥有：用户已有可信条目原样复用并审计为非本 LC 所有，若未信任但条目存在则进入待确认面，不覆盖用户值；LC 删除或解绑时仅撤销有登记归属证明、值仍匹配本 LC 最后写入摘要的条目，遇外部修改或归属冲突 fail-closed 等待，不误删用户或其他 LC 的 trust。登记属于跨工作区副作用，审计记录至少包含 `operation_id`、`lc_id`、provider、canonical root、登记动作（register/revoke）、配置文件/记录 key、前后摘要、时间、结果、登记归属与错误摘要；不得记录无关 trust 条目或敏感凭据。写入任一失败进入 fail-closed 等待面，不启动 recipe 或降级 session；登记成功不等于 provider 写权限已证明，后者仍由 §7 evidence gate 验收。
 
### 6.3 根指令入口与 skills 安装边界
根级通用入口以 `AGENTS.md` 为主，`CLAUDE.md` 作为 Claude Code 兼容副本；recipe rule-config 已生成两者，实施只需核实其一致性，不新增第三套入口。预研报告中四家 provider 均通过该入口读取 `.claude/rules` 并完成真实 MCP 调用。

## 9. 非目标与开放问题

### 9.1 非目标

- C6（LC 注册撞 legacy 身份）只影响存量 legacy 项目，按用户裁决 defer。
- 不改变传统单仓 recipe、prompt、cwd、GitFinalize 或 operation；不把单仓升级为 LC，也不做双读双写迁移。
- 不发布成员仓 thin pointer，不向成员仓复制/生成根配置，不执行成员 Git 写操作。
- 不实现 MCP/settings/rules 的 Aria 主动注入通道；不通过 prompt、环境变量、adapter sidecar 或运行时复制来模拟目录发现。

### 9.2 开放问题（不重开已锁定模型）

1. **多版本 provider-native 根配置与规则发现**：预研报告 §1–§4 已在单版本、非 Git、多成员根下验证 pi/Claude/Codex/Kimi 的根 `AGENTS.md`/`.claude/rules` 与 MCP 真实调用；祖先 Git 污染仅有部分观察，其他 CLI 版本及具体 root recipe 输出路径未验证。版本化支持矩阵与 §4.3 allowlist 须由实施期证据冻结；不重新讨论 cwd 是否统一到 root。
2. **Recipe 输出路径最终 allowlist**：已有 REQ-REG-09 对根冲突有拒绝要求，但本次材料没有给出每条 recipe 命令在各 provider 版本下的完整落盘路径清单；需由真实 CLI 实测冻结后纳入 D2 allowlist，不得在实现中临时放宽为任意根路径。
3. **大型 LC 的 provider 原生发现成本**：根配置不复制不注入，但 CLI 可能因成员目录层级、规则祖先扫描或 MCP 扫描产生重复成本；须以 §7 数据决定限额/阻断条件，不用未经测量的 token 估计替代。
4. **LC 根与 authority root 的路径等价**：实现须证明用于 cwd、rule publisher 与 manifest 的 canonical 根是同一身份；如现有 manifest/provider_context_root 与用户选择的 aggregate root 存在别名路径，必须通过 canonical identity 解决，不能靠字符串路径相等猜测。

以上问题均为实现前验证项；它们不授权改为成员 cwd、注入、复制或修改单仓行为。

- 聚合格式冻结为:`# 聚合政策\n\n` 起头,每个来源依次追加

  示例模板不进入正文;symlink 来源、非普通入口、空/纯白入口、非法
  UTF-8 一律 fail-closed。

### A.2 scope 与 UUID 分离

- LC root identity 取 manifest `provider_context_root` 的 canonical
  path,发布前核验 manifest、operation `input.provider_context_root`
  与参数三方一致;产品 LC record id(`for_lc` scope)只决定 store 数据
  子树,manifest `logical_codebase_id: Uuid` 才进入政策身份与
  `policy_id = policy/{project_id}/{manifest UUID}/{revision}`,两者不
  混用。
- 发布前置状态核验不放宽:operation 必须同 scope/project、`Running`
  且 `current_step = OpenspecAndExamples`。

### A.3 双摘要

- `policy_digest` = 聚合完整正文原字节 SHA-256(`sha256:<小写十六进制>`),
  同时钉在 artifact、locator read-back 复验与最终 receipt 上;
- `rule_digest` 只取 `AGENTS.md` 原字节 SHA-256,与既有
  `root_recipe_receipt::root_rule_digest` 同语义,发布输出单独冻结,
  二者不要求相等。发布输出(`sources`)逐来源记录相对路径与原字节
  摘要,不重复保存正文。

### A.4 不可变输出与发布顺序

- operation-owned 不可变输出固定在
  `<lc_scope_root>/aggregate-initializations/{operation_id}/policy-publication.json`,
  不放会被 cancel/recover 删除的 `staging/`;它冻结候选 revision、
  base 引用、来源摘要、rule digest 与发布时间(`artifact.created_at`
  兼作稳定发布/finalize 时间)。
- 发布顺序固定:不可变输出 → 根下 `canonical_root.join(policy_id)`
  精确 locator 原子 no-clobber 发布(临时文件 fsync 后 `hard_link`,
  目标已存在仅复验同字节)→ read-back 字节/SHA 复验 → current
  artifact durable 替换(唯一允许覆盖式 rename 的位置)。
- save、`ensure_bootstrap` 与发布共用同 scope `.aggregate-policy.lock`,
  内部保存函数不重入取锁;revision 先 `checked_add(1)` 拒绝溢出。

### A.5 恢复边界

- 同 operation 重入:复用不可变候选与首次冻结时间,只补齐未完成的
  locator/read-back/current 步骤,不重复涨 revision;来源字节/清单、
  operation/root/scope/UUID/base 引用任一漂移即冲突停等,不重新生成
  候选、不覆盖 current。
- 实际新 operation 即使正文不变也发布 `revision + 1` 与新 locator,
  旧 locator、旧输出与旧 receipt 保留不覆盖。
- 持久化三阶段(输出/locator/current)故障注入仅存在于 `cfg(test)`,
  生产无任何旁路开关。

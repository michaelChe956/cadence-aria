# 技术方案: Reviewer 能力全开与对账作废(v3.1-B 红队修订版)

- 出具: 测试会话基于 v3.0 裁剪，owner 于 2026-10-17 拍板 B 档；**设计完成未实施**
- 定位: 替代 v3.0 的 A 档（独立 UID 物理铁律 55-70h）——B 档=软铁律+对账作废，约 25-30h
- 复用声明: 快照/窗口/提交通道守卫/启动补偿/纪律改法/group 覆盖的细节沿用 v3.0 对应章节；本文件记录 B 档裁剪决策及红队实施级补全
***

## 一、B 档哲学

挡君子（prompt 纪律）+抓小人（对账发现违规即作废整轮审查+恢复现场）。不阻止恶意写入的发生；在平台记录未被篡改、资源归属可判定且恢复材料完整的前提下，违规结果不进交付、可被发现并恢复。覆盖已发生过的真实事故（构建残留/误提交/崩溃残留），放弃对「恶意 reviewer」的物理防御（单机自用+自有仓库场景，owner 知情接受）。
***

## 二、一场审查的生命周期（B 档冻结时序）

审查窗口必须按以下不可换序的受信步骤推进；任何步骤失败都进入 `RecoveryRequired`，不得把污染态重冻为下一轮基线：

1. **加锁并停 writer**：创建 durable 窗口租约，锁定平台 stage/commit/push/journal 补偿及同一工作树上的其他写入者；停止并确认同树 Coder、平台 Git mutation、登记的子进程/容器没有在途 writer。锁定失败或存在未知 writer 时停等。
2. **持久化基线**：在锁保持期间采集 worktree 全目录项（含 ignored，记录内容/类型/权限/symlink）、`.git`/`.aria` 状态摘要、运行资源归属与窗口身份，并将 manifest、恢复游标和 journal 原子持久化到平台数据目录。基线持久化成功前不得采材料。
3. **采材料**：只从已持久化基线派生报告上下文、证据入口和受信 profile；报告先标记为 `PendingAcceptance`。材料采集不改变基线，也不得释放 writer 锁。
4. **执行**：Reviewer 使用 `ReviewerVerify` 在 HostLocal 白名单环境中运行，能力全开；平台仍拒绝交付推进和 Git mutation。所有进程、MCP、ACP terminal、容器、网络和临时目录先登记后启动。
5. **Quiescing 与违规落盘**：结束、取消、超时或崩溃收口时先停止/回收所有已登记 writer。对账发现的 `.git`、`.aria`、worktree 或平台通道违规，必须在恢复前把事实、路径、摘要、时间、window/attempt、恢复游标和报告绑定关系追加并持久化到违规 journal；恢复不能清除这份事实。
6. **恢复与终核**：按基线恢复 worktree，清理本轮私有运行资源，再核对三域（见下）及恢复完整性。恢复成功只表示现场回到基线，不表示报告可采信。
7. **裁决**：仅当恢复完整、三域均通过、平台记录未被篡改且没有违规事实时将报告标为 `Accepted`；任一违规、未知 writer、快照不完整、恢复失败或 journal 不一致均为 `Invalidated`，进入人工门。任何违规轮恢复成功后必须开**新审查轮**，新轮重新加锁、持久化基线和采材料，不得沿用旧报告或旧基线。

三域分别定义为：

- **worktree 恢复域**：受管 worktree、其 linked-worktree 指针及本轮登记的运行目录；恢复只针对基线差异，保留基线已有的 Coder dirty/staged/unstaged/untracked/ignored 状态。
- **Git 观察域**：`.git` 入口、真实 gitdir/common-dir、HEAD/index/refs/objects/reflog/config 及子模块 gitdir；只允许平台受信观察与恢复，任何 reviewer 写入都算违规。
- **平台合法写入域**：预枚举的报告、role-run、窗口状态和恢复 journal 路径；平台受信写入不等于 reviewer 合法写入，白名单外变化仍使本轮作废。

崩溃补偿必须早于任何新材料采集：启动时读取未关闭窗口，停旧资源，按原 manifest 续恢复，先持久化期间发现的违规事实，再恢复；恢复完成且人工门关闭前不得启动新的 provider。不得依赖 Drop，也不得将当前污染态重冻为基线。

## 五、违规后人工门状态机

违规轮不得直接回到 `Closed`，也不得因恢复成功自动转为可采信。状态转移冻结如下：

`Running → Quiescing → ViolationRecorded → Restoring → ManualGate → (ClosedInvalidated | NewReviewRequired)`

| 状态 | 进入条件 | 离开条件与锁要求 |
|---|---|---|
| `Quiescing` | 正常结束、取消、超时、崩溃 | 先停已登记 writer/子进程/容器；通道锁保持，禁止新 provider 和新材料 |
| `ViolationRecorded` | 发现 `.git`、`.aria`、worktree 或平台通道违规 | 违规事实已持久化 journal，包含路径、摘要、时间、window/attempt、报告绑定和恢复游标；未落盘不得恢复 |
| `Restoring` | journal 已落盘且资源已 quiesce | 以原基线恢复并核验三域；锁保持至恢复核验结束，禁止把当前态重冻基线 |
| `ManualGate` | 恢复成功或恢复异常均进入 | 人工查看违规事实、恢复差异、外部副作用和报告；恢复成功不等于可采信 |
| `ClosedInvalidated` | 人工拒绝采信或恢复异常已处理 | 关闭旧轮，保留 journal/证据；平台锁可释放，但不释放新的 reviewer 资格 |
| `NewReviewRequired` | 人工授权重新审查 | 旧轮报告永久 `Invalidated`；重新获取窗口租约、持久化新基线和采材料后才可执行新轮 |

人工授权只允许选择「作废并关闭」或「作废后开启新审查轮」，不能把违规报告改成 Accepted，也不能把污染态当新基线。若人工拒绝补偿处理，保留窗口锁和 `RecoveryRequired`，记录拒绝原因；只有补偿动作成功、journal 恢复游标持久化且三域复核通过，才可进入 `ManualGate` 再次裁决。锁保持到 `ClosedInvalidated` 或 `NewReviewRequired` 的新轮已完成重新加锁；禁止在人工门期间由 Coder 或 reviewer 写入同一工作树。

## 六、B 档环境构造与 HOME/缓存清理边界

Reviewer 环境由受信 launcher 构造并登记 `window_id/attempt_id/run_id`：`env_clear` 后仅注入固定白名单变量、工具链变量、HostLocal `HOME`、`XDG_*`、`TMPDIR`、短期证据 token 和经配置批准的包仓库/容器连接变量。环境是能力兼容与意外注入控制，不是凭据隔离；不声称同 UID 下 owner 凭据不可达。

可清理目录必须在运行前创建、canonicalize、登记并绑定窗口，且只能位于本轮私有运行根：`private_home/`、`private_xdg/`、`private_tmp/`、`private_cache/`、provider runtime、登记的容器存储/网络临时目录。退出时只清单中仍归属该 `window_id/run_id` 的目录和资源，先 quiesce 再清理；PID 复用、租约未知、canonical 路径漂移或 detached 未登记资源一律停等并人工处理。

**禁止**按 `HOME`、`XDG_CONFIG_HOME`、`XDG_CACHE_HOME`、`TMPDIR` 等变量的值递归删除；禁止 `rm -rf "$HOME"`、`git clean`、整树 `reset` 或按目录名猜测归属。owner 真实 HOME、既有共享缓存、Coder dirty/commit、非本轮容器和不明归属目录均不在自动清理范围。

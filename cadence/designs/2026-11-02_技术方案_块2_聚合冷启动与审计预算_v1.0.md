## 1. 问题与根因

### 1.1 B-1：provider 被三重写死

| 位置 | 内容 |
|---|---|
`src/web/handlers/aggregate_initialization/handlers.inc.rs:98` | `provider: "claude_code".to_string()` 写进 operation input |
`src/product/logical_codebase/coordinator_provider_turn.inc.rs:44-56` | 硬构造 `ProviderRef::claude_code(...)`（**真正决定 provider 的地方**） |
`src/web/handlers/aggregate_initialization/handlers.inc.rs:612` | trust 门准入清单 `&[ProviderName::ClaudeCode]` |

**关键事实**：`input.provider` 字段**全仓唯一读者是测试断言**（`aggregate_initialization_store_tests.inc.rs:315`）→ 它只是记账字段，执行链路无人读。

**现场**：`provider command not found: claude` → 预检 denied，即使该机装了 pi/kimi/codex 也一次都不试。

**另一层发现**：`GatewayFactoryProviderTurnDriver` 是 **state 级单例**（`production_dependencies.inc.rs:872-876`），`for_lc` 不派生它 → **provider 不能放 driver 字段**（会跨 LC 串味），必须走 request。

### 1.2 B-2：能力三态在错误出口被压平

`src/cross_cutting/provider_capabilities.rs:12-24` 是三态（`Confirmed` / `Denied { reason }` / `Unknown`），但 `production_policy_resolvers.rs:301-318` 只放行 `Confirmed`，其余走同一格式串：

```rust
other => Err(ProviderGatewayError::UnsupportedCapability(format!(
    "{PROVIDER_CAPABILITY_LAUNCH_NOT_CONFIRMED}: {action:?} launch cell is {other:?}"
))),
```

`Denied` 的真实 reason 被塞进 Debug 括号，`Unknown` 也走这一句 → **用户无法分辨「没核验」与「真的不行」**。

现场：`provider_capability_launch_not_confirmed: PlanningReadOnly launch cell is Unknown`。

### 1.3 B-3：`no stderr summary` 是投影层单点缺陷

三层叠加：

| 层 | 位置 | 问题 |
|---|---|---|
执行层 | `coordinator_provider_turn.inc.rs:267-374` 的 `consume_turn` | 11 条失败分支里 **6 条把已捕获的输出直接丢弃**（status failed / aborted / permission timeout / stream closed / cancelled / timed out） |

**投影层** | `bootstrap_projector.inc.rs:344` 与 `:586` | **只读 `stderr_summary`，从不读 `action`** —— 而 `action` 里本来就带着真原因 |

**⇒ 改投影层就能立刻消灭 `no stderr summary`**，不必等结构改造。

**顺带纠正记录里的归因偏差**：`machine_skills` 是**确定性代码、不跑 provider**（`coordinator_lifecycle.inc.rs:335` → `AggregateSkillsPreparation::prepare_skills`），所以「provider 未登录」不可能是它的失败原因。

## 2. 方案边界

### 2.1 架构边界原则

1. **provider 选择在 begin 之前完成并冻结** —— provider 一旦选定，全程只用一个（中途换人会让聚合产物割裂）
2. **选择器不新造判定** —— 与 gateway **共用同一个能力判定函数**，准入不放宽一个字节
3. **能力核验不被自动触发** —— `provider_capability_revalidate.rs:1-10` 的契约明写「不点击不运行任何探针」；自动触发会阻塞分钟级且与该契约直接冲突
4. **失败面单一来源** —— 新增 `failure_copy.rs`，投影层 / DTO / 通知一律走它
5. **审计的 purpose 是「证明 recipe 没乱写」** —— 不是「给用户既有体量设上限」
6. **预算口径 = 本次变更量** —— 存量体量不该压垮预检

### 2.2 与既有契约的关系

| 既有契约 | 关系 |
|---|---|
`non-interrupt-repository-bootstrap`（四命令 + 失败面字段） | **MODIFIED**：失败面字段化、文案单一来源、codegraph 前置探测、同根因只报一次 |
`logical-codebase-aggregate-index` spec:99 | **MODIFIED**：明确「无 LKG + 工具缺失 → `codegraph_missing` 致命且在前置探测阶段阻断；有 LKG 的 rebuild/sync 才走 Degraded」 |
`provider-capability-revalidation`（不点击不运行探针） | **保持不变** |
`logical-codebase-registration`（预检 / 登记） | **保持不变**（主体已落地）；只补残项 R2 的 `details.reason` 口径 |
自动重写 / 人工返修账本 | **不涉及**（属块1） |

## 3. 核心改动

### 3.1 B-1：provider 候选选择

#### 3.1.1 选择器模块

**新建** `src/product/logical_codebase/provider_selection.rs`：

```rust
/// owner 2026-11-02 裁定：按序探测，选第一个可用的，全程只用一个 provider。
pub const AGGREGATE_PROVIDER_CANDIDATE_ORDER: [ProviderName; 4] = [
    ProviderName::Pi,
    ProviderName::KimiCode,
    ProviderName::ClaudeCode,
    ProviderName::Codex,
];
```

**判定动作**：只判 `SessionPolicyAction::PlanningReadOnly` —— 这是聚合 driver 唯一使用的 action（`coordinator_provider_turn.inc.rs:120`）。

**两层判据**：

| 层 | 判什么 | 数据来源 | 不通过时 |
|---|---|---|---|
**L1** 命令可用 | 该 provider CLI 在本机可用 | `ProviderHealthSnapshot.entry(&p)` 的 `available` + `reason_code` 六值（`provider_health.rs:29-46`） | `CliMissing{code, reason}` |
**L2** 本 LC 能力已核验 | 该 LC 的 `PlanningReadOnly.launch == Confirmed`，且 `capability_snapshot_ref` 与运行时约定一致 | `ProviderCapabilityStore::for_lc(paths, lc_id).get(project_id, ref_type)` + `row.action_matrix.row(&PlanningReadOnly).launch`（`provider_capability_store.rs:274-296`） | `Unverified` / `Denied{reason}` / `EvidenceStale` |

#### 3.1.2 L2 与 gateway 的同源条款（本方案最容易做错的地方）

选择器**不新造判定**，而是**逐字复刻** `production_policy_resolvers.rs:277-318` 的三条，并把它们抽到 `provider_capability_store.rs` 的一个只读方法上，让 gateway 与选择器**共用同一函数**：

```rust
pub enum LaunchCellState {
    Confirmed,
    Unverified { detail: String },          // 记录缺失 / cell=Unknown
    Denied { reason: String },              // cell=Denied{reason}
    EvidenceStale { detail: String },       // snapshot ref 漂移
}
impl ProviderCapabilityStore {
    pub fn launch_cell_state(&self, project_id: &str, provider: ProviderRefType,
                             action: SessionPolicyAction) -> Result<LaunchCellState, ProductStoreError>;
}
```

`require_supported`（`:307-318`）改调它并保留原有错误前缀与文字形态。

**⇒ 准入不放宽一个字节**：选择器只是提前把 gateway 会拒绝的理由读出来，gateway 仍然自己 fail-closed。

#### 3.1.3 L1 的方案权衡

| 方案 | 做法 | 成本 | 缺点 | 结论 |
|---|---|---|---|---|
L1-a 读快照 | 读 `latest_diagnostic()` 的逐家 `available`（`provider_health.rs:183-232` 已并发探完四家） | 零 spawn、毫秒级 | 快照可能过期（启动刷一次，之后只有 `/api/providers/recheck` 才更新） | 主路径 |
L1-b 每次现场刷新 | 选择前必定 `refresh()`（4 家并发 × 5s 超时 → ≤5s 墙钟） | 最坏 ~5s 阻塞 HTTP | 违反 `start_lc_aggregate_initialization` 的「同步只做 durable 写 + spawn」契约 | 不采用 |
**L1-a+ 条件刷新** | 仅当 `generation == 0`（从未探过）/ `degraded()` / `checked_at` 早于 `now - 10min` 时 await 一次 `refresh()` | 新机器 ≤5s 一次，之后零延迟 | 需显式时间窗常量 | **采用** |

**`degraded()` 必须单独处理**：`provider_availability_gate.rs:107-112` 里 degraded 是一票否决（`provider health state is degraded`）。若无视 degraded 选了 pi，operation 会先创建、再在 spawn 前被 gate 拒成 `provider_unavailable: Pi: provider health state is degraded` → 用户看到一次莫名其妙的失败。

⇒ `degraded() == true` → **不创建 operation**，返回 `aggregate_initialization_provider_health_degraded`，属「重试即可 / 产品缺陷」档。

#### 3.1.4 新机器跑通路径（不放宽准入）

owner 裁定「聚合初始化在选 provider 时不应绕过 gateway 的 capability 准入门」。所以新机器上四家全 `Unknown` 时，**正确行为就是不启动**，并把「去点核验」变成主文案 + 一个按钮：

```
1. 点「聚合初始化」→ 选择器：L1 过（pi 装了），L2 = Unverified
   → 不创建 operation，返回 aggregate_initialization_provider_needs_verification
   → details 带：建议核验的 provider（按顺序第一家 L1 过的）、四家候选表、核验入口、预计时长
2. 前端渲染「核验 Pi」按钮（已有组件与 API：ProviderCapabilityCard.tsx:213-225、provider-capability.ts:48-59）
3. 点 → POST .../capability-revalidate {provider_type:"pi"} → 真实 probe 三 action
   → 导入 durable Confirmed，落盘 capability_snapshot_ref = "cap_managed_snapshot"
   （provider_boundary_probe.rs:1624-1639 已保证，注释点名这是 r47 pi/kimi 首轮 mismatch 的修复）
4. 点「重试」→ 选择器 L2 = Confirmed → 选 Pi → begin（provider 冻结为 pi）
   → 三个 turn 用 ProviderRef::pi("cap_managed_snapshot") 跑通
```

**为什么推荐「引导」而不是「自动触发核验」**：

| 方案 | 代价 | 判定 |
|---|---|---|
引导（推荐） | 用户两次点击；不花 provider 额度 | **采用** |
自动触发（同步） | operation 创建被阻塞分钟级（真实 probe 会启动 provider 跑 LLM 轮次）；与 `provider_capability_revalidate.rs:1-10` 的「不点击不运行任何探针」**直接冲突** → 必须改契约 | **不采用**，需 owner 明确批准 |
自动触发（异步） | 要给五步状态机加前置态；`aggregate_initialization.rs:161-169` 的状态机是 byte-stable durable 协议，改动风险高，且把「冷启动」变成「自动花额度」 | 不采用 |

#### 3.1.5 接线顺序（顺序本身是契约）

```
① 在 handlers.inc.rs:89 之后（dependencies 与 manifest 都在场）插入选择
② :98 → provider: selection.selected.clone()
③ :605-615 ensure_recipe_trust_ready 增参 selected: &ProviderName
   清单由 &[ProviderName::ClaudeCode] 改为 std::slice::from_ref(selected)
④ begin / begin_reinitialization 不变（input 里已带冻结的 provider）
```

**trust 语义后果**（已核实）：选 Pi / ClaudeCode → `requires_workspace_trust` 过滤后为空（`provider_trust.rs:923-926`）→ trust 门 no-op，与今天 Claude 行为等价，零回归；选 KimiCode / Codex → 触发 workspace trust 登记，未 trusted 返回既有 `aggregate_initialization_trust_waiting` 链路。

#### 3.1.6 driver 参数化：provider 走 request

**必须走 request 的证据**：driver 是 state 级单例（`production_dependencies.inc.rs:872-876`），`for_lc` 不派生它（`dependencies.inc.rs:64`）。若把 provider 放进 driver 字段，同一进程里两个 LC 会互相覆盖。

改动三处（闭环）：

1. `aggregate_initialization_coordinator.rs:276-300` → `AggregateProviderTurnRequest` 增 `provider: &'a ProviderName`
2. `coordinator_lifecycle.inc.rs:790` `run_provider_turn` → 从 durable 操作记录解出 provider 再传（`provider_from_wire(&operation.input.provider)?`，未知串 fail-closed）→ **「重试不换人」是结构性保证**
3. `coordinator_provider_turn.inc.rs:44-70` → 换成按 `ProviderName` 构造，**保留 admission 预检**：
   `with_provider(gateway, provider, ref)` 与 `with_provider_and_admission(gateway, provider, ref, paths)`
   用 `ProviderRef::from_provider_name`（`provider_gateway.rs:470-487`）—— 四家显式映射、Fake fail-closed、**无 `_ =>` 静默回退**
4. `production_dependencies.inc.rs:142-145` 与 `:189-192` → 改调新构造器
5. 旧 `claude_code` / `claude_code_with_admission` **删除**（clean cutover），迁移其调用点（含测试夹具）

**约 5 处「必须保持 Claude」的测试断言需重新评估**（改断言口径，不改语义）：`coordinator_tests_contract.inc.rs:107-110`、`coordinator_tests_profile_trust.inc.rs:637-641` → 改为断言「aggregate recipe provider == operation.input.provider」。

**过期注释必须顺手删**：`coordinator_provider_turn.inc.rs:41-43`（Codex 路由阻断）与 `provider_gateway.rs:467-469` —— 实现侧 `:1564-1569` 的 `enforce_route_policy` 已是 `Ok(())` 纯桩、`:1557-1561` 明说规则已退役、`:2961-2964` 说该判别码不再产生。不删的话下一个改这块的人会再次得出「aggregate 只能用 Claude」。

#### 3.5.4 K-3：预算口径改为「本次变更量」（C 方案）

**核心洞察**：预算爆的原因不是「文件多」，是「**读了太多字节**」—— 而读字节是为了算**内容哈希**（`content_digest`）。

**不哈希全部文件，只哈希「可能变了的文件」，就读得少了。**

```
现在：扫描第 1 遍（读内容算哈希）→ 扫描第 2 遍（读内容算哈希）→ 对比
改后：扫描第 1 遍（只记元数据：路径+大小+mtime，不读内容）
      扫描第 2 遍（只记元数据）
      → 对比两份元数据，找出「大小或 mtime 变了」的文件
      → 只对这些文件读内容算哈希 → 得出变更清单
```

**保留的能力**：仍然扫全仓两遍、仍然对比出所有变更 → **「recipe 写到 allowlist 之外」这个检测能力完整保留**（`classify_change` 的 `UnknownPath` 分类不依赖全量内容哈希）。

**为什么不用事件驱动（inotify）**：跨平台成本高（Windows 无等价机制）+ 可能漏事件（缓冲区溢出）→ 会让审计保证变弱。**元数据差分法无新依赖、无漏检风险。**

**预算语义随之改变**：从「快照总量」改为「实际变更文件的内容量」→ 64 MiB 甚至更小的上限都够。

#### 3.5.5 流式读（超大文件先读后计费）

**现状缺口**：`std::fs::read` 发生在 `charge_bytes` **之前** → 一个 4 GB 未忽略文件会**先吃 4 GB 内存**，然后才被预算拦下；40 GB 的文件会 OOM 崩溃（报的是崩溃，不是「超预算」）。

**改法**：改成**流式读**（分块读 + 边读边累加 + 边算哈希），超预算立刻停 → 内存峰值 = 块大小（64 KiB 级），不会 OOM。

**与 K-3 天然配套**：K-3 已经把「读什么」缩小到变更文件，流式读只是同一处的顺带改造。

#### 3.5.6 用户面文案（成品）

**审计预算超限（产品缺陷档）**：

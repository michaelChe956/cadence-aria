# 系统环节与角色标准（v1.0）

> **性质：标准基线。** 本文记录 owner 于 2026-10-22 确认的环节、角色与产出物划分，**自此作为沟通与设计的唯一口径**。后续沟通、设计、契约、实施一律以此为准；如需调整，由 owner 显式修订本文。
> 术语一律使用本文用词：环节 / 角色 / 产出物 / 真实仓库 / lc 仓 / 零锁恢复。不另造词。

## 一、环节清单

系统共 **5 个环节**：

1. issue 环节
2. story 环节
3. design 环节
4. work item 环节
5. coding 环节

## 二、各环节的角色与产出

### 1. issue 环节

- **无角色**：纯用户手工操作。
- **产出物**：用户期望实现的 issue，以及**用户选定的 lc 仓中的真实仓库**。

### 2. story 环节

- **author 角色**：产出 story spec。
- **reviewer 角色**：针对 story spec 进行审核，并给出修改意见。
- 用户可以按照自己的意愿进行 story spec 的定稿。

### 3. design 环节

- **author 角色**：产出 design spec。
- **reviewer 角色**：针对 design spec 进行审核，并给出修改意见。
- 用户可以按照自己的意愿进行 design spec 的定稿。

### 4. work item 环节

- **author 角色**：产出 work item plan。
- **reviewer 角色**：针对 work item plan 进行审核，并给出修改意见。
- 用户可以按照自己的意愿进行 work item plan 的定稿。
- **work item 与 story / design 的区别**：work item plan 会产出**多个 work items**；每个 work item 有**实施要求**和**真实仓库要求**（**只允许一个真实仓库**）。

### 5. coding 环节

- 根据 work item plan 进行拆分。work item plan 中会给出指导意见：部分并行、全并行、部分并行部分串行等。
- **一个 coder 只会开发一个真实仓库里的内容，不会跨仓库。**
- 环节内角色：**coder**、**code reviewer**、**internal reviewer**。

## 三、产出物落位与「零锁恢复」的适用边界

- **story 环节、design 环节、work item 环节的所有产出，都存在 aria 自己规划的目录下**，**不会存在 lc 仓或者真实仓库中**。
- 因此：**story / design / work item 三个环节不需要「零锁恢复」**。
- **只有 coding 阶段的 code reviewer 和 internal reviewer 需要零锁恢复。**

## 四、流程全貌

```
issue 环节（无角色，用户手工）
    ↓  产出：issue + 用户选定的 lc 仓中的真实仓库
story 环节（author → story spec；reviewer → 审核与修改意见；用户定稿）
    ↓
design 环节（author → design spec；reviewer → 审核与修改意见；用户定稿）
    ↓
work item 环节（author → work item plan；reviewer → 审核与修改意见；用户定稿）
    ↓  work item plan 产出多个 work items，每个 work item 只对应一个真实仓库
coding 环节（按 plan 拆分：并行/串行由 plan 指导）
    coder（只开发一个真实仓库，不跨仓库）
        ↓
    code reviewer（需要零锁恢复）
    internal reviewer（需要零锁恢复）
```

## 五、由本标准直接推出的设计约束（owner 2026-10-22 确认）

1. story / design / work item 三个环节的评审**不涉及任何真实仓库的写保护、基线对账、锁与恢复**；相关机制不得为其引入复杂度。
2. 跨真实仓库的写面收敛只发生在 **coding 环节**；每个 work item 只对应一个真实仓库，coder 不得跨仓库。
3. 评审覆盖面以 **coding 环节的 code reviewer / internal reviewer** 为唯一收口点：作者改了什么，评审就要看到什么。

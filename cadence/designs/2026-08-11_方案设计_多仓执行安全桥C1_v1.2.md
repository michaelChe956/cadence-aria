## 2. 背景与目标

### 2.1 背景

阶段 B 让多仓库 issue 能走完整 AI 规划链路（Story 跨仓生成 → Design 带 change_order → WorkItem 按 target 拆分），产出了带 `target_repository_id` 的 WorkItem。但 coding 执行层仍是单仓模型：

- `CodingExecutionAttempt.target_snapshot` 字段已定义（三层身份 logical/checkout/physical + revision + policy_digest + membership_revision），但**所有创建点硬编码 `None`**（`coding_attempt_store/attempt.rs:91`、`group.rs:165`、`group_initialization.rs:465`）
- `CreateCodingAttemptInput` / `CreateGroupCodingAttemptInput` **没有 target 字段**，创建时调用方根本没传 target
- shared worktree 存储仍是单 issue 份（`issue-shared-worktree.json`，二元 `(project, issue)`），`upsert` 时 `target_repository_id` 硬编码 `None`
- group 创建校验（`group_initialization.rs:524 validate_group_initialization_input`）**不检查 target 一致性**，mixed-target group 不会被拒绝

结论：B 产出的 target 在 coding 层被丢弃，多仓 issue 实际无法在各自目标仓隔离 coding。

### 2.2 目标

让多仓库 issue 的每个 WorkItem 在**各自目标仓的独立 worktree** 真正 coding 且安全隔离：

1. **attempt 冻结 target 快照**（REQ-COD-02）：创建即冻结三层身份 + revision + policy_digest，恢复/重放一律用快照，缺失或漂移 fail-closed
2. **shared worktree 三元键**（REQ-COD-03）：多仓 issue 每个目标仓一份独立 worktree，`(project, issue, repository)` 定位，异仓并行、同仓串行
3. **mixed-target group 拒绝**（REQ-COD-04）：创建/恢复/replay 三处一致拒绝，稳定错误码
4. **单目标仓 worktree 执行**（REQ-COD-01，分层 c）：Cadence 显式建目标仓 worktree + cwd 钉死，主 checkout 不动；**post-hoc 越界检测**（coding 后扫主 checkout/成员仓，越界标记 + 阻断交付）。事中配置级阻断（写配置/capability/旁路 fixture）随 C-2
5. **WP5a 收尾**：核实并补全 validator/runtime 层 target 完整性校验（attempt 创建/恢复时校验 target 快照一致性）

### 2.3 成功标准

- 多仓库 issue 的每个 WorkItem 启动 coding 时：在正确目标仓创建独立 worktree（主 checkout 不动），attempt 持有完整 target 快照
- 同仓多 WorkItem 复用同一仓库级 shared worktree（串行）；异仓 WorkItem 各自 worktree（并行）
- mixed-target group 在创建/恢复/replay 三处被一致拒绝，返回 `mixed_target_group_rejected`
- attempt 恢复/重放时校验快照 membership_revision/revision 一致，漂移则 fail-closed
- **单仓红线**：单仓 issue（`logical_codebase_ref=None`）的 coding 行为完全不变（attempt 无快照、shared worktree 走老路径、不查 target 一致性）

## 4. 方案设计

### 4.1 REQ-COD-02：attempt target 快照冻结（方案①：创建时同步冻结 + factory + 5 入口校验）

> **v1.1 修正**（reviewer Critical 1 + Important 1）：① 快照权威源是 WorkItem/group unit 的 target，不是 design；② 三层身份解析用 `resolve.inc.rs` strict resolver，不是 `PlanningContextResolver`；③ 恢复校验覆盖 5 个真实入口；④ `Logical+None` 必须 fail-closed。

**4.1.1 input 加字段**：`coding_attempt_store/inputs.rs` 两个 input 加
```rust
pub target_snapshot: Option<AttemptTargetSnapshot>,  // Some=多仓冻结；Legacy 传 None
```

**4.1.2 新增 snapshot factory**（product 层，修 v1.0 的解析器选错）：
- **权威 target 来源**：① 单 WorkItem attempt → `work_item.target_repository_id`（web/handlers/coding.rs:275-305 现状）；② group attempt → authoritative units 的唯一 target（`web/handlers/coding/group.rs:254-321` 现状，混合由 §4.3 拒绝）
- **三层身份解析**：用 `repository_store_parts/resolve.inc.rs:23-88` 的 strict logical repository resolver（输入 `LogicalRepositoryId` → 输出 `CodebaseMemberRecord`/`RepositoryCheckoutRecord`/`RepositoryRecord`，含 physical id / canonical_path / git_dir_identity）。**不用 `PlanningContextResolver`**（它只输出 aggregate-index fingerprint + membership，不输出 physical/canonical/git-dir）
- **revision 采样**：目标 checkout 实时 `git rev-parse HEAD`（捕获当下 commit）
- **policy_digest**：取自 `AggregatePolicyArtifact`（`logical_codebase/policy.rs`），恢复时重算比对
- **membership_revision**：取自 `LogicalCodebaseManifest` 当前 revision
- **capture_source**：标记 `coding_attempt_create`（区分后续可能的 `migration`/`replay` 来源）

**4.1.3 创建点接线**：`attempt.rs:91` + `group.rs:165` + `group_initialization.rs:465` 把 `target_snapshot: None` 改为 `target_snapshot: input.target_snapshot`。web handler（已有 routing 分流）：Logical 分支调 factory 组装快照传入；Legacy 分支传 None。

**4.1.4 恢复/重放校验（v1.2 核心修正：统一 admission API，不再枚举入口）**

> **v1.2 修正**（reviewer Critical 1 二审）：v1.1 枚举了 5 个入口但仍遗漏 `recover_failed_code_review`（socket/preparation.rs:112-138 → failed_review_recovery.rs:168-224，:223 重开 running）和 `recover_plan_amendment`（runner_support.rs:22-35 → amendment.rs:97-123）两个状态重开入口；且枚举方式无法保证"校验先于状态推进"（这两个入口是先恢复状态、后才可能被 runner 校验）。改为**统一 admission API**。

**设计**：新增唯一 admission 关卡 `admit_attempt_for_execution(attempt_id, app_paths) -> Result<AdmissionTicket, StableCode>`，语义为 **load → routing 判定 → snapshot 校验 →（通过才）状态转换/启动**。**凡 attempt 状态重开、恢复、replay、journal 回放、直接 provider 启动，必经此关卡，且必须在状态转换/启动之前调用**。已知必经点（非穷举，实现时以"任何将 attempt 推进到可执行状态的操作"为准全收口）：
- engine start（lifecycle.rs:123-144）
- gate response/retry（gates.rs:598-835）
- runner 启动各阶段（runner.rs，含从 Coding/Review 重启，不仅 WorktreePrepare）
- provider retry（provider_retry.rs）
- group init replay（group_initialization.rs）
- **failed-review recovery**（failed_review_recovery.rs:168-224，v1.1 遗漏）
- **plan-amendment replay**（amendment.rs:97-123，v1.1 遗漏）

**校验语义（routing-aware）**：
- **`Legacy + target_snapshot=None`**：✅ 放行，走 legacy 路径（红线）
- **`Logical + target_snapshot=None`**：🔴 **fail-closed**，稳定码 `target_snapshot_missing_for_logical`（禁止像现状那样从活 WorkItem/group 推导 target——正是 REQ-COD-02 禁止的，reviewer 证据 `coding_attempt_repository.rs:42-97`）
- **`Logical + Some(snapshot)`**：重读当前 membership_revision / revision / policy_digest，与快照比对：
  - membership_revision 不一致 → `target_snapshot_membership_drifted`
  - revision 不一致 → `target_snapshot_revision_drifted`
  - policy_digest 不一致 → `target_snapshot_policy_drifted`
  - 全一致 → ✅ 放行

所有 fail-closed 统一**持久化为不可继续的「人工恢复」状态**（admission 关卡负责落盘该状态，后续任何启动入口见此状态即拒；不在 C-1 实现自动恢复，记为后续演进）。

**实施约束**：现有 `gate.rs:39-68 ensure_provider_run_allowed`（只校验 lineage/plan-amendment 状态）**不能**充当此关卡（不校验 target snapshot）；admission API 是新独立函数，ensure_provider_run_allowed 内部改为调 admission API 或在其后串联。

**AttemptTargetSnapshot 复用现有结构**（`coding_models/execution.rs:91`，无需改字段）。

### 4.2 REQ-COD-03：shared worktree 三元键（单仓老路径 + 多仓新路径 + 完整删除链）

> **v1.1 修正**（reviewer Important 3 + 4）：补完整删除调用链（attempt/group plan/issue 删除三入口）；迁移契约化（不再“直接砂掉”）。

**4.2.1 path 方法**（`lifecycle_store/paths.rs`）：新增 `repo_shared_worktree_path(project, issue, repository_id) -> PathBuf`（`shared-worktrees/{repository_id}.json`）。老方法 `issue_shared_worktree_path` 保留。

**4.2.2 store 层新方法**（`lifecycle_store/worktree.rs`，与老方法并列）：`upsert_repo_shared_worktree` / `get_repo_shared_worktree` / `delete_repo_shared_worktree` / `try_acquire_repo_worktree_lock`（仓维锁）/ `release_*` / `validate_*` / `mark_*` 系列。锁文件同址 `shared-worktrees/{repository_id}.json.lock`。

**4.2.3 gates 层分流**（`coding_workspace_engine/gates.rs` 10+ 方法）：按 attempt `target_snapshot` 分流——Some=多仓调新方法（repository_id 取自 snapshot.logical_repository_id）；None+Legacy=单仓调老方法；**None+Logical 永不至此**（§4.1.4 的 fail-closed 已拦）。

**4.2.4 删除调用链（v1.1 新增，reviewer Important 3）**：仓维 worktree 的清理需贯穿三层调用入口，不能只靠 store 新方法：
- **attempt 删除**（`coding-attempt-deletion` 能力）：多仓 attempt 删除时，按其 `snapshot.logical_repository_id`（**LogicalRepositoryId 键域，v1.2 修正笔误**——`AttemptTargetSnapshot` 无 `repository_id` 字段，勿误取 `physical_repository_id` 破坏三元键）调 `delete_repo_shared_worktree`；且仅在「该 logical repository 无其他活动 attempt 引用」时删文件（不能一个 attempt 删就清，同仓其他 item 可能复用）
- **group plan 删除**（`work-item-group-deletion` 能力）：同上，按 group 的 target repository 清理
- **issue 删除**（`web/handlers/lifecycle/deletion.rs:236-239` 现状调旧二元清理）：按 routing 分流——多仓 issue 删除**枚举 `shared-worktrees/` 目录下所有 `{repository_id}.json` 逐个清**（含锁文件）；单仓 issue 删除走老逻辑清 `issue-shared-worktree.json`（不变，红线）
- store 层提供辅助：`list_repo_shared_worktrees(project, issue) -> Vec<repository_id>`（供 issue 删除枚举）

**4.2.5 record 复用**（`models/lifecycle.rs:215`，已有 target_repository_id/checkout_id 字段）：多仓 upsert 填 Some；单仓 None。

**4.2.6 迁移契约化（v1.1，reviewer Important 4）**：**不做迁移**，但不是“砂掉”：
1. 仅适用「全新部署」（无历史多仓 issue 数据，用户已确认）
2. 多仓路径首次访问仓维 worktree 前 **preflight 断言**：检查同 issue 下是否存在旧 `issue-shared-worktree.json`
3. 断言失败（发现旧文件）→ **fail-closed**，稳定码 `legacy_shared_worktree_present`（不静默覆盖、不从旧文件推导 repository）
4. **follow-up 债务**：未来若出现历史多仓数据（如生产环境遗留），需恢复 REQ-COD-03 spec 原始的 journal/redirect/F-6 锁顺序协议 —— 记入 `cadence/notes/2026-08-11_多仓库支持BCD阶段路线图.md` 的 C-1 backlog 和阶段 D 迁移演练项

### 4.3 REQ-COD-04：mixed-target group 拒绝（routing-aware，三处一致）

> **v1.1 修正**（reviewer Important 2）：v1.0 的「所有非 None target 相同」会放过 `Some(A)+None`（filter_map 让 None 消失），使缺 target 的 Logical unit 跟随 A 执行。改为 routing-aware。

**改造点**（3 处调同一函数 `validate_group_single_target(routing, unit_bindings, attempt_snapshot)`）：

1. **创建处**（`group_initialization.rs:524 validate_group_initialization_input`）
2. **恢复处**（`group_validation.rs:251 validate_group_attempt_integrity`）
3. **replay 处**（group replay/重放入口）

校验语义（routing-aware，堵 None 绕过）：
- **`RepositoryRouting::Legacy`**：所有 unit `target_repository_id` 必须**全 None** → ✅；出现任何 Some → `mixed_target_group_rejected`
- **`RepositoryRouting::Logical`**：所有 unit `target_repository_id` 必须**全 Some 且互相同**，且与 attempt 的 `target_snapshot.logical_repository_id` 一致 → ✅；出现任何 None / ≥2 不同 Some → `mixed_target_group_rejected`
- **拒绝任何 `source_draft_error`**（draft 溯源已出错，不应进 group）→ `mixed_target_group_rejected`

**稳定错误码与映射（v1.1 明确，reviewer Minor 1）**：`mixed_target_group_rejected` → **error.rs 显式映射 422 UNPROCESSABLE_ENTITY**（直接写入 error.rs 的映射表 + API regression test，不留 writing-plans 再定；未知码默认 500，必须显式声明）。

### 4.4 REQ-COD-01：单目标仓 worktree 执行（分层(c)：worktree+cwd 完整 + post-hoc 越界检测）

> **v1.1 修正**（reviewer Critical 2 + 决策 #8）：v1.0 过度乐观宣称「实现 REQ-COD-01」。实际 COD-01 Scenario 2 的「配置约束 + 事中越界阻断」依赖 gateway（C-2）。C-1 取分层(c)：做 Scenario 1 完整 + Scenario 2 的 post-hoc 检测，不做配置级阻断（随 C-2）。

**4.4.1 worktree 创建 + cwd 钉死（Scenario 1 完整，C-1 做）**：
- 多仓 WorkItem 启动 coding：经 routing 判定目标仓 → 在**目标仓 checkout 路径**下 `.worktrees/aria-issues/{issue}` 建 worktree（复用 §4.2 三元键路径定位）→ provider cwd 钉死该 worktree
- 主 checkout 不动（HEAD + 工作区）：多仓下每个成员仓主 checkout 不动，只各自 worktree 改
- 复用现有 `git_workspace_service.rs:646-687 ensure_safe_worktree_path`（创建时路径安全校验）

**4.4.2 post-hoc 越界检测（Scenario 2 的检测+阻断交付，C-1 做；v1.2 收窄承诺 + 持久化 + 统一门）**：

> **v1.2 修正**（reviewer Critical 2 二审 + 用户决策 α）：v1.1 过度承诺"含 symlink/绝对路径写入造成的越界"，但只采成员主 checkout HEAD+status 检测不到 symlink 跳出仓外、`/tmp` 绝对路径写入。用户选 (α) 收窄承诺。

- **检测范围（收窄，诚实）**：post-hoc **只监控各成员仓主 checkout** 的 `git rev-parse HEAD` + `git status --porcelain` 变更。即能发现：①目标仓主 checkout 被改（AI 应只改 worktree 不该动主 checkout）；②其他成员仓主 checkout 被改（AI 越界改他仓）。
- **不覆盖（诚实列为残余风险，交 C-2）**：symlink 指向仓外目录后经 symlink 写入、`/tmp/...` 等不属于任一成员 checkout 的绝对路径写入、provider 运行中的实时越界——这些靠 C-2 的 provider 写配置约束（writable_roots）+ capability 版本钉定 + 越界矩阵 fixture 才能管，C-1 post-hoc 天生管不了。
- **基线持久化（v1.2 新增）**：每个 provider run（Coder/Reviewer/重试/rework）开始前采的 baseline **持久化到 attempt 绑定的 run 记录**（canonicalized 各成员仓 checkout 路径 + HEAD + porcelain 快照）。run 结束后重采比对。**崩溃重启后基线缺失 → 该 run 视为不可信 → fail-closed**，稳定码 `cross_target_baseline_missing`，阻断交付进人工恢复（不蒙混过关）。
- **统一门位置（v1.2 新增）**：post-hoc 检测在**所有交付入口前**作为统一检查执行——commit/push/完成（internal_pr_review.rs:778-909 交付路径）前必调；检测到越界 → attempt 持久化标记 `cross_target_violation_detected`，**阻断进入 push/完成**，进人工恢复。
- **能力边界（诚实标注）**：post-hoc best-effort（事后发现主 checkout/他仓被改），**非事中配置级阻断**；不覆盖 symlink/绝对路径/运行中越界（随 C-2）；不宣称 OS 级不可达。
- design.md §5.2 原话「路由级 fail-closed ≠ 端到端 coding 已达 fail-closed supported」仍生效，C-1 后多仓 coding 仍标 experimental + supervised。

**4.4.3 不做（随 C-2）**：provider 写配置约束（`sandbox_mode=workspace-write` 等）、capability 版本钉定、越界矩阵 fixture（Claude plan bypass #41758 / PreToolUse deny #37210 / Codex apply_patch #24214）、gateway 路由级阻断 Codex danger-full-access。这些依赖 `LogicalCodebaseProviderGateway`，属 C-2。

### 4.5 WP5a 收尾（validator/runtime target 完整性）

核实并补全：
- compile 路径（`compile_support.rs`）已正确分流（单仓单一 repository_id 回退 / 多仓 per-item target），**不是缺陷**，保留
- 补：attempt 创建/恢复时（4.1 的 admission API）即覆盖 runtime 层 target 完整性校验
- 补：validator 层对多仓 WorkItem 的 target 非空校验（与 4.3 配合，target 缺失即 blocker，已有 `work_item_target_missing` 码，保留）

### 4.6 稳定错误码与 HTTP 映射契约（v1.2 新增，reviewer Important 3+4）

C-1 引入的所有新稳定码 **必须显式进 `error.rs` 映射表 + HTTP 状态 + regression test**（未知码默认 500，不能留实现阶段自由选择）：

| 稳定码 | HTTP | 场景 | 来源节 |
|---|---|---|---|
| `target_snapshot_missing_for_logical` | 422 | Logical attempt 缺快照（admission fail-closed） | §4.1.4 |
| `target_snapshot_membership_drifted` | 409 | 成员表 revision 漂移（成员删/停用） | §4.1.4 |
| `target_snapshot_revision_drifted` | 409 | 目标仓 revision 漂移 | §4.1.4 |
| `target_snapshot_policy_drifted` | 409 | policy_digest 漂移 | §4.1.4 |
| `mixed_target_group_rejected` | 422 | mixed-target group（创建/恢复/replay 三处） | §4.3 |
| `legacy_shared_worktree_present` | 409 | 多仓路径首次访问发现旧 issue-shared-worktree.json（迁移断言 fail-closed） | §4.2.6 |
| `repo_worktree_active` | 409 | 仓维锁竞争（同 target 并发，一获 lease 一得此码） | §4.2.2 |
| `cross_target_violation_detected` | 409 | post-hoc 检测到主 checkout/他仓被改，阻断交付 | §4.4.2 |
| `cross_target_baseline_missing` | 500 | 崩溃重启后 post-hoc 基线缺失，该 run 不可信 | §4.4.2 |

- 映射惯例对齐：现有 `issue_worktree_active → 409 CONFLICT`（error.rs:113-118）、`repository_routing_target_missing → 422`（error.rs:79）已确立 4xx 惯例，本表沿用
- `cross_target_baseline_missing` 是基础设施级（500），因其表示"内部状态丢失"而非用户输入错误
- HTTP/WS 两路表现一致：HTTP 经 `ApiError` 映射状态码；WS 把稳定码前缀进消息（与 B 阶段 confirm gate 一致）
- 每个码配 regression test（error.rs 单测 + it_web API 断言）

## 6. 数据流（单仓 vs 多仓对比）

### 单仓 issue（现状不变）

```
coding 启动 → routing=Legacy → CreateCodingAttemptInput{target_snapshot:None}
→ attempt.target_snapshot=None → shared worktree: issue-shared-worktree.json (二元)
→ 恢复: 无快照校验, legacy 路径 → group: 全 None target, 跳过 mixed 校验
```

### 多仓 issue（C-1 接通后）

```
coding 启动 → routing=Logical → handler 取 WorkItem/group unit 的 target_repository_id
→ snapshot factory: resolve.inc.rs 三层身份 + git rev-parse HEAD revision
  + AggregatePolicyArtifact policy_digest + manifest membership_revision
→ CreateCodingAttemptInput{target_snapshot:Some(...)} → attempt 落盘冻结
→ shared worktree: shared-worktrees/{repository_id}.json (三元), 仓维锁
→ 恢复/重放: 统一 admission API (load→routing→snapshot 校验→状态转换)
           Logical+Some → 校验 membership/revision/policy 一致, 漂移 fail-closed
           Logical+None → 🔴fail-closed target_snapshot_missing_for_logical
           Legacy+None → ✅放行 legacy 路径
→ group: Logical → 校验全 Some 且同 + 与 snapshot 一致 + 无 source_draft_error
           → 不符 → mixed_target_group_rejected (422)
→ worktree: 目标仓 .worktrees/aria-issues/{issue}, cwd 钉死, 主 checkout 不动
→ post-hoc 越界检测(收窄): 只监控各成员主 checkout HEAD/status, 基线持久化到 run
           → 主 checkout/他仓被改 → cross_target_violation_detected (409) 阻断交付
           → 基线缺失 → cross_target_baseline_missing (500) 阻断
           （symlink/绝对路径/运行中越界交 C-2）
```

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 单仓红线被破坏（shared worktree 双路径分流失误） | 所有分流基于 `target_snapshot` 是否 Some；单仓全程 None；**前提**：Logical+None fail-closed（不会误走 legacy API）；单仓 coding 全量测试守护 |
| attempt 快照三层身份解析错误（checkout_id/physical_id 映射错） | 用 `resolve.inc.rs` strict resolver（**不用 PlanningContextResolver**）；补三层身份一致性 unit test |
| **admission API 收口不全**（某状态重开/恢复/replay 入口漏走关卡） | v1.2 改统一 admission API（不枚举入口），以"任何将 attempt 推进到可执行状态的操作"为准全收口；已知含 engine start/gate/runner/provider retry/group init replay/failed-review recovery/plan-amendment replay |
| Logical+None 误从活 WorkItem 推导 target（REQ-COD-02 禁止） | admission 明文 fail-closed `target_snapshot_missing_for_logical`；现状代码（coding_attempt_repository.rs:42-97）须改 |
| mixed-target 拒绝在 3 处不一致或绕过（Some+None） | routing-aware 公共函数，3 处调同一函数；Logical 全 Some 同、Legacy 全 None、拒 source_draft_error；3 入口集成测试 |
| 多仓 worktree 路径与单仓混淆（同一 issue 既有多仓新文件又有单仓老文件） | routing 三态互斥；多仓首次访问 preflight 断言无旧文件，发现旧文件 fail-closed |
| **仓维 worktree 并发创建竞争**（同 target 两个 attempt 同时建） | 仓维锁，同 target 并发一个获 lease 一个得 `repo_worktree_active`（409）；并发同步屏障集成测试；失败后锁释放 |
| 删除调用链漏仓维文件（attempt/group/issue 删除只清老二元） | 三入口全改（§4.2.4）；issue 删除枚举 `shared-worktrees/` 全清；删除回归测试 |
| **post-hoc 越界检测能力边界**（symlink/绝对路径/运行中越界检测不到） | v1.2 诚实收窄：只监控各成员主 checkout HEAD/status；symlink/绝对路径/运行中越界交 C-2 配置级阻断；列出为残余风险 |
| post-hoc 基线丢失（崩溃重启无基线） | v1.2 基线持久化到 attempt run 记录；基线缺失→fail-closed `cross_target_baseline_missing` 阻断交付 |
| target 快照捕获时 revision 已漂移 | 捕获时 `git rev-parse HEAD`（best-effort）；恢复时再校验（双层） |
| C-1 规模偏大（预计 16-22 Task，含 admission API + post-hoc 检测子系统） | writing-plans 按 WP5a/snapshot/admission/三元键/mixed/worktree+检测/稳定码 分 Task 组，每组独立 review |
| 历史数据迁移未做，未来出现遗留数据 | 契约化断言 + fail-closed + follow-up（§4.2.6）；follow-up 已写入路线图（v1.2 同步） |

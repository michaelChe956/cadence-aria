## 1. 摘要与命名理由

### 1.1 一句话摘要

把「已删实体留下的旁支/记账类悬空引用」从**随机爆炸**变成**可枚举、可容错、可按类型销账**的三层治理：① 读侧只对旁支引用容错（跳过 + 告警），② 全量巡检先只报不改，③ 看清清单后按类型自动销账（幂等 + 留痕 + 清理后自证归零）。

### 1.2 问题一句话复述

删掉 story/design/work item group 后，系统里留下三类指向「已不存在对象」的旁支记录：自动化 intent、评审窗口/快照、实体身份台账条目。它们不阻塞任何主记录的读取，却会在**自动化重新开启**、**启动补偿扫描**、**级联删除反查**三条路径上把用户流程卡死或让 fail-closed 判定失真。

### 1.3 命名理由

| 名称 | 取值 | 理由 |
|---|---|---|
| 技术方案文件名 | `2026-10-27_技术方案_悬空引用治理与读侧容错_v1.0.md` | 按 `rule://document-storage` 的 `YYYY-MM-DD_文档类型_文档名称_v版本号.md`；文档类型=技术方案、存储路径=`cadence/designs/` |
| OpenSpec change 名 | `add-dangling-reference-governance` | 本仓新增能力的既有命名法为 `add-<能力>`（对照 `add-provider-run-boundary`、`add-multi-repo-issue-entry`）；本 change 新增一个能力而非修复既有缺陷，故用 `add-` 前缀 |
| capability 名 | `dangling-reference-governance` | 覆盖三层（读侧容错 / 巡检 / 销账），是一个**治理能力**而非单一功能；用名词短语而非动宾短语，便于与既有 capability（`provider-run-boundary`、`coding-work-item-deletion`）并列 |

1. **级联删除只清「子级产物」**：sessions / timelines / drafts / work-items / verification-plans / versions 等。**编排的两层落点**（注意：`src/product/lifecycle_store/cascade_deletion.rs` **不存在**）：用户面三类实体删除入口在 `src/web/handlers/lifecycle/deletion.rs::cascade_delete_entity`（`cascade_delete_entity` 起于 `:107`）；子树清理集合在 `src/product/entity_deletion_cascade.rs`（`purge_entity_closure` 起于 `:113`）；`LifecycleStore::purge_entity_owned_children` 在 `src/product/lifecycle_store/plan.rs:1318` 起。**intent 记录 / reviewer-windows / reviewer-snapshots / entity-identity 台账**均不在其覆盖面内；`entity_deletion_cascade.rs` 未被已落地的自动化改动触碰（自动化策略层在 `src/web/handlers/lifecycle/deletion.rs`）。
2. **自动化 enrollment 被「终止 / 失效」而非删除**（`src/web/handlers/lifecycle/deletion.rs:569` 的 `terminate_automation_bound_to_entity`；在途的 `invalidate_automation_referencing_entity` `:690` 对 source 引用面补齐了级联失效）→ **文件仍在** → 其 `source` 字段继续指向已删实体 → 重新开启时旧 source 被精确校验拒绝。
3. **三个全局分区在 issue 目录之外**（`reviewer-windows/`、`reviewer-snapshots/`、`state/entity-identity/`），issue 级级联天然够不着。

### 3.1 第 ① 层：读侧容错

#### 3.1.1 统一判据能力（新增，与已落地判定共用）

新增**一个**判定能力：「这条记录里的这个引用，目标是不是已经没了」。

#### 3.1.3 告警形状

- **一个稳定码 + 结构化字段**（不按目标类型分裂成一堆码，避免码爆炸）：

  | 字段 | 值 |
  |---|---|
  | `code` | `dangling_reference_target_missing` |
  | `record_path` | 悬空引用所在记录的相对路径 |
  | `record_type` | 记录类型标识（如 `automation_plan_intent`） |
  | `reference_field` | 引用字段路径（如 `source.stories[].id`） |
  | `target_kind` | 九类目标类型之一 |
  | `target_id` | 目标 id |
  | `scope` | 可解析时的 `project_id` / `issue_id`（解析不到则省略，不猜） |

#### 3.1.4 只吞「目标已删」这一种错

读侧容错的错误分类（三分法，逐类处置）：

| 错误类别 | 处置 |
|---|---|
| 目标记录**不存在**（NotFound / 列举结果里查无此 id） | **吞**：跳过该条目 + 告警 |
| JSON **解析失败** / schema 不符 / 字段缺失 | **不吞**：照旧上抛（既有 fail-closed 语义不变） |
| **IO 失败** / 权限错误 / 目录不可读 | **不吞**：照旧上抛 |

> 依据：既有代码已区分这两类——`read_json_if_exists` 的「不存在=未开始/已清」与「真实 IO/JSON 错误必报」（`src/product/entity_deletion_store.rs:12` 模块文档）；`ReviewerWindowStore::list_windows` 的「单条损坏记录跳过并告警」与整体 `read_dir` 失败即报错（`src/product/reviewer_window_store.rs:1160-1192`）。本能力**沿用同一形状**，不发明第四种语义。

#### 3.2.3 边界判据（判定「某读路径能否容错」的三条同时满足条件）

一个读路径**同时**满足以下三条才允许容错，否则只巡检上报、不改行为：

1. **(a) 输出面向列举/投影**，跳过一条不改变任何一致性判定（不是准入依据、不是反查输入、不是物理清理输入）；
2. **(b) 跳过不产生 fail-open**：不会让本应被拦住的写入/删除/占用放行；
3. **(c) 该路径上不存在「主记录缺失」语义**：主记录的缺失错误码与文案不在该路径上产生。

> 依据：R1–R4 全部满足；N1–N12 至少违反一条（N5/N6/N7/N8/N9/N11 违反 (b)；N1/N2/N3/N4/N10/N12 违反 (c) 或 (a)）。

- **r2 新增：无法完成判定进「不可判定」计数，不进悬空计数**（S1）。某判据点的目标核对若因 IO / 解析 / 权限错误**无法完成**，**或所需存在性数据源 / 作用域在本判定点不可用**（U1 四类：无 LC 上下文核对 checkout / aggregate_index / logical_member，无 project/issue 作用域核对 enrollment → 存在性判 `Unknown`，r4），该条记为**不可判定**（`undetermined`），**不**计入「悬空条目数」，也**不**计入「已归零」。

> **r3 更正（N-9）：删除粒度 MUST 按 attempt 聚合**。`purge_for_attempts` 按 attempt id **批量删除该 attempt 名下的全部窗口**（含 `window-archive` 中的归档窗口，`:66-72`、`:85-110`），而 L2 四条件是**按窗口**判的——若某 attempt 下有一个窗口仍持租约或非终态，传该 attempt id 会把**满足条件的窗口一并删掉**，违反「缺一即不删」。故销账 MUST 先按 attempt 聚合该 attempt 名下**全部**窗口（含归档），**全部满足**四条才调 `purge_for_attempts`；任一不满足 → 该 attempt 名下的窗口**一个都不删**，只报不删。
>
> **r3 更正（N-1）：本表的「只报不删」判定口径统一为**「不具备 L1 证据、**且不满足 §3.1.2 等级表中该类型的 L2 专属可算条件**」。窗口簇走 L2（其专属条件 = W-1..W-4），故「无 L1 证据」本身**不**构成不删窗口的理由；其余类型按表降级为只报不删。

#### 3.4.1.1 窗口簇的 L2 四条件（r2 新增，B-3：条件必须「从窗口记录自身可算」）

r1 的 L2 条件是「attempt 记录不存在 **且** 其所属 plan 亦不可达」——**该条件在事实层算不出来**：`CodingExecutionAttempt` **没有 `plan_id`**（结构体定义 `src/product/coding_models/execution.rs:187`；有 `work_item_id` 与 `work_item_group_id`，但无 plan 引用），窗口/快照记录里也**没有任何 plan 引用**（实测 `plan_id` 出现 0 次），墓碑 manifest 亦无 `attempt_ids`（`src/product/entity_deletion_store.rs:131-145`）。r2 改为**四条全部从窗口记录自身可算**的条件：

| # | 条件 | 判定方式 | 依据 | 实测（本现场 6 条窗口） |
|---|---|---|---|---|
| W-1 | **窗口状态为终态** | `ReviewerWindowState::is_terminal()`（三个终态：`ClosedInvalidated` / `NewReviewRequired` / `ClosedAccepted`） | `src/product/reviewer_window_store.rs:113` | ✅ 6/6 满足（5 × `closed_accepted`，1 × `closed_invalidated`） |

> **r3 更正（N-9）：四条是「按窗口」判的，删除却是「按 attempt」批量做的** → 销账 MUST 先按 attempt 聚合该 attempt 名下**全部**窗口（含归档），**全部满足**四条才允许调用物理清理器；任一不满足 → 该 attempt 名下窗口**一个都不删**（详见 §3.4.1 的 r3 注记）。本现场 6 个窗口恰好分属 3 个 attempt、每个 attempt 名下的 2 个窗口都满足四条 → **现场不暴露该缺陷**（待实现时核实，§11 U15）。

> **B-3 的关键**：W-3 的**两路**缺一不可——只查路 1 时，规划面窗口的 `attempt_id`（实为 workspace session id）必然 NotFound → 活的规划评审窗口被判悬空并**被物理删除**（§2.4.1）。

#### 3.4.1.2 intent 销账的四道前置条件（r2 新增，B-4）

r1 的规则「story / design / plan / session 任一没了 → 删整个 intent 文件」在事实层**不成立**：

- `PreparedPlanIntent::from_enrollment`（`src/product/models/automation.rs:432-448`）把 `plan_id` / `session_id` **由 `prepare_intent_id` 预派生**后写入 intent 文件，**plan 尚未创建时这两个 id 就已存在** → 「引用目标不存在」是**正常中间态**，不是已删证据。
- `ensure_plan_binding`（`src/product/issue_automation_store.rs:348-451`）**先写 intent、后建 plan/session**，且函数文档明写「create 失败原样穿出锁外，**意图文件保留为下次补偿锚点**」→ 删掉它 = **删掉补偿锚点** → 自动化链永久卡死。
- 取代路径删 intent 是**两步非原子**：`stale.metadata().is_ok()` 之后 `std::fs::remove_file(&stale)`（`src/product/issue_automation_store.rs:1736-1753`）→ 销账若插在两步之间，会让取代侧 `remove_file` 报 Io 失败（TOCTOU）。
- generation intent 的 `phase` 一旦离开 `Claimed` 就是**防双跑检查点**（`PlanGenerationPhase` 无终态变体；`claim_plan_generation` 在文件缺失时按 `Claimed` 新建，`:519`）→ 删掉它会让下一次认领**从头起跑**。

**r2 规定：删一个 intent 文件，四条必须同时成立**（缺任一条 → **只报不删**）：

| # | 前置条件 | 判定方式 | 依据 |
|---|---|---|---|
| I-1 | **持有 enrollment 文件锁** | 复用 `with_exclusive_lock(&enrollment_path, …)`（锁文件 = `automation-enrollment.json.lock`） | `src/product/issue_automation_store.rs:14`（导入）、`:55-66`（路径）；既有用法 `:149` / `:361` / `:464` / `:651` / `:729` / `:841` / `:876` / `:929` / `:985` |
| I-2 | **锁内重读三项通过** | **三项 MUST 在同一把锁内重读**（MUST NOT 用锁外读到的旧值）：① `automation-enrollment.json`：**文件缺失** → 通过；**存在且 `enabled == true`** → **不通过（只报不删）**；**存在且已终止**（**`terminated_at` 有值**）**且 `enrollment_id` 与 intent 的 `enrollment_id` 一致** → 通过；**`enrollment_id` 不一致** → 不通过（只报不删）；② generation intent 的相位（见 I-4）；③ 目标墓碑证据（见 I-3） | `IssueAutomationEnrollment` 字段 `src/product/models/automation.rs:91-135`（`enabled` / `enrollment_id` / `terminated_at`）；「已终止」只以 `terminated_at` 有值为准（r3 更正，N-12） |
| I-3 | **存在 L1 墓碑**（**在锁内重读**） | 判据字段对应的 story / design / plan 有满足 **L1-a..L1-d** 四条的墓碑 | §3.1.1；**`session_id` 与 `enrollment_id` 的缺失一律不算证据**（S6） |

> **r3 更正（N-12）：「已终止」的口径**。`Disable` 命令**只置 `enabled = false`、不写 `terminated_at`**（`src/product/issue_automation_store.rs:1506-1510`），故「`enabled == false`」**不等价于**「已终止」。本设计取**保守口径**：以 `terminated_at.is_some()` 为准；**仅禁用未终止**（`enabled == false` 且 `terminated_at` 为空）者按「仍有活授权」处理 → **只报不删**。spec REQ-DRG-20 已同步此口径。

> **r3 更正（N-3b）：相位与证据也必须在锁内重读**。I-2 通过后写者已不能推进相位，但**外部先读到 `Claimed`、锁内已是 `ProviderDispatched`** 的窗口真实存在；同理，锁外读到的墓碑读数可能在锁内已变为进行中态或已出现待人工处置的删除失败事实。故三项（状态 / 相位 / 证据）一律以**锁内重读值**为准。

> **I-1 为什么必须**：取代路径的「删 intent」段**就在同一把 enrollment 文件锁内**（`compare_and_set_inner` 的 `with_exclusive_lock(&path, …)`，`src/product/issue_automation_store.rs:149` 起，删除段 `:1736-1753`）。销账若不取同一把锁，就能在 `metadata().is_ok()` 与 `remove_file()` 之间插进去 → 取代侧 `remove_file` 报 `ProductStoreError::Io` → **取代 CAS 整体失败**。r1 写的「两者并发不报错，幂等即可抵消竞争」**对取代一侧不成立**，本设计已删除该论证。
> **I-2 为什么必须**：enrollment 仍 `enabled` 时，intent 是**活链路的补偿锚点**，删它会让自动链永久卡死；「enrollment 文件缺失」与「已终止」是两种不同的死法，都不再有活授权。
> **I-4 为什么必须**：现场实测 generation intent 的 `phase == "provider_dispatched"`（§2.4.3）→ 依 I-4，它**只报不删**。这是修订后的诚实结论：r1 的「intent 悬空即删」在本现场会**丢防双跑检查点**。
> **本现场的销账结果预览**（据实测）：plan intent 的 `plan_id` 有 L1 墓碑、`source.stories[].id` / `source.designs[].id` 有 L1 墓碑、enrollment 文件缺失 → **I-1..I-4 满足 → 可删**；generation intent 因 `phase == provider_dispatched` → **只报不删**；intent 的 `session_id` / `enrollment_id` 引用 → **只报不删**（S6）。

#### 3.4.2 三道闸

| 闸 | 内容 | 实现要点 |
|---|---|---|
| 闸 1 | **默认 dry-run**：先只出清单，经 owner 确认后才开自动清理 | 清理入口默认关闭；开启需显式参数 `--apply` + **确认令牌**；无令牌或令牌不匹配 → 拒绝执行、零删除、零留痕。**令牌口径见 §3.4.2.1** |
| 闸 2 | **按类型定规则**，不搞一刀切 | 销账规则是**数据驱动的白名单表**（§3.4.1）；表外记录类型绝不删；规则表与巡检判据表同源但**独立**（销账表可更严） |
| 闸 3 | **幂等 + 留痕**，清理后再巡检自证归零 | ① 幂等：目标已删 + 记录存在 → 删；重复执行 → 记录不存在 → 视为已清（不报错、不重复删）。**幂等语义只用于重入，MUST NOT 替代 §3.4.1.2 的锁语义**（删 intent 仍 MUST 在 enrollment 文件锁内判定）；② 留痕：每次清理记一行（何时 / 因哪个实体被删 / 清了哪条），进删除留痕台账（§3.5）；③ 自证：清理后**再巡检一次**，按类型给出归零计数；未归零项必须逐条列出，**且只报不删残留单列一栏**（§5.1） |

#### 3.4.2.1 确认令牌的可实现口径（r2 重写，B-5 / S3）

r1 的「令牌 = 巡检清单的摘要哈希」**不可实现**，三条理由：① 若令牌是清单**内容**哈希，令牌行本身在清单里 → **自指**（每次都变）；② 清单含「巡检时间」行 → 两次巡检的内容**不可能逐字节一致**；③ CLI 只有 `--apply --confirm <token>`，**没有 `--report <path>`** → 「当前清单」无从定位。

**r2 的令牌定义**：

> **令牌 = 巡检结果中「findings 规范化序列化」的 sha256 摘要。**
>
> - **findings 集合** = 本次巡检判定为「悬空」的条目（**含其中「只报不删残留」的条目本身**），每条含七个字段：`record_path` / `record_type` / `reference_field` / `target_kind` / `target_id` / `evidence_level` / `proposed_action`。
> - **规范化序列化**：按 `record_path` **升序**排序；同 `record_path` 再按 `reference_field`、`target_id` 升序；每条序列化为**一行紧凑 JSON**（键序固定），行间以 `\n` 连接，末尾**不加**换行。
> - **不参与摘要**：巡检时间、清单正文的时间行、**令牌行自身**、**不可判定条目**、**未归类条目**、各栏（汇总 / 只报不删残留 / 不可判定）的标题与说明文字。**「只报不删残留」条目本身的七个字段值参与摘要**——只排除其所在栏目的说明文字，不排除条目本身（r3 写死，N-8；spec REQ-DRG-22 已同步）。
> - 令牌文本形式：`sha256:<64 位小写 hex>`。

**`--apply` 的校验流程**（不依赖任何外部报告文件）：

1. 解析参数：`--apply --confirm <token>`（无 `--apply` → 只出清单，零删除）。
2. **在入口内部重跑一次巡检**（同一进程、同一现场），重算 findings 摘要 `T'`。
3. `T' != <token>` → **拒绝执行**：零删除、零留痕、退出码非零，输出两份摘要的差异摘要。
4. `T' == <token>` → 按 §3.4.1 白名单销账 → 留痕 → 再巡检自证。

> **为什么必须「内部重跑」**：owner 的原始诉求是「凭清单确认后再清理」。令牌由**同一份巡检结果**算出，而 `--apply` 时**重新算出**同一份结果再比对——「拿旧清单开新清理」与「清单生成后现场又变了」两种错配**一次挡住**。不需要 `--report` 参数，也不存在「当前清单」的歧义。
> **摘要的确定性依赖**：findings 的字段集合与排序规则是**规范**（不是实现细节），因此同一现场两次巡检的 findings 序列化**逐字节一致**；而清单正文含巡检时间，**不**要求逐字节一致。验收第 6 条据此改写（§8 第 2 步验收 6）。

#### 3.5 留痕（r2 如实表述：既有「删除记录机制」的真实形状与不能承载之处）

##### 3.5.1 先核实既有「删除记录机制」到底是什么（r2 新增，S4）

r1 写「留痕进已有删除记录机制（`entity-deletions/` 目录族），不另造」并据此论证「落在既有目录族内（不另造目录体系）」。**r2 核实后认为该表述不成立**，如实更正：

| 事实 | 实测 / 源码依据 |
|---|---|
| 既有删除记录机制 = **逐实体墓碑**：`{issue lifecycle root}/entity-deletions/{kind}/{id}.json`，**每 issue 级** | 路径构造 `src/product/entity_deletion_store.rs:518-529`（`entity_deletion_record_path`）；模块文档 `src/product/entity_deletion_store.rs:4`；实测现场目录为 `projects/project_0001/issues/issue_0001/entity-deletions/` |
| **不存在全局级 `entity-deletions/` 根** | 墓碑根绑定 issue；`{state_root}/entity-deletions/` 目录**当前不存在**（实测） |
| 墓碑记录是**单条 JSON**（scope / kind / id / phase / 时间 / 可选 trigger_reason），**不是日志** | `EntityDeletionRecord`，`src/product/entity_deletion_store.rs:88-103` |
| 既有**追加式 JSONL 审计**的既有范式存在于**根级分区** | `tool-policy-run-audit/<workspace_session_id>/<role_run_seq>.jsonl`，每行 `{"schema_version":1,…}`（`src/cross_cutting/tool_policy_audit.rs:22`、分区路径 `src/product/lifecycle_store/tool_policy_run_audit.rs:59-63`）；实测现场有同形态样本 |

**结论**：既有删除记录机制**无法承载**销账留痕，三条硬理由：

1. **语义不匹配**：`EntityScope.entity_id` 的语义是「**被删实体**的 id」，而销账留痕要记的是「**被清理的旁支记录**的路径」——两者不是同一个 id；
2. **基数不匹配**：一次实体删除可连带清**多条**旁支记录（窗口簇 = 窗口 + 租约 + journal + 快照目录 + 归档目录），墓碑是**一实体一记录**，装不下；
3. **覆盖不匹配**：全局分区（`reviewer-*` / `state/entity-identity`）的清理**没有 issue 归属**，而墓碑根**每 issue 级**，无处安放。

→ 因此 r2 **不再声称**「落在既有 `entity-deletions/` 目录族内（不另造目录体系）」。落点与形态如实表述如下（§3.5.2），并把「是否改归既有根级 JSONL 审计分区范式」列为**需 owner 拍板**的开放项（§11 U10）。

##### 3.5.2 落点与行形态

**落点**：**单一全局台账** `{state_root}/entity-deletions/dangling-reference/cleanup.jsonl`，每行一条 JSON（append-only）。

- **目录名沿用删除语义**（`entity-deletions/dangling-reference/`），便于运维按语义检索；
- 但**该目录由本 change 新建**（`{state_root}/entity-deletions/` 当前不存在）——**这一点如实标注，不谎称属于既有目录族**；
- 放在 `state_root` 下 → 天然在 issue 目录之外 → **永不参与**实体子树 purge。

**约束（与 spec REQ-DRG-16 一致，r3 更正）**：落点是**状态根下单一全局**的追加式 JSONL 台账——MUST NOT 分散为每 issue 一份，MUST NOT 写入 issue 级删除墓碑目录，MUST NOT 改写既有墓碑记录，MUST NOT 扩展 `DeletionEntityKind` 枚举形状。**「落在既有删除语义的目录族下 / MUST NOT 另造审计体系」的旧表述已删除**（与 §3.5.1 的核实结论相悖）。**落点归属仍需 owner 拍板**（§11 U10）。

**行形态**：**沿用既有根级追加式 JSONL 审计的行形态**（每行带 `schema_version: 1`，见 §3.5.1 第 4 行）——即**复用既有追加式审计行规范**，而不是新造一套行格式。

```json
{"schema_version":1,"cleanup_id":"b3f1c0d2a9e48f17","cleaned_at":"2026-10-28T10:00:00Z","action":"delete_record","record_type":"automation_plan_intent","record_path":"projects/p1/issues/i1/automation-plan-intent.json","target_kind":"story_spec","target_id":"story_spec_0005","evidence_level":"L1","deleted_entity":{"kind":"story","id":"story_spec_0005","project_id":"p1","issue_id":"i1"},"trigger":"dangling_reference_cleanup","run_id":"patrol_2026_10_28"}
```

| 字段 | 含义 |
|---|---|
| `schema_version` | 行格式版本，固定 1（与既有根级 JSONL 审计一致） |
| `cleanup_id` | 幂等去重键 = hash(`record_path` + `target_id` + `action`)；重入时同键不重复追加 |

### 6.1 读侧容错 vs 物理清理

| 方案 | 优点 | 缺点 | 裁决 |
|---|---|---|---|
| **A. 先容错、后巡检、再销账（三层，本方案）** | ①层立即让「旁支悬空」不再成为流程阻塞点（且不碰主记录语义）；②层给出全局事实；③层做物理收敛 | 三层 = 三次投入；①层当前**没有面向用户的既有消费面**，收益是「预防」而非「止血」 | **采纳**（owner 已拍板三层顺序） |
| B. 只做物理清理（直接删旁支） | 一步到位 | 无事实即动手 = 拿不准就删；无法复核；与「不删用户业务数据」的边界难划 | 排除 |
| C. 只做容错（永不物理删） | 最小改动 | 残留永久累积（12 + 17 条且只增不减），与 owner 普查结论相悖 | 排除 |

### 6.4 容错落点：新增列举 API vs 注入既有读路径

### 6.5 窗口簇删除：复用清理器 vs 自写

  4. **闸 3 留痕**：台账每行含「何时 / 因哪个实体被删 / 清了哪条」三要素 + `evidence_level`；台账落在**状态根下单一全局**文件，**不进 issue 级墓碑目录、不扩 `DeletionEntityKind`**；
  5. **闸 3 自证**：清理后自动再巡检，**销账白名单内且本次可删的类型**归零计数全部为 0；**只报不删残留**与**不可判定**单列并**不得宣称治理完成**；
  6. **intent 四前置条件**（B-4 的核心断言）：
     - enrollment 仍 `enabled` → intent **不删**（只报）；
     - enrollment **仅禁用未终止**（`enabled == false` 且 `terminated_at` 为空）→ intent **不删**（只报）；
     - enrollment 已终止但 `enrollment_id` 与 intent 不一致 → **不删**；
     - `plan_id` / `session_id` 缺失但**无 L1 墓碑** → **不删**；
     - generation intent 的 `phase != Claimed` → **不删**；
     - **锁外读到 `Claimed`、锁内已是 `ProviderDispatched`** → **不删**（相位以锁内重读值为准）；
     - **锁外读到 L1 墓碑、锁内已变为进行中态 / 已出现 pending failure** → **不删**（证据以锁内重读值为准）；
     - 夹具：取代路径在 `metadata().is_ok()` 与 `remove_file()` 之间被销账插入 → 取代侧**不得**报 Io 失败（两路都持同一把 enrollment 文件锁）；
  7. **窗口 L2 四条件**：W-1..W-4 任一不成立 → **不删**（只报）；四条件齐备 → 删窗口簇（窗口 + 租约 + journal + 快照目录）；**按 attempt 聚合**——同一 attempt 名下有一个窗口不满足 → 该 attempt 下**全部**窗口（含归档）一个都不删；
  8. **墓碑零删除**：清理前后 `entity-deletions/**` 目录树逐文件校验和一致；
  9. **用户业务数据零删除**：story / design / plan 正文、versions、artifact 目录树逐文件校验和一致；
  10. 既有删除语义零回归：既有级联删除与删除准入用例全绿。
- **回滚**：revert 本步提交（**代码层面**）；**已执行的物理删除不可回滚** → 故闸 1 的确认令牌 + 先 dry-run 是唯一的保护；实施 Plan 必须写明这一点。

### 10.3 交界面与一致性约定

1. **共用判定能力**：W2 的「旧 source 悬空」判定与本设计的「目标已删」判定**应共用同一套目标存在性核对**（§3.1.1），避免两套口径漂移。已落地实现**自带判定**（`enrollment_source_dangling`），故以**该实现的判定口径为准**：story/design 的悬空判定 MUST 与之一致地**只判存在性**（版本/确认态漂移不算悬空、读取失败按未悬空处理）。本设计的 **L1/L2 证据分级只服务于 ③ 层销账**（决定「删不删」），MUST NOT 改变读侧与已落地实现的「悬空与否」口径。
2. **共用告警码**：本设计的告警码 `dangling_reference_target_missing` 是**全能力唯一**的悬空引用告警码；已落地实现若需要发同族告警，沿用该码 + 结构化字段，不另立码。
3. **记录边界**：enrollment 记录（`automation-enrollment.json`）的**重新授权与失效语义**归 W2/W3；本设计对它**只报不删**。intent 记录归本设计；两者不交叉。
4. **门禁边界**：③ 层销账**不删** enrollment 记录，因此不会与 W3 的「级联删除把 enrollment 一并失效」产生删除竞态（一个失效、一个保留）。
5. **实施顺序**：在途工作已合并（`dd62e5db`），本设计三步可即刻推进。第 1 步的判定能力若与已落地实现重合，须**以已落地实现为单一事实源**（见 §10.3.1）；第 3 步销账**不得早于**在途工作合并——该前置条件已满足（避免在 enrollment 语义未定时删 intent 造成中间态）。

### 10.4 承接的语义（写进 OpenSpec spec）

已落地变更裁定的「旧 source 悬空时按当前已确认 source 重新授权」这一语义，作为本能力的前提契约写入 spec：巡检与销账**必须**把「enrollment 的 source 指向已删 story/design」视为**已知的、已落地变更覆盖的**状态，不得把它判为「未归类」，也不得对 enrollment 记录执行删除。

同时承接已落地实现的**悬空判定口径**：story/design 的悬空 MUST **只判存在性**（实体仍在但版本/确认态漂移不算悬空），与 `enrollment_source_dangling` 逐条一致。本能力的 L1/L2 证据分级只用于 ③ 层「删不删」的判定，MUST NOT 参与「悬空与否」的判定。

> **r2 收窄（S1）**：「**读取失败按未悬空处理**」这条口径**只约束 enrollment 重新授权判定**（`enrollment_source_dangling`，`src/web/handlers/automation_enrollment_reenable.rs:144-168`）——它是该路径的 fail-closed 选择（保持既有 409，不放宽）。**它不得被当作通用规则**搬到巡检侧：巡检里若把读失败算成「未悬空」，悬空计数会自证归零 → **误报治理完成**。巡检侧另设**「不可判定」计数**（§3.3.3、§5.1），不为 0 时不得宣称归零。

## 1. 结论摘要

### 1.1 三个抱怨的实测根因（**均已定位到代码行**）

| 抱怨 | 实测根因 | 证据 |
|---|---|---|
| ① 生成慢、首 token 前 5-10 分钟无输出 | **不是探索慢**。16 次工具调用执行时间合计 **1.39 秒**；真正耗时是每轮开头烧 2,714→54,812 个 **thinking token**。机制根因：宿主 `~/.claude/settings.json` 的 `"effortLevel":"xhigh"` 被继承（仓库不传 `--effort`/`env_vars` 为空） | 基线 §11；本机 A/B 实测：`--effort xhigh` **300s 超时未完成**，`--effort low` **22.3s 完成** |
| ② IR 校验失败 → 教学重驱 | **一条 prompt 规则缺失**：`done_when_refs` 的合法域被教成「全局清单」，而校验器要求「**本 WI 内**」。run1 的 **15/15 条** `unknown_done_when_ref` **全部是跨 WI 引用**（cross-WI=15, same-WI=0，逐条交叉验证） | 基线 §9 |
| ③ reviewer 反复失败耗尽预算 | **本次未复现**（`run_history` 实测 `repairs_used=0 / transitions_used=1 / initial_review_count=1`）。但本次暴露了**更精确的机制**：reviewer **确实抓到了** run2 重写引入的真缺陷（finding #1 精确描述「依赖边存在而契约来源缺失」），却被 **`severity=suggestion` 门槛 + `class_hint=advisory` 双重降级**为提示，verdict 保持 `pass` | 基线 §16/§17 |

### 1.2 抱怨③ 的闭环（本次现场的完整因果链）

```
run1 生成 plan（16,516 字符）
  → IR 校验失败 15 条（全部跨 WI done_when 引用）
  → 教学重驱：prompt 只给「错误原文 + 规则」，不给上一版、不给 WI 定位
  → run2 整篇重写（run2 请求**确实携带** run1 完整原文 —— 铁证见 §5）
       重写引入新缺陷：CT 编号重排 / WI-004 丢失一个 input_contract / TASK 序号后移 / Traceability 三元组删除
  → reviewer 发现其中一条（finding #1，精确描述 WI-004 契约来源缺失）
  → 但 severity=suggestion + class_hint=advisory → 平台降级为提示 → verdict=pass
  → 缺陷放行，流向下游 coding
```

**⇒ 两个可分别修的断点**：① 缺陷**不产生**（不重写、不改坏）；② 缺陷**不漏过**（reviewer 能给 must_fix）。

## 2. 方案 A：引用域统一（抱怨② 的源头修复）

### 2.1 根因（因果对照，非巧合）

prompt 的引用规则**不对称**：

| 字段 | prompt 是否给「本 WI 内」限定 | 校验器实际作用域 | run1 实测越界 |
|---|---|---|---|
| `requirement_refs` | **有**（`sc_author_teaching.rs:108`：「必须在本 item 的 Traceability section 有对应登记行」） | 本 WI 的 `design_traceability` | **0** |
| `done_when_refs` | **无**（`:90`「仅引用先定义 criterion_id」= 文档序义；`:127`「逐字取自 `[design_requirements]` 清单」= 全局清单） | 本 WI 的 `acceptance_criteria` | **15/15** |

**⇒ 模型照 prompt 做必然失败**。这不是模型能力问题。

### 2.2 改法（**一条改动，两个侧面**）

1. **两个编号域在 prompt 里显式分开**：
   - spec 域（全局）：`[design_requirements]` 的 `REQ-*/NFR-*/AC-*` → 只用于 `requirement_refs` 与 `Traceability.requirement_id`；
   - plan 域（WI 本地）：本 WI `### Acceptance Criteria` 段声明的 `criterion_id` → 只用于本 WI 的 `done_when_refs` 与 `reviewer_check_refs`。
   - 措辞草案（替换 `sc_author_teaching.rs:90` 的歧义句）：
     > `done_when_refs` 只能引用本 Work Item 的 `### Acceptance Criteria` 段已声明的 `criterion_id`；引用其他 Work Item 的 criterion_id（即使该编号在全 plan 中存在）一律拒绝。
2. **plan 域改用独立命名空间**：前缀 **`WIC-`**（Work Item Criterion）。

**为什么是 `WIC-` 而不是 `WAC-`/`PAC-`**：`work_item_plan_policy/fingerprint.rs:145-154` 的
`stable_ids()` 用 `field.find(prefix)` **无 token 边界**，`"WAC-001"` 会被 `AC-` 匹配并抽出
`AC-001` → 与 spec 域 `AC-001` **指纹碰撞**。`WIC-` 不含 `AC-`/`WI-`/`CT-` 子串 → 安全。

### 2.4 裁决：删除 `forged_done_when` —— **采纳**

`single_candidate.rs:417-431` 的 `forged_done_when` 要求 `done_when_refs` 中以 `AC-` 开头的
引用**必须在 spec 清单内**（spec 域）；而 `validation.rs:256-270` 要求它**必须在本 WI 自己的
AC 集内**（plan 域）。两条同时生效 ⇒ 一个 plan 的 criterion 只能叫 spec 已有的 AC 编号。

本次两轮恰好都满足（plan 域编号 AC-001..AC-006 与 spec 域编号**巧合一致**），
所以该分支**从未触发**。但这是巧合，不是设计：若 spec 只有 3 个 AC 而 plan 需要 5 个
工作项级验收，或 plan 域编号与 spec 域任意错位，**合法的 plan 会被判为伪造**。

**裁决**：删除 `forged_done_when`，只保留 `forged`（查 `Traceability.requirement_id` ⊆ spec 清单）。
删除后两个检查的作用域终于一致，§2.1 的潜在缺陷消失。

**删除后 D1 由谁保证**：`validation.rs` 的逐 WI 校验（权威，平台侧）—— **不依赖** `forged_done_when`。

### 2.5 溯源语义造假：三层防御

命名隔离**不能单独**堵住「编号对得上但语义对不上」。基线 §10.2 实测：run1 的 6 条 Traceability
中 2 条**行为主体不同**（plan 说 busi 物理删除、spec AC-003 说的是前端成功流；plan 说网关 404、
spec AC-005 说的是前端错误提示）、2 条覆盖不足、**无一精确匹配**。平台防伪造只比对**编号字符串**
是否在清单内（`single_candidate.rs:406-434`），编号恰好都在清单内 ⇒ 通过。

| 层 | 手段 | 效果 | 代价 | 裁决 |
|---|---|---|---|---|
| **L1** | 命名隔离（`WIC-`） | 让「编号巧合」**不再可能**：plan 的 `criterion_id: WIC-003` 与 `requirement_id: AC-003` 是两个域 | 迁移成本（§2.3） | **采纳** |
| **L2** | prompt 侧 `[traceability_rule]` | 让造假**在文本上暴露**：要求登记前回到 spec 原文核对；显式写「**禁止按编号相近/顺序对应来登记**」。**spec 原文已在 prompt 内**（`[confirmed_context]` 的 story 段实测含 AC-001..AC-006 全文）⇒ **零探索成本** | ~330 字符 / ~600 字节；不改 grammar ⇒ **零解析器影响** | **采纳** |
| **L3** | 平台语义校验（比对 statement 关键词覆盖） | 机器判定 | 中文自由文本误判率高 | **不做**（可作 advisory warning，但不进硬 gate） |

### 2.6 验收

1. 跨 WI 引用**全局已存在**的 criterion → 仍失败；同 WI 引用 → 通过。
2. 本地合法 criterion **不在** spec AC 集合中时 → **不再被 `forged_done_when` 误拒**。
3. `requirement_refs` 未在本 WI Traceability 登记 → 仍失败；清单外源 requirement → 仍失败。
4. 命名隔离后核对 spec 引用**未被机械替换**为 plan criterion。
5. 用本次原始 story/design 重复生成，统计**跨 WI 引用发生率**与 **IR 教学重驱率**（目标：15 → 0）。

## 3. 方案 B/C/D：收敛性（抱怨②③ 的平台侧保障）

> 完整细节见 `cadence/analysis-docs/2026-11-08_WIG方案片段-收敛性_v1.0.md`。此处给裁决与要点。

### 3.1 方案 B —— 教学输入与诊断定位

**改法**：IR/compile 教学重驱 prompt 统一携带：

1. **上一版 source 全文 + 其 hash**；
2. **完整的 `code` / `field` / `line` / `message`** —— 当前 `format_compile_failure_reasons`
   （`single_candidate.rs:250-263`）只取 `code:line:message`，**丢掉了 `diagnostic.field`
   （= 出错的 WI id）**，且 `line` 恒为 `0`、`message` 不含 WI id
   ⇒ **模型拿不到「哪条错属于哪个 WI」**，这是整篇重写的直接诱因；
3. **从本轮 IR/AST 事实生成的 WI/task 定位与本 WI 合法 criterion 集**
   —— **不从 message 文本反解析**（`draft.rs:14-18` 会把 WI 与 contract/capability 引用
   合并进 `work_item_ids`，`field` 可能是 `AC-003,WI-001`，不能当单 WI 字符串）；
4. **允许修改的结构化字段闭包**；
5. 全 source 输出要求 + 最小改动约束。

**裁决：显式携带全文的理由**（必须写准，不能说成「补回缺失原文」）：

- 把权威修复基线**绑定到 source hash**，不依赖 provider 的会话历史保留策略；
- 在 fresh / resume / compaction / 不同 provider 间保持**同一契约**；
- 与方案 C 的保护器使用**完全同一份基线**（不出现两份「上一版」）；
- **本次 run2 的请求已携带 run1 完整原文**（铁证见 §5）⇒ 显式携带**不是**本次的唯一载体，
  **不能称其为「补回丢失的历史」**。

**明确成本**：本次会再增加约 **16,516 Unicode 字符**（应用层字符量；**不等于** token 或账单
增加 8.88 倍 —— resume 原本已有历史与缓存，provider 计量口径不同）。

### 3.2 方案 C —— IR 不变区硬检（**核心防护**）

**为什么需要**：本次 run2 的重写把 CT 编号重排、WI-004 丢掉一个 `input_contract`、
TASK 序号后移、Traceability 三元组删除，**全部无人拦截**。

**选层**：`compiler/lower.rs:17-30` 的 `PlanCandidateIr` / `PlanCandidateItemIr`
已 derive `PartialEq` ⇒ 可**逐字段结构化比对**，不需要文本 diff 比率、不需要第二套解析器。

**时机**：`converge_work_item_plan_source` 成功得到新 IR 后、候选 refs 提升与
`complete_single_candidate_work_item_plan_author` **之前**。

**基线必须分路径**（三类失败形态的可比性不同质）：

| 失败形态 | 正确基线 | 硬检适用 |
|---|---|---|
| IR 契约校验失败（本次） | handler 本轮**内存 IR**（compile 已成功，尚未落盘） | ✅ |
| reviewer 返修 | source store 的 durable `PlanCandidateIrRecord` | ✅ |
| parse/compile 语法失败（`missing_section`/`invalid_ears`/`invalid_work_item_id`） | **不存在旧 IR** | ❌ **不适用** |

**保护范围（未授权结构化变更阈值 = 0）**：WI 集/归属/kind/Plan Intent/依赖边；
TASK/CHECK/criterion ID 集及归属（既有 ID 禁止重编号）；CT 供需键
`(consumer WI, provider WI, contract_id)`；输入/输出能力与兼容策略；
task→requirement 与 task→criterion 引用边；handoff 的 required/provided/reviewer 引用；
Traceability 三元组；写域与验证命令等非自然语言字段。

**针对 `unknown_done_when_ref` 的最小允许闭包**：① 违规 task 的 `done_when_refs`；
② 必要的新本地 criterion（**新 ID，不移走/重编号既有**）；③ 对该新 criterion 的 reviewer check 追加。

**自然语言 statement 改写不进阈值** —— 本层**不声称证明语义不变**，只计量并交原 reviewer 判断。
prompt 仍要求逐字保持，但**平台承诺是「未授权结构化事实不变」，不是「所有自然语言字节不变」**。

**越权终态**（沿既有状态机，**不新增预算、不新增终态**）：
- IR 教学越权 → 沿 `single_candidate.rs:1363-1378` 既有失败路径落 `Failed` + `repair_scope_violation` 差分摘要；**不再 provider**；
- reviewer 返修越权 → 构造**单一 `HumanRequired` 平台结论**走 `route_outcome`
  （Interactive → `WaitingForHuman`；AutoIfValid → `StoppedNeedsHuman`）。
  **不可混入 Repairable findings** —— `evaluate.rs:349-389` 优先处理可修项，混合会意外再触发自动返修；
- 保留旧候选 refs，**拒绝提升越权新候选**。

**语法失败边界**：没有旧 IR 就不声称做了 IR 不变区硬检；无法证明保护域时**不新增自动重跑**。
首期只走「一次 compile 教学槽 + 原始 source + 完整诊断 + 精确 section 修正规则 → 修后全量编译」。

### 3.3 方案 D —— 机械安全补齐（**只做无歧义白名单**）

已有先例：`product/workspace_engine/contract_autorepair.rs:65-104`
`converge_work_item_plan_source`（≤8 轮、零 AI、规则版本治理）。

**可自动执行**（白名单）：
- `acceptance_criterion_without_reviewer_check`：在本 WI 的 handoff 中追加**已声明且唯一确定**的
  criterion ID —— 不生成新验收语义；
- 与已登记事实完全同一、仅重复缺失的结构字段。

**不可自动执行**（明确禁止）：
- 把未知 `done_when_ref` 映射到**数值最近**的本地 AC；
- 为消除报错而删除 task 的引用；
- 把另一个 WI 的验收移过来，或自动扩写验收语义；
- 编造/任选 Traceability 来源。

> 具体例证：本次 WI-001 的现有 AC 只覆盖「删除按钮」和「取消删除」，**不覆盖**成功删除/404 展示。
> 把 TASK-004 的 `AC-003` 改为本地 `AC-002`，虽然 membership 合法，却把「删除成功」验收降成
> 「取消不发请求」——**掩盖真实语义缺口**。

### 3.4 方案 E —— reviewer 输入面补齐与 severity 门槛

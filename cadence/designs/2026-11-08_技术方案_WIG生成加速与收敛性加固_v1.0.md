## 1. 结论摘要

### 1.1 三个抱怨的实测根因（**均已定位到代码行**）

| 抱怨 | 实测根因 | 证据 |
|---|---|---|
| ① 生成慢、首 token 前 5-10 分钟无输出 | **不是探索慢**。16 次工具调用执行时间合计 **1.39 秒**；真正耗时是每轮开头烧 2,714→54,812 个 **thinking token**（生成期长思考占 **87.6%**）。机制根因：宿主 `~/.claude/settings.json` 的 `"effortLevel":"xhigh"` 被继承（仓库不传 `--effort`，SC author 出口 `env_vars` 为空） | 基线 §11；本机 A/B 实测：`--effort xhigh` **300s 超时未完成**，`--effort low` **22.3s 完成**（**本机实测，跨环境复现性未验证**） |
| ② IR 校验失败 → 教学重驱 | **一条 prompt 规则缺失**：`done_when_refs` 的合法域被教成「全局清单」，而校验器要求「**本 WI 内**」。run1 的 **15/15 条** `unknown_done_when_ref` **全部是跨 WI 引用**（cross-WI=15, same-WI=0，逐条交叉验证） | 基线 §9 |
| ③ reviewer 反复失败耗尽预算 | **本次未复现**（`run_history` 实测 A/B 两池 `repairs_used=0 / manual_repairs_used=0`、`initial_review_count=1`）。但本次暴露了**更精确的机制**：reviewer **确实抓到了** run2 重写引入的真缺陷（finding #1 精确描述「依赖边存在而契约来源缺失」），却被 **`severity=suggestion` 门槛 + `class_hint=advisory` 双重降级**为提示，verdict 保持 `pass`；且 reviewer prompt 里 `handoff_contract`/`reviewer_check_refs`/`design_traceability` **出现 0 次** ⇒ 它**结构上无法**核对 AC 配对与溯源 | 基线 §16/§17 |

> ⚠️ **措辞限定（经双审）**：「本次未复现」严格限定为「**A 池与 B 池**未耗尽」——
> handler 内的**通道 C**（教学重驱槽）**不计入任何池**，其一次 provider 重驱在预算口径上是「免费」的
> ⇒ **不能说「任何预算都未耗尽」**。详见 §3.5 的 G-03。

### 1.2 抱怨③ 的闭环（**本次现场**的可观测机制）

```
run1 生成 plan（16,516 字符）
  → IR 校验失败 15 条（全部跨 WI done_when 引用）
  → 教学重驱：prompt 只给「错误原文 + 规则」，不给上一版、不给 WI 定位
  → run2 整篇重写（run2 请求**确实携带** run1 完整原文 —— 铁证见 §5）
       重写引入新缺陷：CT 编号重排 / WI-004 丢失一个 input_contract / TASK 序号后移 / Traceability 三元组删除
  → reviewer 发现其中一条（finding #1，精确描述 WI-004 契约来源缺失）
  → 但 severity=suggestion + class_hint=advisory → 平台降级为提示 → verdict=pass
  → 缺陷放行，流向下游 coding
```

**⇒ 两个可分别修的断点**：① 缺陷**不产生**（不重写、不改坏）；② 缺陷**不漏过**（reviewer 能给 must_fix）。

> ⚠️ **断言强度限定（经双审）**：上链是「**本次现场**」的可观测机制，
> **不是**「用户所述『reviewer 反复失败耗尽预算』那个现场的机制」——那个现场本次**无证据**
> （本次 reviewer 只跑 1 轮且判 pass；A/B 两池未耗尽）。
> 本方案只对**本次现场**的机制下结论；用户所述现场需其 durable history 才能定性。
> 措辞上，§1.1 与本节标题的限定已前移（原文只在 §10-1 出现过该限定）。

## 2. 方案 A：引用域统一（抱怨② 的源头修复）

### 2.1 根因（因果对照，非巧合）

prompt 的引用规则**不对称**：

| 字段 | prompt 是否给「本 WI 内」限定 | 校验器实际作用域 | run1 实测越界 |
|---|---|---|---|
| `requirement_refs` | **有**（`sc_author_teaching.rs:108`：「必须在本 item 的 Traceability section 有对应登记行」） | 本 WI 的 `design_traceability` | **0** |
| `done_when_refs` | **无**（`:90`「仅引用先定义 criterion_id」= 文档序义；`:127`「逐字取自 `[design_requirements]` 清单」= 全局清单） | 本 WI 的 `acceptance_criteria` | **15/15** |

**⇒ 模型照 prompt 做必然失败**。这不是模型能力问题。

### 2.2 改法（**一条改动，两个侧面**）

1. **两个编号域在 prompt 里显式分开**：
   - spec 域（全局）：`[design_requirements]` 的 `REQ-*/NFR-*/AC-*` → 只用于 `requirement_refs` 与 `Traceability.requirement_id`；
   - plan 域（WI 本地）：本 WI `### Acceptance Criteria` 段声明的 `criterion_id` → 只用于本 WI 的 `done_when_refs` 与 `reviewer_check_refs`。
   - 措辞草案（替换 `sc_author_teaching.rs:90` 的歧义句）：
     > `done_when_refs` 只能引用本 Work Item 的 `### Acceptance Criteria` 段已声明的 `criterion_id`；引用其他 Work Item 的 criterion_id（即使该编号在全 plan 中存在）一律拒绝。
2. **plan 域改用独立命名空间**：前缀 **`WIC-`**（Work Item Criterion）。

**为什么是 `WIC-` 而不是 `WAC-`/`PAC-`**：`work_item_plan_policy/fingerprint.rs:145-154` 的
`stable_ids()` 用 `field.find(prefix)` **无 token 边界**，`"WAC-001"` 会被 `AC-` 匹配并抽出
`AC-001` → 与 spec 域 `AC-001` **指纹碰撞**。`WIC-` 不含 `AC-`/`WI-`/`CT-` 子串 → 安全。

### 2.4 裁决：删除 `forged_done_when` —— **采纳**

`single_candidate.rs:417-431` 的 `forged_done_when` 要求 `done_when_refs` 中以 `AC-` 开头的
引用**必须在 spec 清单内**（spec 域）；而 `validation.rs:256-270` 要求它**必须在本 WI 自己的
AC 集内**（plan 域）。两条同时生效 ⇒ 一个 plan 的 criterion 只能叫 spec 已有的 AC 编号。

本次两轮恰好都满足（plan 域编号 AC-001..AC-006 与 spec 域编号**巧合一致**），
所以该分支**从未触发**。但这是巧合，不是设计 —— **作用域冲突是双向的**：

| 方向 | 条件 | 后果 |
|---|---|---|
| **正向误拒** | spec 只有 3 个 AC 而 plan 需要 5 个工作项级验收 | `validation.rs` 通过（WI 本地有 5 个），但 `forged_done_when` 要求 done_when ⊆ spec 的 3 个 ⇒ **合法的 plan 被判为伪造** |
| **反向误拒** | 某 WI 的本域 criterion 编号不在 spec 清单内（如 `AC-007`） | `validation.rs` 通过（本 WI 自洽），但 `forged_done_when` 判其不在 spec 清单 ⇒ **同样误拒** |

⇒ 两个方向都会**误拒合法 plan**，而两个校验的**作用域本就相反**
（一个要求 WI 本地、一个要求 spec 全局）。删除是唯一自洽解。

**裁决**：删除 `forged_done_when`，只保留 `forged`（查 `Traceability.requirement_id` ⊆ spec 清单）。
删除后两个检查的作用域终于一致，§2.1 的潜在缺陷消失。

**删除后 D1 由谁保证**：`validation.rs` 的逐 WI 校验（权威，平台侧）—— **不依赖** `forged_done_when`。

### 2.5 溯源语义造假：三层防御

命名隔离**不能单独**堵住「编号对得上但语义对不上」。基线 §10.2 实测：run1 的 6 条 Traceability
中 2 条**行为主体不同**（plan 说 busi 物理删除、spec AC-003 说的是前端成功流；plan 说网关 404、
spec AC-005 说的是前端错误提示）、2 条覆盖不足、**无一精确匹配**。平台防伪造只比对**编号字符串**
是否在清单内（`single_candidate.rs:406-434`），编号恰好都在清单内 ⇒ 通过。

| 层 | 手段 | 效果 | 代价 | 裁决 |
|---|---|---|---|---|
| **L1** | 命名隔离（`WIC-`） | 让「编号巧合」**不再可能**：plan 的 `criterion_id: WIC-003` 与 `requirement_id: AC-003` 是两个域 | 迁移成本（§2.3） | **采纳** |
| **L2** | prompt 侧 `[traceability_rule]` | 让造假**在文本上暴露**：要求登记前回到 spec 原文核对；显式写「**禁止按编号相近/顺序对应来登记**」。**spec 原文已在 prompt 内**（`[confirmed_context]` 的 story 段实测含 AC-001..AC-006 全文）⇒ **零探索成本** | ~330 字符 / ~600 字节；不改 grammar ⇒ **零解析器影响** | **采纳** |
| **L3** | 平台语义校验（比对 statement 关键词覆盖） | 机器判定 | 中文自由文本误判率高 | **不做**（可作 advisory warning，但不进硬 gate） |

### 2.6 验收

### 3.1 方案 B —— 教学输入与诊断定位

**改法**：IR/compile 教学重驱 prompt 统一携带：

1. **上一版 source 全文 + 其 hash**；
2. **完整的 `code` / `field` / `line` / `message`** —— 当前 `format_compile_failure_reasons`
   （`single_candidate.rs:250-263`）只取 `code:line:message`，**丢掉了 `diagnostic.field`
   （= 出错的 WI id）**，且 `line` 恒为 `0`、`message` 不含 WI id
   ⇒ **模型拿不到「哪条错属于哪个 WI」**，这是整篇重写的直接诱因；
3. **从本轮 IR/AST 事实生成的 WI/task 定位与本 WI 合法 criterion 集**

4. **允许修改的结构化字段闭包**；
5. 全 source 输出要求 + 最小改动约束。

**裁决：显式携带全文的理由**（必须写准，不能说成「补回缺失原文」）：

- 把权威修复基线**绑定到 source hash**，不依赖 provider 的会话历史保留策略；
- 在 fresh / resume / compaction / 不同 provider 间保持**同一契约**；
- 与方案 C 的保护器使用**完全同一份基线**（不出现两份「上一版」）；
- **本次 run2 的请求已携带 run1 完整原文**（铁证见 §5）⇒ 显式携带**不是**本次的唯一载体，
  **不能称其为「补回丢失的历史」**。

**明确成本**：本次会再增加约 **16,516 Unicode 字符**（应用层字符量；**不等于** token 或账单
增加 8.88 倍 —— resume 原本已有历史与缓存，provider 计量口径不同）。

### 6.5 缓存 TTL —— run2 缓存未命中的**真实根因是 TTL 而非前缀不稳定**

**实测**：11 次请求**每次都**在 `system[0]`、`system[1]` 与**最新一条 message** 上放
`{"type":"ephemeral"}` 断点 ⇒ **CLI 侧自动管理 prefix caching，静态前缀天然可缓存，
adapter 无需（也无法）传 cache_control**（全仓 grep 在 `claude_code_provider/` 零命中）。

**run2 未命中的原因**：
- run1 末次请求 → run2 请求间隔 **11.0 分钟**；
- CLI 缓存 TTL 默认：「`5m` or `1h`. **Unset = automatic**: 1 hour on a Claude subscription…
  **5 minutes on an API key**, Bedrock, Vertex or Foundry」；
- 本次接入 `ANTHROPIC_BASE_URL=http://127.0.0.1:3425` + `ANTHROPIC_AUTH_TOKEN=magpie`
  ⇒ **API key 形态 ⇒ 5 分钟 TTL**；
- 实测 run2 `cache_read=128`（run1 末轮 157,824）、`in=90,486`（run1 末轮 35,773）
  ⇒ **整段上下文按未缓存全量重发**。

**改法**：注入 `CLAUDE_CODE_PROMPT_CACHE_TTL=1h`。
**风险**：1h cache write 单价高于 5m；且本次 11 次请求的 `cache_creation_input_tokens`
**恒为 0**（cache write 计数未被该 provider 透传）⇒ **价差无法从本地数据核算，净收益需实测**。

> **owner 2026-11-11 裁决：G-6（缓存 TTL 1h）本期不设。**
> 方向性推理（**不是结论**）：**重驱场景净收益为正**（run2 间隔 11 分钟 > 5 分钟，命中 1h 缓存省下一次
> 90,486 token 的全量重发，量级大于抬一次 write 档的代价）；**短间隔场景净亏**（5 分钟内的连续调用
> 本来就命中 5m 缓存，1h 只把 write 单价抬上去）。净效果取决于**调用间隔分布**，而本地算不出这个

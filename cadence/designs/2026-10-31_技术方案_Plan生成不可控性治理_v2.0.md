## 0. 一句话结论

owner 撞的墙**不是**「模型写不好一百条规则」，而是：

> **同一件事（哪个 Work Item 属于哪个仓、谁必须先做）被写了两份 —— 模型在 markdown 里写一份，平台编译时自己又算一份 —— 而这两份只在最后一步才对账。对不上就报「依赖成环」，然后把人叫过来。可是平台那份是平台算的，让模型重写一百遍也不会变。**

上一版（v1.0）把主因排在「prompt 太重、责任错配」，把「两套图不一致」列为**待证伪假设**放在 P1。本轮用真实现场数据把这个假设证成了，而且比 v1 设想的更具体：**它是本树里的一个确定的分支不对称，不是"可能漂移"**。所以优先序必须反过来。

## 1. Q1：为什么会搞得如此复杂（给 owner 看，不用技术词）

### 1.1 一句话心智模型（能记住、能转述）

> **平台手里有一张"施工总平面图"（哪个仓先动工、哪个仓后动工），模型手里有一张"房间图"（每个仓里具体改什么）。问题是：这两张图从来没有同时摊在桌上。模型画房间的时候看不到总平面；平台验收的时候才把总平面叠上来。一叠，墙撞了。平台说"你重画"，模型重画 —— 而它仍然看不到总平面。**

### 1.2 用你这次的真实案例讲一遍（数据来自现场，不是假设）

这次需求是「公告删除」，三个仓：`busi`（后端）、`gateway`（网关）、`frontend`（前端）。设计文档里写明了先后：**先 busi → 再 gateway → 最后 frontend**。

模型生成了 4 个 Work Item：

| Work Item | 在哪个仓 | 它依赖谁 |
|---|---|---|
| WI-001 | busi（第 1） | 无 |
| WI-002 | gateway（第 2） | WI-001 |
| WI-003 | frontend（第 3） | WI-002 |
| WI-004「端到端验收」 | **gateway（第 2）** | WI-001、WI-002、**WI-003** |

平台在最后一步做的事是：按设计里写的仓序，**自动**给「后仓」的每个 Work Item 补一条「依赖前仓所有 Work Item」的线。这次一共补了 **5 条**：

- busi → gateway：WI-001 → WI-002、WI-001 → WI-004
- busi → frontend：WI-001 → WI-003
- gateway → frontend：WI-002 → WI-003、**WI-004 → WI-003**

而模型自己写的那条是 **WI-003 → WI-004**（WI-004 把 WI-003 写成 provider）。两条方向相反的线一合成，就是一个圈：`WI-003 → WI-004 → WI-003`。

**这个冲突平台完全能自己算出来**：平台知道仓序，知道 WI-004 依赖了哪三个仓，一眼就能看出「WI-004 托管在仓序第 2，却要消费仓序第 3 的产出」在仓序规则下不可能成立。它还能算出两个都能消环的修法：

1. **去掉 WI-004 对 WI-003 的那条消费** —— 后果：端到端验收不再覆盖前端交互；
2. **把 WI-004 连同它那个测试文件一起迁到第 3 个仓** —— 后果：写范围与命令都要改，测试改由最后一仓执行。

它没有算，也没有给你这两个选项，而是把这条规则写进 3 万字的说明书让模型去记住，最后只在终点报一句「依赖环」，再把责任推给 design。

> 平台**不能**替你在这两个修法里选一个 —— 因为 WI-004 的写范围在 `gateway/src/test/…`，只挪托管仓会让写范围越界；只删消费会让验收覆盖变窄。这是业务取舍，得你定。但"要你定"和"让你猜"是两件事：前者是两个选项，后者是一句「依赖环」。

**更糟的是：review 阶段说"没问题"。** review 之前那道结构检查用的是另一套图 —— 那套图里，这 4 个 Work Item 全都没有被识别出「属于哪个仓」，于是平台**一条仓序线都没补**，图上没有圈。所以 review 写的是「4 个 WorkItem 构成无环拓扑、机械校验 0 error」。等 review 通过、平台跑最终编译，这次它认出了仓，补上了 5 条线，圈出现了。

这就是你看到的「**写 plan 成功了，review 之后直接出错，说让人工处理**」。

**还有一件事必须说清**：这次现场里，平台**并没有真的去自动重写**。时间线显示：最终编译 04:19:59.9 开始、0.14 秒就失败；0.09 秒后冒出一个「Review Round 2」节点（0.14 秒结束、没有产出任何内容）；再过 0.15 秒就出现「需要人工接管」，0.06 秒后是「人工确认」。**全流程 0.67 秒，中间没有任何一次 author 重写**。也就是说"平台会先自动帮你改几次"这句承诺，在这个案子里一次都没兑现 —— 具体原因尚未定位，已列为验证项（§9.1-6）。

### 1.3 现在你看到的 vs 应该看到的

| 时刻 | 现在你看到的 | 应该看到的 |
|---|---|---|
| 生成 plan | `lowering_error:0:Plan Intent 声明在场时该字段必填。` —— 一句机器话，你不知道该改哪、为什么 | 什么都不用你管：平台按成员表自己补上归属，只留一行可展开的「已自动补全：WI-001~004 的目标仓」 |
| review | 「4 个 WorkItem 构成无环拓扑」—— 给了你一个**会被下一步推翻**的结论 | 不会出现自相矛盾的两句话：要么一次说清"合法"，要么一次说清"哪条线逆了仓序"并给两个可选修法 |
| review 通过后的最终编译 | 「最终编译失败，需要人工接管……根因可能在 design 的依赖顺序/仓序，需要你决定是否修改 design」 | 不会发生。这类环在生成阶段就算出来了 |
| 需要你决定时 | 一句话祈使句，没有选项、没有后果说明（这次实测的失败卡里 `owner_question`/`owner_options` 都是空的） | **一个问题 + 2~3 个选项 + 每个选项的后果**，答完就往下走 |
| 平台说"会自动重写"时 | 0.67 秒内直接落到人工门，一次重写都没发生 | 要么真的重写一次，要么一开始就说清"这一步需要你" |

### 1.4 复杂度到底来自哪：四个来源，按本案影响从大到小

你问「为什么这么复杂」，答案不是一百条规则，是这四个：

| 序 | 来源 | 在本案里的具体样子 | 实测数字 |
|---|---|---|---|
| **A** | **同一个事实写两份，且两套判定** | 「这个 Work Item 属于哪个仓」：模型写一份，平台编译时又反查一份；review 前那道检查只认后者、还要额外条件才认，最终编译认得更全 → 两套结论 | 3 个仓、4 个 Work Item；平台自动补 **5 条**跨仓线，模型只需对其中 **1 条**（WI-003→WI-004）负责，却必须同时预判另外 5 条会被补上 |
| **B** | **失败后要么整篇重写、要么直接叫人** | 唯一的"精确修复"能力只覆盖 4 类机械缺口；编译类失败只能整篇重写；而本次**连整篇重写都没发生**，0.67 秒直落人工门 | 重写预算 3 次（`work_item_plan_policy/types.rs:229`），本案用掉 1 次标称、实际 0 次作者调用；`repeated: 1` 意味着同一个环第二次出现就停 |
| **C** | **"一次就要写对"的规则条数（而且自相矛盾）** | 见下面细则 | 14 个固定小节、**40 个**白名单 key、**23 个**枚举取值；固定教学块 ≈15.5K 字符；prompt 实测 **31,229** 字符 |
| **D** | **机器判不了的、判错的都塞给人** | 「需要人工接管」那张卡只给祈使句，没有选项、没有后果；而它给出的原因（"根因在 design"）在本案是**错的** | 本次失败卡的 `owner_question` / `owner_options` 均为空（`compile_failure_surface.rs:120-160` 构造处硬写 `None`） |

C 的细则（全部可复核，`src/product/work_item_plan_compiler/grammar.rs`）：

- 固定小节 **14** 个（`STRUCTURED_SECTIONS`）
- 白名单 key **40** 个（`STRUCTURED_KEYS`，未知 key 一律 fail-closed）
- 值域枚举合计 **23** 个（`kind` 7 + `compatibility_policy` 2 + `intent` 2 + `required_evidence` 4 + blocker `route` 8）
- prompt 硬性措辞三个口径（不冲突、别混用）：固定教学块 ≈63 处（v1.0 口径）／对**本次实际 prompt** 逐块计数 **117 处**、其中**结构契约类 ≈57 处**（语法教学 46 + 成员/写范围/格式 11）／整个 prompt **构造源** 208 处（含修订路径）
- 本次实际 prompt：`work-item-split-runs/<session>/1/run.json` 的 `prompt_chars: 31229`

**C 里最要命的是自相矛盾**：`prompts/sc_author_teaching.rs:41` 说「`intent_target_kind=single_repository` 时必写 `intent_target_repo`，**逐字取 `[issue]` 头 `repo=` 的 repository id**」；同一文件 `:253` 又说「LC 多仓限定：**不取 `[issue]` 头 `repo=`**，改为逐字取成员表里的物理成员仓 ID」。同一个字段，两句话给了两个取值来源。而 `:41` 甚至逐字印着那句报错的原文「Plan Intent 声明在场时该字段必填。」—— **规则就写在说明书里，模型照样踩，说明"再写一遍规则"这条路已经用尽了。**

## 3. 根因：一份事实、两份表达、两套判定

### R1 双份表达（A 的主因）

「这个 Work Item 属于哪个仓」有三个替身：

1. markdown 的 `Plan Intent`（模型写）
2. IR 的 `target_repository_id`（`lower.rs:283-393` 解析出来的**物理**仓 ID）
3. 结构门期待的 `logical_target`（**逻辑**成员 UUID）

第 2 与第 3 之间没有同一个反查函数：`finalizer` 有 `reverse_logical`（F8），`plan_projection` 没有（F6）。**同一个物理仓 ID，在一条链上被认成"成员"，在另一条链上被认成"未知"。**

### R2 两套判定（A 的放大器）

- 候选门：`canonical_input` + `change_order`（F5），但仓序边只对 `logical_target` 非空的项生效（F6）→ 本案 **0 条**仓序边（物证 D8：5 条边全是 canonical、`order_indices` 全空）→ 无环 → `Accepted`（F9）
- 终编译：`input_contracts` 推出的依赖 + `change_order` 全量边（F4 + F8）→ **5 条**仓序边 → 成环

**结论（可复核、可复现，不需要任何模型参与）**：同一份候选，在 A 判定下合法、在 B 判定下非法。

### R3 失败后既没有精确修复，也没有真的整篇重写（B）

- 精确修复只覆盖 4 类机械缺口；编译类失败只能整篇重写（F11）
- 而本次连整篇重写都没发生（D6）：0.67 秒直落人工门。**「平台会自动改几次」这句承诺在本次没有兑现**，原因未定位（§9.1-6）
- 环的修复本质是**一个语义决定**（去掉消费 / 迁移托管仓 + 测试），现有指引给的是 4 条通用原则，没有算出选项

### R4 消息把责任指向 design（D 的主因）

`owner_hint`（`compile_failure_surface.rs:370-389`）断言「根因指向 design……需要**修改 design 的依赖顺序/仓序**」。本案 design 仓序正常（D2/D3/D5），错在 plan 的 WI-004 托管仓。**这不是措辞问题，是事实错误**，必须由 witness 计算得出，不能写死。同时失败卡没有任何选项（D10）。

## 4. Q2（本轮核心交付物）：work item group 链上，「平台已知 / 平台能推 / 该问模型」

### 4.1 三类定义

- **平台已知**：生成 prompt 时平台手里**已经**有这个值。模型写它 = 纯抄写风险，平台自己填。
- **平台能推**：值不由模型发明，但能从别的结构**唯一算出**（唯一解，不需要选）。平台算。
- **该问模型/你**：业务内容。**只有这一类留在 markdown 里。**

### 4.2 40 个白名单 key 逐条归位（本轮最重要的表）

> 归位口径刻意保守：**宁可少报，不能虚报**。凡是需要业务判断、或违反既有"不得造证据/不得臆造命令/不得代填声明"纪律的，一律留在模型侧。

**① 平台已知 → 平台填，模型不写（15 个）**

| key | 平台凭什么知道 |
|---|---|
| `schema_version` | 常量（当前 `1`） |
| `logical_work_item_id` | 由 `## Work Item WI-00x` 标题派生 |
| `intent_target_kind` | 成员表在场 → `logical_codebase`；单仓 → `single_repository` |
| `intent_target_codebase` | = 该 issue 绑定的 logical codebase id |
| `intent_target_repo` | 成员表 `logical→physical` 映射（经写范围前缀定位） |
| `intent_target_logical_repo` | 成员表反查（成员 UUID） |
| `contract_id` / `task_id` / `criterion_id` / `check_id` | 全局序号（4 个 key） |
| `compatibility_policy` | 默认 `require_all` |
| `source_type` / `source_id`（Traceability） | 被引用对象类型与 spec id，平台装载（2 个 key） |
| `required` | 默认 `true` |
| `non_zero_test_execution_required` | 由 check 性质决定 |

**② 平台能推 → 平台算（2 个）**

| key | 唯一解算法 |
|---|---|
| `provided_contract_refs` | = 本 WI 契约被下游 Inputs 消费的集合（反向索引，平台已有全图） |
| `required_fields` | 由 Outputs + AC 摘要派生 |

**②′ 待裁决（1 个）**

| key | 争议 |
|---|---|
| `reviewer_check_refs` | 本 WI 内 AC×check **一一对应**时可唯一确定 → 平台补引用；但 v1.0 认为属语义判断、一律不补。**见 §9.2-X1，未定，本版不据此承诺** |

**③ 该问模型/你（22 个）**

| key | 为什么必须问 |
|---|---|
| `intent`（create/existing） | 是业务声明（是否新建基线外文件）；**既有契约明文禁止平台代填**（F15） |
| `provider_work_item_id` | 与 `intent` 同段同源，随 `intent` 一起由模型写 |
| `title` / `summary` / `non_goals` | 业务语义与边界 |
| `kind` | 「要不要一个 integration/验收类 WI」是业务取舍；平台只做「与目标仓类型是否矛盾」的一致性校验 |
| `depends_on` | **同仓内**顺序（跨仓边由平台持有，见 §4.3） |
| `provider_logical_work_item_id` | 「消费上游哪条能力」是业务语义，平台不能代写 |
| `capabilities` / `required_capabilities` | 业务契约措辞 |
| `statement`（Tasks / Acceptance Criteria 共用） | TDD 步骤与验收语义 |
| `requirement_refs` / `done_when_refs` / `requirement_id` | 从清单里**挑哪几条**（3 个 key） |
| `exclusive_scopes` | 要改哪几个文件，只有读过代码的人知道 |
| `forbidden_scopes` | 业务禁区（如 `db/migration/**`、`package.json`、`dto/**`）；平台只额外补「其他成员目录 `xxx/**`」 |
| `required_evidence` | 证据强度是判断 |
| `command` | 跑什么目标（如是否 `-DskipITs`）是判断；平台可给"候选命令清单"，但不得臆造 |
| `manual_instruction` | 人工验收步骤与提示文案 |
| `reason_code` / `route` | blocker 的语义取舍（2 个 key） |
| `target_contract_refs` | 引用哪几个契约 |

**合计：平台确定拿走 17 / 40（① 15 + ② 2），另 1 项待裁决，22 项仍是业务内容。**

### 4.3 每条"平台已知"的前置条件（别把"能填"当"随便填"）

1. **`intent_target_*` 四 key 的派生不是"把已有能力提上来"，而是需要新增接线。** 现状 `PlanMemberTargets`（`lower.rs:47-53`）只有 `physical_by_logical` + `fallback_physical_id`，**没有 checkout 目录前缀表**；前缀表只在写范围校验期才被传入（F14）。要让 lowering 按 `exclusive_scopes` 前缀反查目标仓，必须先把前缀表接进 lowering 上下文，并对「跨成员 / 无前缀 / 前缀不唯一」做 typed 拒绝。
2. **`### Plan Intent` 段不能简单"允许省略"。** 现状省略 → `None` → 落 `fallback_physical_id`（change_order 首仓），**静默把所有 WI 归到第一个仓**（F12），随后才在写范围处撞墙。所以"退役"必须与第 1 条的派生能力同时上线，否则会制造新的静默错归属。
3. **`intent` / `provider_work_item_id` 不能由平台代填。** F15 明文禁止系统自动补声明。若将来要动，必须单独开 MODIFIED 并拿 owner 裁决，不得夹在本 change 里。
4. **成员表为空（legacy 单仓）时以上全部不生效**，走原语义（`plan_projection.rs:1044-1052` 保持不动）。
5. **托管仓不是唯一解**：WI-004 的写范围在 `gateway/`，只改 target 会 `write_scope_outside_bound_repository`（`write_scope_bound.rs:110-148`）。所以平台只能给选项。

### 4.4 这张表回答了「怎么把不可控性降下来」

平台确定拿走 **17 / 40** 个 key，其中 **4 个（`intent_target_*`）正是形态一（写 plan 直接出错）的唯一来源**（F2/F3）；另有 2 个（反向索引类）是纯推导。剩下 22 个才是真正需要模型/你的业务内容。

更重要的是**结构的归属**：跨仓边由平台持有（F4），平台只需在"模型写的 Inputs 方向与仓序冲突"时**检出并给选项**（不是代写 Inputs）。这样模型**不再需要知道 `change_order` 的存在**，prompt 里那一整段仓序教学在语义上就失效了 —— 它保留的唯一理由是现在的代码还要求模型自己写对。

## 5. Q3：上一版是不是过度设计

### 5.1 方向对，优先序错（三条具体问题）

| 上一版 | 本轮判断 | 理由 |
|---|---|---|
| 主因排序：责任错配 > 通道错位 > 图模型漂移（R4 排第 4） | **错**：图模型漂移是本轮「review 通过后出错」的**唯一**机械成因（F6 vs F8，物证 D8），且是纯代码不对称、零风险可修 | D4/D5/D8：same artifact，两种结论 |
| 把 §6「图漂移」写成「先证伪再修」，只做奇偶性测试 + 登记缺陷单 | **太保守**：已证成。继续"先登记后修"会让 owner 多等一轮 | 证伪所需 fixture 就是 D2 的形态 |
| P0 只处理 lowering（形态一） | **不完整**：owner 两种形态都见过，P0 完全没碰形态二 | 形态二体感最差（review 看起来成功） |

### 5.2 四层（L0/L1/L2/L3）是不是把问题复杂化了

**是。作为"分类语言"它是对的，但作为"实施单元"它过重。**

1. **四层在代码里已经存在**：`PlanningFailureKind` + `classify_failure_set` + `PlanningRecoveryDisposition`（`src/product/planning_failure.rs:60-130`、`:404`+）已经在做同一件事。v1 的 L0-L3 是给它们**再起一套名字**；实施时会出现"两套词汇指同一制"，这正是 owner 现在"听不懂"的一部分。
2. **真正要动的只有三处**（§7），都不需要新的层概念。
3. **更简的一刀确实存在**：**「平台持有跨仓结构，模型只填业务内容」**。v1 把这件事拆成 L0/L1/L2 三个层 + 三个 P 阶段，实施成本高得多。

### 5.3 上一版没针对 work item group 专项，算不算漏

**算漏，而且漏的正是 owner 最大的痛点。** 多仓绑定是唯一一处"同一个事实有两个代码替身"、也是唯一一处"review 和终编译用两套规则"的地方；单仓 plan 不走这条链。所以专项不是锦上添花，而是根因所在。

### 5.4 v1 的 P0-a / P0-b 能不能解决「work item group 一直过不去」

- **P0-a（缺 key 时等价解析）**：只覆盖形态一的一部分；**对形态二完全无效**。
- **P0-b（lowering typed fault + 教学重驱）**：让形态一在终态前多一次重试机会，但治的是"能不能重试"，不是"为什么要重试"；同一类错重复时只是把终态延后。
- 结论：**v1 的 P0 只能让形态一"不那么容易死"，形态二的死路原封不动。**

### 5.5 修正后的优先序

1. **P1（先做）**：target 反查同源 + 奇偶性测试 —— 消灭"review 通过后编译失败"
2. **P1+（可并行、0.3 人日）**：删掉 prompt 里互斥取值来源中的一句（纯文案）
3. **P2**：`Plan Intent` 的 target 4 key 平台派生（含前缀表接线）—— 消灭形态一整类
4. **P3**：witness → 2~3 个可执行选项与位次，替代"通用 4 条原则 + 整篇重写"
5. **P4**：prompt 去矛盾 + 瘦身（31K → ≤12K），并加计量测试锁上限
6. **P5**：一次答完（`owner_question` + `owner_options`），只给真正需要 owner 的事

## 6. Q4：三条不同量级的路线

### 路线 A（最简，改动最小、体感改善最大）── **推荐先落地**

- **核心机制（一句）**：让候选门和终编译用**同一个**「物理仓 → 逻辑成员」反查函数，并把误导文案换成 witness 事实 + 两个选项。
- **owner 侧体感**：「review 说没问题、最终编译才报错」这个形态**消失**（环在生成阶段就被算出）；即使用户仍被叫到门前，看到的是「哪两个 Work Item 逆了仓序」+ 两个可选修法，而不是"去改 design"。
- **代价**：**1～1.5 人日**（一个函数 + 一处调用点 + 一个 parity 测试 + 一段文案）。
- **可拆出的 A+（0.3 人日，纯文案，可先单独发）**：删掉 `sc_author_teaching.rs:41` 与 `:253` 互斥取值来源中的一句。这是形态一（`c131b519`）在 prompt 侧的唯一成因，且与后续退役路线不冲突。
- **风险**：此前"侥幸放行"的候选会在生成阶段失败（这是目的），需观测首次通过率。
- **能否单独落地见效**：**能，不依赖 prompt 改造、不消耗 provider 轮次。**

### 路线 B（推荐目标态，5～7 人日）

- **核心机制（一句）**：A + `Plan Intent` 的 target 4 key 平台派生（含前缀表接线）+ 环的**精确选项**（witness → 位次 + 两个修法）。
- **owner 侧体感**：形态一整类消失（不再看到 `lowering_error`）；形态二变成「首轮带选项的精确指令，同一个环重复则升级成一次选择」。
- **代价**：5～7 人日。其中 lower 派生 + 上下文接线 + 测试 **≥2.5 人日**（不是"把已有能力提上来"：`PlanMemberTargets` 缺前缀表，F14），精确选项 1.5 人日，prompt 去矛盾 1 人日，回归 1 人日。
- **不承诺收敛率**：选 A1/A2 是语义取舍，平台不能保证一次重写就好。**并且 owner 的选择当前存不住** —— `HumanFindingDispositionKind` 只有 `Excluded` 一个变体（`models/human_gate.rs:141-145`），要记住"选了 A1 还是 A2"必须新增 `Decided{option_id}`，属独立工作项。
- **风险**：`lower.rs` 改动触及单仓语义 → 必须 fail-closed 兜底；「允许省略 Plan Intent」必须与派生能力同时上线，否则落入 F12 的静默归属首仓。
- **能否单独落地见效**：能，但建议在 A 之后（A 先把两套图对齐，B 才有可靠判定面）。

### 路线 C（重，9～12 人日）

- **核心机制（一句）**：B + **平台生成跨仓骨架**（仓分配建议、编号、`forbidden_scopes` 的成员目录部分、契约引用反向索引）+ prompt 从 31K 砍到 ≤12K + 一次答完选项化。
- **owner 侧体感**：plan 生成变成"填业务内容"；真正需要他时只看到一个具体问题 + 2~3 个选项。
- **代价**：9～12 人日。
- **风险**：骨架与 design 耦合（改仓序 → 骨架重算）；需要新增"骨架与 author 输出对账"这一层，本身也是复杂度。**建议 A/B 上线观测后再决定。**

## 8. 契约条款（对应 openspec change）

| 编号 | 要求 | 层级 |
|---|---|---|
| `REQ-WG-01` | 候选结构评估与 Final Compile 对同一 source 的「有效边集合 / 成环结论 / witness」MUST 一致；不一致 MUST 以结构失败停等并留证，MUST NOT 静默放行 | 修正口径 |
| `REQ-WG-02` | 「物理成员仓 → 逻辑成员」反查 MUST 单一来源；`Unique/Absent/Ambiguous` 三态，非 `Unique` MUST NOT 猜测 | 单一事实 |
| `REQ-WG-03` | **仅** `intent_target_kind/_repo/_codebase/_logical_repo` 四键由平台派生（按成员表 + 写范围前缀）；`intent`/`provider_work_item_id` **不在此列**（REQ-C1-PLAN-01 禁止代填声明）；派生能力未接线前 MUST NOT 允许省略该段 | 平台已知（收窄） |

## 10. 一句话给 owner

> 这块之所以复杂，是因为**平台把"哪个仓先做"这件它自己最清楚的事，写成了说明书交给模型去背，而平台自己又在最后一刻用另一套算法重新算了一遍**。修法不是再写一遍说明书，而是：**同一个事实只留一个来源 —— 平台自己算、自己填；真需要你定的时候，把算出来的选项摆在你面前，而不是把一句"依赖环"丢给你**。明天动的第一处，是让那两套算法先对齐 —— 这样"review 说没问题、到最后才报错"会立刻消失。

- 日期：2026-10-22；版本：v1.0（按同日 owner 最终决策修订）；状态：设计稿，六项范围决策已确认，未实施；OpenSpec 与精确实施 Plan 仍须按既有门禁形成和审核。
- 代码取证基线：worktree `feat-b-0808-add-monorepo` 的 `fabf3e95`（首次设计时读取 `git rev-parse --short=8 HEAD` 确认）；初稿文档提交为 `372b0bb0`，本轮仅修订文档。下列源码行号均指该代码基线，不指主工作区或部署二进制。
- 交付边界：只形成技术方案，不修改实现、OpenSpec 本体或前端，不运行 Cargo，不部署、不 push；后文接口、字段、错误码和新文件凡标为“拟新增”者均不是现有能力。

## 一、背景与问题事实

当前规划评审已经从 LC 根启动，但窗口只锚定一个 Git 工作树。聚合场景会先使用业务仓，无法收敛时回落主成员；因此 `busi/frontend/gateway` 三仓 Issue 的材料读取与对账覆盖不一致：Reviewer 可看到集合上下文，但其他成员变化不属于该单树窗口。扩大 prompt 中的仓库清单、把 cwd 再设成 LC 根，或者仅把报告分成三节，都不能修复这个缺口。

核心依据：`src/product/workspace_engine/review/drive.rs:1468-1482` 已设置 root cwd 和空 writable roots；`:1689-1746` 仍返回单一 worktree；`:1777-1798` 只传一个 worktree 开窗。当前报告在 `src/web/workspace_ws_types/review.rs:149-160` 没有成员分段。

**已选路线（ii）——每个选中成员复用一个现有单树窗口，先全部开窗，全部成功后才依次评审，整轮持续持锁，末尾统一收口；新增 durable 集合屏障，不改造单树恢复内核。** 开窗前检查 common-dir 互异，重复即整轮阻断，不能跳过成员。owner 当前部署的三仓满足该条件；可读面保持 LC 根全树，对账面只含 Issue 选中成员，根级非成员条目不做快照/比对/恢复而逐项披露。

## 二、owner 需求、硬约束与决策记录

### 2.1 已确定要求

1. **范围同源**：Author 和 plan reviewer 的业务成员集合均来自 Issue selection，经 `PlanningContextSetResolver::resolve` 得到有效成员全集；Story/Design 的 involved、focus、change_order 和 WorkItem target 只能描述本阶段改动或评审重点，不能收窄 plan reviewer 的覆盖集合。
2. **cwd、可读面与对象分离**：author、coder、coder reviewer、internal reviewer、plan reviewer 的 LC provider cwd 均为 canonical `provider_context_root`，`readable_roots` 覆盖 LC 根全树；根级规则/工具/索引上下文对所有角色保持可读可加载。Coder/CodeReviewer/InternalReviewer 仍只绑定其一个 attempt target，且 target 属于 Issue 选集；plan reviewer 覆盖 Issue 选集全集。LC 根不是伪 Git 工作树，也不是扩大 Coder writable roots 的理由。
3. **最终 P0 及对账面**：仅 plan reviewer 对 Issue 选中成员全集做 **0 写对账；发现成员 worktree 差异先落违规证据，再恢复原样并使整轮报告作废**。基线已有 dirty/staged/untracked/ignored 不是违规，窗口期间相对于成员基线的变化才是；根级非成员条目在对账域外，报告逐项披露“根域未对账”。**对账域收窄不等于可读面收窄。**
4. 一份报告，按成员分节，再给一个总判定；成员不可评审或对账未完成不能伪装整体成功。
5. 保持现有 fail-closed、三域区分、违规 journal、恢复游标和人工门；不能因多仓化漏检、洗白旧轮或用污染态重新冻结基线。

### 2.2 决策记录与非目标

**owner 于 2026-10-22 最终决定：“不需要物理只读，0 写对账 + 恢复就行了。”** 本稿以此替代此前“物理不能改动任何内容”的表述。2026-10-16 v2.0 设计中的物理 no-exec、Pi 白名单及其能力探针目标当前未实现，本次明确不做，不再作为待决项。历史方案自身也记录已被后续方案替代，见 `cadence/designs/2026-10-16_技术方案_Git提交卫生与Reviewer纯只读权限收敛_v2.0.md:106-108`。

owner 于同日进一步确认以下六项，替代初稿中的待决选项：

1. 不做物理只读/no-exec，以已观察差异的0写对账、恢复和违规作废为准。
2. 采用路线（ii），仅承诺 common-dir 互异拓扑；重复 common-dir 以 `plan_review_window_common_dir_conflict` fail-closed 阻断，不跳过成员。
3. ZeroWrite 仅用于 plan reviewer；coding reviewer/internal reviewer 保持单 target 与既有 B 档临时验证写政策。
4. 某成员不可评审或失败，整轮 fail-closed；PARTIAL 仅诊断，不允许推进。
5. 根级非成员条目 `.agents`、`.claude`、`.codex`、`.codegraph`、`.kimi-code`、`.omp`、`.pi`、`.mcp.json` 等**不纳入对账域**，报告逐项披露；**可读面保持 LC 根全树**。owner 原话：“对账肯定是不需要对这些的，但是在执行 author reviewer coder 都是需要加载这些目录的内容的。”
6. 完整闭环后再启用生产入口，不以分段报告/单仓锚过渡冒充全集对账。

因此本次不重做 coding cwd，不扩大 coding attempt 为多 target，不重启已取消的 Group Reviewer 流程，不新增通用验证 runner，不改变 Author 的写入纪律，**不做 P4 根 guard**；物理 no-exec 和所有 reviewer 统一 ZeroWrite 亦不在本次范围。

## 四、方案 A：范围解析与冻结数据通路

**A 结论：plan review 驱动时可访问 project/issue 与 LifecycleStore.app_paths，直接复用 Issue 有效选集解析；新增集合快照通路，不再从 Story/Design/WorkItem 声明收窄。** 当前没有物理防写，全选集对账是现有检测/恢复模型在多仓成立的必要条件。

**A 的双范围硬边界**：选集解析只决定 `reconciled_member_roots` 与业务target；所有角色的 `working_directory=provider_context_root`、`readable_roots=[LC root]` 保持不变，根级 `.agents/.claude/.codex/.codegraph/.kimi-code/.omp/.pi/.mcp.json` 等内容仍可读可加载，不能把成员对账清单复用成读取allowlist。

### 4.1 读取路径与时机

1. 在 `drive_review_session` 与 gateway 对应公共入口、任何 `ensure_review_invocation_scope/build_review_input/load_plan_review_context` 前执行；现有先开窗位置为 `src/product/workspace_engine/review/drive.rs:41-69,1749-1751`。
2. 用 `LifecycleStore.app_paths`、session.project_id/issue_id 调用 `RepositoryAuthorityResolver` 和 `PlanningContextSetResolver::resolve`，取 `resolution.set` 全量 member_id，不传阶段 involved 作筛选。底层有效集合已经含 include/exclude/active 规则，见 F1。
3. 按 issue 所属 LC，通过已存在 `RepositoryStore::resolve_logical_repository_for_issue_codebase` 映射每个 member 到 checkout/RepositoryRecord；接口及 active/身份校验见 `src/product/repository_store_parts/resolve.inc.rs:12-35,98-149`。不要把 inventory.root_relative_path 当可写路径权威。
4. 冻结每个 canonical worktree/gitdir/common-dir、逻辑成员 ID、checkout ID、alias，以及 canonical LC root、membership revision、policy digest、有效成员集合 digest、artifact/review invocation identity。顺序沿用 resolver 的确定性集合顺序，ID 作主键，alias 只展示。
5. 与本次 Author 已冻结 `PlanningContextSnapshot` 的 effective IDs、成员身份、root/policy 等比对。旧快照缺失或不一致进入已有显式 fresh/等待语义，不先覆写旧快照再比较；参照 `planning_context_resolver.rs:417-449,476-510` 与 anchor-recovery delta 的显式 fresh 合同。
6. 全窗基线完成后、每次 provider spawn 前以及采信前复验冻结集合与身份；selection/membership/root/checkout 漂移使本轮不可采信。运行中不动态增删成员、不把已有成功分节复用到新集合。

**拟新增载体** `PlanReviewScopeSnapshot`：project/issue/LC、review_set_id、root、selection_digest、membership_revision、policy_digest、artifact/invocation refs、ordered members（member_id/checkout_id/alias/canonical identity）、mutation_policy，并分别记录 `readable_roots=[LC root]`、`reconciled_member_roots` 与 `unreconciled_root_entries`。它不是第二套 selection 算法；只冻结 F1 的成员结果。该载体由范围解析→集合协调→prompt→报告证据→最终采信同源传递；根级域外项用于披露，不生成基线/恢复材料。

### 4.2 空集合及失败语义

沿用外层稳定码 `plan_review_window_target_unresolved`，增加结构化 reason，而不是为每个缺失字段制造一组平级错误码：`effective_member_empty`、`selection_invalidated`、`member_checkout_unresolved`、`member_not_git_worktree`、`member_identity_ambiguous`。每项含 member_id（若存在）、可操作原因，不回落 primary/focus/进程 cwd。非 Git 成员不能作为“文档仓例外”悄悄略过：整轮在材料采集/provider spawn 前失败。

新增两个有独立处置含义的拟错误码：

- `plan_review_window_common_dir_conflict`：选集内 canonical common-dir 重复，路线（ii）不支持该拓扑；列出冲突成员，整轮零启动。
- `plan_review_window_scope_drift`：冻结后集合或身份漂移；不沿用本轮报告，进入等待/显式新轮。

## 五、方案 B：N 个成员的窗口承载与路线取舍

**B 结论：owner 已选（ii）复用单树窗口，加 durable 集合屏障；仅在所有选中成员 canonical common-dir 互异时成立，当前实例满足。** 全窗同时覆盖整个评审时间段是必需条件，“开 A→审 A→关 A→再开 B”不合格；成员窗只约束对账域，不把 provider 的 LC 根全树可读面收窄为当前成员。

### 5.1 两条路线比较

| 路线 | 可行性与覆盖方式 | 代价与限制 |
|---|---|---|
| **（ii）每成员一窗，owner已选** | 全成员预检，逐个开窗但不启动任何 reviewer；全部 Running 后形成集合屏障，再依次审各成员；所有窗持续持锁，最后统一 quiesce/对账/恢复/裁决/关闭。每个成员的 baseline 从全局 review 起点前一直有效至全局终点。 | 单树 lease/manifest/恢复/CAS 模型复用；需集合 durable record、全窗失败收口、跨窗采信和根域逐项披露；不做根 guard。共 dir 互异是硬预检条件，不泛化支持所有拓扑。 |
| （i）一个窗口多 tree | 一个窗口冻结 members/identities/baselines/restores 列表；统一取得全体 tree/common-dir 冲突域，按 common-dir 去重冻结通道，全部 ready 才启动；全列表对账恢复后一次采信。 | 修改 lock_identity、租约持有集合、baseline manifest、恢复游标、互斥判定、所有下游 WindowExpectation/compensation/消费者；共享 common-dir 可在同窗内协调，但属于内核改造，不能只数组化请求。 |

路线（i）仍复用现有状态机与恢复算法，**不等于推倒 9.5K 行窗口机制**；但其共享数据合同、崩溃重入与所有窗口消费者改动明显更多。当前实例没有共享 common-dir 需求，owner 已选（ii）以保留单树内核；（i）仅作为未来通用拓扑的留档选项，不在本轮偷偷改闸门共享持有人。

### 5.2 durable 集合屏障（拟新增，不是只有内存 Vec）

拟新增 `PlanReviewSetRecord`，放平台受信数据目录、被审成员树之外。固定 scope snapshot、完整预期 member IDs、每成员 window_id/manifest 指纹/开窗进度、当前评审分节、原始输出引用、集合采信结果及关闭进度，同时保留完整readable范围和根域未对账逐项披露清单。进度从 child durable 事实派生并持久记录；它是集合编排账本，不复制单窗恢复状态机，也不建立根guard。

冻结时序：

```text
resolve/freeze selection + precheck every identity/common-dir
  --> persist set and every expected member/window mapping
  --> open all member windows, no reviewer yet
  --> all windows Running + all baselines complete + scope still current
  --> sequential member reviews; every window stays locked
  --> quiesce every reviewer/resource, stop new materials
  --> compare all domains, persist violations BEFORE any restoration
  --> restore every changed selected member from original baseline
  --> determine one set acceptance, persist report and close progress
  --> close all children; publish final accepted result ONLY after closure succeeds
```

集合账本必须先于第一个 child begin 落盘，避免崩溃后只看到一部分成员而误认完整集合。恢复按完整预期映射装载所有窗，不从“磁盘上现有几窗”倒推选集。

- 任一开窗失败：零 reviewer 启动；停止开新窗，逐一回收已开的窗。失败窗可能已进入 Preparing/RecoveryRequired，同样入账并续恢复，不把失败当“没创建”。恢复未完成保留相应 lease/channel，发人工注意事件。
- 评审中任一成员失败：默认终止本轮，停止所有已登记进程，已完成分节只留诊断；对所有成员终核，不能只核当前仓。
- 任一成员违规：journal 先落盘→恢复该成员并继续完成其他成员安全收口→**集合作废**。不能仅把一节标失败、让其余节推进全局通过。
- 正常结束：先全体 quiesce 和对账，后逐窗恢复/关闭；关闭动作可顺序执行，但不能在审下一成员前释放前一成员。已释放窗之后的合法变化属于下一时间段，报告仍绑定原基线，不将它误当本轮采信依据。
- 崩溃/取消：启动补偿先装载未终结 set 与 child 原基线，先恢复/裁决，完成前禁止该 set 新 provider、材料或路由；不能重冻污染态。

成员子评审之间只做完整集合的只读复验，不恢复、不关窗、不释放锁；若已观察到差异，立即先落违规并停止下一成员启动，转全集合收口。末次全量对账仍不可省略，防止只在成员轮换时检查而遗漏末尾写入。

### 5.3 租约与通道影响

现有不同 common-dir 的窗口可同时持 lease，每个域的四种闸门各被自己的 child window_id 冻结，互不抢持有人；依据 `reviewer_window_store.rs:133-162,179-196,232-255,689-694,1029-1081`。逐个 begin 按稳定 member 顺序，遇冲突失败后补偿已获 lease，不等待持有部分锁继续抢其他域。平台对这些成员的 stage/commit/push/compensation 在整轮结束前均会被阻断，这是预期并发成本。

## 六、方案 C：0 写对账、恢复与 fail-closed

**C 结论：在 Issue 选中成员全集每棵树上冻结完整基线，恢复前持久化全部成员 worktree 差异为违规；扩大成员覆盖和改变临时写豁免必须一起交付，扫描/静止/恢复未完成仍阻断。** 快照/比对/恢复不含根级非成员条目，但所有角色仍从 LC 根启动并保持 LC 根全树可读，二者不得混用。

### 6.1 显式 mutation policy

在 `ReviewerWindowBeginRequest`、`ReviewerWindowRecord` 与 baseline manifest 增加拟字段 `mutation_policy`（枚举 `RecoverableVerification` / `ZeroWrite`），冻结后不可变并进入 manifest 指纹；不是从 provider 名称、prompt 或“这是 plan”字符串临时推导。

- `RecoverableVerification`：现有 B 档，临时工作树残留可恢复且不单独构成违规；供现有 coding reviewer/internal reviewer 继续使用。
- `ZeroWrite`：本次 plan reviewer 使用；基线后新增/删除/内容、类型、mode、symlink、目录形状等任一 worktree 差异都生成 `worktree_*` 违规事实，**包括 ignored 构建残留**。Git 与平台元数据违规仍按既有三域规则判定。
- 缺字段的旧窗口只解释为历史 `RecoverableVerification`，只用于旧记录恢复，不允许被采为新 ZeroWrite 证明。新 plan 窗口缺 policy/集合绑定即拒启动；不覆写存量 active manifest 或把旧 B 轮转成 ZeroWrite。
- Coding reviewer 在 owner 已确认的本次范围下 **不满足“任何 worktree 改动都算违规”的新口径**，它仍是单 target 的既有 B 档；不得在文案或验收中声称全部 Reviewer 已统一零写。

### 6.2 对账证据与 journal-first

复用 `reviewer_snapshot.rs:164-178,283-304` 的 no-follow 完整条目扫描和 Git 观察域。ZeroWrite 收口新增“恢复前全量比较”步骤：保存每条差异的 member/window、相对路径、变更类型、前后摘要及类型/mode、观察时间、原 baseline 指纹；先将差异与恢复前观察持久化，再执行现有恢复。不能依赖恢复后的 `worktree_fixed_entries` 数量猜违规，否则崩溃/恢复可能擦去证据。现有恢复游标和 `violation_pending` 语义继续复用，见 `src/product/reviewer_window.rs:14-25,105-108`、`src/product/reviewer_snapshot.rs:713-798`。

全部文件扫描**不套 gitignore，不把 target/node_modules/ignored 目录排除**。预算仍有限，超限必须报“对账未完成”并阻断；不能为了过关截断清单。各成员预算与总集合预算同时约束；现行单窗 200,000 条/2GiB 是参考上限而非 N 倍无界配额，见 `drive.rs:1788-1792`。实施计划定值前要以三仓实际条目/字节测量，不在设计里声称当前实例一定够。

零写是“与冻结现场逐项相等”，不是要求仓库干净：原有 staged/dirty/ignored 原样保留。任何差异先归违规，无需猜测是 Reviewer 还是外部写；无法安全归属/恢复的外部并发修改进入人工门，不盲目覆盖 owner 新写入。

### 6.3 LC 根非成员条目：可读但不对账（owner 已决）

**对账面仅包含 Issue 选定成员仓及其既有Git观察域，不包含LC根级非成员文件系统条目。** 不新增 `PlanReviewRootGuardBaseline`、根guard lease、根快照/比较/恢复；P4由owner决定不做。该决定不会取消既有窗口/journal/平台合法写入域自身的完整性与采信守卫。

**可读面独立保持LC根全树**：author、coder、coder reviewer、internal reviewer、plan reviewer一律 `cwd=manifest.provider_context_root`，`readable_roots=[LC root]`；`.agents`、`.claude`、`.codex`、`.codegraph`、`.kimi-code`、`.omp`、`.pi`、`.mcp.json`等根规则、工具、配置和索引上下文在存在且配置启用时仍可读取/加载、进入评审输入证据。不会为了不对账而删除根配置发现、过滤prompt上下文或把readable_roots改为成员列表。只保证可读可加载，不强制逐文件注入全部内容或绕过原有上下文预算与工具准入。

报告必须把上述每项分别列成“**根域未对账：<root-relative-path>**”，记录 `reconciled=false` 和“未采集基线/未比对/不恢复”的明确说明；条目不存在或本轮未观察到时如实标记，不省略该边界、不伪称扫描成功。其他已知根级非成员条目及未选中成员也分别列为域外；不能只汇总成一句“部分目录未覆盖”。读取证据可标明该路径可读/已加载，但这不改变其未对账状态。

域外清单从固定披露项与现有根目录上下文/轻量条目枚举生成；这只用于发现和逐项说明，不读取全树字节生成恢复摘要、不建立根基线，也不因域外目录不可做恢复型扫描而增加新的成员评审阻断条件。是否已加载必须有上下文/读取证据，不能由readable_roots配置推定为全部已加载。

范围排除按**LC根级路径归属**判断，不按basename全局过滤：被选成员内部恰好名为`.claude`、`.codegraph`或`.mcp.json`的条目仍属于该成员完整基线，含ignored产物，不得一并略过。根级域外文件变化不触发本次成员ZeroWrite违规，也不由平台恢复；它们可能影响评审上下文的风险由owner接受并在coverage中披露，不用“根域已零写”掩盖。

provider私有日志、报告、窗口journal和scope数据保持在被审成员树外，沿用 `reviewer_window_store.rs:400-402`；平台记录完整性与精确合法写入证据要求不变。根级 `.codegraph` 等后台写在本轮成员对账域外，不新增guard扫描/静止门；但若已存在的authority/policy校验发现显式revision/digest不匹配，仍沿原fail-closed语义处置，不能借域外披露绕过已有准入。

### 6.4 失败关闭与边界

所有选中成员完整扫描、writer 静止、scope current、journal durable、恢复完整、三域一致及集合记录一致，才允许 accepted；任一步不成立均不可通过。基于现有 `reviewer_reconciliation.rs:20-32,373-408` 区分 `Invalidated`（已见违规）与 `NotReady`（未完成），不得用 PARTIAL 覆盖它们。任一成员违规均使set Invalidated，人工只能作废关闭或要求新轮，不能修改旧报告为Accepted；根级非成员条目不进入本轮文件系统比对/恢复。

## 七、只读基线的真实现状与冲突（独立说明）

**现行 ReviewerVerify 物理面仍为全工具、无 deny；本方案依照 owner 2026-10-22 决定，不补物理 no-exec。** 它的真实约束是 durable 窗口、平台写通道闸门、静止登记资源、基线对账、恢复与违规作废，不是物理不能写。证据：`src/cross_cutting/streaming_provider/mod.rs:92-99,858-892`；活 delta `openspec/changes/provider-desandbox-full-open/specs/session-policy-envelope/spec.md:130-152` 是 B 档恢复条款，不是 no-exec。

各层属性必须分清：

| 层 | 当前证据 | 性质 |
|---|---|---|
| role permission mode / envelope roots | `types.rs:212-225`、`lifecycle.rs:136-145,165-185`、`logical_codebase/policy.rs:242-249` | 角色配置与逻辑授权；不能当物理路径沙箱。 |

未登记外部 writer、写后自行恢复或同 UID 篡改平台记录仍可能漏观测；完整成员域解决“另一仓根本不扫描”的确定性漏洞，不宣称解决任意瞬时/恶意写检测。该残余边界必须在报告 coverage 中披露，**不得把本方案写成“已满足物理零写”**。不增加 no-exec 探针或物理能力改造验收项。

## 八、方案 D：一份报告、成员分段与总判定

**D 结论：扩展规划 `ReviewVerdict` 的集合证据与 member_sections，沿用一份 node verdict 持久化与现有可读报告通路；不把多仓 plan 报告塞进单 attempt 的 CodeReviewReport。**

### 8.1 拟数据合同

现有 `ReviewVerdict` 保留 `verdict/comments/summary/findings/review_gate/work_item_plan_review`；新增可选 `repository_review` 服务端投影，旧 JSON 缺字段可读，不改写旧记录。拟内容：

| 字段 | 合同 |
|---|---|
| schema_version / review_set_id / scope_digest | 固定本轮集合与冻结 scope；模型不得伪造 set acceptance。 |
| target_member_ids / mutation_policy / coverage | 由服务端从set record注入；分别列 `readable_roots=[LC root]`、完整 `reconciled_member_roots`、`unreconciled_root_entries`，含成员扫描完成/异常边界和每项“根域未对账”说明，绝不能用同一roots字段代替两面。 |
| member_sections | 每个选中 member 恰一节，包含 member_id、alias、状态 reviewed/unreviewable/failed/not_reviewed、成员 verdict、摘要、finding_ids、raw_output_ref、材料/证据引用、window_id/baseline_sha。 |
| cross_member_findings | 交叉仓问题的 finding IDs 与相关 member IDs；不是用无归属字符串取代各节。 |
| completeness / acceptance / blockers | completeness=complete/partial；acceptance=pending/accepted/invalidated/not_ready，由窗口与集合事实计算，模型不能给 accepted。 |

`ReviewFinding`（`src/web/workspace_ws_types/review.rs:48-67`）拟增稳定 finding_id 与 `repository_ids`；单仓问题恰一 member，跨仓问题列全部受影响 member，必须均在 set 内。finding 主列表仍是唯一内容源，member_sections 只引用 ID，避免复制后分叉；旧 finding 无 ID 只在历史读取投影，不重写历史产物。不能因新增成员分段破坏 existing category/class_hint/contract_field/machine_repair 的封闭校验。

同一问题跨成员重复出现时，复用现有 `FindingFingerprint::identity_for_finding`（`src/product/work_item_plan_policy/fingerprint.rs:59-129`）做同契约身份归并，合并 repository_ids 与证据/raw引用，保留成员原始表述；不改现有稳定ID/legacy指纹哈希，不以单独新增finding_id绕过重复问题门。报告分节ID与既有策略指纹的映射由服务端持久记录，模型不能通过换成员别名重置finding身份。

### 8.2 产出、证据与展示

路线（ii）每成员一次 fresh reviewer invocation，cwd 始终 LC root；prompt 同时带完整冻结选集与“本次重点成员”，明确重点不改变其他成员的窗口覆盖。N 份原始响应是证据，不是 N 份最终报告。按确定性顺序合成一个报告，不新增 LLM reduction 轮或恢复被取消的 Group Reviewer。

每个 raw 引用绑定 review_set_id/member_id/subrun_id、provider session 与 window_id；证据引用带 member ID、相对路径、行范围/内容摘要和材料 digest，不能只写 `src/main.rs` 让三仓歧义。原文只作为 raw 留存，不以最后一个成员输出覆盖前面成员。

最终结构仍通过 `persist_review_verdict` 写 node detail.verdict（`src/product/workspace_engine/session_state/stream.rs:119-127`），可读正文由服务端将各 member section 确定性渲染成 Markdown，再附总判定，走现有 review 消息通路（`routing.rs:119-151`）。因此本方案不要求新增前端组件即可交付“按成员分节的一份报告”；后端 DTO 是公共 WS/历史数据合同的 additive 扩展，实施必须验证现有前端忽略新字段并可显示正文，不能默认客户端解析无限宽松。

`CodeReviewReport` 仍属于 coding attempt，现有 acceptance/window 绑定保持单值，见 `src/product/coding_models/review.rs:190-215`；仍写 `code-reviews/{report_id}.json`（`src/product/coding_attempt_store/paths.rs:18-27`）。本次不数组化、不统一重构两套报告实体；只借用其“报告与窗口采信分离”模式。

### 8.3 总判定与部分失败

owner 已确认 **可保存PARTIAL诊断，但整体fail-closed**：

1. 任一选中成员Invalidated：整个set/report Invalidated，不路由pass，不复用其余“已通过”分节；根级非成员条目仅域外披露，不伪造它的对账结果。
2. 任一成员不可评审、provider/解析失败、未完成扫描/恢复：completeness=partial，acceptance=not_ready；总 verdict 使用现有 NeedsHuman + UserTriageRequired，阻止自动通过/返修/交付。PARTIAL 不是新增“部分通过”业务枚举。
3. 全成员已审、全部成员窗采信通过后，才可合成业务verdict：有必修项则Revise；有不可自动裁决项则NeedsHuman；否则Pass。WorkItemPlan继续消费其已有专用review action/gates，不通过成员合并绕过policy route。
4. 同一窗口全程只用于一个成员子评审/等值修复；任何技术重试新进程必须重验全集屏障。未确认前一进程静止不重试；协议 repair 不改变 scope、不吞违规。下一轮从完整选集重新开始，默认不做分节缓存续评。

**WorkItemPlan 归约合同**：所有成员响应必须绑定相同 review_scope、generation_round_id、draft_id/batch_id、target_outline_id 与 ReviewInvocationScope；任何不一致是协议失败，不挑最后一个覆盖。保留各成员原始专用 verdict，并按 `plan_reopen_required > needs_human > revise_batch（batch）/revise（outline/item）> pass` 合成一个专用结论；affects_items 按现有有效outline集合取并集，gates/action重新走现有映射，不手填第二张路由表（现有解析映射见 `src/product/workspace_engine/parsers.rs:270-378`）。对无显式class_hint的finding，先按它所属成员原始verdict调用既有分类，再合并，避免总verdict把其他成员的建议误升为必修（现行依赖raw_verdict，见 `src/product/work_item_plan_policy/classify.rs:124-176`）。最终只执行一次 `work_item_policy_action`/policy CAS（`src/product/workspace_engine/review/routing.rs:259-309`），一次集合评审消耗一轮业务预算，不因N个成员子调用重置/多扣自动返修预算；实际N次provider调用与技术重试照常逐次审计。

其中“先分类”通过服务端受信归约完成：对各成员响应中未给class_hint的finding，用现有 `classify_finding` 得到Repairable/HumanRequired/Advisory，再在合成报告的finding副本上补同义class_hint（原始响应/raw与原verdict不改），使最终统一路由重复分类仍得同一结果；已给合法hint原样保留。不能仅在局部变量里预分类、随后让总verdict重新推导而丢失原分类。

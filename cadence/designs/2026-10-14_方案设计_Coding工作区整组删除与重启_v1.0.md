## A. 失效 run 的重启语义

### 推荐：③完整执行闭包重置；部分删除用②的显式清剩余出口。拒绝①在 prepare 内暗中归档换命

| 方案 | 裁定与成本 |
|---|---|
| ③全部 Coding 工作区删除完成后，关闭旧执行轮，清活动执行闭包 | 推荐。符合「删干净后可重新开始」。必须同时清 run、advance、初始化事实和资源，不是只删 run；要保留纯 ID 退役围栏，不能允许迟到旧 command 铸新轮 |
| ②保留 Invalidated，409＋显式恢复入口 | 用于部分删除、清理中断、存量残留。入口必须实际执行「删除剩余 Coding 工作区并重置」，不能只改 phase=Prepared 或留无实现的「重新武装」按钮 |
| ①prepare 改名/归档旧 run 再创建 | 不采用。留下旧 Ready/journal 仍会重放，部分删除时还会收养旧非 Created 成员；归档若仍在 run 扫描目录还可能触发 Ambiguous。为这次删除需求引入完整历史归档不是最小解 |

### 状态裁定

| 情形 | 开始 Coding 的行为 | 可用产品出口 |
|---|---|---|
| 活跃完整 run＋同/新 command | 保持 N2：返回原 run，原 selection/首启 command 不漂移、不二次 provider |
| Paused＋新 command，members 仍在 | 409，禁止暗中续跑；S2 负责继续下一项 | 查看进度；用户若要从头重做，可整组删除后再开始，明确会丢弃旧工作区内容 |
| Invalidated，删 2/4，剩余 members 在 | 409，绝不缩水全集、补建被删两个或收养剩余两个 | 「删除剩余 2 个 Coding 工作区」→完整闭包重置→「开始 Coding」新轮 |
| 全部 members 已删，旧 run/Ready/journal 还在 | 显式开始动作内部先调用同一零成员重置闭包，再按最新 Confirmed revision 创建新轮 | 不要求用户修改文件，不要求先删除 Plan；同动作失败重试恢复该清理操作 |
| 本次现场：新 prepared 空 run＋旧 Ready 指亡 attempts | 按上述零成员残留处理，而非继续重放旧 Ready | 开始按钮能走完整清理＋重建，不能再暴露 coding_attempt_not_found |
| 重置清理中断 | 拒绝新首启，返回可重试的清理中状态 | 同一删除/开始动作重入续清；已清对象 missing=OK，不重复副作用 |
| Plan 真删除的 purging/deleted | 沿 REQ-CS-07/D2：旧/新 command 都拒绝 | 不复活 Plan；这不是 Coding 工作区重置 |

“全删”的判据不是 issue 无 attempts，也不是仅 run 冻结四个不存在：要按 `(project,issue,plan)` 枚举真实 group attempts，并与 run、所有该 plan advance records、外层 journal、per-target group journals 交叉核对。保留他 Plan/单 WI/他仓对象。新 attempt IDs、run command、确定性首启 command 均是新轮身份；不复用已删 attempt ID。

### 完整重置闭包

复用 N7 attempt 删除闭包、`AdvanceStore::list_plan_artifacts/purge_plan_artifacts`（938/1004）、N2 run purge 与 D2 的 owner/resource 判据，不复制第二套 issue-wide 扫描器。

1. 只读预检身份、plan 所属 attempts、run/advance/journal owner、目标资源；确认拒绝/取消/版本冲突零变更。
2. 冻结本轮清理清单并耐久标记 clearing；原授权 Invalidated，阻断新的本轮首启/初始化。
3. 逐现存 attempt 复用 abort→等待 runner 退出→mutation→Git/worktree/handoff→N7 闭包。不是浏览器连发四个 DELETE；服务端是一个 plan-scoped 操作。先退役/等待 runner，再取清理独占；不能持 mutation lock 等 runner，以免自锁。
4. 取精确 Plan 独占 lease、按 target 排序的 resource cleanup lease，锁内复核 owner。清 group 初始化残留（含 attempts 已亡的 journal）、WI 锁/资源中的本轮孤儿 owner；他人仍持有的资源保留或 Busy 明示，绝不“强制清别人”。
5. 清该 plan advance retry → 外层初始化 journal → AdvanceRecords；清活动 run；清本轮临时执行残留。Planning 会话、Plan/WI/revision/source/compile、上游 Story/Design 不删。
6. 再枚举复核本轮活动执行引用归零；完成轮次切换并清 pending 清单。之后下一次开始沿现 Manual advance→新 journals/attempts→bind_ready→唯一首启，而不是跳过 advance Ready 门。

零成员自动清理只适用于已证旧执行引用断裂（旧 Ready 或已越 AttemptPersisted 的 journal 指向缺失 attempts）、且无初始化/runner 在途 lease 的状态；**不能仅因 Prepared.target_attempts为空便重置**，正常初始化前缀继续原协议。检测、耐久 clearing、重新准入是同一受保护操作，不能GET判零之后无锁清理。

注意：**不得调用 `EntityDeletionStore::begin/complete` 给仍保留的 Plan 立永久墓碑**，否则未来开始永远 entity_deleting。可复用 `try_acquire_delete(Plan)` 的独占租约，但 Coding reset 自有清理状态不等于 Plan deletion。

### 「journal 在而 attempts 亡」的正确处理

- journal 未达到 AttemptPersisted、无退役事实：这是既有初始化中断前缀，继续原 journal（现 `ensure_group_initialization_attempt` 可以首物化），不要误作删除。
- journal 已达到 AttemptPersisted/Completed，绑定 attempt 已亡：不得用旧 snapshot 重建该 attempt。全 members 亡则经过同一清理闭包退役 journal/advance/run 后新建；尚有成员则 Invalidated＋清剩余出口。
- IO/坏 JSON/真实 scope 错配不当 None，不凭 target 猜归属。失败关闭但显示实际原因与重试/已存在的整组重置入口；不是手工修文件提示。

- 成功200：operation_state、plan_id、generation、deleted/remaining attempt IDs；重复同command同generation返回Replayed，不能扫下一代刚创建的 attempts。资源busy或旧runner尚未退出统一409并保留clearing事实，前端不假装全部已删；不新增异步202任务/轮询协议。确认通过的同一操作重入不重复弹窗，也不把confirmed=true视作跨generation授权。

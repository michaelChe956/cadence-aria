## 2. r2/r3 新夹具设计

### 2.1 设计原则

1. **最常见**：issue 是"给已有函数加文档注释 + 加一个单测"，验证命令是该仓自己的 `cargo test`。
2. **最小**：单仓（alpha）、单文件（`lib.rs`）、单工作项、单条验证命令。
3. **不制造选择**：不出现 beta、不出现"是否全仓检查"、不出现"要不要拆工作项"、不出现外部工具链。
4. **不改变断言面**：M1–M7 的断言代码不动，只换输入。
5. **可落笔**：issue 文本、`Cargo.toml`、`.gitignore`、应答策略、判据全部给到逐字/逐参数。

### 2.2 最小 issue 文本（逐字，直接替换 `default_issue_description()`）

文件：`tests/it_web/web_lc_gateway_multi_provider/harness/issue_scope_guards.rs:70`

```rust
/// create_issue 默认描述（T23 r2/r3 最小常见 issue；r1 共用）。
/// 设计约束：
/// - 只出现 alpha 一个仓，不出现 beta / “不修改某仓”的排除句（防语义应答造出范围题）；
/// - 单文件（lib.rs）+ 单工作项（“用一个工作项完成”）；
/// - 验证命令固定为 cargo test（仓根直接执行），不引入 podman/maven/npm；
/// - 保留只读纪律句（codex）与计划自洽句（kimi）。
pub(super) fn default_issue_description() -> String {
    format!(
        "在 alpha 仓的 lib.rs 中，给已有的 pub fn cross_repo_greeting 增加英文文档注释，\
         并新增一个单元测试（在 `#[cfg(test)]` 模块内用 `#[test]`）验证它返回 \"alpha\"。\
         本次只修改 alpha 仓的 lib.rs，用一个工作项完成。\
         验证命令为 cargo test（在仓根直接执行），Coder 必须自己执行并在完成报告中记录退出码与测试数量。\
         {ISSUE_AUTHOR_READONLY_CLAUSE}{ISSUE_PLAN_SELF_CONSISTENCY_CLAUSE}"
    )
}
```

**逐句说明（为什么每句都在）**

| 句子 | 作用 | 对应红因 |
|---|---|---|
| "在 alpha 仓的 lib.rs 中" | 单仓 + 单文件锚点；不给"是否涉及 beta"留话头 | pi 多 target |
| "给已有的 pub fn cross_repo_greeting 增加英文文档注释" | alpha 基线已有该函数（`member_fixture_baseline.rs:19`），路径/符号都在基线树内 | plan 机械校验 |
| "并新增一个单元测试验证它返回 \"alpha\"" | 给 coder 一个真实、可执行的 `cargo test` 目标；测试数 ≥1 | `non_zero_test_execution_required` |
| "本次只修改 alpha 仓的 lib.rs" | 正向范围声明（不是"不修改 X"的排除句） | 范围漂移 |
| "用一个工作项完成" | 明确不拆多工作项 | kimi 计划自相矛盾 |
| "验证命令为 cargo test（在仓根直接执行）" | 钉定命令，避免作者写 `cd .`/绝对路径/全仓检查 | `acceptance_path_not_in_baseline`、kimi 全仓 fmt |
| "Coder 必须自己执行并记录退出码与测试数量" | 真实执行 + 证据面 | M2/CHECK |
| `ISSUE_AUTHOR_READONLY_CLAUSE` | 规划期禁止写文件 | codex 临时文件 |
| `ISSUE_PLAN_SELF_CONSISTENCY_CLAUSE` | 检查只能挂在可写该文件的 work item 上 | kimi 检查×写域冲突 |

**明确不写进 issue 的内容**

- 不写 `beta`、不写"不修改 beta / beta 不属交付范围"。
- 不写 `fixtures/`、`podman`、`mvn`、`npm`、`CHECK-EVIDENCE.log`。
- 不写"全仓 `cargo fmt --check` / `cargo build` / 工作区级命令"。
- 不写 `.claude/`、`.git/` 等被禁路径。
- 不写"拆成 N 个工作项"、不写跨仓交付。
- 不写 free-text 选项/宣告类回答。

### 2.3 alpha/beta 夹具基线：让 `cargo test` 真实可跑

**现状**：alpha/beta 只有 `lib.rs` + `.claude/rules/language.md` + `.git`（`harness.rs:3778-3793`、`seed_member_rule_material` `harness.rs:8240`、`commit` `harness.rs:8454`），没有 `Cargo.toml`，`cargo test` 在仓根不可执行。

**改法（最小）**：给两个成员各加一个最小的 `Cargo.toml` 与 `.gitignore`，`lib.rs` 保持在仓根（`[lib] path = "lib.rs"`），不改现有 `lib.rs` 内容与 rustfmt 基线。

文件 1：`tests/it_web/web_lc_gateway_multi_provider/harness/member_fixture_baseline.rs`（新增）

```rust
/// 成员仓最小 Cargo manifest：让 issue 的 `cargo test` 在仓根真实可跑。
/// lib.rs 保持在仓根（与既有基线/测试引用一致），用 `[lib] path` 指过去。
///
/// `doctest = false` 是**必须**的：产品 `parse_test_execution_count`
/// （`src/product/coding_attempt_store/role_run_event.rs:549`）对 cargo
/// 只取**最后一条** `test result:` 行。若保留 doc-tests，`cargo test`
/// 的输出顺序是「unittests 1 passed」→「Doc-tests 0 passed」，最后一条
/// 是 0，`non_zero_test_execution_required` 会误判为未执行测试。
/// 关掉 doctest 后，最后一条就是单测的 `1 passed`。
pub(super) fn member_cargo_toml(member: &str) -> String {
    format!(
        "[package]\nname = \"{member}\"\nversion = \"0.1.0\"\nedition = \"2024\"\n\n[lib]\npath = \"lib.rs\"\ndoctest = false\n"
    )
}

/// `cargo test` 的产物不进入交付 diff（受控 commit 只应包含 lib.rs）。
pub(super) const MEMBER_GITIGNORE: &str = "/target\nCargo.lock\n";
```

> 背景（已实测）：带 `doctest = false` 的临时 crate，在 `lib.rs` 内加一个
> `#[cfg(test)] mod tests` 后执行 `cargo test`，输出只有
> `Running unittests lib.rs` → `test result: ok. 1 passed`；
> 不带该键时还会多一条 `Doc-tests … 0 passed`，正是最后一条被取中的风险。

文件 2：`tests/it_web/web_lc_gateway_multi_provider/harness.rs`（新增 helper + 接线）

```rust
/// 成员仓 cargo 化（T23 r2/r3 最小 issue 的验证前提）。
fn seed_member_cargo_crate(path: &Path, member: &str) {
    std::fs::write(
        path.join("Cargo.toml"),
        member_fixture_baseline::member_cargo_toml(member),
    )
    .expect("write member Cargo.toml");
    std::fs::write(path.join(".gitignore"), member_fixture_baseline::MEMBER_GITIGNORE)
        .expect("write member .gitignore");
}
```

接线位置：`build_with_fixed_roots` 中，`git_repo_at(&member_a)` / `git_repo_at(&member_b)` 之后、`commit(...)` 之前：

```rust
seed_member_cargo_crate(&member_a, "alpha");
seed_member_cargo_crate(&member_b, "beta");
seed_member_rule_material(&member_a, "alpha");
seed_member_rule_material(&member_b, "beta");
commit(&member_a, member_fixture_baseline::MEMBER_LIB_RS_ALPHA);
commit(&member_b, member_fixture_baseline::MEMBER_LIB_RS_BETA);
```

**为什么不改成 `src/lib.rs`**：`src/lib.rs` 更像标准 Cargo 布局，但会牵动 `commit()`、`member_fixture_baseline.rs` 以及 harness 内多处 `alpha/lib.rs` 断言（`harness.rs:10957/11006/11027`），扩大 diff；本批目标是"最小常见 issue"，不是"重构夹具布局"。`[lib] path = "lib.rs"` 是合法 Cargo 配置，`cargo test` 正常。

**验收**（实现者本地跑一次即可）：

```bash
d=$(mktemp -d) && cd "$d" \
  && printf '[package]\nname = "alpha"\nversion = "0.1.0"\nedition = "2024"\n\n[lib]\npath = "lib.rs"\ndoctest = false\n' > Cargo.toml \
  && printf 'pub fn cross_repo_greeting() -> &%sstatic str {\n    "alpha"\n}\n' "'" > lib.rs \
  && cargo test --offline
# 期望：Running unittests lib.rs → test result: ok. 0 passed（基线 0 测例）；
# coder 在 lib.rs 内加 #[cfg(test)] 单测后，同一命令输出 1 passed。
# 注意：这里没有 Doc-tests 段（doctest = false），最后一条 test result 就是单测结果。
```

### 2.4 澄清问答：常见回答集合与应答策略

**原则**：issue 文本已经把范围/文件/工作项/命令钉死；harness 的自动应答只允许从下表选，绝不选"扩张"项。

| 编号 | 问题意图 | 典型问法（示例） | 只允许的回答 | 现有实现 |
|---|---|---|---|---|
| A1 | 仓库/成员范围 | "涉及哪些仓库/成员？" "beta 要不要一起改？" | **仅 alpha** | `semantic_option_selection` 的 `repo_scope_question` → `single_scope`（`harness.rs:8961-9003`） |
| A2 | 确认/继续 | "是否确认按此方案继续？" | **确认 / 继续** | `SemanticTier::Confirm`（`harness.rs:9074`） |
| A3 | 保持 Issue 边界 | "以哪个为准？" | **以 issue 为准 / 保持范围** | `SemanticTier::Preserve` + `PRESERVE_ISSUE_BOUNDARY_MARKERS`（`issue_scope_guards.rs:36`） |
| A4 | 其它（语言/用例数/风格） | "文档注释用什么语言？" "要几个用例？" | issue 已钉死（**英文 / 一个**）；若仍出现，选**首个非负向**，且不得改变范围 | 兜底分支（`harness.rs:9004-9035`） |

**明确禁止的选答**（出现即视为夹具设计失败，不视为产品失败）：

- 选"全部成员 / alpha+beta / 两个仓库都改"（`SelectAll` 用于范围题）。
- 选"新增更多用例 / 额外重构 / 拆成多个工作项"。
- 选"修改 beta / 修改 `.claude/` / 跑全仓 `cargo fmt`/`cargo build`"。
- 选 free-text 宣告类（"其他，我来补充"）。

**实现建议（本批不新增分支）**：现有 `single_scope` + `Confirm` + `Preserve` 已覆盖 A1–A3；A4 由兜底"首个非负向"覆盖。因为 issue 已把语言/用例数/工作项数写死，正常情况下 A4 不应出现。本批只加回归测试，不改选答算法：

- 在 `issue_scope_guards.rs` 的 `mod tests` 增加：
  1. 仓库范围题（选项含"仅 alpha"与"alpha+beta"）→ 选"仅 alpha"；
  2. 确认题（"确认继续" vs "取消"）→ 选"确认继续"；
  3. 全 Negative 兜底 → 仍选 Preserve（现有测试已覆盖，保留）。
- 如果首轮真实跑出现 A4 的新问法，记录到证据根，**下一批**再加窄关键词；本批不预造。

### 2.6 r2 与 r3 如何共用同一个 issue

- 二者都走 `run_provider_matrix` → `create_issue()` → `default_issue_description()`，**同一个函数**。
- r2：`LIVE_MATRIX_RUN_MODE=full_chain`，12 格真实执行（story/design/plan×2/coding/review × fresh/resume）。

- 轮次语义只由 `LIVE_MATRIX_RUN_MODE` 控制，issue 文本不含任何"第几轮"字样。

## 3. r1 是否也简化：两案与建议

### 3.1 先校正事实

- 当前 r1（`lcg_live_<provider>_five_stages_fresh_resume`）走的也是 `default_issue_description()`，即"会话过期"issue，不是六条宿主验证命令。
- 六条命令 issue 只属于 T22 的 `b45_live_kimi_host_check`（`harness.rs:11881` 注入 override）。
- 因此"r1 是否简化"在代码上不是"改不改 r1 的 issue"，而是"改不改三轮共用的 `default_issue_description()`"。

### 3.2 方案 A（推荐）：三轮统一最小 issue

- 做法：只改 `default_issue_description()`；r1/r2/r3 自动同款。
- r1 定位：**五阶段链路冒烟**（只跑矩阵，不跑 boundary/failure）。
- 优点：
  - 一处改动，三轮输入完全一致，对比表才成立；
  - r1 不再受 podman/npm/maven 环境噪声影响；
  - 跑时最短，适合每次改动后先跑 r1 门禁。
- 代价：r1 不再覆盖"多能力特性"的作者面；但这不是 r1 的职责，T22 已覆盖宿主工具链。

### 3.3 方案 B：r1 单独保留更复杂 issue

- 做法：新增 `LCG_FIVE_STAGES_ISSUE_OVERRIDE`（或第二个描述函数），只在 r1 注入。
- 优点：r1 保留更丰富的 authoring 面。
- 代价：
  - 多一条代码路径与一份文本维护；
  - r1/r2/r3 输入不一致，三轮对比失效；
  - r1 跑时变长，且再次引入外部工具链/范围歧义；
  - 与 T22 职责重叠。
- 结论：**不推荐**。若 owner 想让 r1 保留"六命令宿主验证"，建议把它明确归到 T22 专项，而不是塞回 T23 五阶段矩阵。

## 5. M1–M7 覆盖如何保持

### 5.1 覆盖保持（断言面不变）

依据 `live_b45_t23.rs:447-547` `b45_t23_assert_role_coverage`：

| 维度 | 断言 | 简化后 |
|---|---|---|
| M1 Author | story/design/plan×2 的轮次覆盖与门/确认链 | **保持**：issue 变短不影响会话/门机制 |
| M2 Coder | coding 至少 1 个真实 confirmed 格 | **保持**：单文件改动仍走 group attempt、受控 commit、CHECK 真实执行（`cargo test`） |
| M3 Reviewer | review 至少 1 个真实 confirmed 格 | **保持**：review 会话仍真实驱动 |
| M4 group/repair | 边界 coding 正向 confirmed + 受控写双拒 + D4 无漂移 | **保持**：边界矩阵独立夹具，不受 issue 影响 |
| M5 失败关闭 | 17 个固定负向场景逐格拒绝/合法 unknown，零 spawn 会计 | **保持**：独立夹具 |
| M6 Codex danger | `b45_live_codex_danger_apply_patch` 独立测试 | **保持**：不依赖 issue |
| M7 lifecycle | fresh/resume 与 spawn 计数；resume 承继链 | **保持**：r3 的 carried 断言不变 |

### 5.2 简化后不再由本矩阵覆盖的维度（明确列缺口）

| 缺口 | 为什么简化后不覆盖 | 处置 |
|---|---|---|
| 跨仓范围决策（involved 多成员、多 target 409） | issue 不再出现 beta；story/design involved 已钉 alpha 单成员 | **留给后续专项**（跨仓范围/多 target 专项），不阻塞本批；M4 仍覆盖写边界/受控写 |
| 多工作项拆分与返修循环 | issue 明确"一个工作项" | **留给后续专项**（多工作项 group/repair 专项）；M4 覆盖 coding 正向与受控写 |
| 外部宿主工具链（podman/maven/npm 六命令） | 本就不是 T23 M1–M7 的内容 | 由 **T22 host check** 承担；不在 T23 补 |
| 全仓级 fmt/build 检查 | 明确不构造 | 由静态检查/M4 承担；不在本批 |

> 结论：**简化只改输入夹具，不改断言面**。M1–M7 的断言代码零改动；上述缺口是"输入不再触发"，不是"断言被删"。

## 7. 风险与待确认

| `cargo test` 在 alpha 仓根可用性 | 当前夹具无 `Cargo.toml`；本方案补最小 manifest | Slice B 的临时目录命令先验证；若 CLI 环境无 cargo，报告 BLOCKED（环境问题，不是产品红） |

## 1. Purpose：用户裁决与范围

**单仓手动正常路径已经验证可用。** 本迭代不重新实现这条链，也不把单仓手动成功当作自动化完成。准确目标是：

1. 打开真实 Legacy 单仓的自动化入口：解决 GAP-I 所示 enrollment 422，贯通目标投影、明确授权、自动准备、自动 advance 和自动首启。
2. 修复自动化新增代码的真实缺陷：enrollment 身份、编排器、人工门、网关准入及其交互路径。
3. 把“出错后靠人在场绕”的恢复路径产品化：业务运行不承重于页面连接；需要人裁决时可靠停等，人在驾驶舱操作后无需直写或常驻 driver 才能继续。**无人值守不等于无人批准。**
4. 将发现 #17／#18／#19 的三个直写旁路变成有权限、有身份、有审计、有真实效果的产品能力。

### 1.1 范围约束

- story／design、choice／危险命令、计划 approve／feedback／abandon、需要人的故障裁决及 FinalConfirm 仍由人完成；不引入自动批准。
- 自动化只允许**一个精确授权的目标**：一个 Legacy 物理仓，或 LC 选择中的一个 logical repository。LC 可以含多个成员，但本次 issue／plan 的自动 target 必须唯一；不增加多 target 自动 fan-out。
- `advance` 只到 Ready；provider 首启仍经过现有 typed StartCoding 单入口。恢复命令不得被伪装成第二次自动首启。
- GAP-E／F／G／H、F1／F2 等已修部分不重复立项；新发现属于同家族的未修断点则仍须解决。
- 外部账号池 503 不由本迭代“修复账号池”，但必须保留可靠诊断和人工恢复，不自动重试未知外部副作用。LC gateway 安全门不降级成直连。
- 旧草案中“原 12 项登记遗留”等未列入本次输入的其他台账不是本方案的隐含排除依据。本方案所列每项必须关账；若真实验收又发现同链产品缺陷，纳入修复循环，不以新的遗留条目换取关闸。

## 3. 总体设计：四种身份和一个真实恢复合同

### 3.1 拟新增身份合同

| 身份 | 负责问题 | 不变量 |
|---|---|---|
| enrollment `generation` | #12／#14、单仓入口 | 同代 prepare／binding／generation action 幂等；新代有独立 intent、plan／session 与 action key；policy_revision 仍只负责授权 CAS，不兼任代号。 |
| runner `run_incarnation` | #3／#4／#5／#8／#11 | 活执行拥有 durable owner；registry 只是本进程协调；旧 token、旧回执、旧 retired 事实不得影响显式认领的新 incarnation。 |
| unit `execution_no` | #13、验证／合同修订后的重执行 | 每次新执行记录实际启动 HEAD；重连／同 run 恢复不增号；真正 restart 或 amendment 重执行增号，旧轮区间不改。 |
| role `context_revision` | #18／#19 | 每版冻结 verification ref、instruction／note IDs、role、renderer、hash 与实际 prompt 输入；同版恢复复用冻结输入，异版合法演进，不改旧 hash。 |

这四者作用域不同，不合成一个“万能 revision”。从 enrollment 到 attempt、unit run、role run、门与命令记录必须可追溯；无法证明身份或外部副作用时可靠停在可操作的恢复态。

### 3.2 恢复动作共同语义

拟新增／扩展动作均携带 `command_id`、对象 ID、expected version／generation／gate ID、理由及作用域；同键同负载返回同一结果，同键异负载或旧身份 409，非法状态 422。REST 与 WS 调同一应用服务，驾驶舱／Coding Workspace 显示同一 durable 结果。

业务完成和观察投递分离：先持久候选、门快照、动作认领、执行上下文或检查点，再发布观察事件；observer 满、无 socket、attachment 换代不反转业务事实。可重复的本地确定性动作可按 journal 续做；provider 是否已启动不明时不盲目再次启动。拟新增状态名是合同草案，实施时应融入现有 enum／journal，不叠加第二套状态机。

## 5. 五个 change 的实施合同

本节是change切分和方案，不是逐步实施计划。change ID均为**拟新增**；用户批准后由OpenSpec提案／delta明确契约，再写实施计划。

### 5.1 C1：`enrollment-lifecycle-and-rebinding`

**Why：** 一个enrollment只能活一次，失败换代又连锁撞子会话、advance和门。必须先定义授权代际与精确绑定，避免C5在旧恒等逻辑上扩目标。

**范围：** #1／#6业务门、#9／#10／#12／#14／#16，以及供C5使用的carrier-neutral目标身份合同；不启用Legacy自动化、不修改coding runner生命周期。

**关键设计决策：**

- **A1 generation＋显式supersede。** 拟新增enrollment generation及历史记录、generation级prepare／generation intents。Enable／Disable同代开关不改source／options／target、不清claim；变更这些身份必须显式新代。`supersede` 请求含expected policy_revision／generation、明确source／options／target及模式：
  - `regenerate`：新prepare intent派生新plan／session；新代动作键不与旧代相同。
  - `adopt_explicit`：冻结人明确指定的plan／session，不再用固定auto ID验证它；必须同issue、Interactive、精确source／target／provider合同、已出版revision可互证。不能按“最新plan”接管，不能把已有Manual已认领attempt升级成自动许可，不能让Completed旧plan隐式再执行。
  - 旧代仍有活run或外部启动未结算时先提供明确阻塞及C2的停止／裁决入口，不能偷偷Abort或并发启动新链。代际切换撤销旧代未认领许可；已认领事实保留。此规则不同于Disable，后者仍不取消已运行动作。
  - 迁移旧合法数据为generation 1，保留原ID／claim／intent。已被直写为不一致的历史数据不得自动“修好”：诊断原intent与当前绑定，允许人经受核验的supersede重开或明确adopt，不能要求再编辑JSON。切换后所有消费者只用新合同，取消旧单文件／固定ID假设，不留两套写路径。
- **A2 role-chain准入。** 扩展已有gateway静态谓词，role集合由实际launch路径确定；GET target和PUT Enable共享判定，attempt准入防御复核。Logical author在plan能直连不代表同author作为coder合法；Legacy不要求LC gateway。动态账号故障仍走已修GAP-H。
- **A3完整门与恢复门。** 候选批准／feedback必须绑定source revision、mechanical／review证据、剩余人工返修预算及snapshot。无这些的relay失败只能是运行恢复门：恢复失败节点，或从权威候选重建完整门；不可赋予裸approve。候选门创建与snapshot durable化同一事务／可重放journal。observer投递状态不参与业务合法性。
- **A4计划路径意图。** 推荐在既有plan grammar／IR及canonical合同新增结构化路径意图（拟字段：`path_intents`，项为repository-relative path、existing／create、提供者WI），而非从自然语言猜创建。existing须在基线或经显式依赖供给；create须在创建者exclusive_scope内、非forbidden且依赖可达。同步parser／lower／source教学／机械finding／projection；旧无意图计划保持已有引用验证，需修订者走合法feedback，不自动扩大写权限。
- **A5 advance显式retry。** 拟新增`retry-initialization`动作，对Failed record做expected版本／journal／plan revision／attempt／target及安全checkpoint核验。恢复复用原attempt，不新发provider、不重新物化已完成prefix；原失败及retry历史并存。CAS失败／身份漂移无写副作用。

**拟API能力：** enrollment supersede、完整SC门恢复／重建、advance retry-initialization；沿现有enrollment、SC恢复、advance路由组织，不以新命令ID绕幂等。已有binding端点收敛到明确generation binding语义，不保留能直写却不被编排器认可的第二入口。

**已核实主要文件：** `src/product/models/automation.rs`、`src/product/issue_automation_store.rs`、`src/web/handlers/automation_enrollment.rs`、`automation_target.rs`、`automation_gateway_preflight.rs`、`src/web/autopilot_orchestrator.rs`、`src/web/advance_plan.rs`、`src/product/workspace_engine/single_candidate.rs`、`compile/finalizer.rs`、`advance.rs`、`src/product/advance_store.rs`、`src/product/lifecycle_store/workspace_single_candidate.rs`、`workspace.rs`、`src/product/work_item_plan_compiler/{types.rs,grammar.rs,parse.rs,lower.rs,validate.rs}`、`src/product/work_item_contract/model.rs`、`src/web/handlers/{lifecycle.rs,dto.rs}`。跨代读取、TS契约及通知投影必须一并迁移，尤其S24的“同名最新session”不能继续用于child权威绑定。

**依赖／可独立验收：** generation、门、路径语义及role预检可先交；advance retry依赖C2租约合同。A07／A10／A12／A13通过；零provider的不支持组合及旧授权竞争负例有永久行为测试。

### 5.2 C2：`coding-execution-resilience-and-triage`

**Why：** 执行恢复依赖内存registry／WS，真实错误又无权威验证裁决；三个直写旁路必须一起闭环，避免#19改合同再次触发#18。

**范围：** #2／#3／#4／#5／#7／#8／#11／#13／#17／#18／#19及#6的运行／事件消费侧。按以下六个子合同实施，但不拆开#18／#19的持久身份切换。

- **B1连接不拥有业务run。** 扩展现有ClaimIfIdle和manager owner，persist action／run_incarnation／completion checkpoint。attach／detach／observer无provider取消权；同identity kick是幂等，不是supersede。只有显式停止／替换且expected run一致才能取消；completed output先按owner提交再发relay。复用router现有关键帧／try_send，保证engine→manager业务事件持续消费；不再引入fake observer来维持进度。

- **B4 execution／context演进。** 以现有unit_run／amendment物化模式扩展：

  4. instruction消费指向真正被认领的role-run／context revision。准备、认领、消费间用journal／CAS衔接；崩溃后能证明已消费而尚未spawn则续同意图，外部启动不明则人工恢复。单凭consumed不能宣布模型收到。

### 6.3 横贯所有场景的审计判据

- **零直写：** 测试执行者不得编辑 `repos.json`、LC selection／manifest／policy／capability／index权威、identity journal、enrollment／intent、child binding、advance record、worktree lock、unit_run／execution hash、rework consumed或context note来脱困。正常产品命令依法持久这些文件不算“直写”；失败注入只制造指定故障，不得顺便修状态。
- **不靠脚本托运行：** 观察脚本可以只读采证；driver点火后可关，不能要求setsid＋ping或双kick／服务重启清内存来维持正确性。服务重启仅作受控故障注入，恢复本身须符合durable事实。
- **通知真实：** plan confirmed必须有成功compile／publication及Confirmed session；coding执行完成通知只在WaitingForHuman＋FinalConfirm＋完整readiness，发生前为0，等待期一次且不增待处理数。人确认后才Completed；key／时间／TTL／K窗口补读／刷新去重不因新代重置历史事实，当前代不能借旧代信息冒报成功。
- **单发及权限：** 每个generation／action、attempt首启、role run／context version的认领和provider实际启动逐项对账；同命令竞争仅一赢家。外部副作用未知不宣称exactly-once，转可操作恢复。多target／错仓／旧source／旧run／observer写入均fail-closed。
- **真实闭环：** 每格留存project／issue／generation／plan／revision／attempt IDs、部署版本、REST或UI回执、timeline／journal／claim／context摘要、真实provider输出、commit区间与实跑验证记录、人工FinalConfirm回执、终态。UI入口通过实际驾驶舱／Coding Workspace点击和可见结果验收，不只调用隐藏API。
- **未通过就是未关闸：** 替身、单仓手动、单段provider成功或“交付已入树但仍blocked”不能替代四格终态；环境不可用如实记阻断并完成可达工作，真实格未通过不得勾完成。

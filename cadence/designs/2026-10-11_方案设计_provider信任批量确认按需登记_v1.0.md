# Provider 信任：批量确认按需登记方案设计

> 阶段：独立方案设计，供接地审查、一致性审查与用户确认；不是 OpenSpec change、实施计划或实施授权。本文仅新增本设计文件，不修改产品代码、测试、五步 recipe 或 gateway。
> 证据基线：`feat-b-0808-add-monorepo` worktree 的实际源码；行号是本次只读取证位置。`local://trust-register-brief.md` 是问题与方向素材，具体落点和安全保证以源码核验为准。

## 一、问题与根因

用户在新聚合根使用 Codex/Kimi 的多 provider 会话时，跨会话批量确认被 gateway 的 `entry absent` 拒收。此前手动登记只能恢复特定根，不能修复产品路径。该用户观察按输入事实接受，本次不重现现场、不访问或删除用户 home 条目。

### 对输入素材的必要纠偏

1. **已 Trusted 不能在调用面完全跳过 registry。** `ensure_trusted` 的 Trusted 分支会经 `reuse_trusted_entry` 刷新 ownership，并记录 `ensure/replay` 或 `ensure/reuse_user_entry`（`provider_trust.rs:458–511,533–548,632–647`）。调用面仅做 read-state 然后退出会漏掉首次复用的归属和审计；“复用跳过”应解释为不重写 home，而不是不记 durable 事实。
2. **现有成功审计不是 `gate_registered`。** 实际 schema 是 `action="ensure"`、`outcome="registered|replay|reuse_user_entry"`；失败前置门另记 `gate_waiting`（`provider_trust_store.rs:51–66`，`provider_trust.rs:635–647,859–870`）。本方案沿用此 schema，确认来源通过 operation_id 关联，不杜撰既有事件名。
3. **现有 CAS 不能宣称无条件跨进程原子。** adapter 先检查 digest，再写临时文件并 rename（`provider_trust_adapters.rs:152–169,358–397,462–478,508–536`）；durable store 的锁只包住单次事实写入，不包住整个 home read→write（`provider_trust_store.rs:99–101,135–151`）。Codex 全 home 配置是共享文件，bulk 并发上限为 3，不能以 per-session 去重当作 home 并发安全保证。
4. **home 与 durable 事实不是跨介质事务。** `ensure_trusted` 先写 home，再写 ownership 和审计（`provider_trust.rs:550–647`）。故失败必须保持确认门未关闭，但不能承诺 home 零变化或自动回滚；回滚更可能误删用户/其他会话刚复用的条目。

## 二、目标与非目标

### 目标

- 用户从收件箱确认所选会话时，服务端按该会话实际配置，为需要 trust 的 provider 登记该会话 LC 的 canonical provider context root；登记成功之前不关闭门、不启动后继 provider。
- 首次登记、重放、复用用户自建条目都走既有 registry 事实模型；相同 root/provider 不重复写 home。
- 登记失败保持待确认门与其可重试性，给出稳定错误码、原始 reason_code、身份信息以及可执行人工指导；既有结果面能看到指导。
- 维持 REQ-CFC-06 的 driver/observer 仲裁、每会话一条短连接/一次 confirm/无自动重试、会话广播和逐条结果语义。

### 非目标与反目标

- 不把 workspace trust 当 capability；不伪造 launch/resume/write-boundary 证据。
- 不修改五步 Claude recipe，不在初始化时枚举所有安装 provider，不让 gateway 自登记。
- 不新增整批 REST endpoint、批事务、全批回滚、复杂等待 UI、自动重试或后台持续登记器。
- 不扩大到单仓库、任意用户路径或尚未配置的 provider；不覆盖用户既有 untrusted/conflict 值。
- 不在本阶段写 change、plan、产品代码/测试或提交；后续契约与计划必须在双审及用户确认后产生。

## 三、候选路径与取舍

| 路径 | 收益 | 成本/风险 | 选择 |
|---|---|---|---|
| 用户确认写链、真实关门前按会话配置登记 | 使用授权动作与权威会话身份，失败仍留门 | 需服务端接线、极小错误透传；共享 home 并发必须明确 | 推荐 |
| admission/gateway 侧缺条目即 ensure | 覆盖所有 dispatch | 把只读 admission/spawn 复验变成 home/审计写面，违反 `ProviderTrustSource` 契约；无用户确认授权 | 不选 |
| 初始化侧从项目/全局默认配置派生 providers | 较早登记 | 初始化输入与后续会话 provider 可不同，旧 LC/换 provider 仍漏；枚举全部则超授权；改动 recipe 的方向错误 | 不选 |
| 前端先传 providers/root 或先调登记接口再 confirm | 表面易定位整批 | 浏览器快照可陈旧且 root 不可信，登记与关门分离形成竞态和额外权限接口 | 不选 |
| 继续纯手工登记 | 不改代码 | 每个新根都依赖外部操作，不能兑现产品自动登记路径 | 只保留故障后的人工恢复指导 |

## 四、既有 registry 能力与边界

- `ProviderTrustRegistry::ensure_trusted(project_id, operation_id, lc_id, provider, canonical_root)` 已存在（`provider_trust.rs:67–75`）。operation_id 只是关联字段，不是确保唯一执行的幂等键；审计每次调用追加，不能要求审计零追加。
- 幂等单位是 home 上 provider/root 的 trust 键；durable ownership/waiting 单位是 project/LC/provider/trust-key（`provider_trust_store.rs:81–129`）。Codex 键对应 `[projects."<root>"]`；Kimi 键按 canonical root 字符串生成 `wd_<basename>_<sha256[:12]>`（`provider_trust_adapters.rs:122–149,318–326,426–435`）。
- 注册新条目记录 `owned=true`；首次复用既有 trusted 条目为 `owned=false`，撤销必须 `NotOwned`；已归属本 LC 的 replay 保持归属（`provider_trust.rs:458–511,567–601,721–757`）。不在确认失败时撤销。
- conflicting/untrusted 条目不覆盖。读取/写入/store/CAS 失败一律不放行；用户处置后可再次显式确认。`ProviderTrustError::retryable=false` 的冲突表示不能无条件立即重试，不表示永远无法恢复（`provider_trust.rs:35–53`）。
- `ensure_before_recipe` 已过滤、去重且记录 durable waiting/`gate_waiting`，其失败事实写盘是尽力而为，写盘失败仍返回 Waiting（`provider_trust.rs:825–883`）。若将其内部逻辑用于确认，应抽成场景中立能力并迁移旧调用，不能令确认伪装成 recipe，也不能复制第二份循环。

**推荐的主要落点：** `src/product/workspace_engine/conversational_gate.rs:557–560`，在 `HumanGateCloseDecision::Approve` 臂内、现有 `compare_and_save_human_gate_close` **之前**。它已经经过 `:502–555` 的类型、stage、durable WaitingForHuman、Busy 与候选恢复完整性检查；尚未关闭门节点、提升 Approval 或进入 compile。不得插在 `:576` compile 之前而 CAS 之后，否则 trust 失败时门已不再是原来的开态。

### 5.2 不能按素材示意承诺的两件事

- **服务端没有整批 provider 集。** 定义 `P(s)=该会话有效 author ∪ 有效 reviewer`，服务端只处理当前 session 的 `P(s)` 并在其中去重。同批跨 session 的相同 provider/root 通过 registry 的 home 幂等复用；不同 project/LC 的 ownership/audit 必须各自记账，不能跨 LC 去重成一次 durable 登记。整批是逐条成功/失败，不是“所有会话 trust 全就绪才一起关门”。
- **SC 确认不是 provider spawn。** `compile.rs:494–595,784–789` 与 `compile/single_candidate.rs:89–404` 显示关门进入 durable source/IR/report 校验、确定性编译、确认和创建子 WorkItem 会话，本路径没有 provider launch；子会话继承当前 author/effective reviewer（`controls.rs:171–181`）。首次 author/reviewer 生成发生在进入确认门之前；gateway 的 early admission 与 spawn 前分别在 `provider_gateway.rs:1954–1970,1749–1766` 只读拒收缺 trust。本方案只能保证“本次确认之前登记本次所选会话配置的 trust，后续真实 launch 仍经 gateway 复验”，不能保证从未登记的 provider 能先生成候选并抵达该门。若 owner 的真实验收期待“新根从首次生成开始自动可用”，只修本落点有功能硬伤：应另外明确授权 start_generation 用户写链的登记时机，不能在 admission 内偷写。该扩展不属于当前推荐范围，双审/用户确认时必须明确验收读取。

此外，wire 不含 bulk 标记，所以公共确认落点必然也覆盖同形的单会话 WS confirm。推荐把契约表述为“人工确认链按需登记，包含收件箱批量入口”，而不是伪称服务端能识别批量来源；若用户坚持只限 bulk，必须另评协议新增来源字段的方案与权限语义。

## 六、provider、身份、依赖与接口设计

### 6.1 权威数据

- provider 取 `WorkspaceEngine.session.author_provider` 和有效 `reviewer_provider`，再经 `requires_workspace_trust` 过滤、按 ProviderName 去重；不取 provisional reviewer、前端 inbox、全局默认或安装列表。字段与恢复映射见 `types.rs:75–112,115–165`。`lifecycle.rs:825–871` 在 start_generation 冻结 author/effective reviewer，reviewer 禁用时清空 effective 并保留 provisional；旧记录必须尊重 `reviewer_enabled_at_start=Some(false)`，启用判据沿用 `lifecycle.rs:1016–1020`。`controls.rs:233–266` 表明生成开始后 provider 选择锁定。
- SC 使用 `close_human_gate` 刚读到的 durable `expected` 的 provider/project/session 身份，不用 manager 建联快照；非 SC 在 engine mutex 内读取当前锁定配置。
- project_id 来自会话；LC 身份沿用 `resolve_issue_logical_codebase_id`（`repository_routing_types.inc.rs:63–73`，读取 issue 持久化归属）。单仓无 gateway 时不登记。旧逻辑代码库使用现有 `legacy_logical_codebase_id(project_id)`（`store.rs:897–900`），与 coordinator `coordinator_lifecycle.inc.rs:230–246` 同约定；`lc_scope_root`（`store.rs:87–99`）将该别名落到原 project 级 LC 子树，不能把空串伪装成新 LC。
- root 使用该 engine 已注入 gateway 的 `authority_root()`（`provider_gateway.rs:1007–1013`），不是 session.repository_path/成员 checkout/worktree。工厂从 manifest.provider_context_root 构造并做 registration/recipe/root 一致性断言（`src/web/gateway_factory.rs:125–172`）。登记前要求该冻结根仍可 canonicalize 且与冻结路径一致，并重读同 scope manifest 的 root 做身份一致性校验；失败停等，不采用原路径回退或其他 LC。
- 注入 context 同时冻结 issue 原始归属（`Option<lc_id>`）与 registry 使用的归属（显式 LC 或既有 legacy 别名）。preparation 用 `LifecycleStore::app_paths()`（`lifecycle_store/mod.rs:46–48`）重新解析 issue 的原始归属，与注入时的值相等才读该 scope manifest；归属改变停等，不能按新 LC 登记旧 gateway 根。无需给只读 gateway 新增写接口或可写 registry 字段。
- 对 LC：有 gateway 却缺 registration context/precondition 属于装配错误，fail-closed；不得把 `None` 当成“无需 trust”。非 LC 与无需 trust 的会话早退，零 home/ownership/audit 调用。

### 6.2 复用既有装配，不给 gateway 写权限

`WebAppState::with_events` 已创建并保存 aggregate initialization dependencies（`src/web/state.rs:239–242`），其中生产 precondition 使用真实 HOME、fake runtime 使用 workspace_root（`production_dependencies.inc.rs:684–719`），避免测试写真实 home。`dependencies.inc.rs:54–58` 提供 `trust()`。

在 `WorkspaceSessionManager::create` 的 LC gateway 装配段 `manager/mod.rs:380–394`，从同一 state 缓存 dependencies 取 precondition 并为 engine 注入确认登记上下文。此段已解析会话 project/issue、LC id，并已拿到正确 gateway；不在 `LogicalCodebaseGatewayFactory::build_readonly_for_lc` 中写 trust。factory 的 `:92–102,203–222` 必须保持只读 source。

**拟议接口（以下新名称是设计建议，不是现有符号）：**

| 位置 | 接口/数据契约 | 约束 |
|---|---|---|
| `provider_trust.rs` 现有 `ProviderTrustPrecondition` | 将场景专属 `ensure_before_recipe(...)` clean-cutover 改名为中立 `ensure_ready(...)`；参数与 PreparationResult 不变 | 原循环继续委托 `ensure_trusted`；迁移 handler、coordinator、fake 和测试全部 caller，不留旧别名/shim |
| `workspace_engine/types.rs`、`lifecycle.rs` | 增加注入的确认 trust context，携带原始 issue LC 归属、registry LC 标签和共享 `Arc<dyn ProviderTrustPrecondition>`；builder 可命名 `with_provider_trust_precondition` | root 仍从已冻结 gateway 读取，不复制第二套 root authority；默认无 context 不允许 LC 确认降级 |
| 产品层确认准备方法 | 返回 Ready、HomeWaiting（原 `ProviderTrustWaiting`）或 ContextWaiting（typed reason/message/retry_action，身份字段可缺省）；只准备当前会话有效 provider 集 | operation_id 使用稳定的 `workspace_confirm:<session_id>` 关联本确认来源；只是审计关联，不冒充 command 幂等键 |
| `HumanGateCloseOutcome`/`WorkspaceConfirmOutcome` | 增加 typed `TrustWaiting` 结果（携带上述 HomeWaiting/ContextWaiting 判据），与 `Busy`/`AlreadyClosed`/compile error 分开 | 不用字符串前缀识别错误，不把 trust waiting 归为 compile failure，也不 abort 会话 |
| `decisions.rs` 的 effect/序列化 | SC 与非 SC trust waiting 统一转既有 `ProtocolError` | 原 compile findings 路由、其他错误语义和成功广播不动；更新所有 exhaustive match |

既有 recipe 仍只传 Claude；中立接口重命名不修改五步行为。原 production registry 装配只抽出可复用名称/注入，不新建一套 HOME 推导或第二份 ensure 算法。

guardrail 原因码建议为 `confirmation_trust_context_unavailable`、`confirmation_trust_scope_changed`、`confirmation_trust_root_unavailable`、`confirmation_trust_root_changed`；这些属于登记前身份等待，不伪造 provider/trust_key/canonical_root，不给错误根的手工登记指引，也不产出 home mutation。context 能从确认调用方读取到的 session/project/已知 LC 身份照实返回，缺失字段省略。scope/root 无效先解决 LC 身份与材料问题，再显式确认；绝不以手工加 trust 绕过 root 漂移。

home 人工指引需要极窄扩展：在 `ProviderTrustHomeAdapter` 增加实际工件路径/指引的只读能力，在 `ProviderTrustWaiting` 增加可展示 `manual_guidance`；生产注册门失败时由命中 adapter 生成，所有原有 waiting fake/构造器与 recipe 等待序列化同步更新。没有 adapter 时只给装配修复指导，不编造 home 路径。该扩展只返回本次键的路径和格式，不读取/泄露完整配置，也不改变 home 写算法。

## 七、幂等、并发、审计与 ownership

### 7.1 确认与登记是两个幂等域

1. client 仍按 sessionId 去重、每目标一条连接和一次 confirm，现有并发上限 3，不自动重试。
2. 每次有效确认，registry 对有效 provider/root 都执行 ensure；Trusted 分支不写 home，但更新/复用 durable 归属和审计。重复审计是“尝试记录”，不代表重复关闭门。
3. trust 全 Ready 之后使用**原 `expected`** 执行关门 CAS。登记期间另一个 worker 已改 workspace record 则仍由既有 CAS 失配/AlreadyClosed 翻译决定；不重新读取并接受新门来规避冲突。至多一个 CAS 胜者 compile/close，失败者不发第二条 close。
4. 部分 provider 已登记、另一 provider 失败时，本会话不关门；已登记条目保留，下次显式确认通过 replay/reuse 恢复。一个 session 失败不回滚其他 session。
5. gateway spawn 前只读复验仍必要：登记后用户删除/修改条目不得继续用旧 Ready 判定放行。自动登记不是持久免检。

### 7.2 共享 home 写入保护

**推荐的必要安全配套：** 在既有 registry 的 `ensure_trusted` 与 `revoke_trusted` 中，为 home 工件取得稳定独占锁，覆盖 read digest/read state→home 写→该次 ownership/audit 提交。继续使用既有 CAS 和 atomic rename，不替换为 last-write-wins。

- 使用现有 `src/product/coding_attempt_store/locking.rs:53–91` 的 `ExclusiveFileLock`（`:235–240` 的目标派生锁约定），不引入新锁框架。adapter 提供该 root 对应 home 工件目标的窄 accessor（拟议名 `mutation_lock_target`）；Codex 所有 root 共锁 config.toml，Kimi 每 trust record 锁对应文件。锁的是稳定 sidecar，不是会被 rename 更换 inode 的数据文件。
- lock 顺序固定为 home 工件锁 → LC durable fact 锁（`provider_trust_store.rs:99–101`）；任何路径不得反向嵌套。锁失败仍 waiting；无 trust provider 不取锁。
- sync registry 文件操作在 `spawn_blocking` 中执行，engine 确认 mutex 保持持有到裁决结束，避免阻塞 Tokio worker/先释放锁后关到别的门；home 锁在 Ready 返回后释放，绝不带入 compile、网络或 provider run。registry 不设内部自动重试循环。
- 该锁只协调使用同约定的 Aria 写方；外部编辑器/CLI 不会遵守 sidecar。CAS 可以发现检查前变化，不能排除“检查后、rename 前”的非协作写入。文档与验收禁止宣称跨外部进程强原子 CAS。若用户要求保护任意外部并发编辑，必须另立更强 home 修改协议，当前源码能力不支持该承诺。

仅加调用面 read_state 快路或仅把 bulk concurrency 改成 1 都不够：其他窗口/进程/LC 会写同一 Codex home。配套修改仍限定既有 registry/adapter，不扩到 gateway。

### 7.3 故障与归属边界

- 成功证据使用 `ensure/registered`、`ensure/replay`、`ensure/reuse_user_entry`；`operation_id=workspace_confirm:<session_id>` 可与会话确认关联。失败保留 `gate_waiting/<reason_code>` 和 durable waiting。不要新增或验收不存在的 `gate_registered`。
- 首次用户自建条目：字节不变、ownership.owned=false，后续 revoke=NotOwned。另一个 LC 创建的同一 home 键不能被本 LC据为 owned=true。
- home 写成功、ownership 写失败/进程崩溃的窗口没有原子事务：本次保持门开；下一次只能保守复用为 user-owned（或沿用已有可读归属），不得猜测并认领。可能留下不再自动撤销的 trusted 条目，列入风险，不自动补偿删除。
- Waiting/audit store 自身不可写时，已有代码尽力记录后仍返回 Waiting；不把“所有失败一定落盘审计”作为可兑现承诺。前端必须拿到错误，门不动优先于记账成功。

## 八、错误语义、等待面与前端透传

### 8.1 服务端响应

推荐稳定场景码 `workspace_confirmation_trust_waiting`，由后续 change 最终冻结。继续使用现有 `WsOutMessage::ProtocolError {code,message,context}`，无需新增 WS 消息族。它表示确认未接受、门仍等待，不是会话 Failed/Aborted/compile failure。

home 登记失败的 context 至少包含：`session_id`、`project_id`、`logical_codebase_id`、`provider`（现有 snake_case label）、`reason_code`、`retry_action`、`trust_key`、`canonical_root`、`retryable:true`、`manual_guidance`。登记前 ContextWaiting 使用同一场景码，但只返回已知身份、reason_code、retry_action、retryable，未知 provider/root/key 省略。`retryable:true` 的含义是修复后可由用户再次显式确认，不意味着冲突可立即安全重试。字段形态参考 `handlers.inc.rs:371–383` 的 aggregate initialization waiting；沿用原 registry reason_code，不将读错误、冲突、CAS/store IO 混成 entry absent。

message 必须是可直接展示的中文：包含失败原因、门未关闭提示、人工处置及“完成后重新选择该门并批量确认；失败不自动重试”。manual_guidance 是结构化补充，不得只藏在 context 而 message 只剩稳定码。

### 8.2 人工指引生成边界

- Kimi：服务端 adapter 实际 HOME 下 `.kimi-code/workspace-trust/<trust_key>`，JSON 为 `{"root":"<canonical_root>","trustedAt":<当前毫秒时间>}`；key 由现有 `trust_key` 算法生成，不让用户自己猜 SHA。示例字符串由正确 JSON 序列化生成，路径不是浏览器机器的 home。
- Codex：服务端 adapter 实际 HOME 下 `.codex/config.toml`，目标表 `[projects."<canonical_root>"]` 和 `trust_level = "trusted"`，TOML 根按既有 `escape_toml_basic_string` 转义（`provider_trust_adapters.rs:426–435`）。提示备份并修改该表，不能覆盖整个配置。
- 对已 untrusted/键绑定冲突：提示人工核验，不能把“追加新表/覆盖旧值”当安全一键修复；对不可读/非法格式优先修复权限/格式。manual_guidance 由同 adapter 的实际路径与 trust_key 生成，fake home 同样隔离，不能硬编码 `~` 就冒充实际服务端路径。
- 不提供自动执行 shell、不返回用户 home 文件全文或凭据；root/path 作为文本展示、无需不安全 HTML。

### 8.3 客户端最小改动

`bulk-confirm-runner.ts:58–61,148–156` 的 ParsedFrame 最小新增可读 message/context。仅对新 trust waiting code，detail 展示 code、message 与必要 retry_action/manual_guidance（去掉重复片段）；其他 protocol_error 保持原 detail=code，普通 error 可保留既有行为，避免顺手改所有错误语义。

结果仍用 `rejected`（该次确认未接受），既有 `BulkConfirmReport.tsx:35–40` 已展示 detail，不新增 waiting 状态、自动重试按钮或长期 pending。原操作审计 markRejected 使用稳定 code，不能把长指导文本当 code。当前会话 live driver 的 ProtocolError.message 也含相同指导，不能仅短连接 bulk 能看见；前端真实确认面须覆盖当前会话分支。

8 秒全协议超时（runner `:6–7,169–171`）保持原语义：超时是结果未知，不是 trust waiting 的证明，更不自动重发 confirm。断连不回滚已提交的登记/确认；若发生超时，用户先观察会话当前门状态再显式操作。禁止借增加超时/重试掩盖未被验证的服务端等待。

## 九、安全冻结与规格衔接

- `openspec/specs/web-cockpit-full-course/spec.md:134–146` 的 REQ-CFC-06 明确依赖服务端显式角色仲裁与 session 广播，每会话批量动作恰一次、危险动作不参与。本设计不把登记加在 arbitrate/stage 拒收之前，不改变 lease 获取/释放，不新增第二次发送；Abandon/反馈不登记。
- gateway factory `src/web/gateway_factory.rs:92–102,203–222`、`ProviderTrustSource` 和 `ReadonlyProviderTrustSource` 保持零副作用。GET/early/admission/spawn 不写 home、ownership、audit，最后复验依旧 fail-closed。
- trust preparation 失败不改 expected workspace status/phase/snapshot、门节点、预算、turn、compile reservation、provider start ledger；只允许本次 trust 工件与 trust durable 事实变化。
- prepare Ready 不是 confirm success。唯一成功标记仍为原 CAS/compile/durable Confirmed 后的 close 事件；不提前向客户端发送伪 close。
- **规格接地差异：** 本次已读主规格 `openspec/specs/logical-codebase-registration/spec.md`（现为 214 行），其中可见 REQ-REG-01…13，没有 brief 所述 REQ-REG-14；`openspec/specs` 范围以精确标识检索也未命中 REQ-LCG-02/03。源码有这些编号的冻结注释，但不能声称主规格已含该承诺。后续契约需确认未同步 delta/归档来源或明确新增 Requirement，不能把“修改既存 REQ-REG-14”当无须核对的事实；本阶段不擅改任何规格。

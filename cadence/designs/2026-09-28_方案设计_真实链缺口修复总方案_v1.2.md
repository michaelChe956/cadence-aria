## 0. v1.1→v1.2 口径修正记录

v1.1 将 max-task 评审中针对“无人值守自愈”推导出的 owner fence、代际体系、统一 context evolution、durable operation 等深水建设误当成本轮产品目标。本版以用户最终澄清为准，作以下根本性改写：

1. **自动化形态改为“自动推进＋人到点处理”。** story／design 阶段继续人工；plan 和 coding 在没有人工门时自动推进。遇到 `AskUserQuestion`、人工门、需用户处理项或不可确认的外部副作用时，系统通知用户，用户在驾驶舱／产品页面点击处理，随后同一条链继续自动推进；不是无人值守自愈。
2. **修法从“系统自愈”改为“可操作停等”。** 错误不再靠后台自动迁移、盲目重试、接管旧代或猜测外部副作用解决，而是落入可诊断、可通知、可点击的等待状态。按钮只执行有明确对象和预期版本的重绑、重试、继续、换代或受限豁免；操作完成后复用既有编排链继续。
3. **M 系列深水项降为按需最小实现。** 不建设全局 durable owner／fencing／epoch／双主防护体系，不建设统一 context evolution 服务，不建设新的通用 durable operation 框架，不做全自动代际迁移。只有人工操作面无法兜底的并发风险保留最小互斥，例如防止两个编码进程同时跑；断连产物则以已有持久化写入顺序保护。
4. **单仓与逻辑代码库并列支持自动化。** 产品文档统一称“单仓（Single-Repository）”和“逻辑代码库（Logical Codebase）”；源码枚举 `RepositoryRouting::Legacy` 保留，仅作为代码标识，不在产品文案中称单仓为 Legacy。
5. **pi 初始化 recipe 暂缓。** Claude 当前可用，本轮不以新增 pi 初始化 recipe 作为关闸条件；登记遗留在网关重新挂接后再处理。产品不得用改 `repos.json`、手工铺底或伪造成功绕过该边界；网关不可用时必须通知并停等。
6. **工期改按四个 change 估算。** C1=4–7、C2=5–8、C4=4–7、C5=3–5 人日，总计 16–27 人日；具备接口并行条件时关键路径 9–14 工作日，不把等待用户处理或外部账号恢复冒充为开发投入。
7. **验收改为可观察的人机闭环。** 单仓和逻辑代码库各跑一遍 plan＋coding 自动化全流程，并对每个修复项注入一次触发前提；必须观察“出错→通知→产品操作→继续自动推进”。全程零手工铺底、零直接改数据、零重启服务。

## 1. 目的、范围与产品口径

### 1.1 目标

当前单仓手动正常路径已经验证可用；本迭代不重写这条路径，也不把手动成功冒充为自动化完成。准确目标是：

- 打开单仓与逻辑代码库两种载体的自动化入口，贯通目标投影、授权预检、自动 plan、人工门停等、自动 advance、自动 coding 和最终人工确认。
- 让 plan／coding 的每一个已知错误都成为产品可见的等待项：错误状态保留证据，驾驶舱 inbox／系统通知告诉用户原因和下一步，用户点击处理后链继续。
- 把 #17／#18／#19 三条直写旁路收敛为有权限、有身份、有审计、有真实效果的产品操作，不以修改 JSON、note、consumed 标志或 findings 作为恢复手段。
- 保护已有成功产物和人工裁决，不因页面断连、observer 拥塞或一次恢复失败而丢失已完成修订。

### 1.2 自动化边界

| 阶段／事件 | 系统行为 | 人的职责 |
|---|---|---|
| story／design | 不自动推进 | 人创建、澄清和确认需求、方案与选择 |
| plan 生成、编译、准备和 advance | 无人工门时自动执行 | 遇 AskUserQuestion、候选反馈、批准、配置或故障通知时在产品面处理 |
| coding provider 运行、结果收尾和分诊准备 | 无人工门时自动执行 | 处理质量门、验证分诊、重绑、重试、继续、受限豁免 |
| FinalConfirm、危险命令和明确的批准／放弃 | 继续保持人工门 | 人在驾驶舱确认或拒绝 |
| 外部副作用是否已发生不明 | **停等，不盲目再次启动** | 人查看证据后点击重试、接管或放弃 |

“自动”表示系统在用户做出一次明确裁决后继续推进，不表示后台替用户批准、自动扩写权限、自动换 provider 或自动抢占另一个运行。

### 1.3 范围约束

- 单仓和逻辑代码库都支持自动化，但一次 issue／plan 只绑定一个精确目标：一个物理仓，或逻辑代码库选择中的一个 logical repository；不增加多 target 自动 fan-out。
- `advance` 仍只推进到 Ready，provider 首启仍使用现有 typed StartCoding 单入口。恢复按钮不是第二个隐式首启入口。
- story／design、计划 approve／feedback／abandon、choice／危险命令、人工故障裁决、FinalConfirm 不自动批准。
- 外部账号池 503、网关不可用和 provider 副作用未知不在本轮自动修复；系统必须可靠通知和停等，不自动重试未知副作用。
- GAP-E／F／G／H、F1／F2 等既有修复不重复建设；同家族未修断点按本方案覆盖。
- “缓掉”的 pi 初始化 recipe 不作为本轮实现；本轮不得用第三方 provider、自写仓库配置或直接修改数据代替它。


范围边界（承接 v1.1 呈报裁决）：旧草案「原 12 项登记遗留」（交接 §2）**维持 defer、不在本方案 33/33 范围内**（登记位置各 change design 的 Deferred 节）；pi 初始化 recipe 按用户 2026-09-28 裁决**缓掉**（Claude 目前可用；网关再挂时立项），此两项不因「解决所有问题」的口径被静默纳入或销账。

## 3. 总体设计：可操作停等，而非无人值守自愈

### 3.1 统一用户可见闭环

所有本轮错误都遵循同一个产品语义，但不抽象成新的通用状态机：

1. 既有 plan／coding／repository 步骤执行到真实错误或需要人处理的边界。
2. 在原有 gate、journal 或步骤记录上保留错误、对象身份、可用证据和下一步；状态为可恢复等待，而不是伪造成功或无限自动 retry。
3. 通过已有驾驶舱 inbox／系统通知通知用户，展示具体原因、影响范围、已完成和未知副作用。
4. 用户点击该对象允许的产品操作：重绑、重试、继续、换代、重跑原命令、配置、受限豁免或放弃。操作带 `command_id`、对象 ID、expected version／gate ID／绑定身份；同键重放幂等，旧版本和错对象拒绝。
5. 操作成功后调用现有编排器／runner／advance／初始化步骤继续；没有用户点击时一直停等是正确结果，不算“链死机”。

操作接口可以是 REST 或页面动作，但两者必须调用同一既有应用服务；页面断开不取消业务事实。未确认 provider 是否启动时不得盲目再启动，转为“请确认／重新绑定”操作。

### 3.2 仅保留的最小身份和并发约束

| 边界 | v1.2 采用的最小做法 | 明确不做 |
|---|---|---|
| 自动 target／绑定 | 复用 enrollment、source、plan／session 的现有身份；用户点击重绑／换代时写一条带 expected version 的新绑定记录，旧记录只读可查 | 不做后台自动 supersede、全局 generation 服务或按“最新 plan”猜接管 |
| plan child | child 选择同时核对 plan／revision／work item 绑定；换代由用户明确操作后创建新 child | 不清空旧 child binding，不建设跨服务代际迁移 |
| coding 并发 | 在现有 attempt claim／工作树锁上加最小原子互斥，第二个启动请求停等并通知；用户确认前不抢占 | 不做 owner incarnation、epoch、fence token、双主检测体系 |
| 断连产物 | provider 已完成的修订先写既有 source／artifact／checkpoint，再发送观察事件；重连页面只读补投影 | 不把 WS attachment 做业务 owner，不靠常驻 driver、setsid 或服务重启保活 |
| execution 区间 | 复用现有 execution_no 和 start／completion commit；新执行启动前记录真实 HEAD | 不重写历史 start，不以最终门回填历史事实 |
| instruction／context | 在现有 instruction／note 记录上使用一次“准备＋认领＋消费”事务，确保实际 prompt 含指令且只消费一次 | 不建立统一 context evolution 服务，不把旧 hash 改成新含义 |
| 初始化／冷启动 | 复用现有 operation 和步骤状态；每步失败提供 retry／repair 按钮 | 不创建通用 durable operation 平台或自动重放未知外部副作用 |

`generation` 在本版只表示用户明确点击“换代／重新绑定”后产生的绑定版本，用来拒绝迟到旧回执；它不是 v1.1 规划的独立 durable 代际体系。任何换代都必须由用户操作触发，不能由后台发现失败后自动迁移。

### 3.3 操作安全共同约束

- 操作页面必须显示：失败原因、已完成步骤、目标仓／logical repository、plan／attempt／gate 身份、可能的外部副作用、按钮会做什么，以及不会做什么。
- 重试只允许可证明未产生外部副作用的本地步骤；副作用未知时按钮文案必须是“确认后重试／重新绑定”，而不是自动重跑。
- `retry`、`continue`、`rebind`、`switch generation`、`waive` 都是受限对象动作，不是任意状态写入；成功后由原链继续，失败再次回到同一个可操作等待面。
- 人工操作不会改变历史 finding、旧 execution、旧 artifact 或旧 gate 证据。受限豁免必须新增审计记录、适用 check／scope、理由和操作者。
- 通知不是业务成功条件：投递失败可以补读，但业务快照、错误和操作结果先落既有持久面。

本节是实施边界和接口合同，不是实现完成声明。每个 change 复用现有模块；拟新增的按钮、动作和字段须进入对应已有 enum／journal／DTO，不另起平行状态机。

### 5.1 C1：`enrollment-lifecycle-and-plan-recovery`（4–7 人日）

**范围：** #1、#6 的 plan 门、#9、#11、#12、#14、#16，以及供 C5 复用的载体无关 target／绑定合同。

**实施合同：**

1. **显式 target 与绑定变更。** 定义单仓／逻辑代码库 target union，所有 GET、Enable、prepare、advance、成功信息按同一目标读取。用户点击“重新绑定／换代”时明确选择精确 plan／session、source、target、provider，写入新的绑定版本；旧绑定只读可追溯。禁止后台扫描旧 issue、按最新 session 猜接管、把 Manual 已认领 attempt 升级成自动。
2. **候选门与恢复门分开。** candidate snapshot、source revision、budget 和 gate 事实先写入现有存储；relay 失败只展示运行恢复／重建按钮，没有完整候选就不能批准。按钮成功后调用原 feedback／approve 流程。
3. **显式 advance retry。** Failed advance 的 retry 按钮核对当前对象和安全 checkpoint，保留失败事实；可重做的本地步骤继续，不确定 provider 副作用先通知用户确认。原命令不会因重试被改写成成功。
4. **计划路径和 child 精确绑定。** 在既有 plan contract 中表达 `existing`／`create` 和 provider WI；缺失时把人导向计划反馈／修订，而不是扩大 scope。compile child 同时匹配绑定版本、plan／revision／work item；换代由用户明确触发新 child，旧 child 不清、不重绑。
5. **通知与操作结果。** 每个等待项在驾驶舱和系统通知中显示原因、按钮、成功后下一阶段和预计副作用；重复点击同一 `command_id` 返回同一结果，版本过期则提示刷新／重新绑定。

**实施合同：**

1. **断连与已完成产物。** 复用 manager／runner 的现有事件路径，provider 已完成的 source、artifact 和 completion checkpoint 先持久化，再发送观察事件。attach／detach 不取消业务结果；外部完成状态不明时转等待，不自动重启。
2. **最小编码互斥（含接管判别）。** 在现有 attempt claim／工作树锁上做一个原子“已有编码进程则拒绝第二启动”的判断，且 **claim 须区分「锁记录存在」与「持有者存活」**：持有者存活（活跃 run/心跳在窗）→第二启动拒绝并通知等待；持有者已死（终态 attempt/超窗无活动）→驾驶舱呈现「确认接管」按钮，**用户确认后接管并继续，旧持有者的迟到写入仍被拒**；活性未知→停等+用户确认（A09 补误确认判据：接管前强制展示最后活动时间与节点证据；误确认双进程并发为已承认残留风险，无 fence 体系）。重复 kick 同一命令幂等；只有用户明确停止当前运行后才显示 restart。无需 owner incarnation、epoch、fence 或双主租约系统。
3. **人工分诊后继续。** `manual_continue`、允许的 quality bypass 和验证处理提交现有 gate 结果后回到原编排阶段；已完成 review 不重复执行。修正 abort→restart 的状态条件，旧回执不能改变当前 attempt。
4. **实际 execution 区间。** 新 execution 在 provider 认领前记录真实 HEAD，零提交时记录空区间；重连不改 start，最终 scope 以各 execution 事实聚合。越权提交仍进入 FinalConfirm／拒绝面。
5. **#18 单次指令消费。** 在现有 rework instruction／context note 写面上，把完整 prompt 准备、认领、消费和 spawn 的关键写入按一次 CAS／journal 完成；实际 prompt 必须包含新指令。发生中断时用户点继续／重试，不能提前把 instruction 标记为 consumed，也不建设通用 context evolution 服务。
6. **#19 独立验证处理／豁免。** 保持 `coding_output_human_triage` 的 `retry_coding`／`abort` 和 Code Review 门的四动作不变；在产品面提供单独的“进入验证处理”入口，严格绑定 finding、check、plan revision、命令、cwd、结果、测试量、环境和 scope。用户可批准计划修订、可信等价证据或限域环境例外；没有证据不能继续，不能清 findings 或让模型隐瞒事实。
7. **#17 受限政策读取。** 复用 C4 authority resolver 产生的 policy reference，在 blocked／rework 页面显示授权读取／重新授权操作；过期、错 role、错 attempt 或越界仍拒绝。
8. **#15 完整预算与传输。** 在扣回合前计算完整 candidate＋固定合同＋feedback＋上下文；用已有 artifact 读取能力或完整有序分块，保留候选原文和组装 digest。不可读、缺块或超过 provider 硬限时通知并停等，用户点击分段返修／重试后才继续；不得截断、假设模型能读本地路径或新增第二候选权威。
9. **文案。** #2 明确“实际执行命令与计划不一致”，#9 明确“计划未声明／计划路径不可执行”，两者不再用升级 Node、泛化 retry 或“忽略 finding”混为一谈。

**非目标：** 不实现 durable runner owner、run incarnation、worktree fence、统一 context evolution、自动 retry 未知 provider 副作用或扩展既有 Code Review 四动作。

**已核实主要文件：** `src/web/workspace_session/{manager/mod.rs,router.rs}`、`src/web/workspace_ws_handler/run/provider_run/entry.rs`、`src/web/coding_ws_handler/{runner.rs,socket/resumption.rs}`、`src/web/state/coding_run_registry.rs`、`src/product/coding_attempt_store/{unit_run.rs,unit_run_amendment.rs}`、`src/product/coding_workspace_engine/{coding.rs,rework.rs,gates.rs,plan_defect.rs,group_completion.rs}`、`src/product/coding_models/{execution.rs,gate.rs}`、`src/product/cadence_skills/routing_reference.rs`、`src/product/logical_codebase/{evidence_token.rs,evidence_mediator.rs}`、`src/product/workspace_engine/prompts/human_gate_revision.rs`。

### 5.3 C4：`logical-codebase-bootstrap-and-repair-surface`（4–7 人日）

**范围：** GAP-A／B／C／D，以及 C2 政策读取所需的 LC authority 路由；不把单仓自动化塞进 LC 冷启动，也不放宽 LC gateway。

1. **唯一 resolver。** 在既有 `RepositoryRouting` 和 LC stores 上统一 authority 路径。明确 LC ID 时只读 LC 子树；单仓只读合法物理仓布局。旧项目级布局和目标冲突时 fail-closed，产品显示迁移／核验，不提供猜路径 fallback。
2. **按步骤停等。** 复用现有 registration／index operation 及步骤事实，GET 只返回缺失步骤和合法“准备／继续／重试”动作。没有 active index 的首建从成员、checkout、manifest、policy 起步；任一步失败都由用户点击继续，不在只读请求里启动 provider。
3. **Failed journal repair。** repair 入口直接读取 journal／registry／authority，不依赖已失败的普通仓列表。安全 prefix 可按 digest 继续；mapping 冲突需用户提交明确映射并重新核验。产品操作完成前不切读，不删 journal、不改 JSON。
4. **规则与能力预检。** 准入前检查实际 provider 将消费的规则和 capability；缺失显示准备按钮，完成后回原链。能力来自实际 adapter／gateway 谓词，不能写一条记录假装支持 Pi 或绕开网关。

**非目标：** 不建设新的通用 durable operation 平台，不自动重复未知 provider 步骤，不在本轮实现 pi recipe，不把成员仓逐个手工铺底列为验收步骤。

**已核实主要文件：** `src/product/logical_codebase/{repository_routing.rs,issue_selection.rs,planning_context_resolver.rs,provider_capability_store.rs,migration_executor.inc.rs,migration_types.inc.rs}`、`src/product/logical_codebase/aggregate_index/operation.rs`、`src/web/workspace_ws_handler/run/single_candidate.rs`、既有 repository registration／initialization handlers。

**受影响 specs：** `logical-codebase-aggregate-index`、`logical-codebase-registration`、`web-runtime-repository-routing`、`project-rule-aware-prompts`、`session-policy-envelope`。登记仍保持零成员仓 Git 写副作用；bootstrap 是产品明确的后续步骤。

**验收：** A03、A04；全新 LC 不手工 seed，安全中断通过产品按钮继续，mapping 未裁决不切读。

**范围：** GAP-I／J 和单仓自动化入口承诺；复用 C1 的 target／绑定、C2 的 runner／门和 C4 的路由，不复制生命周期实现。

### 5.5 共享边界和实施顺序

## 6. 终局验收：双载体、自动推进＋人到点、故障注入

### 6.1 四格硬门槛

| 单仓／手动对照 | 人准备 plan、处理 choice、compile、advance、人工 StartCoding、coding、FinalConfirm | 自动 prepare／advance／首启计数为 0，原手动路径不回归 |

### 6.3 横贯验收与零绕行

- **零手工铺底：** 新单仓／LC 的规则、selection、manifest、policy、capability、index、identity journal、enrollment 和 child binding 均只能经产品操作产生；测试者不得手工复制文件。
- **零直接改数据：** 不编辑 `repos.json`、权威 JSON、journal、lock、unit_run、consumed、context note 或 findings 来脱困。故障注入只能制造指定失败；修复必须使用页面／REST 产品动作。
- **零重启服务：** 不以重启服务清 registry、释放锁或维持进度；可关闭浏览器、执行页和 coding socket，不能依赖常驻 driver／setsid／ping。
- **通知真实：** 每个注入均留 inbox／系统通知、对象身份、原因、按钮、操作人和结果；通知投递失败只允许补读，不得把“未通知”当成功。
- **单发与权限：** 每个用户操作使用稳定 command key；同命令竞争至多一个效果，旧版本、错目标、多 target、旧回执 fail-closed。未知 provider 副作用不宣称 exactly-once，必须转人工停等。
- **真实闭环：** 留存 project／issue／plan／revision／attempt IDs、部署版本、timeline／journal、真实 provider 输出、commit 区间、验证结果、FinalConfirm 回执和最终状态。未达到双载体自动 plan＋coding 全流程不关闸。

估算单位为单人工作日，包含对应 change 的 OpenSpec delta、实现、定向回归、故障注入和产品面验收，不把外部账号恢复、用户点击等待或 provider 不可用时间算作开发投入。

|---|---:|---|---|

|---|---|---|
| 出错后自愈 vs 产品停等 | 推荐通知＋按钮；失败可解释、用户掌握风险，符合自动推进＋人到点 | 全自动迁移／盲重无法确认外部副作用，且扩大本轮范围 |
| 全局 owner/fence vs 最小互斥 | 推荐现有 claim／锁上阻止双 coding 进程 | 全局 fence 体系成本高，当前驾驶舱已有人工裁决可兜底 |
| 统一 context evolution vs 单次事务 | 推荐现有 instruction／note 记录上的一次 prepare／consume／spawn 事务 | 新服务会制造第二套权威；本轮只需避免 #18 自撞 |
| durable bootstrap 平台 vs 既有步骤操作面 | 推荐复用 registration／index operation，每步通知、重试、继续 | 新平台属于体系建设，用户明确要求把死机变停等而非建设 durable operation |
| 单仓伪装 LC vs target union | 推荐真实 `RepositoryRecord.id` target union | 伪装会错误触发 LC gateway、snapshot 和 policy 路由 |
| 本轮实现 pi recipe vs 延期 | 按用户裁决暂缓，Claude 可用时走现有 recipe，503 停等 | 现在做 pi 会扩大初始化 provider、adapter 和产物验收范围；不得以伪造 recipe 关账 |

迁移原则：只对现有数据做读取、校验和产品动作写入；不清历史、不删 journal、不引入 deprecated alias 或两套 bind 规则。能明确核验的历史绑定可作为当前版本；无法核验或曾被直写破坏的状态进入诊断／重绑等待，由用户点击恢复，不自动信任也不永久堵住入口。

## 1. 目标与非目标

### 1.1 目标

1. **按阶段取得最小充分规则集**：阶段路由先确定产物阶段及角色，再从当前项目本地标准 cadence 模板中选择该阶段的必取规则、相关规则及可选关键段；不再用一套“大而全”规则集合覆盖所有 prompt。
2. **把弱引用升级为精选内容**：对 Legacy 生成链路，保留 relax-gate 的“规则缺失不阻塞候选生成”语义，但将原来的路径指针升级为可消费的精选摘要/关键段，并写入读取诊断；不恢复全量强制读取。
3. **标准化且可枚举**：aria 与 cadence-skills 深度绑定；所有平台项目安装同一套 cadence 模板，规则 ID、阶段 ID、内容形态、预算和失败语义可枚举、可校验、可观测。
4. **保护项目本地权威**：规则正文始终读取目标项目本地文件。aria 只内置 schema、读取器、默认安全策略和兼容映射，不内嵌规则正文，以避免跨项目同名规则漂移造成错误注入。
5. **先交付 Work Item**：阶段 2 精确实现 Work Item 规划链路所需的阶段规则获取；其余阶段仅建立登记和接口约束，待阶段 2/3/4 全部完成后统一实施。

### 1.2 非目标

- **不改 Coding/交互的强制式链路**：既有 Legacy coding 与交互入口继续完整读取、读取失败关闭；其强制安全语义不因本设计的生成注入机制而改变。
- **不回退 relax-gate 的不阻塞语义**：生成类 Legacy 路径读不到规则时不得阻塞候选生成；但不得再出现“读不到就忽略规则”的裸台阶，必须跳过该规则并写出诊断。
- **阶段 2 不实现全阶段规则注入**：Story、Design、Coding 各角色、交互、Logical 聚合 author 均不在本切片落地；它们只在矩阵和 defer 登记表中定义目标契约。
- 不把规则正文硬编码到 aria，不把项目差异规则复制到平台内置资源，不新增 Provider、CI、Hook、CLI 或持久化评估语料。
- 不借本设计调整 Work Item Canonical Contract、Validator、Draft 接受门禁的既有业务语义；必要的 prompt 组装改动须保持现有结构化输出和校验契约。

## 2. 背景、事实与设计原则

### 2.1 直接采信的现状事实

以下事实来自 researcher 核实结果，本设计不再重复猜测：

- 标准 cadence 项目规则全集为纯 Markdown、零元数据：`language.md`（每种语言约 0.25 KB）、`markdown-format.md`（约 0.6 KB）、`code-usage.md`（约 1.1 KB）、`code-reading.md`（约 5.2 KB）、`document-storage.md`（约 7.5 KB）、`mcp-servers.md`（约 13.5 KB，混合大文件，必须支持子节级选取）；可选 `playwright.md`（约 4.3 KB）和旧遗留 `serena-usage.md`。
- `AGENTS.md`/`CLAUDE.md` 中存在 cadence-managed L0 块，用于阶段路由表；`cadence/project-rules/` 是用户层项目差异，项目间差异较大。
- 阶段全集为 S1–S14：S1 story author、S2 design author、S3 plan-SC author、S4 work item author、S5 legacy outline、S6 legacy draft（含 batch）、S7 spec reviewer、S8 revision-repair、S9 交互会话入口、S10 coding 各角色、S11 code review、S12 group 终审、S13 Logical 聚合 author、S14 image_create（图像生成边缘阶段）。
- `routing_reference.rs` 目前有四类链路：Legacy 生成类（S1–S8）使用“按需查阅、读不到就忽略”的指针式弱引用，规则正文不进 prompt，这是 codex 英文输出等问题的根因；Legacy coding/交互使用完整读取、失败关闭；Logical 使用 digest/policy 门禁。
- 8-21 relax-gate 的动机必须保留：约 16 KB 规则全文挤占上下文、弱模型结构化生成失败率增加、路由规则对生成本身无语义贡献。新设计采用“选择性内容注入”，不是全量强制注入。
- 平台已有内容式注入先例：`web/workspace_context` 手写 `[code_reading_contract]`，code review 内联代码规范清单；早期 v1 模板有“阶段→必读规则”列，v3 简化时删除。
- 跨项目同名规则内容并不完全一致，因而 aria 不得嵌入正文，必须读取项目本地文件。
- 预算基线：S3 SC author prompt 实测 17,278/18,000 字节，仅余 722；legacy draft 约 15,600 字节；reviewer 预算 64 KiB。规则注入须在已有 prompt 预算之内治理，而不是另起无限预算。

### 2.2 设计原则

| 原则 | 设计含义 |
|---|---|
| 本地权威 | manifest 只声明文件与段，实际正文来自 `project_root` 下已校验的本地路径；拒绝绝对路径、`..` 穿越和外部 locator。 |
| 最小充分 | `必取`表示该阶段缺失会失去基本可执行性；`相关`表示在有预算时注入，缺失可继续；`无关`不读取、不占预算。 |
| 生成不阻塞，安全不降级 | Legacy 生成读取失败=跳过+诊断；coding/交互原有强制链路不改变；Logical policy 门禁不因本设计绕过。 |
| 内容而非指针 | 生成 prompt 至少获得短摘要或关键段，不能仅得到“请去读某路径”的地址；全文件只用于确实小且不具稀释风险的规则。 |
| 可解释、可追踪 | 每个注入片段有 rule ID、文件相对路径、版本/摘要 hash、选取 section、字节数、结果状态；诊断落盘但不写入候选 JSON。 |
| 预算先验 | 每阶段有常量化质量预算和硬上限；超限按既定降级序列处理，并记录降级原因。 |
| 兼容优先 | 未安装新 manifest 时使用 aria 内置兼容映射选择旧文件；映射只负责选择，不复制正文；迁移有可观测 warning。 |

## 3. 术语、阶段与规则全集

### 3.1 规则层级与规则 ID

本设计把“项目规则”拆成四个可枚举层级。层级不是优先级替代物；同一 ID 的本地文件优先于兼容默认值，冲突通过 manifest 校验和诊断暴露。

| 层级 | 规则 ID | 典型来源 | 是否进入阶段矩阵 |
|---|---|---|---|
| L0 阶段路由 | `l0.phase-routing` | 当前项目 `AGENTS.md`/`CLAUDE.md` 的 cadence-managed 块 | 是；所有阶段至少相关，作为路由输入而非大段正文 |
| L1 标准框架规则 | `std.language`、`std.markdown-format`、`std.code-usage`、`std.code-reading`、`std.document-storage`、`std.mcp-servers` | 项目本地 `.claude/rules/*.md` | 是 |
| L1 可选工具规则 | `opt.playwright`、`opt.serena-usage` | 项目本地 `.claude/rules/*.md` 或模板兼容目录 | 是；无安装时状态为未安装，不视为错误 |
| L2 项目差异规则 | `project.rules`（由 manifest 展开到具体相对路径/条目） | `cadence/project-rules/` | 是；按阶段和项目 manifest 条件选取 |

`std.language` 可以展开为语言子规则（如 `std.language.rust`、`std.language.typescript`），但对外矩阵先以 `std.language` 作为列，读取器根据项目声明的语言集合选择对应文件；不因 aria 自身是 Rust 而注入 Aria 的构建规则。

### 3.2 内容获取状态

- **必取**：阶段完成其最低可信产物所需，默认形态为精选关键段；读取失败不自动阻塞 Legacy 生成，但必须产生 `required_rule_unavailable` 诊断并在后续 gate/审计中可见。若该阶段属于原有强制式 coding/交互，则沿用失败关闭。
- **相关**：对特定任务有帮助但不构成最低门槛；预算足够则注入摘要/关键段，缺失仅诊断。
- **无关**：不应读取或注入；若 manifest 将其列为必取，manifest 校验报配置错误并回退到安全默认选择。
- **条件**：矩阵中以“必取（条件）”或“相关（条件）”标记；条件由语言、是否代码阅读、是否 UI、是否已有项目规则等确定，不能由 Provider 猜测。

### 3.3 阶段语义

S3 是 Work Item Plan 的 SC（split/structural context） author，负责把已确认 Story/Design 语义拆成 Outline；S4 是 Work Item author 的阶段总称；S5/S6 是当前 Legacy Work Item 生成实际使用的 Outline/Draft 分支；S7 只在 Work Item 分支验证候选结构和规则遵循；S8 负责返修/repair，不重新发明上游规则。

S14 已按父编排器裁决登记为 `image_create` 图像生成边缘阶段：与规则相关性低，只有 `std.language` 的通用交流语言条件相关；本设计不推断其图像生成内部语义，也不把它纳入阶段 2 实施。

## 4. 规则×阶段必取矩阵（全貌）

### 4.1 判定口径

矩阵覆盖 S1–S14 与全部规则列。单元格格式为“**必取/相关/无关**（注入形态；理由）”。“必取”不是“全文塞入 prompt”：正文只按第 5 节选择摘要/关键段；`l0.phase-routing` 默认只取已解析的当前阶段行。对于 S5/S6，`std.code-reading` 与 `std.mcp-servers` 的必取是有意设计，不代表把 5.2 KB/13.5 KB 全文注入：前者给出可执行的阅读方式/边界摘要，后者按当前 MCP 任务子节精选。

规则列定义如下：

- **L0**：`l0.phase-routing`，阶段路由和规则选择器。
- **Lang**：`std.language`，当前目标项目语言规则。
- **MD**：`std.markdown-format`，Markdown/文档产物格式。
- **Use**：`std.code-usage`，代码变更、TDD、安全与工程规范。
- **Read**：`std.code-reading`，代码检索、结构化阅读及工具顺序。
- **Store**：`std.document-storage`，Cadence 产物路径和命名。
- **MCP**：`std.mcp-servers`，MCP 工具选择、调用和安全规范。
- **PW**：`opt.playwright`，浏览器/UI 验证规则；未安装时不报错。
- **Serena**：`opt.serena-usage`，旧遗留 Serena 规则；默认不选，只有 manifest 明确启用且阶段确需时才相关。
- **Project**：`project.rules`，目标项目差异规则，按 manifest 的阶段标签和 path-scope 选择。

### 4.3 设计立场与 Work Item 重点解释

**(1) S3/S4/S5/S6/S7/S8 是 Work Item 规则获取的第一批闭环。** S3 决定拆分是否可执行，S5 把拆分落成 Legacy Outline，S6 把单项/Batch Outline 转为 Draft，S7 校验候选，S8 只修复已识别问题，S4 是这些 Work Item author 语义的统一 profile。即便 S3 产出的是 Outline 而非代码，`Read` 与 `MCP` 也不是装饰：计划必须知道真实符号、调用关系、测试命令、仓库边界以及必要的官方资料；没有这些事实，弱模型会以猜测补齐任务，导致跨文件范围错误和无效命令。

**(2) `std.code-reading` 的注入形态。** S3/S5/S6 不注入 5.2 KB 全文，而注入一个不超过 900 B 的“执行摘要”：先使用 CodeGraph 建立全局视图；再使用 `ast-grep outline` 取得文件/符号结构；最后只定向阅读所需区间；冲突以 outline 为准；不得用宽泛全文扫描替代。S4 的 Work Item 文本只带约 600 B 的可执行关键段，确保每个 item 的 `scope`、`forbidden_scopes`、`verification_intent` 可追溯到事实。S7/S8 只带审查/修订所需关键段，避免把规则变成重复的审查模板。

**(3) `std.mcp-servers` 的注入形态。** 13.5 KB 混合大文件不得全读进 prompt。manifest 将其声明为 section selectors，例如 `mcp-selection`、`mcp-read`、`mcp-search`、`mcp-security`；S3/S5/S6 只选当前流程实际可能调用的工具子节，默认上限 1,200 B，且将工具名/触发条件/失败处理保留为原子段落。若任务不需要 MCP，仍可在诊断中记录“必取策略已评估、未发现可用子节”，但不伪造规则正文。读取器不得因为规则文件是 Markdown 就把所有标题当成安全可注入；未匹配 section 的必取规则产生诊断。

**(4) `project.rules` 不是标准规则的替代品。** Work Item 阶段必取的是当前项目 manifest 明确适用的构建/测试、目录、仓库边界和 Work Item 特有约束；其 path-scoped 条目只有当目标路径与作用域相交时注入。项目规则与标准规则冲突时，平台不静默覆盖：保留两者来源和冲突诊断，安全边界（TDD、OWASP、路径禁止写入）取更严格者，产品/命名差异交人工确认。

**(5) 必取不等于阻塞。** 对当前 Legacy 生成链路，S3–S8 的规则文件读不到时跳过缺失片段并写 `required_rule_unavailable` 诊断，继续生成候选；候选随后在 S7/人工 gate 看到缺失诊断。只有原有 Direct（S10/S9）及 Logical policy 门禁按其既有失败关闭语义阻塞。这样“必取”表达质量与可审计要求，不暗中把 relax-gate 改回生成前置 gate。

## 5. 机制设计

### 5.1 推荐总方案：本地 manifest 驱动的 Phase Rule Assembler

推荐实现一个平台内的 **Phase Rule Assembler（阶段规则组装器）**，它只负责“解析阶段→选规则→读本地内容→裁剪→注入→记录诊断”，不负责改变业务阶段状态。调用链如下：

```text
workspace/provider invocation
  → 解析 workspace_type + 当前 stage + role + 目标语言/路径
  → RuleSelectionRequest
  → 读取并校验当前项目 cadence/project-rules/manifest.yaml
  → 按 profile 选出 required/relevant 条目
  → 以 project_root 为唯一根读取本地 .claude/rules 与 cadence/project-rules 文件
  → section 级选择、摘要/关键段裁剪、预算治理
  → 注入 [phase_rules]（正文 + 来源/摘要 hash/选择信息）
  → 记录 RuleInjectionDiagnostic（不写入候选 artifact JSON）
```

组装器的输入必须包括 `project_root`、`target_path`（若有）、`stage_id`、`role`、`workspace_type`、项目语言集合、当前 prompt 已用字节和本阶段规则预算。它不得只凭 Provider 的自然语言猜阶段，也不得从目标 worktree 猜同名规则路径。阶段 ID 先由现有 L0 路由解析并做白名单校验；未知阶段只允许走安全的“无规则+诊断”配置，不得默认为 S4。

建议在 aria 中定义不可变的协议类型（名称为设计名，待实现时按模块惯例落点）：

- `RuleManifest`：manifest schema、模板版本、规则来源和 profile。
- `RuleEntry`：rule ID、相对路径、可用 section、阶段选择、作用域和摘要策略。
- `RuleSelectionRequest` / `RuleSelection`：请求上下文和最终选择结果。
- `RuleContent`：来源、section、形态、UTF-8 字节数、摘要 hash、正文。
- `RuleInjectionDiagnostic`：读取/解析/截断/冲突/降级状态及错误原因。

`[phase_rules]` 注入块必须带稳定的边界和来源，但不应把诊断对象完整放进 Provider prompt：

- 正文前声明 `stage_id`、`role`、`manifest_revision`；
- 每条内容标出 `rule_id`、`section_id` 和目标项目相对路径；
- 内容仅陈述该段原文/规范化摘要，不添加 aria 的臆造解释；
- 末尾声明“规则仅约束当前阶段候选产物；Provider 不写入 canonical artifact”，避免与既有 Work Item Draft 合同混淆；
- JSON 候选 schema 不增加 `rule_*` 字段；来源和诊断走 timeline/execution diagnostic 或独立 `.aria` 记录。

### 5.2 元数据来源的核心决策

#### 方案 A（推荐）：cadence-skills 模板升级，提供 manifest

所有平台项目继续安装同一套 cadence 模板，模板新增一个由 Cadence 维护、项目可校准的 `cadence/project-rules/manifest.yaml`。规则正文仍放在项目本地 `.claude/rules/`；manifest 只描述机器可枚举的身份、section、阶段 profile 和作用域。项目可以增加 `project.rules` 条目，但不能把标准规则 ID 偷换为项目自定义语义。

建议形态如下（仅为协议示例，实际正文不内嵌）：

````yaml
schema_version: 1
 template_id: cadence-standard
 template_revision: "2026-08"
 rules:
   - id: std.code-reading
     source:
       file: .claude/rules/code-reading.md
       format: markdown
     sections:
       - id: outline-first
         selector: heading:核心原则
       - id: codegraph
         selector: heading:CodeGraph 与 ast-grep 分工
       - id: workflow
         selector: heading:命令使用方式
     profiles:
       s3_plan_sc:
         required: true
         injection: key_sections
         sections: [outline-first, codegraph, workflow]
         budget_bytes: 320
       s5_legacy_outline:
         required: true
         injection: key_sections
         sections: [outline-first, workflow]
         budget_bytes: 420
       s6_legacy_draft:
         required: true
         injection: summary
         sections: [outline-first, workflow]
         budget_bytes: 360
   - id: std.mcp-servers
     source:
       file: .claude/rules/mcp-servers.md
       format: markdown
     sections:
       - id: selection
         selector: heading:MCP 工具使用规范
       - id: codegraph
         selector: heading:CodeGraph MCP
       - id: security
         selector: heading:智普 MCP 通用说明
     profiles:
       s3_plan_sc:
         required: true
         injection: key_sections
         sections: [selection, codegraph, security]
         budget_bytes: 240
       s5_legacy_outline:
         required: true
         injection: key_sections
         sections: [selection]
         budget_bytes: 240
 project_rules:
   - id: project.build-test
     source:
       file: cadence/project-rules/build-test-commands.md
     scopes: ["src/**", "tests/**"]
     profiles:
       s3_plan_sc: {required: true, injection: key_sections, budget_bytes: 180}
       s6_legacy_draft: {required: true, injection: summary, budget_bytes: 180}
````

> 上述 YAML 中首层缩进仅用于展示 schema，落地时必须通过 YAML 解析器校验。section selector 以稳定 `section_id` 为主，标题只作为当前 Markdown 的可读映射；不能依赖易变的行号。

Manifest 校验要求：

1. `schema_version`、`template_id`、rule ID、阶段 profile、`injection` 枚举和 section 引用必须合法；重复 ID、越权路径、非法 scope 直接标为 manifest 配置错误。
2. `source.file` 必须是项目根下相对路径；规范化后不得越过根目录，不接受 `file://`、HTTP 或绝对路径。读取器对 symlink 也须检查最终路径仍在允许根内。
3. 标准规则的 `source.file` 必须指向项目本地模板副本。manifest 可携带 `content_sha256` 作为漂移诊断，但 hash 不对不应在 Legacy 生成路径自动阻塞。
4. `profiles` 只声明选择策略，不允许给标准规则正文增加自然语言覆盖；项目差异应由 `project.rules` 独立条目表达。
5. 规则缺少 section 时，按“该 section 未提供”诊断；不得把整文件偷偷当作替代，以免混合大文件突破预算。

#### 方案 B（备选）：aria 内置“文件名→阶段”映射

aria 仅内置 `std.code-reading → S3/S5/S6` 等映射，运行时按约定文件名读取本地文件；不要求 cadence-skills 仓立即升级。优点是初期改动小、旧模板可工作；缺点是无法表达 MCP 混合大文件的 section、项目 path-scope、规则版本/漂移，也把 cadence-skills 与 aria 的深度绑定降格为隐含约定。新增或重命名规则必须同时升级 aria，跨项目变体更难解释。

**取舍结论**：A 是标准路径，兑现“所有项目同一套模板、规则集可枚举”的平台契约；B 仅作为旧项目兼容 fallback，且映射表只选择本地文件，不包含正文。manifest 缺失时加载 B 并产生 `manifest_compat_fallback` 诊断；不允许把 fallback 永久当作新项目的成功配置。

### 5.3 注入形态：整文件、摘要、关键段与混合大文件

| 规则规模/形态 | 默认策略 | 适用说明 |
|---|---|---|
| 小且稳定（`language.md`、`markdown-format.md`） | 全文或规范化摘要 | 小文件全文不超过该阶段预算才允许全文；若预算不足仍降为摘要。 |
| 中等且包含多个主题（`code-usage.md`、`document-storage.md`） | 关键段 | 只取 TDD/安全、路径/命名等当前 profile section；删除介绍、重复示例和不相关平台说明。 |
| 结构化阅读规则（`code-reading.md`） | 执行摘要 + 关键段 | 至少保留 CodeGraph→`ast-grep outline`→定向精读顺序、冲突处理和禁止宽泛扫描；不注入约 5.2 KB 全文。 |
| 混合大文件（`mcp-servers.md`） | section 级关键段 | 先按 MCP 工具/触发场景筛选，最多只取 manifest 选定 section；禁止以文件前 N 字节、简单截断或全文摘要替代安全/失败语义。 |
| 项目规则 | path-scoped 关键段 | 仅注入与目标产物/代码路径相交的条目；保留项目命令和目录差异，避免使用 aria 当前仓库命令兜底。 |
| 旧遗留 Serena | 默认不取 | 只有 manifest 显式启用、工具确实存在且当前阶段触发时，才注入简短相关段。 |

摘要必须是确定性生成（标题、规范化段落、清单项优先），而不是每次调用一个 Provider 生成摘要；这样可测试、可 hash、可复现。超出字节上限时按完整段落降级，不得在 UTF-8 字节中间截断，也不得保留未闭合的结构标记。规则正文不应凭“引用路径”让 Provider 自己读取：**生成阶段得到精选内容，路径仅用于来源与诊断**。

### 5.4 读取时机和失败语义

#### 读取时机

1. **阶段路由时**：读取 L0 阶段路由，确定 S1–S14 和 role；不在 Provider 输出后才补读，因为那已经无法影响候选质量。
2. **生成 prompt 组装前**：为 S3、S5、S6 选择规则，形成冻结的 `RuleSelection`，随本次 run 的 prompt 记录 manifest revision 和各内容 hash。
3. **S7 reviewer 前**：重新按 reviewer profile 组装（允许与 author profile 不同），但使用同一工作区快照/manifest revision；发现漂移时诊断，不把 reviewer 偷换成 author 规则。
4. **S8 repair 前**：沿用原始失败 run 的 selection 作为基线，再补充 repair profile 的关键段，防止修复过程获得比原始 author 更宽的未审范围。
5. **每次 resume/retry**：重新校验文件和 manifest hash；若发生变化，保存新 selection 版本并在诊断中标记 `rule_snapshot_changed`，不静默复用旧正文。

#### 失败语义

| 场景 | S3/S5/S6/S7/S8 Legacy 生成 | S9/S10 Direct 链路 | S13 Logical 链路 |
|---|---|---|---|
| manifest 缺失 | 使用兼容映射，继续；诊断 `manifest_compat_fallback` | 保持现有强制读取门禁 | 保持现有 policy/digest 门禁 |
| 必取文件不存在/不可读 | 跳过该片段并继续生成；诊断 `required_rule_unavailable`，后续 gate 可见 | 失败关闭，沿用现有语义 | 未加载有效聚合政策则失败关闭，不能降级为目标仓同名文件 |
| section 不存在/解析失败 | 跳过该 section；诊断 `rule_section_unavailable`；不扩展为全文 | 失败关闭或沿用现有 Direct 处理 | policy 内容不可验证则失败关闭 |
| 预算不足 | 按第 5.5 节降级；至少保留选择结果和诊断 | 不改变已有强制链路 | 不绕过 policy；内容裁剪只能在已验证 policy 内进行 |
| 规则冲突/版本漂移 | 两来源均记录，取安全更严格约束；业务差异进入 reviewer/human gate | 原有安全门禁优先 | 以已验证 policy 的 digest/authority 为准 |

这保留 relax-gate 的“不阻塞生成”精髓，同时消除“读不到就忽略规则”的裸台阶：每次跳过都有结构化诊断，且 S7/人工确认能看见缺失和降级。诊断不得要求 Provider 自行补字段，避免破坏 Work Item Draft 的封闭 schema。

建议诊断落盘为平台已有 execution/timeline diagnostic 机制下的事件，并有独立可检索的文件兜底，例如 `.aria/diagnostics/rule-injection/<session_id>.jsonl`；准确存储 API 在实现计划阶段根据现有诊断 store 确认，不在本设计凭空创建第二套事实源。每条记录至少包含：`session_id`、`node_id`、`stage_id`、`rule_id`、相对路径、manifest revision、section ID、selection 形态、原始/注入字节、状态、错误码、content hash、时间戳。严禁写入规则外的认证信息、完整 Provider prompt 或项目敏感语料。

### 5.5 预算治理与降级

预算必须是代码常量 + 测试 fixture 的双重契约，而不是凭感觉调字符串。定义两个层次：

- **质量预算 `phase_rule_quality_budget`**：规则正文可占本阶段 prompt 的目标预算，默认不超过当前总 prompt 预算的 5%～10%。
- **硬上限 `phase_rule_hard_cap`**：异常 manifest/巨大 section 的保护上限；超过则不组装正文，返回降级诊断。它只保护上下文，不替代质量预算。

阶段 2 初始常量（草案，需 oracle 评审后固化）如下：

| profile | 规则内容质量预算 | 硬上限 | 预算依据 |
|---|---:|---:|---|
| `s3_plan_sc` | 640 B | 1,024 B | 实测 prompt 17,278/18,000，仅剩 722；先保守留 82 B 余量，后续若瘦身再提高。 |
| `s4_work_item_author` | 800 B | 1,280 B | Work Item author 需保留项目差异和 TDD 摘要，但不可挤占 Canonical Contract。 |
| `s5_legacy_outline` | 1,024 B | 1,536 B | Outline 需保留阅读顺序、可信命令与存储边界。 |
| `s6_legacy_draft_serial/batch` | 1,024 B | 1,536 B | Legacy draft 现约 15,600，优先注入精选摘要，避免再次挤压结构化输出。 |
| `s7_work_item_reviewer` | 4,096 B | 8,192 B | reviewer 总预算 64 KiB，但规则仍不能吞掉候选、证据和 finding 空间。 |
| `s8_work_item_repair` | 1,024 B | 1,536 B | repair 继承原 selection，额外内容不得扩大上下文。 |

实际可用预算取 `min(quality_budget, hard_cap, provider_context_budget - prompt_without_rules - safety_reserve)`。`s3_plan_sc` 的 640 B 只是规则块总量，内部优先级为：Read 摘要/关键顺序 320 B、MCP 选择与失败纪律 240 B、项目差异/L0 元信息 80 B；标准语言/Markdown 等若已在 runtime contract 中出现，只保留来源 ID，不重复注入正文。这样满足 S3 对 MCP/代码阅读规则的实际需要，同时不重蹈 8-21 的上下文挤占动机。

超限的确定性降级序列：

1. 移除 `相关` 项和可选 Playwright/Serena；
2. 将 `Project`/中型标准规则从关键段降为摘要；
3. 缩减必取规则到 manifest 标记的最小原子段（标题、操作顺序、失败语义）；
4. 保留必取规则 ID、section ID 和一行“该段未注入”的诊断引用，正文块标记 `degraded`；
5. Legacy 继续候选生成，S7/人工 gate 对 `required_rule_unavailable` 或 `rule_budget_degraded` 做可见提示；Direct/Logical 仍遵循其既有失败关闭门禁。

禁止静默超预算、禁止自动把全文件塞入 prompt、禁止为省字节删除“失败语义/安全边界/可信命令不可猜测”等原子约束。每个 profile 都必须有最大 fixture 测试：断言 UTF-8 字节数、必取规则 ID、关键禁令短语、section 边界和降级诊断；真实 Provider 验证仍不自动调用，遵循项目现有授权规则。

## 6. 与 relax-gate / REQ-WSC-06 的契约关系

### 6.1 现有契约冲突点

`relax-legacy-rule-read-gate-for-generation` 已把 `direct_cadence_routing_rules_reference` 拆出 `generation_cadence_routing_rules_reference`：Legacy 生成类按需查阅、规则缺失不阻塞；coding 和交互继续使用 direct 强制式；Logical 继续 policy/digest 门禁。该改动的关键动机是避免约 16 KB 全读挤上下文、弱模型结构化生成失败和无语义路由文案，而不是永久允许生成器没有规则内容。

`REQ-WSC-06` 又要求 Work Item author/reviewer prompt 只承载产物规格、任务上下文、输出语法、边界和判例，不重复已注入的通用行为教学（Superpowers/OpenSpec/项目规则）。两者并非要求相反内容：本设计的 `[phase_rules]` 是按阶段精选的项目规则事实注入；必须去重已在 runtime contract 出现的泛化句子，并把规则选择的可审计信息放到 diagnostic，而不是把原规则全文再复制一遍。

### 6.2 必需的 OpenSpec delta

需要对 `relax-legacy-rule-read-gate-for-generation` 与 `rearch-workitem-plan-pipeline` 中 `REQ-WSC-06` 提出 delta，且先由用户/评审批准后再实施：

1. **generation 语义从“指针式按需查阅”升级为“精选内容式按需注入”**：Legacy S1–S8 生成类在 prompt 组装阶段按 profile 读取目标项目本地规则的摘要/关键段；不能只注入路径指针；选取规则和预算需持久化诊断。
2. **保留不阻塞和失败语义**：Legacy 生成遇到 manifest/文件/section 读取失败时继续候选生成，产生结构化 `required_rule_unavailable`/`rule_section_unavailable` 诊断；不能把生成失败或阻塞作为默认结果。
3. **新增规则选择与去重契约**：`phase_rules` 必须列出 stage/profile、来源 rule ID 和 section；已由 runtime contract 完整承载的通用教学不得在规则块重复注入。规则正文必须来自项目本地文件；aria 不得嵌入固定正文。
4. **补充混合大文件与预算契约**：`mcp-servers.md` 只能按 section selector 选择；每阶段质量预算/硬上限和超限降级顺序确定性执行，并记录诊断。
5. **修订 REQ-WSC-06 的边界表述**：Work Item prompt 仍不得重复通用行为教学，但允许注入本阶段必取规则的“最小、项目本地、可追踪内容片段”；该片段不是 Superpowers/OpenSpec 教学，也不是 aria 内置规则复制。author/reviewer 的 output schema、Canonical validator、projection 和不写 canonical 的边界不变。
6. **明确 Direct/Logical 保护条款**：S9/S10 Direct 继续完整读取、失败关闭；S13 Logical 继续依赖 policy/digest/authority root，不接受 Legacy fallback。该 delta 不能被解释为全平台统一 relax。
7. **增加诊断可见性场景**：未加载必取规则的候选可以生成，但后续 S7/human gate 必须能够看到缺失/降级记录，并可据此选择重试、人工确认或返修；不得新增候选 JSON 字段规避封闭 schema。

这些 delta 使 relax-gate 回应其原始动机：减少上下文无效开销和模型注意力稀释，同时恢复规则对生成的实际语义贡献；它不是简单回退到全量强制读取。

## 7. 阶段 2 落地切片：Work Item

### 7.1 “Work Item 相关”的边界定义

本切片定义为：**从 Work Item Plan 的 SC/Outline 生成，到 Legacy Outline/Draft（serial/batch）、Work Item 分支 reviewer/repair，再到规则注入诊断可见性所需的共享组装器接线；不包含 coding 执行和交互强制入口。**

明确排除：S1/S2 Story/Design author、S9 交互会话入口、S10 coding 各角色、S11 通用 code review、S12 group 终审、S13 Logical 聚合 author、S14 image_create；也不改 `direct_cadence_routing_rules_reference` 的 coding/交互调用者。阶段 2 不实现跨仓 Logical policy 的全阶段规则注入，只确保 Work Item Legacy 分支不越权读取 target worktree 之外的文件。

### 7.4 TDD 测试策略

按“先失败测试、再实现”拆分以下确定性测试，不调用 Provider：

1. **manifest/schema**：合法 manifest 可解析；未知 stage/rule/injection、重复 ID、绝对路径、`..` 穿越、symlink 越界、缺 section 有明确错误/diagnostic；兼容 fallback 有 `manifest_compat_fallback`。
2. **选择矩阵**：表驱动覆盖 S1–S14 的默认选择，至少断言 S3/S4/S5/S6/S7/S8 的必取集合；S14 只选择语言摘要/弱相关项；S10/S9 不进入新生成 assembler。
3. **section 提取**：精确 selector 取完整段落，不取相邻无关段；MCP 混合大文件只取允许子节；无匹配 section 不升级全文。
4. **内容形态**：小规则在预算足够时全文/摘要可复现；代码阅读必含 outline-first、CodeGraph/ast-grep 顺序；MCP 必含工具选择/失败语义；大段降级不发生 UTF-8 半字符截断。
5. **预算/降级**：对 S3 17,278 B prompt fixture 断言规则块不超过 640 B；对 S6 15,600 B fixture 断言不超过 1,024 B；超限按“相关移除→摘要→最小原子段→诊断”顺序且不静默；硬上限错误码稳定。
6. **prompt 契约**：`build_outline_prompt*`、`build_work_item_draft_prompt`、reviewer prompt 含阶段规则来源和关键禁令，不包含整份规则正文、不增加 JSON 字段、不破坏 nonce；`direct_...` coding/交互固定文案测试继续通过。
7. **失败语义**：S3/S5/S6/S7/S8 缺失必取规则仍得到候选，但诊断可检索且进入 reviewer/gate payload；S9/S10 读失败仍失败关闭；Logical policy 仍不能 fallback。
8. **路径与跨产物回归**：本切片虽只接 Work Item prompt，必须确认 Story/Design/Work Item 三种 workspace type 的共享 routing/diagnostic 逻辑没有被错误改变；若共享层测试触及三者，补齐三种表驱动 fixture；明确 Story/Design 只保持原行为。
9. **门禁**：`cargo fmt --check`、定向 `cargo test --locked --lib <过滤名>`、`cargo clippy --all-targets --all-features --locked -- -D warnings`、`cargo check --locked`，最后按项目要求运行 `cargo test --locked`。若修改 Work Item Draft Prompt/Canonical 约束，交付前提示操作者授权 Case A、Case B 各 10 次 Claude Code 真实验证；未授权不调用 Provider。

## 9. 风险与缓解

| 风险 | 影响 | 缓解/验收信号 | 残余风险 |
|---|---|---|---|
| **模板漂移**：同名规则跨项目内容不同，manifest 与文件 revision 不一致 | 注入错误规范、项目命令错误、审查无法复现 | 正文只读项目本地文件；记录 manifest revision/content hash；兼容 fallback 明确诊断；resume/retry 检测 snapshot changed | 项目手工修改规则未及时更新 manifest，需人处理 warning；不在 Legacy 生成阶段强行阻塞。 |
| **预算挤占**：规则片段与 outline/Draft/context 争用预算 | Prompt 超限、候选字段缺失或输出质量下降 | profile 常量、质量预算+硬上限；先移除相关项再摘要化；最大真实中文 fixture；S3 保持 17,278/18,000 场景不超质量预算 | 现有固定开销仍可能增长，需同步维护 prompt 预算测试和复盘阈值。 |
| **弱模型注意力稀释**：注入过多规则正文重蹈 relax-gate 动机 | 结构化 JSON 失败、规则重点被淹没 | S3/S6 分别限 640/1,024 B；只注入与当前任务直接相关的原子段；去重 runtime contract；规则正文顺序固定 | 真实模型的注意力行为不能由确定性单测完全证明，仍需经授权的 Case A/B 验证。 |
| **“必取”被误解为强制前置** | 生成链路回退到 relax-gate 前的阻塞行为 | 明文区分必取质量语义与失败语义；Legacy 缺失=跳过+诊断；Direct/Logical 单独保留失败关闭 | 旧调用点可能误用 direct 函数，需调用点契约测试和静态审查。 |
| **“精选内容”退化为裸指针** | Provider 仍无规则语义，codex 英文输出问题复现 | `[phase_rules]` 必须含内容正文/关键段；契约测试禁止只有 path locator；诊断仅作辅助不替代正文 | 规则 section 选择器失配时只能暴露诊断，无法保证项目规则语义完整。 |
| **混合大文件被粗暴截断** | MCP 安全/失败语义消失，产生错误工具调用 | manifest section selector；完整段落边界；超限按原子段降级；禁止前 N 字节截断；mcp section fixture | 规则作者新增标题未登记时需更新 manifest，短期会有缺失诊断。 |
| **规则冲突**：标准规则与 project.rules 对同一命令/路径给出不同约束 | Provider 不确定，审查口径分裂 | 记录来源和冲突；安全边界取更严格者；业务差异进入 reviewer/human gate，不静默覆盖 | 对“更严格”的自动判定仅限枚举安全约束，语义冲突仍需人工裁决。 |
| **诊断泄露敏感信息/污染候选 schema** | 项目机密或认证信息进入持久化/Provider 输出 | 诊断只保存来源、hash、状态、字节和错误码；不存完整 prompt/token；候选 JSON 保持封闭类型 | 需对已有 execution log 做脱敏审计，确认共享诊断 store 不会复制 prompt。 |
| **S3 MCP/代码阅读规则缺失** | 计划猜测代码结构、工具选择失当 | 两者列为 S3 必取；缺失不阻塞但 diagnostic 可见；S7/gate 可据诊断返修或人工处理 | Legacy 继续生成意味着低质量候选仍可能产生，这是 relax-gate 有意保留的 trade-off。 |
| **编码/交互误接新 assembler** | 安全门禁被放宽 | 明确 direct 调用点不改；S9/S10 回归测试要求完整读取/失败关闭 | 新增共享 helper 时需 code review 检查调用方向。 |
| **manifest 路径穿越或 symlink 越界** | 读取工作区外规则、信息泄露 | 根目录规范化、拒绝绝对/`..`/外部 URI、检查 symlink 最终路径；恶意 fixture | 文件系统 race 需在实现阶段采用安全打开/再校验策略。 |

## 10. cadence-skills 侧配合项清单

以下均为 **跨仓变更，需用户另行授权 Cadence-skills 仓**；当前 aria 设计文档不直接修改 cadence-skills，不复制任何规则正文。

1. **发布 manifest schema**：在 cadence-skills 标准模板中新增 `cadence/project-rules/manifest.yaml`（或经用户批准的同等标准位置），版本至少包含 `schema_version`、`template_id`、`template_revision`、规则 ID、项目相对 `source.file`、section selector、profile、`required`、`injection`、`budget_bytes`、可选 scope 和 `content_sha256`。
2. **为标准规则登记稳定 ID 与 section ID**：登记 `std.language`、`std.markdown-format`、`std.code-usage`、`std.code-reading`、`std.document-storage`、`std.mcp-servers`、`opt.playwright`、`opt.serena-usage`；为 `code-reading.md` 的 outline-first/CodeGraph/workflow 和 `mcp-servers.md` 的工具选择/读取/安全子节提供稳定选择器。标题改变不应导致读取器默默选错段。
3. **模板副本一致性与漂移机制**：所有平台项目安装同一模板版本；manifest 的 `template_revision` 与规则文件 hash 用于诊断漂移。项目可以升级本地模板，但 aria 必须读取本地副本，不能回退到 Cadence-skills 仓远程正文。
4. **项目差异规则登记约定**：约定 `cadence/project-rules/` 条目如何声明 profile、path-scope、可信构建/测试命令、仓库边界和 Work Item 特有规则；项目差异不能伪装为 `std.*`，也不能覆盖安全门禁。
5. **section 语义维护**：规则文件改版时同步更新 section ID 和 profile；混合大文件必须有可分割的工具子节，不以单个“全文摘要”作为唯一接口。
6. **迁移/兼容说明**：旧项目没有 manifest 时，可暂由 aria 的兼容文件名映射运行并写 warning；cadence-skills 提供升级工具/文档把旧 `.claude/rules/*.md` 安全登记到 manifest。迁移不移动用户规则、不改变规则正文、不覆盖项目差异。
7. **跨仓协作契约**：Cadence-skills 仓需另行评审 schema、示例和版本策略；aria 仓只提交读取器/组装器及测试。两仓变更必须明确先后顺序：先发布模板 schema/样例，再在 aria 启用 manifest 必选检查；过渡期保持兼容 fallback。
8. **授权与回滚**：在用户未授权前，以上仅是待办；获得授权后需单独变更、review、模板安装验证。若模板升级导致项目诊断飙升，aria 可临时使用兼容映射，但不应静默忽略错误或把远端正文嵌入。

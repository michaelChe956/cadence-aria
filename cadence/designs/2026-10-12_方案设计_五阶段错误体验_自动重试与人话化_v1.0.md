### 术语与范围

owner 裁定的“五阶段”是产品生命周期叙事：**story → design → plan → coding → review**，不是新增 workspace/stage 枚举。当前 `WorkspaceType` 实际为 Story/Design/WorkItem/WorkItemPlan（`src/product/models/workspace.rs:17–22`），`WorkspaceStage` 为八种运行状态（`workspace_engine/types.rs:7–15`）；本设计不为叙事强造第五个 workspace type。

范围是四类 workspace 的**已有人类输入后的 author 修订轮统一覆盖**，SC WorkItemPlan typed turn 详设；三道防线的错误都统一人话化。Coding/review/交付保留既有门、预算与动作，只消费同源错误呈现，不新增 coding 自动返修。初始 author、既有 reviewer 自身协议修复和现有初轮教学重驱不扩授权；其原错误呈现仍要收敛到人话＋折叠诊断。

## 1. 目标与不可变约束

用户验收已遇到依赖环长 ID、`validation_reject unknown_structured_key` 与 Final Compile 目标缺失等原始错误；本设计解决的是“用户不知道下一步”，不是放松校验或把失败掩盖为成功。

1. 格式、schema、结构类机械错误，仅在已有真实人类输入授权的 author 修订链中自动携带诊断返修，最多追加两次 author 调用，不消耗用户轮次。
2. 依赖环等逻辑错误不静默改动，显示人话与明确动作；诊断原文默认折叠。
3. 范围、目标选择、取舍等真实人类决策沿用现有门；Task 9c / REQ-CFC-06 人工确认语义零变化。
4. 自动调用、候选版本、结果、升级必须可观测；不能绕过 reviewer，也不能自动 confirm。
5. 错误类别由集中 typed 分类产生；禁止运行时分散匹配错误字符串。

## 3. 错误分类：原因与处理资格分开

### 3.1 分类原则

不能把“由结构校验器发现”直接等同机械错误。当前 parser 的 `invalid_work_item_id` 同时表示 token 格式错、重复 ID、自依赖、不存在依赖和环（`parse.rs::validate_identifier` 449–475、`validate_dependencies` 508–575）；直接按 code 自动重试会把逻辑问题偷偷改掉。分类必须在产生诊断的分支赋值，不从 `message` 猜测。

以下名称均是**新增设计接口**，不是声称仓库已存在：

- `PlanningFailureKind`：带 payload 的封闭枚举，覆盖本章原因；code 是它的稳定 wire 投影，不另存可互相矛盾的 code/category。
- `PlanningFailureCategory`：`mechanical`（表达/格式）、`logical`（内容或依赖矛盾）、`human_decision`（取舍/授权），另有 `operational`（环境/协议/系统错误）防止未知错误被误当成自动修复。
- `PlanningFailureOrigin`：`author_validation`、`reviewer_finding`、`final_compile`、`runtime_guard`；同一种因果错误在不同来源仍采用同一类，但恢复入口不同。
- `PlanningFailure`：`kind`、`origin`、`stage`、`diagnostic_ref`、`source_ref/hash`、关联对象和结构化证据；行号、field、修复示例只用于定位，不参与类别猜测。
- `PlanningRecoveryDisposition`：`auto_author_revision`、`explicit_revision`、`existing_decision_gate`、`existing_operational_recovery`。这是对“类别＋当前授权上下文＋门态”的集中纯函数结果，**机械类别本身不构成自动调用许可**。

`CompilerDiagnostic` 当前是 `code/line/field/message/repair_example`（`types.rs` 63–74），应以 typed `kind` 取代自由 code 的内部权威；保留 wire 原有大码作兼容诊断维度，并新增细分 code。外部/历史未知码进入 `Unknown`，折叠保留原文、不自动返修，不使用 message 补猜细分。既有 `HumanGateTurnFailureClass::ValidationReject` 继续作为旧门失败大类，不用它承担新分类。

### 3.3 三条防线的统一处理

Reviewer 的自由文字 findings 不能可靠推导错误码；仅结构化类别/既有权威 hint 支撑分类，未标注者显示原中文建议并沿现门处置，**不新增模型分类调用**。Reviewer 输出协议坏了不等于 author 产物坏了，不重驱 author，仍走既有 reviewer repair。Final Compile 的依赖与投影错误必须保留结构化证据，不能先 `Display` 拼串再让前端拆解。存储/CAS/审批冲突不得机械重试；“用户确认了”与“编译成功了”始终是不同事实。

混合诊断按最保守 disposition：有真人决策先现门，有 operational 先现有恢复，有逻辑则显式修订，**只有整批阻断诊断均是合资格机械原因才自动返修**。不阻断的建议不扩大自动处理范围；未知 code 永不自动调用。

细分默认保守：缺 Goal/Scope/目标/意图/必需验证命令等若原授权材料没有值，不能通过“补必填字段”编造内容；`Blockers.route`、`intent`、`compatibility_policy` 等 enum 未知值也不能猜一个合法值替换，只能在原候选或已确认上下文有唯一明确等价值时机械纠正，否则逻辑/人决策。`ArtifactValidationReport.forbidden_tokens` 当前把结构污染与未解决待确认项合流（`artifact_constraints.rs:274–283`），迁移必须在源分支拆 typed 结构错与真实待确认，不能将所有 forbidden content 当格式错误。

## 4. 机械自动返修状态机

### 4.1 入口与身份

自动返修的授权证据必须是服务端已接受的**真实人类反馈 command/turn 或原有 author 修订请求**，不能仅看“有 reviewer verdict”或“review_round > 0”。推荐以 `HumanGateTurn` 的 `session_id/turn_id/command_id/feedback_text/source_hash` 为 SC 主锚；已存在的 `budget_reserved=1` 只在首次人类反馈 reservation 扣一次。自动步保持该 turn、原门、原用户 command，不调用 `handle_human_gate_feedback` 创建新轮。

准入同时要求：当前 author 修订链仍在途；整批诊断满足 §3；候选与人类授权/源版本绑定；没有终止/关门/被抢占/原生锚点 waiting；同 turn 唯一在途执行者；追加次数未到上限。初轮生成、定稿 confirm、批量 confirm、Final Compile recovery、reviewer 运行、native fresh 恢复、provider timeout/断线都不是新自动返修入口。

### 4.2 预算口径与待批交叉契约

按 owner 2026-10-12 裁定采用“最多**追加 2 次** author 修订”：纯机械失败链原调用＋两次返修，总 author 调用最多 3 次；计数在真实调用前 reservation，失败/取消也不退还。`mechanical_retry_index=1/2` 与用户轮次分开持久化。

**已发现真实交叉契约，必须在新 OpenSpec 显式批准，不在实施中自行放宽：** `conversational_gate.rs` 28–30 现 `HUMAN_GATE_PROVIDER_MAX_ATTEMPTS=2` 是单 logical turn 的真实 provider start 上限（初次＋一次恢复），`HumanGateTurn.attempt_no` / `HumanGateReservation.provider_start_idempotency_key` 是既有恢复身份。新增两次 author 不能伪装成同 key 第二次启动，也不能只把原常量改 3 让死亡恢复次数同步膨胀。新增 validation 子调用预算，所有真实 author starts 计入同一链总上限 3；既有死亡恢复仍最多一次，若恢复已消耗一个额外 start，机械返修仅剩一个 start，避免“双预算相乘”。人工门、user budget、原 confirm CAS 判据不变。

新增身份是 `(parent_turn_id, validation_step, recovery_attempt)`，与旧 turn/reservation 关联；不复用物理调用 key。已有原生锚点不安全时立即 waiting，不使用剩余预算自动 fresh。B 已获 owner 方向裁定，具体 durable schema 与 provider ledger 的交叉变更仍待 OpenSpec 审阅。

### 4.2.2 执行层与耐久接口定案

推荐并固定为**engine判定/持久化，现handler驱动provider**，不把provider I/O搬进 `revision_turn.inc.rs`，不新增 `ProviderRunKind`：

- `src/product/workspace_engine/conversational_gate_parts/revision_turn.inc.rs::run_sc_manual_revision_turn` 拆出拟新增 `assess_sc_revision_output(turn_id, output) → Accepted(PreparedRevision) | MechanicalRejected(PlanningFailureSet) | NeedsExistingGate(PlanningFailureSet)`，只计算与生成准备材料，不提前置turn Failed/轮换当前source。合法结果由原 `complete_human_gate_revision` 成功路径提交并复评。
- 拟新增engine接口 `claim_mechanical_revision_attempt(parent, failures, expected_source_hash) → Claimed{retry_index,prompt,provider_start_key} | Replayed | Waiting | Exhausted`：在原session锁/CAS内读取唯一durable retry state，推进次数、关联原授权并写入真实start reservation。handler的局部变量只缓存返回值，**不拥有预算/状态权威**。
- `src/web/workspace_ws_handler/run/provider_run.rs` 现 `HumanGateScManualRevision {turn_id,prompt}` arm 负责顺序驱动：输出→assess→claim→同原launch/gateway/full指纹的author调用→assess；最多两次追加；末端唯一一次Accepted提交或Failed升级。新的物理子key由engine给出，不重新发送人类feedback、不另开provider run kind。
- `HumanGateTurn.attempt_no` 继续表达既有provider中断恢复序号（上限2），validation index/start总数在新增durable retry state中；`provider_start_ledger` 显式列每个validation step/recovery attempt及reason，原turn字段不重置。总starts检查同时涵盖原调用，不能通过不同key绕上限。
- `conversational_gate_recovery.rs` 在原 `recover_human_gate_turn` 之前先看retry state：Claimed未start→续同claim；已有output→只恢复assess/commit；Running有真实provider→Wait；未知结果→原中断恢复且消耗剩余total start；Escalated/Resolved→不再驱动。`LcRecoveryRunContext::ScManualRevision` 继续以turn身份为锚，不伪造新native授权；显式fresh成功后只继续已冻结的当前validation step，检查原source hash与子prompt digest，不重置index/start计数。
- durable retry state放在session原子记录内（可选新字段），attempt输出与完整诊断放内容寻址artifact/节点详情；原HumanGateTurn仍独立记录且不变成人工门。这样复用原session CAS恢复模式，避免多文件counter与sidecar成为第二权威。`PreparedRevision`/`PlanningFailureSet` 等均为拟新增内部结果类型，不是已有符号。

legacy顺序固定为**替换计数权威、不增加计数器**：`plan_outline/revision.rs:374–375,433–435` 已有每人类反馈重置、三次失败上限，数值上沿用；新人类授权链的durable retry state成为唯一计算依据，旧 `work_item_plan_revision_retry_count` 不再独立递增判定，只能移除或由同状态派生供既有只读诊断。legacy初轮author计数仍原语义；draft/batch已有RepairOnce机会纳同链，不再追加独立槽。P7b需迁移所有读写点并补重启不重置与逻辑首错升级验收，不在深改/浅改之间留歧义。

### 4.3 状态与转移（新增内部状态，不新增人工门）

```text
HumanRevisionAccepted --> AuthorRunning --> ValidateCandidate
                                             |
                      +----------------------+--------------------+
                      |                      |                    |
                 valid candidate       mechanical only       other failure
                      |                      |                    |
                 ExistingEvaluate       RetryReserved        Escalated
                      |                      |                    |
                ExistingReviewer       AutoAuthorRunning    ExistingGate/Recovery
                      |                      |
                ExistingHumanGate       ValidateCandidate
```

| 当前状态 / 事件 | 动作 | 不变量 |
|----------------|------|--------|
| `AuthorRunning` 完成交付 | 保存非规范的 attempt output 证据，按现有归一化/确定性修补再执行权威校验 | 不把坏 candidate 提升成当前 artifact |
| 校验全机械且未耗尽 | 原授权＋失败 source＋typed 诊断＋grammar/修复例组装 prompt；先持久 claim/audit，再启动同 author | 不扣 user budget；不新建用户 message；不改已确认 spec/target/options |
| 自动步交付 | 同一权威校验重新完整检查；不能只验证上一错误 | 下一次额外调用与前次共用两次上限 |
| 校验通过 | 只提升最终通过 source/IR/report；按现有 `run_sc_manual_revision_turn` 后段重走 Evaluate → reviewer（已启用时）→原人工门 | 不复制/绕过 reviewer；不自动 confirm、compile、advance、publish |
| 第 2 次追加后仍失败，或转成逻辑/人决策/未知/环境错误 | 本链升级终态，原门保持开；展示最后错误人话、已经尝试的真实次数与可用动作 | 原坏产物与尝试日志保留，最后已通过 artifact 不被替换 |
| 既有运行取消、CAS 失配/另方获胜 | 沿现有取消协议停止；迟到结果不提升 | in-flight approve/abandon 仍 `gate_busy`，不新增终止绕行；不复活旧门、不重臂预算 |
| 重连 | 投影 durable retry 状态，不因 attach 再启动 | 已预约同 subcall 不重复计次/调用 |
| 重启且 attempt 有完整输出与诊断证据 | 同 claim 恢复校验/既有结果收口 | 无新增 user turn |
| 重启且物理调用结果未知、native 不可恢复 | 沿现有恢复/锚点 waiting 停等，明确告知；不盲目 fresh 或再次消费 retry | 不承诺外部模型调用恰一次；恰一次 claim 与真实 provider 启动审计分开 |

校验失误不进行指数退避或网络重试：立即顺序返修，永不并行多候选。provider 出错不是机械校验出错，自动机械链立即停并交既有运行恢复。每次新的人类明确反馈才能获得新链预算；刷新、重连、点击诊断不重置。

原SC初轮policy的 `TriggerAggregateRepair`/RepeatedFingerprint 属既有能力，不在本设计中增加次数或偷换成用户授权。新人类反馈链中发现logical/human/operational时直接升级到原合法门/恢复面，不用 `contract_prerevision` 的默认 Repairable hint把新错误悄悄送进初轮自动逻辑返修；共享的是检测与意见，不是自动路由资格。混合机械＋逻辑亦同。

### 4.4 审计与耐久性

新增 durable `MechanicalRevisionAttempt`（名称为拟新增，不修改现有 turn 语义）：关联 `session_id/parent_turn_id/parent_command_id/author_node_id`、`retry_index`、原授权及失败 `source_hash/ref`、`diagnostic_ref/fingerprint`、完整 prompt artifact ref/digest、provider start identity/run ref、状态、时间、结果 source ref、升级原因。内部 full native binding 不暴露前端。

唯一键是 `(session, parent authorization, retry_index)`；claim 与计次沿既有 session lock/CAS 模式持久化，append 事件只用于观察，不用时间线文字作为恢复权威。所有自动步骤留下 requested/claimed/started/completed 或 failed/escalated 事件；未经 durable reservation 不允许 provider start。审计存储失败则停止，不无痕重试；响应如实标为审计故障，不能宣称留痕成功。prompt 原文留既有受控节点详情，公开 DTO 只传安全摘要/ref；不复制 HOME 配置或密钥。

公开诊断继承现有脱敏边界：`ConfirmAggregateGateError::message`（`lifecycle_store/spec.rs:89–99`）已把底层load错误脱敏，不得为了“原文折叠”将原本只在服务端日志的绝对路径、HOME内容或凭据重新传到UI。折叠保留的是该用户原本有权读取的code/位置/业务证据；敏感底层诊断只给受控diagnostic ref。新增 `spec_not_found` / `confirm_gate_spec_load_failed` 均operational，confirm失败不产生author自动修订。

追加步与原 user turn 的唯一关联及 accepted feedback count 不变；在评审、artifacts、执行详情能看见实际自动步；正常主对话只保留一个“正在按反馈修订”的状态，不刷屏两条失败卡。成功后提供可展开的“格式已自动修复，自动返修 N 次”审计摘要，不冒充用户反馈。


## 5. 逻辑错误：人话映射与可执行动作

### 5.1 同源映射形状

扩展现有集中映射模式，而非各组件自由翻译。`web/src/state/protocol-error-copy.ts::protocolErrorCopy` 已提供中文 lead/body 与未知码失败关闭；规划错误以独立 typed 命名空间扩展该模式，不覆盖租约/trust/协议原语义。服务端权威 registry 决定 `kind → category/default instruction`；前端映射仅决定呈现，不决定重试许可。建议 code registry 生成 TS code/category 常量，机器校验完整映射，避免手抄两套规则。

新增设计 `PlanningFailurePresentation` 的字段：

| 字段 | 契约 |
|------|------|
| `code/category/origin` | 来自 typed 原因，禁止解析 message；未知稳定展示“本次修订未完成” |
| `title/summary_key/params` | 前端模板键＋安全参数；params 是 item 名称/短编号、已确认顺序等事实，不是任意 HTML |
| `repair_instruction` | 服务端同源中文修正指令；UI 预填与自动返修 prompt 共用，另附完整 typed 诊断/修复例 |
| `actions` | 服务端针对当前阶段提供的动作集合；前端与现有 gate/driver/blocked 判据取交集，无权从 code 推导“可确认” |
| `diagnostic_ref/diagnostics` | 原码、原文、line/field、对象完整 ID、provider attempt refs 进默认收起详情；不丢证据 |
| `retry_state/used/max` | 明确是系统自动返修次数，不显示成用户剩余轮次；max=2 追加，链真实 starts 总限=3 |
| `failure_id/source_hash/parent_turn_id` | 去重、过期与修订对象绑定；跨版本点击不能作用到新候选 |

`repair_instruction` 是建议，不是新的规格权威：不允许改变 frozen change_order、仓归属、验收范围、provider 权限或确认语义。字段可安全有界，但完整错误证据必须保留在 artifact/ref；截断展示不能成为截断修复输入。

### 5.2 人话与动作映射表（首批完整因果族）

| 原因 / 已有 code | 主显人话 | 建议内容与动作 |
|------------------|----------|----------------|
| `dependency_cycle` 或 parser typed cycle | “AI 拆分出的工作项相互等待，无法确定执行先后，已附修正意见。” | 按已确认设计与 change_order 重新拆分依赖，保留能力交接，不简单删边假通过；显示短编号＋标题的环；主按钮“填入修订建议”，然后用户沿现反馈框“提交反馈” |

| `unconsumed_required_handoff` | “声明了交接产物，但没有后续任务接收。” | 展示现有移除未用引用/补合法消费者建议；涉及新增范围由人决定；“填入修订建议” |
| `work_item_target_missing` | “这个工作项还不能对应到有效成员仓，当前没有改变目标仓。” | 列已确认合法成员及失败原因；已有明确归属时给引用纠错建议；没有授权唯一选择时按钮“查看目标并补充选择”，沿现反馈/上下文门，不自动选仓 |
| options 拆分/验收/引用校验族 | “拆分计划与已确认的选项或验收要求不一致。” | 展示具体已启用选项/真实需求 ID 和逐项动作，不用统一“格式有误”冒充；“填入修订建议” |

| operational / unknown | “当前操作未完成，需要处理运行或会话条件。” | 只显式给当前真实恢复动作；没有安全动作就指出失败事实与可达诊断/原终止入口；绝不出现万能“重试”按钮 |

标题与长 ID 分离：现有 canonical cycle `dependency.rs::report_dependency_cycles` 525–538 把环塞到 message；应保留 typed `cycle_ids/edges`，按 candidate/plan 的 ID→标题表渲染 `WI-003（界面）→WI-001（服务）`。没有映射时显示“工作项（标识尾段）”并在详情保留全 ID，不编造标题、不靠 regex 切原文复原环。

Kahn 检测的 `compile_support.rs::detect_dependency_cycle` 323–369 返回的是未能拓扑出队的相关节点，不保证每个节点都在最小环上、也不保证顺序。该来源人话应称“这些工作项的依赖阻止了排序”，不能把列表画成逐项相接的真实闭环；只有 canonical cycle witness 或新纯检查器明确给出的有向环证据才渲染 `A→B→A`。补结构化证据时保留边的来源（candidate／change_order），让建议指出冲突来自哪一层，不新增无依据因果解释。

### 5.3 动作不突破原门

推荐先**预填而非一击发送**：点击“填入修订建议”只把服务端同源意见填到当前合法反馈编辑器、聚焦编辑器并保持已有草稿；用户可编辑后提交。这是避免每次手写 prompt 的直接改善，又保留真实人类输入授权。相较一击提交，多一次按钮但零新命令语义；相较仅复制文案，少一次粘贴且可明确关联源版本。

不得把 blocking findings 偷塞进现有 advisory 采纳按钮：`GatePromptEntry.tsx` 206–255 当前只采纳非阻断 findings；新增针对逻辑失败的显式预填入口，单独标明用途，沿 `CockpitActionFacade.feedback` 提交。初轮失败不带原 turn 授权，必须显式反馈/现有重开，不借预填触发自动调用。

Final Compile `compile_recovery` 只有 `continue/abort_and_rollback/human_triage`（`workspace.ts` 200–203、`CockpitInbox.tsx::CompileRecoveryActions` 936–983）：此卡保留原动作，可将“转人工”解释为“查看并处理修正意见”，不能擅自追加 feedback 或把 `continue` 变成 author 重生成。已处 SC HumanConfirm 且反馈合法时才预填修订。关闭/blocked/observer/非法 session 卡只读，不呈现可发送伪动作。

## 6. 前端三类呈现与协议落点

### 6.1 三类主体验，运行故障独立保留

| 体验 | 主对话 / 待处理 | 诊断与动作 |
|------|-----------------|------------|
| 机械自动处理中 | 原“正在按反馈修订”状态持续；可补“正在整理格式”，无红错误卡、无新增待人工条目、无用户轮次增加 | 重试细节在节点/执行详情；不把原始 validation_reject 写入可见对话正文；异步状态 `aria-live=polite` |
| 逻辑纠错或机械升级 | 一张当前失败说明卡：人话原因→待修订对象版本→建议→明确动作，不再归到“连接问题”组 | 默认收起“查看诊断详情”；主对话、门局部错误与 inbox 一致；仅停点一次 `role=alert` |
| 真人决策门 | 原门布局、confirm/feedback/terminate/整组发布/compile recovery 分流与预算语义不变 | 范围/取舍保持可见，错误意见不遮盖决策，原详情仍可读 |

Operational/trust/lease/anchor 不是第四种“AI内容决策”，仍沿已有连接/运行等待面；新 typed 层只防其进入机械链，不重写它们的恢复流程。

复用 `design-system/MASTER.md`：中性白卡、语义图标/文字、既有 primary/secondary 按钮、代码等宽只在详情，动作触达区至少 44px、焦点可见、对比度≥4.5:1、无 hover 位移并遵守 reduced motion；本设计不引入新色板、字体或满屏红底。`<details>/<summary>` 采用现 `HardErrorDiagnostics` 模式，键盘可展开，长行 break-words，无 hover-only 诊断。

### 6.2 必须覆盖的四条原文泄漏路径

1. 通用 `error` 帧：`workspace-ws-message-handler.ts` 397–413 把 message 写 `state.error` 并直接入 `ChatEntry.content`；`ErrorEntry.tsx` 5–21 原文整段显示。新规划错误的 `content` 只写人话摘要，原文放 metadata/ref 且由同一映射/折叠呈现；旧未知 error 也默认折叠原文，但不猜类别、不造动作。
2. `protocol_error`：handler 430–469 当前拼 `code · message` 入对话，gate disposition 另写 inline error。规划 compile failure 需保留结构化 details；原协议 code 和拒收语义不变；非规划协议错误仍复用 `protocolErrorCopy`。
3. 门局部失败：`GatePromptEntry.tsx` 392–406 原显 `failure_message` 与 `inlineError`；SC `validation_reject` 必须携 typed failure 而不只换 inbox 文案。
4. cockpit inbox：`selectCockpitInbox` 1057–1092 区分 protocolError 与纯字符串 error；`HardErrorInboxRow` 678–682 原显 inlineError。业务规划错误单独投影为纠错条，连接/trust 仍现组；同 `failure_id` 不同时产生 generic error、gate error、inbox 三个互相矛盾的可操作实例。

### 6.3 Wire、live/rebuild/observer 一致性

新增规划错误与自动返修字段通过现有输出面传递，不新增人工输入命令：

- `HumanGateTurnFailed` 增加 typed planning failure 及尝试摘要；运行中不发 Failed，追加两次仍失败才发一次最终失败。
- `review_complete.findings` 增加稳定 typed reason/evidence；reviewer schema 必须明确，不从自由 text 分类。
- Final Compile 的 `ProtocolError.context`、compile_report/节点详情附 planning failure 列表，保留原 stable protocol code。
- `session_state` 附当前失败/重试 snapshot，节点 detail 保留历史尝试；成功 resolved state 不能被旧帧复活。
- 独立自动步状态可复用 `execution_event`＋快照，事件带现序列/调用 identity；不使用 stage_change 伪造新人工门或把用户修订 round 增加为系统 attempt。

前端扩展 `web/src/api/types/workspace.ts`、store types、live handler、store hydration、`workspace-chat-rebuild.ts::buildGatePromptEntry`、observer reducer 为同一 DTO。`selectObservedInbox` 100–114 已复用 `selectCockpitInbox`，必须继续同源；observer 只显示，无自动发消息。重建、attach、刷新不会再显示一次原文大错误或重置次数。旧记录缺 typed payload 时映射 Unknown，保留证据且零自动动作；新服务端所有在范围内的规划错误生产点迁移到 typed，禁止新旧业务路径双轨字符串猜测。

数据迁移采用可选新字段读旧记录，历史失败保持历史，不重新判定并自动重放旧 author。`HumanGateTurn` 是 `deny_unknown_fields`，增加字段需同步 durable serde、真实回放 fixture 与 DTO；此处兼容旧持久记录不是新增旧运行命令 shim。owner 批准的新预算只适用于新授权链，历史 turn 默认无 retry grant。

## 7. 上游防错：降低错误发生率，再用重试兜底

自动重试不是主修。三层优先级固定为：**上游防错 → 有界机械返修 → 人决策最后兜底**。防错不改变 validator/Final Compile 权威性，重试不改变人工门；两者共享同一 grammar、依赖方向和人话修正指令源。

### 7.1 Author 修订 prompt 硬化

现有 `work_item_plan_markdown_grammar()`（`src/product/work_item_split_engine/prompts/sc_author_teaching.rs:13–56`）已经从 `grammar::STRUCTURED_SECTIONS/STRUCTURED_KEYS/DIAGNOSTIC_CODES` 生成格式边界；`build_sc_manual_revision_prompt`（`src/product/workspace_engine/prompts/human_gate_revision.rs:55–77`）把当前候选、typed feedback、grammar boundary、language rule 和反面清单放入修订 prompt；`build_work_item_plan_compile_reredrive_prompt`（`src/product/workspace_engine/prompts.rs:192–237`）已有 unknown key 白名单与登记 ID 纪律。

在这些**同源 builder** 里补两类硬约束，且初轮、普通修订轮、自动返修轮共用：

1. 格式契约摘要：第一行精确 `# Work Item Plan`；二级 heading 只许 `## Work Item WI-<digits>: <title>`，不得把普通二级 heading 当 Work Item；所有非空结构化内容必须在合法 section 内；structured sections/字段白名单、空 Blockers、EARS 与 ID 纪律来自同源 grammar。`Plan Intent` 按现 parser 为可选，不能因摘要列出 14 个 section 就强制旧候选填 create。摘要必须由 grammar/schema 生成，不复制一份静态白名单。
2. `change_order` 方向与事实：复用 `AggregateDesignSpecScope.change_order: Vec<LogicalRepositoryId>`（`lifecycle_store/inputs.rs:44–61`），从 `load_change_order_from_confirmed_design`（`draft_batch/compile_support.rs:231–246`）加载 plan 已绑定且 Confirmed 的 Design。将成员 ID、别名、前后索引与每 WI 的已解析成员归属一起注入：较后仓 WI 依赖较前仓 WI，前置仓不得反向依赖后置仓；这是执行顺序，不是服务调用图。单仓/无 aggregate scope 空顺序保留现语义；多仓缺必需顺序按既有 `change_order_required_for_logical_codebase` 停人，不发明新 registry、默认仓序或修改已确认 Design。

自动返修 prompt 另携：失败的 typed code、受限安全 params、短中文动作、`line/field` 和合法示例；不携带用户不可见密钥/长原始 provider transcript。成功时输出完整 plan；永远要求只修失败点及必要闭包，不删字段、Outputs、Handoff 三字段，不把提示词当 schema 覆盖。

### 7.2 Reviewer 阶段前移快检

现有 `contract_prerevision.rs::single_candidate_contract_prerevision_verdict` 已将 canonical `validate_dependency_contract_graph` 从 Approval compile 前移到 SC author 每轮落盘（`contract_prerevision.rs:1–33,47–115`），其 `required_action_text` 已对 `dependency_cycle` 给“拆除依赖环”并将 Error 映射为 `Revise + RequiresRevision`；这是可扩展的前移模式。现有规则只覆盖 canonical contract graph，不能声称已覆盖 `change_order`。

新增 reviewer/prerevision 快检需：

- 在 reviewer 复评入口前保留结构快检（grammar parser 与 source/ref 一致性），并在 IR/合法 target 已解析后做顺序快检；快检结果与 reviewer context 同源，全部 finding 带 typed `reason/evidence/required_action`，不让模型重新解释语法。
- 抽出现有 `apply_change_order_cross_repo_depends_on`（`compile_support.rs:267–319`）的纯投影/检测核心，由 prerevision 与 Final Compile 共同消费：原 candidate 依赖＋按 change_order 添加的跨仓依赖共同检环，不仅检查候选自身的 canonical graph。前置阶段用 logical WI ID＋已解析成员表，Final Compile 用 physical WI ID，结果语义必须同构；不得为了前移预创建 WorkItem/compile transaction。发现环或反向边仅给 `RequiresRevision` 与人话建议，不自动改 Design 顺序；同仓不因 change_order 添边。
- 复评命中 mechanical finding 进入同一 author 修订 prompt；逻辑 finding 进入人话意见/现有门；reviewer output envelope/schema 解析错误仍走 `ReviewCompletionError` 的既有结构化输出恢复，不得把 reviewer 自身协议错误误投 author 修订。
- Final Compile 继续完整复验，不能因前移而删除后置权威校验；前移只降低反馈延迟，不能取代提交前 gate。

### 7.3 分层验收

| 层 | 目标 | 失败时 |
|----|------|--------|
| Prompt 防错 | 首次/人工/自动 author 都收到同源 grammar＋已确认顺序约束 | 仍由权威 parser/validator 拒绝，计入机械返修资格 |
| Reviewer 快检 | 复评时即发现环/反向边/结构错，不等 Final Compile | mechanical 进入有界返修，logical 进入人话建议 |

## 11. 设计结论

本方案把“错误原文”拆成可行动的三件事：服务端 typed 原因决定资格，author 前置教学降低发生率，有界自动返修兜底机械表达错误，前端用人话和动作承载逻辑错误，最后把范围与取舍交回现有人工门。自动链始终绑定既有真实人类反馈、候选版本、CAS、审计和 reviewer/Final Compile；不因方便而产生静默 confirm、静默删边、自动选仓或 trust/anchor 副作用。

## 2. 背景与目标

### 2.1 业务背景

用户有大量存量 Java Web 微服务项目，一个业务项目包含 **30–50 个 git 仓库**（后端微服务 + 2–3 个前端工程），仓库之间存在 **Dubbo / HTTP 微服务调用关系**。一个 Issue 可能横跨 **10+ 个仓库**改动。

### 2.2 现状（「代码库添加」业务）

Cadence Aria 产品主线为 **Project → Repository → Issue**，当前「代码库添加」的能力与约束：

| 维度 | 现状 | 代码证据 |
|---|---|---|
| 登记方式 | 逐仓库手工录入表单（单 name + 单 path） | `src/web/types.rs:327-332`、`web/src/components/lifecycle/CreateRepositoryDialog.tsx` |
| 初始化流程 | 每仓库独立 6 步异步初始化：CadenceSkills 准备 → `/pre-check` → `/rule-config` → `/mcp-configuration` → `/project-rules-examples` → GitFinalize | `src/product/repository_store/types.rs:82-120` |
| 初始化副作用 | 每仓跑 4 条 Claude Code 命令（120–200 次/50 仓）；收尾 `git add -A` → commit → push，**不拒绝脏工作区** | `src/product/repository_store/initializer.rs:40-106`、`registration/git_finalize.rs:4-124` |
| CadenceSkills | 每仓都调用 `prepare_skills()`，被进程级全局锁串行化（纯浪费） | `src/product/cadence_skills/manager.rs:62-85` |
| Issue 绑定 | `IssueRecord.repo_id: Option<String>` —— **一个 Issue 只绑一个仓库** | `src/product/models/project.rs:125-137` |
| 全链路单仓 | workspace context、Story/Design/WorkItem、shared worktree、CodingExecutionAttempt、provider `working_dir` 全部单仓假设 | `src/web/workspace_context/entity.rs`、`src/product/coding_models/execution.rs:89-120` 等 |
| 服务拓扑 | **无任何 Dubbo/HTTP 调用关系建模**；现有 `dependency_graph` 是 work item 执行顺序图，非服务调用图 | `src/product/models/lifecycle.rs:219-224` |

### 2.3 设计目标

1. 一个业务项目（30–50 仓）能以「逻辑代码库」整体接入，而不是逐仓手工添加。
2. 规划类产物（Issue / Story / Design / Work Item 计划）能使用**聚合上下文**（跨仓理解）。
3. 执行类产物（Work Item / Coding）保持**单目标仓**语义，但支持一个 Issue 拆成多个单仓工作项。
4. 初始化从「每仓 4 次 Claude 会话」降为「聚合级一次 + 确定性逐仓分发」。
5. 提供一份聚合 CodeGraph 索引覆盖全部成员仓。
6. 保证安全（最终目标）：批量接入不修改存量仓库、provider 不越权写入、独立 checkout 不裸奔；**P1 阶段 coding 为 experimental + supervised（best-effort），OS 级强制隔离后置**。

### 2.4 成功标准（高层）

- 50 仓登记全程零 Git 副作用；manifest 重放不重复、删除后重导不 ID 冲突。
- 一次聚合规划调用不爆 context window；prompt 只含 inventory + 摘要 + 证据。
- 跨仓 Issue 能端到端拆成多个可执行单仓 Work Item 并各自 coding。
- coding 配置目标为单一 worktree（P1 best-effort，非 OS 级强制）；规划只读；集中政策通过 envelope 注入。
- 聚合索引覆盖 50 仓且 freshness 可追溯。

## 3. 已确认的产品决策（讨论结论）

> 以下为多轮讨论后用户确认或三方收敛的决策，后续设计以此为前提。

| # | 决策 | 说明 |
|---|---|---|
| D1 | **一个业务 Project = 一个逻辑代码库** | 不新增顶层 `LogicalCodebaseRecord`；Project 即逻辑作用域 |
| D2 | **规划聚合、执行单目标仓 + 按需跨仓只读检索** | 规划用聚合上下文；每个执行 attempt 单写一个目标仓；coding 仍可检索其他仓只读证据 |
| D3 | **公共父目录假设** | 默认 50 个 git 仓都在同一主目录下；父目录既作聚合 CodeGraph 索引根，也作规划 provider 驱动目录；**父目录为非 git 目录**（聚合资产由 Cadence `.aria` 领域存储管理，避免外层 git 语义陷阱与 includeIgnored 依赖）。**因果链**：非 git 父目录 → 无 super-repo `.gitignore` → 子仓非 gitignored → codegraph 自动发现并索引，无需 `includeIgnored` |
| D8 | **worktree 按每仓处理** | 主 checkout 永不被碰；coding 全部在目标仓自己的 `.worktrees/` 里进行（现有 per-repo worktree 实现可复用）；仅 Issue shared worktree 键改为 `(project, issue, repository)` |
| D9 | **不做自动依赖图，保持通用** | 不做服务拓扑/依赖图建模（不绑定 dubbo/http）；规划时由 provider 从聚合 CodeGraph 索引按需检索关系；成员清单只用通用元数据（repo_type/tech_stack/owner/tags） |
| D10 | **前端仓纳入 P0/P1** | 成员清单含 repo_type；前端仓（package.json/pnpm/Vite）初始化 profile 与后端差异化，不套 Java 六步 |
| D11 | **「按需拉取」= 逻辑选择** | 公共父目录假设下仓库已物化，不做动态 clone；AI 用哪个仓就选择哪个仓 + 检查索引是否新鲜 |
| D12 | **沙箱先轻后重** | P0/P1 先做「不暴露兄弟仓」；**coding 标 experimental + supervised（用户已确认 2026-08-05）**；OS 级沙箱后置 |
| D13 | **索引更新按需 + 兑底** | AI 用某仓前先 sync 该仓；另有定时兑底；索引过时就提示「可能过时」 |
| D14 | **最小指针 P1 随 coding 上线** | P0 保持零副作用承诺（不 touch 各仓），pointer 到 P1 与 coding 能力一起发布 |
| D4 | **聚合索引** | 在父目录跑一次 `codegraph init` 建统一索引（子仓被 gitignore 时 `includeIgnored` opt-in） |
| D5 | **每仓最小安全指针** | 子仓「零重复政策正文」，但保留极薄 bootstrap 文件（AGENTS.md/CLAUDE.md 指针） |
| D6 | **P0 与 P1 合并设计、顺序发布** | 共享 manifest/identity/workspace 契约，但安全接入先于聚合索引与规划交付 |
| D7 | **初始化聚合化** | 规则/配置/MCP/示例在聚合级一次生成；逐仓只做确定性本地化 + 各自 git 操作；不逐仓开 Claude 会话 |

## 4. 关键技术结论（subagent 讨论依据）

### 4.1 为什么「provider 一并使用所有仓库总和」要拆成两层

- ✅ **全集可检索、可引用**：逻辑代码库所有成员仓进入检索召回域，规划 provider 可跨仓理解。
- ❌ **把全集源码塞进一个 provider 上下文 / 一个 provider 直接写所有仓**：会撞上已验证的技术墙：
  - token 爆炸 / context dilution；
  - git 命令歧义（父目录非 git 报错、外层 git 误作用外层仓）；
  - Claude Code worktree 嵌套缺陷簇（#27881/#27974/#59702/#33615 等，均 open）；
  - Codex 多根只认第一个 folder（#2909）、父目录检测不到子仓（#14218）。

### 4.2 codegraph 的聚合能力边界（已复核 v1.5.0 源码）

- **没有**「加参数合并 50 个分散仓库索引」的能力：`init [path]` 只接受单 path，无 `--roots/--merge/--append`；#499 为 open feature request。
- **但 project root ≠ git root**：`init` 不做 `git rev-parse`，直接用传入目录的 `path.resolve`。因此**对非 git 的公共父目录可以建一份统一索引**，覆盖其下全部子仓。
- 子仓被外层 `.gitignore` 忽略时，需 `codegraph.json` 的 `includeIgnored` opt-in（v1.4.1 有回归 #1295，需退到 `include`；v1.5.0 正常）。
- 跨仓编译级精确符号导航（A 仓调 B 仓类）codegraph **不承诺**（v1.5.0 为 Rust 原生内核，非编译器级精确语义）；若需要，长期走 scip-java + Sourcegraph。

### 4.3 「规划聚合 / 执行单仓」在 Claude Code / Codex 上的可行性

| 场景 | Claude Code | Codex |
|---|---|---|
| 规划（聚合根启动，只读） | ✅ 文件可读写全子仓、CLAUDE.md 向上遍历到根、`git -C` 可用 | ⚠️ App 不可用（#14218/#2909/#26338）；仅 CLI `--add-dir`（experimental，写隔离有 bug #24214） |
| coding（子仓 worktree） | ✅ cwd=目标 worktree 单仓执行；但集中 `.claude` 配置跨 git 边界发现断裂（#12962/#18029/#18940/#62237） | ⚠️ 当前 Cadence 用 app-server 固定 `danger-full-access`，必须改造 |
| 政策注入 | `--settings` + `--mcp-config`/`--strict-mcp-config` + `--allowed-tools`（本机 2.1.220 支持，adapter 未用） | config.toml + `-c` TOML override + `writable_roots` + hooks（默认关、只拦 Bash） |

### 4.4 业界成熟模式对照

- **bootstrap repo / meta-repo**（Sahaj、Calandri 41 仓、jclfocused）：公共父目录 + manifest + 分层 CLAUDE.md —— 与 D3 一致，是本方案的行业验证基线。
- **纯中央化「子仓零规则」**（NOGUCHILin）：有实证，但子仓独立 checkout 时裸奔；默认应取「聚合根规划 + 每仓最小指针」（D5）。
- **read/write 分离**（One Agent Per Repo、gh-aw MultiRepoOps）：聚合索引用于规划、单仓 worktree 用于执行，顶层编排跨仓 —— 与 D2 一致。
- **codegraph 多仓统一索引**：物理聚合父目录是唯一「一份 DB」路径；`includeIgnored` **仅在父目录是 git super-repo 时**需要（D3 非 git 父目录恰好规避此需求）。

## 5. 总体架构方案

### 5.1 一句话方案

> **在「公共父目录假设」下，让 Project 成为逻辑代码库：聚合根作为规划驱动目录与统一 CodeGraph 索引根，集中政策经 SessionPolicyEnvelope 注入；每个 Work Item / Coding 仍落单一目标仓 worktree，通过每仓最小指针保障独立 checkout 安全。**

### 5.2 逻辑结构

```text
<公共父目录>                      ← 聚合根（非 git 目录；聚合资产由 Cadence 管理）
├── <repo-a/>  <repo-b/> ...      ← 50 个真实 git 仓（各自 .git，主 checkout 不被 Cadence 触碰）
│     ├── AGENTS.md               ← 最小安全指针（bootstrap，非政策正文）
│     └── CLAUDE.md               ← 最小安全指针
│     └── .worktrees/             ← 每仓自己的 coding worktree（主 checkout 不动）
├── .codegraph/                   ← 聚合 CodeGraph 索引（一份 DB 覆盖 50 仓，非 git root 直接 walk）
├── catalog/repos.yaml            ← 成员清单投影（可读/导入，含 repo_type/tech_stack/owner/tags；权威源在 .aria manifest.json）
├── CLAUDE.md / AGENTS.md         ← 聚合根路由器（<100 行：不变量 + 路由 + catalog 指针）
├── docs/                         ← 主题分片（java/frontend/security…）
└── .aria/projects/{project_id}/  ← Cadence 领域存储（manifest/policy/index 元数据）
```

### 5.3 数据流（两阶段初始化 + 规划 + 执行）

```text
阶段 A（聚合级，一次）：
  manifest 登记 50 仓（扫描父目录发现，零副作用，不操作主 checkout）
  → CadenceSkills 准备（全局一次）
  → 聚合级规则/MCP/示例生成（聚合根）
  → codegraph init（聚合根一次；非 git root 直接 walk，无需 includeIgnored）
  （每仓最小指针发布在 P1 随 coding 能力上线，见 D14，经独立 worktree/branch/PR 受控发布）
阶段 B（按需，逐仓确定性）：
  目标仓技术栈探测 / OpenSpec 本地资产 / MCP 本地合并 / 各仓 git 操作
  （均程序化，不开 Claude 会话；仅共享模板生成用一次 Claude）

规划：provider 从聚合根启动（只读）→ 注入 RepositoryContextSet + 政策 envelope
     → 输出 Work Item 强制携带 target_repository_id
执行：每 Work Item → 目标仓的 .worktrees/{issue}（唯一可写，主 checkout 不动）
     → coding/review/commit/push 逐仓独立
```

### 5.4 分层职责边界

| 层 | 职责 | 边界 |
|---|---|---|
| 聚合索引层 | 跨仓检索（规划用） | 只读；一份 DB |
| 聚合政策层 | 集中规则/目录/政策 artifact | 聚合根 own；版本化 |
| 规划层 | Issue/Story/Design/Work Item 计划 | provider cwd=聚合根；只读 |
| 执行层 | coding/review/commit/push | 每 attempt 单一 target worktree 可写 |
| 成员/身份层 | logical repository ↔ checkout ↔ index 映射 | 稳定 UUID 身份 |

### 5.5 初始化 6 步在新方案下的操作方式

> 回答「初始化项目需要的 6 步（CadenceSkills / PreCheck / RuleConfig / McpConfiguration / ProjectRulesExamples / GitFinalize）在新方案下怎么操作」——这些步骤产出的是 provider 必要的内容，从「每个仓库跑一遍」改为「机器一次 + 聚合根一次」。

**6 步产出的内容与使用者**：

| 步骤 | 产出 | 使用者 |
|---|---|---|
| 1 CadenceSkills | AI 技能/命令库 | 机器级（每台电脑一次） |
| 2 PreCheck | 全局工具检查/安装 + OpenSpec 配置 | 工具=机器级；配置=项目级 |
| 3 RuleConfig | 规则文件（CLAUDE.md/AGENTS.md/.claude/rules）+ 索引 | 项目级 |
| 4 McpConfiguration | MCP 配置（AI 连外部工具的配置） | 项目级 |
| 5 ProjectRulesExamples | 项目规则示例 | 项目级 |
| 6 GitFinalize | 把生成文件提交进仓库 | 仓库级 |

**新方案映射（50 次 → 1 次）**：

| 步骤 | 现在（每仓一次） | 新方案 | 产物位置 |
|---|---|---|---|
| 1 CadenceSkills | 每仓跑 | 每台机器一次（本来就是全局的） | 机器级 `$HOME` |
| 2 PreCheck | 每仓检查+写配置 | 全局工具检查一次 + OpenSpec 配置写到聚合根 | 机器级 + 聚合根 |
| 3 RuleConfig | 每仓写规则+每仓建索引 | 聚合根写一次规则 + 聚合索引一次 | 聚合根 + catalog |
| 4 McpConfiguration | 每仓写 MCP | 聚合根写一次 | 聚合根 |
| 5 ProjectRulesExamples | 每仓写示例 | 聚合根写一次 | 聚合根 |
| 6 GitFinalize | 每仓 commit | 初始化阶段取消（不再往 50 仓提交规则）；仅 P1 每仓最小指针经独立 worktree/branch/PR 受控发布；coding 产生改动时各仓独立提交 | 无 |

**操作流程（大白话）**：

```text
第一次用这台电脑（一次性）：
  ① 装技能库（CadenceSkills）——机器级一条命令
接入项目（一次性）：
  ② 告诉系统 50 个仓库所在父目录 → 自动登记（不改代码）
  ③ 系统在聚合根跑一次「聚合初始化」= 旧 2-5 步合成一次（规则/MCP/OpenSpec/示例生成到聚合根）
  ④ 建一次聚合索引（codegraph init）→ AI 查找手册
日常使用：
  ⑤ 提需求 → AI 从聚合根启动（手里有全部规则 + 全部代码索引）
  ⑥ 改代码 → 每个任务在目标仓库隔离副本改，改完各自提交
```

**每仓最小指针（补充）**：

到 P1，系统给每个仓库放一张极薄「小纸条」（短 AGENTS.md/CLAUDE.md），只写：项目/仓库 ID、完整规则位置（聚合根）、「未加载完整规则前 AI 不许动手改」声明。即使有人单独打开单仓，AI 也知道规矩在哪且默认不越权。

**要点**：provider 必要的内容一点不少，只是从「每仓各放一份」变成「聚合根放一份 + 每仓小纸条」；provider 从聚合根启动时看到的与以前完全一致。

## 6. 数据模型设计

### 6.1 现有模型（不变部分）

- `ProjectRecord`：逻辑代码库作用域（不新增顶层实体，D1）。
- `RepositoryRecord`：单一物理 git 仓（path / repo_hash / runtime_root）；继续逐仓登记，**聚合根绝不注册成 RepositoryRecord**。
- `IssueRecord.repo_id`：迁移期为 primary/focus 兼容投影。

### 6.2 新增领域实体

```text
ProjectCodebaseManifest           1:1  Project 默认聚合配置/成员策略
  ├── CodebaseMemberRecord        1:N  逻辑成员（稳定 UUID、alias、role、source_identity）
  │     └── RepositoryRecord      1:1  现有物理仓（迁移期）
  │           └── RepositoryCheckoutRecord  1:N 原路径 / managed clone / worktree
  └── AggregateIndexRecord        1:N  （通常一个 active CodeGraph index）
        └── AggregateIndexMemberSnapshot    N:1 成员+checkout+revision（不可变证据）

IssueCodebaseSelection            Issue 级稀疏选择：include/exclude/focus_repository_ids
PlanningContextSnapshot           每仓 commit/ACL/index 快照（可恢复、可审计）
AggregatePolicyArtifact           集中政策正文 + digest + revision
SessionPolicyEnvelope             每次 provider run 的不可变政策快照（见 §8）
（不做 RepositoryServiceDependencyEdge 服务依赖边 —— D9 已确认 YAGNI，规划由 provider 按需从索引检索）
```

### 6.3 身份模型（关键：三身份分离）

| 身份 | 键 | 说明 |
|---|---|---|
| LogicalRepositoryIdentity | 稳定 UUID（Cadence 生成或 manifest 固化） | 逻辑成员身份，与路径无关 |
| RepositoryCheckoutIdentity | checkout_id + canonical_path | 当前 `repo_hash` 的正确语义是 checkout path hash |
| AggregateIndexIdentity | aggregate_index_id + aggregate_root | 聚合索引 artifact 身份，可迁移 |

> ⚠️ `repo_hash` 按路径计算（`src/product/id.rs:3-6`）：同一远端仓 clone 到不同路径会得到不同 hash。公共父目录假设下路径稳定，但设计上仍要区分逻辑身份与 checkout 路径，避免未来 managed clone 时身份重复。

### 6.4 存储位置

```text
.aria/projects/{project_id}/logical-codebase/manifest.json
.aria/projects/{project_id}/logical-codebase/members/{logical_repository_id}.json
.aria/projects/{project_id}/logical-codebase/checkouts/{checkout_id}.json
.aria/projects/{project_id}/logical-codebase/indexes/{aggregate_index_id}.json
.aria/projects/{project_id}/logical-codebase/policy-artifacts/{policy_revision}.json
```

## 7. 分期路线（P0 + P1 合并）

### 7.1 合并范围

目标：安全完成「登记多仓（首版本地已 clone，不做远程物化）→ 聚合索引 + 统一规则根 → 聚合规划 → 每个可执行 Work Item 落为一个明确 target repo」。完整跨仓自动执行、多仓 PR 协调、补偿 coordinator **不在本范围**（后续 P2）。

### 7.2 工作包（WP0–WP6，来自 worker + reviewer 修正）

| 包 | 内容 | 依赖 |
|---|---|---|
| **WP0 领域边界与身份** | ProjectCodebaseManifest、logical/checkout/index 身份、迁移现有 RepositoryRecord、路径/remote allowlist、删除引用约束 | 必须先于一切 |
| **WP1 批量成员登记** | manifest 导入/API/UI、逐成员 git root/remote 验证、状态/partial failure/限流/取消/清理（**首版只登记本地已 clone 目录，不做远程 clone/fetch**，D11） | 依赖 WP0 |
| **WP2 聚合初始化与集中规则** | 拆 global-precheck；聚合级 rule/MCP/project-rules/OpenSpec；成员 catalog + 政策 artifact；删除每成员 rule 发布 | 依赖 WP0；与 WP4 协同定义政策 artifact |
| **WP3 聚合 CodeGraph 索引生命周期** | 聚合 init（非 git 根，主路径无需 includeIgnored）、checkout 后 sync/reindex、status/snapshot/diagnostics、多索引 fallback（includeIgnored 仅作非 D3 布局兼容诊断） | 依赖 WP1/WP0 |
| **WP4 聚合规划上下文与 Issue membership** | IssueCodebaseSelection、RepositoryContextSet resolver、member inventory/profile budget、planning provider_context_root | 必须与 WP0/WP2/WP3 协同 |
| **WP5 聚合计划到单仓执行的安全桥** | split 强制 target_repository_id；attempt 冻结 target；shared worktree 按 (project, issue, repository) 键；mixed-target group 一律拒绝；coding provider cwd 强制 target worktree + 政策注入 | 随 WP4 至少实现 guard |
| **WP6 测试/迁移/可观测性** | 2–3 仓与 50 member budget case；路径/remote 伪造、clone 失败、ignored child index、stale index、身份不重复、旧 repo_id 兼容、target missing blocker、同仓串行/异仓隔离、per-repo push partial failure | 贯穿所有 WP（质量泳道，非末尾包） |

### 7.3 顺序发布（不是一次原子发布）

```text
① 授权与身份 → ② 隔离物化与安全检查 → ③ 集中 policy runtime
→ ④ 聚合索引发布与 freshness → ⑤ 聚合规划（RepositoryContextSet）
→ ⑥ 单仓执行实验性桥（experimental + supervised，非 fail-closed，OS 级沙箱后置）
```

### 7.4 验收门

1. **身份门**：同一逻辑仓多 checkout 只有一个 `logical_repository_id`；不以 `repo_hash` 去重。
2. **索引门**：50 仓在非 git 聚合根产生一份 `.codegraph/codegraph.db`；snapshot 列明 member/revision；外部变更后 index 不可静默 stale。（gitignored child 兼容仅作迁移诊断场景）
3. **规则门**：聚合根有唯一集中规则产物，children 无重复政策正文；target coding prompt 收到 versioned policy snapshot。
4. **规划门**：prompt 显示 stable inventory/availability/index freshness/budget；输出每个 Work Item 有合法 target 或 blocker。
5. **执行安全门**：非 git 聚合根永不传入 GitWorkspaceService；每 target 的 branch/worktree/diff/commit/push/journal 可独立审计；mixed-target group 被拒绝。

## 8. 剩余 20% 详细设计（安全与 provider 边界）

> 公共父目录布局解决了结构性问题（聚合索引、驱动目录、初始化聚合化、身份稳定）；以下问题与布局正交，必须靠设计解决。

### 8.1 SessionPolicyEnvelope（核心）

**两层结构**：
- 持久化 `AggregatePolicyArtifact`：集中政策事实来源（正文 + digest + revision）。
- 每次运行的不可变 `SessionPolicyEnvelope`：冻结 policy/target/provider dialect。

**三落点**（不是只拼 prompt）：
1. 产品层 `SessionPolicyEnvelope`（持久化/审计）；
2. adapter 输入 `ValidatedSessionLaunchPolicy`（不可缺省，只含已验证的 cwd/sandbox/配置引用）；
3. prompt 可见性层（同一 validated 对象渲染，标注「这是可见性层，不是沙箱」）。

**硬门（8 条）**：
1. 可执行能力门：PlanningReadOnly 绑定已验证只读沙箱；CodingTargetWrite 绑定单根写沙箱（「只读」必须真只读）；
2. 信任锚门：digest 期望值存于 coding 进程不可写的 Aria 信任存储（provider 改不掉政策）；
3. TOCTOU 门：canonicalize→spawn 之间复验路径身份/containment（防路径被换）；
4. 配置来源门：user/project/local/config/env/子仓 MCP 合并优先级审计（防配置串味）；
5. resume 门：policy digest + target + provider 版本 + capability 全部一致才可 resume（续接不漂移）；
6. 网络/MCP/工具门：写根之外管网络、MCP、Agent/subagent、shell、secrets；
7. 禁止降级门：真实 provider 不得走无政策 fallback；capability 缺失不回落 full-access；
8. 按 action 解耦 freshness：index 新鲜度只约束 planning，不让 coding 被拖累。

> **P0/P1 最小闭环先做 3 条**：⑦禁止降级、⑤resume 一致、①只读真只读；其余 5 条后置。

**建议字段**（示意）：

```text
schema_version, policy_id, policy_revision, content_digest
logical_codebase_id, membership_revision, aggregate_index_id
action: PlanningReadOnly | CodingTargetWrite | ReviewReadOnly
target: Option<{ repository_id, checkout_id, worktree_root, profile_revision, source_revision }>
read_only_roots, single_writable_root, allowed_write_scopes
policy_artifact, target_repository_profile, mcp, provider
```

### 8.2 注入机制取舍

| 机制 | 定位 |
|---|---|
| `--settings`（生成 Aria-owned settings 文件） | ✅ 正式机制 |
| strict MCP allowlist（`--mcp-config` + `--strict-mcp-config`） | ✅ 正式机制 |
| 工具 allow/deny（`--allowed-tools`） | ✅ 附加防线 |
| 政策正文进最高可用指令通道 | ✅ 可见性层 |
| `@path` import | ⚠️ 纵深防御，非安全边界（跨 cwd 警告、路径可移植性） |
| PreToolUse hooks | ⚠️ 纵深防御，非最终隔离（#44534 Agent 旁路 / #33106 MCP 旁路 / #46991 语义旁路） |
| coding 默认 `--add-dir` 聚合根/兄弟仓 | ❌ **禁止**（是授权面，不是只读 ACL；制造「假装只读」） |

### 8.3 最小沙箱原则（先轻后重）

「沙箱」不是给每个仓库建独立沙箱，而是**控制 provider 进程「能看到什么、能写什么」**：

- **轻量层（P0/P1 先做）**：**不暴露兄弟仓**——coding 时只给目标 worktree 路径，不传 `--add-dir` 其他仓，不告诉 provider 其他仓位置；规划时用 provider 只读模式（`defaultMode: plan` / `sandbox_mode: read-only`）。这是行为级隔离，依赖 provider 模式生效。
- **强制层（需要时再加）**：OS 级沙箱（macOS sandbox-exec / Linux bubblewrap / provider native sandbox），从系统层面限制进程只读写指定目录。

原则：
- planning：聚合根 + 成员 checkout + 索引全只读；
- coding：配置目标为单一 worktree 可写；政策 bundle 只读；**兄弟仓 P1 仅 best-effort 不暴露（非 OS 级不可达）**；
- 网络按任务默认关闭或单独批准。
- 若只有轻量层、无 OS 级强制：coding 标 **best-effort experimental/supervised**，不标 fail-closed supported。

### 8.4 Codex 处理（为什么需要「验收标准」）

**背景**：当前 Cadence 的 Codex provider 在 `thread/start`/`resume` 固定发送 `danger-full-access`（全权限，测试还断言该行为，`codex_provider/session.rs:63-104`、`tests.rs:178-206`）。在「只写目标仓」的安全模型里，全权限模式是危险的——它能写碰到的任何仓库。

**「验收标准」= 改完受限模式后，证明它真的受限**（尤其要验证 `apply_patch` 不能绕过写白名单，这是已知 bug #24214）。未证明前不能宣称安全。

- 当前：**unsupported**。
- 路径：保持 **app-server** 方向（复用 streaming/resume/approval 合同），改造为 `workspace-write` + cwd=目标 worktree + 无额外 writable roots + 版本钉定 + 越界测试（shell/apply_patch/绝对路径/父目录/symlink/resume）。
- 完成后：**experimental**（默认关、显式 opt-in）；多版本稳定后升 supported。
- **不新建 Codex exec adapter**（`exec --add-dir` 写隔离有 bug #24214；会重建 streaming/approval/resume 合同）。

### 8.5 每仓最小指针

- 语义：**「零重复政策正文」，不是「零 bootstrap 文件」**。
- 每仓极薄 `AGENTS.md` + `CLAUDE.md`：logical codebase ID、repo ID、pointer template version、canonical policy locator、「Aria 会话必须携带匹配 envelope 否则禁止写」声明。
- **不硬编码 policy content_digest 进 50 个仓**（每次政策更新会触发 50 仓提交）；digest 由 envelope 冻结。
- 安全三层 = **pointer（发现）+ envelope（身份/版本）+ sandbox（执行边界）**；`@path` import / settings / hooks 是兼容与纵深。
- ⚠️ 现有 `direct_cadence_routing_rules_reference()` 要求「完整读取目标根 AGENTS.md/CLAUDE.md」且视为规则正文（`routing_reference.rs:1-10`）——与 pointer 语义冲突，**coding 上线前必须修改**。

### 8.6 Provider 路由（路由级 fail-closed guard：能力不满足即阻塞、不降级；不代表端到端 coding 已达 fail-closed supported）

| Phase | MVP 路由 |
|---|---|
| 聚合规划 | Claude，只读模式（P1 best-effort 只读） |
| 目标 coding | Claude，single-target 配置（P1 experimental） |
| Review | Claude，只读模式（P1 best-effort 只读） |
| Codex | 仅显式 experimental opt-in |
| 能力不满足 | 阻塞，不降级 |
| Fake | 仅测试 |

Capability 记录：adapter dialect、exact version、aggregate read-only、single-target write、strict MCP/config isolation、resume policy binding、**evidence 状态（declared / fixture_verified / production_verified）**。CLI `--help` 只能算 declared。

### 8.7 根 CLAUDE.md 防膨胀

- 聚合根 `CLAUDE.md`/`AGENTS.md` = **路由器**（<100 行：org 不变量 + 路由 + catalog 指针），不是百科全书；
- `catalog/repos.yaml` 为成员清单投影（权威源在 `.aria manifest.json`，含 repo_type/tech_stack/owner/tags 通用元数据）；主题深度文档放 `docs/` 分片；
- coding 不依赖父目录自然发现（靠 envelope 显式注入）；
- 机械检查：行数/byte/token 预算 + 断链检查 + catalog schema lint。

### 8.8 前端仓处理（D10）

- 成员清单 `repo_type`：backend / frontend / lib；前端仓用 `package.json` / pnpm / Vite 探测。
- 前端初始化 profile 与 Java 后端差异化：构建/测试命令、代码规范引用不同；不套 Java 六步。
- 规划时前端仓进入聚合上下文（改后端 API 时能检索前端调用点）。

## 9. 产物生成流程设计（Story / Design / Work Item / Coder）

> 本节回答「逻辑代码库接进来之后，平台核心产物流程怎么跑」。

### 9.1 总原则

- **Story / Design / Work Item 计划** = 聚合上下文生成（provider 从聚合根只读启动，可查全部 50 仓）。
- **Work Item 落地** = 每个 item 绑一个目标仓库（执行边界，必填 `target_repository_id`）。
- **Coding** = 单目标仓 worktree 执行；跨仓只读证据经聚合索引检索注入。

### 9.2 Story Spec（需求故事）

- **输入**：Issue + RepositoryContextSet（成员清单 / catalog / 聚合索引）。
- **AI 视角**：聚合根只读启动，可跨仓检索。
- **模型**：Story 改绑 `logical_codebase_ref` + `involved_repositories`（涉及仓库列表，引用 member ID）+ 可选 `focus_repository`；不再单一 `repository_id`。
- **输出约束**：Story 必须列出涉及仓库；AI 不确定涉及哪些仓 → blocker 向用户确认，不猜测。

### 9.3 Design Spec（设计方案）

- **输入**：Story + 聚合上下文。
- **模型**：显式携带 `logical_codebase_ref` + 引用 Story 的 `involved_repositories`；不再回落 `issue.repo_id`。
- **跨仓关系**：由 AI 从聚合索引自行检索（不做依赖图，D9）。
- **产出**：跨仓设计——接口/契约变更、**改动顺序**（如 公共契约 → provider → consumer），该顺序驱动 work item 的 `depends_on`。

### 9.4 Work Item（工作项）

- **输入**：Design + RepositoryContextSet。
- **拆分**：跨仓 Story/Design → N 个**单目标仓** work item。
- **模型**：`repository_id` 语义固定为 `target_repository_id`（必填，校验在成员集合内）。
- **顺序**：跨仓顺序用现有 work item 级 `depends_on`（执行顺序图，非服务调用图，符合 D9）。
- **输出约束**：拆分引擎每个 item 必须给出 `target_repository_id`；不确定 → blocker，不默认塞给 primary。
- **展示**：Issue 下按仓库分组显示 work item。

### 9.5 Coding（Coder）

- 每个 work item → 一个 coding attempt → 目标仓 `.worktrees/{issue}`（主 checkout 不动，D8）。
- **Coder cwd = 目标仓 worktree**；跨仓只读证据经聚合索引检索注入（改 A 的接口时查 B 的调用点）。
- **policy** = SessionPolicyEnvelope（CodingTargetWrite：配置目标为单一 worktree 可写；P1 兄弟仓仅 best-effort 不暴露，非 OS 级不可达）。
- **并行/串行**：不同仓可并行（per-repo worktree + `(project, issue, repository)` 锁）；同仓串行。
- **group**：MVP 一律拒绝 mixed-target group（现有 group 为单仓假设；自动拆分后置）。
- **完成**：每仓独立 branch/commit/push/PR；Issue 完成 = 所有必需 work item 完成。
- **Coder 不持有聚合根**；聚合上下文只在规划阶段使用。

### 9.6 评审/修订链路

- Story/Design/WorkItem 的 author → reviewer → revision 均在聚合上下文（只读）。
- Coding 的 review 在目标仓 worktree（只读该仓 + 可检索跨仓证据）。

### 9.7 产物模型变化汇总

| 产物 | 现状（单仓） | 改为（多仓） |
|---|---|---|
| StorySpec | `repository_id` 单值 | `logical_codebase_ref` + `involved_repositories` + 可选 `focus_repository` |
| DesignSpec | 无 repo 字段，回落 `issue.repo_id` | 显式 `logical_codebase_ref` + `involved_repositories` |
| WorkItem | `repository_id` 单值（全部塞 primary） | `target_repository_id` 必填 + 成员校验 + `depends_on` 排序 |
| CodingAttempt | 单 worktree/branch | 冻结 `target_repository_id` + 目标仓 worktree + envelope |
| Group | 单 issue worktree | MVP 一律拒绝 mixed-target（拆分后置） |

| C2 | 跨仓证据通道 | Coder 如何查其他仓：中介服务/冻结证据/运行时查询、ACL、index snapshot、freshness 语义、token 预算、审计格式 |
| C3 | 权威数据源 | `.aria/.../manifest.json` 为唯一权威；`catalog/repos.yaml` 为可读投影/导入输入；根 CLAUDE.md/MCP 为 revisioned projection |
| C4 | 指针发布建模 | P1 写入每仓指针是受控副作用（独立 branch/PR/可回滚/与已有文件合并冲突处理）；「零 Git 副作用」仅指 P0 登记阶段 |
| C5 | 数据迁移契约 | 单仓项目自动生成默认 member；旧 repo_id 回填 focus/primary；双读双写窗口；删除引用约束；feature flag 回退 |
| C6 | Work Item target 硬约束 | 删除「从第一个 Story 选仓」默认路径；compile/parser/validator 全程携带 target；missing target = blocker |
| C7 | group 行为 | MVP 一律拒绝 mixed-target group（不自动拆分，避免新 group 语义） |
| C8 | 失败状态机 | 成员登记/聚合索引/单仓执行三个最小状态机（含幂等重试、last-known-good、人工恢复入口） |
| C9 | 可测验收阈值 | token/时间/覆盖/freshness/sandbox 越界矩阵/provider 版本矩阵全部量化 |
| C10 | WP 映射 | WP0-WP6 标注 P0/P1、feature flag、依赖、估算、回滚点 |
| C11 | 安全发布级别一致 | 文档不得同时声称 fail-closed 与 experimental；experimental 阶段明确为 supervised |

**worker 标出的最高实施风险**：安全边界被 prompt/cwd 误当 sandbox（真实 provider 仍有 legacy fallback，需先禁用）；单仓语义迁移导致 silent-primary（编译/分组/恢复链路多处置仓）；worktree 改键/锁迁移影响面远超单个文件；无迁移框架的 JSON 兼容；聚合初始化副作用。

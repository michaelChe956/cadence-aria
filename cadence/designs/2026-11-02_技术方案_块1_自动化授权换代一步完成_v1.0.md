## 0. 一句话方案

**把「换 provider」从三步塌缩成一步**：terminated 记录上直接带新 provider 的 Enable 被接受，走既有完整换代流程（删光旧 WIG → 轮换身份 → 解绑 → binding 换代 → 账本留痕 → 从零建新）。同时把失败面按语义拆成两个稳定码、把过期门卡按 durable 停点分流、把三个额度各用各的名字。

## 1. 问题与根因

### 1.1 换 provider 换不了：被一条硬门逼成三步

**现象**（owner 2026-11-02 真机，issue_0001，3 成员仓 LC）：在「Work Item Plan 配置」把 Author 从 `claude_code` 改成 `kimi_code`、Reviewer 反向互换，点「启用自动化」→ 稳定报 `automation enrollment revision conflict`；报错后自动化仍在跑，**provider 仍是旧值**。

**根因**：`supersede_terminated_enrollment` 对 terminated 记录有一条硬门 ——

`src/product/issue_automation_store_parts/cas_internals.inc.rs:671-681`：

```rust
let options_or_target_drifted = &saved.options != options
    || saved.target.as_ref().is_some_and(|declared| *declared != *target);
let source_drifted = &saved.source != source;
if options_or_target_drifted || (source_drifted && !original_source_dangling) {
    return Ok(CasResolution::Conflict { current_revision: Some(saved.policy_revision) });
}
```

注释写明「授权不改写：options/target 与终止记录逐字段相等」。**后果**：terminated 记录上直接带新 provider 的 Enable 被拒。

**前端因此把「换 provider」拆成三步**（`web/src/components/lifecycle/useIssueLifecycleGeneration.ts:465-588` 的 `runReenableSequence`）：

```
① terminated 上用【旧】options 重新开启  ← 这一步触发了 autopilot 生成
② Disable
③ 用【新】options 重新开启              ← 永远跑不到
```

**这个三步序列本身就是缺陷来源**：

| 环节 | 机制 |
|---|---|
| 步骤①触发 autopilot 生成 | autopilot 建 plan 后调 `bind_plan_ids_locked`，该函数 `next.policy_revision += 1`（`cas_internals.inc.rs:55`）→ 版本号被顶高一格 |
| 步骤②带旧版本号提交 | CAS 校验 `expected_revision != Some(saved.policy_revision)`（`src/product/issue_automation_store.rs:269-273`）→ Conflict |
| 步骤③永不执行 | provider 从未被改 |
| 步骤①的副作用 | **旧 provider 真的开始生成**，产出与 owner 意图不符的产物 |

> **注释与实现自相矛盾**：`cas_internals.inc.rs:49-50` 的注释写着「版本不递增——绑定不是换代」，`:55` 的实现却是 `next.policy_revision += 1;`；`:31` 的文档注释又写「才写入并 revision+1」。两处注释互相打架 —— 这正是该缺陷的起因。

### 1.2 「删除旧 WIG」不是副作用，是换 provider 的前提

**owner 2026-11-02 亲自给出的业务语义**：

> 删了就是全部都删了。重来一遍。想换 provider 也一样，删了重来一遍，**不要做接续**。
> - 当前 WIG 在跑 → 不能删、不能换 provider，要换只能重新生成
> - 当前 WIG 已终止且无法继续 → **必须先删掉它**，才能开新的 WIG 并切 provider

**代码已经做到了**（`src/web/handlers/automation_enrollment_reenable.rs:23-73` 的 `supersede_terminated_plan_generation`）：

> 删除 issue 下全部存活 plan（re-enable 后新代 plan 由新 intent 派生，旧代一律作废）：先收口未终结 attempt，再按同一闭包**物理删除** attempts/worktree/shared-worktree/reviewer 资源与 plan 根，只留一条无内容删除事实。

**换代留痕也已完整**（`cas_internals.inc.rs:688-763`）：`prepare_intent_id` 轮换、plan/session 解绑、两个 intent 文件删除、`attention_facts` 清空、binding 换代（旧代 current 进 `previous`）、账本 Accepted 留痕。

**缺的只有一件事**：那条「options 必须逐字段相等」的检查，把「换 provider」挡在门外。

### 1.3 两条失败路径共用同一个 409 码

`src/product/issue_automation_store.rs:246-268`（enabled 下异 payload）与 `:269-273`（revision 不一致）都返回 `CasResolution::Conflict { current_revision }`，映射成同一 `EnrollmentError::Conflict` 与同一句 `automation enrollment revision conflict`。

owner 读到后无法分辨该「等一下重试」还是「该先终止自动化」。

**接地审查核实**：该错误今天承载 **9 类语义**（33 个构造点 + 6 个字段声明），且旧码被终止自愈逻辑钉住（`web/src/components/chat-workspace/cockpit/automationTerminationConflict.tsx:17`）→ **不能直接改名**。

### 1.4 过期门卡文案与 durable 停点脱钩

过期门卡统一挂「此时只能终止此门后重新发起」+「终止此门」按钮（`web/src/components/chat-workspace/entries/GatePromptEntry.tsx:669-681`、`:777-784`；`gate-next-step.tsx:299-302`），而 `stopped_needs_human` 的真实入口是**页面底部输入框 +「继续自动化」**。

**已修的只有「已确认完成」一类**（`gate-next-step.tsx:87-88` `GATE_STALE_COMPLETED_COPY`，判据 `sessionStatus === "confirmed"`）；`stopped_needs_human` / `failed` / `terminated` / 「推进到别的门」仍按同一段文案渲染。

**文案实际住在 `gate-next-step.tsx`**（不是 `gate-prompt-copy.ts` —— 后者存的是动作/错误条文案，如 `GATE_TERMINATE_BUTTON_LABEL`）。

### 1.5 三个额度被混称为「自动修复」

| owner 看到的 | 实际是什么 | 计数来源 |
|---|---|---|
「自动修复次数已用完」 | 平台自动重写计划的次数 | `run_history.repairs_used / max_repairs`（默认 1）；耗尽信号 `trigger = repair_budget_exhausted` |
「还可自动修复 3 次」 | owner 反馈后平台返修的次数 | `human_gate_snapshot.manual_repairs_remaining`（默认 3） |
「你已回复过 N 轮」 | owner 在底部写说明的回合 | `human_gate_snapshot.accepted_feedback_turns` |

**关键事实**：仓库已有 owner 2026-10-31 的裁定（`src/product/workspace_engine/compile_failure_surface.rs:126-138`）写明 —— **平台自动重写与人工返修是同一个预算池**、记在两处账本上。

**所以「分别命名」不能做成「两个独立额度」**，必须如实表达共用关系。

**另一处事实性错误**：`ChatInputBar.tsx:510-512` 的「人工说明次数已用尽 / 评审轮的人工说明预算已耗尽」与 durable 事实相反 —— 实测当时是 `manual_repairs_used=0` / `manual_repairs_remaining=3`（满的），真正末节点是 reviewer provider run 失败。

## 2. 方案边界

### 2.1 架构边界原则

1. **换 provider = 一次操作**：terminated 记录上直接带新 provider 的 Enable 被接受，走完整换代流程
2. **不做接续**：换 provider 后不残留旧 provider 的绑定身份、生成意图、半成品产物
3. **授权留痕不因放宽而丢失**：只移除「options 逐字段相等」这条**内容检查**，不触碰留痕动作；`source` / `target` 的漂移管控保持不变
4. **CAS 校验不取消**：去掉的是「绑定造成的版本号漂移」，不是版本号机制本身
5. **失败面按语义分诊，不按来源分诊**：「等一下重试」与「该先终止」是两类用户动作，必须不同稳定码
6. **文案与动作同源**：门卡文案集中在 `gate-next-step.tsx`；不另起第二套

### 2.2 与既有契约的关系

| 既有契约 | 关系 |
|---|---|
REQ-WIGA-02（enabled 状态下异 payload 的 Enable fail-closed） | **保持不变**。本方案只放宽 **terminated** 路径 |
REQ-WPS-01（重新开启＝旧 plan 作废） | **保持不变**，且已是「物理删除全闭包」 |
REQ-WIGA-09（终止后禁止启用） | **保持不变**。terminated 的 Enable 走「人工显式取代」分支，非自动路径 |
单 plan 不变量（同一 issue 同时只有一个存活 plan 代际） | **保持不变**。「先删后建」是它的实现方式 |
停机态续跑契约 | **保持不变**。本方案只改门卡文案指向 |
provider 能力矩阵三态与准入 | **不涉及**（属块2 B-2） |
自动重写与人工返修共池 | **保持不变**。本方案只改呈现 |

## 3. 核心改动

### 3.1 放宽 terminated 路径的 options 检查

**落点**：`src/product/issue_automation_store_parts/cas_internals.inc.rs:671-681`

**改法**：`options_or_target_drifted` → 只保留 `target_drifted`；`source` 漂移管控**不动**（仍只在悬空源重授权时放行）。

**为什么安全**：换代留痕全部在 `:688-763` 已实现，与 `options` 是否变化无关。**账本条目已在换代之后用新 `binding_version` 构造**（`:708` 取 `binding_version + 1`，`:731` 使用）→ **不存在「落后一代」问题**。

#### 关键理解：「换代」的判据是**路径**，不是**内容**

这是本方案最容易被做错的一点。

**现状**：「换代」由 **`terminated_at` 是否存在**决定 —— terminated 记录上的 Enable **一律**走取代分支（`cas_internals.inc.rs:660-681` 的 match 臂）；disabled 记录上的 Enable 走 `apply_revision_and_write` 普通路径（`:276-281`）。

**放宽后**：

| 记录状态 | Enable 的结果 | 换代？ |
|---|---|---|
terminated | 走取代分支，**无论 options 是否相同** | **是** |
disabled | 走普通路径 | **否** |

**⚠️ 不得引入「options 不同才换代」的判据** —— 那是已作废的「甲-2 换代」路线的残留，照做会复活它（并导致每次临时开关都删 plan）。

#### 必须同批处理的实现细节

| # | 细节 | 处置 |
|---|---|---|
1 | **既有契约测试只需改 2 条** | terminated 路径只有 2 条断言需翻：`src/product/issue_automation_store/attention_termination_tests.inc.rs:805-819` 与 `:1098-1112`（断言「options 漂移即拒绝」→ 改为「接受并完成换代留痕」）。另有 `src/web/handlers/automation_reenable_supersede_tests.inc.rs:530` / `:617` 的注释与断言需按新契约改写 |

3 | **注释同步** | `cas_internals.inc.rs:665-670`、`src/product/issue_automation_store.rs:85-87` / `:103-107` / `:150-157` 里的「options 逐字段相等」表述需删 |
4 | **绑定注释修正** | `cas_internals.inc.rs:31`（写「才写入并 revision+1」）与 `:49-50`（写「版本不递增」）互相矛盾，需对齐实际行为。**绑定处的递增本身不删**（已不在用户路径上，但仍是并发语义的一部分） |

### 3.4 过期门卡按 durable 停点分流

**落点**：新增单一事实源 `web/src/components/chat-workspace/entries/gate-stale-guidance.ts`

**分流表（主键是 durable `sessionStatus`）** —— 不能只用 `actionBlockReason`，后者只说明「这张卡过期了」，说不出「这一轮归谁管」。

**⚠️ 表的适用前提**（接地审查 v3 的 P0-1）：本表**只适用于过期卡**（`actionBlockReason !== null`）。**非过期卡**（正在等你拍板的那张）**不受本表管辖** —— 它的「终止此门」按钮**必须保留**。

| durable 状态 | 文案（成品） | 指向 | 「终止此门」按钮 |
|---|---|---|---|
`confirmed`（**已修，保持**） | 「这一版已确认完成，此卡是历史记录，无需处理」 | 无 | 不显示 |
`terminated` | 「这次自动化已经终止了，这张卡是历史记录，不用再处理。」 | 无 | 不显示 |
`stopped_needs_human` | 「自动化停在等你回话的地方，这张卡已经过期了。请在页面下方的输入框里写一两句说明，然后点『继续自动化』—— 它会带上你的说明接着跑，不用重新开始。」 | 底部输入框 +「继续自动化」 | **不显示** |
`failed` | 「这一轮自动化跑失败了，这张卡已经过期了。请在页面下方点『继续自动化』重试；也可以先写一两句说明，一并带给 AI。」 | 底部输入框 +「继续自动化」 | **不显示** |
其余（推进到别的门） | 「会话已经走到下一阶段了，这张门卡不再接收操作。请以页面最新的一张门卡为准；如果这一轮确实要作废，可以点下面的『终止此门』。」 | 最新门卡 | **保留**（逃生口） |
`stopped_needs_human` 但**无真实续跑入口** | 「自动化停下来了，但这张卡已经过期。自动化当前不接受新的输入，请刷新页面看最新状态，或到自动化控制面处理这一轮。」 | 无 | 不显示 |
**非过期卡**（`actionBlockReason === null`） | **不适用本表**（保持现有文案） | 现有动作面 | **保留**（默认 `showTerminate = true`） |

### 3.6 「删了重来」失败的语义

owner 已裁定**接受**（先删后建，失败即空态）。

**失败面文案（成品）**：

> 「上一次的工作已经被清空（换 provider 会先删掉再重建），但新的没建起来。」
> **操作**：点「重试」重新开始。

**不得**表述为「什么都没发生」。

**「先删后建」是单 plan 不变量（同一 issue 同时只有一个存活 plan 代际）的实现方式** —— 改为「先建后删」会短暂有两个 WIG 存活，与 owner 的「删了就是全部都删了」直接矛盾，故不改。

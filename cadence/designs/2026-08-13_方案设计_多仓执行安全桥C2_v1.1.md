## 1. 背景与目标

C-1 完成了多仓执行核心（REQ-COD-01~04），但真实 provider 的多仓 coding 目前被 fail-closed 门挡住：`provider_stream.rs` 对 `is_logical_target && validated_input 为空 && 非 Fake` 直接拒绝（`logical_provider_gateway_required`）。**C-2 是解锁真实多仓编码的硬前置。**

Plan 2 已建成 `LogicalCodebaseProviderGateway` 完整机制（validate → ValidatedSessionLaunchPolicy、resume_or_start、run_sync、start_streaming、配置来源审计、Codex `danger-full-access` 路由级阻断，963 行 + 1115 行测试），但生产 Web 层**零处**构造 gateway，各引擎预留的 via-gateway 路径均未接通。

**目标**：把逻辑代码库流程的全部真实 provider 启动入口（split 同步栈 / 聚合初始化 / 聚合规划 / coding / review）统一收口到 gateway，使 REQ-ENV-01~06 在生产链路生效；Legacy 单仓路径行为零变化（单仓红线）。

## 5. 组件设计

### 5.1 GatewayFactory（Web 层新增）

- 位置：`src/web/`（如 `gateway_factory.rs`），挂在 `WebAppState`
- 构造输入：`ProductAppPaths`（从 `workspace_root` 得出）+ 既有 `provider_registry` / `provider_gate` / `provider_adapter`（AppState 已有）
- 每次 `build()` 产出新 gateway（policy store 每次 `validate` 实时读盘 → 政策修订后下次 launch 自动生效，无 stale 缓存）；共享 AppState 级 `Arc<GatewayRunAudit>`（`with_audit` 已为此设计）→ it_web 可跨入口断言累计审计
- `AggregatePolicyArtifactStore` 构造后调 `ensure_bootstrap`（幂等，消解 bootstrap 环，design.md §7.1）

### 5.2 生产 PolicyTargetResolver（REQ-ENV-03）

- `PlanningReadOnly` / `ReviewReadOnly` → 解析聚合根（无 writable root）
- `CodingTargetWrite` → 按 project_id + target_repository_id 复用 C-1 三层身份 `resolve_logical_repository_strict` → spawn 前复验：worktree 存在、canonical path、git-dir、HEAD 与 attempt 冻结快照一致（防 TOCTOU）
- 不一致/漂移 → fail-closed 拒绝启动

### 5.3 生产 ProviderCapabilitySource（REQ-ENV-05）

- store-backed 能力记录（持久化到 `.aria/projects/{id}/logical-codebase/`），三态 evidence（`declared` / `fixture_verified` / `production_verified`）+ exact version + adapter dialect
- 初始记录：ClaudeCode 按 design §5.2 定级（coding experimental，`fixture_verified`）；Codex = unsupported（`danger-full-access` 阻断，现有机制已实现）
- `require_supported` 不满足 → 阻塞不降级

### 5.4 Fake registry 分层（REQ-ENV-02）

- `default_provider_registry` 拆成两个显式构造：`real_registry`（**不含** `ProviderName::Fake`；现状 `web/state.rs:386` 生产模式无条件注册 Fake，必须移除）/ `fake_mode_registry`（测试联调用；控制标志是 `test_provider_enabled`，非 `ARIA_PROVIDER_MODE`）
- 删除 `provider_stream.rs:129` 运行时名字判断；门禁统一为"逻辑代码库流程必须带 validated policy"——Fake 测试里同样经 gateway 校验（同一代码路径），隔离靠构造分层

### 5.5 五入口接线细节

| 入口 | 接线动作 |
|---|---|
| coding | `CodingWorkspaceEngine` 增加 `with_logical_provider_gateway`；socket.rs 3 处构造点按 routing 注入；**validated_input 的生产填充点定在 engine 启动 provider 前**（统一 helper：engine 有 gateway 且 is_logical_target 时先 `gateway.validate`） |
| review | internal_pr_review / group_review_orchestrator / provider_retry 的 `validated_input: None` 改走同一 helper |
| split | workspace_ws_handler 按 routing 分流调 `invoke_provider_via_gateway`（去掉 `#[allow(dead_code)]`） |
| 聚合初始化 | `build_default_aggregate_dependencies` 中 `NoopProvider` → `GatewayBackedAggregateProviderTurnDriver`（注入 factory 产的 gateway） |
| 聚合规划 author（T10a） | `workspace_ws_handler/run/provider_run.rs` 4 处 + `followups.rs` 4 处 `.start` 按 routing 分流：Logical → `drive_author_provider_session_via_gateway`（注入 gateway），Legacy → 原直连 |
| 规划 review（T10b，决策 1A） | 先补 `workspace_engine/review/drive.rs` 的 via-gateway 骨架（对称 author），再在 handler 调用点接线；3 处 `.start` 分流 |

### 5.6 错误码与审计

- `ProviderGatewayError` → `ApiError` 映射：新增稳定码（policy_missing、target 漂移、capability 不满足、`logical_provider_gateway_required` 等）进 `web/error.rs` + `support.rs` 前缀表（沿用 C-1 §4.6 风格，部分已存在）
- 审计：`GatewayRunAuditEntry` 现仅 stack + policy_digest；`ConfigSourceAudit`（argv + config digest）独立构造。C-2 补聚合：final argv 与 config digest 入 run 审计记录（REQ-ENV-06 场景），并在 audit 中聚合 `ConfigSourceAudit`
- **managed-settings 语义修正**：现有 `enforce_config_source_policy` 对 managed-settings 活跃返回 `Err(ManagedSettingsActive)`（阻断），与 REQ-ENV-06 Scenario「运行时在 run 审计显式标注」及 design.md §5.1 不符；C-2 调整为「标注不阻断」（审计标注「managed-settings 活跃，Aria 注入可能被覆盖」）
- **setting sources 数据来源（决策 2B）**：代码库无 provider app-server `/status` 客户端；C-2 把标注逻辑接上审计（`detect_from_setting_sources` 已实现），测试用注入 sources 覆盖，生产采集后置阶段 D——采集不可用时审计标注 `managed_settings_detection: unavailable`

## 6. 数据流与 fail-closed 时序

一次逻辑代码库 coding 启动的完整时序（成功路径）：

1. WS `StartCoding` → runner → engine 在启动 provider 前进入统一 helper
2. helper 判断：`is_logical_target` 且 engine 已注入 gateway → 构造 `SessionLaunchRequest`（action=CodingTargetWrite、target、config artifact ref、capability snapshot ref）
3. `gateway.validate`：
   - `policies.get(project_id)` → 缺失/不一致 → `PolicyMissing` fail-closed 拒启（绝不退化无政策 fallback）
   - `targets.resolve_and_revalidate` → C-1 三层身份 + worktree identity 复验 → 漂移 → 拒启
   - `capabilities.require_supported` → Codex `danger-full-access` → 路由级阻断；其他能力不满足 → 阻塞不降级
   - 产出冻结的 `ValidatedSessionLaunchPolicy`（envelope：policy/target/config/dialect 快照）
4. `resume_or_start`：指纹（policy digest + target identity + provider version/dialect + capability snapshot）一致 → 续接；不一致 → 旧会话 superseded + 新会话
5. 组装 `ValidatedStreamingProviderInput` → `provider_stream` gateway 分支 → `start_streaming`（pre-spawn 复验 canonical cwd/git-dir）→ audit 记录 launch + final argv + config digest
6. 运行中：C-1 的 post-hoc 越界检测（CrossTargetBaseline）+ 交付前统一门，已有，不动
7. 离开 Running：admission marker 清理（C-1 会话语义），已有，不动

fail-closed 矩阵（验收核心）：

| 触发条件 | 行为 | 稳定码 |
|---|---|---|
| 政策缺失/不一致 | 拒启，无 fallback | policy_missing 类 |
| target 漂移（spawn 前） | 拒启 | target 复验失败码 |
| Codex danger-full-access | 路由级阻塞（非仅 UI 隐藏） | `codex_danger_full_access_unsupported`（已有） |
| 能力不满足 | 阻塞不降级 | capability 类 |
| resume 指纹不一致 | 新会话 + superseded | 已有 |
| 逻辑代码库 + 真实 provider + 无 validated policy | 拒启 | `logical_provider_gateway_required`（已有） |
| managed-settings 活跃 | 运行 + 审计显式标注（不阻断；现有实现为阻断，C-2 修正为标注） | 审计标注 |

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 接线点多（8-12 个 handler 调用点），单仓红线压力大 | T1 先行审计精确列点；每 Task 完成后跑 it_web 全量回归；Legacy 分支改动最小化 |
| validated_input 填充遗漏（review 多路径） | 统一 helper 唯一填充路径；T7 用 grep 全量清点 `validated_input:` 出现处 |
| 规划 author 8 处 handler 级 `.start` 分流复杂度 | T10a 拆分专任务；T1 审计精确列点；每处改动后跑 it_web 规划链路回归 |
| 规划 review 无 via-gateway 骨架（工作量低估风险） | 已单列 T10b；骨架实现对照 author 版对称补齐后再接线 |
| managed-settings 生产数据来源缺失 | 决策 2B：本轮注入式接线 + unavailable 标注，采集后置阶段 D（不阻塞 C-2 验收） |
| audit 内存共享的并发安全 | 沿用 `Arc<GatewayRunAudit>` + 内部原子计数（Plan 2 已实现） |
| gateway 每次 build 的构造成本 | factory 构造均为轻量薄封装（policy store 按 paths 构造、读盘发生在 validate 时），无缓存一致性问题 |

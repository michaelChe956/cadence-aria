# 组级最终审查可扩展架构设计

- 文档版本：v1.0
- 日期：2026-08-04
- 状态：待用户复核
- 目标范围：WorkItemGroup Group Final Review
- 首期容量目标：单组最多 20 个 Work Item

## 1. 背景与问题

当前 Group Final Review 把所有 Work Item 的完整 Reviewer Projection、重复的 EvaluationContextPack、完整变更 diff 以及公共审查协议放入一次 Provider 调用。

实测结果如下：

| 场景 | Prompt 大小 | 结果 |
|---|---:|---|
| 单项 Code Review | 16,967 B | 成功输出 JSON |
| 单项 Code Review | 20,976 B | 成功输出 JSON |
| 两项 Group Final Review | 82,497 B | 未输出 JSON |
| 两项 Group Final Review | 83,159 B | 未输出 JSON |
| 两项 Group Final Review | 84,676 B | 未输出 JSON |

第三次失败时 Codex 已正常完成全部命令和审查，并输出完整 Markdown 结论，但遗漏最终 JSON。该次 Provider 已产生 `Turn Completed` 与 `MessageComplete`，因此不是 Provider 截断、上游 503 或用户取消。

当前两项 Prompt 的主要构成为：

| 内容 | 大小 | 占比 |
|---|---:|---:|
| 两份 Reviewer Projection | 31,186 B | 36% |
| EvaluationContextPack | 27,257 B | 32% |
| 完整变更 diff | 15,777 B | 18% |
| 重复公共契约 | 5,250 B | 6% |
| 其他上下文 | 5,206 B | 6% |

如果沿用单次全量调用，20 个 Work Item 的 Prompt 预计达到约 754 KB；即使删除重复、去重公共协议并把 diff 限制到 12 KB，仍约 332 KB。纯减载不能满足 20 个 Work Item 的目标。

## 2. 设计目标

### 2.1 功能目标

1. 支持一个 WorkItemGroup 最多 20 个 Work Item。
2. 每次 Provider 调用的输入保持在 20–30 KB 量级。
3. 保留组级审查不可替代的跨 Work Item 检查能力。
4. 某一批审查失败时，仅重试该批，不重跑全部成功批次。
5. 最终结论继续使用现有 `InternalPrReview`、Group Finding Validator 和 Flow Decision。
6. Claude Code、Codex、Pi 使用相同的组级材料协议，不引入 Provider 特判。

### 2.2 质量目标

| 项目 | 上限 |
|---|---:|
| 正常 Prompt 质量目标 | 28 KiB（28,672 B） |
| 单次 Prompt 硬上限 | 30 KiB（30,720 B） |
| Leaf 最大 Work Item 数 | 4 |
| Leaf 输出大小 | 6 KiB 以内 |
| Leaf 最大 Finding 数 | 8 |
| Final 最大 Finding 数 | 16 |
| Leaf 有限并发数 | 2 |

超过硬上限时不得调用 Provider，应保存分段字节诊断并进入可恢复的材料溢出门禁。

### 2.3 非目标

1. 本设计不修改现有单项 Code Review 的 Reviewer Projection 文本。
2. 本设计不通过修改 Renderer Version 绕过已持久化的 Execution Context Hash。
3. 本设计不让 Provider 读取 `.aria` 内的外部 Artifact 文件。
4. 本设计不在首期接入 Provider 原生 JSON Schema / Function Call 能力。
5. 本设计不以截断完整 Projection 的方式假装材料完整。
6. 本设计首期不支持超过 30 个 Work Item；更大规模由后续树形归并承接。

## 3. 设计决策

采用“固定上限分片 + 全局交叉归约”的语义 Map-Reduce 架构。

```text
Authoritative Bindings
ReviewRequest
Unit Review Conclusion Snapshots
Git / Handoff / Evidence Facts
             │
             ▼
GroupReviewMaterialCompiler（Rust）
确定性检查 + 全局关系图 + 风险材料选择
             │
      ┌──────┴──────┐
      │             │
      ▼             ▼
Affinity Partitioner   Global Compact Ledger
每片最多 4 Unit          全局单位摘要与跨片边
      │             │
      ▼             │
Leaf Provider Reviews │
      │             │
      └── Shard Reports ──┐
                          ▼
                 Final Reducer Review
                          │
                          ▼
              Existing Group Finding Validator
                          │
                          ▼
                    InternalPrReview
```

单位数增加时，Leaf 调用数增加，但任意单次 Prompt 不增长。

| Work Item 数 | Leaf 数 | Final 数 | Provider 总调用数 | 单次 Prompt 目标 |
|---:|---:|---:|---:|---:|
| 2 | 1 | 1 | 2 | 约 26 KB |
| 5 | 2 | 1 | 3 | 约 26 KB |
| 10 | 3 | 1 | 4 | 约 26 KB |
| 20 | 5 | 1 | 6 | 约 26 KB |

## 4. 权威数据来源

所有组级材料必须从 `authoritative_group_reviewer_bindings(attempt)` 取得，不得从松散的 CodeReviewReport 顺序或 Round 反推 Work Item 身份。

该入口已经验证：

1. Unit Run 已完成。
2. Work Item Revision 一致。
3. Projection Bundle ID、Hash 和 Compiler Version 一致。
4. Resolved Handoff Revision IDs 一致。
5. 选中的是每个 Unit 的最新权威 Run。

新架构必须保留这套校验和最终 Group Finding 的唯一 Target 验证。

## 5. 材料模型

### 5.1 GroupReviewMaterialSnapshot

Rust 在启动任何 Leaf Review 前生成不可变快照：

```rust
pub struct GroupReviewMaterialSnapshot {
    pub schema_version: u32,
    pub attempt_id: String,
    pub review_request_id: String,
    pub base_branch: String,
    pub final_commit: String,
    pub authoritative_binding_digest: String,
    pub unit_records: Vec<UnitCrossReviewRecord>,
    pub global_graph: GroupReviewGraph,
    pub diff_index: GroupDiffIndex,
    pub deterministic_findings: Vec<DeterministicGroupFinding>,
    pub content_hash: String,
}
```

快照使用稳定排序和规范化序列化计算 Hash。Retry 必须复用相同快照；以下事实变化时生成新快照，并使关联 Leaf / Final 报告失效：

- Unit Rework 产生新 Completion Commit；
- Work Item Revision 变化；
- Handoff Revision 变化；
- ReviewRequest Commit 变化；
- 权威 Binding 变化。

### 5.2 UnitCrossReviewRecord

每个 Unit 的 Leaf 材料目标不超过 850 B：

```rust
pub struct UnitCrossReviewRecord {
    pub unit_id: String,
    pub unit_run_id: String,
    pub logical_work_item_id: String,
    pub work_item_revision_id: String,

    pub scope_summary: UnitScopeSummary,
    pub contract_interfaces: Vec<CompactContractInterface>,
    pub evidence_summary: UnitEvidenceSummary,

```

它不复制完整 Reviewer Projection，而是保留组级语义真正需要的摘要。

### 5.3 GlobalUnitLedgerRow

Final Reducer 中每个 Unit 只保留约 190 B 的全局状态行：

## 6. Rust 前移的确定性检查

以下检查不再让 Provider 从大量文本中重复判断：

### 6.1 权威 Binding 与 Handoff 完整性

- Run Completed；
- Revision / Projection Bundle / Hash / Compiler Version 匹配；
- Resolved Handoff IDs 与权威 Lineage 一致。

### 6.2 Contract / Capability 精确图

Rust 构建 Producer Output → Consumer Input 图并检测：

- 必填 Contract 缺失；
- 必填 Capability 缺失；
- 多个提供者导致歧义；
- Consumer 声明未绑定来源；
- 孤立 Output；
- 跨片 Contract Edge。

### 6.3 写入范围与 Ownership

- Changed Path 命中 Forbidden Scope；
- Allowed / Forbidden Scope 交集；
- 同一文件被多个 Unit 修改；
- Hunk 归属不唯一；
- 共享文件和跨片文件边。

### 6.4 Commit 与证据一致性

- ReviewRequest Commit 可达并包含所有 Completion Commit；
- Final Diff Base / Head 正确；
- Required Evidence Ref 属于对应 Unit Run 和 Commit；
- Evidence 字段完整。

### 6.5 Requirement / Criterion 聚合

- Requirement 或 Criterion 缺失；
- 多 Unit 重复声明；
- Revision 不一致；
- 完成 Unit 未覆盖已确认 Requirement。

### 6.6 Finding 路由预校验

Rust 汇总完整 Projection 中的 Reason Code、Allowed Route、Target Kind、Contract Refs。最终所有 Finding 仍必须通过现有 Group Finding Validator 和唯一 Authoritative Target 校验。

## 7. Provider 负责的语义判断

Provider 只处理 Rust 无法可靠完成的内容：

1. 多个 Unit 合并修改同一文件后是否存在语义冲突；
2. Contract 名称或 Capability 看似匹配但实现语义不一致；
3. 多 Unit 对 Requirement 的覆盖是否名义重复、实则遗漏；
4. 最终 Diff、证据状态和交付叙事是否自相矛盾；
5. 生成 Impact Scope、PR Description 和 Commit Message；
6. 对 Rust 标出的可疑跨片边和 Hunk 做语义判断。

## 8. 分片策略

### 8.1 最大分片大小

每个 Leaf Shard 最多 4 个 Unit。

### 8.2 亲和性排序

Partitioner 依次考虑：

1. 强 Handoff Dependency Edge；
2. 共同修改文件或 Scope Overlap；
3. 相同 Contract / Capability 边界；
4. 相同拓扑层；
5. 稳定的 `(order_index, unit_id)` 补位。

目标是让强耦合 Unit 尽量处于同一 Leaf。

### 8.3 大连通分量

若强耦合连通分量超过 4 个 Unit，采用稳定最小割分片；所有被切断的 Contract Edge、Shared Path Edge 和 Ambiguous Ownership Edge 必须进入全局 Cross-Edge Ledger，并在 Final Reducer 中审查。

## 9. Diff 选择

不得再把完整 Diff 或 30,000 字符前缀直接放入 Prompt。

### 9.1 全局索引

始终提供完整 Changed File Index：

- Path；
- Insertions / Deletions；
- Owner Unit Run IDs；
- Shared / Ambiguous Flags；
- Scope Violation Flags。

### 9.2 Leaf Hunk 选择

优先级：

1. 本 Shard 内的 Shared File；
2. Scope Anomaly；
3. Contract Producer / Consumer 涉及的文件；
4. Ambiguous Ownership Hunk；
5. 每文件至少保留 Header；
6. 剩余预算按风险公平分配。

Leaf Hunk 正文目标 10,500 B。

### 9.3 Final Hunk 选择

只提供真正跨 Shard 的 Shared / Ambiguous / Scope / Contract Suspect Hunk，目标 8,000 B。普通单 Unit Hunk 已由单项 Code Review 覆盖，不得挤占组级预算。

所有 Hunk 必须经过敏感信息脱敏、UTF-8 安全截断，并附：

- `truncated`；
- `redacted`；
- 原始 Hunk Hash；
- `not_shown_count`。

## 10. Leaf Review

### 10.1 输入预算

| 块 | 预算 |
|---|---:|
| 固定组级指令和一次输出契约 | 4,800 B |
| ReviewRequest / Snapshot Identity | 1,100 B |
| 4 个 UnitCrossReviewRecord | 3,400 B |
| 4 个 Unit Review / Evidence Digest | 1,400 B |
| Shard 内 Contract / Scope 图和 Rust 可疑项 | 2,800 B |
| 选中 Hunk | 10,500 B |
| Headers / Diff Stat / Truncation | 700 B |
| Retry 诊断预留 | 1,100 B |
| **合计** | **25,800 B** |

### 10.2 Leaf 职责

- 审查 Shard 内语义冲突；
- 审查本片 Handoff Consumption；
- 审查共享文件语义；
- 判断 Rust 可疑项是否构成 Finding；
- 生成有限的 Finding 和 Unresolved Obligation；
- 不生成最终 PR Description 或 Commit Message。

## 11. Final Reducer

### 11.1 输入预算（20 Unit）

| 块 | 预算 |
|---|---:|
| Final 指令、输出契约、合并规则 | 4,600 B |
| ReviewRequest / Snapshot Identity | 900 B |
| 20 个 GlobalUnitLedgerRow | 3,800 B |
| 5 份 Shard Conclusion | 3,750 B |
| 全局 Suspect Graph | 3,200 B |
| 跨 Shard Hunk | 8,000 B |
| Headers / Full Diff Stat / Markers | 1,000 B |
| Retry 预留 | 1,200 B |
| **合计** | **26,450 B** |

### 11.2 Final 职责

- 审查所有跨 Shard Contract / Shared File / Scope Edge；
- 合并并去重 Leaf Finding；
- 处理 Leaf 未决义务；
- 判断整组 Commit、Evidence 和交付叙事一致性；
- 生成最终 Verdict、Findings、Impact Scope、PR Description、Commit Message；
- 所有最终 Finding 通过现有 Group Finding Validator。

## 12. Finding 合并

使用稳定 Fingerprint：

```text
SHA-256(
  defect_class |
  reason_code |
  sorted repair_target logical/revision IDs |
  sorted contract_refs |
  sorted capability_refs |
  normalized file path |
  hunk hash-or-line-window
)
```

合并规则：

1. 相同 Fingerprint 合并 Evidence 和 Provenance；
2. Severity 取最高；
3. Verdict 规约：`blocked > request_changes > approve`；
4. 不同 Target、Hunk 或 Contract Ref 一律保留；
5. 不用模糊文本相似度自动去重；
6. Plan Defect 不能被 Implementation Finding 覆盖。

## 13. 失败、重试与失效

### 13.1 Leaf 失败

1. Provider 或 JSON 输出失败时，仅针对该 Leaf 执行一次小型 JSON Repair；
2. Repair Prompt 不得重新发送完整 Leaf Pack；
3. Repair 失败后保存原始输出和 Repair 输出，进入 `group_review_shard_output_invalid`；
4. 其他成功 Leaf 不重跑；
5. 未完成全部 Leaf 时不得启动 Final Approve。

### 13.2 Leaf Request Changes

- Target 唯一时按既有 Flow 路由对应 Unit Rework 或 Plan Repair；
- 新 Completion / Revision 使该 Leaf、所有相连 Cross Edge 和 Final Snapshot 失效；
- 未受影响 Leaf 若 Snapshot 输入未变，可复用。

### 13.3 Final 失败

- Final Provider / JSON 失败时只重跑 Final；
- Final Repair 失败后进入明确的 Group Output Invalid Gate；
- 不重跑已经成功且输入未变的 Leaf；
- 不允许因 Final 包装失败输出空 Findings 的 Approve。

### 13.4 Finding Target 歧义

- 找不到 Target、多个 Target、Revision 不一致、Reason Code 不存在时，视为无效 Provider 输出；
- 不得任意选择第一个 Unit；
- 进入 Human Gate 或明确重试。

## 14. Prompt 预算与诊断

每个 Prompt 构建后记录分段字节：

- fixed_protocol_bytes；
- identity_bytes；
- unit_records_bytes；
- evidence_digest_bytes；
- graph_bytes；
- diff_bytes；
- retry_diagnostic_bytes；
- total_bytes。

行为：

1. `total <= 28 KiB`：正常发送；
2. `28 KiB < total <= 30 KiB`：允许发送但记录 Warning；
3. `total > 30 KiB`：禁止调用 Provider，持久化 Overflow Diagnostic；
4. 任一单字段超限时不能静默截断 Contract Identity，应进一步分片或进入 Overflow Gate。

## 15. 与现有系统的兼容

### 15.1 Renderer Hash

- 不修改 `work_item_projection/render.rs` 的 per-unit 文本；
- 新组级 Pack 不调用旧的 Group `render_reviewer()` 拼接路径；
- 已持久化 Renderer Version / Content Hash 不变；
- 当前失败 Attempt 可以进入新组级架构 Retry，不触发 `IdentityMismatch`。

### 15.2 Provider

Claude Code、Codex、Pi 接收相同的 Compact Leaf / Final Prompt。首期继续使用现有文本 JSON 契约和本地 Parser，保留 Raw Output 审计。Provider 原生 Structured Output 留作独立平台能力项目。

### 15.3 前端

首期最终用户仍只看到既有 `InternalPrReview`。Leaf / Final 中间记录先作为后端审计 Artifact；前端仅需显示“正在进行组级分片审查”与可重试状态，详细 Provenance UI 后置。

## 16. 实施阶段

### 阶段 1：当前故障稳定化与基础设施

1. 新增组级 Prompt 分段字节诊断和 28/30 KiB 预算门禁；
2. 实现安全 Diff Index / Hunk 选择器；
3. 引入 Markdown-only → JSON 的小型 Repair；
4. 保证旧 InternalReviewer Hash Binding Retry 不触发 `IdentityMismatch`；
5. 当前全量单次 Prompt 若溢出则明确 Fail Closed，不再投递不可控输入。

阶段 1 不是 20 Unit 最终方案，只用于停止当前故障重复发生并提供阶段 2 所需基础能力。

### 阶段 2：20 Unit 主路径

1. 新增 UnitReviewConclusionSnapshot 和 GroupReviewMaterialSnapshot；
2. 实现 Rust 确定性预检查和全局图；
3. 实现最大 4 Unit 的亲和性分片；
4. 新增 GroupReviewShardReport 和 Leaf 调度 / Repair / Retry / 缓存；
5. 实现 Final Reducer、Finding 合并和现有 Group Validator 接入；
6. 以 20 Unit Fixture 验证 5 Leaf + 1 Final，每次 Prompt 不超过 30 KiB。

### 阶段 3：更大规模与平台能力

1. 当 Final Ledger 接近预算或需要支持超过 30 Unit 时，引入树形 Reducer；
2. 增加 Shard / Reducer Provenance UI；
3. 评估 Codex `turn/start.outputSchema`，Claude Code / Pi 保留 Prompt + Parser Fallback；
4. 增加 Provider 真实 Canary 与成功率遥测。

## 17. 验收标准

### 17.1 容量与预算

1. 20 Unit 生成 5 个 Leaf 和 1 个 Final；
2. 所有 Leaf Prompt 不超过 30 KiB；
3. Final Prompt 不超过 30 KiB；
4. 超限时在 Provider Start 前失败并列出各 Section 字节。

### 17.2 跨片完整性

1. Unit 1 Producer 与 Unit 13 Consumer 的 Contract / Capability 错配进入 Final；
2. Unit 2 与 Unit 18 修改同一文件时进入 Final Shared Hunk；
3. Unit 5 Forbidden Scope 由 Rust 直接标记；
4. 所有 Final Finding Target 必须唯一绑定权威 Unit Revision。

### 17.3 失败与重试

1. 单 Leaf Provider 失败只重试该 Leaf；
2. Leaf Markdown-only 输出可进入小型 JSON Repair；
3. Final Repair 失败不重跑成功 Leaf；
4. Unit Rework 只失效受影响 Leaf、Cross Edge 和 Final；
5. 任意失败不得生成 Approve。

### 17.4 兼容性

1. 已有 InternalReviewer Renderer Version / Hash Binding 可 Retry；
2. Claude Code、Codex、Pi 使用相同材料模型；
3. 现有单项 Code Review 行为不变；
4. 最终用户可见结果继续使用现有 InternalPrReview。

## 18. 风险与缓解

| 风险 | 缓解 |
|---|---|
| Compact Record 遗漏 Provider 所需语义 | 只压缩已由单项审查覆盖的字段；接口、Scope、Evidence、Target 元数据保留；超大接口进一步分片或 Fail Closed |
| Provider 调用数增加 | Leaf 有限并发 2；Snapshot 缓存；仅重跑失效 Leaf |
| 跨 Shard 漏检 | 所有 Cut Edge、Shared Path、Ambiguous Ownership 强制进入 Final |
| 新中间记录增加复杂度 | 首期只后端持久化；最终 API 继续使用 InternalPrReview |
| Finding 重复或错误合并 | 使用结构化 Fingerprint，不用文本模糊相似度 |
| Diff 证据不足 | 完整文件索引始终保留，Hunk 按风险公平选择，截断和未展示数量明确标记 |
| JSON Repair 改写 Finding | Repair 禁止重新审查；保留原始输出；Repair 后继续跑 Parser 和 Group Validator |

## 19. 后续扩展边界

方案 A 的 Final Reducer 在 20 Unit 时约 26.45 KB；预计 30 Unit 左右接近 30 KiB 上限。超过该规模时应引入树形 Reducer，使每层 Fan-In 固定，而不是继续压缩单个 Final Prompt。

本设计首期容量边界明确为 20 Unit；不得将 30 KiB 硬上限向上调以掩盖材料增长。

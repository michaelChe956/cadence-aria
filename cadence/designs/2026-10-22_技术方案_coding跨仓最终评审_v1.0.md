## 一、判定口径（先定，后文不再重复论证）

1. **分支键 = 代码库形态**，唯一权威 = `IssueRecord.logical_codebase_id`（`src/product/models/project.rs:140-142`，字段注释原文：「Some 表示逻辑代码库 lc_id；None 表示单仓代码库」）。
   - `Some(lc_id)` → **多仓库逻辑代码库** → 新链路（删每仓评审 + 一次 issue 级跨仓最终评审）。
   - `None` → **单仓库代码库** → **完全现状**：per-attempt internal review / GroupFinalReview / 组终审 / 阶段机 / 窗口与零锁恢复，**一行现有行为都不改**。
2. **读取入口** = `resolve_issue_logical_codebase_id(app_paths, project_id, issue_id)`（`src/product/logical_codebase/repository_routing_types.inc.rs:63-77`）→ `Option<String>`。
   - **退化**：issue 不存在（返回 `Ok(None)`）或读取报错 → 按 `None` 处理 = 走单仓现有逻辑（安全默认，绝不因读不到就切换行为）。
3. **不可用的替代判定（已排除）**：`has_aggregate_scope_system_context()` / `is_aggregate_planning_session()`（`src/product/workspace_engine/prompts.rs:411/432`）是**规划侧** session 消息启发式，coding 侧拿不到，不采用。
4. **coding 侧既有相近物不作为分支键**：`RepositoryRouting::load_for_issue`（`repository_routing_types.inc.rs:118-133`）的 Legacy/Logical/FailClosed 三态按「manifest+selection 是否存在」判定，与 owner 的「代码库形态」口径不完全等价（单仓代码库若残留 selection 会被判 Logical）。故：**分支键只用 `logical_codebase_id`**；`RepositoryRouting` 继续作为仓解析权威，行为不变。
5. **不做「issue 涉及几个仓」的计数分支**（owner 2026-10-22 已替代该口径）。

## 二、现状核实（决定删除范围的依据）

1. **fresh attempt 的 per-attempt internal review 在当前生产流里已经不可达**：
   - 唯一把 attempt 推进到 `InternalPrReview` 阶段的写入点是 `internal_pr_review.rs:261`（在 `execute_internal_pr_review_with_commands` 内部）；该函数的生产调用点只有 `runner.rs:698`，而 `runner.rs:660` 的前置条件是 `current.stage == InternalPrReview` —— 循环依赖，fresh attempt 永不进入。
   - group attempt 走 `group.rs:362` → `ReviewRequest` → `prepare_group_final_confirm_from_readiness`（`handoffs.rs:604-636`）→ `FinalConfirm`+`WaitingForHuman`；注释明确「fresh group bypasses InternalPrReview」（`runner.rs:459-461`、`handoffs.rs:638-641`）。
   - 结论：`InternalPrReview` 只对**存量 durable attempt**（磁盘 `stage=internal_pr_review`）与 group 兼容路径可达。
2. **GroupFinalReview 执行入口已无生产调用**：`execute_group_final_review_with_commands`（`legacy_group_final_review.inc.rs:8`）仅被 `src/product/coding_workspace_engine/tests/group_review_compatibility.rs:287/335` 调用（TEST-ONLY）。
3. **两处 GroupFinalReview prompt 重复**：`internal_pr_review.rs:140-212`（group scope：units+handoffs+EvaluationContextPack+diff）与 `prompts.rs:97-163`（单 WI：work item markdown+EvaluationContextPack+diff），两者标题同为 `"Coding Workspace GroupFinalReview"`、输出 JSON 契约同形；分歧只在材料段。
4. **code reviewer 是门**：`code_review.rs:4/13` 的 `execute_code_review{,_with_commands}` 与 `provider_retry.rs:493` 的 retry-cycle 保留不动。

## 四、B｜新增评审（位置与形态）

**B1 模块与记录**
- 新增 `src/product/coding_models/cross_repo_review.rs`：`IssueCrossRepoReview { id, project_id, issue_id, plan_id, verdict: ReviewVerdict, summary, findings: Vec<ReviewFinding>, repository_sections: Vec<CrossRepoRepositorySection>, status: Completed|Failed|Skipped, failure_reason: Option<String>, raw_provider_output_ref: Option<String>, created_at }`；`CrossRepoRepositorySection { repository_name, logical_repository_id, attempt_id, branch_name, base_commit, head_commit, work_item_ids: Vec<String>, diff_truncated: bool }`。
  - 复用 `ReviewVerdict`（`coding_models/review.rs:81-85`）与 `ReviewFinding`（`review.rs:144-176`）。
  - `findings.source_stage` 统一填 `CodingExecutionStage::InternalPrReview`（语义＝internal reviewer 产出面）；**不新增枚举成员**，避免污染 attempt 状态机词汇。跨仓 findings 的来源靠记录 id + `repository_sections` 区分。
- 新增 `src/product/coding_attempt_store/issue_cross_repo_review.rs`（issue 级持久化），登记进 `coding_attempt_store/mod.rs`（`mod` + `pub use` 既有模式）。
- 新增 `src/product/coding_workspace_engine/issue_cross_repo_review.rs`（engine：材料装配 + prompt + 跑一次 provider + 落盘），登记进 `coding_workspace_engine/mod.rs`。

**B2 输出 schema 与解析**
- schema 名：`coding_workspace_issue_cross_repo_review_json`（与既有 `coding_workspace_internal_pr_review_json` 同风格）。
- 输出 JSON：`{"verdict":"approve|request_changes|blocked","summary":"...","findings":[{"severity":"error|warning|info","file_path":"...","line":1,"message":"...","required_action":"...","repository":"<仓名>"}]}`。
- **自写解析器**：复用 `ReviewFinding` 的反序列化，但**不跑** plan-defect 校验与路由（`plan_defect_routing.rs`、`plan_repair_start.rs:47`）——确保 findings 永远不会进入返工 / Plan Repair 路径。

**B3 prompt**
- 全新 prompt（不复用 GroupFinalReview prompt 的「WorkItemGroup 全部 units」假设）。标题 `Coding Workspace IssueCrossRepoFinalReview`；结构：项目/issue/plan 头 → **逐仓分段**（仓名 + work item 列表 + attempt + branch + base..head diff）→ 跨仓一致性检查清单（契约一致性、跨仓调用面、上下游交付闭环）→ 输出 JSON 契约 → 注入既有 reviewer 纪律段（`reviewer_test_scope_contract()` / `reviewer_process_evidence_boundary_contract()` / `no_default_stack_assumption_contract()`，见 `prompts.rs:86-88` 同款用法）。
- 明确写死：**本评审是建议性（advisory），不得要求返工，不得输出门控指令**；findings 的 `required_action` 只作建议。

**B4 材料装配**
- 分段来源：该 issue 下**每个已完成 attempt 一段**（group attempt 一仓一段；单 WI attempt 一仓一段）。
- 分段顺序：按 `attempt.target_snapshot.logical_repository_id` 升序（稳定、可复现）；`target_snapshot` 为 `None`（旧单仓记录）时按 `attempt.id` 升序。
- diff 区间：`git_diff(attempt.worktree_path, code_review_diff_base(attempt))`（`prompts.rs:747-759` + `git_workspace_service.rs:574-608`）——与 code reviewer 看到的材料**同源同口径**（`code_review_diff_base` 对 group scope 返回 base_branch 或 head_commit）。
- 预算：每段 diff `truncate_prompt_section(&diff, 30_000)`（与 code review 同值）；**全包上限 120_000 字节**，超出按仓顺序截断并在末尾写 `truncated_repositories: [...]`（显式标注被截断的仓，不静默省略）。

**B5 provider 与角色**
- 角色 = `CodingProviderRole::InternalReviewer`（编码环节角色表中的 internal reviewer）。
- provider 取值：`get_role_provider_config_snapshot(project, issue, attempt).internal_reviewer`（`coding_attempt_store/attempt.rs:754-767`）；**缺失 → 回退同快照的 `.code_reviewer`**；两者都缺 → 评审不执行，`status=Skipped`，advisory，不阻断。
- 超时：`DEFAULT_PROVIDER_TIMEOUT_SECS`（与 `internal_pr_review.rs:88` 同值），由既有 provider 框架承载。
- **不新建 reviewer 窗口**、不产出 `acceptance` / `review_window_id` 字段（避开 T19 采信门，见 §五）。
- **失败语义**：provider 失败 / 超时 / 输出不可解析 → `status=Failed` + `failure_reason`，advisory，不阻断、**不重试**（advisory 场景重试收益低、复杂度高）。

## 八、F｜验收标准（可判定，含负例）

**F1 单仓库代码库回归（`logical_codebase_id == None`）**
- A1：coder → code reviewer → internal review → FinalConfirm 全链路的**事件序列、状态迁移、门控、reviewer 窗口记录**与改动前逐项一致——既有 `coding_workspace_engine/tests/group_final_readiness.rs`、`src/web/coding_ws_handler/runner.rs` 内联用例、`tests/it_product/product_coding_workspace_engine/*` 全部绿。
- A2：单仓库代码库 issue 的磁盘**不产生** `coding-cross-repo-reviews/` 目录；`coding_attention_items` 中**无** `kind=cross_repo_review` 条目；`pending_gates` 保持为空。
- A3：`CodingExecutionStage` 枚举成员集合**不变**（A3 保留 `InternalPrReview`、不新增成员）；存量 attempt JSON 的 `stage` 取值集合不变。

**F2 多仓库逻辑代码库新链路（三仓夹具）**
- B1：3 个 attempt（3 个仓）全部完成 → **恰好一次**跨仓评审：`review.json` 存在、`status=Completed`、`repository_sections.len() == 3`；材料含 **3 段 diff**（按 logical_repository_id 升序）。
- B2：评审 `verdict=request_changes` → **coding 仍可确认**：`handle_final_confirm` 成功、attempt `Completed`、issue 不被阻断；`coding_attention_items` 出现 `kind=cross_repo_review`；用户确认后 `acknowledgements/` 出现 **1 条**记录（含 verdict、findings 数、通道、时间戳）。
- B3：评审 provider 失败 / `verdict=blocked` → **仍可确认**；记录 `status=Failed` 或 `verdict=blocked`；`pending_gates` 为空；**无任何** `RunCoderFix` / `StopForHumanTriage` 分流（负例断言）。
- B4：code reviewer 不通过 → **仍返工**（`RunCoderFix` 路径回归不变）；跨仓评审的存在不改变该行为。
- B5：group 形态仍工作：group attempt 走 readiness → `FinalConfirm`；多仓库逻辑代码库形态下 **InternalReviewer provider 启动次数 = 0**（provider 计数断言）。
- B6：重复触发（两次进入收口钩子）→ `review.json` 只更新不新增评审，`acknowledgements` 不重复。

## 1. 背景与目标

C-5 = WP5f：向每个成员仓发布极薄 AGENTS.md/CLAUDE.md 最小指针（logical codebase ID、repo ID、canonical policy locator、「未加载集中政策前禁止写」声明），经独立 worktree/branch 受控发布并生成 ReviewRequest（非自动 PR），可回滚，处理仓内已有文件的合并；同步改造 prompts，使逻辑代码库流程的规则依据从「完整读取目标仓根 AGENTS.md/CLAUDE.md」切换为「envelope 校验过的聚合政策为权威正文（携带 revision/digest）+ 指针仅发现 + 未加载有效政策阻塞」。

## 2. 已确认决策（brainstorming 记录）

| 决策点 | 结论 |
|---|---|
| Q1 指针发布触发时机与范围 | **A：独立"指针发布"操作**——成员集合稳定后由用户/前端显式触发一次全量发布（每仓独立 worktree/branch/commit/push/ReviewRequest，可回滚）；之后新增成员触发增量发布 |
| Q2 已有文件合并策略 | **A：标记块追加 + 冲突降级人工**——文件存在时末尾追加显式起止标记的指针块；不存在则创建极薄指针文件；重发幂等跳过；内容不一致降级冲突人工 |
| Q3 prompts 分流边界 | **A：统一 helper 内分流**——`with_cadence_routing_reference` 单点按上下文返回两套 reference 段落，4 个协议 prompt 调用点不重复分支 |
| 总体方案 | **方案 1：独立 PointerPublication 实体 + 泛化现有交付管线**（否决：方案 2 合成 attempt_id 语义污染；方案 3 全新子系统双轨维护） |

## 3. 架构总览与组件划分

新增 3 个组件、泛化 2 个既有组件、改造 1 处 prompts 分流点：

1. **`PointerPublication` 聚合实体（新）**：一次"指针发布操作"的记录（全量或增量批次）。字段：`id`、`project_id`、`logical_codebase_id`、`batch_kind`（Full | Incremental）、每成员条目状态（`pending | skipped(幂等一致) | conflict | committed | pushed | review_created | failed | revoked`）、时间戳。发布进度的唯一事实来源，与 coding attempt 生命周期完全解耦。
2. **`PointerContentTemplate` 生成器（新，`logical_codebase` 模块内）**：生成标记块文本；提供幂等匹配与冲突检测函数（纯函数，易测）。
3. **`PointerPublishCoordinator`（新）**：编排每仓发布流水（临时 worktree → 写入指针 → branch → commit → push → ReviewRequest → 清理）；错误收集为条目状态，不整体失败。
4. **`CodingGitOperationJournal` 泛化（既有）**：journal `kind` 增加 `PointerPublish`，复用既有 phase 状态机（BranchCreated→CommitCreated→PushStarted→Completed）与补偿/重开逻辑，不复制状态机。
5. **`ReviewRequest` 泛化（既有）**：增加 `owner_kind`（`Attempt` | `PointerPublication`）区分两种来源；Attempt 路径行为零变化。
6. **Prompts 分流点（既有）**：`with_cadence_routing_reference` 内按上下文分流（见第 6 节）。

数据流：前端触发 → Web API → `PointerPublishCoordinator` → 逐仓（journal 状态机 + ReviewRequest）→ 前端状态面板轮询。

## 4. 数据模型与存量兼容

1. **`PointerPublicationStore`（新，`logical_codebase` 模块内）**：仿 `AggregateInitializationOperation` 操作级 store 先例。主记录 `pointer-publications/{publication_id}.json`（单文件原子写 + CAS 更新，参照 C-1 AdmissionTicketRecord 先例）；每成员条目状态内嵌于主记录（不拆 N 个小文件，避免部分写窗口）。
2. **`ReviewRequest` 泛化（加法改动，不动既有字段）**：
   - 新增 `owner_kind: ReviewRequestOwnerKind`（`Attempt` | `PointerPublication`），serde 缺省 `Attempt` → 存量记录反序列化零迁移；
   - 新增 `pointer_publication_id: Option<String>`；`attempt_id` 字段名保留（Attempt 语义不变）；
   - PointerPublication 来源的 request：`attempt_id` 填合成稳定 id `pointer-pub-{publication_id}`（命名空间与真实 attempt id 隔离，不创建伪 attempt 实体）；
   - 持久化：`pointer-publications/{publication_id}/review-requests/{request_id}.json` 独立分区，不塞进 attempt_dir（attempt_dir 有 scoped 校验，强绑定 issue/attempt）。
3. **`CodingGitOperationJournal` 泛化**：`kind` 增加 `PointerPublish`；该 kind 下 `issue_id` 置空、`attempt_id` 复用存 `pointer-pub-{id}`；`validate_journal`/`is_allowed_transition` 按 kind 分流校验必填集合。journal 文件落在 `pointer-publications/{id}/git-operations/` 分区。
4. **既有读取器兼容**：`issue_delivery`（IssueDeliverySummary 双条件）、review 列表 API 只按 `owner_kind == Attempt`（或缺省）过滤，PointerPublication 的 request 不混入 Issue 交付聚合；前端 review 展示按 owner_kind 区分来源标签。
5. **并发约束**：同一 logical codebase 同时至多一个进行中发布批次（发布锁，仿仓维锁先例）；成员条目状态推进单 writer。

## 5. 指针内容模板 + 发布/冲突/回滚流程

### 5.1 指针内容（标记块模板）

```text
<!-- aria-logical-codebase-pointer:start
  logical_codebase_id: <id>
  repo_id: <id>
  canonical_policy_locator: <聚合根政策 locator>
  声明：未加载集中政策前禁止写；本块仅用于发现，不作为政策正文
  pointer_version: 1
aria-logical-codebase-pointer:end -->
```

- 目标文件不存在 → 整体创建极薄文件（仅标记块 + 一句说明）；已存在 → 文件末尾追加标记块，原内容零改动。
- **不携带动态 revision/digest**：指针只负责发现；revision/digest 由 prompt 装配时从 envelope 注入（REQ-PROMPT-02 的落实点）。聚合政策每次修订不需要重发指针。

### 5.2 幂等匹配与冲突检测（纯函数，生成器内）

- 无标记块 → 追加，条目 `committed`；
- 有标记块且规范化内容一致 → `skipped`（不建 branch、不 commit、不 push）；
- 有标记块但内容不一致 → `conflict`（不自动改写文件，不 push；条目标记冲突，前端提示人工处理，人工解决后按仓重试）。

### 5.3 每仓发布流水（`PointerPublishCoordinator`）

全量批次：遍历全部成员仓；增量批次：比对成员集合快照只发新增成员。每仓独立执行：

1. 基于成员 checkout 的 HEAD 建临时独立 worktree（publish 专用，不进 coding worktree 注册表）；
2. 建分支 `aria-pointer/{repo_id}/{publication_id}`；
3. 写入指针 → `skipped` 则直接清理 worktree 结束；
4. commit → push → 生成 ReviewRequest（`owner_kind=PointerPublication`）；
5. 清理 worktree；push 失败走 journal 补偿/重开（复用 C-3 reopen 模式），条目 `failed`。

单仓失败不阻断其他仓，整体按 partial 呈现（沿用 C-3 三态风格）。

### 5.4 回滚

「撤回发布」操作：删除远端 publish 分支 + ReviewRequest 标记 `Revoked` + 条目 `revoked`。只动远端分支与记录，不触碰成员仓主 checkout；publication 记录保留作审计。

### 5.5 安全边界

不自动 PR（ReviewRequest 是 GitBranchOnly）；不在成员主 checkout 上做任何 git 操作。

## 6. Prompts 分流改造

### 6.1 分流点

`with_cadence_routing_reference(protocol)`（`src/product/coding_workspace_engine/prompts.rs:408`）增加上下文参数，签名变为 `with_cadence_routing_reference(protocol, context: &RoutingReferenceContext)`；4 个协议函数（`coding_execution_protocol` / `coding_delta_execution_protocol` / `code_review_material_protocol` / `group_final_review_material_protocol`）同步增加 `context` 参数透传。计划阶段需确认各调用点上下文可获取性；若某调用点拿不到，分流上移（plan defect 先例流程处理）。

### 6.2 新类型（`routing_reference.rs`）

- `enum RoutingReferenceContext { Legacy, Logical(LogicalPolicyReference) }`
- `LogicalPolicyReference { policy_id, revision, digest, authority_root（聚合根 locator） }`——来自 envelope 校验过的聚合政策（REQ-PROMPT-02 要求携带 revision/digest）。

### 6.3 两个分支的注入文本

- **Legacy 分支**：现有 `direct_cadence_routing_rules_reference()` 文本字节级不动，现有 2 个单测原样通过；
- **Logical 分支**：新增 `logical_cadence_routing_rules_reference(policy_ref)` 动态模板：
  - `[cadence_project_rules]`：规则依据 = envelope 校验过的聚合政策正文（声明权威根 + policy revision/digest）；目标仓根 AGENTS.md/CLAUDE.md 中若存在 aria 指针块，仅用于发现/路由，不作为政策正文；
  - `[cadence_rule_read_gate]`：未加载有效聚合政策 → 只报告阻塞，不产出候选 artifact/代码/审查结论/JSON（与 Legacy fail-closed 对称，REQ-PROMPT-01 指令层落实）。

### 6.4 双层阻塞

prompt 文本是指令层；真正"未加载有效政策拒绝启动"由 gateway/envelope fail-closed（C-2 已建）保证。本次改造让指令层与启动层语义一致，不新建启动层机制。

### 6.5 范围边界

- 改：`src/product/cadence_skills/routing_reference.rs`（增 Logical 分支）、`src/product/coding_workspace_engine/prompts.rs`（4 协议函数 + helper 参数化）；
- 不改：`src/product/work_item_split_engine/prompts.rs` 的 Draft Prompt 正文（不在 REQ-PROMPT 靶子内）；
- 交付义务：因触及共享 `cadence_skills` 装配模块，交付前必须提醒用户授权 Case A/Case B 各 10 次真实 Claude Code 验证（work-item-draft-prompt-validation 规则），未授权不调用 Provider（见第 10 节）。

## 7. API、前端与错误处理

### 7.1 Web API（新增，`logical-codebases` 域）

| 端点 | 用途 |
|---|---|
| `POST /logical-codebases/{id}/pointer-publications` | 创建发布批次（body：`batch_kind = Full | Incremental`） |
| `GET /logical-codebases/{id}/pointer-publications` | 批次列表（最近批次 + 汇总状态） |
| `GET /logical-codebases/{id}/pointer-publications/{pid}` | 详情（逐成员条目状态） |
| `POST /logical-codebases/{id}/pointer-publications/{pid}/retry-repo` | 单仓重试（人工解决冲突后） |
| `POST /logical-codebases/{id}/pointer-publications/{pid}/revoke` | 撤回发布（回滚：删远端分支 + ReviewRequest 标记 Revoked） |

ReviewRequest 查询：PointerPublication 来源走独立查询端点（`owner_kind` 过滤），不混入 attempt 的 review 列表。

### 7.2 前端

逻辑代码库详情页新增「成员指针发布」区块 `PointerPublicationPanel`：

- 状态总览（批次 kind、逐成员条目：committed/pushed/skipped/conflict/failed/revoked）+ partial 警示（仿 C-3 DeliveryStatusPanel 三态风格）；
- 「发布指针」按钮（全量）+ 新成员注册后的增量发布提示（Q1=A）；
- 冲突条目：展示冲突点 + 「人工已解决，重试」按钮（retry-repo）；
- 「撤回」按钮（revoke，二次确认）。

### 7.3 错误处理与稳定码（沿用 C-2/C-3 稳定码 + 错误映射模式）

| 情形 | 表达 |
|---|---|
| 发布锁冲突（同 logical codebase 并发批次） | 409 + `pointer_publish_busy` |
| 成员未注册 / 参数非法 | 422 |
| push 失败 | 条目 `failed` + `pointer_push_failed`（HTTP 503 层面对应） |
| 冲突未解决重试 | 条目保持 `conflict` + `pointer_conflict_unresolved`（409） |
| journal 补偿失败 | 复用既有 `AwaitingManualRecovery` 呈现模式 |

## 8. 测试策略（TDD，先红后绿）

- **lib 单测**：指针模板生成器（标记块渲染/幂等匹配/冲突检测三态）；`ReviewRequest` serde 缺省 `owner_kind=Attempt` 存量兼容；journal `PointerPublish` 状态机流转与按 kind 校验分流；`PointerPublicationStore` 原子写/CAS/发布锁；prompts 两分支——Legacy 字节不变断言（现有 2 测试原样通过）+ Logical 模板断言（含权威根、revision/digest、阻塞声明）；协调器条目状态流转表驱动。
- **it_web（REQ-ENV-07 / REQ-PROMPT-01/02 验收）**：真实 HTTP+WS+git 场景——全量发布 2-3 仓成功（独立 worktree/branch/commit/push + ReviewRequest）；增量只发新增成员；幂等重发 `skipped`；冲突仓 `conflict` → 人工解决 → retry-repo 成功；单仓 push 失败 partial 三态呈现；revoke 回滚（远端分支删除 + ReviewRequest Revoked）；prompts 分流集成断言（logical prompt 含聚合政策引用与 digest，legacy 不变）。
- **前端 vitest**：PointerPublicationPanel 三态/冲突/撤回交互。
- **门禁**：lib、it_web、it_core、前端、clippy/fmt/tsc、openspec validate；large_file_guard ≤1200 行。

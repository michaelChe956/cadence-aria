## 0. 结论摘要

**推荐最小主流程：复用跨 attempt resolver,将上游 owner 的 `worktree_path + handoff.commit_sha + 契约/能力` 追加到 coder 实际 prompt；修 Kimi 终端 tmpfs 后只读挂入 authority root、仅本仓 target 可写。** 不增加 REST、不把路径写入 immutable handoff、不复制源码、不 merge/push 上游。

三个候选不是三选一：路径未告知与 Kimi terminal `/tmp` 遮蔽均已由源码坐实；api worktree 被外部清除两次是用户/coder 现场观察,不能据此认定 busi 也被删除。`cross_attempt_handoff.rs` 确实存在且为 **7789 字节**,旧报告“找不到”已推翻。`provided_capabilities` 源码类型是 map,不是数组。

上游完成时登记已有 `group_handoff_contract_facts`；最小补齐是 handoff refs 为空时从冻结 `output_contracts` 登记,不增加 coder 自报解析。运行环境问题复用块2已确认的 `coding_operational_blocker`、三动作与 A1 通知；不补 plan blocker_rules、不重复设计门/UI。

owner 已要求主流程优先：独立固定 SHA 快照、运行期目录清除恢复、并发/旧数据/原子性等只登记风险,不纳入本批主流程验收。正文所有推荐均以此收敛版本为准。

## 2. 根因判定:路径未告知 / 沙箱遮蔽 / 目录被清除

| 候选 | 判定与证据 | 主流程动作 |
|---|---|---|
| 路径未告知 | **成立**：执行信封只带 IDs/start commit,resolver 只返回 ID。§1.3/1.5 | 复用 owner,注入明确上游路径+SHA |
| 沙箱遮蔽 | **成立于 Kimi Auto terminal**：target root bind 在 tmpfs 前,fd 仅恢复当前 cwd。§1.2 | tmpfs 后只读挂 authority,再仅 target rw |
| 目录被清除 | api 被删两次是用户/coder 事实；**不能断言 busi 也被删或指认删除进程**。§1.6 | 运行环境问题走 operational gate；自动修复为第二档风险 |
| 未点最终确认 | 已读 resolver **不以 owner attempt final-confirm 为条件**。§1.5 | 不让用户先点上游确认,与块1 D0 独立 |

结论：两个源码缺口并存,删除另属环境风险；本文“实测”指当前 W 源码构造/接线,不冒充历史进程 namespace 重演。

## 3. 目标行为

1. 上游 unit/run 完成并发布 handoff 后,下游自动启动,无需上游 attempt 最终确认。依赖身份沿既有 plan/WI/revision/run 绑定,不按裸 ID 全局搜。
2. 下游 coder prompt 明确上游 WI/仓、handoff SHA、owner worktree 绝对路径、契约/能力；native fs 与 terminal 都能读该真实源码。集成验收用真实上游,不允许 contract double 的 PASS 替代 required 验收。
3. provider 进程 cwd 仍聚合根,terminal cwd 仍 target；authority/上游只读,本仓 target 唯一可写。上游交付路径无需进入 handoff 模型或新增 writable roots。
4. 环境缺目录/不可读时 coder 报 `operational_blocker + operational_gate`,复用块2门与通知；用户“再试”或“说明情况”后继续。
5. 上游完成发布时平台从冻结 WI 契约登记 contracts/capabilities；不让 coder 自报能力成为权威。

运行中目录被删除、上游继续提交导致路径内容前进：已知风险,批1不处理,见 §12。

## 4. 方案选项与推荐

| 方案 | 利 | 弊 | 选择 |
|---|---|---|---|
| **A owner worktree 路径+SHA 注入,修只读 mount** | 复用现有路径/权限/resolver,无源码复制,最快拉通真实集成 | owner 目录可能被删/继续前进 | **本批推荐,符合 owner 主流程裁定** |
| B 独立固定 SHA 快照 | 内容稳定,不依赖 owner 工作树寿命 | 新物化/目录/生命周期设计,非最小改动 | 第二档,批1不处理 |
| C 只注入 diff/文本/符号证据 | 无目录接线 | 不能保证真实完整代码可导入运行 | 不满足主流程 |

主流程仅三步：resolver 拿到 owner/handoff→实际 prompt 追加路径清单→Kimi terminal 恢复 authority 只读可见。新增字段是运行期 DTO,不是 WI projection/envelope 变更；沿用最终 prompt 追加模式,避免修改既有 renderer/hash。若需要只读上游编译产物,构建写入当前 target 测试区,不为上游开写权限。

## 6. 数据模型与接口变更

新增内存 DTO `ResolvedUpstreamDelivery`(cross_attempt_handoff.rs,pub(super))：
- String：`logical_work_item_id,work_item_revision_id,owner_attempt_id,source_unit_run_id,handoff_revision_id,logical_repository_id,commit_sha`。
- `source_path: PathBuf` 来自 owner.worktree_path；`provided_contracts: Vec<String>`、`provided_capabilities: BTreeMap<String,Vec<String>>` 来自 handoff。

新增 `resolved_upstream_deliveries_for_attempt(&self, attempt) -> Result<Vec<ResolvedUpstreamDelivery>, CodingWorkspaceEngineError>`；group+target+有依赖才生成,其余空。沿当前run resolved IDs和既有owner校验取值,不拿baseline替代。

prompt段 `[resolved_upstream_deliveries]` 序列化DTO,固定说明“从source_path读真实上游；只读；测试在本仓target；不可读报 operational_blocker/operational_gate,repair_target=null,reason_code=upstream_source_unavailable；替身PASS不算集成通过”。

`TerminalIsolation::Bubblewrap.readable_root: Option<PathBuf>` 仅从可信boundary authority生成,direct=None。不增持久JSON、REST/WS、renderer版本或writable roots。并发/恢复一致性：已知风险,批1不处理。

## 7. 上游完成时登记 provided_contracts / capabilities

**改哪**：`group_completion.rs::group_handoff_contract_facts`；复用既有 hash/build/publish,不新增字段。

**主流程**：读完成run绑定的冻结canonical contract→refs非空保持原选择；refs空则取 `output_contracts[*].contract_id`→排序去重→从对应output生成capabilities map→原完成链发布handoff并更新unit pointer→下游读取。无output的非接口WI仍允许空,不解析coder自由文本作为权威。

原过滤器只认refs,所以output已声明CT-001而refs为空也会丢契约；新主流程夹具覆盖该形态。**现场WI-001 refs/output原值未读,不声称已证明历史空值根因**。存量空handoff回填/immutable迁移：已知风险,批1不处理。

## 8. 运行环境类阻塞改走 operational gate(与块 2 coding_operational_blocker 对齐)

**改哪**：本块仅 `prompts.rs::resolved_upstream_deliveries_section`；校验/落门复用块2 §3.2/§4.1/P2-b,不改validator本体、不补plan blocker_rules。

**接口**：finding=`operational_blocker + operational_gate`、`repair_target=null`、建议reason=`upstream_source_unavailable`,保留读取命令/路径evidence。门reason是块2的 `coding_operational_blocker`,两者不混用。

**主流程**：coder读不到真实源码→finding→块2 coder-only放宽→OpenOperationalGate→coding/rework落门→Blocked+A1通知→三按钮→A4重跑。owner已确认D-2=A(AI报环境问题即认)、D-4=A(说明情况提交即重跑),不再决策。

这是coding阶段 **gate** 补上下文,不是plan对话窗口。宿主错误绕过finding等失败路径：已知风险,批1不处理。

## 9. 失败与回退路径
- 主流程环境不可读：复用 §8 operational gate,用户恢复后再试/补上下文,不退回契约替身通过。
- 自动恢复被删目录、fallback 快照、Git 对象缺失、依赖安装失败：已知风险,批1不处理。
- 并发/原子性/存量数据迁移/清理责任：已知风险,批1不处理。

## 10. 对单仓与手动模式的隔离方式
- 上游清单只在 group+target_snapshot+存在依赖时生成；legacy 单仓返回空,不增加 prompt 段、不触 renderer/hash 或 final-confirm。
- Kimi direct 的 `readable_root=None`,只修复 root bind 被 tmpfs 遮蔽的顺序,原角色 rw/ro 判定、Supervised 审批、cwd fd 不变；LC 只把已有 authority 读面落实到 terminal,不扩 target 写面。
- 手动多仓同样能读真实上游；不自动点击任何手动门。环境门三按钮采用块2已确认通用行为,plan 对话通道不变。
- 主流程验收包含一条 legacy 单仓正常 coding→review→final-confirm 冒烟,以及多仓 target 可写/上游只读的权限基本断言。

## 1. 目标与范围

补齐多仓库支持（BCD 全阶段）经双轮审计确认的 6 项生产入口缺口，使人工测试可以按 `cadence/notes/2026-08-18_人工测试矩阵_BCD多仓支持.md` 的 P0 主线从登记一路走到规划。

**完成定义**：it_web 通过**真实 HTTP 端点**复现 REG-01 / INIT-01 / IDX-01 / PLN-01（含多仓 Design `change_order` blocker，PLN-05），且单仓 project 行为零变化（默认 feature disabled 不变）。

**出界（后续 change）**：selection 显式编辑 UI、索引定时轮询兜底（`poll_due` 仅保留库能力，不声称有生产 scheduler）、单仓→多仓升级迁移、50 成员生产压测。

## 2. 已确认的产品决策（用户拍板）

| # | 决策 |
|---|---|
| D1 | 多仓库模式=按 project opt-in：创建时勾选，创建后不可切换 |
| D2 | 登记 UI=逻辑代码库页"登记成员"弹窗向导（填聚合根 → 预检分类 → 勾选确认 → 提交 → 结果/恢复） |
| D3 | 聚合初始化=begin → 共享 registry lease → tokio::spawn(execute)，cancel 经 CancellationToken，step 边界检查 |
| D4 | selection=多仓 project 创建 issue 时服务端自动写 all_members（请求体不变） |
| D5 | 索引触发三层：初始化成功尾步首建 + resolver 读时 stale sync + 手动重建（同步） |
| D6 | 登记与索引重建均**全同步**（POST 返回最终结果），前端配 loading 动画 |
| D7 | 首个登记批次提交时原子创建 manifest（用户提交的 aggregate_root 为准；后续批次 root 不一致 → 409） |
| D8 | preflight 冻结快照持久化到磁盘（RegistrationPreflightSnapshotStore，TTL 24h） |

## 3. 架构总览

```
前端 (web/src)
 ├─ CreateProjectDialog：+「多仓库模式」勾选（loading 无需）
 ├─ 逻辑代码库页
 │   ├─ 登记向导（7 类预检分类展示 → 勾选确认 → 同步提交 loading → 结果/partial/恢复）
 │   ├─ 聚合初始化卡片（触发 → 步骤进度轮询 → 取消）
 │   └─ 索引卡片（active/stale/degraded/missing 状态 + 同步重建按钮 loading）
 └─ 新增 api client/types：registration、aggregate-initialization、aggregate-index

后端 (src/web + src/product)
 ├─ Project 模型：ProjectRecord/CreateProjectInput/CreateProjectRequest/ProjectDto + multi_repo
 │   （serde default=false 兼容旧 JSON）
 ├─ RepositoryStore::for_project(paths, project) 构造器：multi_repo→enabled，否则 disabled；
 │   逐点替换 18 处生产 RepositoryStore::new 调用（读路径 legacy 保持 disabled 由调用点判断）
 ├─ WebAppState：扩展现有 InitializationRunRegistry（key 已泛型化）：值从 HashSet 升级为
 │   HashMap<key, CancellationToken>（单仓旧调用方无感，MINOR-1）；另加 per-project 索引重建
 │   进行中注册表（try-register，用于 409）
 ├─ 新建 RegistrationPreflightSnapshotStore（磁盘：logical-codebase/preflights/{id}.json，
 │   存冻结 RegistrationCandidate 全量 + aggregate_root + created_at，TTL 24h，重启存活）
 ├─ handlers/logical_codebase_registration.rs（新建，同步）
 ├─ handlers/aggregate_initialization.rs：spawn execute + 共享 registry + token cancel
 ├─ handlers/aggregate_index.rs（新建，同步 rebuild + GET active）
 ├─ mod.rs：补导出 RegistrationBatch* 系列
 ├─ product_resources.rs：多仓分支 issue+selection 补偿事务
 └─ 错误码映射：registration_* / aggregate_root_* / aggregate_index_* 族补入 support.rs
```

## 4. API 契约

### 4.1 登记（新建，全同步）

```
POST /api/projects/{pid}/logical-codebase/registrations/preflight
  body {aggregate_root, candidate_paths[]}
  → 200 {preflight_id, created_at, items[{path, class, reason?}]}
  服务端顺序：AggregateRootPreflight::validate → coordinator.preflight（B-6 修复）
  class 稳定枚举：eligible / non_git / duplicate / nested / needs_attention / missing / outside_root
  （注：candidate enum 有 dirty 但生产 classifier 对脏仓返回 needs_attention，API 以 needs_attention
   单一状态呈现，UI 标注 reason=dirty；不含 profile 字段——profile 仅 attach 阶段检测，
   避免预检阶段多一次磁盘探测，MINOR-3）
  冻结持久化：结果全量（含每 candidate 各自的 preflight_revision/canonical_path/
   git_root/source_identity）写入 RegistrationPreflightSnapshotStore（D8）；
  响应不暴露顶层 preflight_revision（模型是 per-candidate 的，不虚构批级字段）

POST /api/projects/{pid}/logical-codebase/registrations
  body {aggregate_root, preflight_id, confirmed_paths[]}
  → 200 {batch_id, status: completed|partial_failed, items[{path, status, reason?}]}
  服务端：load 快照（preflight_id 过期/不存在 → 404 registration_preflight_not_found）
         → 按 confirmed_paths 过滤候选 → 重建 ConfirmedRegistrationBatchInput
         （含 needs_attention 项 → include_needs_attention=true，MINOR-9）
         → coordinator.submit + 同步执行 TOCTOU 复验 → 逐项 attach_member
  漂移语义（MAJOR-2，与既有代码行为对齐）：
   - preflight_revision 变化 → item 级 needs_attention 跳过，批次继续
   - 路径/git root/source identity 变化 → 整批中止 409 registration_batch_conflict
  manifest 一致性（B-7 补齐）：
   - 提交的 aggregate_root 与既有 manifest.provider_context_root 不一致 → 409
     aggregate_root_mismatch（无论首批还是后续批次）
   - manifest 不存在（真首批）：manifest 创建 + 首成员 attach 在 manifest store 既有
     single-writer 锁内原子完成
   - manifest 已存在（迁移/指针链先建）：仅校验 root 一致后走正常 attach
   - 单仓 project 调用 → 409 logical_codebase_feature_disabled

GET /api/projects/{pid}/logical-codebase/registrations/{batch_id}
  → 200 批次详情（含单项状态/失败原因）

POST /api/projects/{pid}/logical-codebase/registrations/{batch_id}/resume
  → 200 同步重跑未完成项（漂移语义同上）

POST /api/projects/{pid}/logical-codebase/registrations/{batch_id}/cancel
  → 200 仅对 Queued/PartialFailed 批次有效（终态标记 cancelled）；
     Completed/Cancelled 批次 → 409 registration_batch_not_cancelable
     （handler 显式判定，不依赖 store 的静默 no-op，MINOR-4）
```

revision 漂移后只能新建批次（旧批次终态保留可审计）；不提供单 item 重新确认端点（YAGNI）。

### 4.2 聚合初始化（既有端点，行为修复）

```
POST /api/projects/{pid}/logical-codebase/initializations
  → 202 {operation_id}
  handler：coordinator.begin → 扩展后的共享 InitializationRunRegistry.register(lease+token)
           → tokio::spawn(execute)
  execute：Created→Running→machine_skills→aggregate_preflight→3×provider turns→Completed/Failed
  cancel：POST …/{operation_id}/cancel → 取 token → cancel()；execute 在 step 边界检查
          → Cancelled；provider turn 结束后不再推进
  服务重启恢复：GET 时 Running 且 registry 无 lease → recover_interrupted（标 Failed +
          interrupted reason）；人工重触发=新建 operation，不复活旧 id；前端重触发时
          生成新 idempotency key，避免 deterministic_operation_id 幂等返回旧 Failed 记录
          （MINOR-8）
  生产依赖：AggregateInitializationDependencies 使用真实 skills 准备、AggregateRootPreflight、
          index 接线（替换 NoopSkills/NoopPreflight，B-2 修复）
```

索引首建挂接：execute 成功尾步 spawn `AggregateIndexOperation::build`（包 single-writer 锁）；首建失败不回滚初始化，索引状态=missing+失败原因（无 last-known-good 时不用 degraded，m-4），可手动重建。首建期间漂移同重建语义（见 4.3）。

### 4.3 聚合索引（新建，同步）

```
POST /api/projects/{pid}/logical-codebase/aggregate-indexes/rebuild
  → 200 {record}（spawn_blocking 执行，前端 loading）
  并发互斥（MAJOR-3）：AppState per-project try-register 进行中注册表，已注册 → 409
  aggregate_index_rebuild_in_progress；获取注册后走 single-writer 阻塞 flock（排队语义
  仅在同进程内不可能出现，因 try-register 已拦截）

GET /api/projects/{pid}/logical-codebase/aggregate-indexes/active
  → 200 {state, revision, indexed_at}
  state 映射：Active→active；Stale→stale；Degraded→degraded；Building→rebuilding；
        Superseded→不可见（取最新非 superseded 记录）；
        Failed→有 last-known-good 时返回该 good 记录的 degraded，无 → missing（MINOR-2）；
        无任何记录→200 + state=missing（不用 404，便于前端统一渲染）
```

apply_index 状态机（MAJOR-1）：先 store.create 持久化 Building record（并发 GET 可见
rebuilding）→ CodeGraph 命令 → 成功后 replace_active 切 Active；失败 → Building 记录转
Failed（遵循 store.rs:165 replace_active 文档要求的既有契约）。

快照语义（M-10 + MAJOR-6）：before-snapshot → CodeGraph 命令 → after-snapshot；
- 重建/sync 期间漂移 → 新 record 标 stale（不静默丢弃），active 引用 before-snapshot 组
- 首建（Initialize 模式）期间漂移 → record 标 Failed（而非 stale，避免无 active 可读），
  可手动重建

resolver 读路径（M-8/M-9）：PlanningContextResolver 在读 `active_required` 得 Stale 时调 `FreshnessService::sync_if_stale`（spawn_blocking）；修 `assess` 对 Degraded 记录无条件返回 active 的 bug（保留 last-known-good 告警语义）；Degraded 不自动重建，注入规划上下文告警。

### 4.4 issue 创建（变更）

```
POST /api/projects/{pid}/issues（请求体不变）
  多仓 project 分支（补偿事务，M-4）：
    预校验（manifest 存在 + active members 非空）
    → IssueStore::create_with_repository（repository_id 必须属于 manifest active member）
    → IssueCodebaseSelectionStore::save(all_members)
    → save 失败：删除刚建 issue → 422 issue_selection_write_failed；
      删除也失败：记录 orphan 告警日志并 500（人工修复路径）
```

多仓 project 的 legacy repositories 端点（M-7）：GET 返回成员投影；POST/DELETE → 409 `legacy_repository_endpoint_on_multi_repo`（body 指引走 registrations）；legacy `/repository-initializations/{operation_id}` GET 同码 409（MINOR-5）；单仓 project 行为完全不变。

repository_id 语义（MAJOR-5）：多仓下保持必填，语义=**primary repository**（必须属于
manifest active member；用于 UI 归属展示与兼容投影）；不参与 selection——selection 恒为
all_members（含全部 active member）。前端创建对话框在多仓 project 下从成员列表选择
primary（默认第一个）。（不允许为空：避免本轮改请求体校验链。）

## 5. 数据流与生命周期

- **登记**：无后台任务。请求内同步执行；幂等由 coordinator 既有批次机制保证。
- **初始化**：唯一 spawn 长任务。lease/token/registry 全部 AppState 共享（B-1）；worker panic 时 lease Drop 自动清理（lease 持有移到 worker 任务内）。
- **索引**：首建（初始化尾步 spawn）/读时 sync（spawn_blocking）/手动重建（同步 spawn_blocking）统一走 single-writer 锁。
- **selection**：issue 创建同步补偿事务。

## 8. 风险与遗留

- `replace_active` 跨文件非事务（m-5）：single-writer 锁解决并发，进程崩溃窗口保留为已知限制，park（与既有行为一致，不恶化）。
- 侵入面清单（MINOR-7）：`RepositoryStore::new` 替换为 `for_project`（实测 28 个文件，约 16-17 生产 + 余为测试 fixture）与 `CreateProjectInput` 构造点（约 27 处）+ 前端 Project 类型/fixture 传播，均在 Plan 中列为独立 task + 逐点核对清单；for_project 的 project 查找失败 → 404 project_not_found（不静默降级 disabled）。
- `poll_due` 定时兜底不在本轮（D5 出界），规格 REQ-IND 的"定时"场景以手动重建 + 读时 sync 满足，delta spec 中显式说明。

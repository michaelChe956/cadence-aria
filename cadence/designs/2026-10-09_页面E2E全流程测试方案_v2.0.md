## 1. 结论与范围门

**推荐：复用 Rust 的真实环境与探针能力、使用产品 CLI 单端口服务、在既有 `web/e2e` 体系内新增独立 real 配置；浏览器承担所有业务动作，Rust 仅承担运行材料和真实 provider 前置。** 不新建另一套顶层 Node 测试包，不复用矩阵的 API/WS 旅程来代替页面点击。

**发现确定性前置阻断：当前产品不能把 involved 为 4 仓的 Design 经现有页面准备为可执行 Plan。** `src/web/handlers/lifecycle/plan_preparation.rs::prepare_plan_records`（120–143、251–262）按 Design involved 集执行 `preflight_single_repository_candidate`，后者在 `src/web/handlers/lifecycle/preflight.rs`（28–41）只接受恰一仓；4 仓返回 `SINGLE_CANDIDATE_PREFLIGHT_FAILED`。rollout flag 不提供多仓 fallback。`cadence/plans/2026-09-30_迭代计划_未完成事项收尾_v1.0.md` §C/C7 还记录多 target 页面入口与 fan-out 的延期裁决。因此，**1.5–2.5 天作为测试资产与首轮真实结果的条件目标，不可承诺四仓全流程 PASS；完整通过必须先解除产品能力前置。** 本设计保留完整目标，不自行缩成单仓、四个 issue 或只三仓有 commit。

本次设计只写本文档，不改产品、测试或其他规划文件。后续实施前，双审必须确认上述能力缺口的处理边界，再按项目规则形成 OpenSpec 契约和实施 Plan；不会借测试方案自动授权延期功能。

## 3. 六项必答：证据、取舍与结论

### Q1. 独立 Node 装配还是 Rust harness 引导

**结论：Rust 薄 supervisor + 产品 CLI 子进程 + Playwright 接管；复用真实生产 seam，不整体复用矩阵旅程。**

| 方案 | 成本 | 隔离 | 真实性与问题 |
|---|---|---|---|
| 推荐：Rust 薄 supervisor | 新增一个 ignored 集成测试入口与分文件支持模块；复用既有 trust/probe 签发、导入和 fixture 建法 | 独立 run-root、四 bare origins、受管 PID 子树；浏览器流程与环境职责分开 | CLI 使用真正 `serve_web`；Rust 不创建项目/LC/issue，不发送业务 WS 动作 |
| Node 独立 assemble | 简单启进程便宜，但真实 capability/trust 没有已核对的独立 CLI/HTTP 签发入口，需要新增桥或复制 Rust 逻辑 | 容易形成第二套 HOME/trust/能力落盘约定 | 直接拷矩阵 JSON 或伪造 Confirmed 不可接受；看似便宜实际隐藏前置成本 |
| 整体复用 `MatrixEnvironment::build` | 代码量最少 | tempdir/drop 生命周期绑定矩阵测试 | 已 API 完成建档、初始化、issue，吞掉 S1–S3；只 `build_web_router` 还缺静态 fallback 与 CLI 后台生命周期，违背 Ruling 17 |

supervisor 持有环境与 teardown，拉起预构建 `aria web`；浏览器完成 S1–S3 后通过自己的阶段标记交回 project/LC 身份；supervisor 在产品服务器停止的静止窗口执行 Codex trust 和真实 capability 探针导入，再以同一 workspace 重启 CLI；浏览器重进页面继续。此窗口是**显式运行前置**，不得记成页面动作；不读取或改写业务确认状态。停服导入避免两套 runtime 同时写同一 LC。复用 `WebRuntime::new_real_with_events`、`WebAppState::with_events` 与 `LogicalCodebaseGatewayFactory::durable_probe_writer_for_lc` 装配，runtime 与 app state 共享同一 `EventHub`；以 `src/web/app.rs::serve_web`（649–659）的实际构造链为准。只使用生产签发包与 `record_verified_probe`，不调用矩阵 pump。

### Q2. 前端服务形态

**结论：Playwright 直打产品单端口，不开 Vite 或独立静态服务。** E2 已证实 CLI 嵌入 `web/dist` 并挂载 SPA fallback。正常验收清除 `ARIA_WEB_DIST`；磁盘 escape hatch 只用于明确标记的调试，不作为最终嵌入形态证据。构建顺序固定：前端 build → Rust bin 与 ignored 测试预构建 → 启动 → `/api/health`、`/api/runtime-info`、`/workbench` 同源核对。端口使用 `--port 0`，读取本 run 的 `.aria/web-endpoint` 及监听行，禁止端口探测后重新 bind 的竞态、禁止 reuse 用户服务器。

### Q3. 页面登录与身份

**结论：当前本地产品工作流匿名可用，不设计账号登录或 storageState 认证。** E1/E4 读取范围是路由、全量 router 构造与 API 通用请求层：未观察到登录页面、认证 middleware、Bearer 注入。S0 新 BrowserContext 直接访问；要处理的实际阻碍是 provider 检测、首次引导/更新提示和浏览器系统通知权限。提示通过真实关闭/跳过入口处理，不能注入 Zustand 或 localStorage 伪造已过状态。

三种身份不可混淆：产品页面无登录 ≠ Codex CLI 凭据已就绪 ≠ 生成案例的 `X-User` 鉴权。Codex 真实账号与 trust 在 G1/G2 核验；案例 `X-User: e2e-user` 是通知中心数据归属，缺失 401 在 S9 验收，不用于 Aria 登录。

### Q4. 门与 choice 的稳定语义锚定

**结论：既有 testid 定位容器、role/label 定位控件、只读事实核对语义；不匹配 AI 长正文，不按 first/last 盲点。** E5/E6 已有 `cockpit-page`、`gate-prompt-entry`、`gate-artifact-context`、`gate-inline-protocol-error`、`choice-request-entry`、`coding-pending-gate`、`coding-workspace-page`、`delivery-status-badge[data-status]` 等锚。普通门按钮 `确认当前版本` 与 Coding `确认完成` 是不同动作。

1. 工作台先选定本 run 的 project/issue；会话按实际导航 URL 中 sessionId 绑定；同页面只操作可见、未解决、enabled 的当前门。门多于一个候选且身份不可唯一对应时失败，不用 `.first()`/`.last()` 掩盖歧义。
2. 阶段、gate/choice 身份及允许动作只取当前页面接收的真实 WS/HTTP 只读观测；点击前核对 DOM 与事实同一身份，点击后必须同时观察控件忙/解决态及真实 durable 变化。监听不得产生额外 WS、不得调用 store、不得直接构造回应帧。
3. choice 使用真实 radio/checkbox，`label` 含选项 label/description；归一仅做 Unicode/空白/编号前缀与中英别名，不删除否定词。由题目和案例固定契约决定答案，然后通过该选项可访问名点击。多题逐题作答，再点击 `提交选择`；不得认为所有选择都是可多选。
4. 四仓范围题必须选全部四仓，依赖顺序固定 `busi → api → gateway → frontend`。不得直接移植 E8 的「单仓优先」「无匹配默认首选」策略。未知题、多个同级答案或涉及质量绕过，保存完整题目/选项并 fail-closed，由 controller 分析；不是随机选「合理项」。
5. `GatePanel` 中 `send_to_coder`、验证分诊、质量 bypass 分开；严禁为赶进度选择跳过验证或人工质量豁免。若出现修订，使用页面反馈 editor 并保留输入和 gate 身份；相同 finding 不重复试运气。
6. 只有现场证明确实无法由现有 testid/aria 唯一定位，才在后续 Plan 中申请最小 DOM 元数据增补，属性只投影既有 ID，不增加测试专用业务 API。本文不把不存在的 `data-gate-id` 当现有能力。

### Q5. 单巨 spec 还是每阶段独立 spec

**结论：分阶段文件 + 外层串行编排 + 持久阶段清单；不是一个巨测试，也不是共享 page 的 `describe.serial`。**

单巨 spec 编写快，但一次超时丢失大量步骤计分；`describe.serial` 失败会跳过后续、重试整个组且 worker 重启，不能兑现「最近阶段重放」。依据：[Playwright 重试与串行语义](https://github.com/microsoft/playwright/blob/main/docs/src/test-retries-js.md)。

supervisor 依次调用 S0–S3、S4、S5、S6、S7、S8、S9 对应 spec，每段新 context、重进真实页面、从 `run.json` 读取已观测 ID；进程边界不共享内存。`workers=1`、`retries=0`。`run.json` 只是观测台账，不作为产品状态来源，段首必须重新读取页面/只读 API 并检查前置。失败立即停止后续执行；后续标 `not_executed`，不能标 passed。

**重入与恢复有边界：** 同版本健康服务器上已完成段可重进页面；运行中的刷新会触发卸载保护，不在 active provider 中主动刷新。现有 E9 快照只到 plan-confirmed，且写死 alpha/单首仓 HEAD；四仓快照须另有经审查的适配，不能直接拿旧矩阵快照承继新案例。首轮默认从空环境全链执行，不以快照跳 S1–S6；修复后诊断续跑可只重进未完成段，若需回灌仅恢复测试拥有的目录，先保留失败现场，沿固定绝对路径、四仓 HEAD、schema/build/provider/CLI/策略/能力摘要和 quiescent 门校验。续跑结果标 `diagnostic_resume`，不冒充全链 fresh PASS；源码触及 E9 路径或任何前端流程/选择器/夹具契约即拒绝承继，重新全链。

### Q6. 与既有后端矩阵的断言边界

**结论：不重做四 provider × fresh/resume 格，不重复 split_sync、负向 write probe 与 native-ID 矩阵；保留页面成功所必需的最小 durable 交叉核对。** 真实探针作为能力前置运行、引用原工件，不在本轮重新给 provider 支持格计票。

| 读面 | 最小抽验时点与字段 | 不做的重复工作 |
|---|---|---|
| 成员/初始化/bootstrap | S1、S2 各一次终态读；四 active 成员身份、operation completed、planning_ready | 不枚举所有登记失败码/recipe 拒绝矩阵 |
| issue lifecycle | S3/4/5/6/8 各一次稳定点；本 issue ID、artifact id/version、confirmation_status、WI target/dependency、交付汇总 | 不每个流帧 dump，不复制所有 EvidenceCell 字段，不单独调用生成/confirm 接口推进 |
| Coding snapshot | 每 target 开始与最终确认前后；address、target、stage、status、readiness、completion SHA、push | 不以任意 waiting_for_human 代替终门；不重新测试 native resume 全格 |
| git/bare origin | 初始及隔离基线、每段边界、全程只读监测；主 checkout 内容/HEAD 和交付分支远端 SHA | 不把主仓 commit 当交付成果，不执行破坏性复位抹证据 |

正常业务状态读取均优先产品既有 GET：`/api/issues/{issueId}/lifecycle?project_id=...`、LC scoped members/bootstrap、scoped Coding snapshot（E7/E12）。只有初始化 receipt、provider audit 等无对应可用投影的诊断材料才由 supervisor 只读归档。后端读取不能替代页面断言，页面颜色也不能替代 durable 事实。

## 4. 终版架构与执行契约

### 4.1 数据与控制流

```text
controller 预构建并冻结产品/前端/测试版本
  └─ Rust ignored supervisor（只拥有本 run-root 与进程树）
      ├─ 四层基线 git 仓 + 四个 bare origin + 空产品 workspace
      ├─ 产品 aria web --workspace <workspace> --host 127.0.0.1 --port 0
      │   └─ 同源静态页面 / API / WS / 真 provider gateway
      ├─ Playwright S0–S3：建档、登记、初始化、创建 issue（全真实点击）
      ├─ 静止停服 → Codex trust + 三 action 真探针签发/导入 → 同路径重启
      ├─ Playwright S4–S9：逐阶段页面动作，GET 只核对
      └─ 失败/成功均收束子树、保留证据；S9 启动已交付业务代码验收
```

探针 actions 是 **`SessionPolicyAction` 枚举变体**：`PlanningReadOnly`、`CodingTargetWrite`、`ReviewReadOnly`，其逐 action 能力矩阵经 `ProviderCapabilityRecord::action_matrix` 承载（`provider_capability_store.rs`：121–123、282–284），包含需要的 resume 支持；沿 E7 既有 `run_cli_boundary_probe` 签发包导入，缺 bwrap/user namespace、凭据或真实工件时 BLOCKED，不写允许值替代。Codex CLI exact version 现场记录并冻结；草稿的 `0.155.1` 只当历史值，不假定机器仍是该版。工作流 author/reviewer/coder/code-reviewer 均在页面选择 Codex 并在真实角色快照核对。**聚合初始化仍是现产品固定 Claude recipe（E7）**，故初始化依赖 Claude 可用；这不是暗中改 provider。pi 不自动备用，换 provider 必须新 run 和显式裁决，不接续 Codex 证据。

supervisor 对页面进程的阶段结果只接受原子落盘、匹配 runId/build 的台账；段失败即以非零退出收口。页面不收发自造 WS；禁止 `page.route` mock、`ARIA_PROVIDER_MODE=fake`、`ARIA_E2E_TEST_CONTROLS=1`、test provider 及沿用 fake start-api。JSON 台账字段至少为 runId、sourceRevision、distDigest、binaryDigest、provider/version、baseURL、workspace/aggregate/origin roots、project/LC/issue/session/plan/attempt IDs、stage/status、startedAt/endedAt、evidenceRefs；秘密只记录摘要/路径类型，不能归档账号 token。

### 4.2 四仓案例的可运行契约

采用 **Node 原生 JavaScript ESM + 原生 HTTP + `node:test`** 的小纵切夹具，四仓各自 git/origin；无 Docker、数据库或 npm 运行时下载。此技术栈是本设计新增建议，不是用户已定事实；用途是把生成变量限制在业务实现，避免引入包安装长尾。成员各有构建/运行说明与 `.claude/rules/language.md` 等必要规则材料，不能照抄矩阵「本仓为 Rust」规则。初始材料是可解析的空业务骨架和契约说明，不预置通知接口实现、成品 UI 或测试答案。

| 层 | 固定交付边界 | 验收输入与输出 |
|---|---|---|
| `busi` | 通知模型 `id/user/title/body/created_at/read`；查询、未读计数、幂等标读；从指定 JSON 种子载入内存 | e2e-user 两条未读、一条已读；another-user 至少一条不可串读；重复标读不再递减 |
| `api` | `GET /notifications?user=`、`GET /notifications/unread-count?user=`、`POST /notifications/{id}/read`，组合 busi | 标读由用户归属约束；响应列表/计数与领域一致；无完整认证框架 |
| `gateway` | `/api/notifications*` 转发；`X-User` 必填、缺失 401，用户上下文不得被 query 覆盖 | 浏览器与 API 同网关 origin；body/状态码透传；不新增重试、限流或遥测 |
| `frontend` | 网关提供的通知中心页面：列表、未读徽标、点击标读 | 页面首屏计数 2，点击目标未读变 1，重复点击仍 1，列表读取态更新 |

基线 seed 只是一份输入数据文件，不在尚不存在的 busi 模块中提前运行 seed.ts。请求上下文明确同一功能、全部四仓必须改业务代码、依赖链及接口边界；story/design 由页面上下文与真实 choice 固定范围，不用脚本在请求里补 UI 没有的 involved 字段。E7 矩阵 API 请求的 pinning 并非当前页面表单能力。

Plan 断言按**覆盖和依赖**而非精确数量：至少四个有效业务 WI，target 覆盖四仓，每仓至少一个；可有集成/E2E WI，但不得让其顶替任一层业务产物。`busi → api → gateway → frontend` 是实现依赖顺序，不称「下游先做」。要求显式跨仓 handoff/input contract 与依赖图；四仓有新业务 diff、真实 completion commit 和远端推送，不能放宽成只 busi/api/frontend 三仓。

S9 从各 bare origin 的交付 branch/SHA 创建独立 validation checkout，不动登记主 checkout，也不修改 Coding worktree。`busi` 是被 API 加载的库，不单独起服务器；API 与 gateway 为真实进程，frontend 是 gateway 提供的静态浏览器资源，三段网络/库调用贯通。所有端口使用系统分配或受管独占配置，启动就绪核对真实响应；任一层未可运行、只有假数据 UI 或 direct API 绕 gateway，终验失败。

以下是**生成案例的待建交付接口合同**，不是 Aria 已存在代码。基线说明固定：`busi/src/index.js` 提供带用户参数的领域 API；`api/src/server.js` 通过 `BUSI_ROOT` 载入该库，消费 `NOTIFICATION_SEED_PATH`，监听 `HOST/PORT`；`gateway/src/server.js` 消费 `API_BASE_URL` 和 `FRONTEND_ROOT`，监听 `HOST/PORT`；`frontend/index.html` 及其静态脚本用同源 `/api/notifications` 请求并显式携带 `X-User: e2e-user`。启动合同分别是 API/gateway checkout 内 `node src/server.js`；端口 0 时须输出实际监听 URL，部署不需 package install。初始骨架可有文件/模块位置，但不预实现成功业务响应。

种子固定 `n1/n2` 属 e2e-user 且 read=false、`n3` 同用户且 read=true、`n4` 属 another-user 且 read=false；所有 id/title/body/created_at 值写在输入 JSON。列表 GET 返回通知对象数组，计数 GET 返回 `{count: number}`，标读 `POST /notifications/{id}/read?user=...` 返回已读通知对象（200），不存在或不属用户返回 404；重复标读仍 200 且计数不再减。gateway 的三条 `/api/notifications*` 路由以 X-User 覆盖向内的 user 参数；缺头 401。浏览器只点击 n1，不对未知随机通知断言。内存持久到 API 进程结束，刷新保持、重启复种；不承诺跨进程持久化，不另扩通知创建后台、完整登录或推送服务。

### 4.3 隔离与看门狗

run-root 分离 `workspace/`、`aggregate-root/{busi,api,gateway,frontend}`、`origins/`、`validation/` 与 `evidence/`；四仓不引用用户真实项目。基线 A 在建仓后记录，用于归档初始化合法影响；**隔离基线 B 在 S2 初始化、运行前置材料完成后且 S4 开始前记录**，据此检查研发阶段越界，避免把 recipe 合法生成的材料误判成 coding 漂移。

保护的是主 checkout 的 HEAD/分支、tracked 文件字节、未跟踪文件集合/字节和文件 mode；mtime 只供诊断，不单独判失败。git linked-worktree 会合法增加共享 object/ref/`.git/worktrees`，不能要求整个 `.git` digest 零变化；worktree 身份、活动目标和允许的 Git 元数据单独核对。产品拥有的 `.aria`/规则输出按阶段记录，不作无限宽忽略。每个阶段边界及周期只读监测，异常立即保存路径级 diff、截图和 PID/WS 末帧，再停止新业务动作；不先 reset/clean 后截图。监测不替代产品强制边界，最终字节零漂移也不等同于证明期间没有尝试越界。

HOME 采用既有最小 trust 登记逻辑：只写本 run 的 Codex authority-root 条目，记录 before/after ownership；不复制整个 HOME、不删除既有用户 trust 或凭据、不全目录恢复。真实初始化与其他 matrix capture/HOME writer 不并行。teardown 只管 supervisor 自己启动且核对 PID/starttime 的子树；失败现场与 origins 先保留，禁止 `pkill codex` 一类全局清理。

### 5.2 断言类别与必须产物

| Coding／交付 | 四仓都有新业务 diff、completion commit、远端 branch SHA；all_pushed 与 issue completed 同时成立 | 任意 waiting_for_human 算完成；只有本地 commit；只三仓产出；issue 状态过时未暴露 | Coding snapshots、diff 摘要、`ls-remote` 只读结果、交付面板 |

artifact 内容断言只核固定契约与范围，不全文快照 AI 文稿。trace 的正式配置为 `trace: "on"`，每阶段保存（包含成功轨迹），截图在业务边界显式落盘，失败另抓现场；不使用不存在的 `trace:screenshot-on` 字符串。配置依据：[Playwright trace 选项](https://github.com/microsoft/playwright/blob/main/docs/src/trace-viewer.md)、[用户可见 locators 与等待](https://github.com/microsoft/playwright/blob/main/docs/src/best-practices-js.md)。UI 自动等待与 provider 运行预算分开：控件/短 GET 30 秒，provider health 300 秒，初始化上界沿 E7 为 7200 秒；Story/Design/Plan/Review 长段参考 5400 秒、单 target Coding 3600 秒。以上是失败关闭上界，**不是实际时长预测**；四 target 总时长另计。长段持续记录当前 phase、最后可见状态/WS 活动和 owned 进程心跳，不以 DOM 文本静止 600 秒自动杀活 provider；也不以提高所有 UI expect timeout 掩盖控件缺失。禁固定 sleep 推进，只有采样/只读有界轮询的间隔可以定时。

## 6. 风险、分诊与恢复预案

| 风险 | 性质与依据 | 固定处置，不允许的替代 |
|---|---|---|
| 多仓 Plan 准备硬阻断 | 已观察代码事实 E11，不是 AI 方差 | G0 要求裁决：另立多仓 SC Plan+页面目标入口的产品前置，或明确接受本轮首报为 BLOCKED；不能去掉 involved、绕 legacy、直接注入已确认 Plan |
| 当前多 target UI／fan-out 延期 | 既有 C7/R1 与 REQ-MTG-03 | 保持 manual per-target 模型；自动化不进测试实现；UI 缺口交前置产品 change，不能用 API 偷起四 attempt |
| 固定 Claude recipe／Codex 凭据失效 | E7 初始化和 trust 前提，现场未验证 | G1 真实健康与认证核验；缺失如实 BLOCKED。不得把 workflow 改成 Claude/pi、copy old capability 或扩大 HOME 写面 |
| provider 沙箱/真实探针不可签发 | 缺 bwrap/user namespace、版本漂移或 resume 证据缺失 | 停止 S4；保存 Unknown/Denied 原工件和原因；不能把旧版本 Confirmed 搬进新 LC |
| AI 文稿编号/格式/范围/handoff 漂移 | Ruling 11 明令系统性消除 | 需求输入与规则先固定；新形态保留 prompt/输出/diagnostic，判明夹具、prompt、编译器或产品问题。依真实反馈修订一次是产品操作，不是盲重跑；同 finding 重现停诊断；必须有针对性修正才能新 run |
| choice 语义无法唯一判定 | E8 单仓偏置不能继承，AI 问题可变 | 保存所有问题/选项；fail-closed，请 controller 判定答案/需求而非脚本调用模型随意猜。答案策略变更有单测并引用失败证据 |
| stale 卡片或局部协议错误 | E12/C4；错误可能是页面缺陷而非慢 | 局部门错误/身份错立即失败；保存请求和页面上下文。不用别的「成功面板」替代 issue.status 验收，不无限刷新 |
| 过程静默或 provider death | 既有矩阵慢生成/死亡传播先例 | 产品 phase+owned 进程/WS 双证据分诊；硬超时保留现场；仅停止 owned 子树，不全局杀 CLI；不设自动重跑循环 |
| mtime/git 元数据误报 | recipe 合法写入、linked worktree 共享 refs/objects | 双基线、字节/模式与合法元数据分类；不能直接对全仓 mtime 零漂移，亦不能忽略所有 .git 或未跟踪输出 |
| 交付代码无法跨仓启动 | 同 issue 跨 target 的依赖/handoff 仍需产品支撑 | 明确传递前序交付 SHA/消费路径；S9 从远端交付快照运行；若 coder 看不到前序合同，不外部帮改实现或手工合并解围 |
| 新阶段 spec 被默认 fake config 命中 | E3 testDir 为整个 e2e | default config 排除 real，real config只匹配 real；执行开关缺失即失败；报告中永久标 real provider 模式 |
| 快照承继把历史绿当本轮绿 | E9 首仓/静止点专用 | 首轮 fresh 全链；恢复只 diagnostic_resume；内容/版本/路径/前端 diff 门拒漂移，不重新给跳过阶段计票 |

失败分类只用 `FAIL`（验收不符）、`BLOCKED`（外部/已知产品能力前置不足）、`not_executed`（依赖未达）、`not_observed`（非必触分支）和 `PASS`。已知 S6 阻断可作为首轮结果交付，但**不是**全流程验收通过。代码/夹具/策略修改后有新 revision 与新 runId；Playwright retries 固定 0，绝不运行「直到绿」的循环。正常产品内的有界自动修复保留其真实计数，不人为扩大预算。

### 7.3 估时口径与可验证性

用户窗口按 **8 小时／工作日，12–20 小时工作窗口**解释。W1–W6 的主动开发估算合计 12–20 小时，属于测试资产本身；真实首轮运行、构建等待与故障定位须另计或在无文件冲突时重叠，不能把该工时合计直接宣称为首报日历工期。G2 目标是首个工作日末到次日可展示；G3 目标为 1.5–2.5 工作日内可见可追溯首报。报告分别记录开发工时、构建等待、provider wall-clock、排障和被阻断时间；超出窗口如实报告，而不是删验收项。

**预算前提：** 已有 Node/pnpm/Rust/浏览器工具可用、构建缓存正常；夹具不下载运行时依赖；真实账号就绪；G0 双审及时；没有本轮发现的新产品缺陷。任何前提不符立即从原预算中单列，不悄悄把测试降级。现有矩阵的 Codex 单仓 resume 历史快值不能外推到四仓全链；初始化上界 2h、实体 1.5h、每 target 1h 的超时之和也不能当 2 天内必通过的估算。

首轮计划必须落 `startedAt/endedAt` 与阶段 duration：构建、初始化、三 action 探针、Story、Design、Plan、四 target Coding/Review、S9 各独立计时；阶段结果随完成原子落盘而不是最后一次写总报告。`pipeline wall-clock` 用真实开始/结束差计算，不将并行时长简单相加。每片超过其估算或首报窗口出现关键产品前置时，报告具体证据/剩余路径，controller 决定产品 change；**不能用「1–2 轮通常会收敛」增加抽卡预算**。

**当前基线的预算裁定：** G2/G3 以用户 1.5–2.5 工作日的首报目标安排，测试侧估时和首轮现场数据共同验证是否满足；G4 在已观察的多仓 SC prepare 阻断下不可达。产品能力前置需要独立需求/设计与估时，本文没有足够实现证据给出可靠总工期；历史 C7 的「仅 UI≈1 天」不包含四仓 SC Plan 准备能力，不能据此加一天便许诺全通过。

## 9. 设计自检与双审交接

- 六必答均闭合：Q1 装配选择，Q2 嵌入同源，Q3 匿名产品入口与真实 CLI 身份分离，Q4 DOM/语义安全定位，Q5 阶段编排与有界恢复，Q6 最小 durable 复用边界。
- Ruling 17：所有业务状态变更由浏览器真实点击/输入完成；Rust 仅装配、真探针前置、只读证据与进程生命周期。整体 MatrixEnvironment.build/API pump 禁用。
- Ruling 11：retries=0；不首项猜答、不 provider fallback、不「直到绿」；修复必须有证据与明确系统性改动。页面反馈是产品合法操作，不是无分析抽卡。
- 完整性：目标仍为单功能四仓全触、四仓交付、通知业务纵切可运行；精确 WI 数未被误当业务需求；已知 S6 阻断和 C7 裁决显式保留，没有暗改成四 issue。
- 文件接地：现有符号/端点均来自 §2 的实际读取；§4.4、W1–W6 的新增路径/ignored 名/台账是明确的设计接口，非伪装现存代码。没有改任何实现文件，v1.1 未覆盖。
- 实际验证：仅代码/契约/草稿静态接地与设计一致性自检；没有运行构建、测试、浏览器或真实 provider，不能宣称任何门已经通过。

**供 k3 接地审查的重点：** Rust supervisor→CLI→静止探针导入的生命周期与身份是否安全；页面 current gate 唯一定位是否充分；四仓能力前置的真实最小边界；origin/validation 不污染主 checkout；S9 是否真走四层。**供一致性裁决的重点：** Ruling 11/17、C7 defer、REQ-MTG-03 人工逐 target 首启红线、当前 REQ-WSC-08 单路径失败关闭。

开放前置只剩三类，不隐藏为「可行」：①四仓 SC Plan＋真实页面 target 入口必须有明确产品裁决和实施证据；②Codex/Claude 账号、沙箱、实际 CLI 版本与构建缓存现场 G1 核验；③四层运行合同建议需随设计一起批准并由首轮工件验证。前两类不足时报告 BLOCKED，不能降低 G4；本文可直接进入双审。

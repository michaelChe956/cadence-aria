## 0. 结论摘要

1. **自动批准的最小改法是「打开引擎已有的 `RunPolicy::AutoIfValid`」(方案 A,推荐)**。引擎里评审 Valid 时 `routing.rs:679-690` 对 `AutoIfValid` 直接 `enter_policy_valid_work_item_plan_compile`,compile 成功后 `compile.rs:689-692` 经 `complete_policy_valid_work_item_plan`(`:736-766`)自动落 Confirmed(`confirmed_by="auto_if_valid"`,`:741-745`);评审判 HumanRequired 时 `policy_routing.rs:80-83` 返回 `StopNeedsHuman`,落 durable `StoppedNeedsHuman`+resumable 快照(`policy_routing.rs:146-150`)。自动化链现在是**刻意禁用**它:`plan_preparation.rs:223-224` 绑定 session 恒 Interactive,`workspace.rs:373-387`(lifecycle_store)绑定创建拒非 Interactive,`automation_enrollment.rs:127-133`(binding)与 `:304-309`(rebind)拒 AutoIfValid,`plan_generation.rs:171-176` 准入对非 Interactive 返回 NeedsHuman。
2. **方案 A 的真实改动面比「放开 3 处拒绝」大**(本次实测新增,半份旧文档未提):除 `plan_preparation.rs`、`automation_enrollment.rs`、`plan_generation.rs` 外,还必须改 ① `lifecycle_store/workspace.rs:368-387` 与 `:393-404`(绑定创建的 Interactive 强制与幂等比对);② `web/plan_confirmed_info.rs:54`(要求 `run_policy==Interactive`,否则 `plan_confirmed_info` 返回 None,而 `autopilot_orchestrator.rs:473-477` 在 None 时判 NeedsHuman——不改则 plan 自动 Confirmed 后自动化链**卡在 advance 之前**);③ `workspace_sc_recovery.rs:73`(失败重驱只收 Interactive);④ 自动批准路径**不经过**确认 trust 按需登记(`ensure_confirmation_trust_ready` 仅 `controls.rs:41`、`conversational_gate.rs:772` 两处调用,`compile.rs` 的自动臂没有),LC 多仓自动批准要补这一步;⑤ openspec 现行 REQ-WIGA-02 明文「绑定 plan session SHALL 保持 Interactive,MUST NOT 用 AutoIfValid」(`openspec/specs/work-item-group-autopilot/spec.md:58-60`),需走 openspec 变更先改规格。
3. **AI 提问不被自动通过是结构性保证,不是外部观察器**:SC 作者 run 的 `AskUserQuestion`/`request_user_input` 经 `ProviderEvent::ChoiceRequest` 进入 `provider_drive/work_item_plan.rs:289-306`,provider 会话在等 `ChoiceResponse`(`:197-213`),run 未结束就不会走到评审路由,更到不了自动批准。`TextFallback` 提问**不会**出现在 Work Item Plan:`parsers/choice.rs:7-9` 把文本兜底检测限定在 Story/Design。编排器 `human_stop_point` 仍用 `pending_choice_frames()` 观察并停(`autopilot_orchestrator.rs:429-438`),通知只依赖这个事实。遗留风险:提问无人答 900 秒后 run 被中止(`provider_drive/watchdog.rs:55-56`,`work_item_plan.rs:106-137`),落 Failed,走 plan 阶段失败继续(见 §6)。
4. **plan 阶段失败继续 = 一个新 REST「继续自动化」(plan 阶段专用,走对话窗口)**,携带用户在对话窗口输入的上下文文本;服务端在 session 文件锁内:追加上下文(复用 `append_context_note` 语义)→ 把 Failed/StoppedNeedsHuman 的 session 重新武装 → 若 generation intent 为 NeedsHuman 则重置为 Claimed → 发唤醒。与 coder 门(批 1 A4 `retry_coding_with_context`,WS gate_response,无 REST)完全分开。
5. **`require_execution_plan_confirm` 不是「无消费点」**(修正旧文档):plan 选项只进 prompt(`plan_preparation.rs:148-153`、`work_item_split_engine/prompts.rs:889,906`),真正的消费点在 coding 启动:`web/coding_ws_handler/context.rs:66-81`,work item 上该标志为真且执行计划未 Confirmed 就报 `ExecutionPlanNotConfirmed`。自动化下「不约束」需同时:enable 时把 plan_options 的该项压成 false(+落库),并核对 work item 级标志(见 §9 A-05)。
6. 通知:不建新模型;向批 1 A1 提需求,见 §11。

## 一、判定口径（先定，后文不再重复论证）

## 六、D｜留痕（「已知风险确认」记录，owner 裁定 2 落点）

- **模型**：`IssueCrossRepoRiskAcknowledgement { id, project_id, issue_id, plan_id, attempt_id, cross_repo_review_id, verdict, findings_summary, acknowledged_at }`。
  - **删除 v1.0 的 `acknowledged_by`（确认人）与 `acknowledged_channel`（确认通道）两个字段** —— 留痕只回答一件事：「**我已知道风险，仍然确认**」。`verdict` = 结论（`approve|request_changes|blocked`）；`findings_summary` = findings 摘要（severity 计数 + 前 N 条 finding 的 `message`，整体截断到固定上限）；`acknowledged_at` = 确认时间（RFC3339）。
  - **保留** `id` / `project_id` / `issue_id` / `plan_id` / `attempt_id`：它们是**结构键**（落盘路径 + 幂等键），不是「确认人 / 通道」信息。
- **落点**（issue 级，新建 store 模块 `coding_attempt_store/issue_cross_repo_review.rs`）：评审本体 `projects/{project_id}/issues/{issue_id}/coding-cross-repo-reviews/review.json`；留痕 `.../coding-cross-repo-reviews/acknowledgements/{id}.json`。（issue 根路径口径同 `src/product/app_paths.rs:37-39` `issue_root`；与 `coding-attempts/` 同级，属 issue 维度。）
- **写入时机**：`handle_final_confirm` 成功落 Completed 之后（`handoffs.rs:21` 函数体内，`handoffs.rs:94` `update_attempt_status` 之后）——若该 issue 存在跨仓评审且 `verdict ∈ {request_changes, blocked}` 且尚无同 `cross_repo_review_id` 的留痕 → 追加一条。
  - 两条确认入口都经过 `handle_final_confirm`：plan 级一键确认（`src/web/handlers/coding/plan_final_confirm.rs:455-`）逐个调用它；socket 单 attempt 确认（`src/web/coding_ws_handler/socket.rs:653-`）直接调用它。**单点写入即覆盖两条路径。** 幂等：同一 `(cross_repo_review_id, attempt_id)` 只写一条。
- **不记通道 → v1.0 §六 中「`acknowledged_by` 取值＝确认通道标识」整段删除**；查询面只剩「是否已留痕」这一布尔事实，**不展示确认人 / 通道**。
- **查询面**：`build_plan_final_confirm` DTO 的 `cross_repo_review_acknowledged`；`coding_attention_info` 的 `cross_repo_review` 条目在留痕后消失。**未确认时的呈现**：verdict=request_changes/blocked 且未留痕 → attention 条目仍在 + plan 确认卡片显示警告文案；verdict=approve → 不投影提醒、不留痕。

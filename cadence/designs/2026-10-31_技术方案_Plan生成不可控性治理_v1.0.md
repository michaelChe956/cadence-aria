## 1. 结论摘要

### 1.1 根定性

**不是「模型不够好」，是责任错配 + 通道错位。**

平台把「可按结构判定、可用精确行编辑修复」的契约判定权写进 prompt 交给模型；而模型唯一的返修通道是**重写整份计划**。于是一次机械错误 = 一次整文档重写 = 一次低成功率、不可复现、成本高昂的赌局。

三条决定性证据：

1. **prompt 里已逐字写了被违反的规则，模型照样违反。**
   `src/product/work_item_split_engine/prompts/sc_author_teaching.rs:41` 原文：
   > 另一分支的 key 不顶替——kind=single_repository 却只写 intent_target_logical_repo → lowering_error「Plan Intent 声明在场时该字段必填。」拒绝。

   这正是现场第 2 类失败的错误，逐字命中 prompt。**「把规则再写一遍」这条路已经证伪。**

2. **平台已经具备机械修复能力，但对此次两类失败恰好没有接。**
   `src/product/workspace_engine/contract_autorepair.rs:65 converge_work_item_plan_source` 已是生产通道（`single_candidate.rs:446`、`web/.../run/single_candidate.rs:1209` 两个调用点），compile→指令→精确行编辑→重编译，8 轮，零模型（`:54`）。它只覆盖 capability/handoff/未知 key/重复 command。lowering 与环不在内。

3. **两类失败恰好落在两处「平台自己没实现判定」的坑里，于是变成死路。**
   - lowering 诊断 `kind: None`（`work_item_plan_compiler/lower.rs:1123`），typed 分类器没有对应变体 → `classify_failure_set` 落 `Unknown` → `UnknownStop`（`planning_failure.rs:404`、`:414`），零自修零教学（`web/.../run/single_candidate.rs:84-100` 白名单只收 4 个 parse 码）。
   - 环检测在 Final Compile 那条路上**丢失边来源**（`draft_batch/compile_support.rs:783-823` 把 change_order 自动边拍平进 `depends_on` 再 Kahn），因此无法机械判定「哪条边非法」，只能拼一段人话字符串报错。

### 1.2 目标形态

**契约三层下沉**：把「一次写对 ~100 条机械契约」拆成四种处置，模型只负责业务内容：

| 层 | 名称 | 谁做 | 判据 | 模型参与 |
|---|---|---|---|---|
| L0 | 平台确定性自修 | 平台 | 结构化 typed 诊断 + 唯一解 + 不丢业务事实 | 否 |
| L1 | 平台确定性补全 | 平台 | 可从既有结构投影（先例：capability 末行并入） | 否 |
| L2 | 精确缺口（一次说清） | 平台算 → owner 一次答完 | 缺口可枚举，但填补有语义选择 | 只做内容 |
| L3 | 业务取舍 | owner | 涉及 design 仓序/范围归属/条件可用性 | 不参与判定 |

**prompt 从「承载契约」降级为「承载意图与业务上下文」。** 这是本方案的长期收益来源：L0/L1 能覆盖的条款，就该从 prompt 消失，而不是再写一遍。

### 1.3 明天就能见效的最小改动（P0）

**三项都在 compiler / handler 层，不在人工门层。**

## 3. 根因分解

| 根因 | 描述 | 现症 |
|---|---|---|
| R1 责任错配 | 可机械判定的契约以 prompt 约束形式交给模型 | 31K 规格书；写了照样犯（F4-F7 + §1.1 证据 1） |

## 4. 契约分层模型（核心）

### 4.1 判定矩阵：一条规则该去哪一层

对**每一条** prompt 里的机械契约做四问，任一答案为「是」即下沉：

1. **平台能否在不引入新业务事实的前提下判定它对错？** → 否 = 留在模型（业务内容）
2. **判定结论是否唯一解（不需要在多个合法解中选）？** → 否 = L2/L3
3. **修复是否只做删除/改名/去重/追加（不改变已声明业务语义）？** → 是 = L0
4. **修复所需的新增内容能否从既有结构逐字投影（不发明事实）？** → 是 = L1

| 层 | 定义 | 允许的操作 | 禁止的操作 |
|---|---|---|---|
| **L0 自修** | 唯一解、无业务语义损失、可逆可审计 | 删重复项、删未知 key 行、parse 期等价解析（值已在场且唯一映射，**不改 source**） | 删任一依赖边、改 design 的仓序、发明取值、删被消费的能力/契约 |
| **L1 补全** | 内容可从既有结构投影 | 把 provider 已声明的 capability 并入其 Outputs `capabilities`（既有先例）；移除未被消费的 handoff 引用（既有先例） | 造出 provider 没声明的能力；造出「能验证某 AC」的检查 |
| **L2 精确缺口** | 缺口可枚举但填补有语义选择 | 一次列全：缺哪个 WI 的哪条 AC 的哪个 check + 已有 check 清单 + 参照写法 | 替 owner 选题；分多轮挤牙膏式报；自动补出 check/命令 |
| **L3 业务取舍** | 涉及 design/范围/条件可用性 | 一次问完，给 2-3 个可选答案并标注各自后果 | 平台自行决定 design 仓序或范围归属 |

### 4.2 关键边界（防止「平台替模型做决定」）

四条硬红线，写进契约 **`REQ-CRP-01`**（已落 delta，逐条有 scenario）：

1. **L0/L1 只作用于「尚未持久化、未被 reviewer 消费、未被 owner 确认」的 source。** 已持久或已评审的对象只能经原授权 author 产出新 revision——这是与未实施的 `REQ-SG-02A` 对齐的硬约束（见 §6.5）。
2. **L0 不允许「增加业务事实」。** 唯一例外是既有先例的 capability 追加——内容来自 provider 自己的声明，不是平台发明。
3. **任何 L0/L1 自动修复必须产出可审计记录**（repair_id + 规则版本 + 前/后内容 + 依据的诊断），并随 source revision 落盘；owner 必须能看到「平台替我改了什么」。
4. **`canonical Inputs` 边永远不可自动删。** 它代表真实数据流；与 `change_order` 反向时只能交 author 重组或升级 L3（改 design），平台不得静默抹掉，**更不得以删边让编译通过**。

## 5. 三类失败的归位

### 5.1 A 类：可机械判 → 平台自己修（L0）

**判据必须结构化，不认 message 措辞。** 这是 `REQ-SG-05` 已经付过学费的教训（`web/.../run/single_candidate.rs:96-100`：按 message 含「缺少/缺失」授资格属字符串旁路，已废）。

| 缺口语义 | 结构化判据 | L0 动作 | 判据落点 |
|---|---|---|---|
| 分支 key 错配 | `IntentTargetBranchMismatch{declared_kind, present_keys, sibling_value}` | **等价宽容解析**（不改 source）：兄弟 key 的值能唯一映射到本分支目标 → 直接在 parse 层解析出目标并产审计事件；不唯一 → 不猜，升 L2 | `lower.rs:443-480` + `lower.rs:262` |

### 5.2 B 类：可机械校验但需补内容 → 分两种，不混

| 缺口 | 归属 | 理由 |
|---|---|---|
| `required_capability_missing` | **L1 自动补** | 内容来自 provider 已声明的 capabilities，逐字并入末条（既有先例，`contract_autorepair.rs:416 capability_instruction`） |
| `unconsumed_required_handoff` | **L1 自动删** | 未消费引用无业务价值（既有先例，`:458 handoff_instruction`） |
| `acceptance_criterion_without_reviewer_check` / `unknown_reviewer_check_ref` | **L2 精确缺口，不自动补** | 「哪个 check 真能验证哪条 AC」是语义判断；平台自动补会制造**假验证证据**，违反不造假原则。平台只做：列出缺 check 的 AC 全集 + 该 WI 已有 check 清单 + 已有合法配对样例。判据：`src/product/work_item_contract/validation.rs:287-310` |
| `required_contract_missing` / `unknown_provider_logical_work_item` | **L2**（provider 存在但没声明契约 → 需 author 补契约内容） | 补契约要写 capabilities/compatibility_policy，是内容 |
| `overlapping_exclusive_and_forbidden_scope` | **L3**（哪一侧让步是范围取舍） | 不能替 owner 决定 |
| `empty_required_write_scope` / `missing_required_verification_command` | **L3**（需要真实仓库事实） | 平台不得臆造命令 |

**为什么 AC↔check 不自动补（这是本方案最需要 owner 认同的一条）**：自动补一条 `reviewer_check_refs` 能让编译变绿，但会让「验收标准被验证」这句话失去意义——后续 coder/reviewer 会把它当成真实证据。**宁可在 L2 停一次，也不产出一条假证据。**

**关于现场 #3「reviewer 连报三轮」——已取证到闸门机理，但现场仍属未回放假设；本轮不改契约。**

平台侧闸门确实存在且有四道收紧（已逐行核实）：

1. **集合相等才触发**：`review/routing.rs:893` 调 `review/routing_scope.rs:815 single_candidate_consecutive_repeated_finding_count`，其判据是 `previous_set == current_set`（`routing_scope.rs:~848`）——要求**相邻两轮的非 advisory 指纹集合完全相等**；第二轮新增或消失任何一条 finding 就不触发。
2. **只比相邻两轮**（`timeline_nodes` 反向取第一个 ReviewerRun）。
3. **指纹有稳定/不稳定两域**：`FindingFingerprint::identity_for_finding(category, class, message, contract_field)`（`work_item_plan_policy/fingerprint.rs:73`）——有 `category`+`contract_field` 时**措辞不敏感**，缺则落 `identity_unstable`（措辞敏感）。
4. **owner 排除 key 措辞敏感**：`ReviewFinding::computed_finding_key()` = hash(`severity` + `message`)（`web/workspace_ws_types/review.rs:157-159`），16 位 hex（`models/human_gate.rs` `is_valid_finding_key`）；换措辞=新 key。排除命中后由 `review/disposition_override.rs:50-62 force_owner_excluded_findings_advisory` **平台侧强制 advisory**，不依赖模型是否听话。

→ **现场「三轮同一问题」最可能的成因**：(1) 集合相等被轻微差异绕过（每轮多/少一条无关 finding 即失效），其次为 (4) 换措辞导致排除失效。**但无真实 verdict 回放，仍是假设**，已登记为 tasks 待验证项，不写进契约。

- 若回放证实是 (1)：需要的是「重复判定应基于交集/子集而非集合全等」这一条新要求（**本轮不做**）。
- 若证实是 (4)：需要的是「owner 排除 key 用 typed 结构指纹而非 severity+message」（**本轮不做**）。

### 5.3 C 类：真需要人判断 → 一次答完（L2/L3）

现有基础设施已经够，缺的是**填值**：

- `ReviewFinding.owner_question` / `owner_options`（`src/web/workspace_ws_types/...`，前端 `gate-next-step.tsx:225` 已渲染「带人话裁决（owner_question + ≥2 选项）」）。
- 但编译失败 verdict 现在硬写 `None`（`compile_failure_surface.rs:143-144`）。

**设计**：L2/L3 缺口一律经同一个「一次答完包」呈现：

```
[平台已自动修复]  3 项（可展开：改了什么、依据哪条诊断）
[需要你决定]      1 项：WI-004 的 design 仓序与依赖方向冲突
                  问题：gateway 必须在 frontend 之前（design change_order），
                        但 plan 声明 gateway 依赖 frontend 的产出。
                  选项 A：改 design 的 change_order（gateway 后置）—— 影响：…
                  选项 B：把 frontend 的产出拆成独立 WI 提前 —— 影响：…
                  选项 C：坚持现 design，我手工调整 plan —— 影响：…
[仍需 author 补内容] 2 项：WI-002 的 AC-003 缺 reviewer check（已有 CHECK-001/002 可供参照）
```

落地要点：
- **同一事实只问一次**：复用 `REQ-WSC-13/16` 的 durable「已处置事实清单」做**去重提问**，但**不要指望它能存 owner 的具体选择**——已核实 `HumanFindingDispositionKind` 当前只有 `Excluded` 一个变体（`models/human_gate.rs:141-145`），trait 是 `#[serde(deny_unknown_fields)]`、key 必须 16 位小写 hex（`is_valid_finding_key`）。
  - 因此 `REQ-CG-09` 只承诺「**已回答事实不再重复提问**」，MUST NOT 写成「已有决策表」。
  - 若将来需要记住「owner 选了选项 A 还是 B」，必须新增 `Decided{option_id}` 变体（serde 加 `default` 兼容旧记录），属独立工作项，不在本轮。
  - 去重用的 key 应当用**typed 事实的结构指纹**（不用 severity+message，否则换措辞即失效——见 §5.2 第 4 点）。
- 问句与选项由**typed 事实**生成，不由模型自由发挥（模型经常把「需要 owner 决定」写成祈使句）。

## 6. 图模型漂移：先证伪，再修（P1）

**已知事实**（F10，已复核）：
- Stage1 结构门用 typed 有效图：边 = `canonical_input` + `change_order` 自动边（`compile_support.rs:435-628`）；`declared_depends_on` **只进** `declared_dependency_facts`，**不建边**（`:594-615`）。
- Final Compile 的 `depends_on` **由 `input_contracts` 推出**（`compile_support.rs:1015-1037`），再叠加 change_order 自动边（`:783-826`），然后 Kahn 判环并拼字符串（`:822`）。
- 因此**现场 #1 的环是 canonical Inputs 数据流边与 change_order 反向**，不是「声明依赖反向」。**删它属于假删边**（`REQ-SG-02A`「禁止假删边」）。

**可疑漂移点（未证实，须用 fixture 证伪）**：
- Stage1 ④ 用 `item.logical_target` 对齐 `LogicalRepositoryId` 型 `change_order`；Final Compile 的 `by_target` 用 `item.target_repository_id`。
- Stage1 在成员表缺失时把 `logical_target` 置 `None`（`plan_projection.rs:1053-1058`）→ 该分支下 **change_order 自动边全部消失**，环不可能在 Stage1 被发现，只能到 Final Compile 才炸。
- 另：`project_effective_planning_graph` 与 `PlanningStructureReport` 仍带 `#[allow(dead_code)]` 与「尚未接线」注释（`compile_support.rs:395`、`:425`），但实际已被 `plan_projection.rs:1039` 调用 —— 注释已失真，说明接线状态本身缺乏可信记录。

**方案：先做奇偶性测试，不先改边模型。**

1. **P1-a 建立 fixture**：把现场 #1 的候选形态（多仓、gateway 依赖 frontend 产出、change_order 为 gateway→frontend）固化成测试 fixture（**脱敏、不含业务名**），落 `workspace_engine/tests/` 面。
2. **P1-b 奇偶性断言**：同一 fixture 分别经 Stage1 typed 图与 Final Compile 图，断言「有效边集合」「成环结论」「witness 首跳」三者一致。**不一致即是缺陷单**，附两侧 edges 差异。
3. **P1-c 修法取决于 P1-b 结果**：
   - 若差异来自「Stage1 在成员表缺失/目标解析分叉时丢 change_order 边」→ 修目标解析同源（而不是加边来源）。
   - 若差异来自「Final Compile 无法表达边来源」→ 只把 typed witness 透传到失败面（`prepare_initial_plan_compile` 传 `PlanningCompileFailureKind::Structure`），**边模型不动**。
   - 任何情况下**不引入「平台删边消环」**（违反 `REQ-SG-02A`）。
4. **P1-d 文档一致性**：清掉失真的「尚未接线」注释与 `#[allow(dead_code)]`，让接线状态可读 —— 否则下一个人会再次基于错误的注释做决策。

**收益**：①同一环更早被发现（Stage1 而非 approve 后）；②环带来源与 witness，owner 看到的是「哪一跳逆了仓序」而非散文；③「两套图是否等价」从此有测试保护，不会再次漂移。

## 6.5 与 `REQ-SG-02A` 的关系（必须显式裁决，不假装一致）

`openspec/changes/fix-error-experience-structural-governance/specs/workspace-structural-governance/spec.md` 的 `REQ-SG-02A`（该 change 尚未实施，0/36）规定：**所有新内容修复**（含「原范围内 autorepair 补 capability/删 key/handoff/ref」）**必须**经原授权 author 真实调用，**MUST NOT** 系统直 patch 已持久或已评审的 Markdown/IR；仅「交付前前言修剪、固定中文 heading→英文、EARS 空白规范化」可保留。

这条与现有 `contract_autorepair`（`contract_autorepair.rs:65`，直 patch）**正面撞线**。本方案的立场：

1. **本 change 不新增任何直 patch。** 现有 `contract_autorepair` 的四类修复原样保留（它们发生在**持久化之前**，且从未被 reviewer 消费、从未被 owner 确认），但**不扩大**其收编面。
2. **新增修复一律走「确定性判定 → 结构化指令 → 原 author 执行」**，即平台负责「唯一解判定」，author 负责「内容落笔」。这既满足 SG-02A 的作者来源，也满足 owner 的「可控」诉求（判据在平台，不在模型自由发挥）。
3. **P0-a 的宽容解析不触线**：它不改 source、不改 IR，只在 parse 期做等价归一化（与 `normalize_delivery_before_compile` 同族）。
4. **登记遗留裁决**（需 owner 拍板，本方案不擅自决定）：
   - 选项 A：修订 `REQ-SG-02A`，把「持久化前的纯等价规范化 + typed 判据 + 可审计」明确列为合法例外 → 保留现有 autorepair 的全部能力，成本最低。
   - 选项 B：把 `contract_autorepair` 整体迁成「指令 → author」→ 完全符合 SG-02A，但每次修复多一轮 provider，且现有证据表明弱模型不逐字应用补丁行（`contract_autorepair.rs:4-8` 模块头原话：「模型返修重写整份计划而不逐字应用补丁行，同族缺口跨指纹轮转」），收敛率会下降。
   - **建议 A**（理由：B 已知会让弱模型重写整篇，正是「不可控」的来源；A 只需一句例外条款即可闭合）。

## 8. 落地方案（顺序、代价、收益、验收）

> 顺序原则：**先把「死路」变「活路」，再把「活路」变「不用走的路」，最后才动 prompt。** 反过来做（先瘦身 prompt）会在平台还没接住之前放大风险。

### P0 止血（≈1.8 人日，可并行三个小包）

见 §1.3 的 P0-a / P0-b / P0-c。

- **验收**：
  - P0-a：`kind=single_repository` + `intent_target_logical_repo=<member physical>` → 编译通过且产 `equivalence_canonicalization` 审计；`intent_target_logical_repo=<不在成员表>` → typed 报错且**不猜**；`kind=logical_codebase` 缺 codebase id → typed 报错（负向）。
  - P0-b：`LoweringFault` 在场且事实齐 → 恰一次结构化重驱；无 fault → 维持终态；**同一 candidate 的总重驱次数恒 ≤1**（既有单槽不变，加断言）。
  - P0-c：审计事件可查、可在门卡展开。

### P1 图奇偶性（先证伪，≈1.5 人日）

见 §6 的 P1-a..P1-d。**先写测试，再决定改什么。**

- **验收**：同一 fixture 在 Stage1 与 Final Compile 的「有效边集合 / 成环结论 / witness 首跳」三者一致；不一致的用例先登记为缺陷单（xfail 或 ignored 标注），修完转绿。
- **不做**：不引入平台删边消环（`REQ-SG-02A`「禁止假删边」）。

### P2 环的结构化教学重驱（≈2 人日）

- **改动**：`DependencyCycle` 的 typed witness（含 `sources`）**透传到失败面**——`prepare_initial_plan_compile`（`compile.rs:183`）不再把环包成 `operational("final_compile_prepare_failed", cause)`（`compile/single_candidate.rs:770`），而是 `PlanningCompileFailureKind::Structure(PlanningFailureSet)`；生产判环一律走 typed witness（`cycle_diagnostic` 的人话段保留为呈现层，但**不再是判据**）。
- **教学内容**：重驱 prompt 携带「哪一跳逆了 `change_order` 的哪两个位次」+「必须保留全部 Inputs/AC」+「不得改仓序」三条保护项。
- **代价**：~2 人日（`compile_support.rs` 已 2309 行、large_file_guard 上限 2310 → **必须拆文件**，先例 `cycle_diagnostic.rs`）。
- **收益**：第 1 类失败从「散文 + 3 次盲重写」变成「精确逆序跳 + 1 次定向重写」；同一结构指纹重复时可直接升级 L3。
- **验收**：环失败时 durable detail 携带 witness（逐跳 from/to/sources）；同环重复停的判定改用结构指纹而**不是文案**（既有 `REQ-WSC-22` 已要求，回归确认）。

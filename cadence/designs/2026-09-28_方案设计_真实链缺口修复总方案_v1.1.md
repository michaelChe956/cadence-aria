## 1. Purpose：用户裁决与范围

**单仓（Single-Repository）手动正常路径已经验证可用。** 本迭代不重新实现这条链，也不把单仓手动成功当作自动化完成。准确目标是：

1. 打开真实**单仓（Single-Repository）**与逻辑代码库两种模式的自动化入口：解决 GAP-I 所示 enrollment 422，贯通目标投影、明确授权、自动准备、自动 advance 和自动首启。
2. 修复自动化新增代码的真实缺陷：enrollment 身份、编排器、人工门、网关准入及其交互路径。
3. 把“出错后靠人在场绕”的恢复路径产品化：业务运行不承重于页面连接；需要人裁决时可靠停等，人在驾驶舱操作后无需直写或常驻 driver 才能继续。**无人值守不等于无人批准。**
4. 将发现 #17／#18／#19 的三个直写旁路变成有权限、有身份、有审计、有真实效果的产品能力。

术语约束：本文的产品术语统一使用“单仓（Single-Repository）”与“逻辑代码库（Logical Codebase）”；源码现有枚举 `RepositoryRouting::Legacy` 仅作为代码标识引用，不把单仓称为 legacy／旧模式。是否将该枚举重命名为 `SingleRepository` 在 C5 评估，结论见 §5.5。

### 1.1 范围约束

- story／design、choice／危险命令、计划 approve／feedback／abandon、需要人的故障裁决及 FinalConfirm 仍由人完成；不引入自动批准。
- 自动化适用于**单仓（Single-Repository）与逻辑代码库两种模式**，但每次只允许一个精确授权的目标：一个物理仓，或逻辑代码库选择中的一个 logical repository。逻辑代码库可以含多个成员，但本次 issue／plan 的自动 target 必须唯一；不增加多 target 自动 fan-out。
- `advance` 只到 Ready；provider 首启仍经过现有 typed StartCoding 单入口。恢复命令不得被伪装成第二次自动首启。

- 旧草案中“原 12 项登记遗留”等未列入本次输入的其他台账不是本方案的隐含排除依据。本方案所列每项必须关账；若真实验收又发现同链产品缺陷，纳入修复循环，不以新的遗留条目换取关闸。

## 3. 总体设计：五类身份和一个真实恢复合同

### 3.1 拟新增身份合同

| 身份 | 负责问题 | 不变量 |
|---|---|---|
| enrollment `generation` | #12／#14、两种自动化模式 | **独立 durable 身份**，不是 `policy_revision` 的别名；同代 prepare／binding／generation action 幂等；新代有独立 intent、plan／session 与 action key。`policy_revision` 只负责授权 CAS。 |
| runner `run_incarnation` | #3／#4／#5／#8／#11 | 活执行拥有 durable owner；registry 只是本进程协调；旧 token、旧回执、旧 retired 事实不得影响显式认领的新 incarnation。 |
| worktree `lease_epoch`／`fence_token` | #11／#16 | 租约绑定 attempt＋owner＋incarnation＋epoch；释放／takeover 后旧 fence 不能写，未知活性不自动抢占。 |
| unit `execution_no` | #13、验证／合同修订后的重执行 | 每次新执行记录实际启动 HEAD；重连／同 run 恢复不增号；真正 restart 或 amendment 重执行增号，旧轮区间不改。 |
| role `context_revision` | #18／#19 | 每版冻结 verification ref、instruction／note IDs、role、renderer、hash 与实际 prompt 输入；同版恢复复用冻结输入，异版合法演进，不改旧 hash。 |

`AutoStartOnce`（或同义首启许可）必须携带并校验 `generation`；同一 attempt 的不同代不能互相消费首启许可，旧代许可不得在 supersede 后启动 provider。（来源：oracle-O5）

这五类身份作用域不同，不合成一个“万能 revision”。从 enrollment 到 attempt、unit run、role run、门与命令记录必须可追溯；无法证明身份或外部副作用时可靠停在可操作的恢复态。

### 3.2 恢复动作共同语义

拟新增／扩展动作均携带 `command_id`、对象 ID、expected version／generation／gate ID、理由及作用域；同键同负载返回同一结果，同键异负载或旧身份 409，非法状态 422。REST 与 WS 调同一应用服务，驾驶舱／Coding Workspace 显示同一 durable 结果。

业务完成和观察投递分离：先持久候选、门快照、动作认领、执行上下文或检查点，再发布观察事件；observer 满、无 socket、attachment 换代不反转业务事实。可重复的本地确定性动作可按 journal 续做；provider 是否已启动不明时不盲目再次启动。拟新增状态名是合同草案，实施时应融入现有 enum／journal，不叠加第二套状态机。

## 5. 五个 change 的实施合同

本节是change切分和方案，不是逐步实施计划。change ID均为**拟新增**；用户批准后由OpenSpec提案／delta明确契约，再写实施计划。

### 5.1 C1：`enrollment-lifecycle-and-rebinding`

**Why：** 一个enrollment只能活一次，失败换代又连锁撞子会话、advance和门。必须先定义授权代际与精确绑定，避免C5在旧恒等逻辑上扩目标。

**范围：** #1／#6业务门、#9／#10／#12／#14／#16，以及供 C5 使用的 carrier-neutral 目标身份合同；定义单仓与逻辑代码库两种模式都可消费的 generation／target 联合。不复制 C2 的 coding runner 生命周期。

**关键设计决策：**

- **A1 generation＋显式 supersede（M1）。** 拟新增 enrollment generation 及历史记录、generation 级 prepare／generation intents。generation 是独立 durable 身份，不能由 `policy_revision` 代替；`policy_revision` 仅作授权 CAS。Enable／Disable 同代开关不改 source／options／target、不清 claim；变更这些身份必须显式新代。`supersede` 请求含 expected policy_revision／generation、明确 source／options／target 及模式：
  - `regenerate`：新 prepare intent 派生新 plan／session；新代动作键不与旧代相同。
  - `adopt_explicit`：冻结人明确指定的 plan／session，不再用固定 auto ID 验证它；必须同 issue、Interactive、精确 source／target／provider 合同、已出版 revision 可互证。不能按“最新 plan”接管，不能把已有 Manual 已认领 attempt 升级成自动许可，不能让 Completed 旧 plan 隐式再执行。
  - 旧代仍有活 run 或外部启动未结算时先提供明确阻塞及 C2 的停止／裁决入口，不能偷偷 Abort 或并发启动新链。代际切换撤销旧代未认领许可；已认领事实保留。此规则不同于 Disable，后者仍不取消已运行动作。
  - 旧合法数据迁移为 generation 1，保留原 ID／claim／intent。已被直写为不一致的历史数据不得自动“修好”：诊断原 intent 与当前绑定，允许人经核验的 supersede 重开或明确 adopt，不能要求再编辑 JSON。切换后所有消费者只用新合同，取消旧单文件／固定 ID 假设，不留两套 bind 写路径。
  - **锁协议（M2）：** enrollment/generation CAS 只持有短事务锁；intent 按 generation 分区；callback、provider、WS、事件发布和外部 await 均不得持 enrollment 锁。固定锁序为“对象版本读取 → generation intent CAS → 绑定／动作 journal CAS → 锁外副作用”；锁内不得回调会重新获取 enrollment 锁的服务。旧 generation callback 只能写其代次 journal，不能删除或覆盖新代状态。
  - **跨代 child 不清 binding（M3）：** 新 generation／plan revision 必须创建新的 child 身份；旧 child binding 只读保留，禁止清空、重绑或以“最新同名”覆盖。跨代重复 compile 只能精确复用同 generation／plan／revision 的 child。
- **A2 role-chain 准入。** 扩展已有 gateway 静态谓词，role 集合由实际 launch 路径确定；GET target 和 PUT Enable 共享判定，attempt 准入防御复核。逻辑代码库 author 在 plan 能直连不代表同 author 作为 coder 合法；单仓不要求逻辑代码库 gateway。动态账号故障仍走已修 GAP-H。
- **A3 完整门与恢复门。** 候选批准／feedback 必须绑定 source revision、mechanical／review 证据、剩余人工返修预算及 snapshot。无这些的 relay 失败只能是运行恢复门：恢复失败节点，或从权威候选重建完整门；不可赋予裸 approve。候选门创建与 snapshot durable 化同一事务／可重放 journal。observer 投递状态不参与业务合法性。
- **A4 计划路径意图。** 推荐在既有 plan grammar／IR 及 canonical 合同新增结构化路径意图（拟字段：`path_intents`，项为 repository-relative path、existing／create、提供者 WI），而非从自然语言猜创建。existing 须在基线或经显式依赖供给；create 须在创建者 exclusive_scope 内、非 forbidden 且依赖可达。同步 parser／lower／source 教学／机械 finding／projection；旧无意图计划保持已有引用验证，需修订者走合法 feedback，不自动扩大写权限。
- **A5 advance 显式 retry（M4）。** `retry-initialization` 不是把 JSON status 重置为 Initializing，而是真实状态机：`Failed → RetryingInitialization → checkpointed phase → Ready`，任一 phase 失败仍落回带原因的 `Failed`；每个 transition 写不可变 retry journal，原失败事实不改，新命令带 expected record／journal／plan revision／attempt／target／generation 及安全 checkpoint。相同 command 幂等复用原 retry 结果，版本／身份漂移 CAS 拒绝且无写副作用；恢复复用原 attempt，不新发 provider、不重新物化已完成 prefix。

**拟API能力：** enrollment supersede、完整SC门恢复／重建、advance retry-initialization；沿现有enrollment、SC恢复、advance路由组织，不以新命令ID绕幂等。已有binding端点收敛到明确generation binding语义，不保留能直写却不被编排器认可的第二入口。

### 5.4 C4：`logical-codebase-bootstrap-hardening`

**Why：** 冷启动需人工铺底才能入链，自动化入口成立但载体根本未准备好；必须修路径权威和首建依赖，而非给每个现场追加文件。

- **范围：** GAP-A／B／C／D，及 B6 政策解析所用的逻辑代码库权威路由；不把单仓自动化塞进逻辑代码库 bootstrap，不放宽逻辑代码库 gateway。

- **D1 唯一权威路径（M10）。** 在现有 `RepositoryRouting`／逻辑代码库 stores 建立共用 layout resolver，输入为明确逻辑代码库 ID 或单仓物理 `RepositoryRecord.id`，各自输出唯一**对应模式**的 authority；逻辑代码库的创建、预检、读取和 operation 产物统一 LC 子树，单仓维持其合法物理仓布局，不能让单仓伪造 LC 子树或 logical ID。原项目级历史 LC 布局仅经显式迁移核验到 LC 权威；两个位置冲突可见 fail-closed，无“先读到谁算谁”的长期 fallback。C2 B6、C5 E1 不得各自猜路径。

### 6.3 横贯所有场景的审计判据

- **零直写：** 测试执行者不得编辑 `repos.json`、LC selection／manifest／policy／capability／index权威、identity journal、enrollment／intent、child binding、advance record、worktree lock、unit_run／execution hash、rework consumed或context note来脱困。正常产品命令依法持久这些文件不算“直写”；失败注入只制造指定故障，不得顺便修状态。
- **不靠脚本托运行：** 观察脚本可以只读采证；driver点火后可关，不能要求setsid＋ping或双kick／服务重启清内存来维持正确性。服务重启仅作受控故障注入，恢复本身须符合durable事实。
- **通知真实：** plan confirmed必须有成功compile／publication及Confirmed session；coding执行完成通知只在WaitingForHuman＋FinalConfirm＋完整readiness，发生前为0，等待期一次且不增待处理数。人确认后才Completed；key／时间／TTL／K窗口补读／刷新去重不因新代重置历史事实，当前代不能借旧代信息冒报成功。
- **单发及权限：** 每个generation／action、attempt首启、role run／context version的认领和provider实际启动逐项对账；同命令竞争仅一赢家。外部副作用未知不宣称exactly-once，转可操作恢复。多target／错仓／旧source／旧run／observer写入均fail-closed。
- **真实闭环：** 每格留存project／issue／generation／plan／revision／attempt IDs、部署版本、REST或UI回执、timeline／journal／claim／context摘要、真实provider输出、commit区间与实跑验证记录、人工FinalConfirm回执、终态。UI入口通过实际驾驶舱／Coding Workspace点击和可见结果验收，不只调用隐藏API。
- **未通过就是未关闸：** 替身、单仓手动、单段provider成功或“交付已入树但仍blocked”不能替代四格终态；环境不可用如实记阻断并完成可达工作，真实格未通过不得勾完成。

## 1. 结论与范围（全角色统一，owner 终裁）

| 层 | 行为 |
|---|---|
| **Author/Orchestrator/Splitter/Handoff** | 四家统一 HostLocal 直跑、无 bwrap/no-new-privs；仅保留角色策略差异与平台流程门，不沿用 Kimi Terminal 恒拒或 `policy.rs` 的整段规划拒绝分支 |
| **Coding Coder** | 四家统一显式 `HostCoding`：宿主同用户直跑，支持构建/测试/容器 CHECK；Coder 可编辑代码并由窗口/提交卫生管理交付 |
| **Coding Reviewer** | 四家统一显式 `ReviewerVerify`：能力全开，B 档快照恢复、通道锁、对账作废；详见 v3.1-B，不以 deny 工具实现 reviewer 只读 |

「工具全开」只描述 Aria 不额外撤销 provider 工具；Author 的「不配编辑代码文件工具」是**独立的岗位工具策略**，不由 OS 沙箱、bwrap、HOME、环境变量或 Codex LC sandbox 档实现。所有执行 profile 由受信 factory/gateway 装配并冻结，prompt、ACP 消息、自报 role 和环境变量不得构造或升级 profile。

全角色统一意味着本期 bwrap 执行路径、规划角色旧隔离路径和 Kimi 规划专用拒绝路径均退役；`sandbox.rs` 仅可保留与执行隔离无关的 openat/O_NOFOLLOW 等路径安全工具及二期容器接缝。

Codex 的 Direct 与 LC 两条传输面均以 `danger-full-access` 为 sandbox 目标态（= owner 诉求 1「四家全角色应用层全开」的推论，契约层记录，待 owner 知情确认）；approval 维度与 Author 岗位工具策略独立。REQ-LCG-04 通过 OpenSpec 变更提案修订；Direct 与 LC 各自维护冻结 digest，不复用旧 read-only deny 片段。

## 2. 关键事实(物理证据)
普通 Coder 本就无通用禁写策略(prompts.rs:651-680; streaming_provider:517-556 带策略反而拒绝); 四家主进程均普通宿主 spawn; kimi Auto 强制 bwrap(terminal_handlers:72-118)且限制不止 bwrap(固定 PATH/HOME=worktree 根/GIT_CONFIG_GLOBAL=/dev/null/120s/仅 bash -c); 同步旁路 CliProviderAdapter 不走 ProcessManager; **宿主 Git 会执行仓库 hooks(git_command 只设 LC_ALL, 无 core.hooksPath 覆盖)**; CHECK 无结构化 executor 字段; A' 仓库落点=verification-triage/command evidence(verification_surface.rs:257-358, 重跑唤回 Coder runner 非平台 runner)。

## 3. 统一执行 profile 与权威装配矩阵
`ProviderExecutionProfile{HostCoding, ReviewerVerify}` + `ProviderRunResourceScope` 由受信装配层冻结。覆盖 Author/Orchestrator/Splitter/Handoff/Coder/Reviewer 的 Direct、LC、同步旁路、Kimi host terminal、MCP/ACP 全入口；不由全局 `ProcessManager::spawn` 猜测 profile。非 Coding 角色不是「原样保留旧沙箱」，而是按权威装配矩阵进入 HostLocal；Author 岗位限制另行验证。
***

|---|---|---|---|---|---|

| Orchestrator | `HostCoding`（规划用途） | `HostLocal-Planning` | `role_run(orchestrator)`；先登记后回收 | 否 | 规划编排工具按既有岗位策略；不得因旧 Kimi deny 分支而拒绝终端 |

### 3.1 规划角色旧拒绝分支和 Author 独立入口

- Author 不经过 Coding 工厂的成员 checkout 路径；`author_root_launch.inc.rs:159-177` 的 `resolve_author_root_launch` 及其 `PlanningReadOnly` gateway 校验必须显式装配 `HostCoding + AuthorToolPolicy`。`AdapterRole` 的 Author 映射必须记录是否经 Orchestrator 承载；无论是否经该角色转发，最终 audit role 必须为 Author，不能因承载角色重新注入 Reviewer/Orchestrator deny。没有这条独立接线时，不得以「四家 Coder 已挂 HostCoding」宣称 Author 已覆盖。
- Author 的禁止编辑代码文件是 capability/tool surface 的可验证合同：启动审计记录 `role=Author`、`tool_policy_digest`、禁止的内建工具集合和实际 tool advertisement；负向验收要求 edit/write code-file 工具不存在，正向验收要求 terminal/read/report/document 通道可用。它不依赖 bwrap、路径白名单、HOME 重定向或 Codex sandbox 枚举。
- `codex_provider/mod.rs:701` 的 `validate_tool_policy_for_role` 守卫必须从「Orchestrator/WorkItemSplitter/Reviewer 必带 deny」改为仅 Author 注入岗位策略；Coder/Reviewer 全开，profile 漂移或不合法 role 仍 fail-closed。
***

### 3.2 Codex 全开与岗位限制解耦

- **LC 路径**：所有相位（Planning/Coding/Review）投影 `danger-full-access`；`REQ-LCG-04` 以变更提案修订，删除/反转 `lc_danger_refusal`，并让 LC profile digest 使用独立的 capability 序列，不复用 Direct 的 `deny_file_write_builtins_tokens`。
- **Direct 路径**：Direct 策略档机制保留，但冻结参数重构为 `sandbox=danger-full-access`、`approvalPolicy=on-request`；审批解析、未知形态熔断和双路径审计保留。Author 岗位限制是**检测型**而非 danger 下的预防型：事件流检得 `fileChange` 项后中断 turn、fail-closed 并写 durable 审计（复用已导入的 `parse_file_change_summary`）；危险命令走 `Accept` 与 Claude/Pi 对齐，不使用 `never`，避免 Author 危险命令被 Codex 自禁而产生跨 provider 不对称。Coder/Reviewer 不注入 Direct 策略，使用 danger-full-access 及其原生 approval。
- **冻结片段拆分**：`deny_file_write_builtins_tokens` 旧的 read-only 片段不得继续作为共同 canonical。Direct 侧改为「`danger-full-access` + `approvalPolicy=on-request` + Author 检测型岗位限制」新冻结片段；LC 侧维护独立 projection/digest。`streaming_provider:1327-1350`、`prompts.rs:650-653`、`gateway_sync_provider.rs:151-155` 的角色映射必须使 Author 才注入策略，Reviewer/Coder 映射全开。
***
上述 Author 机制不声称 danger 下能预防 provider 写入；这是对账/事件检测合同，符合 owner 风险接受中「审计是检测而非物理防写」。**[INFERENCE]** Codex CLI 0.155.1 中 danger-full-access 对应 `PermissionProfile::Disabled`、`apply_patch` 可能恒 `AutoApprove`，需目标机真机探针核实，不将该推断写成已验证事实。
***

四家一致性=共同下限：Coder 均无 Aria deny 片段、共享白名单环境、保留进程组回收与原生权限差异；Reviewer 另受 B 档窗口和对账约束。环境策略不承诺凭据不可达，owner HOME 仅为能力兼容。
***

## 4. Kimi 实施点

四家所有角色共用 HostLocal 单路径。Kimi 的 `client_services`、`terminal_handlers`、`terminal`、`session` 必须消费受信冻结 profile；不再探测或启动 bwrap、no-new-privs、netns、解释器白名单或固定 `GIT_CONFIG_GLOBAL`。ACP `command+args[]` 与 legacy shell 形态均按 Host profile 执行，保留进程组回收、输出预算、幂等回收、ETXTBSY 重试和资源登记；不得偷换 permission_mode 为 Supervised 复用。

Kimi 规划角色不再沿用旧 terminal 恒拒，`policy.rs` 的角色拒绝分支改为 action/目标/authority 校验后 HostLocal 执行；Author 是否可编辑代码文件仅由 `AuthorToolPolicy` 决定。`sandbox.rs` 只保留 openat/O_NOFOLLOW 等路径安全工具和二期容器接缝，不保留本期 provider 执行沙箱。

预算不能只改某一个固定秒数：规划、Coding、Review 均以受信 invocation 总 deadline 为上限；`VerificationCommand.timeout_seconds` 只作预算声明，超总预算须启动前暴露为配置问题。真实活动 terminal CHECK 期间必须上报活动状态，不能被 resume stall 检测误判；无活动且无进展的 stall 检测保留。
***

## 5. OpenSpec 变更(delta 语义, 实施用 MODIFIED 不悄悄删)
 - MODIFIED 终端 OS 级隔离(auto)：所有角色在 HostLocal 当前用户直接执行，无 bwrap/netns/no-new-privs；Auto/Supervised 只管审批，不得代替 profile；记录 profile+部署上下文，**不得记为「已隔离」**。验收覆盖无 bwrap 正常、构建容器命令不被阻止、Author 岗位限制不被 sandbox 替代。
 - MODIFIED 终端策略与 grammar：Host profile 接受普通 argv+legacy shell 形式，无只读解释器限制；子进程使用白名单环境+显式注入。Author 的代码编辑工具限制由 `AuthorToolPolicy` 另行校验；Coder/Reviewer 不因该岗位规则失去工具。
 - MODIFIED 权限与路径沙箱：fs 服务保留 API 层目标校验，但不宣称约束 Host terminal 宿主可达；`PlanningReadOnly` 的空 writable roots 是策略合同，不是 OS 沙箱。
 - 终端生命周期：所有角色区分 invocation 总 deadline、活动 terminal 状态、并发/输出/截断/回收；禁止以旧规划 120s 或 Provider 旧固定 timeout 作为全角色合同。
***

## 6. 应用层保留护栏
- **API 鉴权(无条件公共前置)**: 复用 v3 共同设计不建第二套; 现状无入站鉴权中间件(app.rs:631 直接装配 state); 该工作包单 owner 与 v3 一次实施; 残余边界: 非同 UID 恶意 coder 的物理边界
- **.git/.aria 选型留痕**: 窗口式权限预置(不推荐, 备查——同 UID 可恢复 chmod, .git 禁写阻断合法提交)/审计+对账(**推荐**——发现不阻止)/不做(不推荐)。coder 合法 .git 提交保留; .aria 异常变化告警对账
- **宿主 Git 加固(本次必做)**: git_command 统一 `-c core.hooksPath=/dev/null -c core.fsmonitor=false`, 阻断「coder 写 .git/hooks→平台 Git 在 owner 上下文自动执行」桥; 文档明示平台交付不执行仓库 hooks
- **产物清理(扩展到 coder, 不复制 reviewer 整树回滚)**: 共享 ProviderRunResourceScope 最小归属(run_id/boot identity/PID start identity/运行目录/登记容器/cleanup cursor); coder 窗口 kind=code_delivery, Preparing→Running→Quiescing→Reconciled→Closed; 统一规则(先登记后执行/先 quiesce 再清/启动补偿/PID 复用防护/三入口全登记); **不调 reviewer baseline restore; 保留源码/提交/dirty/共享缓存/用户容器; 只清 run-owned 临时产物; 禁按目录名无差别删/git clean/整树 reset**; 未登记 detached 进程不保证回收

## 7. CHECK 与 A' 变化
主路径=coder 自己执行 CHECK（构建/测试/依赖/容器）；executor 标注定义为「环境能力声明」（JVM/Node/网络/容器）而非路由指令；标注不改变受信 profile 或 AuthorToolPolicy，也不承担防写。A'（verification-triage）保留为外部硬件/人工检查/临时缺项补充；缺依赖/认证失败/权限失败/断言失败分类清楚，不都归「沙箱失败」；重跑仍唤回 Coder runner。
***

## 8. 二期 dev-sandbox 最小接缝
deployment_context 仅进 profile 冻结快照(默认 HostLocal), 不扩公开 API/DTO/178 处字面构造。本期记录: profile 版本/deployment context/resource scope/环境策略版本/原生权限画像引用。二期由部署 launcher 实现新 context, **provider+本地 MCP+ACP terminal/fs 一起进容器**(不能只容 CLI 而 kimi host terminal 回宿主)。本期不实现调度器/镜像/挂载 DSL/静默回退(未知 context 显式拒绝)。

## 11. 风险与假设失效条件（如实写明）
1. 全角色 HostLocal 为 owner 已接受的同 UID 风险，白名单环境不是安全隔离，也不防读取 owner 凭据或外部副作用；审计结论以平台记录未被篡改为前提。
2. 平台 API 鉴权、Origin/Host 校验是无条件前置；审计对账不是物理防写；恢复成功不等于报告可采信。
3. 任何二期容器化必须 provider、本地 MCP、ACP terminal/fs 一起进入容器；二期启动时间由 owner 决定，不因本方案自动触发。
4. 验收机工具链、容器引擎和登录态是前置条件；缺项必须列为未验证，不得声称 CHECK 已通过。

## 1. 背景与目标

图片创作功能当前只能调用一个端点、一个写死的模型（`gpt-image-2`），每次生成互相独立。本次落地三项需求：

| 编号 | 需求 | 可验证行为 |
|---|---|---|
| R1 | 多模型可选 | 参数面板出现模型下拉；清单来自设置（用户可增删），内置 8 个 gpt id + 1 个 MiniMax id 为推荐默认值；所选 id 原样出现在出站请求的 `model` 字段 |
| R2 | 连续修改携带上一张生成图 | 会话内已有生成结果且开关打开时，本次请求走 `/v1/images/edits` 并以上一张生成图作为 `image[]` |
| R3 | 模型手动选择 | 模型下拉只列**已配置且可用**的供应方的 model id，由用户逐次选择；所选 id 原样进入出站请求的 `model` 字段；每条结果记录并展示「哪家 + 哪个模型」 |

### 非目标

- 不新增 `quality` 的 `xhigh`/`max`、不新增 `gif`/`svg` 输出格式、不新增 `complexity`/`n`/`stream`/`mask`/`markup`。现有枚举取值均是两家官方取值的子集，保持不变。
- 不新增更大的 `size` 档位。现有 `1024x1024`/`1536x1024`/`1024x1536`/`auto` 保持不变。
- 不展示 MiniMax 的 `revised_prompt`、`data[].size`。
- 不支持多张参考图（保留「仅支持单张参考图」）。
- 不支持「异步任务 + URL」形态的端点（用户硬约束：三方 GPT endpoint 与 OpenAI 官方一致）。

### 2.2 用户硬约束（逐条落到设计）

| 硬约束 | 落点 |
|---|---|
| 三方 GPT endpoint 与 OpenAI 官方 API 一致 | GPT 侧只发官方 Images API 字段与取值；multipart 图字段 `image[]`（D10） |
| 不为 `-2k`/`-4k` 发明请求字段 | 模型 id 是不透明字符串，仅作为 `model` 值透传；GPT 侧无任何分辨率映射字段（D2、D14） |
| 响应按各家官方形态解析 | GPT 读 `data[].b64_json`；MiniMax 显式请求 `response_format=b64_json` 并逐项检查 `data[].error`（D11） |
| MiniMax 只用官方对接方式 | 只发 `H3ImageGenerationReq` / `H3ImageEditReq` 字段集的子集；不发 `quality`/`background`/`input_fidelity`（D10） |
| `input_fidelity` 对 GPT 2.x 省略 | 全链路移除该参数（D11） |
| 不做网关身份推断、无网关特例 | 代码中不存在对 base_url 主机名或模型 id 字符串的任何分支（D2） |
| 8 + 1 个 id 必须在可选清单里 | 内置为推荐默认值，用户可改（D1） |

### 2.3 既有惯例（保持不变）

出站仅 https 或 loopback、禁重定向；图片生成请求不自动重试；600s 超时；同一会话单并发；先写图后写会话引用；key 不进执行器子进程；后端 `mockito` 内嵌单测、前端 vitest。错误信息沿用现有形态：变体前缀为英文（如 `invalid parameter: `），本次新增的说明文字用中文（与现有「仅支持单张参考图」一致）。

## 4. 关键决策

### D1 模型清单 = 每家一份用户可配置的 id 列表

**决策**：模型清单不做枚举。`.aria/image_create.json` 中每家只存一份 `models: Vec<String>`（model id 清单），没有其他按家的模型字段。代码内置默认值：

- GPT 家 `models`：`gpt-image-2.6-flare`、`gpt-image-2.6`、`gpt-image-2.6-flare-2k`、`gpt-image-2.6-flare-4k`、`gpt-image-2.6-sunburst`、`gpt-image-2.6-sunburst-2k`、`gpt-image-2.6-sunburst-4k`、`gpt-image-2.5`（`gpt-image-2.6-flare` 打头，其余 7 个保持用户给出的顺序）
- MiniMax 家 `models`：`MiniMax-H3-Image`

保存时校验（任一不满足则整体拒绝、不落盘，错误为 `InvalidConfig`）：

1. 每个 id 去除首尾空白后长度 1–128，字符集限 `A-Z a-z 0-9 . _ : / -`
2. 同一家内不重复；两家之间不重复
3. 每家至多 256 个；允许为空（空清单 = 该家不可用）

生成请求的 `model` 不再有保留值，清单 id 也不再有保留字限制。

生成时校验：请求的 `model` 必须**逐字符等于**某个已配置且可用的家的清单中的某一项，否则报错、不出站（完整规则见 D15 与 5.1「目标解析语义」）。

**上限由 32 调整为 256（Task 19，2026-11-12 主控裁决）**：清单的候选项现在可由连通性探测从网关 `/v1/models` 拉取（5.11），是机器生成的；32 是手工逐行录入时代的额度，覆盖不了大网关的模型总量。256 既能覆盖，又把配置文件与界面的规模钉在有界内。「两家之间不重复」保留不变：它是 `vendor_of` 判定模型归属的唯一依据（D2）。

**理由**：调研结论表明 8 个 gpt id 中 6 个不是 OpenAI 官方模型，是否可用完全取决于用户 endpoint。硬编码枚举会把「endpoint 支持什么」这个只有用户知道的事实写死在代码里。内置 GPT 清单以 `gpt-image-2.6-flare` 打头，是因为模型下拉的初始选中项优先取该家内置推荐清单的首个 id（5.9「状态」的三级规则第 1 级）：`gpt-image-2.6-flare` 是清单中经官方目录核实存在的 id，在官方与三方 endpoint 上都成立；若以裸 `gpt-image-2.6`（非 OpenAI 官方 id）打头，用户第一次点生成就可能失败。

**备选与否决**：

- 硬编码 `enum ImageModel`：否决。新增/下线模型要发版，且对 6 个非官方 id 做了无依据的背书。
- 生成链路在运行时自动调 `/v1/models` 拉清单并直接当作清单使用：否决。增加一条出站路径；返回大量无关模型；MiniMax 侧无对应约定。（Task 19 起，设置弹窗里由用户显式触发的「测试连通」会带回网关模型列表并用它更新**草稿**清单；用户可在复选下拉框里增删，点「保存」后才落盘。生成链路仍不调 `/v1/models`，见 5.9、5.11。）
- 自由文本输入框（不设清单）：否决。无法在出站前拦截拼写错误，每次拼错都是一次可能计费的失败请求。

### D2 模型 id 是不透明字符串，家只由清单归属决定

**决策**：新增 `ImageVendor { Gpt, Minimax }`。一个模型 id 属于哪一家，**唯一依据是它被配置在哪一家的清单里**。代码不对模型 id 做前缀/后缀匹配、不做正则、不做 `match`；也不对 base_url 的主机名做任何判断。请求字段集、响应解析差异只以 `ImageVendor` 为键。

命名说明：前端已有 `IMAGE_CREATE_PROVIDER_OPTIONS` / `ImageCreateProvider`（对话执行器的 provider），后端会话上也有 `provider_name`。为避免同一功能域内 `provider` 一词两义，图片供应方统一命名 `vendor`（Rust 类型、JSON 键、TS 类型一致）。

**理由**：满足「不做网关身份推断」「不为 `-2k`/`-4k` 发明字段」两条硬约束的最简结构——推断逻辑根本不存在，就不可能推断错。

**边界说明（Task 19）**：有两处会看 id 是否含 `image`（忽略大小写）：参数面板的「初始选中项」规则（5.9「状态」）第 2 级，以及连通性探测第 2 步探测模型 id 的选取（5.11）。前者只决定下拉的**默认选中项**——对用户可见、可随时改选；后者只决定探测请求（不含 `prompt`、不出图）里用哪个 id。两者都不改变清单内容与顺序，不参与供应方归属判定，也不影响任何生成请求的字段——因此不属于本决策禁止的「推断家 / 推断端点身份」。生成链路对模型 id 仍然只做比较与透传。

**备选与否决**：

- 按 id 前缀（`gpt-` / `MiniMax-`）推断家：否决。用户自定义 id 命名不受控，且属于被明令禁止的推断。
- 请求同时携带 `vendor` + `model`：否决。两家清单互不重复（D1 规则 2）时 `model` 已唯一确定家，多一个字段只多一种不一致的可能。

### D3 双家独立凭据；旧配置文件读时兼容、写时迁移

**决策**：`ImageCreateSettings` 由 `{ base_url, api_key, defaults }` 改为 `{ vendors: { gpt, minimax }, defaults }`，每家一个 `VendorSettings { base_url, api_key, models }`。

文件兼容规则（反序列化经中间结构 `ImageCreateSettingsWire`，见 5.1）：

| 文件形态 | 读入结果 |
|---|---|
| 文件不存在 | 两家凭据为空、清单为内置默认值 |
| 旧形态 `{ base_url, api_key, defaults }`（无 `vendors` 键） | 顶层 `base_url`/`api_key` 归入 `vendors.gpt`；`vendors.minimax` 凭据为空；两家清单为内置默认值；`defaults` 原样保留 |
| 新形态但某家缺失，或某家缺 `models` | 缺失项补该家内置默认清单 |
| 新形态且某家 `models: []` | 保持为空（用户主动清空），不被默认值覆盖 |
| 同时存在 `vendors` 与顶层 `base_url`/`api_key` | 以 `vendors` 为准，顶层忽略 |

读取不改写文件；下一次保存设置时整份以新形态写回（不再写顶层 `base_url`/`api_key`）。

**理由**：两家是不同的服务商，域名、密钥、计费账户都独立。旧文件里的那组凭据此前只用于调 GPT 模型，归入 GPT 家语义无损。`load()` 对解析失败的处理是 `unwrap_or_default()`，所以**新结构必须能成功解析旧文件**，否则升级后用户的 key 会无声消失——这是必测不变量（S-01）。

**行为变化（写入 `CHANGELOG.md`）**：旧版本写死使用 `gpt-image-2`；升级后内置 GPT 清单不含该 id，模型下拉的初始选中项为 `gpt-image-2.6-flare`。需要继续用 `gpt-image-2` 的用户在设置的 GPT 模型清单里加一行该 id，保存后在模型下拉里选它即可。

**不支持降级**：新形态文件被旧版本读取时取不到凭据，需重新录入。不为此双写顶层字段（避免 key 在文件中出现两份、避免长期保留兼容分支）。

**备选与否决**：

- 一组凭据服务两家：否决，理由同上；用户若确有同一 endpoint 承载两家，把两家的 base_url 与 key 填成相同即可，无需代码支持。
- 拆成两个文件：否决。`defaults` 是共享的；两处原子写与两处脱敏只增加出错面。
- 加 `version` 字段：否决。「有无 `vendors` 键」已足以判别，版本号是无人消费的状态。

### D4 设置更新与脱敏按家独立

**决策**：

- 读取（脱敏）：`MaskedSettings { vendors: { gpt, minimax }, defaults }`，每家 `MaskedVendorSettings { base_url, api_key_masked, models, recommended_models, available }`。`mask_api_key()` 规则不变，逐家应用。`recommended_models` 由后端给出内置默认清单，供前端「恢复推荐清单」使用（前端不维护第二份 id 常量）。`available = base_url 非空 ∧ api_key 非空 ∧ models 非空`。
- 更新：请求体 `{ vendors?: { gpt?, minimax? }, defaults? }`。某家整体缺省 = 该家全部保留。每家 `{ base_url?, api_key_action, api_key?, models? }`，`api_key_action` 仍是 `retain`/`replace`/`clear` 三态，缺省为 `retain`；`replace` 的取值语义沿用现状。
- `base_url` 允许为空串（表示该家未配置）；非空时必须通过 `validate_base_url`。
- 旧的顶层请求字段 `base_url`/`api_key_action`/`api_key` 一并移除（前后端同一变更内切换，不保留双形态）。
- 校验从「只校验本次提交的 base_url」改为「合并后对整份设置校验」：handler 流程变为 `from_request` → `apply_update` → `validate_settings` → `save`。`SettingsStoreApi::validate_base_url` 由 `validate_settings(&self, settings: &ImageCreateSettings)` 取代。

**理由**：「保留/替换/清除」是针对「一把 key」的语义，两把 key 就应有两个独立的三态；用户只改 MiniMax 的 key 时，GPT 的 key 不应被触碰。模型清单的跨家去重只能在合并后的整体上判定，所以校验点后移到合并之后。

**备选与否决**：一次请求必须提交两家全量：否决。脱敏后前端拿不到明文 key，全量提交必然要带「保留」语义，等价于现方案但更易误清。

### D5（已废止）自动轮转

**按用户 2026-11-12 要求撤回自动轮转**（用户原话：「你就让用户在已配置并可用的provider里选model id就行，轮转不需要」）。轮转机制（自动选家、每家轮转模型、结果里的选择方式）整条删除，改为用户在参数面板手动选择 model id，现行规则见 D15。原先的「失败不消耗轮次」「只配一家恒用那家」「显式选择不被轮转覆盖」等语义随轮转一并失效，不再是契约。

### D6（已废止）某家不可用时自动改用另一家

随 D5 一并废止：不再存在「首选家」，也不再存在「首选家不可用时改用另一家」。现行规则是所选模型不可用即报错、不出站、绝不静默换家（D15）；请求发出后失败不回退、不重试的边界保留（D12.3）。

### D7 携带上一张图在 engine 层完成；上传的参考图优先

**决策**：生成请求新增字段 `use_previous`（`true`/`false`，缺省 `false`）。前端开关「基于上一张图继续修改」默认打开。engine 在 `run_generation` 内按如下优先级确定本次 reference：

1. 请求带了用户上传的参考图 → 用上传图，来源记 `uploaded`。`use_previous` 被忽略。
2. 否则 `use_previous = true` 且会话 `generation_results` 非空 → 取末项，读出图片字节作 reference，来源记 `previous`。
3. 否则无 reference，来源记 `none`，走 `/v1/images/generations`。

末项取图由 `image_files.rs` 新增的 `read_result_image()` 完成，规则与图片读取端点现有逻辑一致：有 `image_id` 且文件可读 → 文件字节；否则有内联 `b64` 且可解码 → 解码字节；否则不可用。`get_session_image` 改为调用该函数并删除 `decode_legacy`，「读一条生成结果的图片字节」只保留一处实现。取到的字节以记录中的 `media_type` 作为 `declared_mime`，与上传图走同一个 `validate_reference_image`。

「末项」取自 `run_generation` 内重新读取的会话记录，时点在 `generate()` 的 `flush_pending()` 之后，保证此前写图成功但引用待补的结果已进入序列。

**理由**：

- 放在 engine：上一张图是会话状态，engine 是唯一同时持有会话记录、图片文件路径与生成生命周期的层。handler 只做协议解析；客户端只做 HTTP。前端不参与传图——让前端把刚下载的图再上传一遍既浪费，又与「上传参考图不持久化」的对象混淆。
- 上传优先且不叠加：保留既有「仅支持单张参考图」约束。两张图同时发送时哪张是「底图」对两家都没有官方定义的优先级。
- 后端缺省 `false`：不带该字段的调用方行为与今天完全一致；「默认携带」是产品层默认值，由前端开关承载，用户可关闭以开始一张无关的新图。

**备选与否决**：

- 前端把上一张图当参考图回传：否决，见上。
- 上传图与上一张图一起作为 `image[]` 两项发送：否决，见上；且改变单张约束会波及校验、请求体上限与既有 spec。
- 后端缺省 `true`：否决。隐式把 generations 变成 edits 改变了既有 API 的默认语义。

### D8 上一张图不可用时：明确失败，不出站

**决策**：D7 第 2 步中，若 `read_result_image()` 返回不可用，或内容校验不通过，本次生成**直接失败**，不发任何出站请求，错误为新增变体 `PreviousImageUnavailable(原因)`：「上一张图片不可用，无法基于它继续修改（<原因>）；请关闭「基于上一张图继续修改」或上传参考图」。原因取「图片文件缺失或无法读取」或校验错误的文本。

**理由**：用户此刻的意图是「修改那张图」。静默退化成文生图会得到一张无关的新图并为此付费，而错误原因被掩盖。失败在出站前发生，零费用，且给出两条可操作的出路。

**备选与否决**：

- 静默降级为文生图：否决，见上。
- 向前回溯到更早一张可用的图：否决。「上一张」被悄悄换成「上上张」，结果与用户看到的画面对不上。
- 为上一张图放宽 10 MiB / 4096 的校验上限：否决。两家对 edits 输入图的上限里只有 MiniMax 有官方数值，放宽等于把未验证的上限当已知。

### D9 既有 spec「参考图不被持久化」的改写

**决策**：把该约束收窄到它本来要保护的对象——**用户上传的参考图**：

- 保留：用户上传的参考图仅在本次请求生命周期内使用，不落盘、不进会话记录。
- 新增澄清：连续修改携带的「上一张图」是会话记录中已持久化的**生成结果图片文件本身**；系统不为携带而另存任何副本；其生命周期随会话记录（会话删除时一并删除），不属于「参考图持久化」。
- 两类参考图适用同一组输入约束（格式、10 MB、4096 像素、静态图）。

推论：用户上传参考图生成后，下一轮携带的是那次的**生成结果**，不是当初上传的参考图。

**理由**：原条款的目的是「用户给的输入图不留存」，而生成结果早已按 `image-create-file-storage` 变更持久化。两者是不同对象，改写后原有隐私边界不变。

### D10 字段过滤集中在一个函数；MiniMax 在 `size=auto` 时发 `area=1K`

**决策**：`image_client.rs` 新增内部函数 `wire_fields(target, req) -> WireFields`，是「按家决定发哪些字段」的**唯一**位置。JSON body 与 multipart form 都从 `WireFields` 构造，不各自判断。完整规则表见 5.4，其中唯一需要论证的一条：

> MiniMax 且用户 `size` 为 `auto` 时：**不发 `size`，发 `area=1K`**。MiniMax 且 `size` 为具体 `WxH` 时：发 `size`，不发 `area`。GPT 恒发 `size`，恒不发 `area`。

**这条规则的理由**（它决定了 R2 的携带链在默认参数下、且用户在两家模型之间切换时能否成立）：

- 前端默认 `size` 是 `auto`（`DEFAULT_IMAGE_PARAMS`），默认打开「基于上一张图继续修改」；用户可随时在模型下拉里改选另一家的模型。
- MiniMax 官方在未指定尺寸时的默认面积档是 `4K`（4096²，约 1677 万像素）。按该档位推算：8 位 RGB 原始数据约 48 MiB，默认输出格式 png 下体积通常远超 10 MiB；非正方形比例下长边还会超过 4096（16:9 时约 5461×3072）。实际出图像素以服务端为准，本条是依据官方默认值的推算，未经真实调用测量。
- 该图会成为下一次生成的「上一张图」，要过 `validate_reference_image`（`MAX_SIDE = 4096`、`MAX_BYTES = 10 MiB`）。按上述推算，MiniMax 出图之后的下一次携带大概率失败；即使个别情况下能通过，结果也取决于图片内容，不可预期。
- `area=1K`（1024²）是唯一能用算术保证携带链成立的官方档位：总像素 1,048,576，在官方允许的 1:3–3:1 比例内长边不超过 1774；8 位 RGBA 原始数据为 4 MiB，PNG 最坏情况也只略高于原始数据，jpeg/webp 更小，均远低于 10 MiB。`2K`（2048²）的 8 位 RGBA 原始数据为 16 MiB，PNG 可能超限。
- `1K` 也与 GPT 侧 `auto` 的常规输出量级（1024–1536）一致，用户在两家模型之间切换时分辨率不跳变。
- `area` 是 MiniMax 官方 `H3ImageGenerationReq` 字段（官方字段表已核实），在用户硬约束列出的 MiniMax 官方字段集内。**证据等级需分侧看**：`H3ImageGenerationReq` 侧已由官方字段表直接确认；`H3ImageEditReq` 侧官方文档只列出 required 字段与 `images`/`mask`/增强规则，**未逐项列出可选字段集**，故「改图端点接受 `area`」是按 MiniMax 官方改图端点与文生图端点同构作出的推定，属 8.2 节待联调确认项 A1，tasks 7.2 已覆盖改图侧的真实调用确认。**该推定不成立时，改动收敛在 `wire_fields()` 一处与 C-02b / C-05 两个用例，但必须回到本决策重新论证，不得在实现中自行调整。**
- 它只发往 MiniMax，与「不得为 GPT 的 `-2k`/`-4k` 发明字段」无关：GPT 请求中永远没有 `area`。
- 不发 `size` 而只发 `area`，是因为官方规定 `size=WxH` 时不得同时传 `area`；两者从不同时出现，无论该互斥规则的边界细节如何都不会触发。

**单点函数的理由**：generations（JSON）与 edits（multipart）两条构造路径若各自 `if vendor == …`，迟早有一条漏改。单点函数让「MiniMax 请求里没有 `quality`」成为一个可以直接断言的性质。

**备选与否决**：

- MiniMax `size=auto` 原样透传：否决，MiniMax 出图之后的下一次携带能否成功取决于出图体积，不可预期（见上）。
- MiniMax `size=auto` 时改发 `size=1024x1024`：否决。丢掉了 `auto` 的本意（由模型按 prompt 决定比例）。
- 每家一个 `ImageClientApi` 实现：否决。两家端点路径、鉴权、multipart 图字段完全同构，差异只有几个字段，拆成两个实现会复制整条 HTTP 与错误处理路径。

### D12 出站安全与计费边界

**决策**：

1. base_url 校验两处生效：保存设置时 `validate_settings` 对每家非空的 `base_url` 校验，不合法整体拒绝；出站前客户端对本次目标家的 `base_url` 再校验（防手改文件）。
2. **不做 URL 兜底下载**。响应项只有 `url` 没有 `b64_json` 时报 `MissingB64`。
3. 一次生成请求 = 至多一次出站 HTTP 调用。无重试、无换家回退（D15）。
4. 600s 超时、30s 连接超时、禁重定向沿用现有同一个 `reqwest::Client`，两家共用。
5. **key 隔离**：`ImageCallTarget` 只携带本次目标家的一把 key，客户端拿不到另一家的 key，因此 GPT 的 key 不可能发往 MiniMax 的 base_url，反之亦然。
6. key 不进执行器子进程：新结构仍只由 `settings_store.load()` 在 engine 的生成路径与设置 handler 内读取，不写入环境变量、不进入对话执行器的任何入参。
7. 日志与错误不含 key：`sanitize_error_body()` 以本次目标家的 key 做替换（HTTP 错误体与逐项错误文本都过它）；`VendorSettings` 与 `ImageCallTarget` 手写 `Debug`，`api_key` 输出为 `<redacted>`。
8. **连通性探测是生成链路之外的独立出站动作**（5.11）：与生成共用 `validate_base_url`、禁重定向与 key 脱敏，但不发送可出图的请求。第 3 条的「至多一次出站」只约束生成请求，探测不计入，也不改变它。
9. **已保存的 key 只发往已保存的 `base_url`**（Task 22）：探测请求未提供 key 时，后端只在请求的 `base_url` 与该家已保存的 `base_url` 一致时才改用已保存的 key，否则拒绝且不出站（5.11）。这是 spec「API Key 安全边界与出站目标约束」中「`api_key` 仅随发往该供应方自身 `base_url` 的请求发送」在探测链路上的落实，不是新增约束。

**不做 URL 下载的理由**：URL 的主机由上游响应决定，不在用户配置的 base_url 约束内，跟随它等于让上游指定本机去访问任意地址（内网、元数据服务）；而两家官方都能直接返回 b64（GPT 恒返回，MiniMax 显式请求即可），URL 下载没有必要性。

### D13 可观测性：结果记录「哪家 + 哪个模型」

**决策**：`GenerationResult` 新增 3 个可选字段，全部 `#[serde(default, skip_serializing_if = "Option::is_none")]`（与现有 `image_id`/`b64` 的属性写法一致）：

| 字段 | 取值 | 含义 |
|---|---|---|
| `vendor` | `gpt` / `minimax` | 实际出站的家 |
| `model` | 字符串 | 实际出站的 `model` 值 |
| `reference_source` | `none` / `uploaded` / `previous` | 本次 reference 的来源 |

`GenerationResultDto` 及其 `From<GenerationResult>` 同步带出这 3 个可选字段。生成接口的成功响应在 `image_id`、`media_type` 之外返回这 3 个字段。

`DefaultParams` **不变**（不加 `model`）。它同时是「设置里的默认参数」与「结果里的参数快照」，而模型选择不是持久化的默认参数（下拉初始选中项由可用供应方的清单推导，见 5.9），且已由 `GenerationResult.model` 单独记录。`GenerationResult.params` 的语义定义为「用户本次请求的参数」；对 MiniMax 结果，其中的 `quality`/`background` 未被发送。

旧会话记录：3 个字段缺失 → 反序列化为 `None` → 前端不显示模型标注；内联 `b64` 的旧结果可作为「上一张图」（D7）。

失败可观测：图片客户端返回的错误（即已确定目标之后、与供应方相关的错误），其错误信息与 `generation_error` 事件文本以「[<家> · <模型 id>] 」为前缀，在 `finish_generation` 的错误分支统一添加。

**备选与否决**：把 `model` 放进 `DefaultParams`：否决，理由见上；且持久化的模型会在供应方凭据或清单变化后失效，等于多出一份需要与清单保持一致的状态。

### D14 未验证项收敛：代码不依赖 `-2k`/`-4k` 的语义

**决策**：唯一未知的是「`-2k`/`-4k` 这类 id 在用户 endpoint 上对应什么分辨率档位、是否覆盖请求里的 `size`」。代码通过以下手法做到完全不依赖它：

1. 模型 id 只有两种用途：与清单做逐字符相等比较；原样写入请求的 `model` 字段。除此之外不被读取。
2. GPT 侧 `size` 始终取用户在参数面板选的值，对该家所有模型一视同仁地发送；不因模型 id 调整、不因模型 id 省略。
3. GPT 请求中不存在 `resolution`、`area`、档位映射表等任何自造字段或映射结构。
4. 内置 id 字面量只出现在 `models.rs` 的默认清单常量中；`image_client.rs` 的非测试代码不含任何模型 id 字面量。
5. 用测试固化：同一组参数下，`gpt-image-2.6-flare` 与 `gpt-image-2.6-flare-4k` 的出站请求体除 `model` 值外完全相同（C-03）；`image_client.rs` 非测试源码不含模型 id 字面量（C-15）。

档位语义由 endpoint 负责；endpoint 若不认识某个 id，其错误响应经 `HttpStatus` 脱敏后呈现给用户，用户据此调整清单。

### D15 模型由用户手动选择；不可用即报错，绝不静默换家

**决策**：生成请求的 `model` 字段**必填**，取值是某个已配置且可用的家的清单中的 model id；不存在保留值。

- `model` 缺省，或去首尾空白后为空 → `InvalidParam`「请选择图片生成模型」，不出站（handler 解析 multipart 时拦截）。
- 目标解析 `resolve_target(model)` 按**逐字符相等**在**可用**的家（`is_available()`：base_url 与 api_key 均非空，且清单非空）里找该 id 的归属；找到即返回 `{ vendor, model }`。
- 找不到可用的归属家时：该 id 在某家清单里、但该家缺 base_url 或 api_key → `MissingConfig`「<家> 尚未配置 Base URL 或 API Key」；该 id 不在任何家的清单里 → `InvalidParam`「模型 <id> 不在已配置且可用的供应方清单中」。两种情形都不出站。
- **没有「首选家」，也没有「降级到另一家」**：解析只依赖设置与请求里的 `model`，不读会话历史；所选模型不可用就报错。
- 请求发出后失败（网络、超时、非 2xx、逐项错误）：原样报错，不回退到另一家、不重试（D12.3）。
- 前端：模型下拉只列可用供应方的 model id；初始选中项取自第一个可用供应方的清单，按三级优先规则确定（内置推荐清单的首个 id → 第一个 id 含 `image` 的 → 清单首项，见 5.9「状态」）；没有可用供应方时 `model` 为空串、生成按钮禁用并提示「请先在设置里配置并启用至少一个供应方」；设置变更后所选模型不再可用时，重置为同一规则的结果（5.9）。

**理由**：

- 用户 2026-11-12 明确要求：「你就让用户在已配置并可用的provider里选model id就行，轮转不需要」。
- 静默换家会让用户不知道自己实际用的是谁。两家是不同的服务商、不同的计费账户、不同的字段集（MiniMax 不发 `quality`/`background`），换家后的出图与费用归属都和用户选的不一致。
- 报错发生在出站之前，零费用；错误文本直接指出是哪一家缺配置，或哪个 id 不在清单里，用户可据此修正。
- 解析变成只依赖「设置 + `model`」的纯函数，不再读取会话结果序列，原先「旧记录无 `vendor` 视为 GPT」这类特例随之消失。

**备选与否决**：

- 保留自动轮转作为下拉里的一个选项：否决。用户已明确撤回；保留它就要同时保留每家的轮转模型、结果里的选择方式与「首选家不可用时换另一家」整套规则。
- 所选模型所属的家不可用时，自动改用另一家的首个模型：否决，这就是静默换家。
- `model` 缺省时由后端取第一个可用供应方的首个 id：否决。调用方漏传字段时，后端会在用户不知情的情况下选定计费方；初始选中项由前端的下拉承载，用户看得见。

#### 目标解析语义（`resolve_target`）

实现须与以下规则逐条一致：

1. 按**逐字符相等**，在**已配置凭据**（`has_credentials()`）**且模型清单非空**（即 `is_available()`）的供应方里找该 model id 归属的家。
2. 找不到 → 参数错误「模型 {id} 不在已配置且可用的供应方清单中」。
3. 找到但该家 base_url 或 api_key 为空 → 配置缺失「{家} 尚未配置 Base URL 或 API Key」。
4. 找到且可用 → 返回 `{ vendor, model }`（`ResolvedTarget` 只有这两个字段）。
5. 没有「首选家 / 降级到另一家」：手动选的模型不可用就报错，绝不静默换家。
6. 生成请求的 `model` 必填：缺省或去空白后为空 → 参数错误「请选择图片生成模型」（handler 层，见 5.5）；不再有 `auto` 保留值。

伪规则：

```text
resolve_target(id):
  owner = ImageVendor::ALL 中第一个满足「is_available() 且 models 含 id（逐字符相等）」的家
  owner 存在
      → { vendor: owner, model: id }
  否则 vendors.vendor_of(id) = Some(v)      // id 在 v 的清单里，但 v 缺 base_url 或 api_key
      → MissingConfig("{v.label()} 尚未配置 Base URL 或 API Key")
  否则
      → InvalidParam("模型 {id} 不在已配置且可用的供应方清单中")
```

说明：

- 解析不读会话历史，没有首选家，也没有换家；同一组设置与同一个 `id` 永远得到同一个结果。
- 清单为空的家不可用：即使它持有凭据，也不参与解析，更不会被当作「另一家」顶上。
- `ImageVendor::ALL` 的顺序（GPT、MiniMax）只在同一 id 被手改文件误配进两家时起作用（可用的家优先）；正常保存的设置里跨家不重复（D1 规则 2）。

```rust
    #[serde(skip_serializing_if = "Option::is_none")]
    size: Option<ImageSize>,
    #[serde(skip_serializing_if = "Option::is_none")]
    quality: Option<ImageQuality>,
    #[serde(skip_serializing_if = "Option::is_none")]
    background: Option<ImageBackground>,
    output_format: ImageOutputFormat,
    #[serde(skip_serializing_if = "Option::is_none")]
    response_format: Option<&'a str>,
    #[serde(skip_serializing_if = "Option::is_none")]
    area: Option<&'a str>,
}

#[derive(Deserialize)]
struct ImageResponse {
    #[serde(default)]
    data: Vec<ImageResponseData>,
}

#[derive(Deserialize)]

}
```

不变的部分：`ImageRefImage`、`ImageGenOutcome`、URL 拼接规则（`{base_url 去尾斜杠}/v1/images/{generations|edits}`，有 reference 走 edits）、`media_type()` 由请求的 `output_format` 映射、`reqwest::Client` 构造参数、`wire_value()`、`sanitize_error_body()`、`normalize_reqwest_error()`、本文件的 `validate_base_url()`。

随签名变化的部分：`validate_settings(settings)` 改为 `validate_target(target)`（base_url 或 api_key 为空 → `MissingConfig`，再过 `validate_base_url`）；鉴权 `.bearer_auth(&target.api_key)`；multipart 表单按 `WireFields` 中为 `Some` 的字段逐个 `.text(...)`（枚举经 `wire_value()`），再加 `image[]` 文件部件。

### 5.4 字段过滤规则表（E）

「发」= 一定出现在请求中；「不发」= 一定不出现。generations 为 JSON body，edits 为 multipart，同一家两种端点的字段规则相同（edits 额外带 `image[]`）。

| 字段 | GPT | MiniMax |
|---|---|---|
| `model` | 发（清单中的 id 原样） | 发（清单中的 id 原样） |
| `prompt` | 发 | 发 |
| `output_format` | 发 | 发 |
| `size` | 发（含 `auto`） | 用户选具体 `WxH` 时发；用户选 `auto` 时**不发** |
| `area` | **不发** | 用户选 `auto` 时发，恒为 `1K`；用户选具体 `WxH` 时**不发** |
| `quality` | 发 | **不发** |
| `background` | 发 | **不发** |
| `response_format` | **不发** | 发，恒为 `b64_json` |
| `image[]`（仅 edits） | 发，1 个文件部件 | 发，1 个文件部件 |
| `input_fidelity` | 不发 | 不发 |
| `aspect_ratio` / `disable_prompt_enhanced` | 不发 | 不发 |
| `n` / `stream` / `output_compression` | 不发 | 不发 |
| `complexity` / `moderation` / `mask` / `markup` / `partial_images` / `safety_identifier` 等其余官方可选字段 | 不发 | 不发 |

依据：

- GPT 不发 `response_format`：官方明确 GPT Image 模型不支持该遗留参数，恒返回 b64。
- MiniMax 必须发 `response_format=b64_json`：官方默认是 `url`。
- MiniMax `size` 与 `area` 二选一：见 D10。
- MiniMax 不发 `aspect_ratio`：`size=WxH` 时官方禁止同传；`area` 模式下不传即由模型按 prompt 定比例，与 `auto` 的本意一致。
- `size` 的三个具体取值与 `output_format` 的三个取值对两家均为官方合法值。
- multipart 图字段两家统一用 `image[]`：GPT 官方多图字段名；MiniMax 官方接受 `image` 或 `image[]`。

#### 连通性探测接口（Task 18）

`POST /api/image-create/settings/connectivity`，`Content-Type: application/json`。探测策略与安全边界见 5.11。

请求体：

```json
{ "vendor": "gpt", "base_url": "https://api.openai.com", "api_key": "sk-…", "models": ["gpt-image-2.6-flare"] }
```

| 字段 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `vendor` | 是 | `"gpt"` / `"minimax"` | 缺省或取值非法 → 400 |
| `base_url` | 是 | 主机根路径 | 弹窗里**当前填写的草稿值**，不是已保存值；缺省、为空或未通过 `validate_base_url` → 400 |
| `api_key` | 否 | 文本 | 非空 → 用它探测（草稿值优先，发往哪由用户负责）；缺省或为空 → 后端读取该 `vendor` **已保存**的配置：没有已保存的 key → 400「未配置 API Key，无法测试连通性」；有已保存的 key 且请求的 `base_url` 与已保存的 `base_url` 一致（两侧去首尾空白并去掉末尾的 `/` 后逐字符相等）→ 用已保存的 key；不一致 → 400「Base URL 与已保存配置不同，请填写 API Key 后再测试连通性」（Task 22，理由见 5.11） |
| `models` | 否 | model id 数组 | 该家当前勾选的模型清单（草稿值）；用于比对 `missing_models`，第 2 步的探测模型从中选取（第一个 id 含 `image` 的项，否则首项，见 5.11）；缺省等同空数组 |

响应：**探测已执行则一律 HTTP 200**，结论在 body 里（网关不通、key 无效都是 200 + `ok=false`）；**只有入参非法才 400**，且 400 时未发起任何出站请求。400 的错误体沿用本处理器现有的错误体形态。

```json
{
  "vendor": "gpt",
  "ok": true,
  "message": "连通性正常",
  "steps": [
    { "key": "models", "label": "模型列表 /v1/models", "status": "ok", "detail": "网关返回 12 个模型" },
    { "key": "generations", "label": "图片端点 /v1/images/generations", "status": "ok", "detail": "图片端点连通且鉴权通过（缺少 prompt 属预期，不会计费）" }
  ],
  "missing_models": [],
  "available_models": ["gpt-image-2.6-flare", "gpt-image-2.6", "…"],
  "duration_ms": 123
}
```

| 字段 | 规则 |
|---|---|
| `vendor` | 回显请求的 `vendor` |
| `ok` | 没有任何一步为 `failed` 时为 `true`（`skipped` 不算失败）；`missing_models` 非空**不影响** `ok` |
| `message` | 中文一句话结论；`ok=true` 时为「连通性正常」，否则为「连通性测试未通过，请查看步骤详情」 |
| `steps[]` | 按执行顺序排列，只含**实际执行过**的步骤；`key` 为 `models` 或 `generations`；`models` 步的 `status` 取 `ok`、`skipped`、`failed` 之一，`generations` 步取 `ok`、`failed` 之一 |
| `missing_models` | 第 1 步为 `ok` 时：请求 `models` 中未出现在网关模型列表里的 id（逐字符比较，保持请求中的顺序）；否则为空数组 |
| `available_models` | 第 1 步为 `ok` 时：该步从网关 `/v1/models` 响应解析出的**全部** model id，去重（保留首次出现）、保持网关返回顺序；不按请求的 `models` 过滤，也不区分是否图片模型。第 1 步为 `skipped` 或 `failed` 时为空数组。与 `missing_models` 相互独立，不影响 `ok`（Task 19） |
| `duration_ms` | 整次探测耗时（毫秒） |

`message`、`steps[].detail` 一律中文，且不含 `api_key` 明文。

`available_models` 是 Task 19 在响应上**只增不改**的一个字段：`steps`、`ok`、`message`、`missing_models`、`duration_ms` 的语义与取值一字不变，请求体也不变。用途见 5.11「模型清单以探测结果为来源」。

### 5.6 响应解析与错误归一

HTTP 2xx 时对 `data[]` 的处理（两家同一套规则，天然满足各家官方形态）：

1. 按顺序找第一个 `b64_json` 非空的项 → 成功，取它。
2. 没有成功项时：存在带 `error` 的项 → `ItemError(msg)`。`msg` 取第一个 `error`：是对象且含字符串 `message` 则取之，否则取其紧凑 JSON 文本；再经 `sanitize_error_body()`（脱敏 + 截断 500 字符）。
3. 没有成功项、也没有 `error` 项：`data` 为空或缺失 → `EmptyData`；否则（例如只有 `url`）→ `MissingB64`。

本功能每次只请求 1 张图（不发 `n`），所以规则 1 的「取第一个成功项」不会丢弃多余的成功图。

错误归一总表：

| 情形 | 发生位置 | 错误 | 是否已出站 |
|---|---|---|---|
| prompt 为空 | engine | `InvalidParam`（沿用现状） | 否 |
| `use_previous` 取值非法 | handler | `InvalidParam` | 否 |
| `model` 缺省或为空 | handler | `InvalidParam`「请选择图片生成模型」 | 否 |
| 模型不在任何已配置且可用的家的清单 | `resolve_target` | `InvalidParam` | 否 |
| 模型所属的家缺 base_url 或 api_key | `resolve_target` | `MissingConfig` | 否 |
| 上一张图不可用 | engine | `PreviousImageUnavailable` | 否 |
| 上传的参考图不合规 | handler / engine | `RefImage`（沿用现状） | 否 |
| base_url 不合法 | client | `InvalidConfig`（沿用现状） | 否 |
| 3xx | client | `RedirectBlocked`（沿用现状） | 是 |
| 非 2xx | client | `HttpStatus`（沿用现状：脱敏、截断） | 是 |
| 2xx，逐项错误 | client | `ItemError` | 是 |
| 2xx，无 b64 | client | `MissingB64`（沿用现状） | 是 |
| 2xx，`data` 为空 | client | `EmptyData`（沿用现状） | 是 |
| 2xx，响应体超过读取上限（128 MiB） | client | `OversizedBody`「图片端点响应体超过大小上限（128 MiB）」 | 是 |
| 网络 / 超时 | client | `Network` / `Timeout`（沿用现状） | 是 |

「client」一栏的错误在 `finish_generation` 错误分支被包装为 `ImageCreateError::ImageClient(message)`，`message` 加前缀「[<家> · <模型 id>] 」，同一文本写入 `generation_error` 事件。出站前的错误不写事件（沿用现状）。

两家的非 2xx 错误信封形状不同（OpenAI `{"error":{…}}`，MiniMax `{"type":"error","error":{…}}`），但现有处理是把响应体文本脱敏后整体带出、不解析信封，因此无需改动。

**响应体读取上限**（Task 22 调整）：响应体一律流式读取并设上限——成功响应体 **128 MiB**，超限报 `OversizedBody`；非 2xx 的错误体 8 KiB（其后错误文本仍截断到 500 字符）；探测的 `/v1/models` 响应体 1 MiB。成功体上限原为 64 MiB：内置清单含 `gpt-image-2.6-flare-4k` / `gpt-image-2.6-sunburst-4k`，4096² PNG 的 b64 载荷最坏会逼近该上限，合法响应会被拒，故提到 128 MiB。超限不再定性为「恶意 / 异常端点」——它也可能是超大的合法图片，但仍一律拒绝以避免大内存分配。错误体与模型列表两个上限不变。

### 5.7 调用时序

```text
[前端] ParamsPanel 点击「生成」
  store.generate() 提交 multipart：
    prompt, size, quality, background, output_format, model, use_previous, reference?

[handler] generate_image
  parse_generate_multipart → GenerateCommand
    （model 缺省或为空 → InvalidParam「请选择图片生成模型」；上传图在此做内容校验；单张约束不变）
  engine.generate(session_id, command)

[engine] generate
  active_record() → flush_pending() → run_registry.try_reserve(Generate)
  spawn run_generation(session_id, command, cancel)

[engine] run_generation —— 步骤 1–7 在出站之前
  1. settings = settings_store.load()
  2. prompt 为空 → InvalidParam
  3. record = active_record(session_id)；last = record.generation_results 末项
     - last 只用于步骤 5 取「上一张生成图」（D7）；不再用于推导下一家
  4. target = settings.resolve_target(&command.model)
     - 只依赖设置与请求里的 model：没有首选家、没有换家；不可用即报错（D15）
  5. 确定 reference 与 reference_source（D7）
     - 上传图 > 上一张图（use_previous 且 last 存在）> 无
     - 上一张图取不到 → PreviousImageUnavailable（D8）
  6. reference 存在 → validate_reference_image
     - 上传图失败 → RefImage；上一张图失败 → PreviousImageUnavailable
  7. call_target = ImageCallTarget { vendor, base_url, api_key, model }
     - base_url / api_key 取自 settings.vendors.get(target.vendor)
  8. select! { 取消 → SessionClosing；image_client.generate(&call_target, &request, reference) }

[client] generate —— 至多一次 HTTP 调用
  validate_target → wire_fields → POST {base_url}/v1/images/{generations|edits}
  响应解析（5.6）

[engine] finish_generation
  9. 解码 → 写图片文件 → 追加 GenerationResult { …, vendor, model, reference_source }

[handler] 响应 { image_id, media_type, vendor, model, reference_source }

[前端] store 追加 generation_image 条目（含家 / 模型 / 来源标注）
```

步骤 1–7 全部在出站之前；任何一步失败都不产生费用。步骤 8 至多一次 HTTP 调用。步骤 9 的落盘顺序、`pending_results` 重试机制不变。

**连通性探测不在本时序内**：它是独立于生成链路的出站动作（5.11），由设置弹窗触发，不经过 `run_generation`、不占用会话的生成并发位、不计入「一次生成至多一次出站」，也不写会话记录。

**设置弹窗的模型清单（`ModelListField.tsx` + `ModelMultiSelect.tsx`，Task 19）**

模型清单由多行文本框改为**复选下拉框**，干净切换：弹窗里不再有模型清单 `textarea`，草稿的 `modelsText: string` 改为 `models: string[]`，按行解析文本的辅助函数（`parseModels`）删除。同目录新增两个组件：`ModelMultiSelect`（纯受控的复选下拉框，不读状态层）与 `ModelListField`（弹窗里每家一份的「模型清单」字段：标签行、「恢复推荐清单」按钮、`ModelMultiSelect`、说明文字与刷新后的提示）。视觉语言沿用 `CustomSelect.tsx`（触发器的边框、圆角、内边距、focus ring 一致）；`CustomSelect.tsx` 本身不改。

三个集合，均按家独立：

| 集合 | 含义 | 存放 |
|---|---|---|
| 网关模型列表 | 最近一次探测返回的 `available_models` | 状态层 `modelPools[vendor].gateway` |
| 候选池 | 下拉里可勾选的全部 id | 状态层 `modelPools[vendor].candidates` |
| 勾选集合 | 草稿清单，即要保存的清单 | 弹窗草稿 `models: string[]` |

```ts
export interface ModelMultiSelectProps {
  /** 候选池（网关返回 ∪ 已配置）。 */
  candidates: readonly string[];
  /** 已勾选（= 要保存的清单）。 */
  selected: readonly string[];
  /** 候选里但网关模型列表没有的（打「网关未列出」标）。 */
  notListed?: readonly string[];
  disabled?: boolean;
  onChange: (next: string[]) => void;
}
```

组件交互：

- 收起时触发按钮显示「已选 N 项」；展开后逐项列出候选 id，每项前一个 `checkbox`。勾选 / 取消勾选即 `onChange(新的已选 id 数组)`，数组按候选池顺序排列。
- `notListed` 中的候选项右侧标一个 chip「网关未列出」。弹窗只在该家**已取得非空的网关模型列表**时传入 `notListed`（= 候选池中不在网关模型列表里的项）；未探测或探测未取得列表时不标注——否则全部候选都会被标上，没有信息量。
- 下拉底部是「添加自定义模型」输入框与「添加」按钮：输入的 id 去首尾空白后加进候选池**并勾选**；与已有候选重复时不重复添加（该候选变为勾选）；空输入不生效。自定义 id 的字符集、长度与跨家重复不在前端预检，由保存时的后端校验把关（5.2），错误原样展示。
- 候选池为空时显示占位文案 `暂无模型，点「测试连通」可拉取网关支持的模型，或手动添加`。
- 键盘可达：展开按钮可聚焦；`checkbox` 可用空格勾选；Esc 收起。
- 视觉约束：图标用图标库，不用 emoji；可点击元素 `cursor-pointer`；过渡 150–300ms；hover 不产生位移。
- 字段说明（`ModelListField`）：下拉框下方一句 `默认从「测试连通」拉取的网关模型列表中选择，可取消勾选或添加自定义模型 id。`；跨家跳过与超限截断的提示显示在它下方。

候选池与勾选集合的来源：

- **打开弹窗**（含关闭后重新打开）：候选池 = 该家已保存的清单，全部勾选。状态层里留存的上一次探测结果不重放，不改动草稿清单（Task 22）。
- **「测试连通」返回后**（「模型清单默认从测试连通获取」的落点）：是否更新**只看 `available_models` 是否非空，不看 `ok`**（理由见 5.11）。

  | 情形 | 候选池 | 勾选集合（草稿清单） |
  |---|---|---|
  | `available_models` 为空（模型列表一步 `skipped` / `failed`，或网关返回 0 个模型） | 不变 | 不变 |
  | 非空 | 网关模型按网关返回顺序在前，探测前草稿清单里有而网关没有的追加在后 | **替换为网关返回的模型**（去重、保持网关顺序），减去已被另一家勾选的 id；超过 256 个时只取前 256 个 |

  - **替换语义**（主控 2026-11-12 修正裁决）：探测取得网关模型列表后，草稿清单就是网关返回的模型。探测前草稿清单里有而网关没返回的项（自定义 id、内置推荐清单里网关未列出的项）移出草稿清单，但**留在候选池**里、未勾选、带「网关未列出」标注，重新勾选即可加回。
  - **已知取舍**：取消勾选过的网关模型，再次探测会被重新勾上；自定义添加但网关没返回的 id，再次探测后会被移出清单。因此「测试连通」按钮下有一行说明「成功后会用网关返回的模型列表更新模型清单」。替换只作用于草稿，点「保存」后才生效。
  - **跨家跳过**：网关模型里已被**另一家草稿清单**勾选的 id 不进入本家的候选池与草稿清单，并提示「以下模型已被 <另一家> 使用，已跳过：<id 列表>」。两家指向同一聚合网关时因此不会互相踩，也不会触发保存时的跨家重复校验。
  - **超限截断**：网关模型（去掉跨家跳过项后）多于 256 个 → 草稿清单只取前 256 个，其余留在候选池未勾选，并提示「网关返回 N 个模型，超过单家上限 256，已只保留前 256 个，请自行精简」（N 为计入候选池的网关模型数）。
- **「恢复推荐清单」**：把该家的 `recommended_models` 并入候选池（池中没有的追加在后）并全部勾选；原有的勾选保留。不再是文本覆盖。
- **保存**：更新请求的 `models` = 勾选集合，按候选池顺序排列；是否算「改动过」仍按与已保存清单逐项比较。用户手动勾选超过 256 个时不在前端拦截，由后端以「<家> 模型清单最多 256 个」拒绝。
- **候选池不落盘**：配置文件只保存勾选集合。重新载入设置后候选池回到「已保存的清单」；再点一次「测试连通」会按替换语义重新更新清单与候选池。

| 默认模型 | 写死 `gpt-image-2` | 不再有写死的模型：内置 GPT 清单以 `gpt-image-2.6-flare` 打头（即下拉初始选中项），不含 `gpt-image-2`；`CHANGELOG.md` 写明如何加回 |

无数据迁移脚本；无一次性迁移步骤。

### 5.11 连通性探测（Task 18，2026-11-12 补充）

**要回答的三个问题**：地址通不通；key 有效吗；清单里的模型 id 网关到底列出了哪些。全程不生成图片、不计费。接口契约见 5.5，交互见 5.9。

#### 两步探测策略

两步串行，至多两次出站请求，均带 `Authorization: Bearer <api_key>`，地址由 `{base_url 去尾部 /}` 拼接。

| 步骤（`key`） | 请求 | 响应 | `status` | `detail` | 后续 |
|---|---|---|---|---|---|
| `models` | `GET /v1/models` | 200 | `ok` | 「网关返回 N 个模型」 | 计算 `missing_models` 与 `available_models`，继续第 2 步 |
| | | 401 / 403 | `failed` | 「API Key 无效或无权限」 | **结束**，不发第 2 步 |
| | | 其他状态（404 / 405 / 5xx 等）或网络错误、超时 | `skipped` | 「该网关未提供 /v1/models，改用图片端点验证」 | 继续第 2 步；`missing_models`、`available_models` 均为空 |
| `generations` | `POST /v1/images/generations`，body 只有 `{"model": "<探测模型 id>"}` | 400 | `ok` | 「图片端点连通且鉴权通过（缺少 prompt 属预期，不会计费）」 | 结束 |
| | | 401 / 403 | `failed` | 「API Key 无效或无权限」 | 结束 |
| | | 404，且请求 `models` 非空 | `failed` | 「路径不对：系统会自动拼 /v1/images/generations，请只填到主机根路径（不要带 /v1 或 /v1/images）」 | 结束 |
| | | 404，且请求 `models` 为空 | `failed` | 「无法判定路径是否正确：未指定模型 id（404 也可能是模型不存在）。请确认只填到主机根路径，或先在配置中填写模型 id 后重试」——同时指出「模型 id 未指定」与「路径不对」两种可能，不直接断言路径不对 | 结束 |
| | | 其他状态（含 2xx、3xx、422、429、5xx） | `failed` | 「网关返回 HTTP <状态码>：<响应摘要>」，响应摘要已脱敏并截断 | 结束 |
| | | 网络错误、超时 | `failed` | 「网络错误或超时：无法在 30 秒内完成探测」 | 结束 |

- **模型列表解析**：兼容 `{ "data": [ { "id": … } ] }` 与顶层直接是数组两种形态（数组元素为对象取其 `id`，为字符串取其本身）；比对为逐字符相等（与 D2 的「id 是不透明字符串」一致），不做大小写折叠或前后缀匹配。HTTP 200 但响应体无法解析时按「网关返回 0 个模型」处理，此时清单中的模型全部列入 `missing_models`（不影响 `ok`），`available_models` 为空数组。`available_models` 是解析结果去重后的列表，而 `detail` 里的 N 是去重前的条目数，网关重复返回同一 id 时两者不等。
- **探测模型 id**（Task 19 起）：取请求 `models` 中第一个 id 含 `image`（忽略大小写）的项；没有则取第一项；`models` 为空时用通用占位 `gpt-image-1`。理由：清单来自网关后首项可能是文本模型，个别网关对图片端点上的文本模型 id 返回 404，会被误提示为「路径不对」。该选取只作用于探测请求里的 `model`：`missing_models` 的比对不变，404 的两个分支仍以「请求 `models` 是否为空」为判据。
- **`ok` 与 `missing_models` 相互独立**：`ok` 只看有无 `failed` 步骤。网关的 `/v1/models` 不保证列出全部可用的图片模型，因此「未列出」是提示而不是失败判据；界面单独高亮，由用户判断。
- **`api_key` 的取值**（Task 22 收紧）：请求非空 → 用请求值（发往哪由用户负责）。为空或缺省 → 后端读取该 `vendor` 已保存的配置，依次判断：没有已保存的 key → 400「未配置 API Key，无法测试连通性」；请求的 `base_url` 与已保存的 `base_url` 一致 → 用已保存的 key；不一致 → 400「Base URL 与已保存配置不同，请填写 API Key 后再测试连通性」。两种 400 都不出站。一致性比较：两侧去首尾空白并去掉末尾的 `/` 后逐字符相等，其余（大小写、路径等）不做归一化——不匹配即要求显式提供 key，安全侧从严。保留回落的理由：最常见的用法是「打开设置直接测已保存的配置」，而前端只有脱敏值、拿不到明文，后端回落是唯一可行解；加前置条件的理由见下文「安全边界」。
- **不重试**：每步至多一次请求。

#### 为什么不生成图片、不计费

1. 第 1 步是只读的元数据请求，不触发任何生成。
2. 第 2 步的请求体**故意不含 `prompt`**。`prompt` 在两家的官方契约里都是生成的必填输入，参数校验先于生成执行；没有 `prompt` 就没有可生成的内容，端点只能以参数错误拒绝。因此「400」同时证明三件事：地址可达、路径正确、鉴权通过（鉴权不过会先得到 401 / 403）。
3. 探测从不调用 `/v1/images/edits`，从不发送 `prompt`、`size`、参考图等任何生成参数。
4. 第 2 步若意外得到 2xx，判为 `failed` 并展示响应摘要：不把它当作连通的判据，也不解析、不保存响应中的任何图片数据。

#### 安全边界

| 边界 | 规则 |
|---|---|
| SSRF 防线 | 探测前对请求的 `base_url` 调用**与生成出站同一个** `crate::cross_cutting::image_client::validate_base_url`（仅 https，或 http + 回环主机）；不合规 → 400，**0 次出站**。不为探测另写或放宽校验 |
| 重定向 | 禁用自动重定向（与生成一致）；3xx 不跟随，落入「其他状态」分支 |
| 凭据范围 | 只携带本次探测的那一把 key；不携带另一家的 key 或仓库里的其他凭据。请求只发往被探测的 `base_url`；已保存的 key 只在被探测的 `base_url` 与该家已保存的 `base_url` 一致时才会被使用（Task 22） |
| key 不外泄 | `message`、`steps[].detail`、400 错误文本、日志均不含 key 明文；网关响应摘要先过 `sanitize_error_body`（替换 key 并截断）再进入 `detail` |
| 无副作用 | 不落盘、不改设置、不写会话记录、不写图片目录 |
| 控制面 | 不改动控制面来源校验（`src/web/api_auth.rs` 一行不动） |
| 超时 | 连接 10s；**整次探测**总预算 30s（两步合计，每步请求的超时取剩余额度，预算用尽后的请求立即超时）。探测单独构造短超时的 `reqwest::Client`（同样禁重定向），不沿用生成用的 600s client |

**已保存的 key 只发往已保存的 `base_url`**（Task 22，合入前安全审查修正）：初版的回落不比较 `base_url`，当时的理由是「既有流程本就允许保留原 key、只改 `base_url`、保存后再生成，届时已保存的 key 同样会发往新地址」。该理由不成立：保存是用户对新地址的显式确认；探测不需要保存，请求里的 `base_url` 由调用方任意指定，回落等于让调用方把已保存的 key 引向任意合规地址。这违反了 spec 既有的「每个供应方的 `api_key` SHALL 仅随发往该供应方自身 `base_url` 的请求发送」。修正后回落只在请求的 `base_url` 与已保存的一致时成立，是让实现回归既有契约，不是新增约束；仍受同一条 `validate_base_url` 约束。用户显式提供的 key 不受此限。

**已知取舍**：用户点了「清除」但尚未保存时，草稿里没有新 key，只要 Base URL 未改动，探测仍会用已保存的 key（清除在保存后才生效）。一致性比较不做大小写与默认端口等归一化，写法不同但指向同一主机的地址会被要求重新输入 key（8.3 的 R19）。

#### 模型清单以探测结果为来源（Task 19）

用户原话：「模型清单默认从测试连通性按钮获取,并渲染,用户可以自己删除部分或添加自定义的部分.做个复选下拉框这样的东西吧」。接口字段见 5.5，交互与刷新规则见 5.9「设置弹窗的模型清单」。

- **来源**：第 1 步（`GET /v1/models`）成功时，探测响应多带一个 `available_models`——该步解析出的全部 model id，去重、保持网关返回顺序。不新增接口、不新增出站请求；两步探测的策略、判定、文案，以及 `steps`、`ok`、`message`、`missing_models`、`duration_ms` 一字不变。
- **刷新判据是 `available_models` 非空，不是 `ok`**：`ok` 要求两步都不失败，而第 2 步（图片端点）失败时，第 1 步拿到的模型列表依然有效，且正是用户此刻要的。`available_models` 为空（该步 `skipped` / `failed`，或网关返回 0 个模型）时，候选池与勾选都不变。
- **探测取得网关模型列表即替换草稿清单**（主控 2026-11-12 修正裁决）：草稿清单 = 网关返回的模型（去重、保持网关顺序）减去已被另一家勾选的 id，至多 256 个。初版裁决是「只扩充候选池、不改已有勾选」，但内置推荐清单非空，照此实现时探测后清单一个都不变，用户原话「模型清单默认从测试连通性按钮获取」落空，故改为替换。代价见下文「已知取舍」。
- **不过滤网关模型**：`available_models` 原样带回网关列出的全部模型，包含文本等非图片模型。按 id 文本过滤会误删命名里不含 `image` 的图片模型，也与 D2 的「id 是不透明字符串」相悖；取舍交给用户在复选下拉框里完成，参数面板的默认选中项由三级规则兜底（5.9「状态」）。
- **上限 256 与跨家去重**：见 D1。前端的配合规则是清单至多取网关模型的前 256 个、跳过已被另一家勾选的 id（5.9），两者都给出提示，不静默丢弃。
- **与 D1 否决项的关系**：D1 否决的是「生成链路在运行时自动拉清单并直接当清单用」。这里的拉取由用户显式点击触发，结果进入的是**草稿**清单，用户可增删，点「保存」后才成为清单；生成链路不调 `/v1/models`。
- **不落盘**：候选池与网关模型列表只在前端内存里；配置文件的形态不变，仍是每家一份 `models`。

已知取舍：

1. 再次探测会把取消勾选过的网关模型重新勾上。
2. 自定义添加但网关没返回的 id（以及内置推荐清单里网关未列出的项）在探测后被移出草稿清单；它们留在候选池并带「网关未列出」标注，可重新勾选，内置推荐项也可用「恢复推荐清单」加回。

5. 第 2 步的探测模型优先取 id 含 `image` 的项（见上文「探测模型 id」）；清单里没有任何 id 含 `image` 时仍取首项（8.3 的 R10）。

### 5.12 会话历史的时间交织（Task 20，2026-11-12 补充）

**缺陷**：重新打开会话时，对话区把会话记录的四条时间线首尾相接地渲染——全部消息 → 全部建议 prompt → 全部生成结果 → 全部事件，图和它的 prompt 被拆到两头，报错掉到最后。实测会话（3 条用户消息、3 张图、1 条 MiniMax 429 失败事件，真实先后为「消息 1 → 图 1 → 消息 2 → 图 2 → 消息 3 → 报错 → 图 3」）被渲染成「3 条消息 → 3 个 prompt → 3 张图 → 报错」。

#### 为什么需要提示词块时间戳

会话记录（`SessionRecord`）把四类条目分存在四个数组里，数组之间的先后只能靠时间戳还原：

| 数组 | 元素类型 | 修复前是否有时间戳 |
|---|---|---|
| `messages` | `ChatMessage` | 有（`ts`） |
| `prompt_blocks` | `PromptBlock` | **没有**（只有 `content`、`version`） |
| `generation_results` | `GenerationResult` | 有（`ts`） |
| `events` | `SessionEvent` | 有（`ts`） |

`PromptBlock` 是唯一没有时间戳的一类，前端的 `buildEntries` 只能给每个提示词块写 `record.session.created_at`。四类里有一类的时间是假的，按时间合并就无从谈起，于是实现成了分段拼接。因此修复分两半：后端给 `PromptBlock` 补时间戳（数据层根因），前端按时间合并排序（呈现层）。

#### 数据层：`PromptBlock.ts`

- `PromptBlock` 新增 `ts: Option<DateTime<Utc>>`，属性为 `#[serde(default, skip_serializing_if = "Option::is_none")]`（与 D13 的三个可选字段同一写法），类型见 5.1。
- 写入：`engine.rs` 的 `persist_iteration` 追加提示词块时写 `Some(Utc::now())`。同一轮迭代里它紧跟在用户消息（`ts: Utc::now()`）之后写入，因此同一轮内「用户消息的 ts ≤ 提示词块的 ts」。
- 存储：`session_store.rs` 的 `append_prompt_block` 只覆盖 `version`（现有最大版本号 + 1），`ts` 随调用方给出的块原样落盘，追加逻辑不需要改。
- 读取接口：`SessionRecordDto.prompt_blocks` 的元素类型就是 `PromptBlock`（`From<SessionRecord>` 原样搬运），所以 `ts` 自动出现在会话记录读取接口的响应里，`handlers/image_create.rs` 不需要改；`ts` 为 `None` 时该键不出现，前端读到 `undefined`。
- 旧会话记录：磁盘上的提示词块没有 `ts` 键 → 反序列化为 `None`，照常读出。之后的追加会整份重写记录，但旧块的 `ts` 仍为 `None`、仍不写出该键——旧块的时间不会被回填。
- 前端类型 `ImageCreatePromptBlock` 新增 `ts?: string | null`（5.8）。

#### 呈现层：排序规则（`buildEntries`）

`buildEntries(record)` 是把会话记录变成对话区条目的唯一位置（打开会话时调用）；它原在 `web/src/state/image-create-store.ts`，Task 21 起随文件拆分移入 `web/src/state/image-create-entries.ts`，行为不变（见 5.13「涉及文件」）。规则如下：

1. **每类条目各带自己的时间戳**：

   | 条目 | 时间戳来源 |
   |---|---|
   | 对话消息（用户消息、执行器回复） | `message.ts` |
   | 建议 prompt | `block.ts`；缺省或为 `null` 时走下文的旧记录兜底 |
   | 生成结果（图片、迁移中提示、图片引用缺失） | `result.ts` |
   | 事件（失败事件、其他系统提示） | `event.ts` |

2. **合并成一个数组**，初始顺序为「全部消息 → 全部建议 prompt → 全部生成结果 → 全部事件」，各类内部保持会话记录中的先后。
3. **按时间戳升序排序**，比较的是 `Date.parse(timestamp)` 得到的毫秒时刻；时刻相同的两条按它们在第 2 步数组中的下标比较。
4. **按最终位置重新编号**：条目 id 为 `history-<会话 id>-<最终下标>`。

#### 同一时间戳的稳定次序

时刻相同时次序固定为**消息 → 建议 prompt → 生成结果 → 事件**，类别也相同时保持会话记录中的先后。它不是另设的优先级表，而是第 3 步「时刻相同比初始下标」的直接结果：初始数组本来就按这四类依次排列。

需要它的理由：

- **同一轮的用户消息与建议 prompt 是连续写入的**（`persist_iteration`），两个 `Utc::now()` 可能落在同一毫秒，而排序用的 `Date.parse` 只有毫秒精度。没有固定次序时，prompt 可能排到触发它的那条消息前面。
- **旧记录兜底会主动制造相同时间戳**：没有 `ts` 的建议 prompt 借用同序号用户消息的时间戳，靠「消息在前」才能紧随其后。
- **可复现**：下标是全序的决胜键，结果不依赖排序实现是否稳定；同一份记录每次打开得到同一顺序。

#### 旧记录兜底

建议 prompt 的时间戳按 `block.ts ?? userMessages[index]?.ts ?? record.session.created_at` 取值，其中 `userMessages` 是 `messages` 里 `role` 为 `user` 的子序列，`index` 是该块在 `prompt_blocks` 中的下标：

1. 有 `ts` → 用它。
2. 没有 `ts`（缺省或 `null`）→ 取**同序号用户消息**的 `ts`：第 n 个建议 prompt 对应第 n 条用户消息，执行器回复不计入序号。
3. 没有同序号的用户消息 → 退回会话创建时间 `created_at`。

同序号配对的依据：后端的一轮迭代在 `persist_iteration` 里**成对**追加「用户消息 + 提示词块」。配对会错位的唯一情形是某一轮没有产出建议 prompt（`suggested_prompt` 为 `None` 时只追加用户消息），此后的旧块会对到更早一轮的用户消息上。这是旧数据的固有歧义——旧块没有任何可还原其时刻的信息——不为此引入猜测性的修正（8.3 的 R11）；新记录带 `ts`，不受影响。

#### 其他约束

- **仅存于 `current_prompt` 的 prompt**：`record.session.current_prompt` 非空且不等于任何提示词块的内容时，补一个建议 prompt 条目，按**当前状态**而非历史事件处理——它不参与排序，在其余条目排好序之后追加到数组末尾，时间戳取其余条目中最晚的时间戳（即排序后末项的时间戳），因此稳定排在时间线最后。没有任何其他条目时，时间戳退回 `created_at`；已有同内容的提示词块时不补（8.3 的 R12）。
- **条目 id** 只用作 React key。历史条目的 id 由「会话 id + 最终位置」决定：同一份记录重开不变，不同会话不碰撞。会话进行中追加的实时条目仍用 `entryId(前缀)`（`<前缀>-<毫秒时间>-<序号>`），与 `history-` 前缀不冲突。
- **只作用于打开会话时的重建**：会话进行中的条目经 `appendEntry` 按到达顺序追加，本来就是时间顺序，不重排。
- **`timestamp` 字段**是条目排序与渲染的唯一时间依据；建议 prompt 不再一律写 `created_at`。
- 不新增接口、不新增依赖；生成链路（5.7）不变。

### 5.13 模型未产出与结构化输出失败的区别（Task 21，2026-11-12 补充）

**问题**：实测中执行器（claude_code）正常跑完一轮迭代，但拒绝给出图片 prompt，也没有按结构化契约输出。后端解析不到 `suggested_prompt`，前端只收到一大段可读文本；「本轮未产出新的建议 prompt，已保留上一版」这句提示追加在长文本之后，被淹没，用户以为执行器断了。

根因有两层：

- **判定层**：`consume_iteration_events`（`prompt_iteration.rs`）把「结构化块解析成功但 `suggested_prompt` 为空」与「结构化块根本没解析出来」都折叠成 `suggested_prompt = None`，系统无法区分「模型主动不给」与「格式不符」。
- **呈现层**：`handleIterationEvent`（`image-create-store.ts`）在 `done` 时把提示追加到条目末尾，而 fallback 文本已在此前的 `text` 事件中追加，提示必然排在长文本之后；并且只在存在上一版 prompt 时才给提示，首轮未产出时没有任何提示。

#### 两种降级

| | 模型未产出 | 结构化输出失败 |
|---|---|---|
| 判定 | `StructuredOutputState::Parsed(value)`，且 `value` 的 `suggested_prompt` 取不到非空字符串（空串、只含空白、缺失、非字符串） | `StructuredOutputState::Failed(_)`（没有结构化块、nonce 不符、JSON 非法等）或 `NotRequested` |
| 含义 | 模型遵守了契约，明确表示本轮不给 prompt（拒答，或判断无法完成） | 模型无视或写坏了契约；系统不知道它是否想给 prompt |
| `suggested_prompt` | `None` | `None` |
| `prompt_declined` | `true` | `false` |
| 提示主句 | 「本轮模型未产出可用 prompt」 | 「本轮未产出新的建议 prompt」 |
| 模型说明 | 折叠为「查看模型说明」，默认收起 | 直接显示，不折叠 |

两种降级的共同点（均为既有行为，本次不改）：`persist_iteration` 不追加提示词块；`update_session_meta` 收到 `None` 时不覆盖 `current_prompt`，上一版建议 prompt 原样保留；后端先推 `text`（带可读文本）再推 `done`。

#### 双出口提示契约

`iteration_input`（`prompt_iteration.rs`）在迭代 prompt 末尾拼接结构化输出契约。修复后的契约全文（`{nonce}` 为每轮生成的随机值）：

```text
请严格按以下格式输出：
<ARIA_STRUCTURED_OUTPUT nonce="{nonce}">
{"nonce":"{nonce}","suggested_prompt":"用中文撰写的最终图片生成 prompt"}
</ARIA_STRUCTURED_OUTPUT>

除上面的 JSON 块外不要输出其他内容。
若你无法或不宜给出图片 prompt（例如内容涉及真实在世人物的私生活传闻、或你判断无法完成），
仍然必须输出上面的 JSON 块，但把 suggested_prompt 置为空字符串 ""，
并可在 JSON 块之外用一段文字说明原因。
要求：suggested_prompt 的内容必须用中文撰写（描述主体、场景、风格、构图等），不要用英文。
```

与修复前相比：

| 位置 | 修复前 | 修复后 |
|---|---|---|
| 首句 | `请严格按以下格式输出（不要输出其他内容）：` | `请严格按以下格式输出：`；「不要输出其他内容」移到 JSON 块之后，改为 `除上面的 JSON 块外不要输出其他内容。` |
| 未产出出口 | 无 | 新增三行：无法或不宜给出图片 prompt 时仍必须输出 JSON 块、把 `suggested_prompt` 置为空字符串，并可在 JSON 块之外用一段文字说明原因 |
| 「要求：……不要用英文。」 | 紧跟在 JSON 块之后 | 文字不变，位置移到末尾 |

首句必须改：旧措辞「不要输出其他内容」与未产出出口的「说明原因」互相矛盾，模型照前一句做就给不出说明。改写后「不要输出其他内容」的范围限定为 JSON 块之外，说明原因是它明确允许的例外（主控 2026-11-12 裁决，10.6）。

这样「拒答」也走结构化通道，系统能确定性地知道模型是主动不产出，而不是解析失败。契约只能提高可判定的比例，不能保证模型一定遵守：模型仍无视契约时落入「结构化输出失败」，提示照常出现并排在前面（8.3 的 R16）。真实执行器是否遵守见 8.2 的 A3：`claude_code` 已在真实调用中验证遵守（2026-11-12，实测记录见 10.6）。

#### 后端：`prompt_declined`

```rust
// prompt_iteration.rs
pub struct IterationOutcome {
    pub readable_text: String,
    pub suggested_prompt: Option<String>,
    /// 结构化块解析成功、但 suggested_prompt 为空或缺失 ⇒ 模型明确未产出。
    pub prompt_declined: bool,
    pub provider_session_id: Option<String>,
}

// models.rs（由 engine.rs 构造，经 WebSocket 推给前端）
pub struct IterationEvent {
    pub kind: String,
    pub text: Option<String>,
    pub suggested_prompt: Option<String>,
    #[serde(default)]
    pub prompt_declined: bool,
    pub provider_session_id: Option<String>,
    pub error: Option<String>,
}
```

- **字段变化**：`IterationOutcome` 由 3 个字段增为 4 个，`IterationEvent` 由 5 个字段增为 6 个，新增的都是 `prompt_declined: bool`，位于 `suggested_prompt` 之后；其余字段的名称、类型与语义不变。`IterationEvent` 没有 `Default`，它的每一处结构体字面量都要补上该字段。
- `prompt_declined` 为 `true` 时 `suggested_prompt` 必为 `None`。
- 各类事件的取值：

  | `kind` | 何时推送 | `prompt_declined` |
  |---|---|---|
  | `text` | 本轮没有 `suggested_prompt`（fallback，带可读文本） | 本轮的真实值 |
  | `prompt` | 本轮有 `suggested_prompt` | 本轮的真实值；有 prompt 时判定结果恒为 `false` |
  | `done` | 每轮成功收尾 | 本轮的真实值 |
  | `error` | 迭代失败 | `false` |

- **推送顺序与语义不变**：未产出时 `text` → `done`；产出时 `prompt` → `done`。
- **线上形态**：`#[serde(default)]` 只影响反序列化（缺该键读为 `false`）；序列化始终写出该键。旧前端忽略未知字段。
- **不落盘**：`prompt_declined` 只存在于迭代事件，不进入会话记录；`persist_iteration` 与会话记录形态不变。

#### 前端：提示、文案与模型说明折叠

- **何时提示**：`done` 时只要本轮未产出 prompt（`lastIterationHadPrompt` 为假）就生成恰好一条 `system_notice`，**不要求存在上一版**。修复前还要求参数面板的 prompt 非空，首轮未产出时没有任何提示。
- **是否明确未产出**：`declined = event.prompt_declined ?? lastFallbackDeclined ?? false`——`done` 事件带该字段时以它为准；未带时取本轮 `text` 事件携带的值；二者都没有（旧后端）时按 `false`，即结构化输出失败。
- **文案**由 `promptNoticeText({ declined, hasExplanation, hasPrevious })`（`image-create-entries.ts`）按「主句 + 说明指引 + 保留说明」依次拼接：

  | 段 | 条件 | 文本 |
  |---|---|---|
  | 主句 | `declined` 为真 | `本轮模型未产出可用 prompt` |
  | 主句 | `declined` 为假 | `本轮未产出新的建议 prompt` |
  | 说明指引 | `declined` 为真，且本轮有模型说明条目（`hasExplanation`：本轮收到过文本去首尾空白后非空的 `text` 事件；空白文本不生成条目） | `（下方是它给出的说明）` |
  | 保留说明 | 存在上一版（`hasPrevious`：参数面板的 prompt 去首尾空白后非空） | `，已保留上一版` |

  六种组合的完整文案（逐字）：

  | 判定 | 模型说明 | 上一版 | 文案 |
  |---|---|---|---|
  | 模型未产出 | 有 | 有 | 本轮模型未产出可用 prompt（下方是它给出的说明），已保留上一版 |
  | 模型未产出 | 无 | 有 | 本轮模型未产出可用 prompt，已保留上一版 |
  | 模型未产出 | 有 | 无 | 本轮模型未产出可用 prompt（下方是它给出的说明） |
  | 模型未产出 | 无 | 无 | 本轮模型未产出可用 prompt |
  | 结构化输出失败 | 不影响文案 | 有 | 本轮未产出新的建议 prompt，已保留上一版 |
  | 结构化输出失败 | 不影响文案 | 无 | 本轮未产出新的建议 prompt |

- **折叠只用于模型明确未产出**：`text` 事件生成 `provider_text` 条目时写 `collapsed: event.prompt_declined === true`（`ProviderText` 新增可选字段 `collapsed?: boolean`）。结构化输出失败（含该字段缺省）时不折叠——此时可读文本可能正是模型以纯文本写出的 prompt 或追问，用户需要直接看到。打开会话时由 `buildEntries` 重建的 `provider_text` 不带 `collapsed`，照旧直接显示。
- **提示排在模型说明之前**：store 在处理 `text` 事件时记下该条目的 id（`lastFallbackEntryId`）与该事件的标记（`lastFallbackDeclined`），`done` 时由 `insertNoticeBeforeFallback` 用 `splice` 把提示插到该条目**前面**；本轮没有模型说明条目时追加到末尾。两个变量在 `done`、`error`、打开会话与 `reset` 时清空，不会跨轮误用。
- **渲染**：`ChatPane.tsx` 对 `collapsed === true` 的 `provider_text` 用 `<details>` 包裹，`<summary>` 为「查看模型说明」，默认收起；其余照旧。

修复前，未产出一轮的实时时间线为「用户消息 → 模型说明（长文本全文）→ 提示（仅在有上一版时）」。修复后，模型未产出时为「用户消息 → 提示 → 模型说明（收起）」，结构化输出失败时为「用户消息 → 提示 → 模型说明（直接显示）」。

#### 边界与已知取舍

- **不落盘**：模型说明与提示只存在于实时时间线。`persist_iteration` 只写用户消息（有 prompt 时再写提示词块），重新打开会话后二者都不再出现（既有行为，8.3 的 R17）。
- **「有上一版」以提示词编辑框为准**：`hasPrevious` 看的是参数面板的 prompt，不是会话记录里是否出现过建议 prompt。用户手动清空编辑框后未产出，文案不带「，已保留上一版」；用户自己在编辑框里写了内容时则带（8.3 的 R14）。
- **模型未附说明**：模型只输出 JSON 块时 `text` 事件的文本为空（或只含空白字符），前端不生成模型说明条目，提示不带「（下方是它给出的说明）」，时间线里只有一句提示（8.3 的 R15）。
- **模型无视契约**：不输出 JSON 块时落入「结构化输出失败」，提示的主句为「本轮未产出新的建议 prompt」，模型的输出直接显示（8.3 的 R16）。
- **明确未产出时说明被折叠**：模型走了未产出出口、却把追问写在说明里时，追问也在「查看模型说明」之内；提示里的「（下方是它给出的说明）」指向它（8.3 的 R18）。
- 不新增接口、不新增依赖、不新增出站请求；生成链路（5.7）不变。

3. 模型 id 在生成链路只被比较与透传（C-03、C-15、T-06）；仅有两处默认值规则会看 id 是否含 `image`——前端的初始选中项（5.9「状态」）与探测第 2 步的探测模型选取（5.11），二者都不参与供应方归属与生成请求的构造。

6. 旧配置文件不丢凭据（S-01、S-07）。
7. 用户上传的参考图不落盘（E-14）。
8. 出站前可判定的错误不产生出站请求（E-10、E-12、E-15、C-13）。
9. key 明文不出现在脱敏视图、`Debug` 输出与错误文本中（S-13、S-14、C-11、C-16）。
10. 所选模型不可用时报错且不换家（T-03、T-04、T-05、E-12）；`model` 缺省即参数错误、不出站（H-01）。
11. 连通性探测不发送带 `prompt` 的请求、不调用 `/v1/images/edits`、每步至多一次请求（P-01、P-04、P-10）。

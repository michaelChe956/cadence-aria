## 1. 背景与目标

图片创作功能当前只能调用一个端点、一个写死的模型（`gpt-image-2`），每次生成互相独立。本次落地三项需求：

| 编号 | 需求 | 可验证行为 |
|---|---|---|
| R1 | 多模型可选 | 参数面板出现模型下拉；清单来自设置（用户可增删），内置 8 个 gpt id + 1 个 MiniMax id 为推荐默认值；所选 id 原样出现在出站请求的 `model` 字段 |
| R2 | 连续修改携带上一张生成图 | 会话内已有生成结果且开关打开时，本次请求走 `/v1/images/edits` 并以上一张生成图作为 `image[]` |
| R3 | 模型手动选择 | 模型下拉只列**已配置且可用**的供应方的 model id，由用户逐次选择；所选 id 原样进入出站请求的 `model` 字段；每条结果记录并展示「哪家 + 哪个模型」 |

### 非目标

- 不新增 `quality` 的 `xhigh`/`max`、不新增 `gif`/`svg` 输出格式、不新增 `complexity`/`n`/`stream`/`mask`/`markup`。现有枚举取值均是两家官方取值的子集，保持不变。
- 不新增更大的 `size` 档位。现有 `1024x1024`/`1536x1024`/`1024x1536`/`auto` 保持不变。
- 不展示 MiniMax 的 `revised_prompt`、`data[].size`。
- 不支持多张参考图（保留「仅支持单张参考图」）。
- 不支持「异步任务 + URL」形态的端点（用户硬约束：三方 GPT endpoint 与 OpenAI 官方一致）。

### 2.2 用户硬约束（逐条落到设计）

| 硬约束 | 落点 |
|---|---|
| 三方 GPT endpoint 与 OpenAI 官方 API 一致 | GPT 侧只发官方 Images API 字段与取值；multipart 图字段 `image[]`（D10） |
| 不为 `-2k`/`-4k` 发明请求字段 | 模型 id 是不透明字符串，仅作为 `model` 值透传；GPT 侧无任何分辨率映射字段（D2、D14） |
| 响应按各家官方形态解析 | GPT 读 `data[].b64_json`；MiniMax 显式请求 `response_format=b64_json` 并逐项检查 `data[].error`（D11） |
| MiniMax 只用官方对接方式 | 只发 `H3ImageGenerationReq` / `H3ImageEditReq` 字段集的子集；不发 `quality`/`background`/`input_fidelity`（D10） |
| `input_fidelity` 对 GPT 2.x 省略 | 全链路移除该参数（D11） |
| 不做网关身份推断、无网关特例 | 代码中不存在对 base_url 主机名或模型 id 字符串的任何分支（D2） |
| 8 + 1 个 id 必须在可选清单里 | 内置为推荐默认值，用户可改（D1） |

### 2.3 既有惯例（保持不变）

出站仅 https 或 loopback、禁重定向；图片生成请求不自动重试；600s 超时；同一会话单并发；先写图后写会话引用；key 不进执行器子进程；后端 `mockito` 内嵌单测、前端 vitest。错误信息沿用现有形态：变体前缀为英文（如 `invalid parameter: `），本次新增的说明文字用中文（与现有「仅支持单张参考图」一致）。

## 4. 关键决策

### D1 模型清单 = 每家一份用户可配置的 id 列表

**决策**：模型清单不做枚举。`.aria/image_create.json` 中每家只存一份 `models: Vec<String>`（model id 清单），没有其他按家的模型字段。代码内置默认值：

- GPT 家 `models`：`gpt-image-2.6-flare`、`gpt-image-2.6`、`gpt-image-2.6-flare-2k`、`gpt-image-2.6-flare-4k`、`gpt-image-2.6-sunburst`、`gpt-image-2.6-sunburst-2k`、`gpt-image-2.6-sunburst-4k`、`gpt-image-2.5`（`gpt-image-2.6-flare` 打头，其余 7 个保持用户给出的顺序）
- MiniMax 家 `models`：`MiniMax-H3-Image`

保存时校验（任一不满足则整体拒绝、不落盘，错误为 `InvalidConfig`）：

1. 每个 id 去除首尾空白后长度 1–128，字符集限 `A-Z a-z 0-9 . _ : / -`
2. 同一家内不重复；两家之间不重复
3. 每家至多 32 个；允许为空（空清单 = 该家不可用）

生成请求的 `model` 不再有保留值，清单 id 也不再有保留字限制。

生成时校验：请求的 `model` 必须**逐字符等于**某个已配置且可用的家的清单中的某一项，否则报错、不出站（完整规则见 D15 与 5.1「目标解析语义」）。

**理由**：调研结论表明 8 个 gpt id 中 6 个不是 OpenAI 官方模型，是否可用完全取决于用户 endpoint。硬编码枚举会把「endpoint 支持什么」这个只有用户知道的事实写死在代码里。内置 GPT 清单以 `gpt-image-2.6-flare` 打头，是因为模型下拉的初始选中项取第一个可用供应方清单的首个 id（5.9）：`gpt-image-2.6-flare` 是清单中经官方目录核实存在的 id，在官方与三方 endpoint 上都成立；若以裸 `gpt-image-2.6`（非 OpenAI 官方 id）打头，用户第一次点生成就可能失败。

**备选与否决**：

- 硬编码 `enum ImageModel`：否决。新增/下线模型要发版，且对 6 个非官方 id 做了无依据的背书。
- 运行时调 `/v1/models` 拉清单：否决。增加一条出站路径；返回大量无关模型；MiniMax 侧无对应约定。
- 自由文本输入框（不设清单）：否决。无法在出站前拦截拼写错误，每次拼错都是一次可能计费的失败请求。

### D2 模型 id 是不透明字符串，家只由清单归属决定

**决策**：新增 `ImageVendor { Gpt, Minimax }`。一个模型 id 属于哪一家，**唯一依据是它被配置在哪一家的清单里**。代码不对模型 id 做前缀/后缀匹配、不做正则、不做 `match`；也不对 base_url 的主机名做任何判断。请求字段集、响应解析差异只以 `ImageVendor` 为键。

命名说明：前端已有 `IMAGE_CREATE_PROVIDER_OPTIONS` / `ImageCreateProvider`（对话执行器的 provider），后端会话上也有 `provider_name`。为避免同一功能域内 `provider` 一词两义，图片供应方统一命名 `vendor`（Rust 类型、JSON 键、TS 类型一致）。

**理由**：满足「不做网关身份推断」「不为 `-2k`/`-4k` 发明字段」两条硬约束的最简结构——推断逻辑根本不存在，就不可能推断错。

**备选与否决**：

- 按 id 前缀（`gpt-` / `MiniMax-`）推断家：否决。用户自定义 id 命名不受控，且属于被明令禁止的推断。
- 请求同时携带 `vendor` + `model`：否决。两家清单互不重复（D1 规则 2）时 `model` 已唯一确定家，多一个字段只多一种不一致的可能。

### D3 双家独立凭据；旧配置文件读时兼容、写时迁移

**决策**：`ImageCreateSettings` 由 `{ base_url, api_key, defaults }` 改为 `{ vendors: { gpt, minimax }, defaults }`，每家一个 `VendorSettings { base_url, api_key, models }`。

文件兼容规则（反序列化经中间结构 `ImageCreateSettingsWire`，见 5.1）：

| 文件形态 | 读入结果 |
|---|---|
| 文件不存在 | 两家凭据为空、清单为内置默认值 |
| 旧形态 `{ base_url, api_key, defaults }`（无 `vendors` 键） | 顶层 `base_url`/`api_key` 归入 `vendors.gpt`；`vendors.minimax` 凭据为空；两家清单为内置默认值；`defaults` 原样保留 |
| 新形态但某家缺失，或某家缺 `models` | 缺失项补该家内置默认清单 |
| 新形态且某家 `models: []` | 保持为空（用户主动清空），不被默认值覆盖 |
| 同时存在 `vendors` 与顶层 `base_url`/`api_key` | 以 `vendors` 为准，顶层忽略 |

读取不改写文件；下一次保存设置时整份以新形态写回（不再写顶层 `base_url`/`api_key`）。

**理由**：两家是不同的服务商，域名、密钥、计费账户都独立。旧文件里的那组凭据此前只用于调 GPT 模型，归入 GPT 家语义无损。`load()` 对解析失败的处理是 `unwrap_or_default()`，所以**新结构必须能成功解析旧文件**，否则升级后用户的 key 会无声消失——这是必测不变量（S-01）。

**行为变化（写入 `CHANGELOG.md`）**：旧版本写死使用 `gpt-image-2`；升级后内置 GPT 清单不含该 id，模型下拉的初始选中项为 `gpt-image-2.6-flare`。需要继续用 `gpt-image-2` 的用户在设置的 GPT 模型清单里加一行该 id，保存后在模型下拉里选它即可。

**不支持降级**：新形态文件被旧版本读取时取不到凭据，需重新录入。不为此双写顶层字段（避免 key 在文件中出现两份、避免长期保留兼容分支）。

**备选与否决**：

- 一组凭据服务两家：否决，理由同上；用户若确有同一 endpoint 承载两家，把两家的 base_url 与 key 填成相同即可，无需代码支持。
- 拆成两个文件：否决。`defaults` 是共享的；两处原子写与两处脱敏只增加出错面。
- 加 `version` 字段：否决。「有无 `vendors` 键」已足以判别，版本号是无人消费的状态。

### D4 设置更新与脱敏按家独立

**决策**：

- 读取（脱敏）：`MaskedSettings { vendors: { gpt, minimax }, defaults }`，每家 `MaskedVendorSettings { base_url, api_key_masked, models, recommended_models, available }`。`mask_api_key()` 规则不变，逐家应用。`recommended_models` 由后端给出内置默认清单，供前端「恢复推荐清单」使用（前端不维护第二份 id 常量）。`available = base_url 非空 ∧ api_key 非空 ∧ models 非空`。
- 更新：请求体 `{ vendors?: { gpt?, minimax? }, defaults? }`。某家整体缺省 = 该家全部保留。每家 `{ base_url?, api_key_action, api_key?, models? }`，`api_key_action` 仍是 `retain`/`replace`/`clear` 三态，缺省为 `retain`；`replace` 的取值语义沿用现状。
- `base_url` 允许为空串（表示该家未配置）；非空时必须通过 `validate_base_url`。
- 旧的顶层请求字段 `base_url`/`api_key_action`/`api_key` 一并移除（前后端同一变更内切换，不保留双形态）。
- 校验从「只校验本次提交的 base_url」改为「合并后对整份设置校验」：handler 流程变为 `from_request` → `apply_update` → `validate_settings` → `save`。`SettingsStoreApi::validate_base_url` 由 `validate_settings(&self, settings: &ImageCreateSettings)` 取代。

**理由**：「保留/替换/清除」是针对「一把 key」的语义，两把 key 就应有两个独立的三态；用户只改 MiniMax 的 key 时，GPT 的 key 不应被触碰。模型清单的跨家去重只能在合并后的整体上判定，所以校验点后移到合并之后。

**备选与否决**：一次请求必须提交两家全量：否决。脱敏后前端拿不到明文 key，全量提交必然要带「保留」语义，等价于现方案但更易误清。

### D5（已废止）自动轮转

**按用户 2026-11-12 要求撤回自动轮转**（用户原话：「你就让用户在已配置并可用的provider里选model id就行，轮转不需要」）。轮转机制（自动选家、每家轮转模型、结果里的选择方式）整条删除，改为用户在参数面板手动选择 model id，现行规则见 D15。原先的「失败不消耗轮次」「只配一家恒用那家」「显式选择不被轮转覆盖」等语义随轮转一并失效，不再是契约。

### D6（已废止）某家不可用时自动改用另一家

随 D5 一并废止：不再存在「首选家」，也不再存在「首选家不可用时改用另一家」。现行规则是所选模型不可用即报错、不出站、绝不静默换家（D15）；请求发出后失败不回退、不重试的边界保留（D12.3）。

### D7 携带上一张图在 engine 层完成；上传的参考图优先

**决策**：生成请求新增字段 `use_previous`（`true`/`false`，缺省 `false`）。前端开关「基于上一张图继续修改」默认打开。engine 在 `run_generation` 内按如下优先级确定本次 reference：

1. 请求带了用户上传的参考图 → 用上传图，来源记 `uploaded`。`use_previous` 被忽略。
2. 否则 `use_previous = true` 且会话 `generation_results` 非空 → 取末项，读出图片字节作 reference，来源记 `previous`。
3. 否则无 reference，来源记 `none`，走 `/v1/images/generations`。

末项取图由 `image_files.rs` 新增的 `read_result_image()` 完成，规则与图片读取端点现有逻辑一致：有 `image_id` 且文件可读 → 文件字节；否则有内联 `b64` 且可解码 → 解码字节；否则不可用。`get_session_image` 改为调用该函数并删除 `decode_legacy`，「读一条生成结果的图片字节」只保留一处实现。取到的字节以记录中的 `media_type` 作为 `declared_mime`，与上传图走同一个 `validate_reference_image`。

「末项」取自 `run_generation` 内重新读取的会话记录，时点在 `generate()` 的 `flush_pending()` 之后，保证此前写图成功但引用待补的结果已进入序列。

**理由**：

- 放在 engine：上一张图是会话状态，engine 是唯一同时持有会话记录、图片文件路径与生成生命周期的层。handler 只做协议解析；客户端只做 HTTP。前端不参与传图——让前端把刚下载的图再上传一遍既浪费，又与「上传参考图不持久化」的对象混淆。
- 上传优先且不叠加：保留既有「仅支持单张参考图」约束。两张图同时发送时哪张是「底图」对两家都没有官方定义的优先级。
- 后端缺省 `false`：不带该字段的调用方行为与今天完全一致；「默认携带」是产品层默认值，由前端开关承载，用户可关闭以开始一张无关的新图。

**备选与否决**：

- 前端把上一张图当参考图回传：否决，见上。
- 上传图与上一张图一起作为 `image[]` 两项发送：否决，见上；且改变单张约束会波及校验、请求体上限与既有 spec。
- 后端缺省 `true`：否决。隐式把 generations 变成 edits 改变了既有 API 的默认语义。

### D8 上一张图不可用时：明确失败，不出站

**决策**：D7 第 2 步中，若 `read_result_image()` 返回不可用，或内容校验不通过，本次生成**直接失败**，不发任何出站请求，错误为新增变体 `PreviousImageUnavailable(原因)`：「上一张图片不可用，无法基于它继续修改（<原因>）；请关闭「基于上一张图继续修改」或上传参考图」。原因取「图片文件缺失或无法读取」或校验错误的文本。

**理由**：用户此刻的意图是「修改那张图」。静默退化成文生图会得到一张无关的新图并为此付费，而错误原因被掩盖。失败在出站前发生，零费用，且给出两条可操作的出路。

**备选与否决**：

- 静默降级为文生图：否决，见上。
- 向前回溯到更早一张可用的图：否决。「上一张」被悄悄换成「上上张」，结果与用户看到的画面对不上。
- 为上一张图放宽 10 MiB / 4096 的校验上限：否决。两家对 edits 输入图的上限里只有 MiniMax 有官方数值，放宽等于把未验证的上限当已知。

### D9 既有 spec「参考图不被持久化」的改写

**决策**：把该约束收窄到它本来要保护的对象——**用户上传的参考图**：

- 保留：用户上传的参考图仅在本次请求生命周期内使用，不落盘、不进会话记录。
- 新增澄清：连续修改携带的「上一张图」是会话记录中已持久化的**生成结果图片文件本身**；系统不为携带而另存任何副本；其生命周期随会话记录（会话删除时一并删除），不属于「参考图持久化」。
- 两类参考图适用同一组输入约束（格式、10 MB、4096 像素、静态图）。

推论：用户上传参考图生成后，下一轮携带的是那次的**生成结果**，不是当初上传的参考图。

**理由**：原条款的目的是「用户给的输入图不留存」，而生成结果早已按 `image-create-file-storage` 变更持久化。两者是不同对象，改写后原有隐私边界不变。

### D10 字段过滤集中在一个函数；MiniMax 在 `size=auto` 时发 `area=1K`

**决策**：`image_client.rs` 新增内部函数 `wire_fields(target, req) -> WireFields`，是「按家决定发哪些字段」的**唯一**位置。JSON body 与 multipart form 都从 `WireFields` 构造，不各自判断。完整规则表见 5.4，其中唯一需要论证的一条：

> MiniMax 且用户 `size` 为 `auto` 时：**不发 `size`，发 `area=1K`**。MiniMax 且 `size` 为具体 `WxH` 时：发 `size`，不发 `area`。GPT 恒发 `size`，恒不发 `area`。

**这条规则的理由**（它决定了 R2 的携带链在默认参数下、且用户在两家模型之间切换时能否成立）：

- 前端默认 `size` 是 `auto`（`DEFAULT_IMAGE_PARAMS`），默认打开「基于上一张图继续修改」；用户可随时在模型下拉里改选另一家的模型。
- MiniMax 官方在未指定尺寸时的默认面积档是 `4K`（4096²，约 1677 万像素）。按该档位推算：8 位 RGB 原始数据约 48 MiB，默认输出格式 png 下体积通常远超 10 MiB；非正方形比例下长边还会超过 4096（16:9 时约 5461×3072）。实际出图像素以服务端为准，本条是依据官方默认值的推算，未经真实调用测量。
- 该图会成为下一次生成的「上一张图」，要过 `validate_reference_image`（`MAX_SIDE = 4096`、`MAX_BYTES = 10 MiB`）。按上述推算，MiniMax 出图之后的下一次携带大概率失败；即使个别情况下能通过，结果也取决于图片内容，不可预期。
- `area=1K`（1024²）是唯一能用算术保证携带链成立的官方档位：总像素 1,048,576，在官方允许的 1:3–3:1 比例内长边不超过 1774；8 位 RGBA 原始数据为 4 MiB，PNG 最坏情况也只略高于原始数据，jpeg/webp 更小，均远低于 10 MiB。`2K`（2048²）的 8 位 RGBA 原始数据为 16 MiB，PNG 可能超限。
- `1K` 也与 GPT 侧 `auto` 的常规输出量级（1024–1536）一致，用户在两家模型之间切换时分辨率不跳变。
- `area` 是 MiniMax 官方 `H3ImageGenerationReq` 字段（官方字段表已核实），在用户硬约束列出的 MiniMax 官方字段集内。**证据等级需分侧看**：`H3ImageGenerationReq` 侧已由官方字段表直接确认；`H3ImageEditReq` 侧官方文档只列出 required 字段与 `images`/`mask`/增强规则，**未逐项列出可选字段集**，故「改图端点接受 `area`」是按 MiniMax 官方改图端点与文生图端点同构作出的推定，属 8.2 节待联调确认项 A1，tasks 7.2 已覆盖改图侧的真实调用确认。**该推定不成立时，改动收敛在 `wire_fields()` 一处与 C-02b / C-05 两个用例，但必须回到本决策重新论证，不得在实现中自行调整。**
- 它只发往 MiniMax，与「不得为 GPT 的 `-2k`/`-4k` 发明字段」无关：GPT 请求中永远没有 `area`。
- 不发 `size` 而只发 `area`，是因为官方规定 `size=WxH` 时不得同时传 `area`；两者从不同时出现，无论该互斥规则的边界细节如何都不会触发。

**单点函数的理由**：generations（JSON）与 edits（multipart）两条构造路径若各自 `if vendor == …`，迟早有一条漏改。单点函数让「MiniMax 请求里没有 `quality`」成为一个可以直接断言的性质。

**备选与否决**：

- MiniMax `size=auto` 原样透传：否决，MiniMax 出图之后的下一次携带能否成功取决于出图体积，不可预期（见上）。
- MiniMax `size=auto` 时改发 `size=1024x1024`：否决。丢掉了 `auto` 的本意（由模型按 prompt 决定比例）。
- 每家一个 `ImageClientApi` 实现：否决。两家端点路径、鉴权、multipart 图字段完全同构，差异只有几个字段，拆成两个实现会复制整条 HTTP 与错误处理路径。

### D12 出站安全与计费边界

**决策**：

1. base_url 校验两处生效：保存设置时 `validate_settings` 对每家非空的 `base_url` 校验，不合法整体拒绝；出站前客户端对本次目标家的 `base_url` 再校验（防手改文件）。
2. **不做 URL 兜底下载**。响应项只有 `url` 没有 `b64_json` 时报 `MissingB64`。
3. 一次生成请求 = 至多一次出站 HTTP 调用。无重试、无换家回退（D15）。
4. 600s 超时、30s 连接超时、禁重定向沿用现有同一个 `reqwest::Client`，两家共用。
5. **key 隔离**：`ImageCallTarget` 只携带本次目标家的一把 key，客户端拿不到另一家的 key，因此 GPT 的 key 不可能发往 MiniMax 的 base_url，反之亦然。
6. key 不进执行器子进程：新结构仍只由 `settings_store.load()` 在 engine 的生成路径与设置 handler 内读取，不写入环境变量、不进入对话执行器的任何入参。
7. 日志与错误不含 key：`sanitize_error_body()` 以本次目标家的 key 做替换（HTTP 错误体与逐项错误文本都过它）；`VendorSettings` 与 `ImageCallTarget` 手写 `Debug`，`api_key` 输出为 `<redacted>`。

**不做 URL 下载的理由**：URL 的主机由上游响应决定，不在用户配置的 base_url 约束内，跟随它等于让上游指定本机去访问任意地址（内网、元数据服务）；而两家官方都能直接返回 b64（GPT 恒返回，MiniMax 显式请求即可），URL 下载没有必要性。

### D13 可观测性：结果记录「哪家 + 哪个模型」

**决策**：`GenerationResult` 新增 3 个可选字段，全部 `#[serde(default, skip_serializing_if = "Option::is_none")]`（与现有 `image_id`/`b64` 的属性写法一致）：

| 字段 | 取值 | 含义 |
|---|---|---|
| `vendor` | `gpt` / `minimax` | 实际出站的家 |
| `model` | 字符串 | 实际出站的 `model` 值 |
| `reference_source` | `none` / `uploaded` / `previous` | 本次 reference 的来源 |

`GenerationResultDto` 及其 `From<GenerationResult>` 同步带出这 3 个可选字段。生成接口的成功响应在 `image_id`、`media_type` 之外返回这 3 个字段。

`DefaultParams` **不变**（不加 `model`）。它同时是「设置里的默认参数」与「结果里的参数快照」，而模型选择不是持久化的默认参数（下拉初始选中项由可用供应方的清单推导，见 5.9），且已由 `GenerationResult.model` 单独记录。`GenerationResult.params` 的语义定义为「用户本次请求的参数」；对 MiniMax 结果，其中的 `quality`/`background` 未被发送。

旧会话记录：3 个字段缺失 → 反序列化为 `None` → 前端不显示模型标注；内联 `b64` 的旧结果可作为「上一张图」（D7）。

失败可观测：图片客户端返回的错误（即已确定目标之后、与供应方相关的错误），其错误信息与 `generation_error` 事件文本以「[<家> · <模型 id>] 」为前缀，在 `finish_generation` 的错误分支统一添加。

**备选与否决**：把 `model` 放进 `DefaultParams`：否决，理由见上；且持久化的模型会在供应方凭据或清单变化后失效，等于多出一份需要与清单保持一致的状态。

### D14 未验证项收敛：代码不依赖 `-2k`/`-4k` 的语义

**决策**：唯一未知的是「`-2k`/`-4k` 这类 id 在用户 endpoint 上对应什么分辨率档位、是否覆盖请求里的 `size`」。代码通过以下手法做到完全不依赖它：

1. 模型 id 只有两种用途：与清单做逐字符相等比较；原样写入请求的 `model` 字段。除此之外不被读取。
2. GPT 侧 `size` 始终取用户在参数面板选的值，对该家所有模型一视同仁地发送；不因模型 id 调整、不因模型 id 省略。
3. GPT 请求中不存在 `resolution`、`area`、档位映射表等任何自造字段或映射结构。
4. 内置 id 字面量只出现在 `models.rs` 的默认清单常量中；`image_client.rs` 的非测试代码不含任何模型 id 字面量。
5. 用测试固化：同一组参数下，`gpt-image-2.6-flare` 与 `gpt-image-2.6-flare-4k` 的出站请求体除 `model` 值外完全相同（C-03）；`image_client.rs` 非测试源码不含模型 id 字面量（C-15）。

档位语义由 endpoint 负责；endpoint 若不认识某个 id，其错误响应经 `HttpStatus` 脱敏后呈现给用户，用户据此调整清单。

### D15 模型由用户手动选择；不可用即报错，绝不静默换家

**决策**：生成请求的 `model` 字段**必填**，取值是某个已配置且可用的家的清单中的 model id；不存在保留值。

- `model` 缺省，或去首尾空白后为空 → `InvalidParam`「请选择图片生成模型」，不出站（handler 解析 multipart 时拦截）。
- 目标解析 `resolve_target(model)` 按**逐字符相等**在**可用**的家（`is_available()`：base_url 与 api_key 均非空，且清单非空）里找该 id 的归属；找到即返回 `{ vendor, model }`。
- 找不到可用的归属家时：该 id 在某家清单里、但该家缺 base_url 或 api_key → `MissingConfig`「<家> 尚未配置 Base URL 或 API Key」；该 id 不在任何家的清单里 → `InvalidParam`「模型 <id> 不在已配置且可用的供应方清单中」。两种情形都不出站。
- **没有「首选家」，也没有「降级到另一家」**：解析只依赖设置与请求里的 `model`，不读会话历史；所选模型不可用就报错。
- 请求发出后失败（网络、超时、非 2xx、逐项错误）：原样报错，不回退到另一家、不重试（D12.3）。
- 前端：模型下拉只列可用供应方的 model id；初始选中项 = 第一个可用供应方清单的首个 id；没有可用供应方时 `model` 为空串、生成按钮禁用并提示「请先在设置里配置并启用至少一个供应方」；设置变更后所选模型不再可用时，重置为同一规则的结果（5.9）。

**理由**：

- 用户 2026-11-12 明确要求：「你就让用户在已配置并可用的provider里选model id就行，轮转不需要」。
- 静默换家会让用户不知道自己实际用的是谁。两家是不同的服务商、不同的计费账户、不同的字段集（MiniMax 不发 `quality`/`background`），换家后的出图与费用归属都和用户选的不一致。
- 报错发生在出站之前，零费用；错误文本直接指出是哪一家缺配置，或哪个 id 不在清单里，用户可据此修正。
- 解析变成只依赖「设置 + `model`」的纯函数，不再读取会话结果序列，原先「旧记录无 `vendor` 视为 GPT」这类特例随之消失。

**备选与否决**：

- 保留自动轮转作为下拉里的一个选项：否决。用户已明确撤回；保留它就要同时保留每家的轮转模型、结果里的选择方式与「首选家不可用时换另一家」整套规则。
- 所选模型所属的家不可用时，自动改用另一家的首个模型：否决，这就是静默换家。
- `model` 缺省时由后端取第一个可用供应方的首个 id：否决。调用方漏传字段时，后端会在用户不知情的情况下选定计费方；初始选中项由前端的下拉承载，用户看得见。

## 5. 详细设计

### 5.1 后端类型（`src/product/image_create/models.rs`）

```rust
/// 图片供应方（「家」）。决定请求字段集与响应解析。
/// 一个模型 id 属于哪一家，只由它被配置在哪一家的清单里决定，绝不从 id 字符串推断。
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum ImageVendor {
    Gpt,
    Minimax,
}

/// 内置推荐清单：仅作为默认值，用户可在设置中增删。
/// GPT 清单以经官方目录核实的 id 打头：它是模型下拉的初始选中项（5.9）。
pub const DEFAULT_GPT_MODELS: [&str; 8] = [
    "gpt-image-2.6-flare",
    "gpt-image-2.6",
    "gpt-image-2.6-flare-2k",
    "gpt-image-2.6-flare-4k",
    "gpt-image-2.6-sunburst",
    "gpt-image-2.6-sunburst-2k",
    "gpt-image-2.6-sunburst-4k",
    "gpt-image-2.5",
];
pub const DEFAULT_MINIMAX_MODELS: [&str; 1] = ["MiniMax-H3-Image"];

pub const MAX_MODELS_PER_VENDOR: usize = 32;
pub const MAX_MODEL_ID_CHARS: usize = 128;

impl ImageVendor {
    pub const ALL: [ImageVendor; 2] = [ImageVendor::Gpt, ImageVendor::Minimax];
    /// 面向用户的名称："GPT" / "MiniMax"。
    pub fn label(self) -> &'static str;
    /// 该家的内置推荐清单。
```

#### 目标解析语义（`resolve_target`）

实现须与以下规则逐条一致：

1. 按**逐字符相等**，在**已配置凭据**（`has_credentials()`）**且模型清单非空**（即 `is_available()`）的供应方里找该 model id 归属的家。
2. 找不到 → 参数错误「模型 {id} 不在已配置且可用的供应方清单中」。
3. 找到但该家 base_url 或 api_key 为空 → 配置缺失「{家} 尚未配置 Base URL 或 API Key」。
4. 找到且可用 → 返回 `{ vendor, model }`（`ResolvedTarget` 只有这两个字段）。
5. 没有「首选家 / 降级到另一家」：手动选的模型不可用就报错，绝不静默换家。
6. 生成请求的 `model` 必填：缺省或去空白后为空 → 参数错误「请选择图片生成模型」（handler 层，见 5.5）；不再有 `auto` 保留值。

伪规则：

```text
resolve_target(id):
  owner = ImageVendor::ALL 中第一个满足「is_available() 且 models 含 id（逐字符相等）」的家
  owner 存在
      → { vendor: owner, model: id }
  否则 vendors.vendor_of(id) = Some(v)      // id 在 v 的清单里，但 v 缺 base_url 或 api_key
      → MissingConfig("{v.label()} 尚未配置 Base URL 或 API Key")
  否则
      → InvalidParam("模型 {id} 不在已配置且可用的供应方清单中")
```

说明：

- 解析不读会话历史，没有首选家，也没有换家；同一组设置与同一个 `id` 永远得到同一个结果。
- 清单为空的家不可用：即使它持有凭据，也不参与解析，更不会被当作「另一家」顶上。
- `ImageVendor::ALL` 的顺序（GPT、MiniMax）只在同一 id 被手改文件误配进两家时起作用（可用的家优先）；正常保存的设置里跨家不重复（D1 规则 2）。

### 5.4 字段过滤规则表（E）

「发」= 一定出现在请求中；「不发」= 一定不出现。generations 为 JSON body，edits 为 multipart，同一家两种端点的字段规则相同（edits 额外带 `image[]`）。

| 字段 | GPT | MiniMax |
|---|---|---|
| `model` | 发（清单中的 id 原样） | 发（清单中的 id 原样） |
| `prompt` | 发 | 发 |
| `output_format` | 发 | 发 |
| `size` | 发（含 `auto`） | 用户选具体 `WxH` 时发；用户选 `auto` 时**不发** |
| `area` | **不发** | 用户选 `auto` 时发，恒为 `1K`；用户选具体 `WxH` 时**不发** |
| `quality` | 发 | **不发** |
| `background` | 发 | **不发** |
| `response_format` | **不发** | 发，恒为 `b64_json` |
| `image[]`（仅 edits） | 发，1 个文件部件 | 发，1 个文件部件 |
| `input_fidelity` | 不发 | 不发 |
| `aspect_ratio` / `disable_prompt_enhanced` | 不发 | 不发 |
| `n` / `stream` / `output_compression` | 不发 | 不发 |
| `complexity` / `moderation` / `mask` / `markup` / `partial_images` / `safety_identifier` 等其余官方可选字段 | 不发 | 不发 |

依据：

- GPT 不发 `response_format`：官方明确 GPT Image 模型不支持该遗留参数，恒返回 b64。
- MiniMax 必须发 `response_format=b64_json`：官方默认是 `url`。
- MiniMax `size` 与 `area` 二选一：见 D10。
- MiniMax 不发 `aspect_ratio`：`size=WxH` 时官方禁止同传；`area` 模式下不传即由模型按 prompt 定比例，与 `auto` 的本意一致。
- `size` 的三个具体取值与 `output_format` 的三个取值对两家均为官方合法值。
- multipart 图字段两家统一用 `image[]`：GPT 官方多图字段名；MiniMax 官方接受 `image` 或 `image[]`。

### 5.6 响应解析与错误归一

HTTP 2xx 时对 `data[]` 的处理（两家同一套规则，天然满足各家官方形态）：

1. 按顺序找第一个 `b64_json` 非空的项 → 成功，取它。
2. 没有成功项时：存在带 `error` 的项 → `ItemError(msg)`。`msg` 取第一个 `error`：是对象且含字符串 `message` 则取之，否则取其紧凑 JSON 文本；再经 `sanitize_error_body()`（脱敏 + 截断 500 字符）。
3. 没有成功项、也没有 `error` 项：`data` 为空或缺失 → `EmptyData`；否则（例如只有 `url`）→ `MissingB64`。

本功能每次只请求 1 张图（不发 `n`），所以规则 1 的「取第一个成功项」不会丢弃多余的成功图。

错误归一总表：

| 情形 | 发生位置 | 错误 | 是否已出站 |
|---|---|---|---|
| prompt 为空 | engine | `InvalidParam`（沿用现状） | 否 |
| `use_previous` 取值非法 | handler | `InvalidParam` | 否 |
| `model` 缺省或为空 | handler | `InvalidParam`「请选择图片生成模型」 | 否 |
| 模型不在任何已配置且可用的家的清单 | `resolve_target` | `InvalidParam` | 否 |
| 模型所属的家缺 base_url 或 api_key | `resolve_target` | `MissingConfig` | 否 |
| 上一张图不可用 | engine | `PreviousImageUnavailable` | 否 |
| 上传的参考图不合规 | handler / engine | `RefImage`（沿用现状） | 否 |
| base_url 不合法 | client | `InvalidConfig`（沿用现状） | 否 |
| 3xx | client | `RedirectBlocked`（沿用现状） | 是 |
| 非 2xx | client | `HttpStatus`（沿用现状：脱敏、截断） | 是 |
| 2xx，逐项错误 | client | `ItemError` | 是 |
| 2xx，无 b64 | client | `MissingB64`（沿用现状） | 是 |
| 2xx，`data` 为空 | client | `EmptyData`（沿用现状） | 是 |
| 网络 / 超时 | client | `Network` / `Timeout`（沿用现状） | 是 |

「client」一栏的错误在 `finish_generation` 错误分支被包装为 `ImageCreateError::ImageClient(message)`，`message` 加前缀「[<家> · <模型 id>] 」，同一文本写入 `generation_error` 事件。出站前的错误不写事件（沿用现状）。

两家的非 2xx 错误信封形状不同（OpenAI `{"error":{…}}`，MiniMax `{"type":"error","error":{…}}`），但现有处理是把响应体文本脱敏后整体带出、不解析信封，因此无需改动。

### 5.7 调用时序

```text
[前端] ParamsPanel 点击「生成」
  store.generate() 提交 multipart：
    prompt, size, quality, background, output_format, model, use_previous, reference?

[handler] generate_image
  parse_generate_multipart → GenerateCommand
    （model 缺省或为空 → InvalidParam「请选择图片生成模型」；上传图在此做内容校验；单张约束不变）
  engine.generate(session_id, command)

[engine] generate
  active_record() → flush_pending() → run_registry.try_reserve(Generate)
  spawn run_generation(session_id, command, cancel)

[engine] run_generation —— 步骤 1–7 在出站之前
  1. settings = settings_store.load()
  2. prompt 为空 → InvalidParam
  3. record = active_record(session_id)；last = record.generation_results 末项
     - last 只用于步骤 5 取「上一张生成图」（D7）；不再用于推导下一家
  4. target = settings.resolve_target(&command.model)
     - 只依赖设置与请求里的 model：没有首选家、没有换家；不可用即报错（D15）
  5. 确定 reference 与 reference_source（D7）
     - 上传图 > 上一张图（use_previous 且 last 存在）> 无
     - 上一张图取不到 → PreviousImageUnavailable（D8）
  6. reference 存在 → validate_reference_image
     - 上传图失败 → RefImage；上一张图失败 → PreviousImageUnavailable
  7. call_target = ImageCallTarget { vendor, base_url, api_key, model }
     - base_url / api_key 取自 settings.vendors.get(target.vendor)
  8. select! { 取消 → SessionClosing；image_client.generate(&call_target, &request, reference) }

[client] generate —— 至多一次 HTTP 调用
  validate_target → wire_fields → POST {base_url}/v1/images/{generations|edits}
  响应解析（5.6）

[engine] finish_generation
  9. 解码 → 写图片文件 → 追加 GenerationResult { …, vendor, model, reference_source }

[handler] 响应 { image_id, media_type, vendor, model, reference_source }

[前端] store 追加 generation_image 条目（含家 / 模型 / 来源标注）
```

步骤 1–7 全部在出站之前；任何一步失败都不产生费用。步骤 8 至多一次 HTTP 调用。步骤 9 的落盘顺序、`pending_results` 重试机制不变。

### 10.2 需求变更后的契约收敛（2026-11-12）

- **撤回原因**：用户 2026-11-12 撤回原需求 3（GPT ⇄ MiniMax 自动轮转），原话：「你就让用户在已配置并可用的provider里选model id就行，轮转不需要」。
- **随之删除的契约**：自动选家（原 D5）；首选家不可用时改用另一家（原 D6）；每家的轮转模型（`default_model` 及其校验、设置弹窗里的下拉）；结果与响应里的选择方式（`selection`）；生成请求 `model` 的 `auto` 保留值与「模型 id 不能为 auto」的清单校验；`ModelChoice` / `ModelSelection`。用例 T-09 至 T-12、E-01、E-04、E-05、S-11、F-14 随之删除，编号不复用。
- **新的目标解析语义**：`resolve_target(model)` 只依赖设置与请求里的 `model`——在已配置凭据且清单非空的家里按逐字符相等找归属，找到即用；id 只出现在缺凭据的家的清单里 → 配置缺失并指出该家；不在任何清单 → 参数错误；`model` 缺省即参数错误。没有首选家，没有换家（D15、5.1「目标解析语义」）。
- **内置清单顺序调整**：GPT 清单由 `gpt-image-2.6` 打头改为 `gpt-image-2.6-flare` 打头，其余 7 个保持用户给定顺序。原因：轮转取消后，模型下拉的初始选中项 = 第一个可用供应方清单的首个 id，它必须是已知可用的官方 id；若仍以裸 `gpt-image-2.6`（非 OpenAI 官方 id）打头，用户第一次点生成就会失败。

# F-60：Story／Design／Plan author 首轮合规率方案（v1.1）

## 目标、边界与判断依据

目标是让 author **每次提交候选产物时就输出完整、可通过现有 gate 的产物**；choice 回答后的「首个正式产物」也算首轮。不以失败后再调用 author 掩盖契约丢失。本次交付是设计分析，不修改运行时或 gate。

现场事实（由任务提供）：`issue_0002` 的 Story `node_003` 在 choice 回答后续跑得到 15,534 B 完整 spec，却没有 `[REQ-*]`，artifact gate 拒绝并失败。代码路径佐证：`src/product/workspace_engine/lifecycle.rs::take_pending_author_choice_prompt` 组装的回答只有问题、选择和「继续生成」（第 592–607 行）；`src/product/workspace_engine/provider_drive.rs::handle_author_choice_followup_message` 以 `DeltaOnly` 调用 `build_streaming_input`（第 24–36 行），后者将 delta 原样作为 prompt（`prompts.rs` 第 145–151 行）；完成后 gate 对所提取正文运行 `validate_workspace_artifact_constraints`，不通过则 `finish_invalid_workspace_artifact`（`provider_drive.rs` 第 711–728 行）。用户裁决：**不增加任何泛化自动重试**；plan 链 artifact gate 失败不能指望补救。已有语法解析教学重驱（F-48）和 options 确定性预检／机械回灌（C1）为不同窄类，不能把它们扩成通用兜底。本报告不提出重试方案，也不改变这些现存机制。

术语须分开：`WorkspaceType::WorkItemPlan` 的 Markdown gate 使用 `artifact_constraint_spec_for`；正式 plan 拆分另有 JSON Outline、Draft、Split 子链，分别使用 `WORK_ITEM_PLAN_OUTLINE_OUTPUT_SCHEMA`、Draft 的封闭字段合同和 `WORK_ITEM_SPLIT_OUTPUT_SCHEMA`（`src/product/workspace_engine/artifact_constraints.rs` 第 189–218 行；`src/product/work_item_split_engine/prompts.rs` 第 285–439、442–735 行）。不能把 Markdown `[TASK-*]` 合同直接附在 JSON prompt 上。当前代码中现存重试至少五类：① Claude/Codex 的 Markdown artifact 一次自动续写、Kimi/Pi 排除（`provider_drive.rs::provider_allows_artifact_retry`）；② JSON Outline 局部 AutoRevision（`plan_outline/authoring.rs`）；③ F2-B SC compile 教学重驱（`build_work_item_plan_compile_reredrive_prompt`，`single_candidate.rs` 活跃调用——即 F-48 本體，显式同名）；④ reviewer 侧 artifact retry（`review/drive.rs`，同 provider 白名单）；⑤ coding 引擎恰一次教学重驱（`coding_workspace_engine/prompts.rs`）。这些是**现存事实，不是 F-60 成功率设计前提**；若「全链禁止任何非确定性现有重试」还包括移除这五类，应作为独立范围裁决，不能由本报告擅改。已确认的是不新增兜底。

## 因素二：稳定 ID、来源追踪的教学强度

Story 初始合同列出二级 headings、`[REQ-*]`／`[AC-*]` 的具体单个 token 例子、source id 标签及 forbidden 项，但不是连贯正文示范：`artifact_constraints.rs::author_artifact_schema_contract_for` 第 310–318 行和 `append_markdown_artifact_schema_items` 第 331–363 行、`format_id_pattern_labels_with_examples` 第 387–406 行。`workspace_context/prompts.rs::output_schema_for` 第 139–142 行有 fence 与决策纪律，仍没有「一段已经合规的 Story 开头」。相比之下 Plan Outline 已有最小正确 JSON 示例，用 request 中真实 spec ID 展开；相应回归测试明确指出空 source 数组示例会被弱模型照抄（`work_item_split_engine/tests/outline_traceability_example.rs` 第 1–42 行）。

建议在**同源 Story 合同后附短正例**，显示：原始 `artifact` fence；`# … Story Spec`；`## 范围` 中引用实际 `session.issue_id`（例如当前场景 `issue_0002`）；`## 用户故事`；`## 功能需求` 的 `- [REQ-001] …`；`## 成功标准` 的 `- [AC-001] …（关联 [REQ-001]）`；`## 待确认项` 的「无待确认项」；`## 非功能需求`。说明这是格式样例、内容必须按真实 Issue 写，不得复制样例事实。选择题后另用一句「已确认的 `author-decision-*` 绑定到受影响的 `[REQ-*]`／`[AC-*]`，不要留成开放问题」。Design 的正例显示 `[DEC-001]`、`[CMP-001]`、`[API-001]`、实际 Story `source id` 与决策映射，不偷换为 Story 的 AC 合同；Markdown Plan 的正例显示 `[TASK-001]` 与实际 Story／Design 来源。正例不是 dummy 产物，不应进入 gate 输入或声称可直接粘贴。优先小样例而非全文模板，避免提示词超预算及照抄虚构需求。

Plan Outline 返修应使用 request 中实际 `story_spec_ids`／`design_spec_ids` 构造来源 ID 正例；当前初次例子的 fallback 占位 `story_spec_0001`／`design_spec_0001`（`prompts.rs::example_source_spec_id_array` 第 271–282 行）仅适合解释形状：如果未找到真实 ID，不得把占位当成真实来源教给 author；应先确认上游关联是否存在，再在 prompt 中区分占位与可用 ID。**不通过机械伪造来源骗 gate。**

## 因素三：上下文漂移与统一契约注入点

**推荐（第一优先）**：以 `artifact_constraints.rs::artifact_constraint_spec_for` 为 Markdown gate 的唯一规则源，由现有 `author_artifact_schema_contract_for` 渲染；再由同一个作者输出合同装配函数合并「fence／一级标题／内部代码块处理」「按类型 gate 正文」「choice 决策归档」「简短正例／出稿前自检」。不要新写一份与 gate 并行维护的 headings 静态字符串；所谓单一 contract 常量应是**唯一规范源及唯一装配入口**，不是把四种不同类型压成同一个文本常量。将装配置于**最终构造 `StreamingProviderInput.prompt` 的出口**，而不是在各业务分支「记得追加」：`workspace_engine/prompts.rs::build_streaming_input` 覆盖 `FullConversation` 与 `DeltaOnly`；`prompts/revision.rs::build_revision_input_with_resume` 覆盖用户反馈、reviewer delta／full、Codex fresh。所有 Story／Design／Markdown Plan 发出 prompt 前，最后一个可信合同块必须为**当前** workspace type 和 gate 版本；不能因为历史消息或用户输入中出现 `[artifact_schema_contract]` 就省略最新合同。`web/workspace_context/prompts.rs::output_schema_for` 首次 brief 仍供全量背景，不作为增量续接依赖；`prompts/author_revision.rs::build_author_revision_prompt` 保留「只修改反馈相关部分／改动摘要」，但移除其作为最终输出格式的自主定义，统一通过出口附加合同。避免旧稿 markdown 的示例地位压过当前返回格式。

顺序不变量：出口合同块必须追加在 F-58 基线教学块之后，为 prompt 最后一块；基线教学块自身无末端位置要求（F-58 报告 §3），聚合会话跳过基线教学（其两合同族末端排序见变体表聚合行裁决）。此相对顺序为不变量，防后续维护重排。

Markdown Work Item Plan 若由同一 `build_streaming_input` 出口生成就自然覆盖；若直接从 `build_work_item_plan_streaming_input` 发出，应**仅对 Markdown author invocation**调用同一个装配函数。这个函数目前同时承载 JSON Outline／Draft 的 provider 输入（`workspace_engine/prompts.rs` 第 165–189 行、`draft_batch/runs.rs` 第 258–263、311–316 行），不能无条件拼 Markdown 合同。优先让调用方传明确的产物类型／合同族，禁止从 prompt 文本猜用途。JSON 子链的最稳妥统一点是 `work_item_split_engine/prompts.rs` 的 Outline 初次／修订共用一段 strict contract＋nonce/schema＋source ID 教学；Split 初次／redo 共用 schema＋nonce＋合法 `kind` 指导；Draft 保持现有单一 `build_work_item_draft_prompt` 与 feedback 注入，不搬到 Markdown 出口。JSON nonce 必须仍按**本轮**生成，不得把旧轮 nonce 随历史复制到末端。

权衡：① **推荐：按 Markdown／Outline／Split／Draft 四个合同族统一装配，Markdown 最终出口强制覆盖**。好处是契约与解析规则可追溯、消除遗漏；成本是要梳理两个 `StreamingProviderInput` 路径、修改现有「marker 只出现一次」的测试，以及 token——出口块估算约 2–3 KB／次，FullConversation 初次 prompt 会与 brief 内 `[output_schema]` 合同双份并存；但 Draft 的 15,600 B 质量预算不约束本方案（Draft 走 JSON 子链、不过 Markdown 出口），真正该看守的是 markdown author 族（Story／Design／Work Item／Work Item Plan）——当前**无字节预算红线**，P0/P2 以 prompt／output 字节记录代替看守，膨胀超预期再立预算。② 只在 choice 拼一段 schema，代码改动小，但作者反馈分支、Plan revision、旧 system marker 仍会漏；只能作为当前正在途的临时止血，不能当 F-60 终局。③ 在 provider adapter 全局注入同一大合同可覆盖表面入口，却混淆 Markdown/JSON/Reviewer，也会把大块拼进受预算约束的 JSON 子链 prompt，拒绝。

原生同进程结构化 choice 没有新的独立 provider prompt（`provider_drive.rs` 第 224–265 行）；这个边界无法仅靠出口注入纠正中途 token 漂移，因此初轮约束放在能直接影响最终答案的位置，并在续跑 text-fallback 和每次 revision 发出当前合同。多轮 reviewer 返修、用户反馈、Outline 增量返修都按照**当前 prompt 是否自足**检验，不以历史保留为验证替代。

## 因素四：gate 前置的输出前自检

把 gate 条款转换为紧贴输出动作的**短检查清单**，不要复制内部错误码或做第二套规则。Markdown 根据 `ArtifactConstraintSpec` 派生：① 输出一个正确的 `artifact` fence 和当前类型的一级标题；② 每个必需二级 heading 都存在、禁止 heading／token 不出现；③ Story 同时含真正的 `[REQ-*]`、`[AC-*]` 和可识别的来源 ID，Design 为 `[DEC-*]`／`[CMP-*]`／`[API-*]`／来源 ID，Markdown Plan 为 `[TASK-*]`／来源 ID；④ 已确认选择记录决策和绑定，待确认项不残留未解问题；⑤ 若内容内有三反引号代码块，使用四反引号外层 fence。来源 token 的 gate 实际还接受 `issue_`／`story_spec_`／`design_spec_`／`work_item_`，不是必须逐字写 `source id`（`artifact_constraints.rs::has_explicit_source_id_traceability` 第 818–826 行）。ID 至少一个仅是 parser 下限，不能据此指导 author 给所有需求复用同一编号（`validate_workspace_artifact_constraints` 第 271–287 行）。

JSON Outline 的清单不是 Markdown headings：唯一、nonce 匹配的 sentinel 内完整 JSON；工作项真实双来源 ID 非空、用户 options 所需 kind、依赖、session fit／估算值、信任命令来源；Draft 沿用现有 `[self_check]`（`work_item_split_engine/prompts.rs` 第 699–717 行）。清单「提交前逐项自查」可能改善弱模型注意力，但**没有当前实测遵循率，不承诺百分比**。正例与清单一起做小规模 A/B 场景测量，分别观察首产物 gate 通过、缺 ID／heading／source 的分布及输出 token；如果对照无增益或占用过高，保留构造器保证而缩短教学文案。

## 因素五：反例登记、实施优先级与验收

**不做**：artifact gate 失败自动重试、扩展自动续写到 Kimi、让新 provider 代写格式、在 gate 上弱化必需 ID、静默补出虚构 `[REQ-*]`／source ID、把 Plan JSON 当 Markdown 混合提示、把 F-48／C1 窄修推广到语义失败。现有重试路径的清理如涉及行为或范围变更需另行审议，不是本设计的隐含工作包。

1. **P0：契约出口强制注入（预期增益最高、对现场直接）**。由 `workspace_engine/prompts.rs`、`prompts/revision.rs`、`prompts/author_revision.rs` 所列入口落地，同源 `artifact_constraints.rs`；修掉 choice delta 和用户反馈修订，覆盖 Story／Design／Markdown Plan。目标：每个请求的最后可信合同包含当前类型的全部 gate 必需条款，即使历史有旧 marker；不改变实际 gate 或自动调用次数。测试应调用构造的 `StreamingProviderInput`，覆盖 Full/Delta、choice 两轮、用户反馈有／无 resume、reviewer delta/full、Codex fresh、四个 Markdown 类型，不是只查某个 helper 字符串。Cutover：出口装配落地时同步删除 `lifecycle.rs` 防线 2 分支注入（stopgap `8ba23f47`）与 `author_revision.rs` Design 特例调用，避免 choice delta 叠加分支＋出口双合同块；`build_prompt` 顶部条件注入同步移除，marker 省略逻辑全废——旧逻辑下 system 旧 marker 压住新合同，正是变体表行 1／行 4 识别的漂移源。
2. **P1：Plan JSON 增量契约等价**。修改 `work_item_split_engine/prompts.rs` 中 Outline 初次／修订的共享合同渲染及真实来源教学；Split 初次／redo 共用 output contract 并补必要选项约束；Draft 仅核对既有合同和预算，不加重复 schema。测试用同一个 request 检查初次／修订／旧本地 AutoRevision 的最新 nonce、source ID、必填 schema、options 语义；Draft serial／batch 初次与反馈不丢 `[self_check]`、封闭字段及唯一 sentinel，维持已有预算。
3. **P2：正例与末端自检（增益不确定，需要测量）**。先为 Story 正例放真实 issue ID，Design／Markdown Plan 按类型置换来源，补短自检；用带 choice、没有 choice、两次 choice、native 同进程 choice、用户修订及 Plan outline revision 的**首份正式产物**跑真实 provider／stage 环境（native choice 场景零出口注入点，不测则该面零证据）。测量按 `cadence/designs/2026-07-24_技术方案_WorkItemDraftPrompt测试基线_v1.0.md` 协议实例化：每场景每臂 ≥10 个有效首份正式产物，`provider_inconclusive` 不耗样本，超时计上限，10/10 pass 才可声称 ≥95%；对照臂为 P0 出口注入但无正例／自检。记录 gate 的 `blocking_reasons` 分布、产物是否实际进入 AuthorConfirm、prompt／output 字节；并**必须加测照抄／伪造信号**——正例带真实 issue id 后被弱模型照抄时机械 gate 反而通过（REQ／heading／source id 俱全，`outline_traceability_example.rs` 的 Bug A 即既有实证），只测 gate 通过率会得假阳性结论，故加对照指标：产物与正例文本相似度抽样、reviewer must_fix 率、需求内容与 issue 事实的抽样核对。不以「测试了 prompt 包含字符串」代替行为测量。若运行环境无法访问 Kimi，标为未测，不声称已提高通过率。

实施者可使用当前覆盖基础：`workspace_engine/tests/part_31.rs::initial_author_prompts_render_parser_derived_schema` 第 184–231 行和 `retry_and_revision_prompts_render_parser_derived_schema` 第 285–352 行已核对通用初次／reviewer／旧 retry，但**没有** choice delta 或用户反馈；`workspace_engine/tests/part_31.rs::full_revision_prompt_does_not_repeat_schema_from_generation_context` 第 354–398 行固定「marker 出现一次」，应调整为「末端最新合同正确」，避免修复受旧测试误拦。Plan Outline 正例真实 ID 的已有行为测试见 `work_item_split_engine/tests/outline_traceability_example.rs` 第 7–42 行。设计完成的验收是这张变体表对应的入口全部有明确合同族和可执行检查，且任何新入口无法在构造 `StreamingProviderInput` 时意外绕过；运行时首轮成功率须按上述现场复测才可声称改善。

# 技术方案：规划三环节评审纠偏（story / design / work item）

> 性质：方案（owner 2026-10-22 确认方向后编写）。**范围仅 story / design / work item**；coding 环节不在此批。
> 原则（owner 明确）：**不过度设计；先打通整体功能；先解决阻断问题与理念问题；其余后续打磨。**

## 一、目标（一句话）

让三个规划环节的 author 与 reviewer 都在"**issue 选定的真实仓库集合**"上工作——**没有主仓/主成员概念**，评审能看到集合内每个仓的真实情况，且不再为此承担多余的窗口/对账/恢复开销。

## 二、标准依据

`cadence/designs/2026-10-22_技术方案_系统环节与角色标准_v1.0.md`：
- 5 环节；issue 环节产出 = issue + 用户选定的真实仓库集合（**1~N，无主次**）
- story / design / work item 的 author 产出 spec/plan，reviewer 审核并给修改意见，用户定稿
- 三环节产出**全部落在 aria 规划目录**，不落 lc 仓/真实仓库 → **不需要零锁恢复**
- work item plan 产出多个 work item，每个 work item 只对应一个真实仓库；coder 只在单仓工作

## 四、设计要点（避免踩空）

1. **删窗不是删纪律**：`ReviewerVerify`（全工具无 deny）保持，只是铸造来源从"活动窗口 id"改成"会话 id"；provider 启动校验不受影响。
2. **材料注入只改一处**：把清单/实况从"消息末尾追加"改为"放进 `[canonical_inputs]`"，同时解决 reviewer 不可见 + 压缩丢失 + author 可见三件事。
3. **不新增存储**：不引入新账本、新窗口类型、新 schema 字段；删除为主、注入为辅。
4. **失败语义保持 fail-closed**：集合解析失败、清单超预算、仓库不可解析 → 明确错误码，不带病评审。
5. **coding 侧零改动**（`code_review.rs` / `internal_pr_review.rs` / 其窗口与对账保持原样）。

## 五、验收（S1 完成即可跑通端到端）

1. 建一个 issue 选择 **2 个**真实仓库 → story / design / work item 三个环节的 author 与 reviewer 的 prompt 中都出现这 2 个仓的清单与逐仓实况；**不出现任何"主仓/主成员/primary"字样**。
2. 三环节评审**不再产生审查窗口记录**（`reviewer-windows/windows/` 下无新增）；不再出现 `primary-member anchored` 事件；不再有 `plan_review_window_*` 错误码。
3. 评审仍能正常启动（`ReviewerVerify` 策略生效，四家 provider 均可）。
4. 长会话（>2 轮）后评审仍能看到清单与实况（`[canonical_inputs]` 原文重放）。
5. 清单超预算 → 明确阻断，不静默省略。
6. 存量 issue（单仓、无 LC）行为不变。

## 六、不做（防范围回流）

- 不做多成员对账域、集合屏障、报告成员分节、ZeroWrite 分档、根域 guard（已作废）。
- 不做 coding 侧写面收口/域外写检测（独立立项）。
- 不做 issue 模型多值化改造（集合表达复用现有 selection）。
- 不改前端组件（仅当 WS 字段变化时做必要兼容）。

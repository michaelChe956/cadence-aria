# 技术方案：WIG 三缺陷与多仓事实供给修复

> 日期：2026-11-11 · 分支 `feat-wig-optimize-11-08` · 状态：**待 owner 批准**

> 本文是《问题简报_WIG三缺陷待修_v1.0》《调研_WIG三缺陷的业界做法_v1.0》及三路 design-task 设计的**合并裁决版**。

## 一、意图与背景

### 1.1 要解决什么

WIG（work item plan 生成）链路当前有三个用户可见缺陷：

| 编号 | 用户表述 | 分析后定性 |
|---|---|---|
| ① | 生成很慢；5–10 分钟才有 token 输出；reviewer 反复失败直到自动化耗尽人工介入 | **不是独立缺陷**，是 ②③ 的端到端结果。实测天花板 55% |
| ② | 容易出现 IR 校验失败（`unknown_requirement_ref` / `acceptance_criterion_without_reviewer_check`）教学重驱，重驱后仍失败 | **信息丢弃缺陷**：诊断对象带修复锚点，被格式化函数丢掉了 |
| ③ | 计划容易 reviewer 失败→重生成→再失败，重复多次 | **概念塌缩缺陷**：三个不同语义被压进 `class_hint` 一个字段 |

另在分析中发现**第四个缺陷（路径域打架）**：同一 prompt 内事实面与纪律面使用不同路径域（见 §5.4）。

### 1.2 为什么要现在

用户诉求是「更准确 / 更省 token / 优化生成与评审 prompt」。分析结论是：**在不加重试次数、不加模型调用、不放宽写权限的前提下，这三件都能做**；而所有收益都被 ②③ 挡住——45% 的 run 在「文件事实」起作用之前就死了，先修文件事实供给对产出率的期望贡献 ≈ 0。

### 1.3 owner 已裁决的三项（2026-11-11）

| 决策点 | 裁决 |
|---|---|
| 闭合资格修到哪一层 | **E 兼容双向资格门**（不修订方案 E / REQ-WSC-17） |
| 多仓基线分支语义 | **一律走逐仓 HEAD 分支**（`resolve_member_head_branch`），登记「`issue.base_branch` 在多仓会话被忽略」这一既有语义变更 |
| 问题① 的验收判据 | **48 run 预算不变**（owner 2026-11-11）。⚠️ 原裁决的「n=24/臂 ⇒ confirmed 率 power≥0.80」建立在**错误的功效算术**上（独立复算：power≈0.33）⇒ 判据框架按 §4.2/§7.2 修正为：**配对设计 + per-run 连续指标为主判据**（dz=0.5 时 power≈0.78）、confirmed 率降为方向性、重复报率作机制判据。**该框架修正是本方案的工程判断**，非 owner 原裁决内容 |

## 二、目标 / 非目标 / 反目标

### 2.1 目标

1. 教学重驱时，作者能看到**「缺哪个字段、应补什么」**的完整修复锚点，而不是泛句。
2. 普通建议**不再因为模型自报 `class_hint`** 进入必关闭集合；真实契约缺口**不漏闭合**。
3. 作者与校验器看到的**基线事实覆盖全部已授权成员仓**，且与写范围纪律**同域**。
4. 问题① 的收益用**预先声明的统计判据**测量，不靠事后叙事。

### 2.2 非目标

- 不增加任何一次模型调用或重试次数（作者轮物理启动次数不变）。
- 不放宽写范围校验（`/tmp/**` 仍然 Error）。
- 不新增运行期开关（env 开关面维持零新增）。
- 不新增计划期执行脚本 / 容器启动 / shell 静态分析器。
- 不改「不改写原生人工结论」（`REQ-TOP-01`）：`routing.rs:531-548` 的 `NativeHumanRequired` 旁路本次不动。

### 2.3 反目标（做到即算失败）

- 让作者轮**自主检索**仓库以替代事实供给（实测 77 节点中 **59 个零工具调用**，不可靠）。
- 用**模型自报的 severity / category** 直接决定阻断。
- **提高固定面预算**（23,500 B）或上下文面预算（32,000 B）。
- **抬 `large_file_guard` 登记上限**来消除超限（必须靠拆分）。
- 把普通建议**全部**降级为不阻断（违反方案 E）。

## 四、事实基础（全部实测或源码直读）

### 4.1 端到端漏斗（改后 20 run）

```text
confirmed 6 / stopped 4 / failed 10     → 早死 9 = 45%
走到评审的 11 个里 confirmed 6          → 55% 天花板
```

⇒ **45% 的 run 在文件事实起作用前就死了**。

### 4.2 统计功效与语料事实（**本节已按独立复算更正**）

#### 观测值（累积窗口 n=35）

| 臂 | 有效 run | confirmed | 走到第二轮评审 | 出现重复报 |
|---|---|---|---|---|
| 改前 | 15 | 4（**26.7%**） | 9 | **8（89%）** |
| 改后 | 20 | 6（**30.0%**） | 11 | **0（0%）** |

**重复报率**：单尾 Fisher p = **0.00131** ⇒ **已显著**（机制级判据，D6 切断重复报链条）。
**confirmed 率**：26.7% → 30.0% ⇒ **不显著**（`[[4,11],[6,14]]`）。

> ⚠️ **p 值口径更正**（此前分析报告的算术有误，须在后续文档中更正）：报告的 p=0.179 来自 `[[6,9],[4,16]]`（**分母互换**）；正确边际表是 `[[4,11],[6,14]]`（改前 4/15、改后 6/20）⇒ **p=0.567**。报告的 p=0.00131 来自 `[[0,9],[8,3]]`；正确表是 `[[8,1],[0,11]]` ⇒ **p=7.1e-05**。
> ⇒ **结论方向不翻转**（重复报仍显著、confirmed 仍不显著），但**算术须用正确表**。本节所有 p 值与 power 均由独立复算交叉验证（`[[8,1],[0,11]]` 复算得 7.0e-05，与文档 7.1e-05 吻合 ⇒ 口径一致）。

#### 语料事实（**决定 ① 的验收能回答什么问题**）

实测装置是「**同一案例、同一装置**」——**单个 issue 反复跑**，不是 N 个不同 issue：

- 批次 ⑤⑥ 干净对照：改前 4 run + 改后 4 run，**同一时段严格交错**；
- 累计：改前 15 run、改后 20 run，跨 4 个时段窗口（22:00 / 12:00–15:30 / 15:32– / 01:36–06:24）。

⇒ **两个直接后果**：

1. **Fisher 的独立性假设不成立**（同一 issue 的固有难度、同一份 story/design、同一批成员仓在各 run 间共享）⇒ 对 confirmed 率做「总体产出率」推断**方法上不成立**。
2. **但它恰好回答了我们要问的问题**：单 issue 重复采样测的是「**同一 issue 的重掷成功率**」——而 ②③ 的机制目标正是「让同一份计划更可能一次通过、让重驱更可能成功」。⇒ **主判据应落在 per-run 的连续/计数指标上**，confirmed 率降为「同一 issue 重掷成功率」的方向性指标。

#### 功效复算（30% → 55%，α=0.05）

**独立两臂（Fisher 双侧）**：

| n/臂 | 总 run | power |
|---|---|---|
| 8 | 16 | 0.09 |
| 16 | 32 | 0.18 |
| **24** | **48** | **0.33** |
| 32 | 64 | 0.45 |
| 48 | 96 | 0.63 |
| 56 | 112 | 0.70 |
| **80** | **160** | **0.86** |

**配对两臂（同 issue 前后各跑一次，McNemar 精确检验）**：n=24 对 power ≈ **0.43**；n=40 对 ≈ 0.74。

⇒ **⚠️ 更正（builder check 发现，已独立复算确认）**：此前文档的「n=24/臂 ⇒ power≥0.80」是**算错的**（与同一节里被更正的 p 值算术属同类错误）。**30%→55% 无论独立还是配对，要达 power≥0.80 都需要 ~96–160 run 量级。**
⇒ 而 **n=8/臂 只在产出率 ≥80% 时才有功效，天花板是 55% ⇒ 8/臂永远无法对 confirmed 率给出显著性**（这一点不变）。

**连续指标（配对 t 检验，每 issue 前后各跑一次）——样本效率高得多**：

| n 对 | dz=0.3 | dz=0.4 | dz=0.5 | dz=0.6 |
|---|---|---|---|---|
| 16 | 0.32 | 0.47 | 0.63 | 0.76 |
| **24** | 0.42 | 0.61 | **0.78** | 0.90 |
| 32 | 0.51 | 0.72 | 0.87 | 0.96 |
| 40 | 0.59 | **0.80** | 0.93 | 0.98 |

⇒ **48 run（24 对）配对设计下，per-run 连续指标在 dz=0.5 时 power≈0.78、dz=0.6 时≈0.90** ⇒ **用户诉求 #2「消耗的 token 更少」与 #1「更准确」对应的正是这些连续终点，它们在既有 48 run 预算内可判**。

### 4.4 ③ 的根因（源码直读复核）

```text
classify_finding()                          work_item_plan_policy/classify.rs:129-159
  if !finding.is_actionable()  ⇒ Advisory
  else ⇒ finding.class_hint.map(class_for_hint)      ← 直接采信模型自报
  severity 仅在 153 行作字符串保留，不参与该分支

fallback_class()                             classify.rs:169-185
  Revise + category∈{ContractGap,SelfContradiction} + contract_field 非空 ⇒ Repairable
  ↑ 不查服务端修复许可；contract_field 本身是模型给的定位字符串
```

**概念塌缩**：

```text
可由本 WI 处理（disposition） ≠ 必须关闭（闭合义务） ≠ 能自动修复（修复许可）
```

**字段来源与可信度**：

| 字段 | 来源 | 能否作权威严重度 / 修复许可 |
|---|---|---|
| reviewer `severity` | 模型自报（`parsers.rs:719-727`） | 否 |
| reviewer `class_hint` | 模型自报（`parsers.rs:735-738`） | **否，且不得授予闭合资格** |
| reviewer `category` | 模型自报（`parsers.rs:731-734`） | 否；白名单只能限制标签作用范围 |
| 平台 disposition 硬化 | 平台规则（`review.rs:187-196`） | 是确定性政策，但类别输入来自模型 |
| owner 显式排除 | durable owner 事实（`disposition_override.rs:43-65`） | 优先于后续闭合判定，不得复活 |
| 机械 finding severity | 编译器/校验器（`plan_preflight.rs:272-318`） | 是平台判定；仍 ≠ 修复许可 |
| `machine_repair` | 服务端配对（raw 解析恒 `None`，`parsers.rs:740-742`） | 可作许可链投影，**必须验证绑定** |

**「必关闭」在两处解释不一致**（这是 ③ 的第二根因）：

```text
控制面：evaluate.rs::actionable_findings (399-406) 只剔除 class == Advisory
呈现面：history_compaction.rs::render_open_required_findings (85-122)
        只认 RequiresRevision + actionable + blocking/must_fix
```

⇒ 同一条 suggestion 可能**没进提示词里的必关闭清单，却通过 class 进入控制面并升人工**。

**归属裁决**：**补 `close-contract-findings-before-pass`，不替代它，不夹进 `rework-prompt-input-surface`**（后者继续独占 REQ-WSC-06，只负责提示词供给/装配）。close 现有设计有两处缺口需修订：D6 承诺普通 suggestion 不阻断，但 D4「闭合资格假时维持既有行为」会继续采信 repairable hint；D1 认强档 severity 的闭合资格，但 D4 对非契约类强 finding 维持旧 hint 行为 ⇒ 七面再次分叉。

### 4.8 业界依据（调研，链接见调研简报）

| 方向 | 结论 | 适用边界 |
|---|---|---|
| 严重度/阻断 | rustc / ESLint / Semgrep / reviewdog `fail_level` / SonarQube Quality Gate / CodeRabbit / SARIF `level` **全部两轴分离，无一个让模型自报级别直接当门禁** | 支持「分轴」，**不证明模型 severity/category 可信** |
| 结构化输出修复 | TypeChat `_max_repair_attempts=1`；Instructor `max_retries` + 终态 `InstructorRetryException` 携带**完整修复包**；Pydantic AI 8 层重试 + `RetryFeedbackPart` 留史；Guardrails per-validator `on_fail` 动作阶梯 | 预算 1–3 次 ⇒ 本项目保持 2 次 |

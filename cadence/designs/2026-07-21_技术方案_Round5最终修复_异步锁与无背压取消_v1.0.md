# Round 5 最终修复：异步文件锁与无背压 Runner 取消

## 目标

- 恢复 Group Attempt 在 Issue Worktree 已绑定、journal 尚未推进 `WorktreeBound` 时的精确幂等 replay。
- 禁止 Single Attempt 替未完成 Group initialization journal 修复或绑定 lease。
- HTTP 与 WebSocket Abort/Delete 不依赖 command channel 或 outbound event channel 的可写性，能够先取消 runner task、等待 RAII remove，再执行 durable 终态或删除。
- 所有 async handler 的跨进程文件锁等待不占用 Tokio worker；guard 仍可跨 `.await` 持有以保持线性化。
- `WorkItemAttemptCreationGuard` 同时绑定业务 identity、canonical Store root 与 canonical lock path，跨 Store root 误用 fail-closed。

## Finding 核验

### Group bind-before-phase

Group 当前依次执行 Attempt/provider 持久化、journal=`AttemptPersisted`、Issue Worktree bind、journal=`WorktreeBound`。bind 与 journal advance 分属不同 Store，无法原子提交；进程在两者之间退出后，lease owner 已是 journal Attempt，但 replay 仍看到 `AttemptPersisted`，现有 `replay_already_bound` 条件会永久拒绝。

Single 的 active Attempt 恢复逻辑当前不区分 scope，会对 active Group Attempt 调用 `bind_issue_worktree_lock_to_attempt`，同样可制造 `AttemptPersisted + owner=journal Attempt`。

### HTTP Abort/Delete backpressure

Registry Abort 当前向 command channel 执行 async `send` 并等待 completion。真实 runner 若阻塞在满 outbound channel、pending socket writer 或 provider wait，无法读取 command，也无法 Drop registration guard；HTTP Abort/Delete 因而无界等待。

### 阻塞文件锁

`ExclusiveFileLock::acquire` 使用阻塞 `flock(LOCK_EX)`。Single create、Group create/replay 和 Group Delete 从 async handler 直接调用同步入口，竞争者会占住 Tokio worker；当竞争者数量达到 worker 数时，持锁请求的 continuation 也无法恢复。

## 方案选择

### 1. Registry-owned CancellationToken

采用 registry entry 持 `CancellationToken`，不采用 task `AbortHandle`：

- production registration 在 registry mutex 内同时分配 run ID 与 token，再返回 `(run_id, token)`；token 在 runner 可能阻塞前已经 attach，不存在 spawn 后 attach race。
- reservation activation 同样原子创建 token并写入 entry。
- runner future 首行创建 RAII registration guard，随后用外层 `tokio::select!` 竞争 `token.cancelled()` 与完整业务 future；取消会 drop 当前 event send、provider wait、gate wait 或其他 async future。
- `CodingWorkspaceEngine` 持 parent token，provider stream 每次尝试使用 `child_token()`；HTTP/WS 取消 parent 时，provider adapter/process 也收到 cancellation，而不是仅遗留后台 provider task。
- registry Abort 先同步快照并 cancel 所有 production token，再用无等待的 `try_send(AbortAttempt)` 兼容旧测试注册，最后只等待 completion watch。command channel 不再承担生产 Abort 必达语义。

HTTP/WS handler 在 runner completion 后取得 Attempt mutation lease并执行 durable `handle_abort`；Delete 在 completion 后执行既有 cleanup/delete。runner task 取消本身不写 Attempt 终态，不承担 journal 补偿。

未采用 `AbortHandle`：它需要 spawn 后 attach，必须额外处理 attach race，而且不能自然向 provider child token 传播取消。未采用逐个 send/wait 增加 cancellation select：调用点多且容易遗漏。

### 2. Async-safe flock acquisition

新增 `ExclusiveFileLock::acquire_async`：克隆 target path，通过 `tokio::task::spawn_blocking` 调用现有同步 `acquire`，将 join failure 映射为 `ProductStoreError::Io`。锁持有仍由 `ExclusiveFileLock` 的 File/Drop 管理。

Store 提供：

- `acquire_work_item_attempt_creation_async`；
- `acquire_group_initialization_arbitration_async`。

Single create、Group create/replay、Group Delete 全部改用 async 入口。同步 `create_attempt` 与同步 acquire 继续服务纯同步 Store API 和现有单元测试。

未采用 `LOCK_NB + sleep`：它会引入轮询间隔、公平性与 Unix/非 Unix 双实现复杂度；`spawn_blocking` 可直接复用已验证的 flock 语义。

### 3. Group bind replay

新增 `BoundBeforePhaseAdvance` checkpoint，触发点严格位于 `bind_issue_worktree_lock_to_attempt` 成功之后、journal advance `WorktreeBound` 之前。

当 `try_acquire_issue_worktree_lock` 返回 `acquired=false` 且 owner 精确等于 journal Attempt 时，只在以下条件同时成立时接受：

1. journal phase 已达到 `AttemptPersisted`；
2. 磁盘 Attempt 文件存在且与 journal Attempt 完全相等；
3. 磁盘 provider config 存在且与 journal provider config 完全相等；
4. 当前 active Attempt 唯一且 ID 为 journal Attempt；
5. 当前请求加载的 journal immutable identity 与磁盘 journal 完全相等。

该路径只读验证，不补写缺失 Attempt/provider。验证通过后既有 bind 为同 owner 幂等，随后 contiguous advance 到 `WorktreeBound`。

Single 遇任何 active `WorkItemGroup` scope Attempt时只返回稳定 `coding_attempt_active` conflict，不调用 Lifecycle bind；Group journal 只能由 Group replay 推进。

### 4. Guard canonical identity

`ExclusiveFileLock` 保存成功打开后的 canonical lock path。`WorkItemAttemptCreationGuard` 保存：

- project/issue/work-item ID；
- canonical `ProductAppPaths::root()`；
- canonical final lock path。

guard-aware API 由当前 `CodingAttemptStore` 重新计算 canonical root 与 lock path并比较；任一不同返回 `work_item_attempt_creation_guard` identity mismatch。由于 lock acquisition 已创建 parent 与 lock file，canonicalization 不需要猜测不存在路径。

## Durable 状态语义

- HTTP/WS Abort：runner 停止并 remove 后，handler 才执行 `handle_abort`。成功响应要求 Attempt=`Aborted`、活动 timeline 收口、Issue Worktree lease 释放。
- Delete：runner 停止后再执行 mutation/init arbitration、workspace cleanup 与 Attempt/journal 目录删除。
- Plan Amendment delivery 已入队但未完成 socket write时，取消不得伪造 `Delivered`。Abort 后 marker 保持 `Pending`，用于审计/恢复；Delete 后 marker随 Attempt 目录删除。
- runner panic 依赖 RAII remove；closed command receiver 依赖 registry 的 closed 检测 remove；两者均不得阻塞 HTTP durable handler。

## 锁序

创建：named async guard（Group）→ Group initialization async file guard → Work Item creation async file guard → Lifecycle Issue Worktree file RMW。

终止：cancel runner tokens → 等待 RAII completion → Attempt mutation lease → Group initialization async file guard（Delete only）→ Lifecycle/Git/store cleanup。

`spawn_blocking` 只负责等待/取得 file guard；持锁业务仍在 async task 中执行。没有路径在持 Lifecycle 锁后反向获取 creation/group guard，也没有 registry mutex 跨 `.await`。

## 测试矩阵

- Group `BoundBeforePhaseAdvance` 新 router/new Store replay：同 Attempt 恢复到 Completed，lease owner不变。
- Group `PersistedBeforeBind` 后 Single 请求：Single typed conflict且 lease仍为 journal temporary ID；随后 Group retry成功绑定自身 Attempt。
- current-thread async lock：holder 由独立线程延迟释放，Tokio heartbeat必须在释放前运行。
- 2-worker runtime + 8 contenders：heartbeat不被 flock contender饿死，释放后全部顺序取得 guard。
- root A guard用于 root B guard-aware create：identity mismatch，root B零写。
- 真实 HTTP Abort：runner 阻塞于满 event queue/pending writer时有界返回，Attempt Aborted、lease释放、delivery marker不为 Delivered。
- 真实 HTTP Delete：相同 backpressure 下有界返回，Attempt/journal/delivery目录与 lease全部清除。
- runner panic与 closed receiver：HTTP Abort/Delete 有界完成，registry count=0，durable状态与 lease一致。
- `src/web/app.rs` 保持无 diff；TestControls seam 默认关闭且无新增 HTTP route。

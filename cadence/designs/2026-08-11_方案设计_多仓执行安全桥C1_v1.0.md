## 2. 背景与目标

### 2.1 背景

阶段 B 让多仓库 issue 能走完整 AI 规划链路（Story 跨仓生成 → Design 带 change_order → WorkItem 按 target 拆分），产出了带 `target_repository_id` 的 WorkItem。但 coding 执行层仍是单仓模型：

- `CodingExecutionAttempt.target_snapshot` 字段已定义（三层身份 logical/checkout/physical + revision + policy_digest + membership_revision），但**所有创建点硬编码 `None`**（`coding_attempt_store/attempt.rs:91`、`group.rs:165`、`group_initialization.rs:465`）
- `CreateCodingAttemptInput` / `CreateGroupCodingAttemptInput` **没有 target 字段**，创建时调用方根本没传 target
- shared worktree 存储仍是单 issue 份（`issue-shared-worktree.json`，二元 `(project, issue)`），`upsert` 时 `target_repository_id` 硬编码 `None`
- group 创建校验（`group_initialization.rs:524 validate_group_initialization_input`）**不检查 target 一致性**，mixed-target group 不会被拒绝

结论：B 产出的 target 在 coding 层被丢弃，多仓 issue 实际无法在各自目标仓隔离 coding。

### 2.2 目标

让多仓库 issue 的每个 WorkItem 在**各自目标仓的独立 worktree** 真正 coding 且安全隔离：

1. **attempt 冻结 target 快照**（REQ-COD-02）：创建即冻结三层身份 + revision + policy_digest，恢复/重放一律用快照，缺失或漂移 fail-closed
2. **shared worktree 三元键**（REQ-COD-03）：多仓 issue 每个目标仓一份独立 worktree，`(project, issue, repository)` 定位，异仓并行、同仓串行
3. **mixed-target group 拒绝**（REQ-COD-04）：创建/恢复/replay 三处一致拒绝，稳定错误码
4. **单目标仓 worktree 执行**（REQ-COD-01）：Cadence 显式建目标仓 worktree + cwd 钉死，主 checkout 不动
5. **WP5a 收尾**：核实并补全 validator/runtime 层 target 完整性校验（attempt 创建/恢复时校验 target 快照一致性）

### 2.3 成功标准

- 多仓库 issue 的每个 WorkItem 启动 coding 时：在正确目标仓创建独立 worktree（主 checkout 不动），attempt 持有完整 target 快照
- 同仓多 WorkItem 复用同一仓库级 shared worktree（串行）；异仓 WorkItem 各自 worktree（并行）
- mixed-target group 在创建/恢复/replay 三处被一致拒绝，返回 `mixed_target_group_rejected`
- attempt 恢复/重放时校验快照 membership_revision/revision 一致，漂移则 fail-closed
- **单仓红线**：单仓 issue（`logical_codebase_ref=None`）的 coding 行为完全不变（attempt 无快照、shared worktree 走老路径、不查 target 一致性）

| 7 | 恢复/重放语义 | attempt 有快照→校验 membership_revision/revision 一致才放行（漂移 fail-closed 或人工恢复）；无快照+单仓→legacy 路径 | design.md REQ-COD-02 scenario 要求 |

## 4. 方案设计

### 4.1 REQ-COD-02：attempt target 快照冻结（方案①：创建时同步冻结）

**改造点**：

1. **`coding_attempt_store/inputs.rs`**：`CreateCodingAttemptInput` + `CreateGroupCodingAttemptInput` 加字段
   ```rust
   pub target_snapshot: Option<AttemptTargetSnapshot>,  // None=单仓(legacy)；Some=多仓冻结快照
   ```

2. **`coding_attempt_store/attempt.rs:91` + `group.rs:165` + `group_initialization.rs:465`**：3 个创建点把 `target_snapshot: None` 改为 `target_snapshot: input.target_snapshot`

3. **web handler 层（`web/handlers/coding.rs:147` + `coding/group.rs:141`）**：这两个点已有 `RepositoryRouting` 三态分流（B 阶段做的）。多仓（Logical）分支新增：解析 confirmed design 的 target → `PlanningContextResolver` 解析三层身份（`logical_repository_id`/`checkout_id`/`physical_repository_id`）+ 读当前 revision + policy_digest + membership_revision → 组装 `AttemptTargetSnapshot` → 塞进 input。单仓（Legacy）分支：`target_snapshot=None`（不变）。

4. **恢复/重放校验**（新逻辑，product 层）：`CodingAttemptStore` 的恢复/replay 入口加 `validate_target_snapshot_consistency`：
   - 有快照（多仓）：重读当前 membership revision / 目标仓 revision，与快照比对。`membership_revision` 不一致 → 成员表已变（成员被删/停用），fail-closed `target_snapshot_membership_drifted`；`revision` 不一致 → 仓已推进，fail-closed `target_snapshot_revision_drifted`（**统一 fail-closed**，人工恢复入口不在 C-1 实现，记为后续演进）
   - 无快照（单仓）：跳过，走 legacy 恢复路径

**AttemptTargetSnapshot 复用现有结构**（`coding_models/execution.rs:91`，无需改字段）：
`logical_repository_id` / `checkout_id` / `physical_repository_id` / `canonical_path` / `git_dir_identity` / `revision` / `policy_digest` / `membership_revision` / `captured_at` / `capture_source`。

### 4.2 REQ-COD-03：shared worktree 三元键（单仓老路径 + 多仓新路径，无迁移）

**改造点**：

1. **`lifecycle_store/paths.rs`**：新增多仓路径方法
   ```rust
   pub(crate) fn repo_shared_worktree_path(
       &self, project_id: &str, issue_id: &str, repository_id: &LogicalRepositoryId,
   ) -> PathBuf {
       self.issue_lifecycle_root(project_id, issue_id)
           .join("shared-worktrees")
           .join(format!("{repository_id}.json"))  // LogicalRepositoryId 的 Display
   }
   ```
   （老方法 `issue_shared_worktree_path` 保留，单仓继续用）

2. **`lifecycle_store/worktree.rs`**：新增多仓版本方法（与老方法并列，不替换）：
   - `upsert_repo_shared_worktree(input)` —— input 含 `repository_id: LogicalRepositoryId`
   - `get_repo_shared_worktree(project, issue, repository_id)`
   - `delete_repo_shared_worktree(project, issue, repository_id)`
   - `try_acquire_repo_worktree_lock(project, issue, repository_id, work_item_id, lease_id)` —— 仓维锁
   - `release_*` / `validate_*` / `mark_*` 系列对应多仓版本
   - 锁文件同址：`shared-worktrees/{repository_id}.json.lock`

3. **web handler / gates 层（`coding_workspace_engine/gates.rs`）**：10+ 个 `*_issue_shared_worktree_*` 方法按 attempt 的 `target_snapshot` 分流（attempt 已存在，用 `target_snapshot` 是否 Some 判定最直接，无需再 load routing）：
   - 有快照（多仓 Logical）：调新方法（`repo_shared_worktree_path`，带 repository_id；repository_id 取自 attempt.target_snapshot.logical_repository_id）
   - 无快照（单仓 Legacy）：调老方法（`issue_shared_worktree_path`，二元，不变）

4. **`IssueSharedWorktree` record 复用**（`models/lifecycle.rs:215`，已有 `target_repository_id`/`checkout_id` 字段）：多仓版本 upsert 时填 `target_repository_id=Some(...)`；单仓保持 None。

**不做**（因无历史数据）：迁移 journal、redirect/tombstone、延迟清理、F-6 锁顺序协议、旧文件兼容读取。多仓路径首次访问文件不存在即新建（无旧文件可迁）。

### 4.3 REQ-COD-04：mixed-target group 拒绝（方案 A：三处一致）

**改造点**（3 处一致校验，复用同一校验函数 `validate_group_single_target`）：

1. **创建处**（`group_initialization.rs:524 validate_group_initialization_input`）：遍历 `unit_bindings`，校验所有非 None 的 `target_repository_id` 必须相同；出现 ≥2 个不同 target → 返回稳定码 `mixed_target_group_rejected`。单仓（全 None）跳过。
2. **恢复处**（`group_validation.rs:251 validate_group_attempt_integrity`）：同校验，防数据被篡改。
3. **replay 处**：group replay/重放入口同校验。

**稳定错误码**：`mixed_target_group_rejected` → error.rs 映射 **422 UNPROCESSABLE_ENTITY**（语义"输入结构上无法处理"，与既有 routing 错误码惯例对齐——writing-plans 阶段核实 error.rs 既有 mixed/structural 错误的 HTTP 惯例，若有出入则对齐到项目惯例）。

**同 target group 放行**：所有 item 同一 `target_repository_id` → 正常创建。

### 4.4 REQ-COD-01：单目标仓 worktree 执行（核实 + 补全）

**现状**：`git worktree add` + cwd 钉死的能力部分已有（单仓 coding 一直在用）。C-1 的工作是把多仓路径接通（依赖 4.2 的三元键 worktree）：

- 多仓 WorkItem 启动 coding 时：经 routing 判定目标仓 → 在**目标仓的 checkout 路径**下 `.worktrees/aria-issues/{issue}` 建 worktree（与单仓一致的相对结构，但在正确仓库下）→ provider cwd 钉死到该 worktree
- 主 checkout 不动（HEAD + 工作区）：多仓下每个成员仓的主 checkout 都不动，只在各自 worktree 改

**越界检测**（best-effort，不宣称 OS 级）：pre/post 检测 provider 是否越出 worktree 写主 checkout 或他仓；标记并阻断，但不宣称硬隔离（OS sandbox 后置，属 C-2/未来）。

### 4.5 WP5a 收尾（validator/runtime target 完整性）

核实并补全：
- compile 路径（`compile_support.rs`）已正确分流（单仓单一 repository_id 回退 / 多仓 per-item target），**不是缺陷**，保留
- 补：attempt 创建/恢复时（4.1 的恢复校验）即覆盖 runtime 层 target 完整性校验
- 补：validator 层对多仓 WorkItem 的 target 非空校验（与 4.3 配合，target 缺失即 blocker，已有 `work_item_target_missing` 码，保留）

## 6. 数据流（单仓 vs 多仓对比）

### 单仓 issue（现状不变）

```
coding 启动 → routing=Legacy → CreateCodingAttemptInput{target_snapshot:None}
→ attempt.target_snapshot=None → shared worktree: issue-shared-worktree.json (二元)
→ 恢复: 无快照校验, legacy 路径 → group: 全 None target, 跳过 mixed 校验
```

### 多仓 issue（C-1 接通后）

```
coding 启动 → routing=Logical → handler 解析 confirmed design target
→ PlanningContextResolver 三层身份 + revision + policy_digest + membership_revision
→ 组装 AttemptTargetSnapshot → CreateCodingAttemptInput{target_snapshot:Some(...)}
→ attempt.target_snapshot=Some → 落盘冻结
→ shared worktree: shared-worktrees/{repository_id}.json (三元), 仓维锁
→ 恢复: 校验 membership_revision/revision 一致, 漂移 fail-closed
→ group: 校验全 item 同 target, mixed → mixed_target_group_rejected
→ worktree: 目标仓 .worktrees/aria-issues/{issue}, cwd 钉死, 主 checkout 不动
```

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 单仓红线被破坏（shared worktree 双路径分流失误） | 所有分流基于 `target_snapshot` 是否 Some；单仓全程 None；单仓 coding 全量测试守护 |
| attempt 快照三层身份解析错误（checkout_id/physical_id 映射错） | 复用 `PlanningContextResolver`（B 已验证）；补三层身份一致性 unit test |
| mixed-target 拒绝在 3 处不一致（漏一处） | 抽公共 `validate_group_single_target` 函数，3 处调用同一函数；集成测试覆盖 3 个入口 |
| 多仓 worktree 路径与单仓混淆（同一 issue 既有多仓新文件又有单仓老文件） | routing 三态互斥（一个 issue 要么 Legacy 要么 Logical，不会同时）；多仓路径首次访问不存在即新建 |
| target 快照捕获时 revision 已漂移（捕获到旧 revision） | 捕获时读当前 revision（best-effort）；恢复时再校验（双层） |
| C-1 规模（12-18 Task）仍偏大 | writing-plans 阶段按 WP5a/4.1/4.2/4.3/4.4 分 Task 组，每组独立 review |

## 1. 背景与目标

契约 REQ-COD-06：每仓独立 branch/commit/push 并持久化 `ReviewRequest`（GitBranchOnly）；Issue 完成 = 所有必需 Work Item 完成（以已推分支为完成级别）；partial failure 显式呈现，不伪装全局成功；自动 PR 不在范围。

**勘察结论（2026-08-13）**：单 attempt 交付机制已存在且完整——`execute_review_request`（越界门 → commit → branch → `git_push` → `ReviewRequest` 持久化，journal 幂等）+ `complete_attempt_after_review_request`（completion gates → Completed → work item 标记）。多仓下每个 attempt 的 worktree 在各自目标仓，push origin 天然到对应仓。`ReviewRequest` 模型已含 GitBranchOnly 全部字段（`push_status`/`branch_name`/`commit_sha`/`base_branch`/`external_url=None`/`push_error`）。

**缺口（C-3 本体）**：①Issue 级「全部已推」完成聚合判定（落盘）②partial failure 的 Issue 级聚合呈现（DTO + 前端）③多仓交付 it_web 验收。

## 2. 已确认决策（用户逐项批准）

1. **范围 A**：契约缺口聚焦——聚合判定 + 呈现 + it_web 验收；复用单 attempt 交付机制；不做 deliver-all 编排（YAGNI）
2. **完成判定 A**：不存在可选 Work Item，全部必需；判定 = 全部 Work Items 的 attempt 均 `Completed` 且 `push_status == Pushed`；判定落盘（attempt 交付完成后触发聚合检查），非前端动态计算
3. **呈现 A**：后端 Issue 级交付聚合 DTO + 前端 Issue 页紧凑面板（各仓状态列表 + partial 警示，不显示"已完成"）
4. **架构方案 1**：后端聚合判定组件 + DTO + 轻量前端面板（方案 2 内联、方案 3 前端动态计算，已被决策排除）

## 3. 架构总览

- **A. 后端聚合判定组件**（新组件，放 `coding_attempt_store` 或 `coding_workspace_engine`）：`compute_issue_delivery_summary` + `maybe_complete_issue_delivery`（在 `complete_attempt_after_review_request` 尾部触发）
- **B. DTO + HTTP**：`issue_delivery_summary` 接口（或并入既有 issue detail DTO）
- **C. 前端交付状态面板**：Issue 页各仓状态列表 + partial 警示

**单仓红线**：聚合判定为纯增量（读盘 + 新状态写入），不改任何既有状态流转；Legacy 单仓走同一路径。

## 4. 组件设计

### 4.1 IssueDeliverySummary 计算

- 查询链：`LifecycleStore::list_work_items(project_id, issue_id)` → 每 Work Item 经 `CodingAttemptStore::list_attempts_for_work_item` / `list_attempts_for_issue`（已有）取 attempt → `list_review_requests`（已有）取 `push_status`
- `DeliveryEntry`：`repository_id`/repo 名、`work_item_id`、`branch_name`、`commit_sha`、`push_status`、`push_error`
- `overall`：全部 Work Item 有 `Completed` attempt 且 `push_status == Pushed` → `AllPushed`；任一缺失/失败 → `Partial`；无 Work Item → `None`

### 4.2 落盘完成判定

- 触发点：`complete_attempt_after_review_request` 尾部调用 `maybe_complete_issue_delivery`（单仓/多仓共用）
- 聚合满足 → 置 `IssueStatus::Completed`（`src/product/models/project.rs:17` 枚举已存在，经 issue store 既有更新接口；现状无人写 Completed，无冲突）
- 不满足 → 不动 issue 状态；幂等（同值写入/跳过）

### 4.3 失败重试

- 复用 `execute_review_request` 既有 journal 幂等重入；前端「重新推送」触发既有 review request 入口；若 T1 审计发现缺重入端点，作为小任务补

## 5. 数据流与边界

- **成功路径**：coding 完成 → `execute_review_request` → `complete_attempt_after_review_request` → `maybe_complete_issue_delivery` → 全部已推 → `IssueStatus::Completed` 落盘 → 前端全绿
- **partial failure**：某仓 push 失败 → 该仓 `push_status=Failed` + `push_error` 落盘，不阻塞其他仓；issue 不置 Completed；DTO 返回失败行 + `overall=Partial`；前端红色行 + 警示
- **边界**：未开始/无 attempt 的 Work Item → Partial；review request 缺失 → Partial
- **幂等与恢复**：重推 → push_status 转 Pushed → 聚合补齐 → issue 完成

## 7. 范围外（YAGNI）

- deliver-all 一键交付编排（Q1 排除，契约未要求）
- 自动创建 GitHub/GitLab PR（契约明示不在范围）
- optional Work Item 概念（Q2 排除，全部必需）
- 每仓指针发布（C-5 范围）
- 跨仓只读证据检索（C-4 范围）

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 聚合查询触及多 store（lifecycle/coding/review request），N+1 查询 | issue 下 work items 数量有限（≤几十），直接循环查询可接受；如 plan 审计发现性能问题再引入批量接口 |
| `IssueStatus::Completed` 与既有 issue 生命周期语义冲突 | 现状无人写 Completed（grep 证实仅 Draft 创建点）；落盘前 T1 审计复核所有 IssueStatus 更新点 |
| 前端面板改动影响既有 issue 页布局 | 单组件插入，组件测试覆盖三种整体状态渲染 |
| push 失败后 attempt 状态与聚合判定的交互 | T1 审计 push 失败路径（ReviewRequest Failed 时 attempt 最终状态），聚合判定只看「Completed attempt + Pushed review request」双条件 |

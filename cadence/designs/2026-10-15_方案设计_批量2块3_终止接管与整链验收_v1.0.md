## 0. 结论摘要(随核实更新)

1. 终止=新增 enrollment 持久字段 `terminated_at`(终态,与 `enabled` 分离)+ 独立 REST `POST .../automation-enrollment/terminate`(幂等、可重入)。**不能**只靠 `enabled=false`:现有 Disable 后再 Enable 走"重开"分支并保留身份与绑定(`issue_automation_store.rs:1003-1042` [已实测]),所以 Disable 可逆,不满足"不可恢复"。
2. 终止同时写 `enabled=false`,使现有两处 enabled 检查(`autopilot_orchestrator.rs:96-98,121-123`、`coding_start.rs:773`)[已实测] 自然生效,编排器与 Enrolled 首启无需改读 `terminated_at`;`compare_and_set` 对 terminated 记录的任何 Enable 一律 Conflict(新增一条守卫)。
3. 服务端顺序(固定):①enrollment CAS 写 terminated(+enabled=false) → ②失效 CodingPlanRun → ③取消 plan 阶段 provider run、**等其退出**后 CAS 置 session Terminated → ④逐 attempt abort(registry abort → mutation lease → `handle_abort`)。每步幂等,整体可重入。
4. **已发现的竞态**:plan 阶段 run 被取消后,引擎 `finish_aborted_run→finish_failed_run` 会用非 CAS 的 `update_workspace_session_status` 把 session 改回 `Open`/`Failed`(`session_state/timeline.rs:21-42,122-132`、`lifecycle_store/workspace.rs:693-713`)[已实测],会覆盖先写的 `Terminated`。必须:先取消并等 run 退出再写 Terminated,且给 `finish_failed_run` 加"durable 已是 Terminated 则不覆盖"守卫(推荐两者都做)。
5. 并行 WI:服务端按 plan 枚举全部 attempt(`list_attempts_for_plan`,`plan_start.rs:303-305` [已实测]),任一 Coding Workspace 点终止即调同一 REST,plan 编写阶段与 coding 阶段是同一命令。
6. 自动化管理识别:用 enrollment 事实而非前端猜测;推荐在 `CodingAttemptSnapshotResponse`(`src/web/types.rs:784-812` [已实测])与 WS `CodingSessionState` 都加 `automation_managed`,由 `plan_id == enrollment.plan_id && enrollment.enabled`(或 terminated 之前的状态)算出;两个出口(REST `get_coding_attempt`、WS `build_coding_session_state`)都要改,否则刷新与实时不一致。
7. coding 阶段失败接管:批 1 A4 的 `retry_coding_with_context` 与既有 `retry_coding`/`retry_review` 都经 `handle_blocked_gate_response`→回 Running→`should_resume_runner_after_gate_response` 唤回 runner(`blocked_gate.inc.rs:2-193`、`runner.rs:313-335`、`coding.rs:672-841`、`socket.rs:844-859`)[已实测]。编排器每 2 秒重读 attempt 状态:Blocked/WaitingForHuman→AwaitingHuman,Running→Coding(`autopilot_orchestrator.rs:527-538`)[已实测],门响应后自动恢复观察,**不需要**新的 enrollment 级继续命令。
8. 通知:不建新通知模型,向批 1 A1 提需求:新增 kind 与 `focus.session_id`,plan 阶段派生函数自带(§7)。

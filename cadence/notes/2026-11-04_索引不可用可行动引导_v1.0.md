3. 用户随即**重新发起跨仓证据检索**（`aria-evidence-query` 走既有 `/api/evidence-query`）；此时 mediator 的 ④/④b 守卫（durable 在册 + 库目录在位）通过，检索按既有语义执行。**没有新增任何重试端点或重试 UI**。

## ③ 三条硬边界自查

### 边界①：库目录在册但查出来是空 ⇒ 仍 200 空结果，不做成失败

- **后端 200 路径未动**：证据检索的 200 空结果路径完全在 `src/product/logical_codebase/evidence_mediator.rs`（本次**未改**该文件）。本次对 evidence 链的改动只有 `src/web/handlers/evidence_error_mapping.rs` 的**响应文案层**：内层码是 `evidence_index_unavailable` 时才换中文成品；其余内层码逐字不变。
- **文案/按钮只挂在「索引不可用」这一分支**：
  - 503 分支（`evidence_error_mapping.rs`）：只在 `code == "evidence_index_unavailable"` 时换中文成品；空结果（200）根本不走这条分支。
  - 前端失败面（`AggregateIndexCard.tsx`）：只在后端给出 `evidence_copy` 时渲染；`evidence_copy` 的判据是**库目录不在**或**无在册世代**，**不依赖查询结果**。库目录在册（哪怕查询零命中）⇒ `evidence_copy` 为 `None` ⇒ 失败面与【重建索引】按钮都不出现。
- **证据**：兄弟 worker 已在 `tests/it_web/evidence_query/part_03.rs` 钉住「库在册而查询无命中 ⇒ 200 空结果」（`indexed_library_present_but_no_hits_returns_200_empty`，`body["text"] == ""`、`index_stale == false`、`truncated == false`）。该用例走的是真实 codegraph 建库路径，我的改动不触碰 mediator，故该契约保持。

### 边界②：不新造重建机制

- 只用既有端点 `POST /api/projects/{project_id}/logical-codebases/rebuild`（`src/web/app.rs:234` 的 LC 路由；项目级 `src/web/app.rs:226` 亦在）。
- 只用既有前端函数 `rebuildAggregateIndex`（`web/src/api/aggregate-index.ts`）与既有回调（`useIssueLifecycleWorkbenchActions.ts`）。
- 未新增任何重建端点、重建 service、重建 UI 组件。

### 边界③：不能只说「请重建索引」却找不到入口

两处都给足：
- 前端失败面**直接带【重建索引】按钮**（就在失败面内，用户不需要回面板顶部找）。
- 中文文案的 `action_zh` **写出入口位置**：「在逻辑代码库管理面板的「聚合索引」处点「重建索引」重建聚合索引；重建完成后重新发起跨仓证据检索。」——覆盖 agent 侧只看到 503 JSON、看不到卡片按钮的情形（`details.copy.action_zh` 与 `message` 都带这句）。

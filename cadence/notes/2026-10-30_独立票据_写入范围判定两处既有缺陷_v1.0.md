# 独立票据：写入范围判定的两处既有缺陷

> 来源：`harden-coder-write-scope-boundary` change 的独立审查（design-task-ds）
> 与 `fix-aggregate-lc-registration-gates` 评审（V2）**两次独立**指出。
> **故意不混入**该 change：改判定语义风险大，会让这批难以回滚。

## 背景

`harden-coder-write-scope-boundary` 解决的是「agent 看不到范围语义」与「本地产物污染 `git status`」，
**没有动机器门禁的判定语义**。该 change 的 prompt 文案已**诚实写明**下面第 1 条的陷阱
（见 `coding_work_item_context.rs` 的「匹配语义」条目），但判定本身未修 —— 属既有缺陷。

---

## 缺陷 1：以 `*` 开头的 scope 实际放行一切路径（P1）

### 事实

`src/cross_cutting/worktree.rs:398-404` 计算匹配前缀：

```rust
let has_wildcard = normalized.contains('*');
let is_dir = normalized.ends_with('/');
let base = if has_wildcard {
    normalized.split('*').next().unwrap_or_default().to_string()   // ← 首个 `*` 之前的部分
} else {
    normalized.clone()
};
```

`src/cross_cutting/worktree.rs:346-355` 判定：

```rust
let pattern = ScopePattern::parse(scope, case_sensitive);
let path = normalize_scope_text(relative_path, case_sensitive);
if pattern.all {
    return true;
}
if pattern.has_wildcard || pattern.is_dir {
    return path.starts_with(&pattern.base);   // ← base 为空串时恒真
}
path == pattern.base
```

### 后果

当 scope 以 `*` 开头（`**/x.rs`、`*.rs`），`base` = 空串 → `path.starts_with("")` **恒为真**
→ **该 scope 放行仓库内一切路径**。

注意：只有 `normalized == "*"` 这一支是**有意**的全放行（`ScopePattern { all: true }`，
`worktree.rs:390-397`）。缺陷出在**其它**以 `*` 开头、但作者意图是「限定后缀/限定目录」的写法。

### 风险

- exclusive 侧：写 `*.ts` 会被读成「可改一切」→ **边界形同虚设**
- forbidden 侧：写 `**/secret*` 会被读成「禁止一切」→ **误杀全部改动**
- 该判定同时被 `scope_allows_member_path`（多仓前缀兼容）复用 → 缺陷一并传导

### 候选修法（待定，需裁决）

| 方案 | 含义 | 代价 |
|---|---|---|
| A | 空 base 时**不放行**（fail-closed），并把该 scope 判为非法/需人工确认 | 改变既有行为：现场若已有 `*.ts` 类 scope，改后立刻收紧 |
| B | 空 base 时按**后缀/全路径 glob** 真正实现 | 实现成本高，且与「前缀匹配」的整体语义不一致 |
| C | 保留现状但在 scope 落库时**拒绝**以 `*` 开头的项（前置校验） | 需要改落库路径；已落库的历史 scope 仍按现状放行 |

**裁决要求**：先查历史 Work Item 里实际存在多少条以 `*` 开头的 scope，再选 A/C。

### 验收（修后必须新增）

- `scope_allows_path("*.rs", "src/main.rs")` 的期望值被显式钉住（不放行 / 或按后缀放行）
- `scope_allows_path("**/x.rs", "src/main.rs")` 同上
- `scope_allows_path("*", "任意路径")` 仍为放行（有意全放行，**不得回归**）
- exclusive 与 forbidden 两个方向各一组用例

## 缺陷 2：门禁硬编码大小写敏感（P2）

### 事实

`src/product/coding_workspace_engine/gates.rs:945-982`（`validate_changed_files_in_scope`）：

```rust
if forbidden_scopes.iter()
    .any(|scope| scope_allows_member_path(scope, relative_path, member_prefix, true))
//                                                                            ^^^^ 硬编码 true
```

```rust
let normalized = validate_write_path(
    base,
    &hygiene_scope,
    std::path::Path::new(relative_path),
    true,                      // ← 同样硬编码 true
)
```

而仓内**已有**正确的平台判定：`src/cross_cutting/worktree.rs:457-459`

```rust
fn platform_case_sensitive() -> bool {
    !cfg!(windows)
}
```

—— 该函数被 `worktree.rs:120` / `:231` 使用，但**门禁路径没有用它**。

### 后果

- **Windows** 上：Work Item 声明 `src/Foo.ts`，改动 `src/foo.ts` → 大小写敏感匹配 → 判越界
  （而 Windows 文件系统本身大小写不敏感 → 同一文件两个名字）
- **Linux** 上无影响（`platform_case_sensitive()` 在非 Windows 恒为 `true`）

### 候选修法

- 把 `gates.rs` 的两处硬编码 `true` 换成 `platform_case_sensitive()`（需把该函数提升为 `pub(crate)`）
- 契约 delta：`coding-workspace-completion` 增加「大小写判定与平台一致」条款

### 验收

- 平台判定函数被门禁路径调用（源码断言，防止回退硬编码）
- 一个大小写不一致的 scope/路径用例（在 Linux 上断言「按平台判定结果」，不硬编码 Windows 预期）

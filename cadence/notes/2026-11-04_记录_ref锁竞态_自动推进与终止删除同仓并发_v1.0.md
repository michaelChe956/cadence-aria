### 失败面 B 的两个子形态（14/14 红例逐条统计）

```
案例 A（3/14）：撞【这根分支自己的】锁
  could not delete reference refs/heads/aria/issues/issue_plan_0001/<UUID>:
    cannot lock ref 'refs/heads/aria/issues/issue_plan_0001/<UUID>':
    Unable to create '.../refs/heads/aria/issues/issue_plan_0001/<UUID>.lock': File exists
  ⇒ 语义：另一个 git 进程正在写【同一根同名分支】

案例 B（11/14）：撞【整个仓共用的 refs 清单锁】
  could not delete reference refs/heads/aria/issues/issue_plan_0001/<UUID>:
    Unable to create '.../.git/packed-refs.lock': File exists
  ⇒ 语义：另一个 git 进程正在改【这个仓的分支清单】
```

**实测钉死的机制边界**（本机 git 2.56.0 复现，报错逐字同型）：

```
删【loose】分支（.git/refs/heads/<name>）   → 不碰 packed-refs.lock ✔
删【packed】分支（分支已在 packed-refs）    → 必须拿 packed-refs.lock ✔
建【loose】新分支                          → 不碰 packed-refs.lock ✔
git worktree add / remove / prune          → 都不碰 ✔
只有 git gc / git pack-refs --all          → 会造出 packed-refs ✔
⇒ ⇒ 案例 B 的前提是「那一刻该分支已在 packed-refs 里」
⇒ ⇒【未查明】谁把分支打进 packed-refs：代码内无 pack-refs/gc 调用；
    git auto-maintenance 在小仓不触发（实测 loose 6 根也不打包）
```

## 3. 已确认的业务机制（本篇核心）

### 3.1 竞态双方

```
【后台】完成挂点自动推进
  src/web/coding_ws_handler/runner.rs:1063-1082
  → 某成员 work item 完成 → 完成事件挂点 → drive_ready_units_for_plan
  → 就地物化【下一个 work item】（同一个成员仓）
  → runner.rs 注释：「drive 桥(切片B in_place 物化)可能已把就绪的下一 unit
     物化为 PrepareContext+active 指针」

【前台】终止并删除整组
  src/web/handlers/coding/plan_start.rs:468 teardown_plan_coding_member
  → 逐成员拆：worktree remove --force + branch -D
```

### 3.2 为什么两者能并发（缺一把共同的锁）

```
自动推进拿的是  【work_item_group:{project}:{issue}:{plan}】组级命名锁
                （runner.rs:1064-1070）
拆除拿的是      【每个 attempt 自己的 mutation 锁】
                （plan_start.rs:477 lock_attempt_mutation）
⇒ ⇒ 两把锁互不排斥 ⇒ ⇒ 同一仓的 refs 可被同时改
⇒ ⇒ 且 abort_attempt 只取消【当前 attempt】的 runner，管不到【另一个 unit】的 runner
```

### 3.3 铁证：14/14 全部落在第一个成员 `n3-busi`

```
14 次红例的仓路径统计：n3-busi × 14（n3-web / n3-gateway / n3-frontend 各 0）
⇒ ⇒ 因为 n3-busi 是【第一个成员】⇒ 它的第一个 work item 最先完成
⇒ ⇒ 只有它才会在「删除刚开始」时还在自动推进
⇒ ⇒ 换言之：撞车必然发生在「最先完成的那个成员」上
```

### 3.4 业务上什么操作会撞上

```
1. 多仓组点【一键首启】⇒ 4 个成员仓各起一个 attempt，每个成员仓含多个 work item
2. 第一个成员的 work item 很快跑完（fake provider 秒完成）
3. 【完成挂点】自动推进：就地物化下一个 work item（同一个成员仓）
4. 同时用户/自动化点【终止并删除】整组
5. 拆除第一个成员 ⇒ 拆它的 worktree + 删它的分支
6. 与步骤 3 同仓同批 refs ⇒ git 不等待、直接失败
⇒ ⇒ 界面表现：删除报 409「本地 worktree 拆除未完成」
⇒ ⇒ 不是用户误操作，是【自动推进】与【终止删除】两条路径缺一把共同的锁
```

## 4. 已排除的修法：退避重试（worker 实测无效）

```
给 `branch -D` 与 `branch <创建>` 加指数退避重试（25ms 起，最多 9 次 ≈ 13s）
⇒ ⇒ 重跑 80 次压力：仍 14 红（与未加重试时同量级）
⇒ ⇒ 原因：锁的持有方是【活进程】（不是 stale 残留）
    · worker 探针：60 次杀在途 add ⇒ 0 残留 ⇒ 非 stale
    · 活锁持有时间可能 > 13s；stale 锁则根本不会自愈
⇒ ⇒ 结论：退避重试【不是解法】
```

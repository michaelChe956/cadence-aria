| `PROVIDER_SELECTION_RULE_VERSION` | 候选表规则版本(`aggregate-provider-owner-order-v1`) |

**行为要点**:
- **L1**:读 health 快照的 `available` + 六值原因码;**仅当** `generation == 0` / `degraded()` / `checked_at` 早于 `now-10min` 才 `await` 一次 `refresh()`(刷新用的 `CancellationToken::new()` 与请求生命周期解耦)。
- **L2**:`launch_cell_state` 的 `Confirmed` 结论(= gateway 的放行结论)。
- **选择**:按 owner 顺序取**第一家**「命令可用 + 已核验」;没有则按态分流:四家命令都不可用 → `NoCliAvailable`;有命令可用但没人核验 → `NeedsVerification{suggested = 顺序中第一家未核验/证据过期的 provider}`;有命令可用但全被真实拒绝 → `Denied`;health 探测失败 → `HealthDegraded`。
- **候选表逐家给**:`provider` / `display_name` / `cli_available` / `cli_reason_code` / `capability_state`(`confirmed`·`unverified`·`denied`·`evidence_stale`·`not_installed`)/ `skipped_reason`(`cli_unavailable`·`needs_verification`·`denied`·`evidence_stale`)/ `action_hint`(可执行动作,非裸状态词)/ `warning`(`Denied` 时带**真实拒绝原因**)。
- **全程不创建 operation**:选择器只读 durable 能力记录 + health 快照,不碰 operation store。

**测试(12 个,全在本文件内联 `#[cfg(test)] mod tests`)**:
`selection_picks_first_confirmed_candidate_in_owner_order` / `selection_skips_provider_with_missing_command_and_picks_next` / `selection_reports_no_cli_available_when_every_command_is_missing` / `selection_needs_verification_without_creating_operation` / `selection_distinguishes_denied_from_unverified_candidates` / `selection_reports_health_degraded_without_creating_operation` / `selection_refreshes_health_only_when_snapshot_is_stale_or_missing` / `launch_cell_state_and_require_supported_agree_on_every_input`(同源锁,表驱动 5 种输入)/ `provider_from_wire_rejects_unknown_and_fake` / `launch_rejection_error_keeps_prefix_and_real_reason`。

## 2. 「判定同源」如何体现在代码结构上

**同一函数、同一数据源**:能力判定只有一份实现,它同时被「gateway 放行门」与「provider 选择器」消费。

判定链(单一入口):

```
ProviderCapabilityRecord.action_matrix.row(PlanningReadOnly).launch
        │
        ▼
launch_cell_state_from_record(record, action)      ← 唯一判定实现(provider_selection.rs:96)
        │  Confirmed → Confirmed
        │  Denied{reason} → Denied{reason}(真实原因原样带出)
        │  Unknown → Unverified
        ▼
LaunchCellState
        ├── gateway:  production_policy_resolvers.rs:314-316
        │              require_supported → launch_cell_state_from_record + launch_rejection_error
        └── 选择器:  provider_selection.rs:265-269
                       decide_selection → launch_cell_state → launch_cell_state_from_record
```

要点:
1. **没有第二套判定**:选择器里没有任何「自己再判一次 Confirmed/Denied/Unknown」的代码;候选表的 `capability_state` 全部由 `LaunchCellState` 映射而来。
2. **同一数据源**:gateway 与选择器读的是**同一份** durable 能力记录(`ProviderCapabilityStore::for_lc(paths, lc_id)` + 同一个 `load_record`),且用**同一个** snapshot 引用常量 `MANAGED_CAPABILITY_SNAPSHOT_REF`。
3. **载入口径也同源**:记录缺失 / snapshot 不一致两条硬门在 `load_record` 里判定一次,`launch_cell_state` 只做映射,不复制判断。
4. **结论一致性被测试锁住**:`launch_cell_state_and_require_supported_agree_on_every_input` 对 5 种输入(Confirmed / Denied / Unknown / 记录缺失 / snapshot 不一致)逐项断言「选择器判定 == gateway 结论」,且 `Confirmed` 之外一律 `Err`。

## 2. 七个布局码全表（码 → 三段中文 → triage）

#### `aggregate_root_is_git` — triage=`environment`

- 问题：逻辑代码库根目录不能是 git 仓库
- 原因：布局规则「逻辑代码库根目录不能是 git 仓库」未满足：当前根目录下有 .git，会被当成单仓，成员仓就变成别人仓里的嵌套目录，聚合索引与冷启动都无法正确识别边界。
- 怎么做：另建一个空的普通目录作为逻辑代码库根（不要在某个 git 仓里，也不要在 git 仓里 mkdir），把成员仓移到它的直接下一层，然后重新登记。

#### `aggregate_root_member_outside_root` — triage=`environment`

- 问题：成员仓{member}不在逻辑代码库根的直接下一层
- 原因：布局规则「每个成员必须是逻辑代码库根的一层直接子目录（<LC根>/<成员>/）」未满足：当前成员路径多套了目录层级，或落在逻辑代码库根之外，聚合索引找不到它。
- 怎么做：把成员{member}移动到 <LC根>/<成员>/（只一层，不要再套目录），然后点「重试」。

#### `aggregate_root_member_symlink_escape` — triage=`environment`

- 问题：成员仓{member}经符号链接指向逻辑代码库根之外
- 原因：布局规则「成员必须是 LC 根内的真实目录，不能经符号链接指向根之外」未满足：该成员的链接目标在逻辑代码库根之外，索引会越过声明范围读写。
- 怎么做：用真实路径放置成员（不要把它 symlink 到别处），然后点「重试」。

#### `aggregate_root_overlap` — triage=`environment`

- 问题：这个聚合根已被另一个逻辑代码库占用{member}
- 原因：布局规则「一个聚合根只能归属一个逻辑代码库」未满足：当前根（或它的上下级目录）已是另一个逻辑代码库的根，两个 LC 会互相覆盖同一批成员。
- 怎么做：换一个未被占用的目录作为逻辑代码库根；要多个逻辑代码库就各自用互不重叠的根目录。

#### `aggregate_root_nested_worktree` — triage=`environment`

- 问题：成员仓{member}是嵌套 worktree
- 原因：布局规则「成员必须是正常检出，不能是嵌套 worktree」未满足：嵌套 worktree 的 git 元数据指向另一个工作区，索引快照无法稳定归属。
- 怎么做：成员改用正常检出（单独的 clone / 普通工作区），不要塞嵌套 worktree，然后点「重试」。

#### `aggregate_index_layout_unsupported` — triage=`environment`

- 问题：当前目录布局不被聚合索引支持
- 原因：布局规则「每个成员必须是逻辑代码库根的一层直接子目录（<LC根>/<成员>/）」未满足：索引只接受 LC 根下每个成员一层直挂、且成员是真实检出目录；当前 LC 根或成员的自定义相对路径无法安全遍历。
- 怎么做：让 LC 根与成员保持 <LC根>/<成员>/ 一层直挂，成员使用真实检出目录，然后点「重试」。

#### `aggregate_index_member_coverage_failed` — triage=`environment`

- 问题：成员仓里没有可索引的代码文件
- 原因：布局规则「每个成员至少要有一个可索引的源码文件」未满足：被纳入的成员{member}下找不到可索引的源码文件，索引会得到空结果。
- 怎么做：把真实源码放进成员仓（.js/.ts/.py/.go/.rs 等）；.html/.json/.md 不算源码；只放在 .worktrees/ 下的代码同样不算。放好后点「重试」。

### 2.1 未知码中性兜底（§1.1.2）—— 实际实现代码

```rust
fn neutral_fallback(input: &FailureInput<'_>) -> FailureCopy {
    let title_zh = match input.subject {
        Some(subject) => format!("{subject} 的本次操作未完成"),
        None => "本次操作未完成".to_string(),
    };
    FailureCopy {
        title_zh,
        reason_zh: "当前无法确定具体原因，请查看下方诊断信息。".to_string(),
        action_zh: "请重试；连续两次仍失败时，提交问题并附上机器码与下方诊断信息。".to_string(),
        triage: FailureTriage::ProductDefect,
        machine_line: input.reason_code.to_string(),
    }
}
```

断言该形态的测试（`failure_copy::tests`）：
- `unknown_code_falls_back_to_neutral_chinese`：`describe_code("unknown_code_xyz", Some("raw english error text"))` → title 恰为「本次操作未完成」、reason 含「无法确定具体原因」、action 以「请重试」开头、`triage == ProductDefect`、`machine_line == "unknown_code_xyz"`、**title 不含英文原文**。

### ② `bootstrap_placeholder_with_valid_receipt_waits_for_explicit_recipe_api` —— **真信息丢失，修实现**

`panicked at bootstrap_tests_placeholder.inc.rs:178: assertion failed: notice.summary.contains(&api)`。

**语义判定：那个 `api` 标识「该」出现在用户可见的 summary 里。** 理由：该失败的全部可执行性就建立在「调用 `POST /api/projects/{project}/logical-codebases/{lc}/initializations` 并携带新的 idempotency_key」——API 路径是用户唯一入口。而且通知卡**没有**独立的折叠诊断区（不像步骤行由 `BootstrapFailureLine` 折叠 detail），所以诊断里的路径一旦不进 summary 就**彻底丢了**。⇒ 这是我在 `render_detail(copy, None)` 里丢掉诊断段造成的**真信息丢失**，不能改断言糊过去。

**修法**（`bootstrap_projector.inc.rs`，897 行）：
```rust
// 新增
/// 通知主文案：中文三段（成品 copy）+ **原始诊断段**。
/// 通知卡没有独立折叠区，诊断里的可执行信息（如实际 API 路径）必须进主文案。
/// 已经是成品序列化（operation_failure 产出的 detail 以「问题：」开头）时原样复用，避免二次包裹。
fn notice_summary(failure: &BootstrapFailure) -> String {
    match failure.copy.as_ref() {
        Some(_) if failure.detail.starts_with("问题：") => failure.detail.clone(),
        Some(copy) => render_detail(copy, Some(&failure.detail)),
        None => failure.detail.clone(),
    }
}
// project_notices 内
- .map(|failure| match failure.copy.as_ref() { Some(copy) => render_detail(copy, None), None => failure.detail.clone() })
+ .map(notice_summary)
```
结果：summary = 「问题 / 原因 / 怎么做 / 机器码」**+ 诊断段（含真实 API 路径）**，主次关系不变（机器码仍是次要行），`notice.reason_code` / `external_side_effect` / `allowed_actions` 全不变。我自己的 codegraph 通知（测试点 #9）走的是独立合成路径 `render_detail(&copy, None)`，不受本次改动影响（其断言 `summary == render_detail(copy, None)` 仍成立）。

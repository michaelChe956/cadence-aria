## 一、BLOCKER（必须改才能进 Plan）

### BLOCKER-1：B-5 修复不完整——preflight「冻结持久化」没有存储落点
- 文档位置：§4.1「preflight 结果由服务端冻结持久化，preflight_id 供提交引用」；§4.1「preflight_id 不存在/过期 → 404」。
- 理由：coordinator 的 `submit_confirmed_batch` 要求 `ConfirmedRegistrationBatchInput.candidates: Vec<RegistrationCandidate>`（含 canonical_path/git_root/source_identity/preflight_revision 全量字段），而 POST 只传 `{aggregate_root, preflight_id, confirmed_paths[]}`。设计说"冻结持久化"但**全文未定义任何 preflight 快照 store**——现有 `RegistrationBatchStore` 只持久化 batch record，`RegistrationPreflightResult` 无任何持久化。没有这个新 store（key=preflight_id、TTL/过期机制、重启存活），handler 无法从 `preflight_id + confirmed_paths[]` 重建 `ConfirmedRegistrationBatchInput`。
- 代码证据：`src/product/logical_codebase/registration_coordinator.inc.rs:19-84`（submit 要求全量 candidates）；`registration_batch.inc.rs` 全文只有 batch store、无 preflight store。
- 附加矛盾：响应体顶层 `preflight_revision` 在数据模型里不存在——模型是**每个 candidate 各自** `preflight_revision`（`registration.rs:74-120`、`RegistrationCandidate::new`），batch 幂等 key 用的是排序后的 item revision 列表（`registration_coordinator.inc.rs` batch_idempotency_key）。§4.1 契约与模型不对齐。

### BLOCKER-2：B-7 修复不完整——manifest 首批创建与后续批次一致性/原子性未定义
- 文档位置：D7、§4.1「首批次原子创建 manifest（D7）」。
- 理由：D7 只回答了 B-7 的"何时建 manifest"（首批提交时，以用户 aggregate_root 为准），但 B-7 的子问题一个都没回答：(a) 后续批次提交的 `aggregate_root` 与已建 manifest 的 `provider_context_root` 不一致时如何拒绝；(b) 首个成员 attach 与 manifest 创建如何共用同一把锁保证原子性；(c) 若项目已有 manifest（迁移产物/指针链先建）时首批提交的冲突语义。若后续批次带不同 root 被放行，成员会落在 manifest root 之外，索引 build 在 `checkout_root_name`/`included_main_checkouts` 会 fail（layout_unsupported）。
- 代码证据：`src/product/logical_codebase/registration_coordinator.inc.rs` attach_member 与 submit 均不校验 aggregate_root 与既有 manifest；`aggregate_index/operation.rs:checkout_root_name` 要求 checkout 是 aggregate root 的直接子目录。

## 二、MAJOR（应改）

### MAJOR-1：B-4 只修了一半——「先持久化 Building record」未定义，"Building→rebuilding" 是死映射
- 文档位置：§4.3 GET active「Building→rebuilding」；§4.2「首建 spawn build（包 single-writer 锁，B-4 修复）」。
- 理由：v1.0 审核 B-4 的第二半明确指出「apply_index 注释声称先写 building record 再切 active，但实际构造后直接设 Active」。v1.1 只修了"build 加锁"，**没有规定 apply_index 必须先经 `store.create` 持久化 Building record**。由于 §4.3 把 Building 映射为 `rebuilding`，而重建是同步 200，该状态只有在"先持久化 Building、再 replace_active"时才对并发 GET 可见；不修则 `rebuilding` 永远不可达。
- 代码证据：`aggregate_index/operation.rs:294-335`（`AggregateIndexRecord::building(...)` 后立即 `record.status = Active` → `replace_active`）；`aggregate_index/store.rs:165` replace_active 文档注释明确要求「caller persists the new record as `building` first (via `Self::create`)」，apply_index 未遵守。

### MAJOR-2：revision 漂移语义自相矛盾（§4.1 vs §7），且 identity change 整批中止未说明
- 文档位置：§4.1「revision 漂移项标 needs_attention 跳过（item 级，不整批拒绝）」vs §7 测试「revision 漂移 409」。
- 理由：两处矛盾。实际代码里两种漂移行为不同：(a) `preflight_revision` 变化 → item 标 `NeedsAttention` 并继续（非 409）；(b) 路径/git root/source identity 变化 → `revalidate_batch_item` 返回 `Conflict`，经 `?` 传播**中止整个 resume_batch**（整批 409，非 item 级）。设计把两者混为一谈，测试矩阵的"revision 漂移 409"会写出与实现不符的用例。
- 代码证据：`registration_coordinator.inc.rs:151-185`（NeedsAttention 分支与 revalidate 错误传播）。

### MAJOR-3：「并发重建 → 409」与「统一走 single-writer 锁」矛盾，409 无产生机制
- 文档位置：§4.3/§6「并发重建 → 409 aggregate_index_rebuild_in_progress」vs §5「统一走 single-writer 锁」。
- 理由：`with_single_writer` 用的是**阻塞 flock**（`with_exact_exclusive_lock` → `flock(LOCK_EX)`，无 LOCK_NB），并发请求会排队等待而非返回 409。要兑现 409 必须新增 try-lock 或 in-memory 进行中注册表，设计未说明。
- 代码证据：`coding_attempt_store/locking.rs:27-50`、`247`（阻塞 LOCK_EX）；`operation.rs` 并发测试 `concurrent_rebuilds_are_serialized_under_the_single_writer_lock` 证明其行为是"等待"而非"拒绝"。

### MAJOR-4：M-14 未完全关闭——aggregate_root_* 族在 §3 声明、§6 表零枚举
- 文档位置：§3「错误码映射：registration_* / aggregate_root_* / aggregate_index_* 族补入 support.rs」vs §6「新增稳定码」表（8 条，无任何 aggregate_root_*）。
- 理由：root preflight 的确定性失败（aggregate_root_is_git / member_symlink_escape / member_path_outside_root / nested_worktree / aggregate_root_ownership_conflict 等）在代码里是 `AggregateRootPreflightError` 库级错误，support.rs 当前**完全没有**这些码的 HTTP 映射；§6 作为规范性错误码表却一个都不列，实现者无法确定 4xx 状态码。
- 代码证据：`registration_preflight.inc.rs`（上述 code 字面量存在）；`grep registration_|aggregate_index_|aggregate_root_ src/web/handlers/support.rs` → 零命中。

### MAJOR-5：M-4 补偿事务落地了，但多仓 issue 的 `repository_id` 语义未定义
- 文档位置：§4.4「repository_id 必须属于 manifest active member」「请求体不变」。
- 理由：审核 M-4 的遗留子问题未回答：多仓下 `repository_id` 是否承担 primary/focus 语义、`all_members` selection 是否允许 repository_id 为空。D4 说"自动写 all_members"，但请求体不变意味着客户端仍必须传一个物理 repository_id——它与 all_members 的关系（它是 include 的第一个？focus？）直接决定 ROUTE-01/PLN-02 行为。
- 代码证据：`src/web/handlers/product_resources.rs:140-160` 强制 `repository_id` 必填。

### MAJOR-6：首建期间漂移「标 stale」会留下无 active 索引
- 文档位置：§4.3「期间成员 HEAD/dirty 变化则该 record 标 stale（不静默丢弃）」。
- 理由：首次 build 若期间漂移，按此规则新 record 标 stale → 无任何 active/degraded 可读记录 → `active_required` 返回 `aggregate_index_active_missing`，planner fail-closed。这与 §4.2「首建失败 → missing + 失败原因」的语义不统一（漂移≠失败，但结果同样是 missing）。需明确首建漂移应记为 Failed/missing 而非 stale，或重试。
- 代码证据：`aggregate_index/store.rs:101-137` active_required 只读 Active/Degraded/Stale；`operation.rs:147-168` build 走 `IndexApplicationMode::Initialize`。

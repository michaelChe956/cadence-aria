# 独立票据：失败面可行动化 —— 说清是什么问题 + 告诉用户如何操作

> 来源：owner 2026-11-02 裁定（连测多仓链路，撞了一串"看不懂也不知道该干嘛"的报错之后）。
> **这是纲**：把 2026-11-01/02 记录的全部失败面按同一标准收敛 —— 一条规则、一份清单、一次做完。

## 一、判定标准（合格线）

任何一个**用户会看到的失败面**，必须同时满足三条，缺一即不合格：

| # | 要求 | 反例（今天实测到的） |
|---|---|---|
**1. 说清是什么问题** | **中文**、人话、**点名对象**（哪个成员仓 / 哪个 provider / 哪个文件 / 哪一步） | `provider_capability_launch_not_confirmed: PlanningReadOnly launch cell is Unknown`；`stage aggregate_initialization: no stderr summary`；`audit snapshot budget exceeded ... (fail-closed; paths ignored by .gitignore/...)` |
**2. 告诉用户如何操作** | 具体到**点哪个按钮 / 跑哪条命令 / 改哪个文件**，并说明**要等多久** | 「只能终止此门后重新发起」（指向了一个不该做的动作）；只给机器码不给出路 |
**3. 机器码保留但降级** | 机器码/原始 detail 保留在**次要行或折叠区**，供排查用；**不当主文案** | 机器码当主文案，用户读到的是 `provider_gateway_capability: ...Unknown` |

**外加一条分诊**：失败面要能让人一眼分清 **「你的环境要处理」/「产品缺陷」/「重试即可」** 三类 —— 三类给**不同**的指引（现在三类混成一句 fail-closed）。

## 三、实施要求

1. **一个批次做完全部**（一次改动、一轮真机复验），不要分多次小修 —— 否则失败面会长期半中半英。
2. **每条都要有可执行动作**：不许出现"请联系管理员""请重试"这种无信息的出路。
3. **不丢原始事实**：机器码与 detail 保留在次要行/折叠区（排查要用），但**不当主文案**。
4. **文案与动作要同源**：别在两处各写一份（今天「还可自动修复 3 次」就是两处口径不一致的产物）。

## 四、验收（真机逐条走查）

用同一台**干净机器**（无 codegraph / 未核验 / provider 未登录 / 有大构建产物）依次触发：

| 场景 | 期望失败面 |
|---|---|
未装 codegraph → 冷启动 | 一次中文提示 + 安装命令；**不出现三步各报各的** |
provider 未核验 → 写 Story | 中文点名 provider + 「点核验」指引 |
provider 未登录 → 冷启动 skills 步 | 中文 + stderr 摘要 + 未登录这一具体原因 |
成员仓有大构建产物 → 预检 | 中文点名**成员仓 + 路径** + 清理/exclude 两条出路 |
换 provider（启用状态下） | 区分「等一下重试」与「需关闭后重开」两种文案 |
已完成的 plan 的旧门卡 | 「已确认完成，历史记录，无需处理」 |

**验收标准**：以上六条，**每条都能让用户在不查源码的情况下知道「是什么问题 + 下一步点哪里」**。

## 五、流程

- 属**行为变更**（owner 可见面的文案与指引）→ 走 OpenSpec change（brainstorming → delta specs → 实施 → 归档）。
- 建议与**票 2（多仓入口布局引导）**、**票 3（能力核验一键化）**合并成同一个「多仓入口体验」change —— 三者都改同一批 owner 可见面。
- 单独可回滚。

# 测试方案：全流程端到端验证 v1.0

> 用途：可复用的全链回归/验收测试方案。基于 2026-09-18~21 三轮实测经验（F-01~F-24 全系）沉淀。
> 执行环境：本地 aria 服务（默认 `http://127.0.0.1:4317`），项目 cad（project_0001），代码仓 naruto。
> 红线（继承测试交接）：禁碰代码/git；只读文件+浏览器+REST/WS 探测；发现写登记文件。

---

## 0. 环境基线与预检（每轮 5 分钟）

1. `curl -s http://127.0.0.1:4317/api/health` → ok；记录 PID（`pgrep -x aria`）与二进制 mtime（部署指纹）。
2. 浏览器开 `/workbench`：确认无红色报错、Projects=1（cad）、Issue 队列可加载。
3. 记录基线：`git -C <worktree> log --oneline -1`、台账 mtime（轮询对账用）。
4. 测试数据命名规范：issue 标题前缀「验证：<场景名>」，便于事后清理与追溯。

**时间预算参考**（pi 基准，F-06 修复后）：会话起跑→首字 <10s；story/design 生成 2-4min；plan 生成+评审 5-10min；coding unit 5-20min。codex 同场景 ×3-10 倍且方差大。单轮 L1 全链约 30-45min（pi）。

| # | 步骤 | 预期 | 证据点 |
|---|---|---|---|
| 0.1 | 任一 plan 会话 →「开始生成」 | 状态行 3s 内转「正在生成 · pi · 运行中」 | 状态行文本 |

## 2. L1 主链标准（全流程 E2E，30-45 分钟）

**前置**：新建 issue（UI「新建 Issue」对话框；注意：React 受控输入必须 focus+键盘输入，直接赋值会建出空 issue——历史踩坑 F-案例）。描述写小而清晰的单仓特性（参考模板：一个 HTTP 端点+测试，明确「仅 Node 内置模块」）。

| # | 阶段 | 操作 | 预期 | 已知坑 |
|---|---|---|---|---|
| 1.1 | issue | UI 创建 | issue 落盘、出现在队列 | 空标题 issue（输入法坑） |
| 1.2 | story | 卡片「生成 Story Spec」→ 会话页「开始生成」 | 2-4min 到「等待作者确认」；**期间留意选择卡**（L4.3 采样） | provider 选 pi；codex 慢且可能触发 choice |
| 1.3 | story 确认 | 点「确认」 | HTTP POST `/api/workspace-sessions/{id}/confirm`，引擎 status=confirmed | — |
| 1.4 | design | REST `design-specs:generate`（story_spec_ids 指向已确认 spec）→ 同上走完+确认 | design_spec 落定 confirmed | — |
| 1.5 | plan | REST `work-item-plans:prepare` → UI「开始生成」 | 生成+评审（可能多轮返修）→「等待人工确认」 | **`include_integration_tests` 必须与预期计划内容一致**（strict validator 会拒，历史 0478） |
| 1.6 | plan 门确认 | 点「确认」 | Final Compile 通过→「已完成」+「手动推进」出现；编译失败则见内联 findings（可「确认产物」重试） | 候选编译有方差（capability 补齐器已修大头） |
| 1.7 | advance | 点「手动推进」 | 引擎建 coding attempt+worktree（页面不自动跳转，需手动开 coding 页） | — |
| 1.8 | coding | coding 页「开始 Coding」 | unit running、命令流实时上屏、worktree 出现真实文件 | — |
| 1.9 | 落地 | 等 unit 完成 | worktree 有 commit（feat+test）；attempt → waiting_for_human（设计停点） | commit 责任在 provider |
| 1.10 | 收尾（可选延伸） | 人工验收门应答 | 报告审阅→接受→合流终态（这段历史未验，验收时补） | 留白区 |

**判定**：1.1-1.9 全过 = 主链贯通。样本量建议 ≥2 轮（候选质量方差）。

对**每种门**验证 确认 / 终止 / 反馈 三动作（可用测试 issue 造多个一次性门）：

| 门类型 | 确认通道 | 终止通道 | 历史缺陷对照 |
|---|---|---|---|
| story Author 门 | HTTP confirm（0476 验证路径） | 两步终止→abandon_human_gate | F-20（确认路径曾删）、F-18（终止曾死线） |
| design Author 门 | 同上 | 同上 | 同上 |
| plan human_confirm 门 | 裸 confirm（WS） | 两步终止 | F-08（曾发错消息）、F-21（终止三连挂） |
| plan Compile Recovery | 「确认产物」=编译重试 | — | F-16（死按钮已移除，重试通道换壳） |
| coding waiting_for_human | 验收应答 | — | 未充分验证 |

附加：
- 2.6 生成期「中止」：running 态页面必有「中止」；点击→`{"type":"abort"}`→「生成已终止 · 准备上下文」+开始按钮回归（v29/v30 已修）。
- 2.7 终止 armed 时效：点「终止」后 ~1s 内必须点「确认终止」，armed 态会过期（实测 ~2s 窗口）。

## 4. L3 连接韧性（REQ-WCR 面，25 分钟，需一个活跃 run 作载体）

| # | 场景 | 操作 | 预期 |
|---|---|---|---|
| 3.1 | 刷新 | run 中整页刷新 | run 不死、elapsed 续算、流式恢复 |
| 3.2 | 断网 10s | CDP `Network.emulateNetworkConditions` offline 10s→恢复 | 重连+回放不丢（plan 面全量回放；coding 面历史消息数一致） |
| 3.3 | 冻结 tab | CDP `Page.setWebLifecycleState frozen` 2-9min→active | 状态与内容与对照 tab 一致 |
| 3.4 | 双 tab 同步 | 第二 tab 同 URL 挂着 | 流式增长/门开/阶段变更实时双端一致 |
| 3.5 | 观察只读 | 裸 WS observer 发 `user_message` | `protocol_error OBSERVER_WRITE_REJECTED` |
| 3.6 | 跨重启恢复 | （需部署窗口配合）重启后开旧 run 会话 | 僵尸自动转「失败·准备上下文」可重跑（F-23 修复） |

## 5. L4 循环、修复与交互深水区（按机会触发，各 15-30 分钟）

### 5.1 plan 返修循环（review→revision→re-review）
- 触发：评审 findings>0 时观察 Round1→Round2。
- **判定关键**：Round2 findings 必须与 Round1 不同或减少——逐字相同=返修无效（F-17 历史症状）。
- 证据：两轮 timeline 节点 summary 对比。

### 5.2 plan-repair（Compile Recovery）
- 触发：Final Compile 失败后出现 recovery 节点。
- 操作：「确认产物」重试编译；若持续失败→「提交反馈」走修复 run；「终止」弃门。
- 预期：每次重试有新 compile 节点+内联 findings；修复 run 后编译通过或耗尽轮次转终态。
- 历史对照：F-16（死按钮）、F-17（contract_gap 返修无效——已修）。

### 5.3 choice 卡（ask_user，F-24 治本验证——当前唯一开口）
- 触发：provider 生成/评审中发问（不可强造；codex 概率高于 pi；权限敏感操作更易触发）。
- 验证点：页面出现选择卡（radio/选项按钮）；应答后 provider 继续（流式恢复）；**不应**再出现 900s `provider_choice_wait_timeout`。
- 兜底验证（可强造）：任一 run 悬置 15min→看门狗转可诊断失败（v29 已验，回归项）。

### 5.4 coding→review→re-coding 循环
- 触发：coding unit 完成→reviewer 发现问题（findings）→rework。
- 验证：rework run 自动重启、修复后 review 通过、unit 终态 completed；修复轮次计数与「剩余修复轮次」展示一致。
- 历史线索：inbox 门文案「复验发现新问题 · findings N 条 · 剩余修复轮次 M」。

### 5.5 批量确认（P2-6，未实测留白）
- 前置：≥2 个会话各挂一门（用测试 issue 造）。
- 操作：勾选多门→「批量确认 N 项（M 个会话）」→确认。
- 预期：所有选中门依次关闭、各会话进入后继态；未选中门不动。
- 风险控制：只在测试 issue 上做。

### 5.6 C2 多仓（未实测留白）
- 前置：项目添加第二仓库（UI「添加代码库」）；造跨仓 issue。
- 验证：plan prepare 不被拒（multi-repo preflight 终态）；advance 产生多 target 分流（per-target attempt/journal）；混合仓 group coding 走通。
- 对照 REQ：REQ-MTG-01..05。

## 7. 测试工具箱（实测有效的方法）

1. **WS 帧级验证**（判定按钮接线）：CDP `Network.webSocketFrameSent/Received`；滤掉 ping/pong/hello。零出站=按钮死线（F-18/F-21 判定法）。
2. **引擎状态直读**：`.aria/projects/{proj}/issues/{issue}/`
   - `workspace-sessions/{sid}.json`：status/stage/phase/ledger
   - `workspace-timelines/{sid}/timeline_nodes.json`：节点全史（supersede 改写=看这里）
   - `timeline_node_details/{node}.json`：prompt/streaming_content/execution_events
   - `coding-attempts/{aid}/`：units 状态+worktree 关联
3. **裸 WS 探针**：`ws://{host}/api/workspace-sessions/{sid}/ws`，hello(role=observer/driver)。observer 写入必被拒（3.5 用）。
4. **进程判活**：aria 子进程按 `pgrep -P <pid>`——**注意 codex 是 `codex app-server`（node 包壳），`-x codex` 匹配不到**（F-19 误判教训）。CPU 零增长+出站连接 0=真死；在跑命令=活。
5. **轮询节奏**：UI 采样循环 ≤265s/窗口（eval 300s 硬顶）；引擎侧采样放 bash 后台任务。
6. **React 输入**：一律 focus+keyboard.type；直接赋值 value 不生效。

## 9. 执行建议

- **每次部署**：L0 必跑（10min）。
- **每次大版本/验收**：L1×2 样本 + L2 + L3（约 2 小时）。
- **机会触发**：L4 全部（登记触发样本，攒齐一个补一个）。
- **发版前**：L5 两留白（多仓/批量）+ L6。
- 所有发现写当日登记文件（`cadence/notes/YYYY-MM-DD_测试发现登记_*.md`），格式=时间+信号来源+现象+复现步骤+证据路径。

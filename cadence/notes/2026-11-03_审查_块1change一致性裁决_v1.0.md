### ② REQ-WPS-01（重新开启＝旧 plan 作废）vs「换 provider = 全部删除」及 owner 语义

**判定：完全一致 —— 而且 REQ-WPS-01 比 owner 语义更强：它不是「允许」失败即空态，而是「强制」先删后建。**

`openspec/specs/work-item-plan-single-instance/spec.md:10-14`：
```
10: ### Requirement: 单 plan 不变量与建立前先删旧（REQ-WPS-01）
12: 系统 SHALL 保证同一 issue 任一时刻至多存在一个存活 plan 实体，覆盖 legacy 与 schema-v2 两路存储。任何建立 plan 的路径 MUST 在 issue 级 plan 作用域互斥内先完成旧 plan 的完整删除（REQ-WPS-03），旧 plan 删除未成功前 MUST NOT 建立新 plan；建立完成后该 issue 的存活 plan 数恒为 1。MUST NOT 以摘除列表摘要、解绑 session、改写 plan_id 引用、置软删标记或仅增代际版本号代替删除；旧 plan 的 id、session 与新 plan 的 id、session MUST 互不复用。
```
```
16: #### Scenario: issue 已有 plan 时再次建立
17: - **WHEN** 某 issue 已存在一个存活 plan，客户端或自动链再次触发 plan 建立
18: - **THEN** 系统 MUST 先按 REQ-WPS-03 完成旧 plan 删除，再建立新 plan，对外不出现两个存活 plan 同时可见的窗口
```

`openspec/specs/work-item-plan-single-instance/spec.md:38-42`（REQ-WPS-02）：
```
38: #### Scenario: re-enable 轮换 prepare_intent_id 时删除旧 plan
39: - **WHEN** terminated enrollment 经人工 Enable 重新开启，新代 `prepare_intent_id` 与终止前不同
40: - **THEN** 系统 MUST 在新 prepare 建立 plan/session 之前删除旧 plan 及其完整闭包
```

三点一致性：

1. **「换 provider = 全部删除」不是新增语义，是既有强制语义。** REQ-WPS-01 `:12` 已经要求「任何建立 plan 的路径 MUST 先完成旧 plan 的完整删除」，且 REQ-WPS-02 `:38-42` 点名覆盖「terminated → 人工 Enable 重开」这条路径。change 的 `design.md:25-29`（决策 2）把「先删后建」说成单 plan 不变量的**实现方式**，与契约原文一致。
2. **owner 决策 4「接受失败即空态」不是宽容，而是 REQ-WPS-01 `:12` 的唯一合法结果。** 「旧 plan 删除未成功前 MUST NOT 建立新 plan」⇒ 删除成功、新建失败时，合法状态只能是空态；「先建后删」在契约层面被禁止。因此 `specs/work-item-group-autopilot/spec.md:31-34`（delta，失败面如实告知）与 REQ-WPS-01 是**互相支撑**，不是互相让步。
3. **「不做接续」有独立契约依据。** REQ-WPS-01 `:12` 末句「旧 plan 的 id、session 与新 plan 的 id、session MUST 互不复用」，对应 SWAP-01 的「SHALL NOT 复用旧链的身份派生产物」（delta `:22-24`）。一致。

**唯一需要补的表述**：REQ-WPS-01/02 全文不含 provider 维度 —— 「换 provider 也必须删除」这层语义确实需要新 requirement 承载。因此 `REQ-WIGA-SWAP-01` 的**归属正确**，只是如 ① 所述应以 MODIFIED 形式锚定到既有条款上，避免与 `:712` 并置矛盾。

### ⑤ 四个新 requirement 的 capability 归属

**（a）REQ-WIGA-SWAP-01 / 02 → `work-item-group-autopilot`：归属正确，但形式错误。**

- 归属正确：enrollment 的授权语义由 `REQ-WIGA-01`（显式授权与范围）、`REQ-WIGA-02`（durable 策略）、`REQ-WIGA-09`（终止与重新开启）在同一 capability 内承载（`openspec/specs/work-item-group-autopilot/spec.md:9/127/656`）。换 provider = 授权换代，落在这里是对的。
- 形式错误：净效果是 **MODIFY 两条既有 scenario**（`:219-223`、`:709-712`）。用 ADDED 叠一条新 requirement，会让主 spec 出现「同状态同动作两条相反 MUST」，且归档后 OpenSpec 不会自动消解。

**（b）REQ-CWS-GATE-01 / 02 → `coding-workspace-completion`：归属不合适。**

- 该 capability 的 Purpose（`openspec/specs/coding-workspace-completion/spec.md:3`）是「Coding Workspace completion gate 对 testing report 的依赖…文件范围、runtime binding、handoff、terminal 完整性等非 testing 门禁」，既有 requirement 是 `REQ-CWS-01/02`（本地产物写入 `.git/info/exclude` 等）—— **与对话流门卡文案、门预算展示无任何既有关系**。

## 3. 诊断：主 agent 可能漏掉的

1. **三步序列不是前端自作主张，而是主 spec 明文契约。** `openspec/specs/work-item-group-autopilot/spec.md:712` 写着「改授权 payload 须先成功重新开启，再走既有 Disable→Enable 路径」。只改代码不改 spec，`openspec validate` 仍会通过（它校验格式，不校验语义冲突），但归档后新旧条款并存 —— 下一个人照老条款实现，缺陷原样复活。**这是本 change 最可能的「静默失败模式」。**

2. **`attention_termination_tests.inc.rs:1098-1113` 那条测试不是随手写的断言，是 REQ-DRG-18「只有 source 可被放行」的执行证据。** `tasks.md:14` 把它列为「改写」时没有提到 REQ-DRG-18，实施者会以为是「测试跟着实现走」，实际是在**静默推翻一条悬空治理的 MUST**。

3. **proposal / design / delta 三处对「改了哪些既有条款」各说一套。** `proposal.md:99` 说 MODIFIED REQ-WIGA-02；`design.md:86-87` 说 REQ-WIGA-02 与 REQ-WIGA-09 都「不变」；delta 实际一个 MODIFIED 都没有。三方口径三种说法，评审时只要看其中一份就会得出不同结论。

4. **delta 里唯一没有 owner 裁定、没有任务、没有技术方案落点的那条 scenario**（`:26-29`），也是最容易被当成「块2 会做」而留下的重复条款 —— 两块的 requirement 会各自归档，各自被不同的人实现。

5. **把 `max_repairs` 叫「平台自动重写」会让 REQ-WSC-21 的 `MUST NOT` 在文案层被违反**，而且与 2026-10-28 现场记录的标签（「自动返修额度用完」）冲突。owner 决策 5 只裁了「承认共池」，没裁「谁叫平台自动重写」。

6. **「同一块门卡至多一个余量数字」在共池前提下是不充分的。** 共池意味着真实余量应为 `max_manual_repairs − (manual_repairs_used + repairs_used)`，而 `src/product/workspace_engine/review/routing.rs:606-609` 现在算的是：
```
606:                 attempts_used: history
607:                     .repairs_used
608:                     .saturating_add(history.manual_repairs_used),
609:                 manual_repairs_remaining: RunBudgets::default()
610:                     .max_manual_repairs
611:                     .saturating_sub(history.manual_repairs_used),
```
`attempts_used` 把两个账本相加，`manual_repairs_remaining` 却只减 `manual_repairs_used` —— 同一份快照内两个字段的算术口径不一致。**只显示一个数字**会把这份不一致固化成一个「看起来唯一、实际偏高」的数字。change 把账本合并列为「独立事项」，那么至少要在 REQ-CWS-GATE-02 里写明「显示的余量数字以 `attempts_used` 为扣减口径」，否则 G-2 会以「只有一个数字，但那个数字是错的」形态复发。

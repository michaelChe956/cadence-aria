## 2. ★ 五个最易漏点的实际处理方式（X1 / X2 / X3 / X18 / X25）

### X1 —— `StoreBackedProviderCapabilitySource::for_lc` 的双重职责 ⇒ 职责拆分 + 改名自证

**处理**：`for_lc` **已删除**（不是留别名）。新构造器名字把两件事都写进名字：

```rust
pub fn global_capability_with_lc_recipe_recheck(
    paths: ProductAppPaths,
    project_id: String,
    lc_id: String,
) -> Self {
    Self {
        store: ProviderCapabilityStore::new(paths.clone()),   // ← capability：项目级全局
        project_id,
        recipe_recheck: Some(RootRecipeCredentialRecheck {
            operations: AggregateInitializationOperationStore::for_lc(paths, &lc_id), // ← 通道：仍按 LC
            lc_id,
        }),
    }
}
```

**为什么这样**：名字自带两个作用域（`global_capability` + `lc_recipe_recheck`）⇒
下一个改这块的人**从签名就能看出**「能力是全局的、recipe 凭据是按 LC 的」，
不必再翻实现。旧的 `for_lc` 名字只像「能力按 LC」，且它同时挂了 operation
store ⇒ 半改状态下会骗人。

**结构体字段也各自加了作用域注释**（`store` = 项目级全局 / `recipe_recheck` = 按 LC）。

### X2 —— `revalidate(project_id, lc_id, provider)` 的 `lc_id` 不能盲删

**处理**：**参数保留**（public API 形状不变），但**职责被重新界定并落到实物**：

| lc_id 原承担 | 现在的归属 |
|---|---|
| 记录作用域 | ⇒ **项目级全局**（store 路径不再经 `lc_scope_root`） |
| 证据根作用域 | ⇒ **项目级全局**（`capability_evidence_root(paths, project_id)`，与全局记录同根） |
| 探针执行上下文 / 审计归属 | ⇒ **保留在探针资源身份里**：`resource_scope_id = format!("aria-capability-revalidate-{lc_id}-{uuid}")` |

**为什么这样**：证据根全局化后，`lc_id` 若原样跟着丢掉，探针工件就再也说不清
「这次核验是哪个 LC 的面板发起的」⇒ 审计归属丢失。故把它**下沉到探针的资源
身份**（`ProbeInvocation.scope` → `HostOpenProbeScope.resource_scope_id`），
而不是让它继续决定落盘作用域。

**连带**：`ProbeScope` 私有结构体的 `lc_id` 字段**已删**（它原本只服务于记录
作用域 + 证据根，两处都全局化后是纯噪音）；`capability_snapshot(project_id,
lc_id)` 的 `lc_id` 参数**已删**（投影与 LC 无关）；`select_aggregate_provider*`
的 `lc_id` 参数**已删**（L2 读全局 ⇒ 选择结论与 LC 无关）。三处都是「**删掉
会说谎的参数**」，不是「留一个没人用的参数」。

### X18 —— `provider_selection.rs` 两个测试场景靠不同 `lc_id` 区分 ⇒ 重做为记录内容/项目内容区分

**原状**（`launch_cell_state_and_require_supported_agree_on_every_input`）：
4 个 case（confirmed / denied / unknown / record-missing）各写一个 `lc_id`
子树来隔离；另一个场景（snapshot 漂移）读 `"lc_confirmed"` 子树。
**全局化后这个区分方式失效**（全部落同一份全局文件 ⇒ 互相覆盖）。

**处理（未删断言、未放宽强度）**：

1. `write_records` 的第二参由 `lc_id` 改为 **`project_id`**（语义显式化）。
2. 4 个 case 改为**不同项目**（= 全局作用域的真实边界）：
   `project_confirmed` / `project_denied` / `project_unknown` / `project_missing`
   ⇒ 每个 case 仍断言**同一套** `LaunchCellState`（Confirmed / Denied{reason} /
   Unverified{unknown 文案} / Unverified{记录缺失文案}）+ 同一套 gateway 同意断言
   + 同一套 `EvidenceStale` 断言。
3. **snapshot 漂移场景**：改为读**同一个项目**（`project_confirmed`）的全局记录，
   但用**不同的快照引用**（`ProviderRef::pi("cap_other_snapshot")`）去问它 ⇒
   区分方式从「不同 lc_id」变成「**记录内容 / 查询内容不同**」。

**另外 6 处 `write_records(&paths, "lc_0001", …)`**（选择器其余用例）同样把
`"lc_0001"` 改为 `"project_0001"`（选择器实际读的项目）——这是同一处语义
迁移，不是断言改动。

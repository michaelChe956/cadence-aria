### 1.1 核心代码（关键行）

**元数据载体**（`root_recipe_snapshot.inc.rs`）：

```rust
pub struct SnapshotMeta {
    path: PathBuf,                 // canonical 相对路径
    kind: RootRecipeSnapshotEntryKind,
    size: u64,                     // 文件字节数
    mtime_ns: i128,                // 修改时间（Unix epoch 纳秒）
    link_target: Option<String>,
    special_type: Option<String>,
    escapes_root: bool,
    in_git: bool,                  // 是否属「成员 git 面」
}
```

> Plan §7.2 的契约字段是 `path`/`size`/`mtime_ns`；另加 `kind`/`link_target`/`special_type`/`escapes_root`/`in_git`——差分必须能识别「类型变了」「链接目标变了」，且必须能把「成员 git 面」与快照观测面分开。

**两遍扫描（只记元数据，不读内容）**：

```rust
fn scan_meta(root: &Path) -> Result<Vec<SnapshotMeta>, ProductStoreError>   // 第一遍 / 第二遍共用
fn walk_meta(root, dir, metas, ignores) -> Result<(), ProductStoreError>    // 递归采集元数据
fn collect_git_face(root, dir, metas) -> Result<(), ProductStoreError>       // .git 子树：只记元数据
fn meta_of(root, path, relative, file_type, in_git) -> Result<SnapshotMeta>  // 单路径元数据
```

**元数据差分（变更清单）**：

```rust
fn diff_meta<'a>(before: &'a [SnapshotMeta], after: &'a [SnapshotMeta]) -> Vec<MetaChange<'a>>
fn meta_equivalent(before: &SnapshotMeta, after: &SnapshotMeta) -> bool
```

`meta_equivalent` 的口径：**目录只看类型**（目录 mtime 会在任意子条目增删时变化，把它当变更会把「写一个文件」放大成「父目录也变了」的噪声；目录内容变化由子条目各自承载）；**普通文件看 size + mtime**；symlink 看链接目标；非常规条目看类型。

**预算计费（口径 = 本次变更量）**：

```rust
fn describe_changes(root, changes, budget, allowlist)
    -> Result<(Vec<RootRecipeObservedChange>, AuditCharge), ProductStoreError>
fn budget_failure(over_line_path, charge, budget) -> ProductStoreError
fn budget_group_key(relative, kind) -> String      // `<成员仓目录名>/<一级目录或 <文件>>`
fn budget_member(relative, kind) -> String         // 顶层文件归 `root`，其余按第一段目录名
```

**流式读（边读边计费，越限立刻停）**：

```rust
const AUDIT_READ_CHUNK: usize = 64 * 1024;
fn stream_file_digest(path, budget, charged) -> Result<StreamDigest, ProductStoreError>
```

64 KiB 分块；每块读完立刻 `charged += n` 并 `hasher.update`；`charged > max_bytes` **立刻 break**（不再读剩余内容）。

### 1.2 关键口径决策（与 Plan / spec 的对照）

| 口径 | 本片实现 | 依据 |
|---|---|---|
| 遍历 | **仍扫全仓两遍**（第一遍 before、第二遍 after），只用元数据 | REQ-AUD-01「保留全仓两遍扫描」+ Plan §0-2 |
| 读内容 | 只对**变更清单**里的、**现在还存在**的普通文件读 | REQ-AUD-01「只对变化文件读内容并计算哈希」 |
| `.git` | **不进快照条目、不计条目/字节、不读内容**；但其**元数据**单独采集 → 窗口内写 `.git` 仍判 `MemberGit`/`MemberWorktree` 越界 | REQ-AUD-02 场景 1/3 + Plan §7.2「分类保留」 |
| 预算 | `bytes`/`entries` **都只对进入变更清单的路径计**；未变化路径与 `.git` 子树一律不计 | REQ-AUD-01 + Plan §7.2 |
| 分组 | 键 = `<成员仓目录名>/<一级目录或 <文件>>`（`pms/target`、`root/AGENTS.md`）；**`.git` 永不入列** | Plan §7.2 |
| 内容摘要 | 新快照的 `content_digest` 恒为 `None`（内容哈希只落在变更项的 `after_digest`）；`before_digest` 恒为 `None` | 元数据差分法拿不到「变更前」的内容（要拿到就得读完整个仓） |

### 5.2 旧 receipt 与「恢复分支全树复验」的兼容缺口 —— **controller 判为真缺陷，已派单修**（2026-11-03）

**现状**：`src/web/handlers/aggregate_initialization/production_dependencies.inc.rs:740-780`（**非我独占，我没动**）用 `audit.after_snapshot.entries` 与重拍的 `fresh.entries` 做**逐条目相等**比较。新快照的 `content_digest` 恒为 `None`（元数据差分法不读未变更文件的内容），而**改造前**写下的旧 receipt 里 `content_digest` 有值 ⇒ 两者不再相等 ⇒ **改造前审计过的 operation 无法走「恢复」分支**（会误报 `path X changed since the audited final command`）。新 receipt 之间不受影响（两侧都是 `None`，条目级比较退化为 path/kind/link_target/special_type/escapes_root 比较）。

1. 比较侧需要能同时接受「旧 receipt（`content_digest = Some(...)`）」与「新 receipt（`content_digest = None`）」两种条目 ⇒ 或在比较时忽略 `content_digest` 字段（只比 path/kind/link_target/special_type/escapes_root），或在旧 receipt 反序列化时把 `content_digest` 归一为 `None`。
2. 无论哪种，都必须**保留**对「新 receipt vs 新 receipt」的敏感度（新旧条目在 path/kind/link_target/special_type/escapes_root 上的差异仍要能判出来）。

**⇒ 承接方（`OldReceiptCompat`）实际采用的是第三种、更严格的做法**（比「忽略摘要」严）：归一化只做在**恢复分支的比较侧**（旧条目的 `content_digest` 临时视为不可复验），**不动持久化格式、不动反序列化**（本片用例 `legacy_receipt_with_content_digests_still_deserializes` 不受影响）；且**不把旧摘要当成「内容没变」**——旧 receipt 带摘要 + 新快照无摘要而其余元数据一致时，**单列一档**「无法用旧摘要复验」并给出可执行动作（重跑末条审计命令以记录新的审计快照后再恢复），**不再**误报 `path X changed since the audited final command`；新 vs 新（两侧 `None`）时该判据恒 false，落回原 `changed` 分支，敏感度不变（并另有用例钉住）。

### 5.3 `before_digest` 恒为 `None`（口径的必然结果）

元数据差分法拿不到「变更前」的内容哈希——要拿到就得在命令执行前读完整个仓（= 退回旧口径）。所以新 receipt 的 `RootRecipeObservedChange.before_digest` 恒为 `None`，内容证据只在 `after_digest`；**旧 receipt 仍带 `before_digest`**（反序列化兼容 ✓，用例 T7 钉住）。

### 5.4 mtime 精度依赖

变更判定依赖 `size` + `mtime_ns`。Linux ext4/btrfs 是纳秒精度 ✓；秒级精度的文件系统（部分 NFS / FAT / HFS+）上「同秒内改写且大小不变」的文件可能漏检。这是 REQ-AUD-01 明文规定的方法（mtime 差分），不是实现取舍，但真实部署里值得知道。

### 5.5 目录不参与 mtime 判定（避免噪声）

`meta_equivalent` 对**目录只看类型**：目录 mtime 会在任意子条目增删时变化，把它当变更会把「写一个文件」放大成「父目录也变了」的噪声（并连带把父目录判成 `UnknownPath` 越界）。目录内容的增删由子条目各自承载 ✓；目录本身的新增/删除仍被检出（Added/Removed）✓。

### 5.6 载荷里两个字节口径的差异（有意为之）

- `cumulative_bytes` = 越限瞬间**已流式读到**的字节数（回答「读到哪儿越线了」，恒 `> max_bytes`）；
- `top_groups` / `member_summaries` = **本次变更清单**的已知体量（按元数据 size 聚合，回答「谁占得多」）。

越限点之后的内容还没读，所以两者不相等——这是有意的：分组排行要完整，越限中止时给半张榜没有意义。`.git` 永不入列 ✓（REQ-AUD-04）。

# 问题记录：勘察派工角色分级错误现场（2026-09-24 v1.0）

> **本文用途**：交给 `cadence-subagents-config` 项目的新会话。与 `2026-09-23_问题记录_controller绕过subagent派工现场_v1.0.md`（第一现场：该派不派）同属派工纪律改进线，本案是**第二现场：派了但派错层级**。核心问题一句话——**roster 把「勘察」当单一角色，controller 缺少「摸底级 vs 诊断级」的分级判定门禁，导致定案级诊断被派给 fast 模型的 scout。**

## 0. 给新会话的任务

1. 读本文 §2-§4 还原决策链与实证依据
2. 结合第一现场记录（路径见 §7），设计统一改进：两案共同根因是「派工决策没有难度/证据强度分级」，只是表现形式相反（第一案：亲自做；第二案：机械派工）
3. 产出 roster / subagent-protocol 的分级补丁（方向见 §5），保持分发链兼容
4. 用两个现场做回放验收：第一案理想行为=≤2 轮定位后转派；第二案理想行为=F-47/F-48 直接派诊断级角色（或 scout 只做摸底、定案升级）

## 1. 背景

- 2026-09-23 第一现场：controller 对用户对话中途的 bug 分析亲自做 23 轮勘察，被点名「为什么不用 subagents」→ 已记录并交本项目
- 2026-09-23 当晚 F-46 修复流程：scout（glm5.3-f-scout）出勘察报告 → design-task + oracle 复核时**发现 scout 两个实质性失误**（见 §3）
- 2026-09-24 第二现场：用户报两个新缺陷（F-47 token 刷新间歇 / F-48 plan EARS 编译失败），controller 两个都派了 glm5.3-f-scout，被点名「为什么勘察 bug 用 glm5.3-f-scout」

## 2. 决策过程还原（controller 自述，如实）

当时的决策链只有两步：
1. 任务定性：两个缺陷都需要「查根因」→ 匹配 roster 表格「勘察 | glm5.3-f-scout | 只读勘察」
2. 派工：两个 task 并行派 glm5.3-f-scout

**没有发生的判断**（复盘补）：
- 难度分级：F-47 需要「durable 数据统计 + 前端水合链路推理」跨前后端证据链；F-48 需要「statement 原文 vs 校验器规则交叉判定 + 终态链路追溯」——两者都是**对结论负责的定案级诊断**，不是「符号在哪/结构什么样」的摸底检索
- 历史教训对照：F-46 刚刚实证 scout 在同类诊断任务上的失误模式（§3），本次派工时未回顾
- 成本对照：F-46 实际链=scout 白跑一轮（结论被推翻）+design-task 重做+oracle 裁决；若首诊即派诊断级，省一轮往返

**矫枉过正动因（如实登记）**：第一现场被批后的矫正压力（「必须派工」）在决策中压过了「派对工」的判断。两个现场叠加看，controller 的派工决策在「全亲自」与「机械外包」之间摆荡，缺的正是中间的分级门禁。

## 3. F-46 实证的 scout 失误模式（glm5.3-f-scout = GLM-5.3-flash 通道）

| # | 失误 | 事实 | 后果 |
|---|---|---|---|
| 1 | 「最终产物原文未留存」误判 | durable session json 的 assistant.content 实有 19,921 字符完整原文；scout 把 read 工具的**长行展示截断**当成文件内容缺失（「read 展示截断≠文件截断」） | 根因定案缺一条腿（污染来源「模型 vs 提取器」无法定责）；design-task 用 python 直接 JSON 解析才推翻 |
| 2 | 报告落错仓 | 相对路径解析到主仓而非 worktree，controller 手动移正 | 轻微，但反映对多仓环境路径语义的把握不足 |
| 3 | 根因颗粒度 | scout 定案「provider 输出污染」方向对，但「原文未留存」错误直接改变修法空间评估（B 诊断留存面因此被高估，后被证伪降级） | oracle/design 基于错误前提做了一轮裁决，靠 design 主动重取证才纠偏 |

结论：flash 级通道做**摸底**（定位文件/列结构/找符号）胜任；做**定案**（多源证据交叉、工具输出可靠性辨别、结论影响修法方向）证据强度不足——F-46 是单案实证，样本量 1，但失误模式（工具输出误读、环境语义疏忽）与 fast 通道特性一致，供本项目判断是否泛化。

## 4. 本次两任务的实际难度（应为诊断级的依据）

- **F-47（token 刷新间歇）**：需先做 A/B 分叉判定（durable 时有时无=后端竞态 vs durable 恒有=前端水合竞态）——要求统计多个会话的 node detail、再沿 TimelineNodeList/workspace-chat-rebuild 的水合链路推理刷新时序；判错 A/B 整个修复方向错
- **F-48（plan EARS 失败终态）**：要求把 author 原文第 158/193 行 statement 与 EARS 校验器合法句式集逐字比对（真不合规 vs 校验器过严），再追溯 outcome 分类为何走终态而非返修——三个答案都直接决定修法分层（改 prompt / 改校验器 / 改恢复链），且可能达 OpenSpec 立项阈值

两者都满足「结论影响修法方向 + 多源交叉 + 工具输出需可靠性辨别」的诊断级特征。

## 5. 给本项目的改进方向（供参考，非定案）

1. **勘察分级**：roster「勘察」拆两档或加判定门禁——
   - 摸底级（定位/结构/清单，结论仅作线索）：glm5.3-f-scout
   - 诊断级（根因定案/证据交叉/结论影响修法）：design-task 或 ds-task 起，必要时 oracle 裁决
   - 判定问句建议：「这个结论错了会不会带偏修法方向？」「是否需要辨别工具输出截断/缓存等假象？」任一为是→诊断级
2. **scout 报告采信纪律**：controller 对 scout 的「否定性结论」（「X 不存在」「原文未留存」类）在用于定案前须独立复核一次（一次 grep/read 级验证，不算亲自勘察）——F-46 失误 1 即否定性结论
3. **矫正压力登记**：第一现场的教训是「别亲自做」，但要防矫枉过正成「机械外包」——两个教训应写进同一节，以「分级」统摄
4. **回放验收**：见 §0.4

- 该处置与 §5.2 采信纪律一致，作为改进建议的即时演练

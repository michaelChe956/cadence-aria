# 分析: 四 Provider 沙箱现状与解决路线(cadence-aria)

- 出具: max-task (ProviderSandboxMap), 2026-10-16, 受测试会话委托; 只读调查, 源码证据均物理文件复核
- 关联: 2026-10-16_分析-pi与kimi执行环境差异.md / 2026-10-16_分析-无沙箱路线安全护栏论证.md / 2026-10-16_调研-四CLI沙箱机制与业界实践.md

## 一、结论先行

1. **四家不存在同一种「沙箱导致无法验证」问题**: Kimi Auto=强制 bwrap(写隔离+断网+环境净化); Codex LC=原生 read-only/workspace-write(非 Kimi 同款); Claude Code=**平台未强制 OS 沙箱且 Bash 未被移除**(Auto 桥自动批准); Pi=内建 Bash 不经 Aria 桥宿主直跑
2. **三个决策误判必须纠正**: ①Claude `--allowedTools` 是免审批名单**不是工具白名单**(`--tools` 才是, 官方文档证实); ②Kimi **Supervised 审批后宿主直接执行无 bwrap**(spec 明确允许, 改语义需契约变更); ③`danger-full-access` 未全产品消失——**LC 路径拒绝它, 非 LC direct coder 路径仍在使用**(不能作为绕过 REQ-LCG-04 的后门)
3. 「统一 Pi 式不沙箱」两种含义: 同账号共享宿主裸跑(能力最强但无防注入/target-only 保证) vs **专用低权限执行宿主上的直跑**(边界从逐命令沙箱移到会话执行环境, 不是消除隔离)
4. ProviderBoundaryLauncher 值得投产但非万能: 只约束 Pi/Claude 本地工具子进程, **管不了 Aria 另起的 Kimi ACP terminal**; 当前主要是写边界(保留网络/继承环境/宿主只读可见+放行四家五个 HOME 路径); 已实现未接生产
5. 推荐**统一「可证明的执行保证」而非统一沙箱开关**: 按 owner 倾向优先评估「专用低权限执行宿主直跑」; Codex LC 保留受限模式, 要全放开必须先正式变更 REQ-LCG-04

### 执行/权限/隔离
| 维度 | Claude | Codex | Kimi | Pi |

| 命令网络 | 未隔离 | workspace-write 默认禁网但**未显式钉死网络字段**(配置可改) | Auto 新 netns; Supervised 宿主网络 | 宿主网络 |

| 角色 | 判断 | 真正限制 |
|---|---|---|

## 三、三个边界事实(细节)

### Claude
LC argv=--allowedTools Read,Glob,... --permission-prompt-tool=stdio; 策略角色加 --disallowedTools Edit,Write,NotebookEdit。**无 --tools 限制, 无 Bash deny**(projection.rs:37-44; mod.rs:346-384; 官方 CLI 文档)。Aria Auto/Supervised 都设 CLI "default", 区别只在桥怎么答(mod.rs:178-182,580-604)。源码注释「只读 allowlist」不足以证明 Bash 被禁。

### Codex
LC 投影: Planning/Review→read-only, Coding→workspace-write(projection.rs:48-92,172-190)。thread/start 只传 cwd/approvalPolicy/sandbox, **无显式网络开关**(session.rs:73-98)——官方 workspace-write 网络可由 config 开, 不能凭 mode 宣称网络冻结。direct coder tool_policy=None→CODEX_DEFAULT_SANDBOX_MODE="danger-full-access"(session.rs:49-70; mod.rs:43-47), 非 LC provider.start 仍是有效生产分支(launch.rs:44-82)。**待验收风险**: commandExecution 审批转普通 approve/deny, 未保留独立「请求跳出沙箱」判断(parse.rs:12-19,246-286); [INFERENCE] LC Supervised 批准原生提升可能单命令越界, 未实测。

### Kimi
Auto 真实边界(sandbox.rs:435-539): / 只读+私有 /tmp+unshare-net/pid+no-new-privs+target 可写+冻结 git 路径 rw。**非保密边界**(宿主文件只读可见, mod.rs:296-303 注释自认「写边界非读边界」); target 内 .aria/.git 指针不受保护。Supervised: terminal_handlers.rs:114-116 返回 Unavailable, terminal.rs:524-533 直接 Command::new; **spec.md:109-128 明确允许 Supervised 经审批非隔离执行**——改语义需契约变更。脚本通道: bash/sh -c <script> 整段保留(terminal_handlers.rs:205-255), 与 spec 封闭 grammar 要求(:84-103)偏离——Auto 靠 bwrap 兜底, Supervised 只剩人工审批+固定环境。另有 4 终端/1MiB/120s 限制。

## 四、产品 role→provider 映射
无固定「Claude 规划/Kimi 写码/Pi 评审」映射; 四家 adapter 均注册(state.rs:514-548), 实际受健康检查/capability/网关门禁约束。Coding 三角色(coder/code_reviewer/internal_reviewer)由 attempt role snapshot 独立配置; 只有 Pi 被强制 Auto。**含义: Kimi 当 reviewer 不能跑 terminal 是角色策略; Pi 当 reviewer 能起容器是执行权限; reviewer 名称不是更高可信度——运行待审代码=执行不可信程序。**

## 五、launcher 投产边界
已有: / 只读+target 可写+私有 tmp+.git/.aria/protected roots 后置只读+不断网不清环境+**放行四家五个 HOME 路径**(provider_boundary.rs:188-216,261-335)。保留问题: ①五路径是四家并集非按 provider 最小化(跨 provider 配置污染面); ②只读≠保密; ③[INFERENCE] 不能自动封 socket/外部 daemon/远端 MCP; ④保留网络≠保留 Podman 可用(未实测); ⑤write_boundary 恒 Unknown 不能自动改 Confirmed。
逐家接入: Claude=CLI+后代进写边界(审批不得突破外层); Pi=内建 Bash 受约束(**可能破坏现有宿主 Podman 工作方式**); Codex=补外层+仍需钉死 native 网络/提升; **Kimi=ACP terminal 是 Aria 另起进程必须独立消费同源政策, 只包 CLI 没用**。
两个投产依赖: ①根初始化 recipe 相位(Claude Executor+PlanningReadOnly+bootstrap marker)不能套普通边界; ②capability 过渡桥(Unknown+legacy 放行)必须以真实正负探针替换。

## 六、路线图

### 四家最低保证(结果合同, 非同参数)
1. 执行 profile 与审批模式分离(Auto/Supervised 只决定谁批准, 不暗中决定宿主权限)
2. 明确谁能写什么(target/验证 scratch/缓存/runtime/git 元数据/.aria 分别授权; 需要验证的 reviewer 明确获得 scratch 权限而非标「只读」)
3. 执行能力前置声明(JDK/Maven/Node/缓存/联网/容器/时长逐项匹配 CHECK; 缺能力准确报告, 不让 coder 自救)
4. 凭据与控制面不进普通命令权限域(盘上凭据/.aria/控制 API/容器 socket)
5. 相同有效配置可审计复验(exact 版本/argv/网络写集合/MCP 来源/审批留证; digest≠物理探针)
6. 命令和资源可回收(进程组清理≠容器网络卷回收; 验证产物不混交付树)

### 路线比较
| 路线 | 安全 | 验证能力 | 成本 | REQ-LCG-04 |
|---|---|---|---|---|
| 补齐受限环境运行时/缓存(保 native/bwrap) | 较清晰但有读边界/MCP 缺口 | 本地编译可改善; Kimi Podman 仍结构受限 | 低-中 | 兼容 |
| launcher 加固投产 | 改善写边界≠完整隔离 | 普通构建可; 原 Pi Podman 原样不保证 | 中 | 兼容 |
| **专用低权限执行宿主直跑** | 显著缩影响面(取决于身份/数据/凭据/网络/控制面隔离) | **最接近 owner 要的直跑体验** | 中-高 | Codex 保留 native 时兼容 |
| 同账号四家裸跑 | 无可靠防注入/target-only | 最高 | 初低后高 | **LC Codex 明确不兼容** |

专用宿主与已否决方案的区别: **同一 Provider 会话自己直接执行, Podman 在专用宿主普通运行, 不新增逐命令代跑 runner, 不把容器塞回 Kimi bwrap。**

### 专用宿主必要护栏
专用低权用户(不与 Aria 控制进程/开发者账号共权); 仅放本会话仓库数据; 工具链/缓存/容器存储会话作用域; 凭据最小权限短生命周期(可任意 shell 同用户=承认可读, 不靠提示词保密); 不暴露高权容器 socket/SSH agent/Aria 管理 API; MCP/配置来源固定入威胁模型; reviewer 验证用受控 scratch; CPU/内存/磁盘/容器网络生命周期上限。**护栏不保证不受注入, 是把注入成功的损失控制在可承受范围。**
若连身份/数据/网络/控制面分离也拒绝(同账号裸跑)→只能定义**显式 trusted-host 风险接受模式**, 不得标为满足 LC 安全合同。

### 实施三阶段
1. **统一事实与契约**: 修正三误判; 明确角色需静态读/改码/动态验证; 选定执行环境路线成正式契约; 四家全放开则显式改 REQ-LCG-04/只读证据要求/Kimi 权限规范(不新增隐藏回退)
2. **先环境供应后权限调整**: CHECK 配运行时/依赖/缓存/scratch; 受限路线=launcher+Kimi ACP 独立接入+Codex 验证 native; 专用宿主=先身份/凭据/控制面/产物隔离再放开; 根 recipe 相位独立接
3. **真实行为证据切门禁**: 逐 action/profile/fresh/resume 验证正向写+负向越界+网络凭据 socket 边界+Codex 提升+Kimi 双模式+资源回收; 证据齐全才 Confirmed 并关 Unknown 过渡桥

## 七、最终推荐与反方风险
**推荐: 接受 owner 要的「Provider 自主直接执行」体验, 但不接受「同账号裸跑=安全可行」。**
1. 统一执行 profile 与最低保证, 不统一沙箱实现; 2. 动态验证落专用低权限执行宿主, 命令由原 Provider 直接执行; 3. Codex LC 暂保留受限至正式变更 REQ-LCG-04; 4. launcher 用作选定动作写边界, Kimi ACP 单独治理; 5. 不以切 Supervised/direct/Pi 绕过安全门。
反方风险: 专用环境增加部署/缓存/凭据/回收复杂度; 收紧可能破坏配置发现/会话恢复/Git/Podman(需实测); 只放宽 reviewer 仍防不住恶意仓库脚本/依赖钩子; 保留全宿主可读可联网同控制面的路线无法靠审计/提示词恢复预防边界。

# 分析报告: 为什么 pi reviewer 能跑 podman, 而 kimi coder 不能

- 分析人: design-task (PiKimiRuntimeDiff), 2026-10-16, 受测试会话委托
- 仓库: feat-b-0808-add-monorepo worktree (只读分析)
- 状态: DONE_WITH_CONCERNS (未验证项见第 4 节)

## 0. 结论

**根因是两个 provider 的命令通道不同, 不是同一个沙箱的不同配额.**

- **kimi coder** 的命令走 Aria 宿主 ACP `terminal/*` 服务, 被强制套进 Aria 自建的 bwrap 沙箱, 参数是 `--unshare-net --clearenv --ro-bind / /`(`kimi_code_provider/.../sandbox.rs:450-465`). podman 在这个环境里先后死在两处: `/run/user/1000/libpod` 只读, 以及 `newuidmap: Could not set caps`.
- **pi reviewer** 的 `bash` 是 pi CLI 自带的内建工具. pi 以 `ProcessManager::spawn` 直接作为宿主进程启动, 继承宿主环境和网络, 没有任何 OS 沙箱(`pi_provider/mod.rs:665,983`). podman 在用户自己的 rootless 环境里直接可用.
- pi 的唯一"限制"是 `--exclude-tools edit,write`(`pi_provider/mod.rs:48-52`), 它只是工具名黑名单, 不限制 `bash` 能做什么.

**这是设计形成的结果, 但 pi 一侧是已记录的残余风险, 不是被认可的能力.**

- 设计文档明说 pi 的 terminal 是"显式逃逸面, 未验证只读边界即 Unknown"(`openspec/changes/lc-gateway-multi-provider/design.md:40`).
- 能收紧 pi 的产品级 launcher(`ProviderBoundaryLauncher`,`provider_boundary.rs:219-258`)只在探针中使用, 生产路径没有调用它.

## 1. 证据链

### 1.1 两家 provider 的启动与命令通道

| 项 | pi reviewer | kimi coder |
|---|---|---|
| 实现模块 | `src/cross_cutting/pi_provider/` | `src/cross_cutting/kimi_code_provider/` |
| 进程启动 | `ProcessManager::spawn`: 继承宿主环境, 不套 bwrap(`mod.rs:665,983`) | 同样 `ProcessManager::spawn`(`mod.rs:367,631`), 进程本身无沙箱 |
| 命令执行方 | pi 内建 `bash`, 直接 fork 宿主进程 | ACP `terminal/create` 由 Aria 宿主执行(`client_services/mod.rs:44-49,239`) |
| 沙箱 | 无, 审计里 `sandbox: None`(`mod.rs:720,1058`) | bwrap 强制, Auto 模式无 bwrap 直接拒绝(`terminal_handlers.rs:72-118`) |
| 网络 | 继承宿主 | `--unshare-net`(`sandbox.rs:459`) |
| 环境变量 | 继承(`process_manager.rs:302`) | `--clearenv`, 仅放行 PATH/HOME/TMPDIR/LANG(`terminal.rs:342-347`) |
| 文件系统 | 宿主原样, 仅 `edit`/`write` 被排除 | `--ro-bind / /`, 仅 worktree+git 目录 rw(`sandbox.rs:447,490-504`) |
| 命令语法 | 无限制 | 仅 `bash`/`sh -c` 单命令(`terminal_handlers.rs:210-228`) |
| 权限模式 | 只支持 Auto, `bash` 直接执行(`pi-provider-integration/spec.md:55-56`) | 本次 attempt 为 Auto |

### 1.2 现场证据: pi 的 podman 链路

`role-run-events/coding_role_run_0003.jsonl`(provider=pi, cwd=/tmp/test-center-java):
- 事件 139-140: `command -v podman` → `/usr/sbin/podman` 6.1.1
- 事件 172-173: `podman run -v <worktree>:/ws -v /tmp/test-m2-cache:/root/.m2 ... mvn -B package` → BUILD SUCCESS
- 事件 239-244: 创建网络 `review-net-3358`, 起 mysql:8.0 + busi 容器
- 事件 265: `podman exec` 查库; 事后自行清理

### 1.3 现场证据: kimi 的 podman 失败

`provider-raw/coding/provider_stream_attempt_0001.txt`:
- `chmod /run/user/1000/libpod: read-only file system`
- `newuidmap` 受限; 无外网; coder 自述"podman/crun 不可用(no new privileges + /run 只读 + 无镜像)"

### 1.4 复现实验

用 kimi 同款 bwrap 参数复现: A=同款 read-only 报错; B=XDG_RUNTIME_DIR 指到 tmpfs 后 `newuidmap: Could not set caps`; C=bwrap 0.11.2 no-new-privs 强制(`sandbox.rs:462-464`), setuid/file-capability 的 newuidmap 无法提权.
**kimi 链路 podman 不可用是结构性必然**(ro-bind+unshare-net+no-new-privs+clearenv 四叠加), 不是漏配开关.

### 1.5 spec 与设计意图

- kimi: spec 明确要求"OS 级隔离…只读根文件系统、无网络、有限 /tmp、无新特权"(`openspec/specs/kimi-acp-client-services/spec.md:113`)
- pi: spec 只写 Auto 下 `bash` 直接执行, 无沙箱需求(`pi-provider-integration/spec.md:55-56`)
- design.md:40 承认 pi terminal 是显式逃逸面; :42 给出补救"产品拥有的 OS sandbox launcher"= `ProviderBoundaryLauncher`, 但只被探针路径使用(`provider_boundary_probe.rs:563,1277`), 生产 pi/claude/kimi 的 `start_validated` 均未调用
- `write_boundary_state()` 恒返回 `Unknown`(`provider_boundary.rs:253-255`), `production_policy_resolvers.rs:354-358` 对 Unknown+旧 allow 列表放行——pi 无边界仍能启动的制度原因

## 2. 影响评估

1. **宿主权限等同运行用户**: 现场 pi 可写挂载 worktree 进容器、建删容器与网络、访问宿主缓存; "只读 reviewer"身份在 edit/write 之外无物理约束
2. **可绕过 --exclude-tools edit,write**: bash 的 sed -i/重定向/git/podman -v 均可写任意 rw 目录(设计已承认的残余面, 本次现场证明真实存在)
3. **prompt injection 面比 kimi 大**(推断, 未做注入实验): reviewer 读的 diff/源码/依赖文件均为不可信输入, 可诱导 pi 以宿主用户+网络执行任意命令(外传凭据等)
4. **评审者能验证、实现者不能验证的不对称**: 同一 attempt 内 pi 拿到真实运行证据, kimi 只能如实报 blocked——coder CHECK 证据缺失的直接原因
5. 与 REQ-LCG-04 不冲突(它只约束 Codex), 但违背其设计原则("逻辑 writable root 不能替代物理边界", design.md:61); 属**治理缺口**: 各 provider 沙箱强度无对齐的最低保证

## 3. 结论与建议

- kimi 不能跑 podman: **设计如此**(spec 要求), 换配置无解
- pi 能跑 podman: **spec 允许+设计文档承认的残余面, 生产未接缓解**(launcher 已实现未投产)

建议:
1. (推荐) 不给 kimi 沙箱开 podman, 走**受控验证 runner**(即 CHECK 预声明命令+Aria 宿主 podman 代跑+网络白名单, 可复用 `bounded_command_runner.rs`); coder/reviewer 共用证据, 消除不对称
2. 收紧 pi 使两家最低保证对齐: a) `--tools` 只读白名单(最小); b) `pi_provider::start_validated` 改用 `spawn_with_boundary`(已有, `process_manager.rs:344`), 但会使 reviewer 也不能跑 podman, 必须与建议 1 同步上线; c) 保持现状但 spec 正式记录风险(短期过渡)
3. 收口 `write_boundary=Unknown` 放行过渡桥(`production_policy_resolvers.rs:354-358`): launcher 接入+probe 确认后移出 allow 列表
4. 挂载层面: coder 验证→平台宿主层(bounded_command_runner+CHECK 通道); reviewer 物理只读→provider 启动层; 能力状态→能力门; REQ-LCG-04 无需改动

## Q1｜进同一张表：具体输入、输出与调用链

### 1.1 输入类型：共享事实，不共享业务记录

在块2拟新建 `src/product/logical_codebase/failure_copy.rs` 内采用以下**设计签名**，不在本次写实现：

```rust
pub struct FailureInput<'a> {
    pub reason_code: &'a str,
    pub stage: Option<&'a str>,
    pub cause: Option<&'a str>,
    pub provider: Option<&'a str>,
    pub detail: Option<&'a str>,
    pub action: Option<&'a str>,
    pub subject: Option<&'a str>,
}

pub fn describe(input: FailureInput<'_>) -> FailureCopy;

pub struct FailureCopy {
    pub title_zh: String,
    pub reason_zh: String,
    pub action_zh: String,
    pub triage: FailureTriage,
    pub machine_line: String,
}
```

- 只有 reason_code 必填；字段借用，不为适配另造、克隆一个初始化记录。stage/cause/provider 保留块2既有步骤/确定性原因/provider 分流能力，不能简化到 code 后让已有验收缩水。
- 实现 `From<&AggregateInitializationErrorRecord> for FailureInput`：借用 reason_code/stage、片1拟加入的 cause/provider、stderr_summary 和非空 action。旧拟定调用统一迁移为 `describe(FailureInput::from(&record))`。
- 索引输入直接取 code/warning，`action=None`；预检输入取 error.code()/message()，由产品层 `AggregateRootPreflightError::copy()` 封装。该方法只做输入适配并委派 describe，**不自持表**。
- `action` 是原始诊断，不是中文动作来源；绝不把非空 record.action 直接提升为 action_zh。action/detail 脱敏后放原始诊断折叠区；已知码动作只来自模板，未知码只来自共享中文兜底。
- **唯一推荐：`reason_zh: String`，不是 Option；`FailureCopy` 五个字段全部必填。码表每一条必须给出非空 `reason_zh`，七个布局码必须给出具体规则依据；不可确定原因的非布局条目也必须如实写“原因尚未确定”，而不是缺字段、空串或编造原因。** 它与 durable cause 子码分工不同。
- machine_line 保留实际收到的原始码；若内部码命中别名，不改写成另一机器码。统一模板/别名表以对外稳定码为 canonical key。
- 原 `describe_code` 不再独立保留另一套匹配/兜底；拟定入口尚未实现，可直接统一迁移到 describe，无需兼容别名。`copy()` 方法是产品对象适配入口，不是兼容旧查表入口。
- 文本序列化器明确为 `render_detail(copy: &FailureCopy, sanitized_detail: Option<&str>) -> String`：问题 → 原因 → 怎么做 → 机器码 → 脱敏原文。五字段必有，序列化器只序列化成品，不再把固定四行当作三段协议。

对象填充也在同源边界完成：登记/索引已有的英文消息中，已知格式包含成员/root/占用方（见 §1），共享模块可定向提取后填入模板；已有 item.path 时直接借用 subject。识别不出不编造事实，不能让块3另翻译一份问题句。主标题应点名可确认对象，`frontend` 场景的动作能落到 `<LC根>/frontend/`。

### 1.1.1 FailureCopy 完整字段合同（给块2实现与块3消费）

| 字段 | Rust类型 | Option/可缺失 | 语义与生成责任 | 对外DTO/TS |
|---|---|---|---|---|
| `title_zh` | `String` | 否，非空 | **问题**：中文主标题；点名可确认对象，不把机器码当标题；仅由共享模板生成 | 必填 `string` |
| `reason_zh` | `String` | **否，非空** | **原因**：布局码给出具体规则依据/已确认检查失败原因；非布局无法确定时诚实写中性未知原因；仅由共享模板生成 | **必填 `string`，不得 `?`/`null`** |
| `action_zh` | `String` | 否，非空 | **怎么做**：明确安装/移动路径/检查权限/重试等可执行下一步；不是原始 `record.action` 的复制 | 必填 `string` |
| `triage` | `FailureTriage` | 否 | 三值枚举 `Environment` / `ProductDefect` / `RetryOnly`；序列化为 `environment` / `product_defect` / `retry_only`，不可用任意字符串漂移 | 必填三值联合类型 |
| `machine_line` | `String` | 否，非空 | 原始输入机器码的**降级展示位**，次要行/折叠区；原始输出另走已脱敏的detail，不与中文主标题混合 | 必填 `string` |

Rust `FailureCopyDto`、`ApiError.details.copy` 对象和 TS `FailureCopyDto` 必须是这五字段的同构结果；不允许后端有 `reason_zh` 但Rust DTO漏搬，或TS把它改成可选以掩盖断链。`BootstrapFailure.copy` 这个外层载体是否因既有非失败投影形态使用Option，不改变**一旦存在copy，其五个字段全部必填**的合同；七个已知布局失败必须产生copy。

**选择非Option的理由**：当前失败来源本来就要求中文可执行说明；统一的五字段结果让两条链、DTO与组件无需“布局特殊分支”决定是否有原因，且使漏项在构造/类型检查时显现。原因不可判定与字段不存在不是一回事：前者用诚实的中性文字承载，不靠空串/None表示。

### 1.1.2 码表外未知码的唯一中性兜底

未知码例如 `unknown_failure_xyz` 仍返回完整五字段，不panic，不使用英文原文替代中文主标题：

| 字段 | 兜底产物 |
|---|---|
| title_zh | `本次操作未完成`（有可信subject时可点名该对象） |
| reason_zh | `当前无法确定具体原因，请查看下方诊断信息。` |
| action_zh | `请重试；连续两次仍失败时，提交问题并附上机器码与下方诊断信息。` |
| triage | `ProductDefect`（未知失败的分诊入口，不据此编造确定根因） |
| machine_line | 原码 `unknown_failure_xyz` |

这是一组**中性三段**，不是伪造具体布局原因。`REQ-LAYOUT-02` 要求具体规则依据和布局处置动作的对象，是已登记的布局错误码；真正码表外的未知码不属于该七码集合，使用诚实的中性兜底不违反该条。但**不能**把任一已知布局码/现有别名因漏登记、DTO漏字段、查表失败而改称未知码；这属于实现缺陷，不能用兜底当验收通过。后续若新增布局码，必须先同源登记完整三段再允许对外呈现。

### 7.1 复核结论：同一码有两类产出时序，fail_building不是全部Failed的必经出口

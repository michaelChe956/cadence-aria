## Q2. `max_repairs` 是什么？`repairs_used_delta` 谁写？与 REQ-WSC-21 一致吗？

**结论：`max_repairs`（默认 1）是「评审发现→机械聚合返修」的轮内预算，即 REQ-WSC-21 亲口命名的「机械返修池」；与契约完全一致。**

- **语义**：`ReviewCycleState.repairs_used` 文档（`types.rs:176-178`）：「Automatic repair consumption for this reviewed artifact only. Session totals remain observability counters and must not gate a new cycle」——**按被评审产物（outline/draft/batch）计周期**，不是会话级。
- **唯一生产写入点**：`routing.rs:623-637`——当路由动作是 `TriggerAggregateRepair`（评审发现可自动返修→平台聚合返修）时，`RunHistoryDelta { repairs_used_delta: 1, review_cycles_to_add: {cycle_key: {repairs_used: 1}} }` 原子合并；注释 :624-626「Keep the cross-cycle session total for observability, while consuming the automatic-repair budget only inside this artifact cycle」。
- **判定/执法**：`evaluate.rs:354-367`——存在可自动返修 finding 且 `phase==Initial && cycle_repairs_used < max_repairs` 才给 `Repairable`（继续机械返修）；否则 :369-376 `HumanRequired{RepairBudgetExhausted}`。合并校验 `evaluate.rs:465-472`：`manual_repairs_used <= max_manual_repairs && transitions_used <= max_transitions && 每轮 repairs_used <= max_repairs`。
- **注意**：`TriggerAggregateRepair` 是「不重跑 author 的机械 repair」（REQ-WSC-21 scenario :840 原话），**与**「平台自动重写（重跑 author）」是两回事——后者扣 B1 账本（`compile_failure_surface.rs:302-314`，AutoRewrite 路由 `used+1`），不碰 `repairs_used_delta`。
- **与 REQ-WSC-21 一致性**：一致。契约 :820 末句「`max_repairs`（机械返修池）MUST NOT 被当作自动重写预算」与代码注释 :131-132 逐字对应；`max_auto_rewrites()` 取的是 `max_manual_repairs`（:134）而非 `max_repairs`。

## Q3. `repair_budget_exhausted`（`evaluate.rs:373`）触发时扣的是哪个池？另一个池剩多少？

**结论：字面触发的是 A 池（机械返修池，轮内 `repairs_used >= max_repairs=1`）耗尽；B 池（author 重写预算，容量 3）此刻通常一笔未扣，剩 3。**

- `evaluate.rs:360` 的条件 `cycle_repairs_used < budgets.max_repairs` 只读 A 池轮内账本；不满足即 :373 `HumanReason::RepairBudgetExhausted`。
- 触发时 B 池状态：`auto_rewrites_used` 只在编译面 AutoRewrite 路由 +1（`compile_failure_surface.rs:313`），评审侧机械耗尽不动它；`manual_repairs_remaining` 只在门内反馈 turn CAS −1（`human_gate.rs:195`），同样不动。若此前无门内反馈，B2 剩 3、B1 剩 `3 − auto_rewrites_used`。
- 随后 SC 分流（`routing.rs:593-622`）：单候选计划 + durable 结构授权在场时，`TriggerAggregateRepair` **根本不执行**（:589-592 注释：零 `repairs_used`/轮内增量），改道人工门，快照字段：
  - `attempts_used = repairs_used + manual_repairs_used`（:605-607）
  - `manual_repairs_remaining = 3 − manual_repairs_used`（:608-610，生产恒 3−0=3）
  - `trigger = RepairBudgetExhausted`（:611，**该分支的固定标签**，见 Q4）
- **重要**：SC 分流条件（:593-595）不检查任何预算，**首次**可返修 finding 也会带着 `trigger=RepairBudgetExhausted` 开门——此时 A 池实际用量为 0，「已用完」三个字在该路径上是标签复用，不是真实计数陈述。

## 裁决草案（供会审比对）

**一句话：owner 与主 agent 各对一层，分歧源于把「池的语义定义」与「账本的实现现状」混为一谈；真实结构是「一个语义池、两处未合并账本、两套执法」。**

1. **owner 对语义**：「同一个预算池」指 B1（`auto_rewrites_used`）与 B2（`manual_repairs_remaining`）共用的 **author 重写次数预算**（容量 `max_manual_repairs`=3）——owner 裁定原文（`compile_failure_surface.rs:126-129`）自己就把 A 池（`max_repairs`=1 机械池）排除在「同一个池」之外（:131-132「另一个池……不得拿来当自动重写预算」）。REQ-WSC-21（`spec.md:820`）与交付说明 #3 同口径。
2. **主 agent 对执法**：B1/B2 在代码里确是两本独立的账、两处独立的执法（`decide_route` vs `human_gate.rs:181-186`），互不扣减、复位周期不同（B1 编译成功清零 `compile_failure_surface.rs:364-365`；B2 随 logical gate 生命周期 carry-forward），最坏合计 3+3=6 次 author 重写。但由此得出「两个独立的池」是**语义结论错误**——「未合并」是交付说明 #3 明文登记的**已知实现差距**，不是两池的设计意图；若按两池呈现，等于推翻 owner 裁定与 REQ-WSC-21 而无新裁定授权。
3. **主 agent 第 5 条证据的真实含义**：`human_gate.rs:195-201` 同 CAS 的两个计数是「**人工返修扣预算**（B2）」与「**人工说明回合计数**（C）」——它证明的是 B2 与 C 同步，**不是** B1 与 B2 分池。这组关系与 owner「同一个池」的 B1/B2 关系是两回事，论证里替换了主语。
4. **owner 现场不矛盾于账本、矛盾于文案**：两个数字分属 A 池事件标签与 B2 池余量（Q4 表），账本各自为真；「自动修复」一词被 A、B 两个池共用才是病灶（P1-5 早已记录）。修文案（G-2）即可消除，无需动账本。

### ② 账本 `binding_version` 差一代 —— **有问题（伪前提，任务 1.3 不成立）**

**v1.0 的原话（`cadence/notes/…_v1.0.md:122`）**：

> 「**账本 `binding_version` 会差一代**：`cas_internals.inc.rs:480-493` 在**变更前**用 `saved.binding_history.current.binding_version` 构造 `enable_ledger_entry`，而 `:500` 之后才（**甲-2 将要**）换代 ⇒ 账本条目的 `binding_version` 会落后一代。」

注意括号：「甲-2 将要」。这个隐患的成立前提是**在 `apply_revision_and_write` 的 Enable 重写分支里新增换代**（甲-2）。重写版把甲-2 作废、改在 `supersede_terminated_enrollment` 里放宽，于是：

**现状事实（terminated 路径）**：

```
706:    let binding_version = saved
707:        .binding_history
708:        .as_ref()
709:        .map(|history| history.current.binding_version + 1)
...
725:    next.command_ledger.push(EnrollmentCommandResult {
726:        command_id: command_id.to_string(),
727:        payload_digest: digest,
728:        state: OperationState::Accepted,
729:        binding_version,          ← 已是换代后的新版本号
730:    });
```

**账本条目构造已在换代之后，且显式用 `binding_version + 1`。差一代不存在。**

**`cas_internals.inc.rs:480-493` 是什么**：`apply_revision_and_write` 的 **non-terminated Enable 重写分支**（`:483-507`），该分支**不做换代**（注释 `:479-480`「binding_version 沿当前代，重开不换代」），因此用 `history.current.binding_version` 是**正确的**。若按任务 1.3 把它改成 `binding_version + 1`，会**制造**一个真实的差一代 bug。

**结论**：任务 1.3「命令账本条目构造移到换代之后（或显式传 `binding_version + 1`）」→ **应改写为**：

> 1.3（改写）「**验证** `supersede_terminated_enrollment` 的账本条目用的是换代后的 `binding_version`（现状 `:706-733` 已正确），**新增断言**锁定 `ledger.last().binding_version == binding_history.current.binding_version`；`apply_revision_and_write` 的 Enable 重写分支（`:480-493`）维持 `current` 不递增，不得改。」

### ③ 「换代 vs 同 payload 重开」判据 —— **有问题（判据需重写，否则复活甲-2）**

**现状判据（唯一）**：`terminated_at.is_some()`。

- `issue_automation_store.rs:167-181`：`(Some(saved), Enable{..}) if saved.terminated_at.is_some() => supersede_terminated_enrollment(...)`
- `issue_automation_store.rs:182-185`：`(Some(saved), _) if saved.terminated_at.is_some() => Conflict`
- 其余 Enable 落到 `apply_revision_and_write`，`:483-507` 的 Enable 重写臂：只改 `selection_key/source/options/target/enabled` + `policy_revision += 1`（`:500`），**保留** `plan_id/session_id/prepare_intent_id`、**不动** intent 文件、**不动** `binding_version`。

**⇒「同 payload 的 disable→enable 今天就不换代、不删 plan」。这是既有行为，不是本 change 要新增的东西。**

**tasks 1.2 原文**：

> 「1.2 写死「换代 vs 同 payload 重开」的判据：`options`/`selection_key`/`source`/`target` 任一不同才换代；同 payload 的 disable→enable **不得换代、不得删 plan**」

按字面实现 = 在 **disabled→Enable 路径**新增「payload 不同则换代」= **甲-2 复活**。这与 change 自身两处直接冲突：

| 冲突点 | 原文 |
|---|---|
proposal 决策 1 | 「原设计的「甲-1/甲-2/甲-3 版本号 workaround」**作废**——它们是为绕过那道硬门而存在的，门拆了就不需要」 |
design §1.3 | 「REQ-WIGA-02（enabled 状态下异 payload 的 Enable fail-closed）| **保持不变**。本设计只放宽 **terminated** 路径」 |

且会翻红 3 条 fail-closed 契约测试（见 ④）。

**结论**：任务 1.2 应改写为：

> 1.2（改写）「**换代主键＝`terminated_at`，`options` 从 terminated 路径的判据中退出**；`source`（非悬空）/`target` 漂移仍 fail-closed。**`apply_revision_and_write` 的 disabled→Enable 路径保持现状（不换代、不删 plan、intent 一致性 fail-closed 不变）**。新增回归测试：同 payload 与异 payload 的 disable→enable 均不轮换 `prepare_intent_id`、`binding_version` 不变、旧 plan 不被删。」

## 3. 跨项发现（主 agent 可能漏掉的）

### F-1 ★ 重写版把 v1.0 的「甲-2 细节」原样搬来，但甲-2 已作废 —— 最高风险

v1.0 §2.4/§2.5 的两条细节（「3 条契约测试」「账本差一代」）都是**为甲-2（disabled→Enable 换 payload 同时换代）准备的**。重写版决策 1 明确「甲-1/甲-2/甲-3 作废」，但 design §2.1 的细节 1/2/3 与 tasks 1.2/1.3/1.5 仍是甲-2 的文案。**后果**：

- 任务 1.2 会让 worker 在 `apply_revision_and_write` 里新增换代 → 翻红 3 条 fail-closed（`tests.rs:634-678` / `autopilot_orchestrator_parts/tests.inc.rs:232-265` / `automation_enrollment_tests_termination.inc.rs:135-170`）。
- 任务 1.3 会让 worker 改错分支（给不做换代的分支加 `+1`），**真的制造**差一代。
- 任务 1.5 会让 worker 找不到「3 条 terminated path 断言」，转而把那 3 条无关测试改掉。

**建议**：design §2.1 的细节 1/2/3 与 tasks 1.2/1.3/1.5 **整段重写**（我在 §2.2/§2.3/§2.4 给了可直接替换的文案）。

### F-2 ★ 「换代 vs 同 payload 重开」判据在本 change 里无事可做

一步完成路线只改 terminated 路径的一个条件表达式（删 `options` 项）。**disabled→enable 的换代判据与本次改动零交集**。delta spec 里 `REQ-WIGA-SWAP-01` 的 scenario「同 payload 的临时关闭再开不得换代」**恒真**（现状即如此）——它可以留作回归锁，但不能作为「本 change 要实现的新契约」。

### F-3 「无真实续跑入口」的判据在 WS 与 control 之间有**两套词汇**

- WS `session_status`（9 值，`models/workspace.rs:30-40`）
- control `stage`（`workspace_sc_recovery.rs:803-830`：`"terminated"/"failed"/"stopped_needs_human"/"generation_needs_human"/"waiting_for_human"/"unmanaged"`）

名字重叠但**计算源不同**：前者来自 session record，后者来自 `resolve_plan_stop`。设计说「主键是 durable sessionStatus」，而「可继续」的事实源是 control 的 `allowed_actions`。⇒ **新 WS 字段必须由 control 同一份判定派生**，否则会出现「sessionStatus=stopped_needs_human 但 plan_continue_available=false」的自相矛盾帧。这一点必须在 design 里写死（复用 `resolve_plan_stop`，不新写第二套）。

### F-4 换 provider 后「source 版本推进」仍会被 409 挡住 —— 但文案不能说是「运行中」

terminated + provider 变更 + **design spec 已重新确认到 v2**（source 变了但未悬空）→ `cas_internals:677` 仍 Conflict。这不是 owner 语义覆盖的场景，但**它就是「一次操作完成」会撞到的第二类拦截**。若判别位按函数聚合（把 supersede 的 Conflict 全标成「运行态限制」），owner 会看到「这个自动化正在运行中」——而它已终止。⇒ **#26 必须单独归类**（见 §2.6 表尾注）。

### F-5 前端 `providerChangePending` 的提示语包含三条链路假设

`WorkItemPlanOptionsDialog.tsx:395-411`：

```
404:                {providerChangePending
405:                  ? `；本次将应用：Author ${…}、Reviewer ${…}（重新开启后关闭再开启生效，其余参数按原授权）`
406:                  : "；本次按原授权重新开启（其余参数不变）。"}
```

塌缩后 `:405` 的括号注释是**假话**。这条文案是 owner 唯一能预知「点了会发生什么」的地方，且与 owner 决策 4（失败即空态）应当**同源告知**（「将先删除现有工作项组」）。建议在这里就加一句「换 provider 会先删除现有工作项组再重建」，比只靠失败面告知更符合「删了就是全部都删了」。

### F-6 `expected_revision` 与「一步完成」的一致性（未被任何 task 覆盖）

塌缩后步骤③消失，只发一条 Enable，`expected_revision` 取 `enrollment.policy_revision`（terminated 记录当前值）。这在 `cas_internals:661-664` 的线性化下是正确的 ✔。但**若 owner 在弹窗停留期间后台终止清理写了 attention fact**（`attest_attention_binding_locked` 不改 `policy_revision`，`cas_internals:155-177`）→ 不影响 ✔。**若后台 reconcile 触碰了 enrollment**（terminated 已阻断全部自动路径，`issue_automation_store.rs:182-185`）→ 不影响 ✔。**结论：不存在真并发风险**，可在 design 里补一句「terminated 记录无写入者」以关闭质疑。

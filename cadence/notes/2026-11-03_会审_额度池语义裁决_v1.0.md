## 裁决摘要

不能把问题压成「全是一个池」或「全是独立池」。必须区分三层：

1. **既有契约**：评审自动返修预算 A（`max_repairs`，默认每 cycle 1 次）独立于 author 重写预算 B（`max_manual_repairs`，默认 3 次）。B 的编译失败自动重写与 owner 反馈重写，按 REQ-WSC-21 应共用一份额度。
2. **实际实现**：A、编译失败重写账 B1（`auto_rewrites_used`）、门内反馈可用账 B2（`manual_repairs_remaining`）具有不同的读取/扣减/重置边界。当前核实的路径没有完成 B1/B2 共享执法；编译失败重写还会进入扣 A 的评审路由，违反 REQ-WSC-21 的不挪用约束。
3. **展示计数**：`accepted_feedback_turns` 是已接受人工反馈轮数，不是第三份额度；`attempts_used` 是不同来源累计数的相加，也不是共享池余额。

本文只覆盖本题的额度族；`max_transitions=12` 是另一条流转上限，不列为人工说明额度。结构 attempt、结构化输出修复与 Coding 返修预算也不借本次裁决扩界。

**G-2 应修正语义和展示，但不能靠隐藏数字、改名或前端算式冒充预算已经共池。完整修复必须包含后端预算归一；该行为变更需从纯呈现块中显式拆出并获范围批准。**

## Q1｜owner「同一个池」究竟指什么

明确指 **编译失败触发的平台自动重写 + owner 反馈触发的重写**。

`src/product/workspace_engine/compile_failure_surface.rs:123-135` 的原文逐项列明两者，并在 131-132 行明确排除 `RunBudgets::max_repairs`。它不是「同一类事」的模糊比喻，也不是说 `manual_repairs_remaining` 与 `accepted_feedback_turns` 是两份额度。REQ-WSC-21（`openspec/specs/work-item-plan-single-candidate/spec.md:818-840`）同样明确共池、不挪用机械返修池。

指定代码注释实际写的是「这是同一个预算池，两类重写都扣它」；「两处账本」是对实现落点的概括，不能把概括改写成注释逐字原文。

补充历史证据：`cadence/notes/2026-10-31_交付说明_候选编译失败呈现与自动重写_v1.0.md:54-59` 已把「两处预算账本未合并」列为当批未做事项，并规定编译重写呈现取 `auto_rewrite.remaining`。这证明是**已知未完成的落地差距**，不能证明两账已同步，也不能覆盖主 spec 的共池 MUST 或 REQ-HGC-01 的门反馈授权规则。

`src/product/lifecycle_store/human_gate.rs:188-222` 的同一 CAS 中，反馈预留使 B2 减 1、`accepted_feedback_turns` 加 1，并创建用户预算 hold：这是**同一次受理的可用额度变化和动作计数**，不是两个池。还要注意结构失败释放会退还 B2，而不撤销已受理的事实（`src/product/models/workspace.rs:538-567`）。所以已受理轮数也不等于最终收费轮数。

## Q2｜`max_repairs` 的真实行为

### 写入及执行链

- `evaluate.rs:349-376` 汇集 `MechanicalError | Repairable`，只有 Initial 且当前 cycle `repairs_used < max_repairs` 才给 `PlanOutcome::Repairable`；evaluator 不扣返修额度（同文件 98-102、427-457）。
- `review/policy_routing.rs:49-56` 把 Repairable 变成 `TriggerAggregateRepair`。
- `review/routing.rs:623-638` 在该 action 仍成立时生成 `repairs_used_delta: 1`，同时当前 cycle `repairs_used: 1`；二者合并到待持久化 history。`work_item_policy_action`（264-337）经 CAS 持久化 route，成功才派发。
- `review/routing.rs:717-722` 对无结构 grant 的 SingleCandidate 路径真实请求 `WorkItemPlanSingleCandidateAuthor`；不是不运行 author 的纯机械修补。
- `evaluate.rs:465-472` 对 A 按 cycle 执法，session `repairs_used` 不作为跨 cycle 配额。`manual_repairs_used` 与 `transitions_used` 仍分别有检查，因此不能把 types.rs:195-196 的 review-total 注释推广成「所有 session 数字都只是观测」。
- `review/routing_scope.rs:20-78,672-727` 进一步证明：repair action 预领 `single_candidate_author` 启动键和 repair reservation，与 history 一并送入 `compare_and_save_policy_route`；A 的消费落在授权／预领 CAS，不是 author 成功返回后才扣。

因此目前 UI 可称 A 为 **本轮评审自动返修**，不能无条件解释为「不重跑 author 的机械修补」。契约所称的机械池与这一具体执行行为不完全一致。

### 编译失败通道与契约冲突

`compile_failure_surface.rs:640-673` 将编译失败合成 verdict 送入 `single_candidate.rs:751-776` 的 prerevision → `complete_review`。`review/routing_platform_rescue.rs:93-155` 的专用恢复分支仍检查 `cycle.repairs_used < max_repairs`，恢复后又进入上述 repair delta 和 author 请求。它既受 B1 判定，又消费/受限于 A。这与 REQ-WSC-21:837-840「自动重写不得消耗 max_repairs」构成实际契约违背，不能只归为注释过期。

已有测试反而锁住这个冲突：`src/product/workspace_engine/tests/compile_failure_auto_rewrite.rs:191-265` 在同一个测试里，234-243 行断言请求 `WorkItemPlanSingleCandidateAuthor`，254-260 行又断言 `cycle.repairs_used == 1`。本次只读其源码、未运行测试。REQ-WSC-25（主 spec:885-897）只要求尝试可观测，并未豁免 WSC-21 的预算隔离；不能把受限制的 cycle 扣次重新解释为纯观测。

**Q-D 归类裁决：**「max_repairs 只用于不重跑 author」这句描述对现行普通 SC policy 路由不准确；但**编译失败重写消费／受限于 A**不止是注释过期，而是代码和现行规范的实质不一致。需另立后端缺陷处理，不在 G-2 文案变更里删除／放宽评审闸门。普通评审 policy 返修本来就包含模型返修，不能因为名字含 mechanical 就把所有 author 请求误改成确定性修补。

### `repair_budget_exhausted` 并不再扣任何池

该 trigger 表示一次路由结论，不是扣款事件。普通 Initial 配额耗尽分支反映 A 已达到上限；B2 没有因进入门而被扣，现场可以仍为 3。B1 的值无法由该 trigger 推出。

此外 trigger 还覆盖非数值耗尽：

| 生产分支 | 证据 | 为什么不能推导「剩余 0」 |
|---|---|---|
| Verification 阶段仍有可返修 findings | `evaluate.rs:355-373` | 即使 cycle repairs_used 为 0，也因不是 Initial 而走该 reason |
| 初评与复评槽均已使用 | `review/routing.rs:502-509` | 判据是 review 计数，不是 repair 次数 |
| SC 已有结构授权窗口，旧 policy repair 被拦 | `review/routing.rs:585-618` | 固定写此 trigger，且注释与后续分支保证零 repairs 增量 |

## Q3｜现场两句分别从哪里来

- 「自动修复次数已用完，需要你来定」来自 `gate_trigger=repair_budget_exhausted` 的固定文案映射：`web/src/components/chat-workspace/entries/gate-next-step.tsx:94-102`；`GatePromptEntry.tsx:564-565` 渲染。**它不是读取 `auto_rewrites_used=3` 得出的句子。**
- 「还可自动修复 3 次」来自 entry metadata 的 `remaining_budget`：`gate-card-metadata.ts:54-56` → `GatePromptEntry.tsx:153,570`。该数的业务来源是门反馈余额 B2，不是 A 的余额，也不能自动认作 B1/B2 的合并余额。
- `accepted_feedback_turns` 则由当前 store 的 `humanGateSnapshot` 读取（`GatePromptEntry.tsx:210-218`），与 metadata 中的余量不是同一取值方式。

完整前端投影链：`workspace-cockpit-gate-projection.ts::selectGateProjection:333-376` 在 typed turn 存在时，按 snapshot 身份是否替代 turn 选择 snapshot 余量或 `turn.remaining_budget`；无 turn 时 410-430 行直接取 snapshot 的 trigger 与 `manual_repairs_remaining`。`workspace-chat-rebuild.ts:638-651` 再将其写成 entry metadata。故修改 copy 不等于刷新已存在卡片；但也不能断言这些值永远不更新，state／projection 和 entry 更新是实际链条。

**现场这对值在数据上可合法并存，文案把不同事实叫成同一种「自动修复」，且把非数量停机原因说成数量耗尽，才制造表面矛盾。** 另一个独立存在的后端问题是 B1/B2 没有共享扣减；不能把后者当成这张现场卡已经证明 `auto_rewrites_used=3` 的证据。

另外，`manual_repairs_used` 的零写入不能推出门余额恒为 3。在本工作树 `src/product` 范围针对 `manual_repairs_used_delta|manual_repairs_used\s*[+]?=` 的检索，非零构造／直接赋值仅见测试；生产仅有 delta 定义和合并逻辑。更决定性的规范是 REQ-CG-02（`work-item-plan-conversational-gate/spec.md:197-205`）：真实用户 turn 不增加 policy counters。**初次构造**可以是 3，但 CAS 真扣与同门 carry-forward 同时存在；`routing_scope.rs:885-917` 明确区分二者。不得据此把现行反馈账标作「没接线」。

## Q4｜同屏只准一个余量数字是否如实

**作为无条件要求，不成立。**

- 不同预算域可以各自显示真实数字；只要标清作用域、用途和事实来源，不构成矛盾。
- 同一共享 author 预算应当只给一个经过后端证实的可用余额；但当前 B1/B2 未对齐，不能任选一个冒充共享真值，也不能隐藏另一个后宣称修复。
- 允许主行只有一个「当前可提交反馈轮数」，同时显示评审停止状态、已接受轮数及编译重写账面事实；这不等于全屏只能一个数字。
- 仅有 `repair_budget_exhausted` 时，A 只能显示中性停止状态，不能补造「0 次」。

## Q5／Q-A～Q-D｜具体裁决草案

### 命名

1. A：**本轮评审自动返修**，有独立 cycle 上限。
2. B：**候选重写共享额度**，触发方式分为「编译失败自动重写」与「按你的反馈重写」。这是既有契约目标，不是两个独立承诺额度。
3. C：**本门已接受反馈 N 轮**，纯历史动作计数，不叫额度、不叫已成功修复次数。

### 当前实现下必须采用的如实文案

普通现场卡：

> 本轮评审自动返修已停止，需要你决定下一步。\
> 本门还可提交修改反馈 3 轮。

若已有 C 则另外写「本门已接受反馈 N 轮」。余额大于 0 不代替连接、相位、失败状态等动作许可；不承诺自动运行或保证成功。

如果 B1 也存在且尚未证明与 B2 对齐，不显示虚构总余额，逐字分列：

> 编译失败重写账面剩余：R 次。\
> 本门反馈可提交：M 轮。\
> 两类重写按规则共用额度；当前记录尚未对齐，无法确认共享剩余额度。

这里 R 仅是 `auto_rewrite.remaining` 的编译账面事实，M 仅是当前 logical gate 的 `manual_repairs_remaining`。这两个数不是两份可叠加额度。对旧卡只显示历史快照，不冒充当前可用余额；当前卡应随 durable 快照重建/刷新。

**数字数量裁决：**普通门主行 1 个反馈余量，另可有 1 个已接受轮数；编译账同时存在而未对齐时显示 2 个分别命名的账面数字，并明确无法确认共享总余额；A 仅有 trigger 时显示状态不造数。若未来已有同一预算身份的共享权威，则 B 只显示 1 个共享余量，文案为「候选重写共享额度剩余 N 轮（编译失败自动重写与反馈修订共用）」；A 若确有自己的 durable 余量，可在同屏独立显示。**“同一池一个权威余额”成立，“全屏只许一个数字”不成立。**

### 余额怎么算

**不能采用 `3 - max(auto_rewrites_used, manual_repairs_used)`，也不能直接取两个余额的最小值或简单相减作为生产真值。**

- B1 在候选编译失败派生时先加 1（`compile_failure_surface.rs:292-325`），即使随后未委托 author，只把 phase 改为 stopped 而不撤销计数（682-714）。它不等同于实际完成/被正确计费的重写次数。
- B2 由门 CAS/hold/receipt 管理，结构失败可退款；C 不随退款减少。
- B1 在编译成功时清零（353-369），B2 按 logical gate 接续（`policy_routing.rs:116-130`），两者边界不同。
- session 的 `manual_repairs_used` 不是 gate-local 预留/结算事实，不能替代 B2。

正确共享余额应来自**同一预算身份下、按逻辑重写授权去重的后端预留与计费事实**：总额减已计费授权数、减活动预留数；结构退款按既有 receipt 语义释放。已有用户账模式 `StructuralGovernanceState::available_user_budget`（`models/workspace.rs:481-517`）体现这个模式，但现有输入未覆盖独立的编译重写账，不能直接宣称已是 B 的总账。展示端不补造这个账本。

更精确地，当前可如实取出的只有：

| 数值 | 如实定义／来源 | 不能解释成什么 |
|---|---|---|
| 编译账 R | 已投影的 `auto_rewrite.remaining`；`decide_route` 先算 `max_manual_repairs - previous.auto_rewrites_used`，AutoRewrite 再减本次 1；stopped 可能 R>0 | 不能称已经包含人工反馈扣次的共享余额；R>0 也不保证允许继续重写 |
| 门反馈账 M | 当前 logical gate 的 durable `manual_repairs_remaining`；REQ-CG-02:37-75 规定同域总额 − delivered charge − nonstructural failure charge − active hold | 不能用 `3 - run_history.manual_repairs_used` 代替已接续门快照 |
| 已接受轮数 C | 当前门 `accepted_feedback_turns` | 不能用 `3-C` 算余额；released_structural 会退额但保留 C |

目标共享余额的数学定义是 `B_available = B_total - |本预算域已计费的唯一授权| - |本预算域活动预留的唯一授权|`，两个集合互斥；不允许同一授权因物理重试／不同流水重复扣次。不是对两个现成汇总数字取 max。即使理想化为同周期、无退款、互不重叠，自动消费 1、人工消费 1 后正确剩余是 `3-(1+1)=1`，`3-max(1,1)=2` 仍错误。**当前真实数据连这些理想前提也不成立，因此没有一个只依赖 B1、B2、C 标量的通用合并公式。**

这里「授权」须保留 REQ-CG-02:75,197-205 的现有边界：只有真实用户命令建立人工 turn，同 turn 的 L1 结构 attempt 不增加用户次数。自动路径不能假造人工反馈、不能增加 C；它需要自己的幂等消费身份并进入同一预算权威。该接口设计属于后端后续工作，不是本报告凭空宣称已有的能力。

### 是否改代码

裁决：**完整解决必须改后端预算归属/共享执法；只改文案不能修复既有 REQ-WSC-21 不符合。** 但不把行为变化暗塞进 G-2：

- G-2 做当前真实投影、命名、停止原因及刷新；不改扣次、不硬合并数字。
- 独立后端工作包扩展现有 CAS 预算权威，让编译重写与反馈重写按同一授权身份恰扣一次；保留 B1 作为诊断计数而不是另一份授权余额。不能仅在编译失败函数里额外 `manual_repairs_remaining -= 1`：此时可能没有门、尚未 author 委托，而且独立 JSON 与 session CAS 不原子。
- A 的编译重写挪用缺陷独立修复，不能简单扩大 `max_repairs`、删除所有评审保护或仅修改注释。普通评审返修的现状与命名问题，应与编译失败专用通道的契约违背分开处理。

**唯一需要 owner 重新拍板的语义／范围项：共享 B 的生命周期如何与既有同门接续合同统一，并是否批准相应后端修复成为完整修复的依赖。** 推荐问法：

> 是否批准以同一 logical gate 的授权账作为共享 B 的权威，编译成功只清编译诊断／自动重写段计数、不返还该门已占额度，并保留人工 turn 内结构重试不另扣的既有规则；将这一后端共池修复单独纳入完整修复范围？

理由：REQ-WSC-21:820 写「编译成功 MUST 清零」，而 REQ-HGC-01:11、REQ-CG-02:194-205、REQ-CG-07:615-620 要求同门乃至批准后修订门接续预算。两本账独立时可各自遵守；合成一个执法权威时必须明确清零对象。我的推荐是**只清编译诊断段计数，不补回同门反馈额**，并据此澄清 WSC-21。若 owner 选择成功即重置整个 B，则必须显式改 HGC／CG 合同，不能静默覆盖。

「总额是否本来就应互扣」不是尚未定过的新产品问题：WSC-21 已明确要求共池且每轮扣 1。授权可以决定本次是否纳入后端修复、如何化解生命周期冲突，不能把既有不符合改说成已合规。G-2 的中性文案与准确取源可单独完成，但不得冒称完整共享预算问题已经解决。

### Q-B 的取舍与代价

推荐**保留诊断账、归一授权权威**，而不是把所有计数物理合为一个计数器。已有 CAS、hold／receipt、provider-start 幂等模式可复用，但自动入口必须有同域预算身份、恰一次预留／结算以及崩溃恢复；候选状态 JSON 只作诊断投影。主要风险是跨文件非原子、先记消耗后未委托、历史清零丢失证据、同门重新开卡补额度，以及用户 turn 的退款规则被破坏。

| 路径 | 一行代价 | 裁决 |
|---|---|---|
| 只改命名／如实展示 | 小、无扣账语义变化；只能解决当前呈现错误 | 适合作为 G-2 的明确交付边界，不能验收共池行为 |
| 扩展现有 session CAS 的共享权威，保留诊断计数 | 跨自动／反馈入口、预领／结算／恢复／生命周期与测试，必须独立设计批准 | **完整修复推荐** |
| 把所有计数物理合成一个计数器 | 丢失动作数、物理尝试数、收费数的区别，迁移面更大 | 不推荐 |

此处不是后端完整实施 Plan；边界批准前不写 schema、不改执行代码、不承诺仅改两个文件即可完成。现有后端缺陷由普通实施链在后续获批设计下处理，无需静默依赖额外 gated 角色。

## Q6／Q-E｜块1 REQ-CWS-GATE-02 内容结论

1. 删除「三个互不相干的额度」；改成「评审自动返修预算、候选重写共享预算，以及已接受反馈次数」三类不同事实。

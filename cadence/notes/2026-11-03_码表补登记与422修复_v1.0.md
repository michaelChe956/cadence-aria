## 缺口②：缺 LC 提交 → 稳定错误码（不再是 serde 通用 422）

**定位**（grep，非猜测）：

- 路由：`src/web/app.rs:312` `POST /api/projects/{project_id}/issues` →
  `create_product_issue`（`src/web/handlers/product_resources.rs:157`）。
- 请求体：`CreateProductIssueRequest`
  （`src/web/types.rs:459`）中 `logical_codebase_id: String` 为 serde 必填字段；
  缺字段时 axum `Json` 提取器在反序列化阶段即拒（`JsonDataError` → 通用
  422 纯文本响应），handler 根本执行不到——即「字面稳定码只在
  `issue_store.rs:195`（读老记录缺归属）与 `support.rs:239`（载体判定无归属）
  两条路径产出」的原因。

**改法**（`src/web/handlers/product_resources.rs`）：

- handler 提取器改为 `payload: Result<Json<CreateProductIssueRequest>,
  JsonRejection>`（axum 0.8 原生支持的 Result 提取器；serde 仍在反序列化阶段
  拒，但拒绝**到达 handler** 可判别）。
- `Err` 分支：`rejection_is_missing_logical_codebase_id` 只认
  `JsonDataError` 且 `body_text()` 含 ``missing field
  `logical_codebase_id` `` → 返回
  `ApiError::validation("issue_not_bound_to_logical_codebase", <英文
  message>)`，经 `src/web/error.rs:178` 映射 **HTTP 400**；中文文案唯一来源
  是块2 码表（缺口①已登记），handler 不另写中文。
- 其余反序列化拒绝（缺 `title`、类型不匹配、JSON 语法错、缺 content-type
  等）走 `rejection.into_response()` **原样透传**，与既有 axum 行为逐字节
  一致——只有「缺 LC」这一种形态从通用 422 变为稳定码 400。
- **未改字段类型**：`CreateProductIssueRequest.logical_codebase_id` 仍是必填
  `String`（块3 收敛结论保持；typed 反序列化依旧强制该字段在场）。
- 原校验链整体移入 `create_product_issue_inner`（project 404 →
  `repository_required` → LC 链路），顺序与语义不变。
- 未自造 reason_code；未改 spec/design/proposal/Plan/技术方案。

**测试钉死**（同文件新增 `create_product_issue_tests` 模块，router oneshot 实测
HTTP 行为，非纯函数断言）：

- `create_product_issue_missing_lc_yields_failure_copy_registered_stable_code`：
  POST 缺 `logical_codebase_id` 的合法 JSON → **400 + 响应体
  `code == "issue_not_bound_to_logical_codebase"`**（不是 serde 的 422）。
  测试名含 `failure_copy`，使窄跑 `cargo test --lib failure_copy` 一并覆盖。
- `create_product_issue_other_rejections_keep_generic_behavior`：
  缺 `title` → 仍 axum 通用 422（不冒充稳定码）；LC 在场 → 照旧进 handler
  → 未知项目稳定 404 `project_not_found`（透传路径未受损）。

**未阻塞说明**：任务预告的「若缺字段在 axum 层拦不住 ⇒ 换口径改
`Option<String>`」**未发生**——Result 提取器让 serde 拒绝可判别地到达
handler，无需改字段类型、无需 Main 换口径。

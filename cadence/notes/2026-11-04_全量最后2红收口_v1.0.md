## ① it_core `workspace_ws_abort_with_pi_reaches_cancelled_state_and_stops_output`

### 事实依据（文件:行 + 原文）

1. **validated 投影面按设计不含 provider/mode** —— `src/cross_cutting/session_launch.rs:73-80`：
   > 「本投影只借出三个启动事实,不借出结构化契约与资源归属」——`launch_view()` 只借 `role/working_dir/prompt`；`into_parts` 为 `pub(crate)`（同文件 :11 注释：「外部调用方只能消费 validated input,无法拆出裸 input」）。⇒ adapter 侧对 `(provider_type, permission_mode)` 不可观察，登记红的根因属实。
2. **引擎 launch input 的唯一事实源是 durable session 记录** —— `src/product/workspace_engine/prompts.rs:407-419`（`build_streaming_input`）：
   > `provider_type: provider_type_for_name(&provider)`、`permission_mode: permission_mode_for_provider(&provider, self.session.permission_modes.author.clone())`，`provider` 即 `session.author_provider`。durable 字段 `author_provider`（`src/product/models/workspace.rs:814`）与 `permission_modes.author`（:820，`WorkspaceRolePermissionModes.author` 默认 `Auto`）。
3. **Pi ⇒ Auto 是强制不变量** —— `src/product/workspace_engine/mappings.rs:40-46`：
   > 「Pi does not support per-tool approval, so it can only execute in Auto mode」（`provider_type_for_name`/`permission_mode_for_provider` 的 crate 内单测在同文件 :279-）。
4. **引擎启动前有 durable 账本登记（public store 方法）** —— `src/product/workspace_engine/provider_drive.rs:163-167`：author run 拉起前 `register_provider_start_in_ledger(Author, session.author_provider)`（LC gateway 分支与 legacy 分支共用此前置口）；`watchdog.rs:165-208` 经 `LifecycleStore::claim_provider_start_with_details`（`src/product/lifecycle_store/workspace.rs:899-935`）**排它锁下原子落盘**，条目含 `provider`/`started_at`。`ProviderStartLedgerEntry::is_actual_launch_observation()`（`src/product/work_item_plan_policy/types.rs:168-174`）为 public 判别法。
5. 时序：登记（provider_drive.rs:163）先于 `start_validated`（:186 gateway 臂），测试收到首段输出即已保证登记落盘。

### 所选路径及理由

**选 (a)+(c) 复合：把断言换到「引擎构造 launch input 的同一 durable 事实源 + 引擎启动登记账本」。**

- (b)（给 `launch_view` 增 provider/permission 投影）**不需要**：这两个事实在 durable 层完全可观察，无需改生产契约面。
- (a) 单独不够（durable 记录是配置事实源，还差「真的启动了」一环），(c) 的 `provider_start_ledger` 正好补上 actual-launch 观察——三项合并后 `(Pi, Auto)` 语义不减：
  - `author_provider == Pi`（durable）→ 经 `provider_type_for_name` ⇒ input.provider_type == Pi；
  - `permission_modes.author == Auto`（durable）→ 经 `permission_mode_for_provider`（Pi 恒 Auto）⇒ input.permission_mode == Auto；
  - `provider_start_ledger` 恰一条 actual-launch（provider=="pi"）+ 既有 `started==true`（Pi 名下注册的 adapter 被 validated 启动）⇒ 「真的以 Pi 启动了」。

### 改前 → 改后断言对照（`tests/it_core/workspace_ws_integration/part_04.rs:331`）

## ② it_web `evidence_query::invalid_query_returns_422_and_uninitialized_index_returns_503`

### 事实依据（文件:行 + 原文）

1. **产品侧「未建索引」有 durable 层判定，不靠 CLI 退出码** —— `src/product/logical_codebase/evidence_mediator.rs:899-909`（`load_or_pin_index`）：
   > `manifest.active_aggregate_index_id.clone().ok_or_else(|| EvidenceError::QueryFailed { code: "evidence_index_unavailable", … "project {} has no active aggregate index to pin" })`。
2. **CLI 层判定（非零退出）在 codegraph 1.6.2 上对「未建索引」不触发** —— `src/product/logical_codebase/aggregate_index/codegraph_cli.rs:199-212`：`query_json` 仅把「exit != 0」映射为 `codegraph_query_failed`。**本机实测**（2026-11-04）：未建索引根上 `codegraph query cross_repo_symbol --json` → 输出 `[]`、**exit 0** ⇒ 0 命中 ⇒ 200。与登记描述一致。
3. **版本区间已闭合：1.6.2 即最新** —— npm `@colbymchenry/codegraph` 已发布版本止于 **1.6.2**（2026-10-03 发布，无更高版）；产品声明支持区间 `>=1.6.0, <2.0.0`（`codegraph_cli.rs:22-23`）。⇒ 不存在「更高版本会非零退出报未建索引」的版本区间问题；在产品支持区间内「未建索引 ⇒ 非零退出」前提恒不成立。
4. **503 契约映射** —— `src/web/handlers/evidence_error_mapping.rs:39-43`：`QueryFailed { code }` → 稳定码 `evidence_query_failed` + `details.reason_code=code`；`src/web/error.rs:379` → 503（单测同文件钉住）。
5. 原 fixture 注释自认前提：「用于 503 evidence_query_failed 场景（真实 `codegraph query` 非零退出）」——该前提是**错的**，属测试侧选错了触发层，不是产品缺陷。

### 所选路径及理由

**改断言前提：把场景⑩的「未建索引」从「CLI DB 缺失（退出码不可识别）」改经产品自己的 durable 未建索引判定触发。** 理由：

- 产品对「未建索引」的权威判定就在 durable 层（事实 1），原测试绕开它去赌第三方 CLI 的退出码，赌错了对象；
- 期望值**没有迁就现状**：断言仍是 **503 + `evidence_query_failed`**（原样），仅 `reason_code` 从事实性不可达的 `codegraph_query_failed` 换成产品为「未建索引」定义的稳定码 `evidence_index_unavailable`——语义从「赌 CLI 报错」校正为「断产品未建索引契约」；
- e2e 无法在真实 codegraph 1.6.2 上确定性地制造非零退出（崩溃/超时除外），伪造 CLI 二进制又违背该测试文件「真实 codegraph」的既定口径；CLI 层失败→503 的上层契约已由 `evidence_error_mapping.rs` 单测钉住（Main 登记时已认可）。

### 改前 → 改后断言对照（`tests/it_web/evidence_query/part_03.rs:57-62`）

改前：

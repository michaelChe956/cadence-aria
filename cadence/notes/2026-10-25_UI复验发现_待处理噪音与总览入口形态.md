## F-A 待处理列表把「状态」当成「待办」（owner 截图：租约活跃 + 旧代绑定）

### 现象
待处理抽屉「需要人工处理」下出现两条**不需要人动手**的条目：

1. **租约活跃，自动链等待中** — `lease active; automation keeps waiting (lease coding_attempt_3681bce5…)`，无任何按钮。
2. **存在旧代绑定（只读可查）** — `5 previous binding generation(s) kept read-only`，带「去换代」按钮，但当前绑定有效时是空转。

### 证据
- `src/web/plan_confirmed_info.rs:398-420`：后端把两种租约处置**都**推成等待项——
  - `LeaseDisposition::ActiveWait` → kind `lease_wait`，`actions: vec![]`（**无动作**，语义是"到期自动恢复"）
  - `LeaseDisposition::DeadNeedsTakeover` → kind `lease_takeover`，`actions: vec!["confirm_takeover"]`（**真需要人**）
- `src/web/plan_confirmed_info.rs:507-540`：`generation_history` 的触发条件是
  `history.previous` **非空**，**不判断当前绑定是否有效**；固定 `actions: ["rebind"]`、`next_phase: "rebind"`。
- 现场（`project_0001/issue_0001`）：enrollment `enabled=true`、rev 17；当前绑定 `binding_version=6`
  → plan/session `97eb9c83-…-f5d423168c02`，**两者均存在**；5 条旧代
  （`618ea4e54c0c / af5eaacd76ab / 08d8f4099819 / 6d3bae1da6a4 / 1bd27808bb45`）的
  plan/session 已被单 plan 级联删除（plans 目录只剩当前 1 个）→ 旧代只剩只读审计痕迹。
- 现场 attempt：`3681bce5` = `created / prepare_context`（从未 started）；`4ce6f4d7` = `running / coding`（真在跑）。

### 影响
待处理计数被"自动等待"与"只读历史"灌水，owner 分不清哪些"不点就过不去"。

### 建议改法（待 owner 裁定）
1. `lease_wait` 移出「需要人工处理」，归入「自动等待中」（可显示到期时间），**不计入待处理数**；
   `lease_takeover` 保留在待处理。
2. `generation_history` 仅当**当前绑定的 plan/session 不存在**才保留为待办 + 「去换代」；
   否则降级为只读信息（折叠/详情）。
3. 待处理计数只算"真需要人决策"的一类。

### 已实施（F-A，2026-10-25）
后端 `src/web/plan_confirmed_info.rs`：`C1WaitingItemDto` additive 新增
`requires_human: bool`（serde 缺省 true，旧响应按需要人工解释）；`lease_wait`
（ActiveWait）产出 `requires_human=false`；`generation_history` 仅当当前绑定
失效（绑定 plan 记录或 session 缺失，如单 plan 级联删除）才保留 `rebind`
动作 + `requires_human=true`，否则降级只读信息（无动作，reason 注明
current binding active/dangling）。
前端 `web/src/state/workspace-cockpit-projection.ts`：`requires_human=false`
的等待项投 `kind="info"`——两个待处理抽屉（CockpitInbox / WorkbenchInboxOverlay）
按 kind 分组后自动落「进度信息」，不渲染 C1 恢复卡（无「去换代」按钮）；
`lease_takeover`、失效绑定的 `generation_history` 维持「需要人工处理」。
计数：shell 侧告警条/标题/favicon/系统通知（actionableCount）本就不含 C1
等待项；**遗留**——驾驶舱页头「待处理 N」徽标（`ChatCockpitPage.tsx:1047`
`inboxCount={observedInbox.length}`）仍按展示条目计数（含 info 类），需该
文件（F-C/D/E 代理独占）一行改为 `observedInbox.filter((item) => item.kind
!== "info").length`，已另行协调。spec 无需改动（无既有 MUST 约束这两类
等待项进「需要人工处理」）。

## F-C 会话页「终止整个自动化」确认面看不见、点不到（owner 截图 + 真机复现）

### 现象
会话 `workspace_session_auto_675946f6-08d8-4b69-9a41-204ad10336fb` 页面右上角「终止整个自动化」
按钮，**点击后确认弹窗看不到、也点不到**（owner 原话：「点击的弹窗看不到也操作不了」）。

### 真机实测（headless Chromium，同一 URL）
```
点前: automation-termination-confirm 数量 = 0
点击后: 数量 = 1, isVisible = true
但:  面板 rect 高 17px，自身 scrollHeight = 44px（内容被压扁）
     面板按钮实际位于 y=131~167（高 36px / 32px）
     elementFromPoint(按钮中心) → DIV（内容 "Projection Validation Report 仍报 integrat…"）
                                  **不是面板内的按钮**（isInsidePanel = false）
     同位置重叠的兄弟节点: cockpit-conversation-flow-list（y=123，高 376px）
```

### 根因（文件:行号）
- `web/src/pages/ChatCockpitPage.tsx:1163-1164`：右列 grid 的行模板按"有没有 pending choice"二选一：
  ```jsx
  className={cond
    ? "grid-rows-[auto_auto_minmax(0,1fr)_auto_auto]"   // 5 行
    : "grid-rows-[auto_minmax(0,1fr)_auto_auto]"}         // 4 行（默认）
  ```
  实测计算样式 `grid-template-rows: 60px 0px 376px 259px`。
- `web/src/pages/ChatCockpitPage.tsx:1274`：`<AutomationTerminationConfirmSurface />` 是**无条件**渲染的
  第 2 个子节点。
- 4 行模板时子节点映射：header→auto、**确认面→minmax(0,1fr)**、对话流列表→auto、输入框→auto。
  1fr 行被其余行挤成 **0px** → 确认面内容（44px）溢出可见，但**被第 3 行的对话流列表整块覆盖**
  （列表在 DOM 中靠后 → 同层叠放顺序更高）→ 看不见、按钮也点不到。
- 有 pending choice（5 行模板）时确认面落在 auto 行 → 正常显示。
  ⇒ 缺陷是"**行模板按条件切换、但确认面无条件存在**"造成的错位，只在默认（无 pending choice）路径暴露。

### 影响面
- 仅 `ChatCockpitPage` 这一处挂载点有问题。
- 另两处挂载点**正常**（都是 flex column 里的块级兄弟，独占行）：
  - `web/src/pages/CodingWorkspacePage.tsx:952` 附近（`</header>` 之后、页面根 flex column 内）
  - `web/src/components/lifecycle/WorkbenchInboxOverlay.tsx:228`
    （`workbench-inbox-content` = `flex min-h-0 flex-1 flex-col overflow-y-auto` 内）

### 建议改法（待 owner 裁定，暂不动）
1. **推荐**：把 `AutomationTerminationConfirmSurface` 改为**脱离 grid 流的浮层**
   （`position: fixed` + 合适 `z-index`，自上而下居中/贴右），不再参与行模板分配；
   顺带满足 owner 对"弹窗"的形态预期（当前是**内联面板**而非 modal）。
2. 备选：给 4 个子节点**显式 `grid-row`**（不靠自动放置），行模板只管行高；
   或把行模板条件扩展为"pending choice **或**确认面可见"（需保证行数与子节点数严格对应，易再错位）。
3. 修完需补回归测试：断言"点击入口后确认面在视口内可点"（例如按钮中心 `elementFromPoint` 命中自身），
   避免只断言 DOM 存在（本次缺陷正是"DOM 存在但不可用"）。

## F-D 分诊门的「提交给 Coder 修复」在当前门必然失败（按钮可见但不可用）

### 现象（owner 截图）
分诊门（`reason=code_review_output_human_triage`）上点「提交给 Coder 修复」→
```
coding_gate_response_failed: coding_provider_stream_failed: send_to_coder_latest_review_not_actionable
```

### 证据
- `src/product/coding_workspace_engine/code_review.rs:283-288`：该门由
  `CodeReviewFlowDecision::StopForHumanTriage` 产生，标题「Code Review 结论需人工分诊」——
  触发前提就是 **review 输出无法机械判定为自动判决**。
- 「提交给 Coder 修复」= `send_to_coder` 动作，前提是 `latest_review` **可 action**；
  本门场景下二者互斥（不可 action 才升级分诊）→ **该按钮在此门上必然失败**。
- 门卡同时给的动作：重试代码审查（`retry_review`）／提交给 Coder 修复（`send_to_coder`）／
  人工继续（`manual_continue`）／终止（`abort`）。

### 影响
用户看到四个按钮，其中一个必失败；失败文案是 provider stream 错误，无法反推"这个门不能发回 Coder"。

### 建议改法（待 owner 裁定，暂不动）
1. 该门**不渲染** `send_to_coder`（动作可用性由服务端 `available_actions` 驱动，前端只渲染可用动作）；
   或服务端在该门直接拒绝并返回可读原因（"本门为人工分诊，不支持发回 Coder；请人工继续或重试审查"）。
2. 动作可用性统一走 `available_actions`（`src/product/coding_attempt_store/gate.rs:37` 附近的
   `resolved_action` 语义），避免前端硬编码动作清单。

## F-E 「人工继续」的必填提示指代不清，两个错误码混在一起

### 现象（owner 截图，同一张卡上先后出现）
1. 文本框空着点「人工继续」→ 行内红字 `需要填写人工修复意见`；
2. 卡片底部另有 `请使用上方门禁操作提交人工修复意见` + `coding_gate_response_failed: ...`（来自另一次点「提交给 Coder」）。
   → 两条文案说的是**同一件事**（"意见要走门禁动作提交"），但一条像字段校验、一条像动作失败，
   且第二条的 `coding_provider_stream_failed` 属于另一次点击 → owner 无法判断"到底该做什么"。

### 证据
- `manual_continue` 强制非空意见：文本为空即报 `需要填写人工修复意见`；
  其语义（`src/product/coding_workspace_engine/gates_parts/blocked_gate.inc.rs:264-295`）是
  **写 context note（意见优先于 Code Reviewer findings）+ 写质量豁免审计 + attempt 回可执行态**。
- 门卡正文已写"人工放行会记录质量豁免；请说明跳过该门禁的原因和后续风险处理"，
  文本框占位也写"该意见会优先于 Code Reviewer findings"——但**没有说"意见会记入质量豁免审计"**，
  也没说这条意见是**放行豁免**（而非"修复意见"）——命名与语义有偏差。

### 建议改法（待 owner 裁定，暂不动）
1. 错误文案带上动作名与后果：
   `「人工继续」需要填写人工修复意见（将记入质量豁免审计：reason_code=code_review_output_human_triage）`。
2. 必填校验**前置**到文本框（禁用提交 + 就地提示），避免点了才知道要填。
3. 命名对齐：该门是"人工放行分诊"，文本框标签建议区分「人工放行说明（记入质量豁免）」与「修复意见」，
   避免与"发回 Coder 修复"路径混淆。

### owner 现场可用的通过路径（本次已确认）
> 在文本框写明"原因 + 后续风险处理"（非空）→ 点 **「人工继续」** →
> 写 context note + 质量豁免审计 + attempt 回到可执行态继续往下跑。
> 「提交给 Coder 修复」在当前门不可用；「终止」会中止该链；「重试代码审查」会重跑一轮 review（可能仍回本门）。

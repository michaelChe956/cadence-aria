- 出具: 测试会话 (2026-10-16), 依据=issue-001 全流程实测(4 WI, 3 attempt, 6 role-run)与源码勘察
- 边界遵守: 不动沙箱安全设计; B/C 已按 owner 裁决排除

## 一、CHECK 沙箱不可执行——剩余选项决策

### 实测介入成本(本 plan 真实数据)

| WI | coder 遇限行为 | 人工介入 | 说明撰写成本 |
|---|---|---|---|
| WI-001 busi | 上报阻塞→三按钮卡 | 1 次(点按钮+贴说明) | ~5 min(结构化模板已验证有效) |
| WI-002 gateway | 静默交付,验证漂移给 reviewer | 0 次(CHECK 面) | - |
| WI-003 frontend | 按 evidence=manual_check 留人工 | 0 次 | - |
| WI-004 联调 | 上报阻塞→三按钮卡 | 1 次(点按钮+贴说明) | ~5 min |
| (附) WI-002 reviewer 空输出中断 | - | 1 次(点重试) | - |

关键观察: 同样的沙箱限制, 三个 coder 三种呈现(卡/静默/留人工)——**CHECK 定义的证据语义
(evidence 字段)已经在影响 coder 判定**, 这正是 A' 的抓手, 也是必须产品化的理由:
不产品化, 行为就随模型心情漂移(gateway 静默交付那轮, 运行时验证事实上无人做,
靠 reviewer(pi)自觉补跑才闭环)。

### 选项对比

| 选项 | 内容 | 人工介入 | 开发量 | 缺陷 |
|---|---|---|---|---|
| A | 现状: CHECK 标注「宿主验证代理执行」, 人工补做回贴(自由文本) | 每 WI 1 次 | 0 | 证据非结构化不落 attempt; coder 行为漂移; 说明质量依赖人 |
| **A'(推荐)** | A + 两个产品小改: ①CHECK 预声明执行环境 ②分诊卡开「回贴验证证据」结构化入口 | 每 WI 1 次(轻: 只贴证据不写作) | 小 | 仍是每 WI 一次人工 |
| D(补充, 不单独成案) | 承认现状: reviewer(pi)在 review 轮宿主代跑运行时 CHECK | 0 次(CHECK 面) | ~0(现状已如此) | 依赖 pi 零沙箱逃逸面(=bug#3 待收紧项), 路线互斥不可成文依赖 |

### 推荐: A'(主) + 问题3 的生成侧约束(必做) ; D 仅作过渡期事实, 不成文

A' 组件:
1. **CHECK 执行环境预声明**: verification plan 生成时按命令指纹判 executor
   (podman/docker/java/mvn/npm run build/curl <host:port> → `executor: host`;
   其余 → `executor: sandbox`)。coder 见 host 类不再尝试(实测 frontend coder
   浪费了 29 次 podman 探测), 也不再把环境缺失误判为自身缺陷
2. **分诊卡「回贴验证证据」入口**: 结构化回贴(CHECK id × 结果 × 输出摘要),
   落 attempt durable 证据区; reviewer 与确认门可直接引用——替代自由文本说明
   (本会话两份说明模板已验证 coder 接受度高: 「定性+证据+指令」三段式)

### 问题2: 每 WI 一次人工介入是否可接受

- 短期(批2): **接受并制度化**——写进验收流程: 「运行时类 CHECK 允许宿主回贴证据,
  分诊卡响应建议 ≤10 min」; 这与批1 前人工验证成本一致, 不构成回归
- 中期: A' 落地后介入退化为「贴证据」单击级; 若未来 owner 转向, B(受控 runner)
  仍是彻底解, 该决策不堵死 B 的路
- 单仓小 issue: 通常 0-1 次介入, 无感

### 问题3: plan 生成侧要不要避免产生 coder 侧不可执行的 CHECK

**要, 但方向是「改标注」不是「不生成」**:
- 运行时 CHECK 是验收质量的一部分, 砍掉=验收降级
- 生成侧改动: ①command 类 CHECK 若 env 指纹判定为 host → 标 executor:host +
  证据通道=宿主回贴; ②跨仓/联调 WI 的 CHECK(如 CHECK-008/009/010)默认全 host
- 拆分器已有半成品先例: WI-003 的 CHECK 定义已出现 `evidence: ["manual_check"]`
  字段(实测事件可见)——统一化即可, 不是新机制

## 三-1 中断门未收口: 影响面结论(数据面已核实)

- **无推进风险**: plan 运行状态(coding-plan-runs)对该门 0 引用, 不会重复触发重试
- **影响=两点**: attempt 数据不一致(open+resolved_action=null, 流程实际已完成);
  UI 残留待 owner 页面确认(数据面查不到通知 durable 投影, 无法代验)
- 修复建议维持 bug 报告三条(gate action 统一回写 / run-gate 关联幂等收口 / 对账告警)

## 三-2 跨仓验收 WI 证据死锁: 推荐「确认侧 scope 并集 + 生成侧落位标注」组合

| 候选 | 评估 |
|---|---|
| **①确认校验取 plan 内全部 WI scope 并集(推荐, 确认侧)** | 最小改动解死锁; 越权拦截不弱化(仍只放行 plan 声明过的 scope, WI-003 coder 写 busi/src 依旧拦); 语义补丁=确认 UI 标注「本仓 diff 含跨仓 WI 产物」避免背书混淆 |
| **②拆分器给跨仓 WI 显式落位仓(推荐, 生成侧)** | 生成时指定 primary worktree(如联调 WI 落首个仓), 不再产生「scope 无落位」的 WI; 防新增死锁面 |
| ③独立证据落位(issue 级目录/attempt 回填) | 语义最干净, 但新机制开发量大, 且丢失「证据进 git 可追溯」价值 → 建议批3+ 演进, 不占批2 |
| (原报告的建议2 即③, 本轮调整为①+②组合先行) | |

理由: 死锁在确认侧, 最小面修复; ①解存量, ②防增量, ③留演进。

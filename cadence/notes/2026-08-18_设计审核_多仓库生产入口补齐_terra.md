# BLOCKER

## B-1：聚合初始化按方案 spawn 后，registry 与 cancellation token 仍然无法成立

**证据：**

- 当前 handler 只执行 `begin`，注册 lease 后立即释放，没有执行 coordinator：

  - `src/web/handlers/aggregate_initialization.rs:110-149`
  - 其中 `:133-144` 明确 `drop(lease)`，并注释“worker is not spawned”。

- 方案要求复用传统模式：

  > begin → registry.register(lease) → tokio::spawn(execute)；cancel 经 lease cancellation token。

  但当前通用 registry：

  - `src/web/state/repository_initialization_run_registry.rs:61-98`
  - `InitializationRunRegistry` 只保存 `HashSet<InitializationRunKey>`；
  - `InitializationRunLease` 只负责 `Drop` 时移除 key；
  - 没有 cancellation token，也没有 token 查询/触发能力。

- `WebAppState` 只有 `repository_initialization_runs`：

  - `src/web/state.rs:121-134`
  - 没有共享的 aggregate `InitializationRunRegistry`。

- `aggregate_initialization_dependencies(state)` 在没有注入依赖时，每次 handler 调用都执行：

  - `src/web/handlers/aggregate_initialization.rs:205-225`
  - `build_default_aggregate_dependencies` 每次新建 `InitializationRunRegistry::default()`。

因此，若简单按方案在 POST 中 `tokio::spawn`：

1. POST 使用的 registry 与后续 GET/Cancel 使用的 registry 不是同一个实例；
2. GET 必然可能判断“无 active lease”；
3. GET 会把正常运行中的任务误判为中断；
4. Cancel 无法拿到并触发 worker 正在使用的 token；
5. worker 结束前 lease 若未被正确持有，registry 状态会失真。

这不是简单补一个 `tokio::spawn` 就能解决的问题。必须先明确：

- aggregate registry 是否放进 `WebAppState`；
- registry 是否保存 `(key, CancellationToken)`；
- cancel 如何获取并触发 token；
- worker 完成、失败、panic 时如何释放 lease；
- 重启后如何区分“无 active lease 的 Running”与仍在其他进程运行的任务。

**建议：**增加共享的 aggregate run registry/token registry，或明确采用持久化 operation 状态 + 无进程内取消的模型。不能继续使用当前仅有 HashSet 的 lease 语义。

## M-1：registration“同步短操作”与 `202 + 批次进度/取消`相互矛盾

方案同时声明：

- 登记批次是同步短操作；

- `src/product/logical_codebase/registration_coordinator.inc.rs:19-84`

真正执行在 `resume_batch`：

- `:106-239`

- 同步 `POST`：直接执行并返回最终/partial 状态；
- 或异步 `POST`：Queued → worker → Running，配套 token、进程恢复、取消语义。

> GET 若 Running 且无 active lease → 标 Interrupted，人工重触发，不自动恢复。

当前 durable enum 没有 `Interrupted`：

- `src/product/logical_codebase/aggregate_initialization.rs:153-163`
- 状态只有 `Created/Running/Completed/Failed/Cancelled`。

当前 `recover_interrupted`：

- `src/product/logical_codebase/aggregate_initialization_store.rs:330-370`
- 将记录改为 `Failed`；
- 写入 `AggregateInitializationErrorRecord::interrupted()`；
- 设置 `completed_at`。

而 coordinator `execute` 只允许：

- `Created`；
- `Running`。

因此一旦标记 Failed/Interrupted，不能通过同一个 operation 直接人工重触发。方案必须定义：

- 新增 Interrupted 状态；
- 或保留 Failed + interrupted reason，但提供 reset/retry API；
- retry 是否复用 operation_id/idempotency identity；
- 已完成步骤是否重跑；
- staging 是否保留。

## M-12：`cancel` 当前只持久化状态，不会取消正在执行的 provider

当前 `cancel_aggregate_initialization`：

- `src/web/handlers/aggregate_initialization.rs:180-203`

只调用 coordinator 的持久化 `cancel`。

`AggregateInitializationOperationStore::cancel` 会把 operation 改为 Cancelled，并清理 staging：

- `src/product/logical_codebase/aggregate_initialization_store.rs:260-329`

但没有触发任何 worker token。若 worker 正在 provider turn：

- provider 可能继续执行；
- worker 后续 `checkpoint/complete` 可能因 operation 已 Cancelled 而失败；
- 取消的“尽快停止”语义不成立。

这与方案“cancel 经 lease cancellation token”直接相关，必须和 B-1 一起解决。

但当前模型注释仍写：

方案测试策略只提：

- issue → selection → Story 可达；

这不是本次生产入口的唯一阻断，但 PLN-01 完成定义若覆盖 Design/WorkItemPlan，就必须纳入测试和实现修正。

## m-1：`RepositoryInitializationRunRegistry` 不是聚合初始化应复用的类型

当前前端没有：

- registration API；
- aggregate initialization API；
- aggregate index API。

现有仅有：

- `web/src/api/logicalCodebaseMembers.ts`
- `web/src/api/pointer-publication.ts`

- 7 类 preflight item；

## m-3：GET active 的 `state` 与持久化状态需定义映射

持久化索引状态包括：

```text
Building / Active / Stale / Degraded / Superseded / Failed
```

方案 API 只有：

```text
active / stale / degraded / missing
```

需要定义：

- Building 是否返回 rebuilding/in-progress，还是 409；
- Failed 且存在 last-known-good 是否返回 degraded；
- Failed 且无 last-known-good 是否返回 missing；
- Superseded 是否永远不可见；
- `revision` 是 membership revision、index id 还是 operation revision；
- `indexed_at` 使用 created_at、updated_at 还是 snapshot indexed_at。

## m-4：首建失败时“索引 degraded”语义需要区分

方案说：

> 首次 build 失败，索引记 degraded，可手动 rebuild。

但没有 last-known-good 的首次 build 实际上没有可读索引。当前 `degrade_last_known_good` 在没有 active record 时是 no-op：

- `src/product/logical_codebase/aggregate_index/store.rs` 的 `degrade_last_known_good`。

首次失败更合理的状态可能是：

- missing + failure reason；
- 或 Failed record；
- 只有已有 active index 的 rebuild 失败才是 degraded。

---

## m-5：AggregateIndexStore 的 active 替换不是跨文件事务

`replace_active` 先将旧 record 标记 Superseded，再保存新 Active：

- `src/product/logical_codebase/aggregate_index/store.rs:145-188`

如果第二次保存失败，可能留下没有 active 的状态。single-writer 锁只能解决并发，不能解决进程崩溃或跨文件写入失败。若设计要求 last-known-good，需要考虑 active pointer 文件或两阶段发布。

# 方案内部矛盾与范围问题

1. **同步登记 vs `202`/批次进度/取消**：需要二选一。
2. **GET Running 无 lease 标 Interrupted vs 当前 `recover_interrupted` 标 Failed**：需要新增状态或 retry/reset API。
3. **初始化成功尾步 spawn index vs index rebuild API 也是异步 202**：两个 worker 生命周期、single-writer 和 operation 状态需要统一。
4. **方案假设 AggregateIndexStore 既有锁覆盖所有写入**：事实只覆盖 rebuild/sync，不覆盖 build。
5. **方案说 selection 写失败 422 且不建 issue**：当前 issue store 没有事务或 rollback 机制。
6. **按项目 feature 构造 RepositoryStore**：当前生产调用点至少 18 个，方案没有列出影响面和统一构造策略。
7. **项目创建时 opt-in 不可切换**：旧 Project 的 `multi_repo` serde 默认、migration 行为、UI/API 回读均需明确。
8. **定时轮询 park**：如果 `poll_due` 继续保留，需明确它只是库能力，不声称已有生产 scheduler；否则会形成“设计已支持但没有调用方”的新半成品。

# 建议的设计文档修改顺序

1. 先补一节“运行时生命周期与共享状态”：
   - aggregate registry；
   - cancellation token；
   - worker；
   - restart/retry；
   - operation 状态。

2. 再补“Project feature 与 authority 初始化”：
   - `multi_repo`；
   - 空 manifest/root；
   - project-aware RepositoryStore；

   - preflight token/snapshot；

   - NeedsAttention 重新确认。

   - 同步 `200` 或完整异步 operation；
   - 首建/重建共用 single-writer；
   - operation/status/failure；

6. 将 PLN-05 `change_order` blocker 与真实 HTTP 集成测试纳入完成定义。

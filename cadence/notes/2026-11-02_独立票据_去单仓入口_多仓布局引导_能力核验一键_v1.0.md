# 独立票据：去单仓入口、多仓入口布局引导、能力核验一键化

> 来源：owner 2026-11-02 裁定（多机真机连测多仓链路之后提出）。
> **三条都是产品行为变更**（尤其第 1 条是能力下线）→ 实施前必须走 OpenSpec
> （brainstorming → change → 归档），不直接改代码。

---

## 背景

多仓（逻辑代码库）链路已在真机跑通，但暴露三类**产品面**问题（与 P1-13 / P1-14 同批真机）：

1. **单仓与多仓两条路并存**：多仓是**按 project opt-in** 的实验性路径，单仓仍是默认路径 →
   用户要理解「什么时候有多仓」，而且两套语义（legacy 投影 / LC 权威）长期并存是复杂度与
   缺陷的来源（`RepositoryRouting` 三态里 `Legacy` 一支、以及各处 `legacy_projection` /
   `legacy fallback` 兼容层）。
2. **多仓入口没有布局说明**：用户要自己猜「LC 仓目录」「代码仓库目录」该怎么摆，
   踩了三个坑（过期绝对路径、成员仓无可索引代码、成员 checkout 不在聚合根下）。
3. **provider 能力核验要一个一个点**：能力矩阵按 (provider, action) 分格，未核验的格
   `Unknown` → gateway 准入 fail-closed（P1-13）；核验按钮**每个 provider 一个**，
   多个 provider 就要点多次，每次还分钟级同步等待。

---

## 票 1：去掉单仓库入口，单仓功能后续全部下线

**owner 裁定**：不再保留单仓路径，后续单仓相关功能**全部去掉**。

**要清掉的范围**（需在 OpenSpec 里逐条列清并给出兼容口径）：

| 面 | 现状 | 要做的 |
|---|---|---|
**产品入口** | 多仓按 project opt-in；单仓是默认路径（创建 issue / 绑定代码仓 / 逻辑代码库登记向导） | **去掉单仓入口**：只保留多仓创建/登记一条路 |
**路由与解析** | `RepositoryRouting` 三态：`Legacy` / `Logical` / `FailClosed` | 去掉 `Legacy` 一支，解析只剩「多仓 / fail-closed」 |
**身份与投影** | `legacy_projection` / `legacy fallback` / `shared worktree` 单仓兼容层、身份迁移（阶段 4-7 回填 + 双读双写 + attempt 特例） | 明确**存量数据口径**：历史单仓记录是「只读保留 + 不再支持新写」还是「一次性迁移」 |
**LC 登记** | 预检允许 legacy 仓的公共非 git 父目录作为聚合根（`migration_executor`） | 单仓不再作为聚合根来源 |
**测试与文档** | 大量 legacy 语料与用例 | 随面清退；行数门禁登记表同步回收 |

**必须先定的问题（OpenSpec 里要 owner 拍板）**：
1. **存量单仓数据**：只读保留（不再支持新写）还是迁移？
2. **下线节奏**：一次性切换，还是给一个版本的过渡期 + 明确的迁移指引？
3. **多仓的最小形态**：最少几个成员？（现在 `member_ids` 允许 1 个；但 1 个成员的「多仓」与单仓语义几乎等价 → 是否直接禁止 1 成员？）

**影响面**：很大（解析层、身份层、投影层、迁移层、测试语料）。**建议单独一个 OpenSpec change 做**，
不要与其它优化混批。

## 票 2：多仓入口必须有明显提示（讲清目录布局）

**要做的**：在**多仓创建/登记入口**（以及聚合初始化卡片）显著位置，给出**目录布局说明**，
并在用户填错时**按错误码给出对应的具体修正动作**。

### 布局规则（已按代码核准 → 用户能懂的话）

设 **聚合根** = LC 仓目录（下面简称「LC 根目录」），**成员仓** = 各代码仓库的检出目录。

| # | 规则 | 对应错误码 | 用户该怎么摆 |
|---|---|---|---|
1 | **LC 根目录必须不是 git 仓** | `aggregate_root_is_git` | 另建一个**空的普通目录**当 LC 根（不要在某个 git 仓里） |
2 | **每个成员仓必须是 LC 根目录的直接子目录** | `member_path_outside_root` / `aggregate_index_layout_unsupported` | `LC根/<成员名>/` 一层，不要再套一层 |
3 | **成员路径不得用符号链接绕出 LC 根** | `member_symlink_escape` | 用真实路径，不要 symlink 到别处 |
4 | **同一个 LC 根不允许两个逻辑代码库**（跨项目也不行） | `aggregate_root_overlap` | 一个 LC 根只对应一个逻辑代码库；要多个就换根目录 |
5 | **成员仓不能是 worktree 嵌套** | `nested_worktree` | 成员要用正常检出，不要塞嵌套 worktree |
6 | **每个成员仓至少 1 个「可索引代码文件」** | `aggregate_index_member_coverage_failed` | 放**真源码**（`.js/.ts/.py/…`）；**`.html`/`.json`/`.md` 不算**；代码若只在 `.worktrees/`（Aria 的 issue 工作树）下**同样不算**（被明确排除） |

### 建议的呈现

- 入口处给一张**目录树示意图**（ASCII 即可）：
  ```
  my-lc-root/              ← LC 根目录：普通空目录，不是 git 仓
    backend/               ← 成员仓（真实检出，直接子目录）
    frontend/
  ```
- 并附一句：「成员仓里的代码要放在**仓库根或普通子目录**；只在 `.worktrees/` 下的代码不可被索引」。
- **错误面按错误码给动作**：例如 `aggregate_root_is_git` → 「LC 根目录不能是 git 仓，请另建一个普通目录」；
  `aggregate_index_member_coverage_failed` → 「成员 X 没有可索引代码文件：请在成员仓里放至少一个源码文件（.html/.json/.md 不算）」。

## 票 3：provider 能力核验要「一键核验全部」

**现状**：逻辑代码库管理面板 → 提供方能力卡（`ProviderCapabilityCard`）**每个 provider 一个「核验」按钮**，
单次 POST `POST /api/projects/{project_id}/logical-codebases/{lc_id}/capability-revalidate`
（body `provider_type`，首次**分钟级**同步等待），四态回显：已核验 / 未核验 / 核验中 / 失败。

**owner 裁定**：要一个**一键按钮**，别一个一个点。

**要做的**：
1. **后端**：加**批量**核验入口（一次提交该 LC 下所有 provider），或前端并发调用单 provider 端点。
   ⚠️ 单次核验是**分钟级同步等待** → 批量**不能串行**（4 个 provider 串行 = 4×分钟级），
   必须并发 + 逐项进度反馈（哪几个在跑/成了/失败了）。
2. **前端**：能力卡头部一个「一键核验全部」按钮 + 每行状态；进行中禁用并显示进度；
   失败项给可重试的单项按钮。
3. **关联 P1-13**：能力格 `Unknown` 导致的准入拒绝，报错面要引导到**这一个按钮**（而不是
   「去逐个点核验」）。

## 流程要求

- 三条都是**行为变更**（第 1 条更是能力下线）→ 各自走 OpenSpec change：
  `brainstorming` → proposal/design/delta specs/tasks → 实施 → 归档。
- 第 1 条建议**独立成一个 change**（影响面大，需单独可回滚）。
- 第 2、3 条可合并为一个「多仓入口体验」change。
- 每条落地前用**真机**（多机）复验：至少覆盖「新机器首启 + 成员无代码 + checkout 不在根下」三种布局偏差。

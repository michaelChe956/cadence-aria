# 调研简报: 四 CLI 官方沙箱机制 + AI Coding Agent 沙箱业界实践(cadence-aria 决策对照)

- 出具: researcher (SandboxIndustryScan), 2026-10-16, 受测试会话委托
- 所有来源为官方文档/官方博客/安全公告, 引用带链接与读取日期; 供应链二手源已剔除

## Summary

四个 CLI 中只有 Claude Code 与 Codex 内置 OS 级沙箱(且默认关闭); Kimi Code 官方安全模型仅为「审批门+名称规则」, pi 核心零沙箱、官方文档明确把隔离责任交给用户。业界 2025-2026 收敛方向清晰: 交互式工具纷纷补装 OS 级沙箱(Anthropic 2025-10、Cursor 2026-02、Gemini CLI、Devin CLI, 机制高度趋同于 bubblewrap/Seatbelt+网络代理, Anthropic 已开源 sandbox-runtime 且 Devin/pi 直接复用), 而**所有无人值守/平台派发型产品(Claude web、Codex cloud、Cursor 云代理、Devin、OpenHands)无一例外用 VM/容器**——「宿主直跑+护栏」在无人值守场景没有任何主流先例, 且 2026 年密集的绕过/逃逸判例(Pillar「沙箱逃逸周」、Cursor CVE-2026-73218、IBM Bob)直接否定其作为安全边界的地位。

## 1. Claude Code(Anthropic)

1. 双边界 OS 沙箱(默认关): sandbox-bash 只覆盖 Bash/PowerShell/Monitor 及子进程; macOS Seatbelt, Linux/WSL2 bubblewrap+socat(可选 seccomp 阻断 Unix socket); 文件默认可写=工作目录+临时目录, 读取默认全机可读(含 ~/.ssh)。[docs/en/sandboxing](https://code.claude.com/docs/en/sandboxing)
2. 网络隔离=代理白名单制: 沙箱内无直接出口, 经本机代理按 network.allowedDomains 检查, 白名单起始为空。Anthropic 工程博客: 「有效沙箱必须文件+网络隔离成对」; 内部数据: 沙箱使审批提示减少 84%。[engineering 2025-10-20](https://www.anthropic.com/engineering/claude-code-sandboxing)
3. 已知缺口: 文件工具/MCP/hooks 在沙箱外; 沙箱依赖缺失时**默认降级为不沙箱**(需 failIfUnavailable/strict 才 fail-closed); 有 dangerouslyDisableSandbox 逃生门。[GH #26616](https://github.com/anthropics/claude-code/issues/26616)
4. flag 语义(与平台 LC argv 直接相关): `--allowedTools` 是**免审批白名单, 不移除工具**(`--tools` 才是硬限制); `--disallowedTools` 裸工具名才移除工具; `-p` 模式未白名单默认拒绝; `--restricted` 整体移除执行类工具。[cli-reference](https://code.claude.com/docs/en/cli-reference)
5. 企业建议: 不受信内容「用 VM 运行」列最佳实践第 4 条; 云版本每会话独立 VM、凭证经代理替换、真凭证永不进 VM。[security](https://code.claude.com/docs/en/security)
6. 事件: 曾静默修补可与注入链式实现外泄的沙箱绕过。[SecurityWeek 2026-05-20](https://securityweek.com/anthropic-silently-patches-claude-code-sandbox-bypass)

## 2. OpenAI Codex CLI

1. 三档: read-only / workspace-write / danger-full-access; `--yolo` 官方标注 **"YOLO (not recommended)"**。[docs/sandbox.md](https://github.com/openai/codex/blob/87cce88f4865685a863e1430f0fad4cf5ea542e62/docs/sandbox.md)
2. 机制: macOS Seatbelt; Linux Landlock+seccomp; 默认无网络+仅工作区可写。
3. 网络默认禁用: workspace-write 下须 config.toml 显式开, **该开关只在 config 不在 CLI flag**——平台只传 --sandbox 时网络策略继承宿主 ~/.codex/config.toml。
4. **官方 Docker 指引(与平台场景直接对应)**: 容器内 Landlock/seccomp 不可用时, 「配置容器提供所需隔离, 然后在容器内以 --sandbox danger-full-access 运行」——官方背书「外层容器即沙箱、内层放开」。

## 3. Kimi Code(月之暗面)

1. 官方无任何 OS 级沙箱; 安全模型=统一审批门: 只读工具自动放行, Write/Edit/Bash 默认审批。[tools.md](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/reference/tools.md)
2. 三权限模式: Always Ask(默认)/Ask When Needed(/yolo)/**Never Ask(/auto: 全自动含敏感文件与危险命令, 内置守卫不拦截)**。[interaction.md](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/guides/interaction.md)
3. 规则体系=名称模式匹配(Bash(rm -rf*) 式)+hooks——命令名级护栏, 非调用/副作用级。
4. 结论: **Kimi 官方不提供隔离边界; 平台的 bwrap 四重隔离是平台自建能力**。

## 4. pi(earendil-works/pi)

1. 核心 bash/文件工具宿主直跑、零沙箱、无内置审批安全模型。[pi.dev](https://pi.dev/)
2. 沙箱=示例扩展: 官方 examples/extensions/sandbox 直接复用 **@anthropic-ai/sandbox-runtime**(与 Claude 同一 runtime): denyRead ~/.ssh 等、域名白名单。[sandbox/index.ts](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/sandbox/index.ts)
3. 官方隔离指引=外接四路线(Plain Docker / Docker 沙箱·代理代持凭证 / NVIDIA OpenShell / Gondolin 微 VM)。[containerization.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/containerization.md)
4. 判读: pi 的「不沙箱」是极简 harness 哲学(隔离当用户自选外挂), **不能读作「直跑安全」背书**; pi 官方自己给出了需要隔离时的全部路径。

## 5. 业界对照(要点)

- OpenHands: Docker sandbox 默认; Process 档官方明示 "unsafe, but fast"; **docker-in-sandbox(强化运行时+非特权嵌套 Docker+userns+无宿主 socket)解决「代理需要容器」**。[docs](https://docs.openhands.dev/enterprise/docker-in-sandbox)
- Devin: 云=每会话 VM; CLI --sandbox 与 Claude 同构+**fail-closed(沙箱解析失败拒绝启动)**+企业强制三态。[docs](https://docs.devin.ai/cli/sandbox)
- Cursor: 云=VM; 本地沙箱 2026-02 三平台落地; 「必须教模型认识沙箱」; 沙箱化停顿 -40%。[blog 2026-02-18](https://cursor.com/blog/agent-sandboxing)
- Gemini CLI: 五档(Seatbelt/Docker/**gVisor·runsc 官方称最强**/LXC/icacls)。
- Aider: 无沙箱, headless --yes=全信任, 靠外部平台补隔离。

## 6. 关键判例

1. **无人值守零先例**: 所有平台派发型产品全部 VM/容器; 交互式工具 2025-26 全在补 OS 沙箱, 共同动机=approval fatigue+「审批不可依赖」。
2. **Pillar「Week of Sandbox Escapes」(2026-07)** 四类失败模式: ①denylist 追不上 OS 复杂度 ②工作区配置即代码 ③白名单按名信任 ④**特权本地守护进程在沙箱外**; 核心论断: 「agent 爆炸半径不是 agent 进程, 而是它能写的一切以及宿主后来信任的一切」。[Pillar](https://www.pillar.security/blog/the-week-of-sandbox-escapes)
3. **Docker socket 逃逸链(Pillar Day 2, 直接命中平台现场)**: 沙箱 deny-default 也挡不住 docker CLI+socket+网络 → 宿主家目录读写(Cursor 定 High, CVE-2026-73218)。**映射: pi reviewer 宿主自主拉容器栈正是失败模式④的良性实例——同一通路在注入场景即完整逃逸链。**
4. 护栏被绕过直接证据: IBM Bob 注入诱导跑恶意软件; DeepSeek Harness 逃逸 CVE-2026-82533(CVSS 9.4); IDESater 10 个 AI-IDE 100% 可注入。

## 对 cadence-aria 的启示(5 条)

1. **沙箱问题普遍存在, 但解法已收敛成标准件**: 统一补边界不必自创——@anthropic-ai/sandbox-runtime 是现成业界标准件(pi 官方扩展示例可直接平移)。
2. **「宿主直跑+护栏」无人值守零先例且判例全负面**: pi 的不沙箱是「用户自担隔离」哲学, 非安全背书; 平台走 pi 式直跑=全行业首个无人值守宿主直跑平台, controller 对注入面的顾虑与业界证据一致。
3. **若仍倾向 pi 式直跑, 最小补偿控制集**: 专用低权 OS 用户; 域白名单代理; **Docker socket 对 agent 不可达**(Pillar 逃逸链第一步, pi reviewer 事件即此通路)或非特权嵌套; 全量审计+trust handoffs 监控; 凭证不进 agent 环境; fail-closed。成本接近自建沙箱且无内核级保证——应如实标注「降级接受风险」而非等效替代。
4. **kimi 构建类 CHECK 不可执行的正解是「沙箱内给运行时」**: OpenHands docker-in-sandbox 证明隔离与容器能力可兼得; Codex 官方背书外层容器+内层放开; 被否的原方案 C 的顾虑(特权嵌套/挂 socket)恰是 OpenHands 明确排除的做法——非特权+userns 路线有现成参照。
5. **REQ-LCG-04 处理**: danger-full-access 官方 "not recommended"、业界无平台作无人值守默认; 若最终方案采用容器内放开或宿主直跑, 应以变更提案显式修订 REQ-LCG-04(区分「宿主特权」与「隔离边界内特权」两种语义), 不绕过。

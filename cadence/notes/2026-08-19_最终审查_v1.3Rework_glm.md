## Issues

**Important（merge 条件）**
1. `src/web/handlers/support.rs:default_logical_codebase_id` + `store.rs:list`（按 id 字典序取首条）：legacy 别名的“默认首 LC”在「已迁移 v1.2 数据 + 之后新建 LC」的 project 里**不确定**——legacy LC id 为 `logical_codebase_<sha256(project_id)前缀>`，新 LC id 为 `logical_codebase_<uuid>`，二者字典序随机。新 LC 排前时，旧客户端打 `/logical-codebase/initializations` 等别名端点会被改指向新 LC。测试只覆盖“首个创建的 LC”与“迁移即首 LC”，未覆盖迁移后新建 LC 的排序竞争。建议：别名钉住 legacy 迁移 LC（存在则优先），或在 design.md 明示“别名=当前字典序首 LC，非 v1.2 数据 LC”并接受。不影响新端点正确性（全部按显式 lc_id），故非 blocker。

**Minor**
2. `project_store.rs:get/list`：每次读取都执行 `migrate_legacy`（锁 + manifest 存在性检查），list_projects 对每个 project 逐个执行——热路径重复 I/O，幂等但可优化为一次性。
3. `store.rs:create`（LC）名称唯一性仅在同 project 内比较且 tombstone 后可复用名——软删后重建同名 LC 会让旧 issue 的 lc_id 指向不同代码库；当前 DELETE 后 issue 不迁移/不校验，属已知软删语义残余（R6 已记录“迁移 DELETE 语义”残留）。
4. `IssueStore::create` store 层不强制 `logical_codebase_id`/`repo_id` 互斥或 lc 存在性（依赖 handler 层 guard）；内部调用点绕过 handler 时无防线。

**残余风险**：park-1/2（多 target plan→coding 断裂，文档化待专项）；人工 P0 浏览器冒烟仍留待 controller（自动化 HTTP e2e 已覆盖同路径）；`it_provider parse_error_timeout` flake 本轮未复现。

## 2. Q1 附答：「聚合初始化没自动开始」与「冷启动卡在规则/政策」是不是同一个原因

### 2.1 结论：**同一个原因**（同一条因果链的两个面）

因果链（HEAD 现状，逐步带文件:行）：

```
登记提交（submit.inc.rs:95-118，后台 spawn）
   └─► advance_lc_bootstrap（logical_codebase_bootstrap.rs:319）
        └─► 推进器（bootstrap_advance.inc.rs:315-345）选中第一个可动步 = rules_policy，Prepare
             └─► ensure_lc_initialization_started（handlers.inc.rs:243）
                  └─► start_lc_initialization_outcome（handlers.inc.rs:336）
                       └─► start_lc_aggregate_initialization（handlers.inc.rs:83）
                            └─► select_aggregate_provider_blocking（handlers.inc.rs:100-116）
                                 └─► NeedsVerification ⇒ Err ⇒ operation **不创建**
             ◄── advance 收到 WaitingForHuman{reason_code}
                  （bootstrap_advance.inc.rs:341-352 —— 只写进 advance 的返回值，
                    **不落任何 durable 事实**）
```

投影层因此「什么都没发生」：

- `src/product/logical_codebase/bootstrap_projector.inc.rs:227-246` `project_rules_policy_step`：
  没有 policy artifact ⇒ 投影 = `NotStarted` + `failure: None` + `allowed_actions: [Prepare]`。
  ⇒ 界面只显示「未开始」+「准备」按钮，**看不到任何停止原因**（与 owner 截图一致）。
- `rules_policy` 之后的两步（`member_index` / `aggregate_index_active`）依赖前一步的产物 ⇒ 一起停在 `NotStarted`。
  ⇒ owner 截图里「成员索引 / 聚合索引激活 未开始」也是同源。
- `src/product/logical_codebase/bootstrap_projector.inc.rs` 里 `aggregate_initialization` operation 不存在 ⇒
  `web/src/components/lifecycle/AggregateInitializationCard.tsx:167` `operation ? STATUS_LABELS[...] : "尚未初始化"` ⇒
  显示「尚未初始化」+ `:213` 「启动聚合初始化」按钮。

⇒ **两个现象是同一个根因的两个投影**：
「聚合初始化没自动开始」= 创建被拒；
「冷启动第三步（规则/政策）卡住、原因不暴露」= 同一个拒绝**没有落 durable 事实**，投影回 `NotStarted`。

**创建链上共有两道「不创建 operation」的闸门**（顺序固定，命中即短路）：

| 序 | 闸门 | 位置 | owner 现场是否命中 | 稳定码 |
|---|---|---|---|---|
| ① | provider 选择门（L1/L2 两层判据） | `handlers.inc.rs:100-116` | ✅ **命中**（四家全「未探测」） | `aggregate_initialization_provider_needs_verification` |
| ② | trust 硬前置门 | `handlers.inc.rs:140` → `:627-651` | ❌ 未到达（① 已短路）；选中 Kimi/Codex 时才会命中 | `aggregate_initialization_trust_waiting` |

⇒ **修复必须把两道门都算进去**：只修 ①，选中 Kimi/Codex 的机器仍会在 ② 卡住；只修 ②，owner 现场仍卡在 ①。

### 2.2 补充说明（避免与已知缺陷混淆）

- 本波另有两条**独立**的冷启动阻断缺陷（与本条不同源，只在选择门通过后才会暴露）：
  - 审计快照预算超限阻断冷启动（`cadence/notes/2026-11-03_*P1-18*` 一族；本波 `root_recipe_snapshot.inc.rs` / `audit_snapshot_budget.rs` 相关）；

## 5. 风险提示：与「不点击不运行探针 / 无点击不花 provider 额度」的冲突评估

### 5.1 冲突面

| 既有契约 | 出处 | 与「恢复第一次自动执行聚合初始化」的关系 |
|---|---|---|
| 「不点击不运行任何探针」 | `src/product/logical_codebase/provider_capability_revalidate.rs:1-10`（模块头注释） | **直接冲突**（若恢复方式 = 自动触发 capability 核验） |
| 「选择器 SHALL NOT 自动触发 capability 核验」；「无可用候选或 health degraded 时 SHALL 不创建 operation」 | `openspec/specs/non-interrupt-repository-bootstrap/spec.md:230`（REQ-BOOT-07） | **直接冲突**（若恢复方式 = 绕过 L2 判定创建 operation） |
| 决策 3「能力未核验时引导用户显式核验，**不自动触发探针**」；理由明写「自动触发（同步）与『不点击不运行任何探针』的既有契约**直接冲突** → 必须改契约才能做 → 超出本方案范围」 | `openspec/changes/archive/2026-11-03-fix-aggregate-cold-start-and-audit-budget/design.md:60-95` | **直接冲突**（同上） |
| 「不自动重试失败步骤；绝不自动重试」 | `src/product/logical_codebase/bootstrap_advance.inc.rs:169-175`（「失败绝不自动重试：这是人工决定」） | 不冲突（恢复的是「首次自动开始」，不是自动重试） |
| 「无点击不花 provider 额度」 | 同决策 3 | **部分冲突**：跳过路径下**零 provider turn**，不冲突；非跳过路径下必有 provider turn ⇒ 必须先有一家**已核验**的 provider |

### 5.2 评估结论：**存在两条互斥路线，必须 owner 选一条**

**路线甲（不违反任何既有契约）：让「无需 provider」的路径自动开始**

- 前提：聚合根已具备 `AGENTS.md` **且** `.claude/rules/language.md` ⇒ 整条链**零 provider turn**（durable 用例已钉住 `stream_launches() == 0`，`tests_parts/bootstrap_advance.inc.rs:322-327`）。
- ⇒ 在这种情形下**不存在**「自动花额度」问题，也**不需要**触碰 capability 探针契约。
- 代价：需要把「用户规则文件跳过」判定从执行期**前移到创建期**（§4-B），且要处理「创建期判定 vs 执行期判定」的一致性。
- 覆盖面：**只**覆盖「聚合根已初始化」的用户。owner 现场若是**空目录新建 LC**（截图里 `my-lc-root/` 是「普通空目录」），则**不适用** ⇒ 这条路线**修不好 owner 的现场**。

**路线乙（能覆盖现场，但与既有契约冲突，必须走 OpenSpec 变更）：**

- 覆盖现场需要在「L2 未核验」时也自动创建 operation 并自动开始 ⇒ 要么
  - **乙-1** 自动触发 capability 核验 ⇒ **直接违反**「不点击不运行探针」+ 决策 3 + 会自动花 provider 额度；
  - **乙-2** 绕过 L2 判定创建 operation ⇒ **违反 REQ-BOOT-07「不创建 operation」**，且 gateway 侧仍会 fail-closed 拒绝真正的 provider turn（`provider_selection.rs:130-155` 与 `production_policy_resolvers.rs` 的 `require_supported` 同源判定）⇒ 只会把「不创建 operation」变成「创建后执行期失败」，**更糟**；
  - **乙-3** 把「provider turn 三步」与「确定性步骤（machine_skills / aggregate_preflight / 政策发布）」拆成两个 operation / 两段状态机 ⇒ 五步状态机是 **byte-stable durable 协议**（步骤枚举 `aggregate_initialization.rs:110-123` + 校验 `aggregate_initialization_store_validation.inc.rs:143-160`），改动面大，决策 3 已明写「异步自动触发要给五步状态机加前置态……改动风险高」。
- ⇒ **乙-3 是唯一技术上说得通的「真·第一次自动开始」，但代价与契约变更都最大。**

**路线丙（零契约冲突、只改失败面，最小可行）：**

- 保持「不创建 operation」不变（符合 REQ-BOOT-07），但让**停止原因落 durable 事实并被 UI 渲染**（§4-C）：用户点一次「启动聚合初始化」/「核验 Pi」后，冷启动第三步自己能继续。
- 代价：owner 的期望（「点了添加代码库后初始化应该自动开始」）**只能部分满足**（需要用户点一次能力核验）。

### 5.3 其它风险

1. **静默失败风险**（当前已在发生）：`submit.inc.rs:104-112` 的后台 advance 失败只 `tracing::warn!`，UI 无任何出口 ⇒ 用户看不到「为什么没自动开始」。**这条无论选哪条路线都应先修**。
2. **幂等与并发**：`advance` 持 LC 级 `.bootstrap-advance.lock`（`bootstrap_advance.inc.rs:245-260`）；`ensure_lc_initialization_started` 的幂等键 = `command_id` = `bootstrap-advance-{lc}-rules_policy-rev{n}`（`:206-224`）⇒ 恢复自动执行时**不要改 command_id 派生**，否则会绕过既有幂等语义、可能起第二个 provider turn。
3. **provider turn 额度**：一旦 provider turn 真跑起来（跳过路径之外），每次自动开始 = 一次真实 LLM 轮次 × 3 步。自动触发意味着「用户没点也花额度」——这正是决策 3 拒绝自动触发的原因，**不是可以顺手放宽的细节**。
4. **trust 门**：选中 Kimi/Codex 时会进 `aggregate_initialization_trust_waiting`（`handlers.inc.rs:627-651`）⇒ 自动开始会撞上人工 trust 登记 ⇒ 自动链照样停在 `rules_policy`。恢复方案必须把 trust 也纳入「可自动继续」的条件，否则只是把失败点后移。
5. **与既有并行 worker 的冲突**：`FixBootstrapAdvanceStall` 正在改 `rules_policy` 的停止原因暴露面。本报告 §4-C 与其改动面**高度重叠**（`bootstrap_projector.inc.rs` + `bootstrap_advance.inc.rs`）⇒ 若 Main 决定实施，**必须与该 worker 合并**，避免两人同改一个投影器。

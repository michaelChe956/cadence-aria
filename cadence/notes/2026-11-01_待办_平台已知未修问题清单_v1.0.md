## P0-1 自动化换代序列被 autopilot 抢 revision → provider 永远改不掉

**现象**：在「Work Item Plan 配置」对话框把 Author 从 `claude_code` 改成 `kimi_code`、Reviewer 从 `kimi_code` 改成 `claude_code` 后点「启用自动化」，**稳定报** `automation enrollment revision conflict`。报错后自动化仍在跑，且 **provider 仍是旧值**。

**为什么"你怎么点都错"**：前端在**同一次点击**里做三步（`web/src/components/lifecycle/useIssueLifecycleGeneration.ts:525-585`）：

```
① 记录是 terminated → 先用「旧 options」重开
② provider 不同 → 立刻发 Disable（"关闭自动化"，界面无此按钮，纯内部）
③ 再按「新 options」Enable
```

- 第①步成功（并**立即触发 autopilot 开始生成**）；
- **autopilot 建 plan 后调 `bind_plan` → `bind_plan_ids_locked` 把 `policy_revision += 1`**（`src/product/issue_automation_store_parts/cas_internals.inc.rs:55`）；
- 第②步 Disable 携带的是第①步返回的 `expected_revision` → 撞 CAS 臂 B（`expected_revision != saved.policy_revision → Conflict`，`issue_automation_store.rs:267`）→ 409；
- 第③步永不执行 → provider 从未被改。

**实测数据**：`enabled=true / policy_revision=19 / updated_at=16:27:17`（= 00:27:17，正是那轮开始时间）；命令账本 10 条，最后一条 `76ed74f9` bind_v=6；`options.provider` 仍是 `claude_code / kimi_code`。

**影响**：**owner 无法通过 UI 更换 provider**（除非等生成完全停下、autopilot 不再写记录的那一瞬间，属于靠运气）。

**建议修法**（任一）：
- 前端第②③步发送前**重新 GET 当前 revision**（而不是沿用第①步返回值）；
- 或服务端提供「换 payload 重开」的**原子命令**（一次 CAS 完成 disable+enable），前端不再拼三步；
- 或 `bind_plan` 不顶 `policy_revision`（绑定不是授权变更；代码注释也写着「版本不递增——绑定不是换代」，但实现里 `+= 1` 与注释矛盾 ← **注释与实现不一致，按注释改更合理**）。

## P0-2 旧 plan 在 CAS 之前被删 → Enable 被拒后留下「旧的没了、新的没授权」

**代码**：`supersede_terminated_generation_and_cas`（`src/web/handlers/automation_enrollment_reenable.rs:175`）先调 `supersede_terminated_plan_generation(...)` **删除旧 plan 世代**，**之后**才做 CAS；CAS 失败（如上条 409）时**不回滚**。

**实测**：00:19 建出 plan `f0dbe09c`；00:20 Enable 被拒；随后 `issue-work-item-plans/` **空目录**、`work_item_plans=0`、`work_items=0`。

**影响**：owner 一次失败操作就**丢掉上一代 plan 产物**，且没有任何提示说明"旧 plan 已被删"。

**建议修法**：CAS 成功后再删旧世代；或删除前先做完整校验（把 409 提前到删除之前）；至少失败时回滚/保留旧世代。

## P1-3 409 文案不可区分

`issue_automation_store.rs` 里两处不同语义都返回同一个 `enrollment_conflict`：

| 语义 | 位置 |
|---|---|
| revision 不等 | CAS 臂 B（`:267`） |
| enabled 下 payload 被改（授权范围不可原地改写） | CAS 臂 A（`:250-265`） |

线上文案恒为 `automation enrollment revision conflict`（`details.current_revision` 只在部分路径带）。

**影响**：owner/前端无法判断「该重试（版本号变了）」还是「该改流程（payload 不能原地改）」——本次排障就被这句话带偏。

**建议**：拆成两个稳定码（如 `automation_enrollment_revision_stale` / `automation_enrollment_payload_immutable`），文案各给下一步。

## P1-6 「进程重启：委托返修接力未启动」误报

**现象**：会话时间线出现

```text
human_confirm | SC 返修接力启动失败，已回落人工门：进程重启：委托返修接力未启动
```

但**该轮根本没有进程重启**。

**定位**：`recover_delegated_rerun_orphan`（`src/web/workspace_session/manager/durable_projection.rs:518`）→ `recover_delegated_author_rerun_failure("进程重启：委托返修接力未启动")`；孤儿判据是「durable `phase=Generate` ∧ `status=running` ∧ 本进程无活动 run」。**评审→委托返修的交接窗口**正好同时满足这三条（phase 已回 Generate、status 仍 running、接力的 run 尚未注册）→ 活会话被判孤儿 → 多开一个门节点 + 写一句骗人摘要。

**影响**：owner 看到「重启了」会误判要不要自己接管；时间线多一个假门节点。

**建议**：判据加时间窗/租约证据（例如「距最后一次 provider 活动 < N 秒则不下孤儿结论」），至少文案改成「在飞委托返修接力未在本进程注册（可能是重启，也可能是交接窗口）」。

## P2-8 作者阶段结构拒收在流水里记成 `stage=final`

`candidate_attempt_record_from_failure` 按 `PlanningCompileFailureKind` 派生 stage：`Structure(set)` → `Structure`，`Operational{..}` → `Final`。作者阶段的结构拒收是**自建 `Operational`**（为了带自定义稳定码与共享环模板），于是落成 `stage=final`。

**影响**：读数里分不出「作者阶段结构拒收」与「终编译失败」（两者稳定码同为 `final_compile_structure_rejected`）。`CandidateAttemptStage::Structure` 变体存在但未被使用。

**建议**：给派生加显式 stage 入参（调用方知道自己在哪个阶段），不要靠 failure kind 猜。

## P2-9 门快照不带 `owner_question` / `owner_options`（契约级）

`human_gate_snapshot.findings` 是 `ClassifiedFinding`，没有 `owner_*` 字段；这两个字段只存在于 review verdict 的 `ReviewFinding` 上。

**现状**：UI 门卡从 verdict 读得到 2~3 个带后果的选项（实测第 5 次跑的卡有 3 个选项）；但**门快照 API 读不到**，而 `human_gate_feedback` → SC 修订提示词走的是快照的 `required_action`（该字段是可执行的，实测给出了两条具体修法 ✅）。

**建议**：给 `ClassifiedFinding` 增加 `owner_question` / `owner_options`（可选字段、向后兼容）。**属 durable 结构调整 → 必须先走 OpenSpec。**

## P2-10 规则 vs design 决策冲突无裁决点（locale 案例）

**实测**：业务仓 `cadence/project-rules/frontend-ui-standards.md` §4 写「必须配置中文 locale（zh-cn），此为强制条款，不是可选项」、§10 缺口 #1 写「强制待办，首次前端需求优先补齐」；而该 Story 的 design `[DEC-010]` 明确「本 Story 不补齐 Element Plus 中文 locale，缺口保留」（并登记风险 R-05 + 缓解 DEC-005）。

## P1-13 provider 能力未核验 → gateway 准入 fail-closed，但没告诉用户去点「核验」

**现象**（2026-11-02 新机器真机，写 Story/Design 时）：

```
logical author gateway validation failed: provider_gateway_capability:
provider_capability_launch_not_confirmed: PlanningReadOnly launch cell is Unknown
```

**根因**（`src/product/logical_codebase/production_policy_resolvers.rs:314`）：
gateway 准入要求该 provider 能力矩阵的 `launch` 格为 **Confirmed**；`Unknown`（从未被真实
probe 写过）与 `Denied` 一律 fail-closed 拒绝（注释原文：「等待真实 probe(2d)写入 Confirmed 行后
才可启动」）。**所以这是「这台机器上没做过能力核验」，不是模型或网关能力不行。**

**缺口**：报错只给机器码，**没有任何可行动指引**。用户不知道：
- 能力矩阵是**本机**状态（换机器 = 全 Unknown）；
- 需要去**逻辑代码库管理面板**（`LogicalCodebaseManagementPanel`）的**提供方能力卡**
  （`ProviderCapabilityCard`）对**每个要用的 provider** 点「核验」；
  该按钮 POST `POST /api/projects/{project_id}/logical-codebases/{lc_id}/capability-revalidate`
  （首次**分钟级**同步等待），四态回显：已核验 / 未核验 / 核验中 / 失败，成功后重读。

**要做的**：
1. **引导**：凡出现 `provider_capability_launch_not_confirmed`（或矩阵任一格 Unknown），
   错误面必须直接给出「请到 逻辑代码库管理面板 → 提供方能力卡 → 对该 provider 点『核验』，
   核验通过后再试」的可点击指引（并说明核验是分钟级同步等待）。
2. **面上区分**：`Unknown`（没核验过 → 去点核验）与 `Denied`（真实负向证据 → 不要重试，
   换 provider）当前是同一句 fail-closed，owner 无法分辨该做什么。
3. **与 P1-14 合并诊断**：同一台新机器上「skills 步失败」与「能力格 Unknown」是**同一个根因**
   （provider 从未被确认可启动），却报出两条互不相干的错。

## P1-14 skills 步失败的 `stderr_summary` 生产路径恒空 → 「no stderr summary」是废话

**现象**（同一次新机器真机，聚合初始化第 1 步 `MachineSkills` 失败）：

```
aggregate_machine_skills_failed: stage aggregate_initialization: no stderr summary
```

**根因**：`AggregateInitializationErrorRecord.stderr_summary` 在**生产路径恒为 `None`**
（只有测试会填 `Some`）；`bootstrap_projector.inc.rs:344` 用
`.unwrap_or("no stderr summary")` 兜底 → **任何**该步失败都显示这一句，**零信息量**。

**要做的**：
1. 把 provider turn 的 **stderr（截断 + 脱敏）** 带进错误记录，让失败面能说清「命令没找到 /
   权限不足 / provider 未就绪 / 根目录不可写」等具体原因；
2. 该步失败同样要给**可行动指引**（provider 未登录 / CLI 不在 PATH / 四条斜杠命令未安装到该仓 /

## P1-15 用户机器未装 codegraph → 聚合冷启动三步全红被永久卡住

**现象**（2026-11-02 新机器真机，机器上没装 codegraph）：

```
规则/政策     失败  aggregate_pre_check_failed: stage aggregate_initialization: no stderr summary
成员索引      失败  aggregate_pre_check_failed: stage aggregate_initialization: no stderr summary
聚合索引激活  失败  aggregate_index_failed:aggregate_index_degraded:codegraph_missing:
                  codegraph: provider command not found: codegraph
product store operation failed
```

**要点**：
1. **只有索引步说真话**（`codegraph_missing: provider command not found: codegraph` ✅ 可行动）；
   另两步落到 `no stderr summary`（P1-14 的空洞）→ 用户看到三条红，其中两条无信息。
2. **三步都依赖 codegraph**：成员索引直接调 `CodeGraphCli`；`pre_check` 步跑
   `/pre-check`（内部同样依赖 codegraph）。
3. **语义矛盾**：`codegraph_missing` 在 `codegraph_cli.rs:311` 是 **`Degraded`（降级）**
   —— 降级本该意味着「可继续、索引未就绪」，但冷启动仍把它当**致命失败**，
   于是「没装 codegraph」= **整个 LC 冷启动永久卡死**，四条命令一条都跑不完。

**要做的**：
1. **前置探测**：冷启动**第一步之前**就探 `codegraph --version`；缺失时**只报一次**、
   明确指引：「未检测到 codegraph（成员索引与跨仓符号检索依赖它），请先安装：
   `npm i -g @colbymchenry/codegraph`」，不要让三步各报各的。
2. **统一错误码**：`pre_check` / `member_index` 两步在 codegraph 缺失时也返回
   `codegraph_missing`（可行动），不要落到 `no stderr summary`。
3. **降级语义落地**：要么 `codegraph_missing` 真的降级（跳过索引、标记「索引未就绪」、
   其余步继续、之后可补建索引），要么明确它是致命并**在前置探测就拦住** ——
   不能既标 Degraded 又阻断整个冷启动。
4. 与**票 2（多仓入口布局引导）**合并：入口的依赖前置里加一条「需先安装 codegraph」。

## P1-16 审计预算超限：英文长句 + 没点名成员仓 + 一个构建产物能阻断整个冷启动

**现象**（2026-11-02 新机器真机，聚合初始化**预检**步失败）：

```
root recipe filesystem audit failed: product_store_io: audit snapshot budget exceeded at
/Users/<user>/code/zhgc/pms/target/pms/log/error-2026-07-11.log:
68205791 cumulative bytes > max_bytes 67108864 (fail-closed; paths ignored by
.gitignore/.git/info/exclude are already excluded — clean up or .gitignore remaining
untracked build outputs)
```

**机制**（`root_recipe_receipt_store.inc.rs`）：审计**递归走聚合根**，逐路径
- 被 `.gitignore`（含嵌套成员仓）/`.git/info/exclude` **忽略的路径 → 整个跳过**
  （不计条目/字节，不进快照）✅；
- 其余路径 → 计条目（上限 20000）与字节（**上限 64 MiB**）；
- 超限 → **fail-closed**，整个预检步失败 → 冷启动卡住。

**本次这一条是环境问题不是代码缺陷**：该成员仓的 `target/pms/log/error-*.log`（68 MB）
**没被 .gitignore 忽略** → 计入 → 一个与 recipe 无关的本地构建产物把预算撑爆。

> ⚠️ **但同一道门还有平台侧成因**：`.git/objects/pack/*.pack` 同样会撑爆预算，且**用户无从处理** → 见 **P1-18**。
> 两者必须分开归因。

**你那台机器的解法**（1 分钟）：
```bash
cd /Users/<user>/code/zhgc/pms
rm -rf target/pms/log/error-*.log        # 或整个 target/
# 让审计以后跳过它（被 gitignore/info-exclude 忽略的路径不计预算）
printf '/target/
' >> .git/info/exclude   # 首选：不改被跟踪的 .gitignore（改它会撞写入范围门禁）
```

**平台侧要做的**：
1. **文案**：报错是**英文长句**且**没点名是哪个成员仓** → owner 看不出该改哪个仓的
   ignore 文件。应给中文 + 「成员仓 X 的路径 Y 超出审计预算（64 MiB）」+ 可执行动作。
2. **区分两类失败**：现在的「审计预算超限」与「recipe 写了不该写的东西」共用同一条
   fail-closed 通道 → 用户无法判断该**改代码**还是**清磁盘**。前者应是可跳过的提示，
   后者才该阻断。
3. **预算口径**：单个 68 MB 日志就爆 64 MiB 预算、对含真实构建产物的仓偏紧 →
   建议单文件超阈值时**跳过并记录**（而不是让整仓审计失败）。

## P1-18 审计预算口径：累计字节记在单个路径上（必被误读）+ 预算对真实工作区偏小 + `.git/` 被计入

**现象**（2026-11-02 新机器真机，聚合初始化**预检**步失败）：

```
root recipe filesystem audit failed: product_store_io: audit snapshot budget exceeded at
/Users/<user>/code/zhgc/pms/.git/objects/pack/.pack-523bea2d6a5871669bd2663c9d38f26214a38c8.pack:
69696018 cumulative bytes > max_bytes 67108864 (fail-closed; ...)
```

**用户实测（`git count-objects -v`）**：`.git` 总大小 **21 MB**、`size-pack` **17.31 MiB**、
**最大的 pack `pack-523bea2f…` 只有 10 MB** —— 与报错里的 66.5 MB **对不上**。

**真相（三层，逐层都要修）**：
1. **文案把「累计」记在「单个路径」上**（`{bytes} cumulative bytes > max_bytes`，
   而 `{path}` 是**越线时正在处理的那个文件**）→ 必然被读成「这个文件 68 MB」。
   **实测反证**：那个 pack 只有 10 MB。**这条错误文案把 controller 和 owner 都误导了**
   （2026-11-02 我自己先误判成「`.git/` 被计入是直接原因」）。
2. **`.git/` 确实被计入**（审计唯一跳过条件是「被 `.gitignore`/`.git/info/exclude` 忽略的路径」，
   而 `.git/` 目录默认不被忽略；代码里 `.git` 只被**分类**不排除）→ **21 MB 的对象库被算进预算**。
   **同仓两个排除面矛盾**：codegraph 的清单**含** `**/.git/`（`aggregate_index/exclude.rs:19`），审计的**不含**。
3. **64 MiB 预算对真实多仓工作区天然偏小**：审计快照的是**整个聚合根**（所有成员源码 + 各自 `.git` + 未忽略产物），
   66.5 MiB 累计里只有 21 MB 来自 `.git/`，其余约 45 MiB 来自源码与未忽略产物。
   → 预存在体量就能压垮预检。

**与 P1-16 的关系（必须分开归因）**：同一道门（审计预算）、两种成因 ——
P1-16 是**用户侧**（`target/pms/log/error-*.log` 未被 gitignore 忽略 → 用户清理或加 ignore 即可）；
P1-18 是**平台侧**（累计口径 + `.git/` 被计入 + 预算偏小）。**失败面必须能分辨这两类**。

**owner 裁定（2026-11-02）**：「也记录一下。**不一定要解决**，但是要给用户描述清楚怎么做，
这应该是和上面那个同一个问题。」→ **确认与 P1-16 / P1-17 同源同门**（预检步快照整个 LC 聚合根，
上限 64 MiB，沙箱开始前的基线就超了，与沙箱写入无关）。
→ **本条最低要求 = 文案与指引，不要求改预算逻辑**；用户面文案草案见
`cadence/notes/2026-11-02_独立票据_失败面可行动化_说清问题与给出操作_v1.0.md` 第 2.1 节。

**要做的**：
1. **文案分诊**（P1-17 的直接输入）：改成「审计快照累计字节 66.5 MiB 已超上限 64 MiB（**当前聚合根共 3 个成员仓**；最大计入项：`.git` 对象库 21 MB、未忽略的构建产物约 45 MB）。
   操作：① 把不参与检索的产物加进 `.git/info/exclude`（不改被跟踪的 `.gitignore`，改它会撞写入范围门禁）；② 或等平台提高/自适应预算。」
   —— **必须把「累计」与「单文件」分开表述，并点名是哪个仓的大项**。
2. **`.git/` 整目录跳过**（与 codegraph 排除口径统一）。
3. **预算按规模自适应**（或改为对「本次 recipe 新写入的文件」计预算 —— 那才是审计的本意：
   证明 recipe 没乱写；而不是给用户既有体量设上限）。
4. **单文件超阈值改为跳过并记录**，不让整仓审计失败（与 P1-16 第 3 条同）。

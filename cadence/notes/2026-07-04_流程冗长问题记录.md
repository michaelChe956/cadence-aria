# 流程冗长问题记录

## 背景

当前 coding workspace 流程按角色串行推进：Coder → Tester → Analyst → Code Reviewer。实际使用中，一旦任一环节发现问题并要求回退，后续环节需要重新等待，整体耗时明显放大。

## 当前观察

- 对简单任务而言，完整走完 Coder、Tester、Analyst、Code Reviewer 的成本偏高。
- 本轮几个较小问题已经累计耗费至少半小时，用户感知为流程过重。
- Tester 能发现有效问题，例如孤儿 Rust 文件未接入 crate 导致 `cargo check` / `clippy` / `test` 假通过，但这类有效性不应以过长链路为代价。
- 当前流程的主要痛点不是单个角色能力，而是串行门禁、失败返工、重复上下文构建和重复 provider 调用带来的总延迟。

## 待讨论问题

周一继续讨论如何在保证效果的情况下简化流程，重点评估：

- 是否需要对任务按风险分级，简单任务走轻量验证链路，复杂任务保留完整角色链。
- 是否可以把 Tester 分为快速 smoke check 与完整独立验收两档。
- 是否可以在 Coder 阶段强制更可靠的自检契约，例如禁止 `0 tests` 被视为通过、要求目标文件进入编译树。
- 是否可以减少 Analyst / Code Reviewer 的默认触发频率，只在测试失败、风险高或用户显式要求时进入。
- 是否可以复用角色上下文与执行结果，避免失败后整条链路重新生成。

## 目标

设计一套更短、更可控的 coding workspace 流程：低风险任务更快完成，高风险任务仍保留足够独立验证与审查。

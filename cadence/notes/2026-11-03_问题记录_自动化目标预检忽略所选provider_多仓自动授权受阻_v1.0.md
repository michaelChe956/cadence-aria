# 问题记录：自动化目标预检忽略所选 provider，导致多仓「启用自动化」被拒

日期：2026-11-03
状态：**owner 裁定「先记录，不解决」** —— 本文件只做留痕，不开 OpenSpec change、不实施
触发来源：owner 真机跑多仓 work item group，在「Work Item Plan 配置」对话框切「自动化」后稳定报错

## 现象

- 入口：issue 工作台 → 「Work Item Plan 配置」对话框 → 生成模式切「自动化」
- 页面显示（红字）：

  ```text
  自动化目标加载失败：automation role chain has unsupported providers or missing action evidence
  ```

- 「启用自动化」按钮**被禁用**（投影读失败 → `automaticSubmitBlocked`），点「重试」重复同一失败。
- owner 侧选择：Author Provider = **Claude Code**、Reviewer Provider = **Claude Code**；claude_code 已核验，story / design 生成正常。
- 后端返回 422（`GET /api/projects/project_0001/issues/issue_0001/automation-target`，owner 现场抓包）：

  ```json
  {
    "code": "automation_role_chain_unsupported",
    "message": "automation role chain has unsupported providers or missing action evidence",
    "details": {
      "hint": "reconfigure the automation providers or re-select the automation target",
      "violations": [
        {
          "action": "planning_read_only",
          "capability_snapshot_ref": "cap_managed_snapshot",
          "projection_ref": null,
          "provider": "codex",
          "reason_code": "provider_capability_launch_not_confirmed",
          "role": "plan_author"
        },
        {
          "action": "coding_target_write",
          "capability_snapshot_ref": "cap_managed_snapshot",
          "projection_ref": null,
          "provider": "codex",
          "reason_code": "provider_capability_launch_not_confirmed",
          "role": "coder"
        }
      ]
    }
  }
  ```

- **owner 明确表示「我没选 codex」** —— 现场数据与选择一致：violations 里的 provider 是 **codex**，而 owner 选的是 claude_code。

## 根因（代码级）

**这次预检判的不是 owner 选的 provider，而是服务端默认 provider。** 四步：

### 1. 前端把选择丢掉了

`web/src/components/lifecycle/WorkItemPlanOptionsDialog.tsx:155`：

```ts
getAutomationTarget(targetScope.projectId, targetScope.issueId, {})
```

query 是**空对象** —— 对话框里选中的 `author_provider` / `reviewer_provider` **没有随请求发出**。
（同文件 `:566` 附近的 `web/src/api/client.ts:566-577` 已实现 query 序列化能力，只是这里没传。）

### 2. 后端在「没指定」时自己挑，且第一顺位是 codex

`src/web/handlers/automation_target.rs:115-125` → `resolve_enrollment_options_with_provider_workspace_config` → `src/web/handlers/support.rs:381-390`：

```rust
let author = match author_provider {
    Some(provider) => resolve_explicit_provider_name(provider, provider_availability)?,
    None => resolve_default_coding_provider("codex", test_provider_enabled, provider_availability)?,
};
let reviewer = match reviewer_provider {
    Some(provider) => resolve_explicit_provider_name(provider, provider_availability)?,
    None => resolve_default_coding_provider("claude_code", ...)?,
};
```

→ query 为空 ⇒ **author 默认 codex**、**reviewer 默认 claude_code**。

### 3. codex 被判为「可用」，于是没走回退

`src/web/provider_availability.rs:96-102`：requested（codex）不可用时按 `claude_code → codex → pi → kimi_code` 回退到第一个可用的。
可用性来自健康探针 `codex --version`（`src/web/provider_probe.rs:134`）。

⇒ 现场 codex 被判可用 ⇒ 默认 author 就落在 codex 上（**待查**：owner 自述该机器「只装了 claude code」，需现场 `which codex` 确认是否有残留 CLI / PATH shim，或工作区健康快照 `.aria/state/provider-health.json` 过期）。

### 4. 拿 codex 去查能力表 → 没核验 → 拒绝

`src/web/handlers/automation_gateway_preflight.rs:180-220` 逐角色判定（plan_author/coder ← author_provider；plan_reviewer/code_reviewer/internal_reviewer ← reviewer_provider）：

- `plan_author`（planning_read_only）+ `coder`（coding_target_write）→ provider = **codex** → codex 在该 LC 下没核验过 → `provider_capability_launch_not_confirmed` → 两条违规；
- 3 个 reviewer（review_read_only）→ provider = **claude_code** → 已核验 → **通过**（故 violations 里没有 reviewer）。

→ 任一角色违规即 422 + 那句泛文案（`:219`）。

## 契约违背

设计稿要求「GET target 和 PUT Enable 共享判定」（`cadence/designs/2026-09-28_方案设计_真实链缺口修复总方案_v1.2.md:266`，A2 role-chain 准入）。实际：

| 调用点 | 判定用的 provider |
|---|---|
| GET 目标投影 | 服务端**默认**（codex）—— `src/web/handlers/automation_target.rs:115` |
| PUT Enable | 提交体里的 owner 所选 —— `src/web/handlers/automation_enrollment.rs:415-420` |

⇒ 两者判定对象不同：**GET 通过 ≠ PUT 通过**；且 GET 会拿 owner 没选的 provider 判 owner 的操作。

## 可诊断性缺陷（同一现场的次生问题）

1. **页面丢掉了具体原因**：目标加载失败路径只取 `reason.message`（`web/src/components/lifecycle/WorkItemPlanOptionsDialog.tsx:166`、渲染在 `:381`），**没有渲染 `details.violations`**；而提交路径是渲染的（`:225`、`:473-476`）。⇒ owner 只能看到一句英文，定位不到「哪个 provider / 哪个角色 / 哪一格」。
2. **dev 环境查不到服务端日志**：`src/cross_cutting/mod.rs:56-57` 的 `tracing_capture` 是 `#[cfg(test)]`，**生产/dev 路径没有 tracing subscriber** ⇒ `readonly_preflight_gateway` 里的 `tracing::warn!`（`automation_gateway_preflight.rs:230-246`）**不输出任何内容**。仓库的诊断惯例是 `eprintln!` → 直接打到启动服务的终端（无日志文件）。
3. ⇒ 现场唯一可取的事实来源是 **422 响应体的 `details.violations`**（本次即靠它才定位）。

## 当前处置（owner 裁定：先记录，不解决）

可用绕过（均不改代码）：

1. 面板「逻辑代码库管理面板 → Provider 能力核验」对 **codex** 点「核验」→ 默认 author=codex 通过；
2. 或让 codex 不被判可用（移出 PATH / 修健康快照）→ 默认回退 claude_code，再对 claude_code 点「核验」（会只补 planning/coding 两格 —— reviewer 格已通不代表另两格通）；
3. 直接请求带参数的 URL（`?author_provider=claude_code&reviewer_provider=claude_code`）可验证「GET 不看选择」这一结论。

## 若将来立项，候选修法

| # | 方向 | 代价 | 说明 |
|---|---|---|---|
1 | 前端 GET 带上当前选择的 provider，并在 provider 变更时重取投影 | 低 | 治本：判「owner 选的那个」，且 GET/PUT 判定同源 |
2 | GET 目标投影退化为纯身份投影，role-chain 预检只留 PUT Enable | 低 | 需重新确认「GET 也要预检」这条契约是否必须 |
3 | 目标加载失败路径渲染 `details.violations` + 中文可行动文案 | 中 | 同族票「失败面可行动化」；owner 可见面变更 → 走 OpenSpec |
4 | dev 环境给预检失败加 `eprintln!`（与 `[aria-startup]` 同风格） | 低 | 让失败面在终端可见；纯诊断补齐 |

> 1 与 3 属 owner 可见行为变更 → 走 OpenSpec change；4 是诊断补齐，可单独小改。

## 影响面

- 命中条件：**多仓（LC）载体** + 该 LC 下**服务端默认 author provider（codex）被判可用但未核验** → 「启用自动化」全程不可用。
- 单仓载体不命中（`validate_role_chain` 对单仓直接放行，`automation_gateway_preflight.rs:180-190`）。
- 与「只装 claude code」的机器相比：**装了 codex 的机器更易命中**（owner 现场即此形态）。

## ③ 间歇条件的实证（机制链，逐环验证过）

**共享资源不是临时目录/端口/全局注册表，而是：同一 fixture 仓内的 git worktree 注册状态（`.git/worktrees/<name>/locked`），被「后台自动推进的 worktree 物化」与「删除 teardown 的 worktree 拆除」并发触碰。**

机制链（每环都有代码行号或实验输出背书）：

1. **后台物化**：`post_start` 一键首启返回 Started 回执后，**detached runner 仍在后台推进**——首个 unit（fake provider 秒完成）走完成链，`src/web/coding_ws_handler/runner.rs:1063-1082` 完成挂点调 `drive_ready_units_for_plan`，自动启动后续就绪 unit，spawn 的 runner 在 `prepare_worktree`（`src/product/coding_workspace_engine/lifecycle.rs:440-476`）里跑 `git worktree add <repo>/.worktrees/aria-issues/<issue>/<uuid>`。
2. **测试侧立刻删除**：测试在毫秒级后续步（get_progress → 未确认 409 → 确认删除）进入 `delete_plan_coding_workspaces`（`plan_start.rs:246`），逐成员 `teardown_plan_coding_member`（`plan_start.rs:468`）：先 `abort_attempt`（取消 runner token 并**等 runner 完全退出**，`state/coding_run_registry.rs:313-373`）。
3. **取消杀死在途 add**：`GitWorkspaceService::run_git` 的 `select!` 命中 `Cancelled` 分支执行 `child.terminate()`（`git_workspace_service.rs:706-716`）——**正在执行的 `git worktree add` 被 SIGKILL 于半途**。
4. **git 实证（本机 git 2.56.0，隔离探针复现）**：`git worktree add` 开局写 `.git/worktrees/<name>/locked`（内容 `initializing`），成功才删；**中途被 SIGKILL 则锁残留**，且随后 `git worktree remove --force`（单 `-f`）必败：`fatal: cannot remove a locked working tree, lock reason: initializing` —— 与失败现场**逐字相同**。
5. **补偿拆除撞锁**：`reconcile_coding_git_operation_for_termination`（`coding_workspace_engine/git_operation.rs:26`）看到该成员 WorktreePrepare journal 非终态 → `compensate_cancelled_worktree_prepare`（`lifecycle.rs:596-641`）→ `git_worktree_branch` 匹配 → `remove_worktree` → 撞第 4 步的锁 → `CommandFailed`。
6. **误标上抛**：`coding_termination_reconcile_api_error`（`web/handlers/support.rs:537-551`）把任何 `CommandFailed|PushIndeterminate` 一律映射为 409 `review_push_indeterminate`（文案指向远端 push，与真相无关）→ 测试 `.expect("confirmed group delete")` 于 1944 行 panic。

**为什么有时红**：只有当取消/teardown 恰好落在某个后台 `git worktree add` 的执行窗口（每成员约十几~几十 ms，共 3 个成员可撞）才致命。无饥饿时后台链要么尚未推进到 add、要么早已完成（worktree 解锁，remove 正常）⇒ 稳定绿；全量套件的并行调度饥饿把窗口拉宽到与删除时序重叠 ⇒ ~20-30% 命中。超订阅实验直接证实了这一条件依赖（见 ② 表：饥饿前 0/126 红，饥饿后 24/80 红）。

**排除项**（都查过、均有负证据）：非 `advance.rs:50` 崩溃注入（结果行 ok）；非 10-31 笔记的 `logical_codebase::policy` durable-write 家族（该机制已在 11-01 按多 root 分槽修复，`policy_test_faults.inc.rs:19-33` 有修复注释）；非 codex `launch_ownership`（另案，笔记载单跑 1/3 红，与本签名无关）；非 test_pause 机制（本测试未注册 pause）；非跨测试共享目录（fixture 临时目录每次唯一）；非 fmt/重编译（run 1 于干净树上首跑即红）。

## ④ 处置：需 Main 授权的产品缺陷（本 agent 未改任何产品实现）

**判定依据**：竞态双方都是**产品组件**——「自动推进物化」（runner 完成挂点→drive）与「组删 teardown」；测试时序（启动后立即删除）是端点声明支持的场景（端点注释与 409 文案即「终止并删除」）。生产用户在自动推进物化途中点删除会命中同一 409，且**被杀 add 残留的 `initializing` 锁永不自愈，重试删除仍撞同一锁 ⇒ 该 plan 的组删被永久卡死**（`sweep_issue_worktree_residue` 只在成功路径末尾执行，失败时跳过）。测试侧无合法夹具修复：等待后台静默再删 = 掩盖产品缺陷 + 削弱「删除可终止执行中工作区」的覆盖。故按任务规程停下上报，**不改产品实现、不改断言、不删测试**。

需 Main 授权的修复面（供决策，均未实施）：
1. `compensate_cancelled_worktree_prepare` / `remove_worktree` 容忍锁定 worktree：先 `git worktree unlock <path>` 再 `remove --force`，或 `remove -f -f`（两条路线都已在探针仓实证可行）；或在 Cancelled-kill 后清理 `.git/worktrees/<name>/locked`/`index.lock` 残留。
2. 错误映射误标：worktree 拆除失败被标成 `review_push_indeterminate`（远端 push 语义），误导排障。

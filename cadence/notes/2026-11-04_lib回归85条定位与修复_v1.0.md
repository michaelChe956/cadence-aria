## ① 真正的根因

### 改动本体（seed.rs，02:38）

基座夹具建组从无快照改为带冻结快照（并补 LC 权威、issue 归属回填、聚合索引）：

```rust
// 改动前（22:55 基线，cab2cbd 侧）：
            target_snapshot: None,
// 改动后（ee41dac 侧，02:38）：
            target_snapshot: Some(target_snapshot),   // 经 build_attempt_target_snapshot 冻结
```

伴随同一改动集：

```rust
// issue 记录归属回填（改动前 None）：
            logical_codebase_id:
                crate::product::logical_codebase::store::legacy_logical_codebase_id(PROJECT_ID),
// + manifest/member/checkout/selection/policy 产物 + repos.json 逻辑归属回填 + 聚合索引
```

该改动方向本身是本会话「去单仓入口两态化」协同改造的收尾（23:15–23:18 已有成批夹具按
「LC 权威 + 冻结快照」改造并通过，如 group_amendment_chain / p2_campaign /
campaign_stage3 等），**不可回退**——当前 5879 条通过用例中已有大量用例依赖新世界形态。

### 模式 A（84 条）：播种 attempt 换桶 ⇒ None 桶检索落空

生产侧桶键语义（`coding_attempt_store/group.rs`，20:37 基线前已存在、22:55 时全绿）：

```rust
pub(crate) fn attempt_target_bucket(attempt: &CodingExecutionAttempt)
    -> Option<LogicalRepositoryId> {
    attempt.target_snapshot.as_ref().map(|s| s.logical_repository_id)  // 有快照 ⇒ Some(id)，无 ⇒ None
}
```

`get_attempt_for_work_item_group(..., target)` 按 `attempt_target_bucket(attempt) == target`
过滤。播种 attempt 补上 `target_snapshot: Some(...)` 后桶从 `None` 变
`Some(logical_repository_id)`，所有仍写死 `None` 桶的下游夹具取数 `Ok(None)` ⇒
`.expect("seeded group attempt")` panic。改动前后的夹具取数对照：

```rust
// 改动前（22:55 可绿）：
    let seeded_attempt = coding_store
        .get_attempt_for_work_item_group("project_0001", "issue_plan_0001", "work_item_plan_0001", None)
        .unwrap()
        .expect("seeded group attempt");
// 修复后（桶无关取「按 plan 取最早」，与 group.rs doc 建议口径一致）：
    let seeded_attempt = coding_store
        .list_attempts_for_work_item_group("project_0001", "issue_plan_0001", "work_item_plan_0001")
        .unwrap()
        .into_iter()
        .next()
        .expect("seeded group attempt");
```

### 模式 B（1 条）：登记投影未随聚合根上提 ⇒ gateway 组装 fail-closed

实测错误（临时探针取得，已还原）：

```
[PROBE_DBG] coding runner failed pre-provider:
coding_provider_stream_failed: logical gateway factory build failed:
provider_gateway_target_mismatch: registration_root
```

因果链（快照实测取证）：

1. 基座播种（02:38）以单仓 worktree 为聚合根建 LC 世界；`ProjectStore::get` 幂等
   `migrate_legacy` 冻结 legacy 别名 LC `record.aggregate_root = <tmp>/worktree`
   （`logical-codebases/<legacy>/record.json`，实测值确认）。
2. `n3_fixture`（21:03，基线前即存在）把 4 个 n3 仓挂进同一 manifest 后，将
   `manifest.provider_context_root` 上提到夹具根 `<tmp>`（多仓成员必须是聚合根直接子
   目录），但 record 的登记投影没跟着动。
3. 基座回填 issue 归属 + 别名 record 在场 ⇒ runner（`coding_ws_handler/runner/task.rs`
   :124-164）对带快照 attempt 走 **LC 作用域** gateway 构建
   `factory.build_readonly_for_lc(project, Some(legacy_id))`（22:55 前该 issue 无归属、无
   别名 record ⇒ `Ok(None)` ⇒ 项目作用域构建，根断言因两投影均 None 被跳过 ⇒ 通过）。
4. `build_scoped`（`web/gateway_factory.rs:119-173`）读 legacy 别名作用域（`for_lc(legacy)`
   按字节等价映射回项目级根）的 manifest（已上提到 `<tmp>`）与 record（仍 `<tmp>/worktree`）
   ⇒ REQ-ENV-10 四路根投影断言 `registration_root ≠ authority_root` ⇒
   `provider_gateway_target_mismatch: registration_root` fail-closed（zero spawn）。
5. runner pre-provider 失败时 attempt 仍 `created/prepare_context`（非 Running），F-14
   manual-recovery 兜底不覆盖该相位 ⇒ 零 durable 痕迹的**静默**止步 ⇒ 测试 10s 轮询超时。

实测冻结现场（运行中快照 tempdir）：busi attempt `status=created, stage=prepare_context,
claim=True, snap=True`，无任何 coder role run。

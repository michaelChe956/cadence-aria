# 分析报告: 「provider 宿主直跑不沙箱」路线的安全护栏论证

- 出具: anthropic-task (NoSandboxGuardrails), 2026-10-16, 受测试会话委托; 行号已物理复核(HEAD 2a274bbf, codegraph 仅定位)
- 交付对象: owner 沙箱路线决策

## 结论

**条件可行, 但仅限 reviewer, 不能作为统一路线。**

1. 完全不沙箱不能推广到 coder, pi 现状也不该原样保留
2. reviewer 想保留 podman 验证又想遮蔽凭据, 两者只能在「进程外 podman + API 过滤」(F)里同时成立
3. **缺鉴权的本机控制面是比凭据泄露更大的问题**(新发现, 见结构性事实 1)

## 1. 威胁模型

### 1.1 资产与 blast radius(= 运行用户权限面, 宿主实测存在)

| 资产 | 位置 | 后果 |
|---|---|---|
| LLM 凭据 | ~/.pi/agent/auth.json、~/.codex/auth.json、~/.kimi-code、~/.cc-switch | 盗刷/冒充 |
| Git 凭据 | ~/.config/gh/hosts.yml; ~/.gitconfig 配了 gh auth git-credential | 免密 push/改远端 |
| SSH 私钥 | ~/.ssh/github | 横向移动 |
| Aria 数据 | workspace .aria/ | 污染证据链 |
| 本机控制面 | Aria web 回环监听(web/app.rs:734) | 自批 gate/确认计划 |
| 容器栈 | rootless podman | -v $HOME:/x 等同全量读写 |

### 1.2 不可信输入面
被 review 的 diff/README/依赖描述/搜索网页; 注入可逐级传递(恶意依赖 README→coder 上下文→diff 注释→reviewer), reviewer 并不比 coder 安全; coder 还执行不可信构建代码(mvn 插件/npm postinstall)。

### 1.3 攻击链(pi 现状全部可达, 结构推断未实测)

- C1 凭据外传: bash cat 凭据 → curl 外发(继承环境+网络)
- C2 控制面自批: 读 .aria/web-endpoint → curl 回环 gate 接口(**该 API 无调用方鉴权**, handlers/coding.rs:700-704 只收 State/Path/Json, src/web 无任何鉴权中间件)
- C3 git 越权 push(hooks); C4 写 .aria 投毒证据; C5 podman -v 挂宿主全量读写; C6 资源残留(已发生)
- 现场佐证: pi 一次 run 46 次 bash; 快照事件里有 cwd 外遍历 .aria、cat evidence-token 的"好奇式"读取

## 2. 护栏逐项评估(要点)

| 护栏 | 结论 |
|---|---|
| A env 清洗(spawn_isolated, 已有 API) | 便宜但单独无效(cat 文件即绕) |
| B landlock/bwrap 遮蔽凭据目录 | 效果最强, 但 no-new-privs 杀死 podman(与验证能力互斥) |
| C 网络白名单(netns+pasta+nft) | 与 B 叠加才有意义; landlock 不能按域名 |
| D 命令黑白名单 | **有效性接近零, 不建议投入** |
| E 内建 bash 换自有扩展工具 | 机制非防御, 前提未验证(pi 是否支持 --exclude-tools bash) |
| **F 进程外 podman + API 过滤** | 唯一同时保留验证与强隔离的路径, 需自建过滤器 |
| G 高危审批门 | 审批疲劳(46次/run), 需 E/F 之后才有挂点 |
| H 审计 | 需外移到 agent 写域外(append-only/hash 链) |
| I canary | 低成本检测补充 |
| K 现有 ProviderBoundaryLauncher 投产 | **只防写不防读不防外传**(保留网络+ro-bind 全盘可读), 不是 C1/C2 的答案 |

## 3. 三条结构性事实

1. **Aria 本机 API 无鉴权是前提缺陷**: 宿主直跑的 provider 能直接 curl 回环自批 gate, 绕过所有人工门; 修法小(状态变更路由加令牌或 unix socket peer 校验), 无条件先做
2. **podman 与强 OS 沙箱互斥**(no-new-privs vs newuidmap): 「reviewer 直接 podman 验证」与「沙箱遮蔽凭据」二选一, 除非走 F
3. write_boundary 恒 Unknown + 旧 allow 放行(provider_boundary.rs:253-255; production_policy_resolvers.rs:354-358): 路线选定后须把 pi 移出过渡桥

## 4. 四档方案权衡

| 方案 | 残余风险 | 验证能力 | 人工介入 | 与 owner 倾向 |
|---|---|---|---|---|
| P0 现状(pi 不沙箱) | 高(C2 控制面自批) | reviewer 强/coder 无 | 每 WI 回贴 | 一致但 C2 不可接受 |
| **P1 受控直跑(仅 reviewer)**: 控制面鉴权+env 清洗+凭据遮蔽+网络白名单+审计外移+canary | 中低 | reviewer 保留 | 同 P0 | **推荐平衡点** |
| P2 统一强沙箱 | 低 | 双侧无 | 全人工补验 | 与倾向相反 |
| P3 进程外 podman+过滤(F)+全员沙箱 | 低 | 双侧可 | ~0 | 精神接近已否决 B, 需 owner 裁决 |

**P1 是 owner 倾向与安全底线的平衡点, 但只对 reviewer 成立; coder 保持 kimi bwrap。**

## 5. MVP(前三项缺一不可, 独立于路线可先做)

1. Aria 状态变更 API 加调用方校验(无条件)
2. pi 改 spawn_isolated 重配环境(先确认 pi 不依赖 env key)
3. 盘上凭据挡出 pi 可读域(~/.pi/agent/auth.json 保留; .aria 对 pi 只读)
   — 若用 landlock/bwrap 实现, reviewer podman 失效 → 在 F 与 A'(人工回贴)之间二选一
4. 网络出口白名单 → 5. 审计外移 → 6. canary/限速

## 6. 与已否决方案的区别(F vs B/C)

F: 命令 agent 自写、约束在容器参数、信任模型=命令不可信; B: 命令 plan 预声明、宿主执行; C: 沙箱内提权。F 与 B 在「宿主侧受控出口」相近, **需 owner 明确裁决, 不建议悄悄推进**。

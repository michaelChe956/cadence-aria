# 项一：契约 capability 的标识符与描述分离

## 问题

`input_contracts.required_capabilities` 与 `output_contracts.capabilities` 都是 `Vec<String>`，
被当作**标识符**消费，却被鼓励写成**自然语言描述**。

匹配逻辑在 `src/product/work_item_contract/dependency.rs:206-220`：`BTreeSet` 集合差，
纯字符串相等比较。全仓没有任何位置解析 capability 的内容，只有相等/不相等一种用法。

实测失配样本（`draft_010` → `wi_library_core`）：

```
provider wi_library_core contract oc_library_core_duration_module lacks capability
src/format-duration.js 存在，并以 ES module 具名导出 formatCompactDuration，
是消费方以相对路径直接导入的目标文件本身
```

下游把 capability 写成了自己的描述，与上游措辞不同，于是失配。

## 自然语言做标识符的三个必然失败模式

1. **改写即失配** —— 下游意译一遍就对不上
2. **长句无法可靠对齐** —— 要求 provider 逐字复制 40+ 个汉字，标点、全角半角、空格任一
   差异都失配
3. **语义与匹配职责绑死** —— 描述本该是可读文档，现在承担匹配职责，想改措辞就会破坏匹配

## 建议方案

capability 从 `String` 提升为结构：

```rust
pub struct ContractCapability {
    pub capability_id: String,   // 标识符，如 named_export_format_compact_duration
    pub description: String,     // 人读说明，可自由改写
}
```

- 匹配**只用** `capability_id`
- `description` 纯给人与 reviewer 看，不参与任何比较
- prompt 约束变为可检查的：`capability_id` 用 snake_case、仅含 `[a-z0-9_]`、下游逐字引用上游 id

**关键论据**：契约 ID（`oc_library_core_duration_module`）加上逐字引用约束后 provider
一次就对了，证明**短标识符的逐字引用是 provider 能可靠做到的**；40 个汉字的长句不是。
失配时的错误信息也会可读。

## 影响面（破坏性变更）

`CanonicalWorkItemContract` 的 `input_contracts` / `output_contracts` 结构变化，牵动：

- `work_item_split_engine` 的 schema、prompt、parse
- `work_item_contract` 的 validation、dependency
- `HandoffRevision.provided_capabilities`（当前是 `BTreeMap<String, Vec<String>>`）
- `plan_repair` 的 `subgraph.rs`、`package_fingerprint.rs`
- `work_item_projection` 的 reviewer projection 与 render
- 前端 capability 展示
- 已落盘的 draft 与 contract 全部不可读（按"全新系统"处置原则可接受）

## 为何暂不做

当前目标是**跑通一遍完整 coding 流程**。在验证途中引入 200 文件级别的结构变更，
会要求重新拆分、重新生成全部 draft，且大概率撞上新的一层问题。

临时缓解已落地：prompt 中约束 `required_capabilities` 每个元素必须逐字取自上游
`output_contracts`，按字符串精确匹配，改写或意译即失配
（`work_item_split_engine/prompts.rs` 的 `[projection]` 与 `[self_check]`）。

# 项二：verification check 的执行者显式化

## 问题

`VerificationCheck`（`src/product/work_item_contract/model.rs:63-69`）只有 `required: bool`，
该字段同时承担了两个不同含义：

- **这项验证是否必需**（验收闭环要不要它）
- **Coder 是否必须自己完成它**（交付前提）

人工核对（`command == null` 且 `manual_instruction` 非空）天然不是 Coder 能执行的，
但一旦 `required: true`，Coder 读到的语义就是"必须完成才算交付"。

## 实测死机

用户目标是"所有需要人工核对、处理、测试的事项都不应阻碍 Aria 走完全流程，而应在每步
提醒人工处理"。当前结构表达不了这个语义，实际发生的是：

1. 为解开 author↔reviewer 死循环，将人工核对设为 `required: true`
2. Coder 发现执行环境无浏览器（chrome/chromium/firefox 均无），三项浏览器核对无法执行
3. Coder 输出 `operational_gate` blocker（`reason_code:
   browser_supporting_native_es_modules_unavailable_for_manual_check`）
4. `runner.rs:182-200` 的 `start_plan_repair_for_execution_outcome_if_needed` 只处理
   `StartPlanRepair`，`OpenOperationalGate` 直接 `return Ok(None)`
5. attempt 停在 `stage=coding` / `status=running`，unit 为 `running`，role run 为
   `completed`，**无任何 open gate** —— 用户无按钮可点

Coder 的行为是正确的：它写完了三个文件、完成四项只读复核、还用 Node DOM 桩驱动真实
`main.js` 做了旁证。错在契约把 Coder 做不到的事写成了它的交付前提。

## 建议方案

```rust
pub enum VerificationExecutor { Coder, Human }

pub struct VerificationCheck {
    pub check_id: String,
    pub command: Option<String>,
    pub manual_instruction: Option<String>,
    pub required: bool,              // 验收是否必需
    pub executor: VerificationExecutor,  // 谁执行
    pub non_zero_test_execution_required: bool,
}
```

- `required` 只表达"验收闭环要不要它"
- `executor` 表达"谁执行"，Coder 只对 `executor == Coder` 的项负责
- `executor == Human` 且未完成是**合法交付状态**，不构成任何自动阶段的阻塞

同时需要一个结构化的待人工事项清单（供 UI 渲染"本次有 N 项待人工核对"），而不是
只靠完成报告的自然语言。

## 临时缓解（已落地）

四处 prompt 统一口径，用现有结构表达：

| 位置 | 约束 |
|---|---|
| `work_item_split_engine/prompts.rs` | 需人工操作/目视确认的 verification_intent 必须表达为 `acceptance_criteria` 的 `required_evidence=[manual_check]`；`verification_checks` 的 `required=true` 仅限 Coder 可自行执行的命令或只读检查 |
| `coding_workspace_engine/prompts.rs` Coder 执行协议 | 人工事项不属于 Coder 执行范围；不得因无法执行而报阻塞、拒绝完成或降低完成度；缺浏览器/设备/外部账号不是运维阻塞 |
| 同上 完成报告契约 | 必须单列"待人工处理"小节，并声明该清单是交接内容、不是未完成项 |
| 同上 两个 reviewer 协议 | "待人工处理事项不是缺陷"，不得据此 finding / request_changes / blocked；GroupFinalReview 需在 summary 汇总整组待人工清单 |

**缓解的局限**：待人工事项只能以自然语言出现在完成报告与 handoff 中，没有结构化清单
给 UI 渲染；用户需从报告文字里读。这正是项二要解决的。

## 未修复的相关缺陷（不在本文档范围）

`OpenOperationalGate` 在 coding 阶段无门禁落地（上述第 4 步）。这与 change
`open-group-final-review-change-gate` 的缺陷同构——「决策已产生但无落地」，只是发生
阶段不同（coding vs internal_pr_review）。C 的范围未覆盖 coding 阶段，需扩范围或另立项。
一并注意：`manual_continue` 不在 `runner.rs:162-180` 的恢复白名单内，点击后 attempt 变
`Running` 但无 runner 推进（C 的已知缺口第 1 条）。

# 同一模式的相关缺陷

本轮验证连续暴露的缺陷可归为两个模式。

## 模式一：prompt 定义了字段却未声明它是引用关系

provider 因此在"命名"而不是"引用"：

| # | 字段 | 症状 | 处置 |
|---|---|---|---|
| 1 | `input_contracts.contract_id` | 自行命名 `ic_` 前缀 | 已修（prompt 约束） |
| 2 | `required_capabilities` | 自行撰写描述文本 | 临时缓解，项一立项 |

## 模式二：同一语义约束散落在 prompt 与 Rust 校验两处

改一处另一处就打架：

| # | 约束 | 症状 | 处置 |
|---|---|---|---|
| 1 | 「required 必须有 command」 | prompt 与 `work_item_contract/validation.rs` 各有一处混淆，人工核对无法必需；只改 prompt 后闸门挪到 Rust 校验 | 已修（两处同改） |
| 2 | 「人工事项是否阻塞」 | 散落在 draft / Coder / Code Review / GroupFinalReview 四处，改一处闸门就往后挪一格 | 已修（四处同改），项二做结构化 |

**教训**：这类语义约束必须一次性把所有承载点找齐再改，否则症状只会转移。判断方法是
问「这个约束在哪些地方被独立地重新判断了一次」。

### 3.2 现有摘要口径使「版本号变化后重放」不可行 —— 有问题（任务口径需改）

`cas_internals.inc.rs:553-560`：

```
553:    let payload = serde_json::json!({
554:        "command_id": command_id,
...
559:        "expected_revision": expected_revision,
560:    });
```

而账本命中臂在 revision CAS 之前（`issue_automation_store.rs:199-232` 早于 `:269`）⇒ **同 command_id + 不同 expected_revision ⇒ digest 不同 ⇒ 直接 Conflict（永久）**。

因此 tasks §3.2「同一条命令在版本号变化后重放不被当成新命令（不撞幂等账本）」**按字面不可实现**。可实现的两条口径（需在 change 里选一条写死）：

- **口径 A（推荐，后端不动）**：前端把 `(command_id, expected_revision)` 成对缓存并**原样重放**（revision 用提交当时那个值）。命中账本 ⇒ `Unchanged` 幂等成功，与当前 revision 无关。代价：若首次根本未落盘，重放会撞 revision CAS ⇒ 得到 stale 码 ⇒ 此时前端**必须换新 command_id** 再试。tasks 需补这一条「stale 后换新 id」，否则用户点第二次会永久 409。
- **口径 B（后端照终止账本先例改摘要）**：`src/product/termination_command_ledger.rs:37-50` 已经做过同一件事并写明理由：

```
37: /// 终止命令的 intent 摘要：`command_id` ＋ `expected_enrollment_id` ＋ `reason`。
39: /// **不含** `expected_policy_revision`（乐观前置条件）——它就是本 endpoint
40: /// 冲突投影里交给客户端刷新的那个值，同一命令的重试必然携带新值。
```

  即「乐观前置条件不进摘要」是本仓已确立的口径。Enable 摘要与之相反。走 B 需新增 digest 版本/兼容分支（终止侧用 `intent-sha256:` 前缀区分新旧口径，Enable 侧需同样处理旧账本条目）。

**判定：可行但任务口径有误**；建议按口径 A 写 tasks（改动最小、无兼容面），并在 spec 的文字上把「命令身份与预期版本一并携带」改成「命令身份与提交时的预期版本一并携带；预期版本已过期时换新命令身份」。

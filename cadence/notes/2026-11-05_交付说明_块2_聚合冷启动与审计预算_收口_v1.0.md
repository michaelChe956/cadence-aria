- 门 L2 联动：全局记录已 Confirmed 时冷启动 advance 自动推进（不再
  `needs_verification`）；未核验仍 fail-closed 且**不自动发起**核验；聚合根两个
  判定文件都在时仍走零 provider turn 路径（该路径未被取消或改写）。
  新增 `l2_global_capability.inc.rs` 三条用例。
- 界面文案改全局口径：「逐 LC 核验」→「全局核验 / 一次核验全项目可用 /

### 3.1 恢复过程中撞到的第二个问题：成员初始化在 mcp_configuration 步挂死

```
现象：三个成员仓初始化（6 步：cadence_skills / pre_check / rule_config /
      mcp_configuration / project_rules_examples / git_finalize）中，
      memberA 顺利走完（22 分钟）；memberB / memberC 停在
      `mcp_configuration` 超过 30 分钟且 `updated_at` 不再变化。

根因：该步骤派生的 `claude -p --verbose --output-format=stream-json
      --input-format=stream-json` 子进程进入 `do_epoll_wait`，其 socket
      最后活动在 01:23 / 01:26 ⇒ **22~25 分钟无网络活动**，且无超时兜底。
      同时段单独跑 `claude -p "回复 OK"` 19.7 秒正常返回 ⇒ 不是 Claude 侧
      不可用，是这两个子进程自身挂住（与并发 3 条初始化争 npm 缓存/子进程资源
      有关，未定位到更细的触发条件）。

处置：kill -9 两个子进程 ⇒ 两条 op 转 `failed`（failed_step =
      mcp_configuration，code = repository_init_command_failed）⇒ 手工把
      memberB/C 的工作区产物提交（提交信息对齐 memberA 的「初始化cadence-aria
      代码库」）⇒ 重新 preflight（三者均 eligible）⇒ 提交 registration batch
      ⇒ completed。
观察：**`mcp_configuration` 步骤对派生子进程没有超时兜底** —— 这是产品侧的
      真实缺口，本轮未改产品代码（不在块2 范围内），按缺口记录。
```

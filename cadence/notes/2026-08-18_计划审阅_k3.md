# 审阅报告：多仓库生产入口补齐实施计划 v1.0

**审阅方式**：只读静态审阅。已通读计划全 870 行、OpenSpec change 全部契约（proposal/design/tasks/5 个 delta specs）、设计 v1.2、两轮前置审核（terra 7B/14M/5m、deepseek 2B/6M/9m）、build-test-commands 规范，并对 **15 个 Task**（1.1/1.2/1.3/2.1/2.2/2.3/3.1/3.2/3.3/4.1/4.2/4.3/5.1/5.2/6.1，超出要求的 8 个）做了代码现状抽查，全部关键行号用 grep/sed 实测核对。

## Issues

### BLOCKER（必须改才能开工）

**B-1：`--test web_logical_codebase_entrypoints` 测试 target 不存在，15 处红/绿命令必然失败。**
- 计划位置：Task 1.4 Step 2/4、2.2 Step 2/4、2.3 Step 2/4、2.4 Step 2/4、3.3 Step 2/4、4.3 Step 4、4.4 Step 2/4、5.1 Step 2/4、5.3 Step 2/4（共 15 处 `cargo test --locked --test web_logical_codebase_entrypoints ...`）。
- 代码证据：`Cargo.toml` 无 `[[test]]` 段，target 全部自动发现（`tests/it_web.rs`→`it_web`）；`tests/it_web/` 是 `it_web` 二进制的模块目录，其下新建 `web_logical_codebase_entrypoints.rs` **不会**生成新 target。且计划 1.4/5.3 的 Files 均未列出对 `tests/it_web.rs` 的修改（现有模块经 `#[path = "it_web/xxx.rs"] mod xxx;` 注册，见 `tests/it_web.rs:109-168`），新模块连编译都进不去。
- 修法二选一，计划必须写明：(a) 把根文件放到 `tests/web_logical_codebase_entrypoints.rs`（自动发现为新二进制，命令保持）；(b) 在 `tests/it_web.rs` 注册 mod 并把 15 处命令改为 `--test it_web <过滤名>`。注意 (b) 会与其他 it_web 模块共享编译，(a) 更符合计划"独立二进制"的措辞。

### MAJOR（应改）

**M-1：Task 5.2 的"先红"不成立——change_order gate 已完整实现并接线。**
- 计划位置：Task 5.2 Step 1/2（红预期"注释/validation 落点允许流程进入 compile"）。
- 代码证据：`spec.rs:499 validate_confirm_aggregate_spec` 已存在且含 `ChangeOrderRequired`（spec.rs:35,43-44）；HTTP 确认唯一漏斗 `confirm_workspace_entity`（`lifecycle.rs:945-953`）已调用该 gate；`workspace_session.rs:61-64` 注释确认"先 gate 后确认"；store 层已有通过中的测试 `tests.rs:883 validate_confirm_aggregate_spec_rejects_multi_repo_design_without_change_order`；it_web 已有 `part_02.rs:983 confirm_logical_design_without_change_order_is_blocked`（计划 Step 4 把它当"确认绿"命令，恰好自证其早已存在）。Step 1 新写的 lib 测试是 tests.rs:883 的重复，首次运行即绿，红证据伪造。
- 该 Task 真实剩余工作仅为注释修正（`models/lifecycle.rs:135-137` 与 `spec.rs:215-216` 仍写"缺失不强制 blocker"，与代码行为相反——这正是 deepseek MINOR-6 的落点）。建议改写为"验证+注释修正"型 Task（红证据改为：先证明无矛盾注释、复跑既有 gate 测试组），或指出一个真实未接线的 confirm 路径（审阅中未发现）。

**M-2：Task 4.3 的 `socket.rs:80` 接口缺口——resume 路径的 fresh 语义未定义。**
- 计划位置：Task 4.3 Files（`src/web/workspace_ws_handler/socket.rs:80 — 使用 async resolver 入口`）与 Interfaces（仅生产 `build_with_fresh_index`）。
- 代码证据：`socket.rs:80` 调的是 `PlanningContextResolver::resume`（非 build）；`resume`（`planning_context_resolver.rs:283-332`）内部调用旧同步 `build`/`resolve_context`，stale 索引不会触发 sync。计划 Interfaces 未定义 resume 的 async/fresh 变体，但 Files 又要求改 `workspace_ws_handler/tests/planning_resume.rs:65` 与 `tests/it_web/evidence_query/part_04.rs:414` 的 await——暗示 resume 也要改签名，接口未锁定，worker 无法确定是"resume 内部走 fresh"还是"socket 改用 build_with_fresh_index"（后者会改变 StaleContext 判定语义，风险高）。

**M-3：4.4 ↔ 4.5 rebuild 响应 DTO 不一致。**
- 计划位置：4.4 Produces `POST .../rebuild -> 200 AggregateIndexDto`；4.5 Produces `rebuildAggregateIndex(...): Promise<AggregateIndexActiveResponse>`（五态 `{state, revision, indexed_at, warning}`）。
- 设计 §4.3 亦规定 POST 返回 `{record}`。前端"成功后替换状态"若按 `AggregateIndexActiveResponse` 解析 record 形状会失败。需统一：POST 改返回 active 投影，或 4.5 改为 rebuild 后重新 GET active（并在 4.5 Step 1 mock 中体现）。

**M-4：前端并行边界存在共享文件冲突风险。**
- 计划位置：Task 依赖图"可并行组 A/B"。2.5、4.5、6.1 三个 Task 均修改 `web/src/components/lifecycle/IssueLifecycleWorkbench.tsx`（行段重叠：1-110 与 895-913 三者共有）和 `IssueLifecycleWorkbench.test-utils.ts`（801-888 等）。依赖图允许 2.5 与 4.1–4.4 并行、4.5 与 5.1/5.2 并行、6.1 与 5.3 并行——若 2.5 拖期即与 4.5 撞车；计划未声明前端三 Task 互斥或文件级串行。建议在并行边界段显式加注"2.5/4.5/6.1 共享 workbench 文件，三者不得两两并行"。

### MINOR（建议）

1. **Task 3.2 Step 3 数字错误**：称"既有 1600+ 行 file"，实测 `src/web/handlers/aggregate_initialization.rs` 为 626 行（Global Constraints 也写 626，自相矛盾）。
2. **Task 1.3 测试骨架引用不存在的 helper**：`product_app()` 全 tests/ 无定义（`web_product_api.rs:13-22` 是内联 `WebAppState::with_events` + `build_web_router`；`request_json` 为文件内私有 fn :387）。骨架可直接抄现有内联模式。
3. **Task 1.3 Reviewer 核实点计数笔误**：写"Files 中 16 个生产点"，正文与实际均为 18 个。
4. **Task 5.1 Step 5 commit 路径错配**：`git add src/web/handlers/support.rs`，但本 Task Files 改的是 1.4 拆出的 `support_parts/product_store_error.inc.rs`；support.rs 本体本 Task 不再应改。
5. **tasks.md 2.2 的"mod.rs 补导出 RegistrationBatch* 系列"在计划 2.2 Files 中无对应步骤**（虽可经 `pub mod registration` 全路径访问而不阻塞，但与 OpenSpec task 文字不一致，建议补一步或在 ledger 中说明偏离理由）。
6. **契约覆盖小缺口 1**：registration spec「同步提交」Scenario 含"登记期间成员主 checkout 无 git 写副作用"，2.3/5.3 均无对应断言（仓内已有 `tests/aggregate_initialization_zero_git_side_effects.rs` 模式可复用）。
7. **契约覆盖小缺口 2**：multi-repo-project-mode spec 要求 legacy 409"响应体指引使用登记端点"，1.4 Step 3 未要求响应体含指引。
8. **Task 1.4 Files 行段未覆盖 `get_repository_initialization`**：`repository_registration.rs:261-309` 止于 :309，而该 handler 在 :311（tasks.md 1.4 明确要求 legacy 初始化 GET→409，deepseek MINOR-5 吸收点）。

**其余审阅维度结论**：OpenSpec 22 条与 5 个 delta spec 的 Requirement/Scenario 除上述 m-5/m-6/m-7 三处小缺口外均有落位；依赖图正确（2.2→1.4 的 guard、4.4→3.3 的 handlers.inc.rs、5.3 收束均正确表达）；后端并行组（2.x ∥ 3.x、4.5 ∥ 5.1/5.2 后端侧）实测无共享文件；单仓零变化红线在 1.1/1.2/1.3/1.4/2.2/4.4/5.1/5.2/6.1 均有验证步骤；大文件预防（support 拆分、registration 首拆、operation/resolver 测试移出）与现状行数全部吻合。

**修掉 B-1（必修）与 M-1/M-2/M-3/M-4（应修）后，本计划可作为 SDD 执行输入。** 计划整体质量高：行号盘点经独立 grep 复核精确，前两轮审核意见吸收完整，TDD 红证据除 5.2 外均指向真实缺口。

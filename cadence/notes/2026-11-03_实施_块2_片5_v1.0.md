## 5. concerns

- **C1（Plan 内部冲突，已按必需路径实现）**：Plan §6.1 把 `aggregate_initialization_coordinator.rs` 的改动限定为「仅快照结构体这一处」，§6.3 亦写「只许改 `AggregatePreflightSnapshot`」。但 §6.2 的落点纪律要求「探针以 `CodeGraphCli::new(state.command_runner.clone(), "codegraph")` 构造后注入 coordinator」，设计 §3.4.2/3.4.3 明确写 `self.probe.ensure_ready()` /「注入一个 `Arc<dyn AggregateEnvironmentProbe>`」—— coordinator 必须持有一个探针字段，而字段只能在结构体定义处声明。故实际在该文件加了 **2 个私有字段**（`environment_probe` / `skills_home`）与 1 行 `use`，区域与片1 的错误枚举/`error_record()` 完全不重叠（片1 已确认）。
- **C2（`skills_home` 也是新增字段）**：Plan 只给了 `ensure_skills_commands_linked(home: &Path)` 的签名，没说 home 从哪来。coordinator 的 `AggregateSkillsPreparation` 只暴露 `prepare_skills`，拿不到 HOME；生产 HOME 由 `aggregate_skills_home(state)` 决定（fake runtime 时是 workspace_root），不能改成读 `std::env::var("HOME")`。故同样以字段 + builder 注入，生产在 `production()` 里传同一个 `home`。
- **C3（`dependencies.inc.rs` 未改）**：Plan §6.1 要求该文件「测试装配注入 `StubEnvironmentProbe`（默认 `Ok("1.6.0")`）… 结构体不加字段，只加一个 `probe()` 访问器/`with_probe`」。但该结构体持有的是 `Arc<AggregateInitializationCoordinator>`，而探针字段是 coordinator 的私有字段、coordinator 不可 Clone ⇒ 在不加字段、不给 coordinator 加「复制式重建」API 的前提下，`with_probe` 无处落地；且既有测试的 `::new(...)` 因默认 `None` 已零回归。若 controller 要求补，请裁决「给 coordinator 增加 `clone_with_probe()`」或「允许该结构体加字段」。
- **C4（`coordinator_tests.inc.rs` 净 +2 而非 +1）**：`include!` 新测试片段需要 1 行，片4 可用余量从 59 降到 58（文件 1142/1200）。若片4 超线，请按 Plan §3.5 的 `include!` 先例拆新片段。
- **C5（探针是同步阻塞调用）**：`CodeGraphCli::verify_version()` 内部 `std::thread::spawn(...).join()` 起临时 runtime 跑 `codegraph --version`，在 `advance_remaining`（async 上下文）里是**阻塞**的。与既有索引路径（`spawn_blocking`）不同。契约 `fn ensure_codegraph(&self)` 是同步的（Plan §6.2），故按契约实现；若要求不阻塞 runtime，可后续把 trait 改 async 或包 `spawn_blocking`。
- **C6（`cargo fmt` 基线不干净）**：`rustfmt --edition 2024 --config-path ./rustfmt.toml` 对 **HEAD 版本**的 `coordinator_lifecycle.inc.rs` 就报 diff（如 `with_policy_publication` 应合并成单行），说明该文件在本批之前就不是 rustfmt-clean。我只对新文件跑了 `rustfmt`（已 clean），没有对既有文件做全文件格式化（避免动别人的行 / 冲破行数门禁）。
- **C7（`--lib coordinator` 与新增片段的过滤器关系）**：新用例落在 `product::logical_codebase::environment_probe::tests::*`（匹配 `environment_probe`）与 `product::logical_codebase::aggregate_initialization_coordinator::tests::*`（匹配 `coordinator`），两条 Plan 验收过滤器都能真命中（非假绿）。
- **C8（索引构建「未被触发」的取证层级）**：coordinator 层没有索引对象，故 #6 的断言是「`execute` 返回 `Err` + 三个下游调用计数为 0」。而 `handlers.inc.rs:143-161` 实测只在 `match ... { Ok(_) => { ... index.build ... } }` 分支里 spawn ⇒ `Err` 即索引不触发。若要在 handler 层再加一条 spy 断言，需要改 `tests.inc.rs`（不在本片清单内）。

## 9. 一个要记下来的事故模式（controller 2026-11-03 要求）

本轮我先后修了两处**同类**破坏，二者根因完全一样：

| # | 现象 | 真根因 |
|---|---|---|
| 8.1 | `E0433 AggregateRootPreflight` 报「找不到类型」，但类型在 `registration_preflight.inc.rs:5` 明明还在 | `aggregate_initialization_coordinator.rs` 的 import 块里 `use …::registration::AggregateRootPreflight;` **整行被删**（疑似被当作 unused import 清掉） |
| 8.3 | `E0433 GatewayBackedAggregateProviderTurnDriver` 报「找不到类型」，但类型在 `coordinator_provider_turn.inc.rs:27` 明明还在 | `aggregate_initialization_coordinator.rs` 的 include 列表里 **`include!("coordinator_provider_turn.inc.rs");` 整行被删**（插入新片段 `coordinator_frozen_provider.inc.rs` 时把相邻旧行覆盖了）⇒ 整个 57 KB 文件（含 18 个测试）掉出编译单元，一次性带崩 10+ 条「找不到符号」 |

### 模式（写进团队手册）

> **在既有文件里插入新的 `include!` / `use` 行时，必须逐行核对相邻的既有行没有被覆盖。**
> **症状特征**：编译期大量报「找不到符号」，但那些符号在源码里明明还在 —— 此时**先查 `include!` / `use` 列表的完整性**，再怀疑符号是否真的被改名/删除。
> **判别法**：`grep -n 'include!("' <module 根文件>` 与 `grep -n '^use ' <模块根文件>`，逐一对照预期清单。
> **反向禁忌**：看到「找不到符号」就直接改名/重造同名类型 —— 会把测试指到错的东西上（B2S4Finish 差点这么做，已被 controller 拦住）。

同类风险点（本批仍在动的）：`aggregate_initialization_coordinator.rs` 的 import 区与 include 区都是多方共用的「单行插入」热点（片1 加 `use`、片4 加 `include!`、片5 加 snapshot 字段与 `use`）⇒ 每次插入后都应重跑一次 `grep -c 'include!("'` 核对条目数。

# it_web 聚合索引重建超时 · 夹具修复 v1.0

- 日期：2026-11-04
- 范围：`tests/it_web/**`（本波新增的 12 个红用例的**夹具前置**）
- 结论：夹具不再真跑 codegraph 同步；改走**生产聚合索引操作 + 假 CodeGraph CLI**。
  **src/** 零改动（30s 超时值、业务语义、既有 seam 全部未动）。

---

## 1. 根因复核（本机实测）

12 个红的签名完全一致（同一个断言点 `tests/it_web/web_coding_attempt_api/part_05.rs:64`）：

```
left: 422, right: 200
{"code":"aggregate_index_unavailable",
 "details":{"copy":{"machine_line":"codegraph_timeout","triage":"retry_only"},
            "detail":"codegraph sync . timed out after 30s",
            "reason_code":"codegraph_timeout"}}
```

因果链（本波 `fd0b9a8` 引入）：

1. `migrate_rebuild_and_seed_capabilities`（part_05.rs）新增了对**真实端点**的调用
   `POST /api/projects/project_0001/logical-codebases/{lc}/aggregate-indexes/rebuild`；
2. 该端点 → `AggregateIndexOperation::rebuild` → `CodeGraphCli::sync` → **真跑
   `codegraph sync .`**（工作目录 = `manifest.provider_context_root` = 聚合根）；
3. 真跑受 `AggregateIndexBudget::INCREMENTAL.fail_secs = 30` 约束 ⇒ 本机偶发超时
   ⇒ `AggregateIndexError::Failed{code:"codegraph_timeout"}` ⇒ 422 ⇒ 12 个用例
   全挂在这一个夹具前置上（与被测行为无关）。

补充实测（本次修复期间现测）：

- **该失败是负载/时序相关的，不是当前机器状态下的稳定红**：修复前跑完整
  `cargo test --locked --test it_web` ⇒ `595 passed; 0 failed; 17 ignored`
  （耗时 241.87s）。⇒ 12 个红只在「机器有其它 cargo/codegraph 负载」时复现
  （Main 观察到的那轮正是多 worker 并行跑 cargo 的时刻）。这正是「夹具真跑
  codegraph」的本质危害：**把集成测试的确定性绑在本机负载与 CLI 环境上**。
- 本机 codegraph CLI 存在（1.6.2），单跑 `codegraph init .` + `codegraph sync .`
  在小目录里约 1~2s；但夹具的聚合根是**跨并行测试共享**的底座
  `/tmp/aria-it-web-member-repos`（排除清单 `codegraph.json` 与库目录 `.codegraph`
  都在里面被并行用例反复覆写/同步），叠加全局 `/tmp/.codegraph/codegraph.lock`
  与其它真跑 codegraph 的夹具（evidence 链夹具）互踩 ⇒ sync 可能越过 30s 预算。

## 2. 修法：选哪条 + 为什么

### 2.1 注入点勘察（先查再选）

| 候选 | 勘察结果 |
| --- | --- |
| `src/product/logical_codebase/aggregate_index/` 下有无 runner/sync 抽象 | **有**：`CodeGraphCli` 持有 `Arc<dyn BoundedCommandRunner>`（`codegraph_cli.rs:93`），`AggregateIndexOperation::with_snapshot_dependencies(...)` 可整份注入 CLI + 快照采集器 |
| 生产侧有无「可注入 seam」 | **有，且是既有公开 API**：`WebAppState::with_aggregate_index_operation(index)`（`src/web/state.rs:415`，其 doc 明写 “used by integration tests to control the index CLI”），与既有 `tests/it_web/web_lc_operations_api.rs` 的用法同款 |
| 夹具能否就地注入 | **不能**：12 个用例的 `axum::Router` 是在**各测试函数里**构造的（`build_web_router(WebAppState::new(...))`，约 50 处），夹具 helper 只拿到成品 router，改 router 内的 state 不可行；逐个测试点改 app 构造面 = 50+ 处无关改动 |

⇒ 判定：注入点存在，但**只对「自己构造 app 的用例」可用**；被 12 个用例共用的
夹具 helper 拿不到 app state ⇒ 走 **② 号修法**（夹具前置改道 + 另写 fake 用例
覆盖端点），端点覆盖不丢。

### 2.2 选定方案

**夹具（`migrate_rebuild_and_seed_capabilities`）不再调真实 rebuild 端点、不再真跑
codegraph sync**，改为经**生产聚合索引操作 + 假 CodeGraph CLI**发布 active 世代：

```
IdentityMigrationExecutor::ensure_identity_schema(...)        // 不变（LC 权威）
aggregate_index_fixture::seed_active_aggregate_index(...)      // 新：假 CLI 驱动
    └─ AggregateIndexOperation::for_lc(lc).rebuild(project_id) // 生产操作
         ├─ 真实 git 成员快照（AggregateIndexSnapshotCollector）
         ├─ 真实成员覆盖校验（每成员 ≥1 可索引源码文件）
         ├─ 真实排除清单写入（codegraph.json）+ 真实 durable 世代落盘
         └─ CLI 应答层 = 假 CodeGraphCli（--version/init/sync/files/query）
provider_capability_fixture::seed_confirmed_capability(...)   // 不变
```

**假 CLI 的边界（只换「应答」，不换「事实」）**：

- `--version` → 生产兼容区间下界（`CODEGRAPH_MIN_VERSION` ⇒ 1.6.0）；
- `init` → 在聚合根建 `.codegraph` 库目录（真实 init 的行为 ⇒
  `codegraph_library_present` 判据不变形，证据链 fail-closed 语义不变）；
- `sync` → 成功（不真跑）；
- `files --json` → **按 LC 权威推导**（manifest + member + main checkout）逐成员报
  一个可索引源码文件（`<成员根名>/src/main.rs`）⇒ 成员覆盖校验走生产逻辑，
  不是硬编码名单；
- `query --json` → `[]` ⇒ 负向排除语义（被排除符号不得出现在索引里）成立。

⇒ 读侧（`PlanningContextResolver` → freshness）看到的是**真实 git 快照**，判定
`active` ⇒ **不会**触发真实 codegraph 同步；generate 路径与修复前语义一致。

### 2.3 为什么不用「只隔离聚合根」的半步修法

工作区里另有（被停掉的 worker 留下的）改动：把成员仓从 `/tmp/.tmpX` 挪到专属底座
`/tmp/aria-it-web-member-repos`（避免聚合根 = 共享 `/tmp`）。该改动**保留**（它是
必需的：聚合根 = `/tmp` 会让排除清单写到 `/tmp/codegraph.json`、库目录落到
`/tmp/.codegraph`（与 codegraph 全局状态目录同名 ⇒ 互相污染）），但它**不足以**消除
本红：真跑 codegraph 仍吃 30s 预算、仍抢全局锁、仍依赖本机 CLI ⇒ 负载一上来照样
超时。⇒ 假 CLI 是根治，底座隔离是必要配套。

## 3. rebuild 端点本身的行为覆盖：**没丢**

新增 `tests/it_web/web_aggregate_index_api.rs`：

- 用例名：`web_aggregate_index_api::rebuild_endpoint_publishes_active_generation_and_active_projection_reads_it`
- 覆盖内容（真实路由 + 生产 handler + 同一假 CLI）：
  1. `POST /api/projects/{p}/logical-codebases/{lc}/aggregate-indexes/rebuild`
     ⇒ **200** 且 `state == "active"`；
  2. durable 世代可读（`active_required`）⇒ status active，且
     `codegraph_version` 取**假 CLI 的实测应答**（证明走的是注入的 CLI 而非真 CLI）；
  3. `GET …/aggregate-indexes/active` ⇒ **200**、`state == "active"`、
     `revision` 与 durable 世代一致。

⇒ 端点覆盖与「其他 12 个用例的夹具前置」解耦，覆盖不丢、不弱化。

## 6. concerns

1. **其它夹具仍走真实 codegraph**（同类隐患，本轮未动，因不在本波红的范围）：
   - `tests/it_web/web_lifecycle_api/part_02.rs:541`、`part_06.rs:255`
   - `tests/it_web/web_work_item_generation/part_01.rs:418`
   - `tests/it_web/web_workspace_recovery_consistency/part_01.rs:282`
   - `tests/it_core/workspace_ws_integration/part_05.rs:721`
   它们当前是绿的（聚合根是**每测试独立**的临时目录，不是共享底座），但仍吃 30s
   预算、仍抢全局 `/tmp/.codegraph` 锁 ⇒ 负载上来时同样可能 `codegraph_timeout`。
   建议后续统一改走 `aggregate_index_fixture` 的假 CLI。
2. **evidence 链夹具按设计用真 codegraph**（`tests/it_web/evidence_query/*`：它测的
   就是真实索引与检索；缺 CLI 时显式 skip）——这条不能改。
3. **src 未新增任何 seam**：用的是既有公开 API
   `WebAppState::with_aggregate_index_operation`，其语义就是「集成测试控制 index CLI」
   ⇒ **生产行为零影响**（生产 `WebAppState::new` 仍装配真实 CLI）。
4. **lib 侧一条 flake**（与本改动无关，`src/` 未动）：首跑 `--all-targets` 时
   `web::handlers::coding::plan_start_tests::plan_coding_h4_group_delete_end_to_end_then_new_round`
   因 git worktree 竞态失败（`cannot remove a locked working tree, lock reason:
   initializing`）；单跑复跑即绿。
5. **全局阻塞（非本线）**：`ImplementGlobalCapabilityScope` 正在删
   `ProviderCapabilityStore::for_lc`（能力核验全局化），其调用点未改完 ⇒
   `src/` 编译不过（E0599）⇒ 本线的 `--all-targets` / `--lib` / `clippy` 验收项
   需等它改绿后复跑（本线未碰 `src/`）。

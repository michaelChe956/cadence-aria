## 结构性慢点候选

### A. 请求路径上的全局开销（已验证结构性事实）

- `src/web/app.rs:656-663`、`:725-740`：每个 `/api/**` 请求经最外层 `enforce_api_auth` 中间件；但 `src/web/api_auth.rs:247-249`、`:381-383` 只是内存 `Vec::contains`（小 Vec、无 IO）——**中间件本身不是慢点**（排除项）。
- `src/web/state.rs:186-196`：生产路径 `provider_availability` 闭包 = `availability_from_gate(provider_gate)`（非直通）；`ProviderHealthService::with_dependencies(..., Duration::from_secs(5), 4096)`（`src/web/state.rs:165-171`）。探活刷新点：启动时 `src/web/app.rs:863-872` + autopilot 周期任务 `src/web/autopilot_orchestrator.rs:390-395`——**未见每请求同步探针**。gate 每次判定读缓存快照还是触发探针未逐行核实 [INFERENCE：gate 读缓存，不阻塞请求]。
- `src/web/handlers/runtime.rs:8`、`:19`、`:52`、`:109`、`:167`、`:195`、`:229`、`:290`、`:304`、`:320`：tasks/advance/stop/file-content/file-diff 等旧 runtime 端点全部持 `state.runtime`（`StdMutex`）——**同步互斥锁在 async handler 内跨整个 handler 体**，持锁期间做同步文件/JSON 工作 [INFERENCE：runtime.create_task 等内部含同步 IO，会串行化并发点击]。较新的 workspace-session 族 handler 不走这把锁。

### B. 热门端点的已知重活（已验证结构性事实）

1. `src/product/lifecycle_store/workspace.rs:1230-1265`：`find_workspace_session_path` 对 **projects 下每个 project × 每个 issue 目录**逐一探测 `{sid}.json` 存在性；对不存在的候选路径还会 `read_workspace_session_record` 比对 id。**所有** `GET /api/workspace-sessions/{sid}/...` 族端点（confirm、timeline-node-details、artifact-versions、lease-diagnostics 等）都经它。
2. `src/product/lifecycle_store/workspace_timeline_artifacts.inc.rs:64-84` + `src/product/lifecycle_store/workspace.rs:1270-1277`：`load_node_detail`（timeline-node-details 端点 `src/web/handlers/workspace_session.rs:326-335`）每次调用 = 全目录扫描 → 再读一个 JSON；**404 也发生在全扫描完成之后**（扫描成本已付）⇒ 同日 P2 记录的 404 洪水让每个请求都付一次全扫描价。
3. `src/web/handlers/lifecycle.rs:51-310`：issue lifecycle 投影一次组装要读 `list_workspace_session_summaries`/`list_story_specs`/`list_design_specs`/`list_issue_work_item_plans` + 每 plan 的 group projection、lineage、revision、projection bundle、per work-item binding 解析 + `list_attempts_for_work_item_group`/`list_coding_units`——**每个 `get` 都是独立 JSON 全量 parse，无缓存**；N plan × M work item 时请求级成本线性放大。
4. `src/product/lifecycle_store/candidate_attempts.rs:273-301`、`:360-378`：`list_candidate_attempts`/`list_issue_candidate_attempts`/`list_project_candidate_attempt_series` 都是**读时全量逐行解析 JSONL**；项目级 series 还对每个 issue 重复全读（`:360-364` `for issue_id { list_issue_candidate_attempts }`）。metrics 端点 `src/web/handlers/candidate_attempt_metrics.rs:107-109` 直接消费。

### C. 前端放大器（已验证结构性事实）

- `web/src/pages/useCockpitNodeDetailHydration.ts:47-79`：水合 effect 依赖 `[sessionId, activeNodeId, timelineNodes]`——`timelineNodes` 是数组引用，**每次 WS 事件重建引用即重跑**；对每个未水合节点并发 `fetchWorkspaceNodeDetail`；404/detail 空则 `hydratedNodeIdsRef.delete` → 下一轮 timeline 变化**重发**（与同日 P2 记录一致）。
- `web/dev-server-proxy.ts:9-22`：vite dev 代理目标是 `http://`（**HTTP/1.1**，node-http-proxy 无 h2c）——dev 模式浏览器→vite→axum 全走 HTTP/1.1，**同源并发上限 6 条连接**；timeline-node-details 洪水（每节点 1 请求 × 全部终态节点）会占满这 6 条，**后续任何按钮请求排队**——「不管点哪个按钮都慢」的最强前端侧解释。
- 生产模式前端 rust-embed 单源直达 axum，axum 默认 HTTP/1.1，同样受 6 连接限制 [INFERENCE：axum serve 未配 h2c]。
- WS 全量重渲：`web/src/state/workspace-ws-store-helpers.ts:286-290` 等分片 set，未见明显每事件整页 set [INFERENCE：非主要嫌疑，未逐 store 审计]。

# 交付说明 · 阶段 1「爆栈根治 + 产品可用」（2026-11-06）

> **一句话**：owner 真机点 Story「开始生成」会**爆栈打死整个服务进程**（exit 134）。本阶段**已根治并部署**：根因是 provider run 的**栈帧体积**（poll 帧 724,992 B）与 WS inbound 深链（~1.5 MiB）**之和超过 tokio worker 默认 2 MiB 栈**；已用「**各臂装箱**（帧 724,992 → 4,096 B）+ **8 MiB 栈兜底** + **四层门禁**修掉，并把「原来只在 main 上潜伏」的同类缺陷翻案查清。

---

## 1. 根因（gdb 实锤，非推测）

```
tokio worker 栈 = 2 MiB（tokio 默认；Rust std spawned 线程默认同）
同一线程上同时活着：
 ① WS inbound 深链（axum→socket→poll）        ~1.5 MiB   ← 一直都在，与本次改动无关
 ② provider_run_drive_body poll 帧             724,992 B   ← ★病灶
 ③ provider_run_task_body poll 帧              114,688 B
 ④ 评审链再嵌 6+ 层 async poll（read_json ← list_human_dispositions ← build_review_input …）
—————————————————————————————————————————————
①+②+③+④ ≈ 2.3 MiB > 2 MiB ⇒ 写穿栈保护页 ⇒ SIGABRT ⇒ 整个进程死
```

### 1.1 关键机制：async 状态机把子 future **按值内联**

```
main：一个 1360 行 async 块 ⇒ 一个 future ⇒ 帧 = 243,880 B（实测）+ 深链 ≈1.74 MiB < 2 MiB ⇒ 不越界
分支：拆成「入口外壳 + body + drive + 各臂」
      ⇒ 各臂 future 被【按值内联】进 drive_body 的状态机
      ⇒ drive_body 帧 = 243,880 B → 724,992 B（★拆分反而放大了 3 倍）
      ⇒ + 深链 ⇒ 越界
```

### 1.2 ★ 翻案：「main 没问题」是**环境造成的假象**

| 二进制 | 栈 | 实测结果 |
|---|---|---|
**main(827a990)** | **2 MiB（默认直启）** | **abort（+4.2s）** —— 同款签名 ⇒ **main 同样有这缺陷** |
main(827a990) | 32 MiB（`RUST_MIN_STACK`） | 不崩 ⇒ **「main 能跑」= 32 MiB 环境掩盖**（`.cargo/config.toml` force） |
bugfix | 2 MiB | abort 4/4（ReviewOnly poll 链） |
bugfix | 8 MiB | 不崩（全流程含评审轮，ledger=2） |

⇒ ★ **回退到 main 不会解决问题**；★ 这条缺陷在 main 上**一直潜伏**（静态：main 的 ReviewOnly 链 ≈2.29 MB）。
⇒ ★ **分支没有把好流程改坏**：所有 ≥300 KiB 的 engine/WS 大帧在 main 与 bugfix **逐字节同值**（共有存量）；分支还把 main 的 spawn 侧第一步链从 **2.03 MB 降到 1.33 MB**（1,331,360 B 是**分支修后**链和，main 为 2,031,752 B）。

### 1.3 ★ 为什么这一整类缺陷长期没被测试拦住

```
.cargo/config.toml:8-13  RUST_MIN_STACK = { value = "33554432", force = true }
⇒ 仓里【所有测试线程】都拿 32 MiB 栈 ⇒ 栈问题在测试里永远测不出来
⇒ 这就是「漏网之鱼的根源」（owner 已决：保留 force + CI 加一个 2 MiB 栈专项 job）
```

## 10. 设计裁决备忘（★勿再翻案★ —— 下个会话直接引用）

### 10.1 「后端每次开一个新的自动化实施」= **错**；后端**换代**（同 enrollment_id）= **对**

磁盘实证（部署实例 `/tmp/aria-verify`）：
```
磁盘上只有 1 个 automation-enrollment.json（没有第二个）
enrollment_id = 9df5de30-ba17-4254-870a-a77086f11913      ← 全程唯一
binding_history.current  .plan_id    = issue_work_item_plan_auto_8f6819c7…  ← 本轮
binding_history.previous[0].plan_id = issue_work_item_plan_auto_9df5de30…  ← 上一轮
binding_history.previous[0].enrollment_id = 9df5de30…     ← 与 current 相同
command_ledger 含 cmd-fe-terminate-9df5de30…              ← 终止记在同一条上
```
**为什么换代是对的（三条）**：
```
① 层次：enrollment = 长生命周期登记（授权 + provider 配置 + 销账凭证），一个 issue 一份；
   plan/session = 每轮实例身份（每轮本来就换）⇒ 需要「每轮不同」的已经每轮轮换了。
② 幂等/防重复：同一条 + command_ledger ⇒ 重试/崩溃重放打在同一条，不会开出第二个自动化；
   反过来「每次新建」⇒ 每次重试多开一条 ⇒ 重复执行。
③ 销账语义：设计明文「终止后 MUST NOT 删除 enrollment 记录」⇒ 保留带终止标记的登记，
   正是「这单终止过，别再复用」的凭证；每次新建就把凭证冲掉。
```
⇒ **不要**为此改后端。★若将来要「按次计费 / 审计每轮配置」，该加**run 记录**（每轮一行），不是新 enrollment。

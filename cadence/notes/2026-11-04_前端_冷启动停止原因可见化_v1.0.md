## 2. 界面最终呈现的样子

### 2.1 通知卡：**通用渲染自动显示，前端没动**

面板的 notices 走通用渲染（`LogicalCodebaseBootstrapCard.tsx` 的
`projection.notices.map`），后端 advance-stop 通知的 `summary`（服务端渲染好的
成品三段「问题/原因/怎么做」+ 「机器码：…」+ 「诊断：…」）因此**自动可见**；
通知卡已有自己的机器码次要行 `lc-bootstrap-notice-machine-line-<step>` 与
`allowed_actions` 按钮（「准备」）。**前端没有重复渲染这一段中文。**

### 2.2 新增：停止原因次要信息块（步骤列表之后、通知卡之前）

`data-testid="lc-bootstrap-advance-stop"`（`Card.tsx:369-406`），只在
`projection.advance_stop` 存在时渲染（后端在就绪/链启动后清除该字段）：

```
冷启动停在「规则/政策」：等待人工处理  [需先核验 provider]     ← 首行 + 闸门短标签徽章
机器码：aggregate_initialization_provider_needs_verification  ← 次要行（等宽小字）
no provider carries verified capability evidence | details: …  ← 次要行（等宽小字）
```

- **机器码与 detail 都在次要行**（`font-mono text-[11px] text-slate-500`），与面板既有
  「机器码保留但降级到次要行」风格一致（同 `BootstrapFailureLine` 的机器码行、通知卡的机器码行）。
- **detail 始终可见**（不收进折叠区）：它是 provider 选择门那条候选表的唯一入口，
  折叠起来等于不可见；后端已做脱敏 + 截断（4096B / 40 行）。
- 该块**不渲染按钮**：动作按钮仍由通知卡的 `allowed_actions` 承担（不重复入口）。

## 3. 两个 reason_code 在界面上如何区分

新增前端常量 `ADVANCE_STOP_GATE_LABELS`（`Card.tsx:76-79`，沿用面板既有
`RULE_DRIFT_DETAILS`「稳定码 → 中文」风格）：

| reason_code | 闸门 | 界面徽章（短标签） |
|---|---|---|
| `aggregate_initialization_provider_needs_verification` | ① provider 选择门（装了但没核验能力证据） | **需先核验 provider** |
| `aggregate_initialization_trust_waiting` | ② trust 门（还没拿到这台机器的信任/登录） | **需先完成信任确认** |

- 徽章挂在停止原因首行尾部（`lc-bootstrap-advance-stop-gate`），两个码**一眼可区分**。
- 只给**短标签**（不重复通知里「怎么做：…」整段文案）；详细做法仍由后端成品文案承担。
- 步骤行仍显示「未开始」（后端语义：没开始 ≠ 失败），停止原因由本块与通知卡解释。
- 未登记的新码 → 不渲染徽章，只显示裸机器码（不崩、不猜）。

## 6. Concerns

1. **契约与任务书有一处出入（已按后端实际实现对齐，未改后端）**：任务书写
   `advance_stop.reason` 是「人话原因（中文成品文案）」，实际后端 `reason` 是**停止枚举字符串**
   （`waiting_for_human` / `failed` / `no_actionable_step` / `iteration_limit`，见
   `src/product/logical_codebase/bootstrap_advance_tests.inc.rs:720`）。前端因此把 `reason`
   走既有的 `ADVANCE_STOP_LABELS` 映射成中文（"等待人工处理"），中文成品三段仍由后端 summary 承担。
   若后端希望 `reason` 直接是中文文案，需要后端改，前端映射可删。
2. **同一信息在面板上重复出现**（后端把机器码与诊断塞进 summary 造成的既有形态）：
   - `reason_code` 出现 3 次（通知 summary 内「机器码：…」、通知卡的机器码次要行、本次新增块的机器码次要行）；
   - `detail` 出现 2 次（通知 summary 内「诊断：…」、新增块的诊断次要行）。

   本次选择「保留新增块的机器码+诊断次要行」，理由是通知 summary 里的那两段是**主段落**内的文本
   （不是次要行），而契约要求机器码与 detail「以次要行呈现」，且新增块独占**停止步骤**这一信息
   （通知卡不显示步骤名）。若 Main 认为界面太吵，最小回退是删掉新增块的机器码行
   （`lc-bootstrap-advance-stop-machine-line`），保留诊断行——单点删除即可，不影响其余断言。
3. **前端新增了一张稳定码 → 中文短标签表**（`ADVANCE_STOP_GATE_LABELS`）。后端将来加第三道
   闸门时这张表会缺项：表现为「不显示徽章、只显示裸机器码」（不崩、不误判），但区分度下降；
   建议后端加新码时同步通知前端补一行。
4. **advance 响应的 `stopped_detail` 只进了类型、没进 UI**：因为 advance 响应的
   `projection` 已带 `advance_stop`（后端 `finalize_advance_stop` 落盘后会**重投影**，见
   `bootstrap_advance.inc.rs:379-420`），机器码与诊断已由投影块呈现；「一键推进」按钮旁的
   `advanceSummary` 未重复加码。若 Main 希望按钮旁也直接看到原始 detail，可再加一行（未做，避免重复）。
5. **`detail` 始终展开显示**：provider 选择门的候选表 JSON 在里面，折叠即不可见；若版面吃紧，
   可改成与 `BootstrapFailureLine` 一致的 `<details>` 折叠区（需同步调整断言）。
6. **未改后端、未改 spec/tasks 勾选框、未做任何 git 操作**；`web/src/api/logical-codebase-bootstrap.ts`
   因响应形状由 `api/types` 描述而**无需修改**（已在第 1 节说明）。

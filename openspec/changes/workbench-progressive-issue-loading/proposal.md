# Proposal: workbench-progressive-issue-loading

> 本 change 补记 PR #90 / #91 已落地的「工作台先列表后详情」行为，并把首屏优化过程中被验证出来的功能契约固化下来。已有实现（`web/src/components/lifecycle/**`）保持不变，本次只补契约与后续缺陷修复的验收边界。

## Why

PR #90 把工作台从「等全部生命周期响应齐了再渲染」改成「议题列表先出、详情分批读取」。这带来两个此前不存在的界面状态：**详情尚未到达的议题**与**详情读取失败的议题**。这两个状态落在既有规格 `lifecycle-workbench-pipeline-ux` 没有覆盖的空隙上，于是出现了两类用户可见缺陷：

1. **列表行的能力被临时抹掉。** 规格要求每行显示四阶段 mini-graph，且悬停时「生成 Story Spec」与「删除」可用。详情未到时行没有阶段图、也没有操作入口，用户看到的是「这些议题还没有阶段信息」，而不是「还没加载完」。
2. **故障面不可见。** 深链指向的产物详情读取失败时，抽屉打不开且页面没有任何提示；项目元数据读取先失败时，议题列表还在加载，队列却显示「没有匹配的 Issue」，用户会以为项目是空的。

复审另外确认了三个与首屏优化同源的缺陷：旧项目的详情请求占满读取槽位导致新项目详情永远发不出；分组迁移使键盘焦点落回 body；迟到删除回执打断当前项目的加载。这些都在 `web/src/components/lifecycle/**` 内修复，不触及后端、API、JSON 存储或 WebSocket。

## What Changes

- **待查看态的阶段图与删除入口**：详情未到达的议题仍显示四阶段 mini-graph（未知态），并保留「删除」入口。「生成 Story Spec」在详情到达前不可用——该动作的幂等性依赖已知该议题是否已有 Story，未知时不得放行。
- **加载态与空态分离**：议题列表仍在读取时，队列显示加载提示，不得显示「没有匹配的 Issue」。
- **深链失败的可见反馈**：深链目标自身的详情读取失败时，页面在入口处给出可读的中文提示，不得静默。
- **读取槽位按批次隔离**：切换项目或刷新后，新批次的详情读取不得被上一批次的在途请求阻塞。
- **焦点保持**：议题行在「待查看」与正式阶段分组之间迁移时，键盘焦点保持在同一行。
- **迟到回执不打断当前作用域**：旧项目的删除或刷新回执不得切走当前项目，也不得使当前项目的加载失效。

### 接受面的明确改变

- 「生成 Story Spec」按钮的可见时机从「列表到达即有」改为「该议题详情到达后有」。这是**有意的可用性收窄**：重复生成 Story 的风险大于等待成本。
- 待查看态的行不再按阶段分组，集中在末尾的「生命周期待查看」分组；分组顺序在规格中登记。

## Capabilities

### New Capabilities

- 无。

### Modified Capabilities

- `lifecycle-workbench-pipeline-ux`：**MODIFIED**「紧凑 Issue 队列与阶段 mini-graph」（待查看态的阶段图与操作入口）、「队列滚动边界与渲染上限」（待查看分组的渲染上限）、「既有契约兼容」（加载态与深链失败面）。

## Non-Goals

- 不改后端、API 路径、请求参数、响应类型、WebSocket 协议与 JSON 存储格式。
- 不改首屏提速的取数架构本身（列表先行、详情分批、有界并发）。
- 不为「生成 Story Spec」在详情未知时提供放行或猜测。
- 不修 WIG 分支的旧会话兼容问题（属部署分支切换，独立处理）。
- 不引入真实 Provider 端到端回归以外的任何新业务流程。

## Impact

- 影响范围限于 `web/src/components/lifecycle/**` 的队列渲染、详情读取调度与错误呈现。
- 既有测试（`IssueLifecycleWorkbench.*.test.tsx`、`IssueQueue.test.tsx` 等）继续作为回归基线；本次新增用例覆盖待查看态、加载态、深链失败、槽位隔离与焦点保持。

# 设计：工作台渐进加载的界面状态与读取调度

> 权威来源：`openspec/changes/workbench-progressive-issue-loading/proposal.md` 与 `specs/lifecycle-workbench-pipeline-ux/spec.md`。本文件记录实现边界与取舍，不重复契约。

## 一、界面状态模型

工作台的议题数据有两级：**列表级**（`listProductIssues` 返回的 Issue 摘要）与**详情级**（`getIssueLifecycle` 返回的产物投影）。首屏优化后二者解耦，于是每个 Issue 处于两轴之一：

| 轴 | 状态 | 界面表现 |
|---|---|---|
| 列表 | 未到达 | 队列显示加载提示，不显示空态 |
| 详情 | 未到达 | 该行在「生命周期待查看」分组，阶段图未知态 |
| 详情 | 失败 | 该行保持待查看态，详情区给出错误提示 |

「生命周期待查看」分组是**过渡态**，不是长期分类：详情到达后该行迁入阶段分组并获得完整操作入口。

## 二、待查看态的阶段图

既有 `StagePipState` 只有 `done | active | blocked | pending`，其中 `pending` 的语义是「待开始」——已知该阶段没做。详情未知时我们不知道该阶段做没做，因此**复用 `pending` 会说谎**。本次扩展 `StagePipState` 增加 `unknown`，渲染为中性灰点并配「未知」文案。既有四个状态的判定规则与配色不变。

「生成 Story Spec」在待查看态不可用：动作幂等性依赖「该议题是否已有 Story」，未知时放行会重复生成。**删除**不依赖详情，待查看态仍可用。

## 三、读取调度的批次隔离

`useWorkbenchLifecycleDetails` 以 `DetailBatch` 为单位持有：项目 ID、议题集合、待读集合、失效集合、每议题修订号、**在途计数**。

在途计数放在批次内而非 hook 级 ref：批次是「切换项目 / 刷新」的自然边界，新批次必须立刻拥有自己的完整预算。上一批次的迟到响应仍被既有的批次身份 + 每议题修订号守卫丢弃。

**取舍**：跨批次的总在途数可能超过 3（旧批次的残余请求各自持有预算直到结束）。接受该上限，因为旧批次请求本身已是服务端事实、无法取消；强行取消需要引入 `AbortController` 并改动 `requestJson`，超出本次范围。真正要防的是**新批次被旧批次饿死**，那已修掉。

## 四、错误面的归属

详情读取失败有三种去向：

1. **当前聚焦议题**：详情区显示错误（既有 `issueDetailError`）。
2. **深链目标**：目标不在当前聚焦议题上时，既有错误面不覆盖它。新增「深链目标读取失败」提示，挂在详情区顶部，指向具体目标。
3. **后台其它议题**：不弹错误——用户没在看它。它只在被选中时通过第 1 条显示。

**不把后台失败写进全局横幅**：那会让一次无关失败覆盖用户刚看到的操作错误（PR #91 已修过一次同类问题）。

## 五、焦点保持

行在分组间迁移意味着 React 卸载旧节点、挂载新节点，焦点随之丢失。做法：在队列容器记录「当前聚焦的 issueId」，迁移后用同一标识重新聚焦该行的标题按钮。**不依赖 React key 跨父节点保留**——key 只在同一父节点内有意义。

## 六、验证方式

浏览器实测（隔离 fixture + 真后端 + 受控 HTTP 时序）为主，单测覆盖时序分支。浏览器验证的是「用户看到什么」，单测覆盖的是「哪条状态写入被拒绝」。

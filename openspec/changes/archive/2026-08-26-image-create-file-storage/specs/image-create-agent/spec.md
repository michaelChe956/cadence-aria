## MODIFIED Requirements

### Requirement: 生成结果按媒体类型直接展示

系统 SHALL 将 image2 网关返回的单张 `b64_json` 解码后按其 `output_format` 对应的媒体类型持久化为图片文件（`.aria/image_create/images/` 下，稳定 `image_id` 命名），会话历史中的生成结果 SHALL 只保存图片引用（`image_id` 与 `media_type`）而不内联 base64 字节。前端 SHALL 通过图片读取端点按 URL 懒加载展示，SHALL NOT 依赖会话记录 API 返回图片字节，SHALL NOT 固定为某一种图片格式。系统 SHALL 将生成结果（含所用 prompt 与参数及图片引用）纳入该会话历史供回看。

#### Scenario: 按输出格式构造数据 URI

- **WHEN** image2 网关返回 `b64_json` 且本次 `output_format` 为 webp
- **THEN** 系统以 webp 媒体类型将图片字节写入 images 目录，会话历史记录 `image_id` 与 `media_type`，前端经图片端点按 URL 以 webp 媒体类型渲染该图片

#### Scenario: 打开会话不传输图片字节

- **WHEN** 用户打开一个含多张历史生成图片的会话
- **THEN** 会话记录 API 响应不包含任何图片二进制或 base64 内容，前端按需逐张加载图片

#### Scenario: 结果纳入会话历史

- **WHEN** 一次图片生成完成
- **THEN** 该结果与对应 prompt、参数及图片引用一并记录进会话历史，用户可在会话中回看

#### Scenario: 图片文件缺失时的可读错误

- **WHEN** 会话历史中的图片引用对应的图片文件在磁盘上缺失
- **THEN** 图片读取端点返回明确错误（非 2xx），前端在该图片位置展示可读的缺失提示，不影响会话其余内容的加载

### Requirement: 会话生命周期与资源清理

系统 SHALL 为每个会话维护独立的执行器 scratch 目录。系统 SHALL 将会话删除实现为线性化操作：先将会话原子标记为删除中（tombstone）并拒绝该会话任何新请求，再取消进行中的执行器 run 与图片生成请求，并在确认这些在途任务已终止（或以其会话 generation token 对完成写入做条件校验）后才删除 scratch 目录、该会话的图片文件与持久化记录。会话删除后，任何在途异步完成（生成成功/失败、迭代输出）SHALL NOT 重建会话历史、scratch 或会话记录。会话删除 SHALL 失败时不静默吞错，SHALL 向用户报告失败。

#### Scenario: 删除空闲会话清理资源

- **WHEN** 用户删除一个无进行中操作的会话
- **THEN** 系统删除其 scratch 目录、其生成图片文件与持久化记录，且其不再出现在会话列表

#### Scenario: 删除运行中的会话先终止操作并等待

- **WHEN** 用户删除一个存在进行中 prompt 迭代或图片生成的会话
- **THEN** 系统先将该会话标记为删除中并拒绝新请求，取消进行中操作，待其在途任务终止确认后再执行删除与资源清理

#### Scenario: 删除后异步完成不回写

- **WHEN** 一个已被删除会话的在途生成或迭代在删除后才完成
- **THEN** 系统不将其成功/失败结果或输出写回，不重建该会话的历史、scratch 或记录

#### Scenario: 会话不存在的请求

- **WHEN** 客户端对已删除或不存在的会话发起请求
- **THEN** 系统返回明确「会话不存在」结果，不创建副作用

## ADDED Requirements

### Requirement: 生成图片崩溃一致写入与旧数据迁移

系统 SHALL 保证生成结果的落盘顺序为先写图片文件成功、再更新会话记录引用。图片文件写入失败时，系统 SHALL NOT 写入任何会话引用，SHALL 按既有失败边界记录失败事件并向用户暴露可读错误。会话引用更新失败时，系统 SHALL 仅以进程内待重试状态保留该结果（遵循既有持久化失败边界），SHALL NOT 丢弃已写入的图片文件。对会话中「引用存在但图片文件缺失」的结果，系统 SHALL 以可读错误暴露，SHALL NOT 静默接受为正常数据。对升级前已内联 `b64` 的旧会话记录，系统 SHALL 保持兼容读取并 SHALL 在首次访问该会话时将旧图片迁移为文件存储形态；迁移过程 SHALL NOT 丢失或篡改图片内容，迁移失败时 SHALL 保留原 `b64` 数据并可重试。

#### Scenario: 生成落盘顺序与失败暴露

- **WHEN** 一次生成成功且图片文件写入成功但会话记录更新失败
- **THEN** 系统按既有持久化失败边界向用户暴露错误并保留进程内待重试状态，不产生引用与文件不一致的静默状态

#### Scenario: 图片文件写入失败记录失败事件

- **WHEN** 一次生成成功但图片文件写入磁盘失败
- **THEN** 系统不写入会话引用，按既有失败边界记录失败事件并向用户展示可读错误

#### Scenario: 旧会话首次访问自动迁移

- **WHEN** 用户打开一个 `generation_results` 仍内联 `b64` 的旧会话
- **THEN** 系统将旧图片字节迁移写入 images 目录并把会话记录更新为引用形态，图片内容不变，此后会话记录不再内联 base64

#### Scenario: 迁移失败保留原数据

- **WHEN** 旧会话迁移过程中写盘失败
- **THEN** 系统保留原 `b64` 数据不丢失，会话仍可按旧形态展示，后续访问可重试迁移

### Requirement: 图片读取端点与会话隔离

系统 SHALL 提供按会话与 `image_id` 读取图片二进制的 HTTP 端点，响应 SHALL 携带正确的 `Content-Type` 与支持浏览器缓存的强校验头；端点 SHALL 校验 `image_id` 归属该会话，SHALL NOT 允许路径穿越或访问其他会话的图片。

#### Scenario: 按引用读取图片

- **WHEN** 前端以合法会话 id 与该会话内的 `image_id` 请求图片端点
- **THEN** 系统返回对应图片字节与正确 `Content-Type`

#### Scenario: 跨会话访问被拒绝

- **WHEN** 客户端以会话 A 的 id 请求属于会话 B 的 `image_id`
- **THEN** 系统返回明确错误，不返回图片内容

#### Scenario: 非法 image_id 不触碰文件系统之外的路径

- **WHEN** 客户端传入包含路径分隔符或 `..` 的 `image_id`
- **THEN** 系统返回明确错误，不读取 images 目录之外的任何文件

#### Scenario: 未迁移旧图经端点实时解码返回

- **WHEN** 会话中一条旧记录尚未完成文件迁移（仍内联 `b64`）且前端请求其图片
- **THEN** 图片端点解码该 `b64` 返回图片字节，迁移成功后同一引用切换为读取文件

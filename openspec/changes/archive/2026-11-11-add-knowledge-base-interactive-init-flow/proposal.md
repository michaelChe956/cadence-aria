# 知识库初始化：交互式两段流程（起草 → 补充 → 确认 → 建库）

## Why

两段式输入草稿的**后端契约**已落地（起草 / 确认记录 / 建库分叉），但**交互链断在起草完成那一刻**：

真机走查（2026-11-11，LC `kb-test-lc`，Pi provider）复现的事实：

- 起草 operation 正常完成，9 份 `user-input/` 全部生成（`api-scope.md` / `base-info.md` / … / `project-scope.md`）；
- 界面停在卡片上的「知识库 / completed / 知识库操作已完成 / prepare_user_input / 本次使用 Pi」——
  **没有任何下一步入口**：用户不知道「该去补充这 9 份文件」，也不知道「确认后怎么建库」；
- 详情页的输入确认区只有一行计数提示（已确认 0/9），没有操作引导；
- 逐份「确认」只写确认记录，**建库仍需回卡片再点一次【知识库初始化】**——用户视角是「确认完还要再点一次 mysteriously 才会建库」；
- 建库完成后也不会落到详情页，用户无法在同处继续改知识库文档。

结果：用户完成了一次 provider 调用，却停在「操作已完成」的死角上，两段式流程的后半段（补充 → 确认 → 建库）实际走不通。

## What Changes

把「起草完成」到「知识库建好」这一段补成**可交互的闭环**（纯前端交互层 + 既有后端契约复用）：

1. **起草完成 ⇒ 打开输入文件**：卡片出现【打开输入文件并补充】入口；起草刚完成时自动进入知识库详情页并打开第一份待确认的 `user-input` 文件（右侧可写编辑器，与【查看知识库详细内容】同一形态）。
2. **引导**：详情页输入确认区给出四步操作指引（逐份核对补充 → 改完点确认 → 全部确认 → 执行初始化）、确认进度、以及「还有 N 份未填」的阻塞说明。
3. **确认即建库**：输入确认区新增【确认并初始化】——先批量确认全部待确认文件，随即执行 `/knowledge-base-bootstrap`（不再要求用户回卡片再点一次）。
4. **建库后落回详情页**：bootstrap 运行中显示进度，完成后刷新文件树与状态投影并给出「知识库已生成，可继续编辑」的提示；知识库文档以用户自己的修改为准。

## Non-goals

- 不改后端两段式契约：起草 / 确认记录 / 建库分叉（未准备 ⇒ 起草；未全部确认 ⇒ 422；已确认 ⇒ bootstrap）**逐字不动**。
- 不放宽「9 份必须全部已填写且已确认才允许建库」的后端口径（未填文件只做引导，不改成「已填写的都算」）。
- 不做知识库文档的自动格式化/自动合并（bootstrap 产物只是起点，最终以用户修改为准，这一条是既有语义，本变更只是把它讲清楚）。
- 不改变更包（`/knowledge-base-update`）链路。
